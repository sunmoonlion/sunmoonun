## 规划、冻结和撤销的对照样例

1. **两个独立终点。** 同一个两方法目录，要求“用我给的两份独立输入，分别交回标准明细和费用核对回执，两份分开交”。手工构造的两步平图经 KnowBench 的 read_choice 与 compile_choice 生成 detail、check 两个导出，无需第三种方法。对同样的需求，两端 HierarchicalPlanner 的 parallel_join 必须把每个子目标绑定到真实父方法的输入；两个独立终点无法这样表达。把第一步单独交给规划器，两端均回 ready，只有 detail。复现覆盖宿主决策校验和编译，未测真实模型选错的频率。设计要让每项需交付的成果都有可编译来源，结案前逐项核对。业务要求另写综合报告时，仍需能编制报告的方法。
2. **同一原稿的适用范围。** 原稿写“只对同币种原行”“排除预测”。KnowLab 的直接指令构造函数把适用场景改为模板目标“核对金额”，排除场景为空。将原 scope、模板和生成的方法一并交 WorkdraftBody 验证通过。组合方法已有传入原 scope 的分支。两个来源都需要对照同一份作者审定的声明。该样例只到草稿验证。
3. **资料订阅取消后重试。** KnowFeed 的 change 与 end_items 分属两个数据库事务。用真实 cancel 服务方法和存储替身令第一次清理在途需求失败，再以已存 cancelled 状态重试。第二次调用返回成功，两次请求累计只尝试清理一次。KnowBase 的撤回又是逐个修订操作，续订与撤回并发还需补双端事务验证。此处未操作真实订阅。

自动检查另列于[语法检查汇总](syntax.tsv)。Python、TypeScript 系列及 Shell 共 3,810 份源码通过解析，另检查了 496 份 JSON、SVG 与 TOML。语法检查没有占用已读行段。

可在本工位复跑两个独立交付的样例，使用 KnowBench 后端的测试环境执行本目录的 [verify_planner.py](verify_planner.py)。两个入口共用精确版本，方法目录与步骤来自合成用例。已有 KnowBench 递归规划与即时计划图回归 49 项通过，KnowLab 作者选型与交付模板回归 14 项通过。上述独立双终点在这 63 项外另测。

## 从自然语言到可采用的草图

- 以“请核对这份清单，只查一次。不要无限重试。”进入 KnowBench 的临时规划启动服务。宿主将“无限重试”识别成用户要求，写入 `unsupported_capability` 回执，目录查询为 0 次。输入解析、门禁和回执均运行原代码，存储与已核验的前序匹配结论使用替身。这个样例没有模型费用。后续方案需要区分用户要求、用户禁止和显式勾选的执行条件。
- 用同一份明细作两个核验方法的共享输入，第三个方法接收两份结果。两份输入只在槽位说明上有差异，规划器接受显式共享并返回 ready，采用时正式定义却要求整个槽位字典一致。将文字改为相同，原图编译成功。两组均使用与定义内容对应的版本摘要。需要明确哪些字段影响业务相容性，以及对必填和缺失处理有差异时如何向作者解释。以上两项也可运行本目录的 verify_planner.py 重现。

KnowLab 的定义、编译、规划、准入、执行、草图共六份后端模块由源码导出至 KnowBench。已读提供方全文，人工逐行核对消费方与提供方的全部差异，并执行导出器的 `--check`。在该基线上，六份差异限于生成标记和导入。行段登记明确标明了这种对照读法。另跑 KnowLab 定义、固定计划、递归展开、候选分派回归 82 项，KnowMart 专家目录回归 17 项，均通过。

## 从申请选方法到回炉

普通申请页的 IdeaMethodChooser 用 MethodVersionBrowser，走 `/method-units` 默认分支。设计页的 ExpertFromTool 使用同一路径的 `formal=true` 分支及单独的共享工具接口。服务端分别交给作者方法服务与正式方法服务。两个选择器的分页、版本读取和可绑定对象都不同。因此，在正式方法页看到一个工具，还不能据此断言它一定会出现在普通申请的选项里。此项核到了两套前后端调用路径，未查询用户账号。

即时计划转回孵化时，KnowBench 从已保存计划取出草图摘要、方法引用和输出名，经 FormalHandoff 交给 KnowLab。申请页再把方法编号、版本和输出名列给作者。这个往返保留来源，已有分支条件、输入连线和逐项交付关系没有进入附件。对需要“沿用这张图、只修改一处”的回炉场景，后续设计须明确哪些草图内容可以交接，接收方采用时怎样重新核权。

运行 [coverage.py](coverage.py) 可按组件核对人工记录的行数，去重总数按 Git blob 内行段的并集计算。

把进度观测、签名 HTTP 采样、定时投递、时钟回拨用例纳入后，隔离库共 50 项通过。B37 的同一消息在采样中显示已确认 1、未完成 0、死信 1。人工重放又发布一次，消费者借原业务回执跳过，业务计数仍为 1。B38 的消息则从未开始业务处理；仅据死信数无法区分两种结果。prefork 用例本轮逐行审读，未计入 50 项。

扩查出队前数据契约后，加入 NaN 和正负无穷三例，合计 53 项通过。B39 只证实传输对象的校验与实际存储约束不一致，尚未确认某一项生产业务会生成这些值。

## 运营如何改稿和预检

沿 KnowLab 管理端入口审到工作稿、提议差异、步骤字段及校验模板，另核了服务端发布时的重新编译。运营原有组件用例 2 项和[本次补充的 4 项](verify_operator_preview.test.tsx)共同通过。组件用例以测试接口提供数据，未在共享环境出版本。统一编辑流程需有修订号、未提交修改及同修订的预检结果，输出改名还应能定位关联的交付检查。
