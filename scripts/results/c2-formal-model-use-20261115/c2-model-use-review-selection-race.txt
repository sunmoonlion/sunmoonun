Scope: FormalMethodCalls._check_model vs Capabilities.save_selection.

Reproduction used the real _check_model method with an async in-memory repository.
capability_selection returned a deepcopy of revision 1, including the exact selected
formal method and matching applied runtime token, scope and accepted user turn.
FormalSessionTools.resolve was patched to simulate a concurrent selection commit:
revision became 2 and detail.formal_methods became [], then it returned the same
unchanged current method/source spec. The verified observed invocation remained
unchanged. No database or external operation was used.

Original process output:
{'check': 'accepted', 'committed_selection_revision': 2, 'formal_methods': [], 'selection_reads': 1}

Feasible database interleaving before fix:
A: approval owns session/child locks and reads selection revision 1 without lock.
B: save_selection owns selection/assets locks, reads session without FOR UPDATE,
   clears formal_methods, increments revision to 2, commits successfully.
A: current source resolution resumes after asset lock, unchanged source/spec and
   invocation match, approval can consume and dispatch using the old model scope.

Recommendation: serialize scope updates and formal request/approval on a uniform
session -> selection -> assets lock order; verify stale read placement as well as
lock acquisition order. Parent accepted and assigned runtime locking fix plus a
real database concurrency regression. This reproduction is an internal self-check,
not an independent formal approval or proof of a passing end-to-end execution.
