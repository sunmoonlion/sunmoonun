## 一、一句话

**连接器是让 Agent 用上外部服务的接口**：比如读邮件、查日历、翻网盘、改在线文档、查项目管理系统。没有连接器，Agent 只能用它自己手边的东西（对话、上传的文件、它电脑上的文件）；有了连接器，它能替用户去别的系统里取东西、办事。

现在几家的连接器，底下基本都是 **MCP**（模型上下文协议）：外部服务提供一个 MCP 服务，里面列出一组"工具"（比如"搜邮件""读这封邮件""发邮件"），Agent 按需调用。要登录的服务，用 **OAuth** 让用户授权，Agent 拿到一张有范围、有期限的令牌去调。

## 二、几个词

| 词 | 指什么 |
| --- | --- |
| **MCP** | 模型上下文协议，Agent 和外部服务之间约定的一种说话方式。现在各家通用 |
| **MCP 服务** | 外部服务按 MCP 提供的那一端，比如"某邮箱的 MCP 服务" |
| **工具** | MCP 服务里列出的一个个能做的事，每个有名字、说明、参数 |
| **远程 MCP / 本地 MCP** | 远程的跑在对方的服务器上，经网络调（HTTP）；本地的跑在用户自己电脑上，作为一个程序起起来（stdio） |
| **OAuth** | 一种授权办法：用户在对方的登录页上点"允许"，对方发一张令牌给我们，我们凭令牌去调；用户的密码不经我们的手 |
| **令牌** | 对方发的通行证，有**范围**（能做哪些事，比如只读邮件、不能发）和**期限**；过期了用**刷新令牌**换新的 |
| **授权范围（scope）** | 令牌准许做的事。原则是**只要刚好够用的** |
| **连接器包** | 有的产品把"MCP 服务地址 + 鉴权方式 + 使用说明（技能）"打成一个包，在市场里上架，用户点"连接"就能用 |

## 三、连接器在 Agent 里是怎么转起来的

```text
用户：帮我把上周客户的邮件整理一下
  ↓
Agent（模型）看到手里有"邮箱"连接器的几个工具，决定调「搜邮件」
  ↓
平台：核这次调用准不准（用户接过这个连接器吗？这段对话里允许用吗？这是只读还是会改东西？）
  ↓  准
平台带着用户的令牌，去调对方的 MCP 服务
  ↓
对方返回结果（几封邮件）
  ↓
平台把结果交给模型；要是下一步是「发邮件」这种会改东西的，先停下来问用户
```

关键点：**模型只决定调哪个工具、传什么参数；令牌在平台手里，模型看不到**。准不准调、要不要先问用户，是平台按规则判断，不是模型自己说了算。

## 四、市面上怎么做

| 产品 | 怎么做 |
| --- | --- |
| **OpenAI**（ChatGPT、Codex） | 叫"插件"：一个插件能装技能、MCP 服务、浏览器扩展、钩子。装好后连上它的 MCP 服务，用的是对方自己的鉴权和权限；"用 ChatGPT 登录"只共享姓名、邮箱、头像，"不授予插件访问你数据的权限，也不自动批准动作"。会改东西的动作先问，比如发消息默认要用户批准内容和收件人，可选"这次允许"或"对这个会话一直允许"。工作区管理员管公司账号和谁能用。开发者能自己写 MCP 服务打成插件，公开上架要过审核 |
| **xAI**（Grok） | 内置 Gmail、Google 日历、Google Drive、OneDrive、Outlook、Teams、SharePoint、Salesforce 等，都是 OAuth 一次登录；连上以后问到相关的才去取。Outlook 申请的权限是读写邮件、发邮件、读个人资料、离线访问，是**委托权限，只能访问登录者本人的邮箱**。还能接自定义 MCP，要能从公网访问 |
| **腾讯 WorkBuddy** | 连接器是"扩展能力接口"，让第三方应用接进来；接法二选一：**MCP + 技能**，或 **命令行工具 + 技能**。鉴权三种：**云端托管的 OAuth（推荐）**——"授权与凭证由 WorkBuddy 云端托管，端侧不持有第三方 token"；用户自填 API Key（存本机）；不用认证。开发者打包、自查、提交审核、上架到连接器市场；规定不许硬编码密钥、只申请最小权限、远程地址用 HTTPS、日志里不输出完整凭证。项目里还分公共授权（大家共用一个账号）和个人授权（凭据只存本地，协作任务里用不了） |
| **腾讯 WMA** | "MCP、OAuth 等连接器开箱即用"，平台统一管连接器的版本与授权 |
| **Meta Muse** | 用户选接哪些应用、给多少权限：邮件可以选"只读"或"也能代发"；登录信息存在 Muse 看不到的凭据库里 |

**共同的做法**：
1. 底下用 MCP；
2. 要登录的用 OAuth，**令牌在平台手里，不给模型**；
3. 权限分读和写，**写的、发的先问用户**；
4. 只申请刚好够用的权限；
5. 连了能断，断了令牌作废。

## 五、MCP 规范对授权的要求（要点）

MCP 规范里授权是可选的；做的话，远程（HTTP）的要照这套来，本地（stdio）的不走这套，凭据从本机环境取。要点：

- **角色**：要登录的 MCP 服务是"资源服务器"；我们调它，是"客户端"；发令牌的是对方的"授权服务器"。
- **流程**：调了没令牌，对方回 401 并告诉我们去哪找它的授权服务器 → 我们找到授权服务器 → 打开浏览器让用户登录、点允许（用 **PKCE** 防截获）→ 拿回授权码换令牌 → 每次请求都在请求头里带上令牌。
- **令牌要绑死在一个服务上**：申请令牌时必须写明"给哪个 MCP 服务用"（RFC 8707 的 `resource` 参数）；对方只收发给它自己的令牌。
- **不许转交**："MCP 服务器不得接受或转交别的令牌"——不能拿用户给 A 的令牌去调 B。
- **令牌不进网址**：只能放在请求头里。
- **权限从小到大**：先按对方给的最小范围申请；用到更多权限时对方回 403 并说明还要什么，再让用户补授权。
- **刷新令牌要保密**：存储和传输都要保密；对方不一定给刷新令牌，不能假设有。
- **要防的攻击**：令牌被盗、冒用（混淆代理人）、开放重定向、授权码被截。

这些照着做，就不用我们自己发明一套。

**登录的到底是谁**（所有者 11-10 问：「登录的到底是mcp服务还是mcp服务去调用的比如邮件服务」）：用户登录、点"允许"的，是**邮件服务的账号**——浏览器打开的是邮件服务（或它指定的授权服务器）的登录页，平台和任何 MCP 服务都碰不到用户的密码。登录换来的令牌，由平台后端替用户保管。

**本方案新增的受管外部连接器通过平台 MCP 提供给模型**（所有者 11-10 指正：「我们的用户使用的都是平台的mcp服务，平台的mcp服务是否使用第三方mcp还是直接使用第三方服务」）：Codex 根据模型请求调用工作台工具，平台后端执行外部请求；此范围不排除第六节已有的不带凭据本机 MCP。平台背后再分两种接法：

| | 平台 MCP 背后怎么接 | 令牌在谁手里 | 特点 |
| --- | --- | --- | --- |
| **甲：转接第三方的 MCP 服务** | 平台 →（给它的令牌）→ 第三方 MCP 服务 → 邮件服务 | 平台握着给那个 MCP 服务的令牌；那个 MCP 服务要是第三方包装的，它自己还握着一张用户邮箱的令牌 | 通用：现成的 MCP 服务都能接，每家几乎不用写代码；但工具长什么样、权限多大、可不可靠，取决于对方 |
| **乙：平台直接调第三方服务** | 平台 →（邮箱令牌）→ 邮件服务的接口 | 只有平台握着一张邮箱令牌，中间没有别人 | 每家要我们自己写一层适配，算资源；但工具由我们定义，权限能收到最小，留痕、出错处理统一；xAI、WorkBuddy 的内置连接器是这种 |

规范规定 MCP 服务"不得接受或转交别的令牌"：每张令牌只给对应的那个服务用。甲里平台不能把用户邮箱的令牌塞给第三方 MCP 服务原样转发。

**建议两种都留**：常用的几家（邮箱、日历、网盘）走乙，平台自己写适配，最稳、最可控；其余的走甲，用户接现成的 MCP 服务。走甲时要写明这个 MCP 服务是谁提供的、它背后会不会替用户握着别的令牌——第三方包装的，等于用户把邮箱交给了它。不管哪种，放行判断、要不要先问用户、留痕，都在平台这一层做。

## 六、我们现在已经有的几种"连接"

| 我们有的 | 是什么 | 是不是连接器 |
| --- | --- | --- |
| **数据 MCP** | knowbench 工作台给沙箱里的模型一组工具（查主体、提数据、读数据……），后端凭运行授权去 knowbase 取（[SDD 0048](../design/SDD/modules/0048-model-data-tools.md)） | 是，我们自己的、平台提供的连接器 |
| **用户自己的 HTTP MCP** | 用户在自己电脑上确认后，经 link 接进来给模型用（`sunmoon-link/agent/src/mcp.ts`） | 是，但**只接不带凭据的**：地址里不能有用户名密码和查询串，也不能带请求头，所以要登录的服务接不了 |
| **knowfeed 的渠道**（巨潮、Wind） | 平台按需求去外部取数据，取回来入库（[数据拓扑](数据拓扑.md) 第七节） | **不是**：这是平台的供给链，取的是公开披露或平台有授权的数据，入库成真源；连接器取的是用户自己账号里的东西，只给这一次用 |
| **link** | 把用户电脑接到云端，让专家在用户的项目目录里干活 | 不算：它是执行端，不是某个外部服务 |
| **A2A 外部 Agent**（已定、没做） | 调别家的 Agent 办一部分事（第七节「调用外部 Agent」） | 不是同一个东西，但和要登录的连接器**共用一套凭据和放行机制** |

**主要缺口是受管外部连接器及其完整接入链。** 2026-11-13 的 Jenkins #92 已发布 MCP、Skill 与会话能力三个基础入口，后续安装、方法步骤和包内脚本为待发布候选。已有 MCP 账号管理不等于邮箱、网盘、日历的完整连接器：OAuth 生命周期、业务操作和资源范围映射仍缺失，具体见 10.14。

## 七、要补成什么样（已定的方向）

11-09、11-10 所有者定；原《请专家与执行》第 5.10、5.11 节并入这里。

- **聊天、工作、各级方法都能用，同一套实现**：用户在「连接与工具」页接好账号，普通会话按选定范围使用；方法声明连接器操作要求，运行时绑定该用户已有连接。专家与子方法沿同一调用链收窄授权，不另接一份账号或复制凭据。需求和规则来源不同，选择、准备及核权复用同一机制。
- **用户出账号和钱**，和"模型费用都由用户出"（⑯）一致。
- **受管外部连接器由 knowbench 后端持有凭据并执行外部请求**：模型路径由沙箱 Codex 调平台 MCP，宿主直接调用复用后端执行模块；后端再按第五节甲、乙两种方式接外部服务。外部凭据沿用 Fernet 加密基础，**不进模型、沙箱、清单、日志**；这里限制的是外部认证和执行位置，不是说模型请求不经过沙箱中的 Codex。
- **取来的是用户自己的数据**：只作这段对话或这件委托的输入，带出处，不自动进 knowbase，不成为第二个真源。
- **写操作先问**：发邮件、改文件这类，对话里每次先给用户看，专家里走行为审批。
- **先做机制，用一家验通**；接哪几家服务（每家都要去对方那里注册应用、过审核）按资源排。
- link 上不带凭据的用户 MCP 照旧。

### 需要登录的连接器：各场景怎么用、凭据怎么放

**两处都能用**（11-10 所有者定 A2A「不一定是专家才能使用」，连接器同理）：

| | 用户自己的聊天、工作里 | 各级方法（包括专家） |
| --- | --- | --- |
| 谁接 | 用户在「连接与工具」页接上，设哪些对话里可用 | 作者声明连接器操作契约、允许的工具和必要的提供方限制，随版本冻结；运行时用户选择自己的已有连接，缺项仍到同一个设置入口补齐 |
| 什么时候调 | 模型按会话有效范围提出请求，宿主核权后执行 | 宿主直接调用或按步骤允许范围向模型提供工具，均核本次运行绑定 |
| 取来的东西 | 用户自己的数据，当这段对话里读到的资料，带出处；不自动进 knowbase | 用户自己的数据，当这件委托的输入资料存下，带出处（哪个服务、什么时候取的）；不自动进 knowbase |
| 写操作（发邮件、改文件这类） | 每次先给用户看要做什么，他点了才做 | 照专家的行为审批，有影响的动作先问用户 |

各场景的外部请求都由 knowbench 后端带着用户的令牌，通过适配器直接调用外部 API 或转接第三方 MCP；沙箱 Codex 可以发起平台工具请求，但不持有外部账号凭据，link 也不代管这些凭据。两种接法共用权限与审批检查。用户要长期留的数据，自己在 knowbase 上传或转为数据。

**共用的凭据机制**（一套，不做两套）：
- knowbench 设置统一使用「连接与工具」入口（本文旧称「连接」）：管理连接器和 MCP，展示账号、工具、状态、默认选择及哪些执行正在依赖它；会话另选本次范围，A2A 接通后复用此入口。具体页面、技能页和会话选择设计见接入实施方案第 11.2 节，不另建专家专用连接页。
- 凭据加密复用现在模型 Key 的 Fernet 基础，但按用途隔离，不进入模型凭据的默认选择或沙箱注入；外部连接另记账号、scope、有效期和撤销状态。只有支持且取得刷新令牌时才刷新；失效、断开与并发刷新按连接器方案处理，不能使已撤销连接复活。
- 凭据只在 knowbench 后端发调用时解出来用，**不进模型、不进沙箱、不进清单、不进日志**。
- 每次调用记一笔：哪段对话或哪件委托、哪个方法、调了谁、传出去什么、拿回来什么（只记编号和摘要）。

**跟现有规矩怎么对上**：
- "谁的数据谁挑"：接哪个服务、给哪段对话或哪件委托用，由用户定；专家的能力声明里写明"这一项要你自己有某某账号"。
- 定数据：专家里连接器取来的是用户自己的数据，取之前照样要这件委托用户确认过要用（和定数据一样停在步骤边界等确认），不能因为接上了就随便读；聊天、工作里用户本人在场，按需读。
- 数据拓扑"云端真源只有 knowbase"不变：连接器的数只作这段对话或这件委托的输入，不成为第二个真源。
- link 上用户自己接的、不带凭据的 HTTP MCP 照旧，这次不动。

**算资源、不在这次做的**：每接一家服务都要在对方那里注册 OAuth 应用、过对方的审核，接哪几家、先接哪家，按资源排。这次只做机制，用一家能注册的服务验通。

### 调用外部 Agent（A2A，11-09 所有者定）

所有者 11-09：「你能不能现在就把A2A实现了」，随后定了：**我们调外部 Agent**（对标 WMA 的"把外部 A2A Agent 绑定到指定 Agent"）；作者能把它绑进专家、随专家版本冻结；**并进专家方案一起做**（绑进专家要改清单格式，而清单格式正在这次方案里重新设计，一起做不返工；11-12 起「专家也是方法」，绑定写进方法六要素第二项「所需输入与权限」，随方法版本冻结）；账号和费用「用户出」。11-10 所有者又说：「关于a2a为何放在专家里，我觉得它不一定是专家才能使用吧」——**用户自己的聊天、工作里也能用**，不只专家。

**协议**（A2A 规范 1.0.0，已并入 Agentic AI Foundation）：对方公布一张 Agent Card（能做什么、技能、能力、鉴权方式），我们按它发消息、建任务（SendMessage、GetTask、CancelTask，可流式）；任务有提交、进行中、要输入、要授权、完成、失败、取消、拒绝几种状态，结果以成果（Artifact）交回；传法有 JSON-RPC、gRPC、REST 三种，鉴权支持 API key、HTTP、OAuth 2.0、OpenID Connect、mTLS，凭据在协议外取得。有官方 Python SDK。

**两处都能用**：

| | 用户自己的聊天、工作里 | 专家里 |
| --- | --- | --- |
| 谁接 | 用户在 knowbench 设置的「连接」页自己接 | 作者在 knowlab 工作稿里绑：哪个外部 Agent、名片摘要、准许调它的哪几项技能、哪些方法能调，随方法版本冻结；请专家的用户在「连接」页用自己的账号接上 |
| 什么时候调 | 用户自己的模型在对话里按需调，像用一个工具；用户能在「连接」页设哪些对话里可用 | 执行到绑了它的方法时，在准许的技能范围内才能调 |
| 交回的东西 | 当资料，回答里标"来自外部 Agent 某某" | 当资料，存成这一步的输入，由方法再核，不当验收过的结论 |
| 用户的数据传出去 | 用户本人在场：每次要传用户的数据时，先给他看传什么、传给谁，他点了才传（走现有的工具审批） | 在这件委托用户确认过的授权范围内，事先在能力声明里写明"会把哪类数据交给哪个外部 Agent" |

两处的调用都由 knowbench 后端发出：模型调的是工作台给的一个工具，后端带着用户的凭据去调外部 Agent，不从用户沙箱直连。

**两处是同一套实现**（所有者 11-10：「可以用同一套实现吧」）：A2A 客户端、「连接」页与凭据、给模型的工具、交回资料的存法、费用与取消、留痕都只有一套；只差放行规则从哪来——对话里看用户在「连接」页的设置、传数据和写操作每次问本人，委托里看这一版专家冻结的绑定和这件委托的授权。和现在的工具调用鉴权一样，是同一个判断按"对话还是委托"取不同的规则来源。需要登录的连接器（上面几条）也走这同一套。

**五条规矩**（两处都守）：
1. **交回的只当资料，不当验收过的结论**：外部 Agent 的数没有出处、没有计算收据；专家里由方法再核，成稿引用时标"来自外部 Agent 某某"，不算平台核过；聊天、工作里回答照实标来源。
2. **数据给出去要有依据**：聊天、工作里每次传之前用户点头；专家里在委托授权范围内、事先写进能力声明。每次传了什么、传给谁都留痕。
3. **钱记得清**：外部 Agent 的费用记进这件委托或这段对话的花费，实时显示、随时能停；停下时对它发取消。
4. **用户出账号和钱，凭据不进模型、不进清单**（11-09 所有者定「用户出」）：用的是用户自己的账号和密钥，费用记用户，和"模型费用都由用户出"（⑯）一致。用户在「连接」页接上（填密钥或走 OAuth 授权），凭据存在用户自己的私有配置里，模型看不到，和需要登录的连接器共用一套。清单里只记鉴权方式和名片摘要。
5. **用户没接上时**：聊天、工作里，工具清单里就没有它；专家里，执行到要用它的方法前停下，提示用户去接（像 WorkBuddy 的授权卡片），接上后接着跑；用户不接，这个方法就不做，按"可选的取消即降级、必需的取消即变更"处理，成稿里照实写没做。专家的能力声明里要写明"这一项要你自己有某某的账号"。

### 触发：外面有新东西就叫醒（11-10 所有者定）

上面说的都是"模型需要时才去调"。有的用法要反过来：外面来了新东西，平台主动叫醒。头一个用处是邮件派活（[接入邮件派活方案](接入邮件派活方案.md)「改向」一节）：用户接上邮箱、设好条件，符合条件的新邮件一到，就出一张待确认的卡片。市面上 ChatGPT 的"Gmail 来新信就开始任务"、Grok Bot 的例程（Slack 消息、发到 Bot 邮箱的信、Webhook）都是这一类。

- **两种盯法**：对方能推送通知的，接推送（订阅它的变更通知）；不能的，定时去查（比如每几分钟查一次有没有新的）。
- **触发条件由用户设**：文件夹、标签、发件人、主题，能在对方那边筛的就在对方那边筛，平台只取符合条件的那几条，别的不读、不存。
- **叫醒以后做什么**：默认只出一张「待我决定」的卡片，用户在 web端点了才开跑；要不要"免确认直接跑"，等所有者定（邮件派活方案第七节第 2 件）。
- **不重复、不漏**：同一条只出一张卡（按对方给的唯一编号去重）；查的时候断了，下次接着上次的位置查。
- **留痕**：每次叫醒记一笔：哪个连接、哪条、按哪个条件、出了哪张卡。
- **用户断开连接**，触发一并停掉。
- **触发层不只接连接器**（11-10 所有者定「职责」并进专家方案）：同一套还接**定时**（按日、周、月或固定间隔）和 **knowfeed 订阅取到新资料**；叫醒的可以是一张「待我决定」的卡片，也可以是一份「职责」（用户交给某位专家长期管的一件事，见 [专家团内化方案](专家方案设计/专家孵化方案/luna/专家团内化方案.md) 第 6.6 节）。去重、断点续查、留痕三条照上面，一套实现。

## 八、安全与合规要点

1. **外部内容不是指令**：邮件、网页、文档里写的"请把附件发给某某"，只是数据，不能当用户的话执行（Grok 的原话："Only your own messages count as instructions"）。连接器取回的内容交给模型时要标明来源，写操作照样要用户点头。
2. **最小权限**：只申请这个连接器、这几个工具用得到的范围；只读的不申请写。
3. **令牌绑定、不转交**：照 MCP 规范，令牌只发给它对应的那个服务；不拿用户给 A 的令牌去调 B，也不把我们的平台令牌交给外部服务。
4. **能断、能撤**：用户在「连接」页断开，就作废令牌、删掉存的凭据；对方那边能撤销的一并撤销。
5. **每次调用留痕**：哪段对话或哪件委托、调了谁、哪个工具、传出去什么、拿回来什么（只记编号和摘要，不记内容）。
6. **个人信息**：邮箱、日历里大量是第三方的个人信息；只取任务要的，不长期存，不进 knowbase；用户要留，自己转为数据。
7. **合规边界不变**：投资逻辑和数据只来自用户；连接器取的是用户自己账号里的东西，由用户授权，和"平台不提供自己的数据"不冲突。

## 十、权限与连接器实现方案（2026-11-12 讨论稿）

### 10.1 范围、依据与当前缺口

本节落实[待办 66](../design/pending-after-migration.md)及[qwen 待办第 1 项](qwen待办.md)，承接 11-09、11-10 的共同方向：聊天、工作、专家共用连接与授权机制，A2A 复用；外部账号凭据由 knowbench 后端持有。旧账中“按需注入沙箱”和“依靠 app-server OAuth 登录”的方案不再作为本轮实现路线。连接器服务可以直接调用外部 API，也可以转接第三方 MCP；不强迫所有服务都先提供 MCP。

方案的核心是：**方法声明所需权限，用户选择具体资源并授权本次用途，宿主核对每次调用，资源端保留最终访问检查。**连接成功、获得外部 scope、批准某次动作和结果通过验收是不同事实。

2026-11-12 只读核对的代码位置与边界如下，路径相对于相应后端 `app/` 或 link 仓；这是工作区事实，不代表线上版本已核验：

| 位置 | 可复用的基础 | 本方案需要补齐 |
| --- | --- | --- |
| knowbench `app/interfaces/endpoints/workbench_routes.py` 与 `app/infrastructure/workbench/repository.py` | 模型 Key 的 Fernet 加密、按所有者读取及撤销 | 外部连接身份、scope、令牌到期与刷新、独立用途及生命周期；不把外部凭据混入模型 Key 的默认选择和沙箱注入 |
| knowbench `app/application/workbench/method_tools.py` | 对部分现行方法调用核对任务、Attempt、turn 与观测到的工具请求 | 按连接、操作、资源范围核授权；宿主直接调用采用可信执行上下文，不伪造模型 turn |
| knowbench `app/application/workbench/data_relay.py` | 服务端绑定 knowbase 运行授权，拒绝模型自带授权引用替代 | 继续保持数据裁决边界；连接器不能获得替代 knowbase 授权的能力 |
| knowbench `app/domain/workbench/tool_policy.py`、`app/application/workbench/runner.py` | allow/ask/deny、任务内批准、Interaction 与等待恢复 | 外部动作预览和结构化范围匹配；命令前缀批准不能用于邮件发送或网盘写入 |
| runner `_on_elicitation` | 旧可信 MCP 表单按默认值自动接受，URL 模式拒绝 | 第三方询问必须按来源路由，不能自动接受；授权跳转与普通问题分开 |
| `sunmoon-link/agent/src/mcp.ts` | 用户确认的不带凭据 HTTP MCP 配置 | 保留现有路径；不借此传第三方 token，不把连接器建设变为 link 凭据同步 |

### 10.2 架构归属与调用路径

| 责任方 | 本方案职责 | 保持的边界 |
| --- | --- | --- |
| knowlab | 编辑、校验方法权限要求与审批规则，随方法版本冻结 | 不保存使用者的连接或 token；作者只能声明需要，不能替使用者授权 |
| knowmart | 展示必要连接条件，交付已冻结方法与绑定定义 | 不编辑方法权限，不把购买或请入当外部服务授权 |
| knowbench | 管理连接、凭据、运行绑定、调用检查、审批、回执及恢复 | 在现有后端内增加模块，复用 Task/Attempt/Interaction，不新增执行引擎或独立授权服务 |
| knowbase | 继续管理数据使用权、同意依据、绑定及运行授权 | 只有它能裁决其数据访问；连接器结果不自动入库 |
| link | 本地目录、网络、脚本与命令行的执行边界 | 云端连接授权不能抬高本地权限，也不向本地注入外部连接器 token |
| 外部服务 | 校验发给自身的凭据、外部账号权限并执行 | 外部权限只是访问上限，平台仍须检查用户对当前任务的授权 |

```text
会话能力选择／方法定义与冻结计划 ──→ 本次资源与授权绑定
                                  ↓
模型请求 → 平台工具入口 ──→ knowbench 调用检查 ←── 宿主执行动作
                                  ↓
                         必要审批／现有批准匹配
                                  ↓
              ┌───────────────────┼───────────────────┐
              ↓                   ↓                   ↓
       knowbase 运行授权    外部连接执行模块       link 本地检查
                                  ↓
                       直接 API／第三方 MCP／A2A
```

新外部连接工具只通过平台入口提供给模型，原始外部凭据不进入模型、沙箱、方法包或日志。平台与外部资源之间分别使用对应身份，不转交 Casdoor 登录令牌、内部服务令牌或 knowbase 授权。tools 中心解析方法版本及绑定，注册或发现本身不授予权限。

### 10.3 方法权限与审批契约

方法六要素的字段定义只在[方法、步骤、组合与模板 §1.6](专家方案设计/专家孵化方案/luna/方法、步骤、组合与模板.md#16-权限要求审批与运行授权)维护。本节使用其中的 `access_requirements` 和审批规则，不另设专家专用权限结构。

方法通过资源角色声明依赖，如 `source_mailbox`、`report_destination`；在本次任务中才绑定用户连接。所需操作须对应版本化的能力契约。允许替换供应商时，由已验证的适配关系匹配，不能由模型仅看名称决定等价；作者明确要求固定服务时，运行不能偷偷替换。

例如“整理本周客户邮件并发报告”：

| 方法约定 | 本次运行绑定 | 实际检查 |
| --- | --- | --- |
| 读取来源邮箱指定文件夹、指定期间 | 用户选定连接与文件夹，期间来自已确认输入 | 读取工具、账号、文件夹、期间均在本次授权范围内；过滤发生在返回给模型之前 |
| 输出报告，再按需发送 | 报告产物版本、发件连接及收件人 | 发送是独立操作，不从读取权限推导；发送范围与数据外发依据同时满足 |
| 发送前确认内容 | 对应审批规则与具体动作预览 | 核全部收件人、正文与附件；批准后内容变化则重新核准 |

纯计算方法可以没有资源访问要求；计算输入的来源仍须在取得时合法。步骤仅引用权限要求和执行绑定，不成为独立授权资产；父方法向子方法传递必要子集，子方法不能自行扩权。程序块调用外部服务同样经过执行模块。涉及直接 HTTP 或本地命令的旧方法，若仍能绕过检查使用外部凭据，须完成改造和验证后才接入这一统一权限机制。

### 10.4 需要持久化的对象

以下为逻辑对象和建议字段，并非已建表或已发布接口。实现时先复用既有主档与关联，不按每个逻辑对象新建服务。

| 对象 | 建议保存的内容 | 关键约束 |
| --- | --- | --- |
| 连接器定义 | `connector_id`、版本/摘要、资源与操作契约、适配入口、鉴权方式、工具到操作及 scope 的映射、资源选择器、出站目标、结果限制 | 无用户凭据；明确只读、外发与副作用，不信任远端自行标注只读就自动放行 |
| 用户连接 | `connection_id`、所有者、连接器引用、外部账号稳定标识与展示名、实际 scope、状态、`access_revision`、凭据引用、到期信息 | 同一用户可有多个同服务账号；运行必须明确选中哪一个，不自动选“最近使用”或作者账号 |
| 加密凭据 | 用途、所属连接、密文、加密密钥版本、刷新版本及失效信息 | 复用 Fernet 加密基础并区分用途；外部凭据只供后端适配器使用，查询接口不返回明文 |
| 运行授权及资源绑定 | 所有者与执行主体、Session/Task、方法版本和调用链、要求编号、连接或资源引用、允许操作、范围、外发目标、同意依据、有效期、撤销记录 | knowbase 使用既有 `grant_ref`，本地使用环境与目录引用；平台授权记录不取代资源端权限 |
| 动作批准 | 现有 Interaction/审批记录，扩充连接、操作、范围、方法与规则版本、参数摘要、产物版本、授权修订、决定与有效范围 | 是事实记录，不能由模型参数或方法定义伪造；与现有命令前缀记录区分类型 |
| 外部调用回执 | `call_id`、运行上下文、连接、工具与操作、授权/批准引用、参数摘要、幂等依据、外部请求编号、结果/费用状态 | 记录最小必要元数据，和现有事件及成果引用关联；不另建任务账或费用账 |

密钥引用只存在于受控执行配置，公开方法中只写资源角色和鉴权要求。连接 scope 是外部授予范围，任务授权是本平台允许范围；API Key 无法报告精确 scope 时记为未知，不能伪造“已最小授权”，平台侧仍按操作和资源约束执行。

`access_revision` 在账号、资源目标、授权范围或连接撤销发生变化时递增，原运行绑定必须重新核对。仅在同账号、同范围内正常刷新 token 不扩大任务权限，也不要求用户重复批准；凭据刷新版本单独用于处理并发。

### 10.5 连接与凭据生命周期

用户在「连接」页选服务、完成 OAuth 或录入 API Key，查看账号、已授范围、可用操作、可供哪些会话使用及哪些任务依赖它。列表只显示状态和脱敏信息。Casdoor 登录解决平台身份，不自动取得邮箱等外部系统的权限；OAuth 客户端的部署密钥与用户令牌分开保管。

拟定连接状态为 `connecting`、`active`、`reauth_required`、`disabled`、`disconnected`；这些是连接对象状态，不增加 Task 状态词。临时服务不可达另记健康信息，不把网络超时直接判为用户撤权。

| 事件 | 处理 |
| --- | --- |
| 发起连接 | 后端创建短期、一次性授权事务，绑定当前已认证用户、连接器、回调、目标资源及来源任务；只接受受控返回位置 |
| OAuth 回调 | 绑定并校验事务、state、PKCE 及授权服务器身份后换取令牌；拒绝串用户、过期和重复回调，不从模型提交的账号身份认领连接 |
| 连接成功 | 保存实际账号与授予范围，返回连接状态；不会自动批准等待中的发送或外发动作 |
| token 到期 | 后端按连接串行刷新，带版本条件保存轮换结果；不假设一定存在 refresh token，不允许旧刷新响应覆盖新状态 |
| 刷新无效或 scope 不足 | 标记需重新授权或明确缺少范围，相关动作等待；不循环重试、不自动申请更大权限 |
| 更换账号、目标或扩大权限 | 生成可追溯修订，重核关联任务；不能把原账号的发送批准转移到新账号 |
| 断开 | 先禁止新调用并失效本地授权、停止相关触发，再尝试外部撤销与订阅取消，清除活动凭据；对方撤销失败如实展示，不恢复本地访问 |
| 加密密钥轮换 | 使用受控密钥版本重加密、验证旧密文读取与恢复，再退出旧密钥；不因轮换丢失所有连接，也不在日志打印密文或明文 |

断开与刷新必须共享连接版本检查：晚到的刷新不能使连接复活。恢复备份时须重放或核对撤销记录；无法确认时不得启用旧凭据。已进入外部服务的请求可能已生效，撤权不能承诺回滚既有副作用。

HTTP MCP 授权按[官方授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)核对目标资源、回调和令牌用途；本次 2026-11-12 查阅。直连外部 API 则按该提供方支持的 OAuth 流程实现，不把 MCP 的资源参数要求机械套给所有 API。刷新令牌保密且并非必然签发。协议版本与适配器能力须在接入时登记。

自定义 MCP 的服务地址、发现文档、授权/令牌端点及重定向均需出站校验，防止访问平台内网、实例元数据或携带令牌跨目标跳转；DNS 解析和重定向不能绕过原限制。首期仅开放已审连接器目录，自定义远程 MCP 在同一机制通过验证后开放，不允许用户借地址配置在云端启动任意本地进程。

### 10.6 本次执行怎样获得访问范围

1. 普通聊天与工作根据会话选择和当前请求解析需求；调用方法时，根据已选方法版本及实际分支解析权限要求。方法创作时检查所有可达分支的要求是否声明，运行时只申请当前需要的范围。
2. 将资源角色绑定用户有权使用的具体连接、数据或本地目录，明确账户和目标，检查实际 scope、工具与环境是否可满足。
3. 把本次用途和范围交用户确认，或引用已有效、确实覆盖本次动作的授权。确认结果关联真实 Session、执行上下文及存在的 Task；调用方法时再关联精确方法版本。系统不得仅因用户当前在线就推定同意，也不为聊天虚构专家任务。
4. 每次调用分别核：平台准入、会话允许范围、存在的方法约束和父调用传递范围、用户本次同意、当前资源权限、连接状态及动作审批。全部满足才执行；未满足时说明缺哪一项。没有方法契约的普通聊天仍有会话授权和平台限制，不等于没有权限边界。
5. 追加资源或扩大范围时新增授权依据与绑定修订，保留旧记录，不原地放大既有批准。方法升级不自动沿用旧方法的授权。

聊天、工作采用用户为会话选定的连接与范围；专家采用冻结方法要求和本次委托授权。它们共用判断与执行模块，区别在于约束来源。现有规则要求聊天写操作和 A2A 外发逐次确认时继续逐次确认；专家可复用覆盖该动作的已有批准。不能用新的“会话都允许”按钮绕过既有产品规则。

授权失效取任务终态、会话结束、用户撤销、批准截止或资源端失效中先发生者。运行授权必须有截止时间；首期建议会话最长 24 小时、任务最长 7 天，与既有数据运行授权上限对齐，资源端或用户要求更短时取更短值；续签须核原同意依据，不能静默扩大范围。连接长时间有效不等于任务长期有效。后台职责必须另有明确的持续用途与范围，每次唤醒仍创建普通任务并核授权；第一期不默认启用免确认自动发送。

### 10.7 工具目录与逐次调用检查

平台工具别名解析到冻结的连接器版本、操作契约和方法要求。会话发现只返回当前允许展示的工具；专家可以展示缺少连接的需求状态，但不能让未绑定工具成为可执行入口。目录过滤只是帮助选择，实际调用仍完整检查，旧缓存或模型直接拼工具名不能绕过。

knowbench 从认证身份、Session/Task、执行上下文和已有调用观测确定调用者；不接受模型自报所有者、连接凭据或授权事实。模型可以提出业务参数，涉及账号和范围的引用必须属于服务端允许集合；宿主直接调用则使用同一执行模块签定的上下文，不假装来自模型。

拟在现有检查之后加入以下顺序：解析工具与参数 → 核绑定版本和所有者 → 核资源选择条件与外发范围 → 核当前连接和授权 → 匹配批准 → 持久化待执行回执 → 发送前再次检查可变授权 → 执行 → 保存回执。授权记录、批准消费和派发状态以事务及条件更新约束，同一动作不因并发双击派发两次。

范围检查必须覆盖参数与返回内容：用户只允许某文件夹时，不得先把全邮箱返回模型再提示“不要看”。供应商 scope 比用户授权粗时，由适配器限制查询、分页、下载与结果；如果服务能力无法实现所承诺的范围，拒绝该绑定或显式提出更大范围供用户决定，不能虚称已限制。出站上传、搜索关键词及附件也属于要核对的数据传递。

脚本和程序块在受限执行环境运行，不继承 knowbench 的环境秘密、凭据表访问能力或内部服务身份；外部账号操作通过受控平台调用入口发起，宿主构造调用上下文并限制可访问的连接集合。执行环境的出站和文件范围须能强制落实方法约束；只在提示词里写“不许越权”不算完成。无法隔离的旧执行路径不开放这类连接器权限，先做兼容改造和绕过验证。

远端工具列表、参数 Schema 或副作用语义变化时，核已冻结摘要与适配兼容性；未知变化阻止受影响调用并请求重新验证，不直接把新工具注入运行中的方法。目录快照不是远端实现不变的证明，无法取得实现版本时记录可复现限制。

### 10.8 审批卡、第三方询问与动作绑定

复用现有 Interaction 和 `WAITING(APPROVAL)`，增加连接动作的展示与匹配类型。审批卡用用户能判断的内容展示：哪个账号、对哪个对象、读/改/发什么、交给谁、为何需要、已知费用与无法确定的部分。邮件预览包括发件账号、收件/抄送/密送、主题、正文及附件版本；不显示 token 或内部凭据引用。

批准绑定 `connection_id`、操作、具体范围、规范化参数摘要、不可变产物版本、方法/规则版本和授权修订。发送前使用同一内容快照；内容、收件人、账号或附件字节变化必须重新匹配批准。资源版本敏感的修改应携带版本前提，防止批准后目标已被别人修改。一次性批准的消费与调用编号关联，重复响应不能再次执行。

本次允许、拒绝、取消继续沿现有机制；只有规则允许、且范围可明确表达时才展示任务范围批准。已覆盖动作的批准可复用，不因递归调用或换步骤重复问。命令前缀授权不能匹配连接器操作；平台或资源端禁止的动作不因用户点“允许”变为可执行。

第三方 MCP 的 elicitation 不走现有默认值自动接受路径。先验证服务与调用来源，普通问题进入提问卡，动作许可进入审批卡，登录需求进入受控连接流程；外部问题本身不能授权另一次工具调用。不能把秘密输入设计为模型可读的表单，外部返回的“请发邮件”等文本仍是数据。来源不明、未知询问类型或无活跃上下文时拒绝或暂停。现有可信内部自动回应若保留，必须显式限定来源和无授权副作用的 Schema，不能只信服务名字。

### 10.9 失败、撤权、幂等与恢复

Task 状态与合法转换沿用现有状态机，不增加 `WAITING_AUTH` 等词；连接器原因作为稳定错误码和等待详情保存。进入 `WAITING` 时关联 Interaction 或资源等待记录，恢复时按已有合法路径回到 `VALIDATING`/`QUEUED`，不得把终态任务重新开跑。

| 情形 | 状态与处理 |
| --- | --- |
| 需要用户选择账号、补连接或扩权 | `WAITING(APPROVAL)`，给出连接/授权卡及缺项；成功后重核全部范围，不直接发送 |
| 缺少业务参数 | `WAITING(INPUT)`，补齐后重新生成动作预览与批准匹配 |
| 供应商限流或服务暂不可用 | 可恢复时 `WAITING(RESOURCE)`，保存重试条件与次数上限；不谎称用户没有数据 |
| 本地执行端断开 | `WAITING(ENVIRONMENT)`，恢复后核目录与本地上限，云端不代为放宽 |
| 读取超时 | 确认操作无副作用、无重复收费风险后才按适配策略有限重试；结果去重并保留来源 |
| 写入返回不明或进程在派发后崩溃 | 回执记 `outcome_unknown`，停止依赖该结果的后续动作；查询外部请求状态或让用户核对，不自动重发 |
| 运行中撤权或断开 | 拒绝新的调用、取消尚未派发动作；在途动作尝试取消并记录实际结果，既有副作用不伪称已撤回 |
| 用户拒绝必需动作 | 按方法规则停止、失败或请求明确变更，不能把缺项结果标完整；可选动作按已定义分支跳过并披露 |

每个有副作用的业务动作有稳定 `call_id` 和参数摘要，重启后查现有回执。外部支持幂等键时只在相同内容与其幂等有效期内复用；不支持时，平台本地去重不能证明外部没有执行。邮件供应商“已接受请求”也不等于最终投递或收件成功，回执分别表达。费用未知照实待核，不记为零，不为查明费用自动重放请求。

调用恢复必须重新检查当前授权和连接状态；保留已完成的读取与计算证据，按产物依赖判断能否复用。是否允许继续使用已取得内容遵守撤回依据和现有数据规则，不把“之前下载过”当作永久使用权。补授权只恢复原范围内可继续的工作，不能自动恢复已经取消或过期的动作批准。

### 10.10 结果、审计、触发与费用

外部结果作为当前会话或任务的受控输入保存，关联连接器、来源对象编号、取得时间、内容摘要及本次授权；按既有任务成果访问与保留策略管理，不自动入 knowbase，不另做长期外部资料库。单次结果、分页、附件大小和执行时限由连接器版本配置，缺少上限不得发布；超限返回受限状态，不能静默截断后宣称已读全。需要长期保存时走明确的转为数据流程并核来源许可。

审计只记调用主体、任务/步骤/方法/动作、操作和资源标识、授权依据、批准来源、结果及费用状态。正文与附件存受控成果，不复制进普通日志；远端原始错误、授权码、token、URL 查询凭据及任意 elicitation 元数据不得直接输出。审计和成果都按当前身份检查，避免另一个用户通过连接编号读取。

触发层与此前“职责”方案衔接：Webhook 验来源，轮询按授权范围读取，按外部事件 ID 去重并保存游标；重放不能重复出卡。默认只生成待确认卡，不因新邮件自动授权运行。断开后停止新增触发和派发；恢复游标不恢复被撤销的授权。定时与 knowfeed 订阅沿同一触发入口，仍不替代它们自己的数据权限。

连接器与 A2A 的费用沿现有会话/任务费用记录，以外部回执为依据，缺少价格或结算结果时标未知。报价、用户批准的预算、平台已记支出与外部实际扣费分开；不在本任务建设充值或支付系统。A2A 后续复用连接、授权与回执机制，另实现任务与取消适配，外部 Agent 成果仍需方法验收。

### 10.11 接口、迁移与实施顺序

需要补齐的接口职责为：连接目录与状态、开始授权和回调、停用/断开、会话可用范围设置；任务权限需求预检与资源绑定；动作审批与结果查询。具体路由和 Schema 沿现有后端提供方生成、消费方锁版机制确定，不由前端手抄。调用入口只接受业务参数和受限引用，管理连接和授权的接口必须校验登录主体与 CSRF 等现有浏览器约束。

部署的 OAuth 客户端配置走现有私有输入/Secret；密钥值不进 Git。方法发布包携带要求、批准规则和连接器定义引用，不携带用户连接或批准事实。旧方法、旧凭据和已发布摘要保持可读；新要求先按版本显式启用，不能把旧方法缺权限字段解释为允许访问所有外部连接。

以下为按依赖划分的实施批次。最初讨论时只交方案；后续用户已要求实施统一接入，当前差距见 10.14。批次用于安排开发与验收，不把连接器留到 MCP 和 Skill 接口定型以后再补设计：

| 批次 | 范围 | 交回依据 |
| --- | --- | --- |
| 1：契约与兼容 | knowlab 方法要求、knowmart 展示/清单、knowbench 运行绑定的提供方与消费方对齐 | 六要素与现有方法/包版本兼容，旧财务流程行为不变，权限要求不能伪装授权 |
| 2：连接生命周期 | knowbench 后端、网页连接页、加密凭据、OAuth 事务、刷新与撤销 | 假授权服务验证跨用户隔离、刷新并发、断开竞争和秘密不外泄 |
| 3：执行与审批 | 扩展调用检查、资源范围、审批卡、第三方询问、回执与恢复 | 模型/宿主/程序块均不能绕过；精准动作批准与未知结果不重发 |
| 4：首个真实连接器 | 邮件读取、受控发送，以及失效/撤权/恢复闭环 | 真服务真实收发与故障验证证据；通过后再接 A2A、其他服务及后台触发 |

首个场景选“读取本人指定范围邮件，生成摘要，批准后向本人另一个测试邮箱发送”。优先核现有邮箱服务能否注册委托 OAuth 应用并支持所需操作；不把已配置的阿里云注册验证码 SMTP 当成用户邮箱读取授权，也不凭已有邮箱账号就宣布具备 API 接入资格。供应商、应用注册、回调域名和真实测试账号在开发准备时核实；无法满足则更换适配选择，不降级成复制浏览器登录态。

首期优先通过平台适配器直连该邮件 API，以便明确每个操作和范围；第三方 MCP 转接使用同一授权模型，但须另验工具契约和身份链。模拟 MCP 与模拟 OAuth 的通过只能证明机制，不能代替真实服务的权限、投递及撤销验证。

### 10.12 验收矩阵与方案待定项

| 场景 | 必须取得的证据 |
| --- | --- |
| 方法契约 | 六要素结构相同；权限与审批分工明确；空权限不允许外部访问；组合与可选分支不暗中扩权 |
| 连接隔离 | 用户不能读取或使用别人的连接；同用户两个邮箱明确区分；连接身份改变使相关绑定重核 |
| OAuth | 回调串用户、重放、state/PKCE 错误被拒；拒绝授权不会生成 active 连接；无刷新令牌能正确处理 |
| 读取范围 | 超出文件夹、期间、分页或数据版本的请求被拒或受控过滤；模型收到的结果不越界 |
| 动作审批 | 未批准不发送；改收件人、抄送、附件或账号后旧批准不匹配；并发重复答卡只产生一次派发 |
| 第三方询问 | 不再自动填 true/默认值；未知来源拒绝；连接成功不等于动作批准；外部文本不升级为指令 |
| 过期与撤权 | 正常刷新不重复询问；失效需重连；断开与刷新竞态不复活；撤权后新调用停止 |
| 崩溃与恢复 | 派发前、派发后未收回执、保存结果后分别故障注入；未知发送不重发，已完成步骤可按依赖恢复 |
| 多种调用主体 | 模型调用、宿主调用及程序块适用相同授权约束；knowbase 和 link 的最终拒绝不可绕过 |
| 跨场景复用 | 同一用户连接供聊天、工作、方法及子方法使用，不重复保存凭据；各自运行授权隔离，停用／断开阻止所有场景的新调用 |
| 前端闭环 | 从会话或方法缺项进入统一连接页，返回原执行后重新预检；接通不自动批准发送；多账号必须明确绑定；状态刷新后不重复派发 |
| 目录与版本 | 新工具不自动加入既有批准，变化的 Schema/目标被阻止；旧包摘要和在跑方法不被覆盖 |
| 数据、审计与费用 | 结果有出处且访问隔离，token 不进模型/日志；部分完成与费用未知如实显示；无自动长期入库 |
| 真服务闭环 | 指定范围真实读取、本人测试地址批准发送、实际失效与撤销、恢复后不重复发送；回执区分接受与投递 |

实现须将这些字段与批准范围对齐现有契约，不能把方法工具勾选当成资源授权。真实接入前尚需落实供应商应用注册、最小可授 scope、范围过滤能力、断开/撤销支持及发送回执语义，逐项写入该适配器规格。真实发信和付费调用仍须有对应动作授权；已有软件发布授权不替代它们。

### 10.13 聊天、工作和方法的统一连接器接入（2026-11-13 补充）

统一的不只是凭据存储，还包括连接器定义、用户连接身份、凭据生命周期、能力解析与准备、运行授权检查、审批、调用回执和恢复。不同场景引用同一 `connection_id`，不各自复制 token；同一服务的多个账号仍是多个明确区分的连接，不因共用机制而混用。停用或断开按用户连接生效，不能只撤掉专家里的入口而让聊天继续调用。

| 对象 | 它解决什么 | 和其他对象的关系 |
| --- | --- | --- |
| 连接器定义 | 某服务有哪些操作、怎样鉴权和执行 | 可采用直连 API 或第三方 MCP 适配；不是某用户账号 |
| 用户连接 | 用户接入的具体服务账号及其当前状态 | 引用连接器／服务定义，由后端持有对应凭据；聊天与方法共用 |
| 工具注册与执行绑定 | 把可调用操作映射到实现和运行环境 | MCP 是可能的协议；受管工具绑定引用连接，不另保存账号密码 |
| Skill | 作业指令、资源与依赖声明 | 可以依赖连接器工具；启用 Skill 不会自动连接账号或批准动作 |
| 本次执行能力快照与运行授权 | 本次使用哪个版本、哪个账号、哪些操作与资源 | 来源可为会话选择、方法要求或父调用；和用户连接的长期状态分开 |

连接器、MCP 和 Skill 因此不能做成三个互不相通的账号配置系统，也不能混成一个没有类型区别的对象。一个连接器可提供多个工具和配套 Skill；一次连接成功后，其他使用入口引用既有连接。在界面上，“连接与工具”管理接入和账号，“技能”管理指令资产与依赖，“本次能力”决定当前执行范围。

共用的准备流程为：解析会话选择／方法需求 → 匹配操作契约和可用版本 → 绑定具体用户连接与资源 → 核对当前授权和必要批准 → 固化执行快照 → 交给宿主直接执行或向 Codex 提供工具与 Skill → 每次调用重核并记回执。授权规则和精确动作批准仍按 10.6—10.8 执行，不因已准备就跳过发送前检查。

聊天转入方法执行时，可复用已有连接及确实覆盖该用途的授权依据，但必须重新核对方法需求。方法返回聊天时，不把方法临时获准的范围变成聊天默认权限。父方法调用子方法沿用必要授权子集；Skill 通过工具访问连接器同样遵守该边界。切换入口、模型或调用主体都不产生新增权限。

用户修改“新会话默认选择”只影响以后创建的会话；从当前会话移除能力立即阻止该会话后续新调用，再在空闲边界更新模型侧范围；停用连接则立即阻止所有引用它的执行发起新调用，重新启用仍须重核运行授权；断开另外清除活动凭据并尝试外部撤销。已经在外部执行的请求保留原回执和未知状态，不承诺撤销能回滚。后台任务不得在等待用户重连期间自动改用另一个账号。

前端三部分的页面、操作与接口职责统一维护在 [MCP 和 Skill 接入实施方案第 11.2 节](专家方案设计/专家使用方案/luna/mcp和skill接入实施方案.md#112-前端三个入口及交互闭环)。本文维护连接身份、授权和生命周期语义；该方案维护执行交付和界面流程。二者引用同一后端契约，不新增第二套连接服务或账本。

### 10.14 连接器、MCP、Skill 与安装一起设计（2026-11-13 实施纠偏）

本节落实所有者“连接器应该一起设计”的要求。统一范围包括安装与版本、账号连接、工具注册、依赖解析、运行授权、执行与回执。只让三个页面互相跳转，或给 MCP 地址加一个“连接器”名称，都没有完成统一。

#### 对象关系与现有代码差距

连接器定义描述服务的业务操作、认证与资源限制；MCP 是可选的工具接入协议；Skill 是带文件、指令和依赖的技能包。它们可以组合发布，但不互相替代。例如邮箱连接器可由直接邮件 API 实现，也可由经过验证的 MCP 适配器实现；“邮件周报”Skill 依赖它的读取和发送操作。

| 对象 | 本轮共同设计的要求 | 当前代码及需要调整之处 |
| --- | --- | --- |
| 安装记录与不可变版本包 | 用户安装一个能力包，可包含 Skill、MCP 服务声明和连接器定义引用；记录来源、摘要、兼容性及依赖。安装本身不登录账号、不执行安装脚本、不批准动作 | 已有完整 Skill 导入和链接安装候选；不能把它宣称为任意连接器包安装。远程 MCP 登记与 stdio 软件安装分别验收 |
| 连接器定义与工具注册 | 定义由 API 管理；每个工具映射到确定版本的操作、适配器和资源检查器。原生工具没补齐六要素时保留技术工具身份 | `ConnectionCreate` 仅有 URL、账号标签和 Bearer；`tools/list` 的结果尚无完整业务操作映射。不能信远端注解就自动批准只读调用 |
| 用户连接 | 以稳定 `connection_id` 引用账号与凭据；多个账号可共用同一定义，各场景引用同一连接 | 复用现有 `kind=connection` 资产与加密机制，扩充定义引用、真实外部身份、scope、凭据刷新与授权修订；不另建一套“Skill 账号” |
| 依赖要求 | 方法与 Skill 用资源角色、操作契约和约束表达需要；发布包不携带使用者的连接 ID | 方法候选 `MethodCapabilities` 目前只有 MCP URL/工具名及 Skill 摘要；Skill 的字符串依赖目前指向个人工具。两者均不能充当完整的可移植连接器契约 |
| 运行绑定 | 在当前场景、方法调用链和步骤范围内，把依赖绑定到用户账号及资源；安装可共享，授权不自动共享 | 现有 selection、method_context 和修订检查继续复用；补连接器角色、操作、资源、批准与授权截止，而非只判断工具是否被勾选 |
| 调用回执 | 区分“来源能力资产”“使用的连接”和“实际操作”，关联原有任务账 | 当前 `skill_run` 借用回执的 `connection_id` 保存 Skill 资产 ID。迁移须显式区分来源资产与真实连接绑定；不能把脚本包当作外部账号，更不能给整段脚本只记一个笼统外部动作 |

六要素中的权限真源仍为方法主稿 §1.6 的 `access_requirements`；连接器操作依赖引用它，不在 `managed_capabilities` 另造一份可冲突的权限规则。后者承载具体 MCP／Skill 实现选择与版本。Skill 原有 `SKILL.md` 及目录结构保留；平台的结构化依赖是安装元数据，可由配套清单导入或在界面配置，不强迫第三方 Skill 改正文。仅从正文推断的依赖只能作为待确认建议，不能产生授权。

#### 一次安装，多处使用的完整流程

1. 用户从统一安装入口选择连接器、MCP 或 Skill。平台展示包来源、内容、版本、执行环境和依赖，再保存安装记录；同一个包包含多类能力时保持一个安装来源，页面按功能展示。
2. 平台注册该安装提供的工具描述与依赖。需要账号时显示“连接账号”；已有兼容账号可直接选择，不再重复录入凭据。版本更新先预览差异，新增操作、scope 或出站目标不能自动进入既有授权。
3. 普通聊天／工作默认发现启用 Skill 的简介；发现技能不意味着其全部依赖自动可用。执行前解析实际需要，用户选择账号和资源。方法则由已冻结要求和步骤范围解析，父方法只能传递授权子集。
4. runner 从 API 管理的数据准备本次能力快照，交给 Codex 必要的工具描述、Skill 目录和受限入口。模型负责提出调用与业务参数；宿主负责身份绑定、权限、审批和派发。
5. 每次外部调用回到 knowbench 同一检查与执行模块。检查连接、操作、资源、数据外发及具体动作批准后，适配器取凭据并执行。宿主直接调用也经过这一模块，不为确定的调用额外启动模型。
6. 结果和费用证据进入既有回执、任务成果与费用记录。账号断开、权限变化或任务取消，使后续调用失效；已派发动作按实际结果或未知状态处理。

API 承担管理接口、工具网关、连接授权与外部适配执行；runner 承担任务推进和范围准备。它们是两个 Deployment，共享持久记录不等于共享进程内对象。知晓连接 ID 的 runner、模型或脚本都不能仅凭该 ID 获得凭据。

#### Skill 脚本怎样使用连接器

同一依赖与授权模型支持以下两种执行组织，按脚本行为选择：

| 组织方式 | 适用情形 | 执行及审批边界 |
| --- | --- | --- |
| 宿主调用连接器，脚本处理已取得的数据 | 读取、计算和发送可拆成明确步骤，例如取邮件 → 算周报 → 发周报 | 宿主先按授权读取，输入绑定将必要数据交给隔离脚本；脚本返回产物后，宿主对具体内容和收件人申请发送批准。脚本本身不需要联网 |
| 脚本运行中请求连接器 | 脚本必须按中间结果分页查询或选择下一项业务操作 | 平台提供受控调用客户端，脚本只提交本次已绑定的操作引用与业务参数；服务端重核当前账号、资源范围和批准。原始服务凭据仍只在外部适配器 |

后一种方式需要明确的新执行能力，不能用“开放脚本联网＋把 token 写环境变量”代替。受控入口使用短期、可撤销、只绑定该脚本调用和指定依赖的**平台执行凭证**；它与外部服务凭据不同，不能访问管理接口、添加连接、扩大范围或读取其他调用。凭证视为可能被脚本读取，安全性依赖服务端授权和网络隔离，不能依赖脚本保密。执行容器仅获准连接该入口，入口按服务端绑定选择目标，不接受脚本传任意 URL 代请求。

脚本内的每次外部操作独立记 `call_id`，关联外层脚本调用，并复用同一 Task/Attempt/Interaction。批准“运行脚本”不批准它以后产生的发送、修改或外发。脚本内容改变、账号改变、参数或附件改变均按既有规则重核。外层脚本退出失败也不代表其已完成的发送被回滚；界面须展示这些已完成或未知的子调用。

**等待与恢复是该模式的实现前提。** 现有候选脚本 30 秒执行、Job 总计 90 秒且拒绝全部网络，不能直接接入可能等待数分钟的审批。需要单独定义允许连接器的执行配置、有限总时长、资源占用上限、取消与回执查询；等待期间 API 不持有长数据库事务，脚本客户端用短请求提交／查询既有调用。到期取消未派发动作，在途副作用保留结果；批准必须再核父脚本仍有效。Job 或进程丢失后不能假装从原指令位置恢复，也不能自动从头重跑曾发送过邮件的脚本。能明确拆阶段时优先采用前一种方式，将检查点留给任务 runtime。

标准 Skill 若直接使用第三方 SDK、环境 token 或任意网络，并不会自动变成平台连接器调用。安装兼容性检查应说明是否需要适配；不支持时显示“需要适配连接器”，而不是显示已就绪后在运行中无解释地失败。

#### 验收及交付边界

共同验收至少覆盖：同一连接供聊天与方法使用；一个 Skill 同时依赖读取和发送；两个同服务账号不可混用；安装或启用不授权发送；脚本不能绕过网关访问服务；改资源或收件人使旧批准失效；父方法收窄、脚本结束、撤权和超时使旧执行凭证失效；外层失败保留子调用已产生的副作用；恢复不重复发送。

当前隔离脚本候选只能证明无网络计算路径，尚无脚本连接器入口；现有 MCP 参数批准也没有证明资源范围和 OAuth 生命周期闭环。安装、MCP、Skill、方法步骤的后续实现须共同对齐上述契约，再分别按已验能力开放界面。模拟连接器可以验证共同机制；真实供应商应用注册、授权及收发仍须独立验收，不能借平台注册验证码 SMTP 代替用户邮箱连接。
