## 四、要你定的

1. **Wind 的用量护栏。** Wind 渠道现在是所有账号都能用（`audience=all_users`），每日上限 0 表示不限（账 184 按这个口径修的），而且**没有按用户的上限**：任何一个用户都能不停提 Wind 查询，耗你付费账号的额度。我建议在渠道配置里加「每人每日最多几次」，超了回明确原因，默认值你定（比如 20）。要不要加？
2. **审核人和作者分开。** 交付审核和特批放行，现在都不核「审的人不是作者本人」。眼下你既是作者、又是唯一的审核和放行人，所以这样能用。上线以后，要不要加「不能审自己的公开交付、不能批自己的特批」？可以留一个只给所有者用的例外开关。
3. **0051 第 4 步动工前要定的口径**（knowfeed `jobs.py:252`）：现在 Wind 报的错（包括「没有数」）一律让这一项直接失败，不换渠道。眼下 Wind 只接显式查询，这样没问题；按 0051「Wind 先、巨潮保底」落地时，Wind 回「没有数」应该转巨潮，不算失败。我打算在做 Wind 对照时一起改，先跟你说一声。
4. **两项做好了但部署里没开**（不是代码错，是开关）：
   - knowbench「把委托成稿写进 knowbase 产出区」（`WORKBENCH_OUTPUT_WRITE_ENABLED`），默认关，部署里没配，所以线上一直不写。代码注释说「knowbase 那边上线后由 Fable 发版时打开」。knowbase 那边 11-01 已经带上了；但打开前要先修好第三节第 1、2 条，否则写进去的成稿许可算错。要不要随下次发版打开？
   - knowfeed 渲染工作负载（`SUPPLY_RENDER_URL`）没配，平台也还没起这个服务，所以审核定了「要渲染」的网页渠道一律回「不能渲染」。这是平台的活，等你排。

### 12.2 先说结论

安全上的几道闸是认真做的，我逐条核过代码：

- 外联 MCP 只许运营审核过的地址，解析出的地址必须全是公网、连接钉在解析出的那个地址上、不跟随重定向、证书按原域名校验。
- 外部凭据用 Fernet 加密存在 API 的库里，不进沙箱；沙箱里的 Codex 拿到的是限定本轮、限定会话的平台令牌，库里只存哈希。
- 每次外部调用都要用户批准，批准绑着账号、连接修订、工具描述、完整参数和本轮范围的摘要；批准后先落「派发中」回执再发请求，不自动重试。
- 脚本在独立 Job 里跑：非 root、只读根文件系统、丢掉全部 capabilities、不挂 ServiceAccount 令牌、不带任何凭据、出入网全拒；命名空间里没有别的网络策略会给这类 Pod 放行（现有策略只选 `app=sandbox` 的 Pod）。
- 技能包只在内存里解，限文件数、单文件和总大小，拒链接、特殊文件、加密包、越界路径。

要修的：一条是实打实的错（第 1 条）；一条是日常操作会把会话卡死（第 11 条）；两条是设计上会让「方法步骤用 Skill 和连接」跑不通或不好用（第 2、3 条）；两条是装的东西一多就会慢（第 4、12 条）；其余是小毛病。架构上的问题和完善建议在 12.4。

### 12.4 架构上的问题和完善建议

1. **knowbench 里现在有两套工具体系，没合上。** 原有的一套是平台自己的工具（计算、读数、方法工具）：MCP 服务 `sunmoon_workbench`、步骤的 `tools` 白名单、`method_tools.py` 按任务和 Attempt 核调用、`tool_policy` 的允许/询问/拒绝。这批新加的一套是外部连接和技能：MCP 服务 `sunmoon_capabilities`、步骤的 `managed_capabilities`、自己的令牌与范围、自己的调用表 `workbench_capability_calls`、自己的审批卡。同一个步骤要在两处声明工具，一次运行的调用记录分在两处，审批是两种做法。主稿（方法稿 1.9、接入实施方案第 9 节）说的是「统一调用入口、一套核权」。建议：下一步先把两套并到一个登记和一个调用账上（平台工具也是一种绑定），再往上加连接器，不然 C2–C5 每一项都要在两套里各做一遍。
2. **方法和能力靠「地址加工具名」「技能名加版本加压缩包摘要」对上，不是主稿定的六要素权限要求。** Luna 自己列成了 C2。我补一点：现在这种对法已经随 #93 写进了能力契约 `method-capabilities-v1` 和 knowlab 的工作稿，作者一旦用它出了版本，以后改成 `access_requirements` 就要迁移或者弃掉这些版本。建议在作者真正用起来之前先把 C2 做了，或者先别让方法步骤这个入口对外。
3. **技能没有随方法冻结**（见第 2 条）、**绑定不能提前和沿用**（见第 3 条）。这两条合起来的效果是：带技能或连接的专家，别人请不动，自己请也要每步停一次。
4. **所有外部调用（含只读）每次都要人批。** 首期这样做是稳妥的，但方法步骤里读十封邮件就要点十次，「职责」这种没人守着的运行完全走不通。主稿六要素第六项本来就是让方法声明哪些动作要批、哪些可以预先批准；建议和 C4 一起，把「同一连接、同一只读操作、同一资源范围，本件委托内批一次」做出来，写操作仍然逐次批。
5. **每轮换令牌导致每轮重载线程**（见第 4 条）。
6. **脚本的输入走 Kubernetes Secret。** 每次运行把整个技能包（最大约 5.6 MB 的 JSON）切成十几个 Secret 写进 etcd，跑完再删。量小没事；调用多了会给 etcd 添负担，也会在审计日志里留下大量 Secret 写入。建议改成由供给器按调用编号提供一次性下载、初始化容器拉取（只放行到供给器这一条出口），或者等量上来再改，但要先记着。
7. **脚本现在只能收参数和 32 KB 的标准输入**，读不到委托里的资料和前序产物，也调不了连接器（C5）。作为「技能里的小工具」够用，要让方法的程序块用它算数就不够。这关系到我对主稿提的第 1 条（确定性方法的实现在哪跑），建议定那一条时把这个执行器一起考虑进去：它正好可以是「作者脚本在隔离环境里跑」的那条路。
8. **发布分支和工作分支分叉**（见 12.5 第 1 条）。
