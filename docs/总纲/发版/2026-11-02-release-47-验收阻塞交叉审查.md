## 证据与结论

luna 通过正确 kubeconfig / app-platform-dev / knowbench-api 的现有数据库连接执行只读事务，仅聚合目标任务来源与状态：任务 `9319ae09-c8b7-4c3b-844e-27306e9e98d8` 有 **10 条 source=knowbase** 的钉住数据，状态 **WAITING(DATA)**。没有读取财务内容、Cookie 或 Token，没有代用户发送确认请求。

迁移 `20261028_0030_drop_data_v1.py:54` 已把 `workbench_task_data` 约束收敛为 source=knowbase，cloud/local 旧路已退役；后端 `expert_desk.py:202` 直接输出该字段。因此这不是畸形数据库值。翻译保留 cloud/local/knowbase 文案只能说明展示代码存在历史分支，不能作为支持三种来源的现行契约依据。

本地探针加载已发布版本的真实 TypeScript schema / HTTP helper（transpile 后执行，无应用修改），使用非敏感合成数据验证：

- 原 schema 加 10 个 knowbase 条目：恰好 10 个错误，全部在 task.chosen_data[*].source。
- HTTP 200 携该响应：getJson 抛 contract_invalid，status=200；ExpertRunScreen 在 run.data 为空时提前返回，采单组件无法显示。
- HTTP 401、code=auth_required：steps 和 board 均走非成功分支，不进入正常响应 schema 校验。
- 只在内存把来源改为 literal knowbase：合成合法响应通过；未知来源仍被拒绝。换成 string 时，未知来源也通过。

探针与输出：`/tmp/luna-release47-review.cjs`、`/tmp/luna-release47-review-result.json`。这是独立代码复现和线上数据只读交叉核对，**没有重新捕获用户浏览器同一条 /steps 的 HTTP 200 或其 correlation_id**；不能将其写成新的浏览器端到端验收，也不替 Gemini 的运行时 HTTP 取证做背书。

## 对两份结论的裁定

1. Gemini 关于 source 枚举缺失的核心定位已独立证实；但“全部真因 100% 破案”“改一行即可恢复全流程”超出证据。修复该字段不能修复 401，采单面板还依赖独立 task-data 查询成功及实际缺项状态，后续派采与续跑也尚未验收。
2. qwen 对看板 401 和统一失效处理的反馈有据；其最新版已承认用户截图对应的 /steps 状态尚未取得。这些 401 不能用于排除另一次已认证请求的契约失败。两条路径都显示同类错误文字，是争议产生的原因。
3. `session_ttl_seconds=3600` 是配置事实；具体这次为何失去认证仍未证实。不能直接认定 Pod 重启、一小时到期、Cookie 丢失或 GET 漏认证，更不能据此直接延长 Web/Admin 共用期限。
4. source 缺陷在 #47 前的前端 `6e4e0c4` 中也存在，未证明由本次采集修复引入；此次验收暴露的是旧契约与实际数据不一致。

## 修复范围与验收要求

- 先修 steps 的现行数据契约：当前应与后端一致使用 `z.literal('knowbase')`。不以 `z.string()` 放开所有来源；如要保留旧来源兼容，应先明确契约与迁移政策，不能仅凭翻译存在便恢复已退役入口。
- 单独修认证失效展示：正常处理 401、停止失效身份轮询、提供保留原页面/输入的重新认证路径；区分 403、404、服务端异常、contract_invalid。公共机制按模板规则处理，恢复登录后不得自动重放确认/派采/取消。
- 前端预览目录共 11 份 steps 响应，**非空 chosen_data 的样例为 0**。现有“契约对真实后端样例”测试因此遗漏此次字段；此前前端 359 项测试通过不足以证明这条链，这属于 luna 上次验证的覆盖缺口。应加由当前后端生成的非空 knowbase 任务响应，验证整份 runSchema 和实际 GET helper；增加未知来源、401 与缓存/重登的回归。
- 修复后仍经 qwen 组装 Jenkins 候选；应用检查与业务验收分别记录。原任务先恢复页面，本人核对并确认原采单，再验证新需求、真实交付和自动续跑；保底仍走巨潮，不用 Wind 替代，不删除任务掩盖失败。
