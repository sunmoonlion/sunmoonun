# knowbench 登录恢复循环修复（待 Qwen 发布）

2026-11-04 Luna。基于已上线 #70，仅更新 knowbench web。专家第 5 版无需修改、重新孵化或重测。本文是 #70 之后的新候选，前一交接中的后端、迁移和配置已经发布，不重复执行。

## 问题与证据

提交专家委托连续返回 HTTP 401 / `reauth_required`。浏览器会话仍有效时，普通登录页直接跳回工作台，没有重新交换身份凭据；原页“我已登录”只检查 `/auth/web/me`，同一旧会话返回 200 就重新放行，下一次委托再次失败。

API 现场日志（北京时间）：03:40 至 03:47 多次 POST `/api/workbench/projects/2571913d-b2f8-43d3-ac0f-09ad7241d9d5/delegations` 返回 `reauth_required`；03:48:10 用户退出，03:48:40 重新登录后的提交返回 201，随后出现 MCP 调用记录。说明本次重新登录已恢复委托提交，不代表完整财务任务验收通过。初次凭据失效究竟来自存储缺失还是身份服务拒绝，现有日志不能区分，不能将其报告为已查明。

## 修改

- 恢复链接直接进入既有 `/api/auth/web/login?return_to=...`，触发实际 OIDC 登录，不经过会跳过登录的普通页面；返回地址继续由 `nextPath` 限制为站内合法路径。
- 原页恢复时，除会话有效、同应用同账号外，要求 CSRF 标识相对本页最后一次有效会话更新。后端每次成功登录都会重新生成会话及 CSRF；同一旧会话不能充当重新登录完成。连续第二次失效也必须重新登录，不能接受上一次恢复的凭据。
- 保留原输入；更换账号仍清空原账号内容与缓存；恢复只重读查询，不自动重试委托、确认或任何 POST。
- 不改变账号、电脑配对、沙箱或专家版本；不清 Redis、不改数据库、不重启付费任务。

## Qwen 发布与回执

1. 按既有 Jenkins 流程更新精确父/web 来源，只构建与滚动 web；API、runner、admin 保持 #70 镜像，无迁移、无新配置。核对流水线实际计划；若会滚动后端，先调整计划或等待维护窗口，不能中断正在运行的委托。
2. 回执记录 web 镜像和父子 SHA，确认后端及 runner 摘要保持 #70。回退只恢复 #70 web `2a0d722` 对应镜像，不回退后端或专家包。
3. 浏览器检查恢复链接实际进入 `/api/auth/web/login`。仅点“继续”而未完成新登录时不得解除提示；同账号重新登录可保留原输入恢复；不同账号不得继续旧账号输入。不得代用户重复提交或启动付费委托。
4. 如真实重新登录后仍返回 `reauth_required`，继续排查服务端存储和身份服务交换，不能靠循环让用户登录或放松鉴权。当前修复不宣称覆盖所有身份服务错误。
