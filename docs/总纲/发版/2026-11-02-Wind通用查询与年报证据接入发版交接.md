## 3. 具体改变与生产配置

1. `source_query` 是 data-request/v1 的兼容可选扩展，包含渠道、服务、工具、原参数、解析器分配的请求标识。用户确认面板展示并能改参数；新提案不隐式复用旧任务“最新”响应。ordinary 请求键不变。knowbase 提供方 schema、knowfeed 预切合及 bench/lab 消费锁已同步。
2. Wind 在既有供给目录登记 `plugin=wind-mcp`、`kind=catalog`、`doc_types=[other_text]`、`readings=[original,text]`、`zone=collected`、`license=self`、`max_running=1`、`daily_cap=0`、`config.owner_subject=<已核实际用户主体>`。这描述的是供应商响应的存储形态，不是只支持文本领域或只支持财务。每分钟限速按账号约束设置，不能为不限总次数而关闭限频。
3. 服务端正式秘密输入：`WIND_API_KEY`（SecretStr）、`WIND_OWNER_SUBJECT`。走现有私有配置/SOPS/Secret，不写 values/源码/回执明文；值由授权的现有私有凭据托管流程取得，禁止打印。API 负责能力发现、worker 负责取数，两者需要同一账号配置及到 `https://mcp.wind.com.cn` 的正式 HTTPS 出口。沙箱不拿 Key。
4. 首次登记按已有管理 API/页面 → worker 试采 → 人的正式审核；不能直接 SQL 设 approved。试采已覆盖 pending → trial → approve；普通发现/执行不放行 pending。scope `knowfeed:supply-demand` 沿用原关系。MCP discover owner 来自工作台任务身份，不能填显示名或代用模型传入 owner。
5. quota/auth 错误持久暂停渠道；已取响应在下游失败后从原件存储重交，不重复收费；有请求意图却无留存响应则报 provider_outcome_unknown，不自动重放。限流正常延期。本轮未新增业务表或迁移；另逐项对比 #52 sources 中四个后端至候选 HEAD，alembic/versions 也均无变化；daily_cap=0 新语义必须与本次后端/管理端一起使用，旧后端会把 0 当已耗尽。
6. 不开启普通商城 v3 准入，不把 agy 合成方法夹具当作通过验收的作者资产。此前受控动态作者测试仍只是默认关闭构造入口，本包没有偷偷启用全体用户。

升级顺序须保证新的查询请求到达前提供方可识别：knowbase → knowfeed → knowbench/knowlab，前端同包。发布期间保持 Wind 未登记或暂停，待组件、契约及账号探针检查过再走正式试采/审核启用。普通巨潮请求保持原路。生产秘密、渠道和活跃任务均尚未由 luna 修改。
