# 方法实施方案

> 更新：2026-11-14。本文将所有者与 Fable 的讨论整理为方案，并吸收 Luna 对现有代码的核对及实施意见。面向方法作者、执行系统开发者与评审者。
>
> **状态：四项方法定义调整已经确认；本文细化的是目标设计，不表示递归调用、动态输入汇总或公共权限机制已经实现。** “五项作者定义＋两个生成视图”的组织方式为建议，是否正式替代“六要素”的名称尚未确认。

## 一、目标与已确认的决定

目标是用同一种方法结构表达基础方法、组合方法和专家：作者定义能力边界与执行规则，使用时围绕用户问题形成具体计划，程序负责绑定、核权、调度和验收。方法能够调用其他方法，专家团因此可以在同一体系内表达，不另建一种执行对象。

所有者已同意以下四项调整及对应补充，记录见 [2026-11-14 方法定义决定](../design/decisions.md)：

| 调整 | 已确认的含义 | 必须保留的边界 |
| --- | --- | --- |
| 输入移到步骤 | 步骤按需声明输入变量，执行时由程序绑定，或由模型提出取值、程序校验；方法对外输入由程序归纳，不要求作者重复手写 | 不赋值不等于不声明；变量须有名字、类型与适用口径。第二项保留为“所需权限” |
| 方法递归执行 | 规划自上而下、用到哪层规划哪层；沿满足依赖的执行路径向下执行，结果逐层向上返回 | 首期串行；限制调用深度、循环和整棵调用树预算；每层独立验收 |
| 能力声明只含第一层 | 本层说明自身解决什么问题、适用与排除范围，并引用直接调用方法的能力及版本 | 不递归抄写全部后代能力；数据、外发、账号和费用影响仍须跨层核算与披露 |
| 使用时编排并确认 | 作者在孵化时定义候选方法、必做、条件必做与依赖；AI 使用时按题编排，程序校验，用户确认或在边界内修改 | 用户不能删掉作者必做项或破坏依赖，不能添加范围外方法；下层在已确认范围内自动规划 |

固定专家仍按作者确定的顺序执行，可视为规则限定到只有一种有效计划的特例，不推翻 2026-11-03 的决定。最底层已有明确做法的方法不让 AI 每次重新发明算法；需要模型判断的方法也应固定其职责、输入、产物及验收规则，不要求所有底层方法都变成确定性公式。

步骤仍不是方法。一个步骤的执行内容可以包括方法调用、多个方法的组合及程序块；这些内容共用步骤的数据依赖和执行范围，但不能因此把每个步骤另注册成具有完整方法结构的对象。

## 二、方法定义与生成视图

作者应维护业务规则的唯一来源，输入和返回接口从这些规则生成，避免在方法层与步骤层反复填写同一内容。建议采用下列组织方式；在命名确认前，不将“六要素已取消”写成既定事实。

| 作者定义的内容 | 内容与职责 |
| --- | --- |
| 能力声明 | 本层要解决的问题、适用与排除范围、结果承诺，以及直接使用的方法能力引用 |
| 所需权限 | 资源责任域、用途角色、操作契约、允许操作、资源约束、外发要求和缺项处理 |
| 步骤与编排规则 | 候选方法及版本、必做与条件必做、依赖、可选范围；步骤输入、执行内容、产物与对外导出标记 |
| 校验 | 计划是否符合作者规则，输入口径是否匹配，各层结果是否满足业务要求 |
| 审批 | 计划确认、资源授权及具体动作的审批条件、范围、等待与拒绝行为；这些批准不能互相替代 |

| 程序生成的视图 | 来源 | 用途 |
| --- | --- | --- |
| 对外输入 | 步骤中需要由调用方或外部来源提供的输入槽及其条件 | 让调用者知道需要提供什么；规划和派发前检查缺项 |
| 对外返回 | 被明确标记为最终交付的产物及导出映射 | 让上层绑定返回值、让使用者看到交付物、让程序验收 |

生成视图仍是方法调用接口的一部分，应随相应方法版本或已确认计划固定。取消重复手写，不等于取消输入输出契约，也不等于等执行失败后才知道缺什么。

## 三、输入声明、赋值与对外输入

### 3.1 步骤先声明，执行时绑定

步骤可以没有输入；一旦声明某个输入，就要明确名称、类型、必需或可选、来源约束及缺失处理。财务数值等有业务口径的输入还须包含主体、期间、单位、币种、合并口径等适用字段，不能仅以“一个数字”判断匹配。

作者固定的窗口、阈值、算法选项属于方法定义，不应混入每次运行都要求调用方填写的输入。产物绑定须保留来源及版本，不能把模型复述的数值当成原始证据。

| 输入来源 | 谁提出或提供 | 程序必须核验什么 |
| --- | --- | --- |
| 调用方显式传入 | 上层方法或用户 | 输入槽、类型、业务口径和当前调用允许使用的范围 |
| 前序步骤产物 | 程序根据依赖绑定 | 上游实例、已验收的产物版本、字段和口径是否匹配 |
| 用户资料或连接器资源 | 模型可提议选择；用户按既有定数据与授权流程确认 | 资料身份、访问授权、资源约束与本次用途 |
| 需要语义判断的参数 | 模型提出候选值 | 可检查的条件及证据；不能确定时请求确认，不把模型判断写成授权事实 |
| 受控环境信息 | 宿主提供 | 来源可信、类型明确、仅向本次调用提供必要信息 |

“未赋值”必须与“允许缺失”区分。必需输入缺失时等待补充或按规则失败，不能自动改成可选、填零或从对话里猜一个值继续执行。业务语义不能完全靠类型检查保证，口径校验和必要的人确认仍要保留。

### 3.2 方法输入如何生成

对已确定的计划，程序逐项检查步骤输入：由内部前序产物供给的输入保留内部绑定；需要上层、用户或外部资源提供的输入形成对外要求。同名但主体、期间、单位或授权范围不同的输入不能直接合并。需要访问的资料与连接也不能都当作普通参数要求用户手填，而应接到已有定数据和连接绑定流程。

动态方法分三个阶段表达输入：

| 阶段 | 可以确定的内容 | 不能据此作出的推论 |
| --- | --- | --- |
| 孵化与选用 | 各候选分支可能需要的输入类别、条件，以及所有有效计划共有的要求 | 不能把全部候选输入都列为本次必填 |
| 本次计划确认 | 已选分支的具体输入要求、已满足项和待补项 | 不能把未展开部分冒称为已经完全确定 |
| 下层展开与派发 | 当前子调用的精确输入绑定和资料版本 | 不能从整件委托已确认的数据中任意取用 |

上层不必预先知道所有后代输入的具体值，但必须知道下层的调用接口或可能需求范围。下层只能在上层明确传入且授权覆盖的资料中绑定；需要额外资源时按规则补充，不能把展开当成扩权通道。

## 四、能力承诺、步骤产物与方法返回

### 4.1 区分声明、计划与实际交付

能力声明与返回产物有关联，但职责不同，不能把二者都变成两份人工维护的详细输出说明。

| 时间 | 要表达的内容 | 主要使用者 |
| --- | --- | --- |
| 孵化与选用 | 方法承诺解决什么问题，哪些产物必有、哪些仅在特定条件下产生 | 用户与负责选方法的 AI |
| 计划确认 | 本次选择交付什么，由哪些步骤或子方法负责 | 用户与计划校验程序 |
| 执行结束 | 实际交付的产物、版本、证据和未完成项 | 上层方法、用户与验收程序 |

动态编排不意味着所有产物都事先不可知：可以有所有有效计划必须交付的公共产物，也可以有按分支选择的产物。作者应明确两者，不能以“动态”为由取消结果承诺。

### 4.2 用导出映射生成返回接口

步骤产物声明名称、类型、业务口径和证据要求，并明确哪些是内部中间结果、哪些允许对外导出。方法返回由导出映射生成，至少要能确定：对外名称、来源步骤或子调用、来源字段、产物版本及适用条件。

程序不能把最终步骤的全部输出简单拼接，也不能自动暴露内部资料。需要汇总、计算或改写的返回，应由显式步骤或程序块完成并验收；“汇总视图”本身不暗中添加模型推理或业务计算。

每条能力承诺通过结构化引用关联相应产物，程序检查引用存在、分支覆盖、类型匹配及计划是否履约。自由文字承诺是否真正兑现仍需业务验收，不能声称只靠字段关联就能证明内容正确。

技术调用的成功、失败或结果未知，与业务上的完成、不适用、部分完成分开记录。平台提供公共状态约定；各方法仍负责定义“不适用”和“部分完成”的成立条件、所需证据及是否允许上层继续。

### 4.3 第一层能力与跨层影响

能力声明引用直接候选或调用的方法及其版本，区分可能使用和本次已选。引用的能力不能被夸大；组合方法自身的新结果承诺由组合规则和本层验收支撑，不能简单求下层能力并集。

封装不隐藏风险。程序应沿依赖分析资料需求、账号、外发目的和费用：规划前披露可能范围与预算边界，计划确认时说明本次范围，展开后补充精确绑定。未确定的范围明确标出；不能把所有候选分支的需求都自动变成一次性授权，也不能把费用上界当作实际费用。

## 五、使用时编排、确认与复用

1. 作者固定候选方法版本、步骤执行规则、必做与条件必做、先后依赖、可选项、权限边界和验收要求。
2. 用户提出问题，模型在作者允许范围内形成顶层计划；固定计划由程序按作者规则生成，不增加无意义的规划轮次。
3. 程序检查方法引用、依赖、输入来源、最终产物、权限和预算。对不合法计划给出明确问题，不修改作者规则来迁就模型输出。
4. 用户查看并确认计划，可调整可选项及满足依赖的顺序。修改后须再次校验，不能删除必做项、破坏依赖或加入专家范围外的方法。
5. 执行到组合方法时，按需形成下层计划。只要没有超出已确认的目标、资料、权限、交付与预算范围，下层无需反复请求计划确认。
6. 超出已确认范围时暂停，提出明确变更；用户拒绝后按既定规则停止或形成有依据的部分结果。取消、撤权和预算耗尽均须能传递到下层。

顶层计划确认不代表之后每次写入或外发已经获批。发送邮件等具体动作仍须核对账号、对象、正文、附件和本次批准；审批规则不能被“计划已确认”覆盖。

已确认的计划可以保存并复用，但复用前要核对方法版本、适用问题、数据口径、连接状态、授权与预算。复用的是计划及允许复用的确认事实，不是自动延长旧凭据或旧写操作批准。职责等无人值守场景同样受这些范围约束。

## 六、递归语义与展开执行

### 6.1 首期方案：一个任务账本，保留调用层级，按需展开

递归描述方法调用关系；展开描述调度如何落地，两者并不互斥。首期建议沿用现有任务账本，把当前可执行的下层步骤展开到调度计划中，按依赖串行执行，同时保留完整的方法调用关系。

步骤依赖采用有向无环图（DAG）表达；首期选择满足依赖的串行调度，不把串行实现等同于方法只能是一条直线。方法间递归调用的循环检查与单个计划的 DAG 检查分别执行。

不为每次方法调用新建一套独立任务引擎。为子调用建立持久记录也不等于另造任务引擎；它是现有任务中用于核权、验收和恢复的执行记录。独立子任务可作为未来有明确需求时的方案，不能笼统断言所有嵌套执行都不可行。

执行顺序是：确认顶层计划 → 到达待展开的方法调用 → 生成并校验下层计划 → 绑定输入并执行 → 验收下层结果 → 按返回映射交给上层 → 验收上层结果。

### 6.2 展开不能抹掉方法调用边界

每次方法调用至少要有以下持久信息；字段名称在运行契约设计时确定，不以本表充当已实现的数据库 Schema。

| 信息 | 作用 |
| --- | --- |
| 调用标识、父调用标识、根任务标识 | 区分同一方法的不同调用，追踪层级及取消范围 |
| 方法标识与固定版本 | 确认使用哪份作者规则，不随市场更新漂移 |
| 所属步骤及计划版本 | 关联每次展开、确认和实际派发 |
| 输入绑定及来源版本 | 恢复时重建实际使用的数据，不重新猜测输入 |
| 返回映射及验收证据 | 子方法完成后正确交回，保留每层业务验收 |
| 当前权限范围、审批关联和预算归属 | 子调用不能扩大父授权，所有层计入同一根预算 |
| 执行状态、尝试与外部调用关联 | 断线重启后识别已完成、待批准和结果未知的动作 |

不能只靠“预测.回测.第三期”这样的显示名称承载层级。名称可以帮助用户阅读，稳定标识及父子关系才是恢复和核权依据。子方法验收通过不自动使父方法通过；父方法还要检查自己的结果承诺与导出映射。

正常的下层展开与因错误、缺资料或目标变化而重排，应分别留痕并限制次数。它们可以共用计划版本及已执行部分保护机制，但不能把每次合法展开都消耗成一次纠错重排。

### 6.3 明确的执行上限与恢复规则

- 独立限制调用深度、累计展开数量、总步骤数、方法调用次数及实际重排次数；计划最多 100 步等现有限制不能自动代替递归深度限制。
- 按当前祖先调用链检查循环引用；同一方法在不同分支中的合法重复调用按次数与预算约束，不能误判成循环。
- 整棵调用树共用根预算，子调用的额度只是分配，不能每进入一层就重新取得完整预算。规划、执行及重试成本均应记入。
- 已完成的执行事实不可改写。重新展开、重排或返工产生新记录，明确哪些依赖结果失效，不覆盖历史证据。
- 恢复依据持久化的计划、调用和尝试记录；未知外部副作用不自动重发，审批等待不持有长数据库事务。

## 七、权限与当前 C2 开发的关系

第二项按已确认决定改为“所需权限”，与输入视图分离。方法声明资源角色和操作需求；本次执行才绑定用户账号、资料及授权。具体业务权限不能只用 MCP 地址和工具名代替。

| 负责方 | 职责 |
| --- | --- |
| KnowLab | 编辑、校验并冻结方法规则、权限要求、依赖和导出声明 |
| KnowBench API | 工具登记、可信操作映射、连接与凭据、公共核权、审批和调用记录 |
| KnowBench runner | 按当前计划及父调用范围选用能力、准备步骤、派发和恢复；不持外部凭据 |
| 沙箱中的模型宿主 | 按本次范围暴露工具与 Skill，承载模型规划和工具请求 |
| 资源所有者 | KnowBase 等数据服务、本地 link 等继续复核自己的资料或目录权限 |

子调用的有效范围不能超过父调用已授权的范围，同时还要满足子方法自身声明、用户资源权限和平台规则。模型可以提出选择，不能授予权限；登记、暴露、授权和执行保持分离。

当前工具登记基础候选可继续使用，它不依赖“所需输入与权限”的旧名称。下一步业务权限契约按独立权限结构设计，并能关联父子方法调用；纯聊天与工作继续使用同一登记和核权机制，不为它们伪造一个方法或专家任务。

方法依赖交付仍须记录来源、版本和许可。允许用户安装某个 Skill 不自动意味着作者可以随专家包再分发；公开上架资质与资源访问授权也分别检查。

本方案不替代 [MCP 与 Skill 接入实施方案的统一任务清单](专家方案设计/专家使用方案/luna/mcp和skill接入实施方案.md)。C2 的权限结构应立即吸收上述边界；多层动态规划另做验证，不能把尚未实现的递归能力算作 C1–C6 已完成。

## 八、现有代码可复用什么、还缺什么

以下为 2026-11-14 静态代码核对，不是本次新增运行实验。

| 内容 | 已有基础 | 尚需实现或验证 |
| --- | --- | --- |
| 输入绑定 | `InputBinding` 指向前序实例；未来产物可在派发时绑定版本 | 通用外部输入视图、完整口径匹配、父子调用间的显式传参 |
| 计划与保护 | 存在计划版本、重排限制、已执行部分保护、候选与依赖检查 | 下层展开及其独立计数、调用层级、用户确认与修改的完整流程 |
| 返回 | 作者的 `planning.final_units` 约束最终方法集合；计划的 `final_outputs` 指向选中的实例 | 字段级返回导出、跨层产物映射、每层完成与验收 |
| 权限 | 既有连接归属、执行范围、精确参数审批；共同登记基础已有候选 | 可信业务操作、方法权限契约贯通、父子范围收窄与公共调用机制 |
| 确定性执行 | 平台通用计算工具及隔离脚本载体已有基础 | 确定性方法直接派发并接入统一结果、验收和计费，而非每个方法都开模型轮次 |

现有 `validate_composition` 只接受当前方法目录中的方法，输入只能引用前面匹配的方法，`final_outputs` 的键必须与作者的 `planning.final_units` 一致。因此不能仅把若干子步骤插进数组就声称实现递归；还须扩展子方法解析、计划校验和返回关联。

代码依据：[方法计划与输入绑定](../../../knowbench-app/knowbench-backend/app/app/domain/workbench/method_plan.py)、[方法目录与作者约束](../../../knowbench-app/knowbench-backend/app/app/domain/workbench/method_catalog.py)、[规划服务](../../../knowbench-app/knowbench-backend/app/app/application/workbench/method_planner.py)。

## 九、两层组合验证方案

先验证机制，再检验模型规划质量。使用“财务专家 → 季节性预测与回测 → 单季还原、同比、预测、回测”的例子，其中包含两次向下调用层级；该例用于机制验证，不将财务算法写成平台专用特权代码。

### 9.1 无付费模型的机制验证

使用合成输入、假驾驶器和受控工具适配器，至少覆盖以下情况：

| 验证点 | 通过条件 |
| --- | --- |
| 展开与执行 | 顶层计划确认后按需展开；执行遵守依赖；正常展开不误耗纠错重排次数 |
| 输入绑定 | 主体、期间、单位及版本匹配；缺项明确暂停；内部可满足输入不重复向用户索取 |
| 返回与验收 | 下层验收后按导出映射返回；上层仍独立验收；不暴露未导出的中间资料 |
| 权限 | 子调用不能扩大父范围；使用同一账号不等于共享全部权限；新增外发须审批 |
| 限制 | 拒绝循环、超深度、超次数和超预算；合法重复调用可以被区分 |
| 用户修改 | 可选步骤可修改；必做项、依赖及专家范围不能被绕过 |
| 恢复 | 展开提交、审批等待、派发后断线均可恢复；未知副作用不重放；取消传到下层 |
| 复用 | 计划可复用，但版本、数据、账号或授权变化后重新校验 |

### 9.2 真实模型的质量验证

机制验证通过后，在已授权的模型与费用范围内，对代表问题运行真实规划。记录候选方法、作者规则、输入口径、实际计划及版本、调用树、模型轮次、费用和各层验收结果。

检查该选的是否选中、不该选的是否排除、必做和条件必做是否满足、最终结果是否正确，并与可用的单层或固定计划比较。不能凭一个成功案例声称通用递归质量已验证，也不预先承诺一定节省费用。

原讨论提到 11-02、11-03 的单层动态专家联调，历史记录位于平台 `scripts/results/第二轨联调/`；本轮没有重新执行，也没有多层质量实验。该历史经验只能说明部分单层机制曾验证，不能替代本节验收。
