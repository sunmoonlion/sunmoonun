1. **意见是否正确吸收：核心机制与工程纠偏均已准确吸收（吸收率约 90%），且无机械照搬。**

## 三、问题二：它整合如何？（整体架构与行文评估）

### 3.1 整合得极好的四个方面

1. **保持了“唯一主稿”的清晰骨架，没有产生拼贴感**：
   Luna 没有把 H 稿作为外挂附录贴在文末，而是将不同维度的内容精准拆入主稿对应章节：
   - 顶层分类与市场两区 $\rightarrow$ 入 **§1.1、§1.5、§1.12、§3.5**；
   - 角色职责与物理隔离 $\rightarrow$ 入 **§2.10.1**；
   - 创意/模板到草图、宿主检索、展开器、差异包与承诺覆盖 $\rightarrow$ 入 **§3.2.1**；
   - C2 现状基线与后续六步实施切片 $\rightarrow$ 入 **§4.2、§4.3.1**。
   这样既吸收了新设计，又避免了同一规则在主稿不同位置出现两套表述。
2. **在多份方案碰撞处作出了正确的架构取舍**：
   当 H 稿与 Opus 评审稿存在张力时（例如：跨作者基础积木是否在 Stage 0 直接引用、AI 是否在孵化回合内二次调工具检索、是否首版就做动态拓扑并行调度、先做编排合流还是先做单指令工具测试），Luna 全部选择了**工程上可收敛、不破坏现有安全与账本不变量**的路径（见 §3.2.1 与 §4.3.1）。
3. **跨文档联动同步到位**：
   在修订主稿的同时，提交 `8324ecdf3` 与 `2d3df4843` 同步更新了 `decisions.md`、`methods.md`、`glossary.md`、《方法市场方案.md》《专家及专家团使用方案.md》《协作编排参考模式.md》《新财务专家孵化方案.md》，消除了“主稿改了两类、配套稿还在写三类”的跨文档漂移。
4. **严格区分“已验证代码事实”与“目标设计”**：
   §4.2 开头（L1101–1106）与 §4.3.1 第一行（L1165）如实记录了 2026-11-19 本地递归候选的真实边界（已验证同一冻结版本重复调用、独立父链、逐层导出与恢复，但仍限于宿主测试、唯一必做计划和零模型轮次 MCP 叶子），没有因为文档吸收了草图和动态分支就把它们写成已完成能力。

### 3.2 整合中存在的 4 处不足与待补缝隙（建议后续微调）

尽管方向与原则全部对齐，但在整合密度和局部衔接上仍有 4 处值得注意的问题：

#### 1. §3.2.1 压缩度过高（12 行正文承载了整套创作与编译规范），缺少结构化字段表
- **现象**：主稿在 §1.6.2（权限字段）、§2.1（步骤字段）、§3.1.6（`method_selection` 字段）、§3.2（模板字段）都提供了清晰的“建议字段—含义与约束”表格；唯独新增的 **§3.2.1《从创意或模板形成可审定的编排》（L986–997）只有 5 段高密度散文（共 12 行）**。
- **影响**：
  - 散文里提到了“编辑草图”“候选快照”“5 项无损保留内容”“完整差异包”“接口草案”，但没有给出 **`OrchestrationSketch` / `SketchStep`、`MethodCatalogEntry`、`ProposalBundle`** 的结构化字段表；
  - 开发者在实施 M0/M2 时，光读主稿 §3.2.1 无法直接对齐契约字段，仍必须回头翻阅参考资料中的 H 稿与 Opus 评审稿。
- **建议**：在 §3.2.1 中补充一张精简的**「编排草图、候选快照与差异包核心字段表」**，使 §3.2.1 的规格颗粒度与 §2.1、§3.2 保持一致。

#### 2. §3.1–3.2 的“通用多级模板 `T=(D,V,C)`”与 §3.2.1 的“编辑草图 `Sketch`”未挑明工程包含关系
- **现象**：§3.1–3.2 用了近 200 行阐述通用多级模板（`definition`、`variables`、`constraints`、`base_template_ref`、`bindings`、`constraint_refinements`），随后在 §4.3（L1159）声明“通用多级模板的存储、部分赋值、跨模板派生检查在具体方法闭环后推进”；而 §3.2.1 又引入了“编辑草图（Sketch）”。
- **影响**：读者容易把“模板对象”和“编排草图”理解成两套都要建的数据结构。实际上正如 Opus 评审稿 §3.7 所论证：**在 M0–M6 阶段，方法模板在工程上完全可以直接表示为“带未赋值空位（`candidates=()`）和槽位 `meaning` 约束的草图”**，由同一个 `elaborate()` 报“待赋值”诊断，无需另建模板展开器。
- **建议**：在 §3.2.1 开头或 §4.3（L1159）补一句明确衔接：**“在通用多级模板服务落地前，创作期的专家模板直接以带空位与槽位约束的编辑草图（Sketch）承载，共用同一展开器校验闭合。”**

#### 3. 工具积木的“前端 `ValueSlot` 编辑断头路”与“合格积木粒度标准”在主稿中缺位
- **现象**：
  - H 稿 §1（第 3 项）与 §3.0.1、§7（Stage 0）专门指出：当前 `knowlab-web-frontend` 没有任何增删/编辑 `ValueSlot`（`schema`、`meaning`、`required`、`on_missing`）的界面，工具方法作者连受控 `meaning` 都填不进去（只能手写 `.json` 上传），这是展开器按 `schema_ + meaning` 自动连线的硬前置；
  - 同时，H 稿 §3.0.1 提炼了“合格工具积木的四条粒度标准”（职责完整粒度适中、输入封闭内部不越界、载体与业务语义分离、出入口对齐共享 `meaning` 词表），以及同目录新整理的 [财务方法工具积木与模板提炼.md](./财务方法工具积木与模板提炼.md)。
- **影响**：主稿 §3.2.1 只写了编排侧怎么用 `meaning` 自动连线，却没写**工具方法孵化侧必须提供受控 `meaning` 词表选择与 `ValueSlot` 预设配置界面**；且主稿 L13 与 §3.3 只链接了旧稿 `原20个财务方法的工具方法提炼.md`，未链接同目录的 `财务方法工具积木与模板提炼.md`。
- **建议**：在 §3.2.1 或 §4.3.1 的“作者编辑与积木供给（M0–M2）”中补入**“工具方法工作台支持基于受控词表配置输入输出槽位（`ValueSlot`）”**，并在文首/§3.3 补上对 `财务方法工具积木与模板提炼.md` 的参考链接。

#### 4. §4.3.1 的“自组计划持久修订与继承已完成事实”尚未反哺回第 2 节正文
- **现象**：§4.3.1 第 6 行（L1170）写道：“自组计划有单独来源，持久保存修订、继承的已完成事实和待变更步骤；一次确认计划后，具体外发仍逐次审批。保存计划可供重新核验后复用，成为正式专家须经孵化。”这准确吸收了 H 稿第五节的 `Plan v1 -> Plan v2` 快照演进与 Opus 评审稿 §3.9/§6.3 的意见。
- **影响**：但翻回正文 **§2.8.2《修改、退出专家约束与复用》（L693–700）** 与 **§2.9.1（L723–733）**，正文里只写了“另存为用户自行修改的计划”，并没有展开“自组计划运行中途重排时如何生成新计划版本快照、冻结继承已完成步骤事实、仅对新增未覆盖范围补充确认”。导致第 4 节验收表比第 2 节正文规则多出一块。
- **建议**：在 §2.8.2 末尾补入两句与 §4.3.1 L1170 对齐的正文规则，使第二章设计正文与第四章验收出口完全闭环。
