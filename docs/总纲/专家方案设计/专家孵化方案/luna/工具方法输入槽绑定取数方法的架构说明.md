# 工具方法输入槽绑定取数方法的架构说明

2026-11-28 · 架构提案，待定稿与实施

作者可以在工具方法的输入槽上绑定一个取数工具方法。以资产平衡核验工具 Q01 为例，作者声明“报表行”可由某个取数工具的指定输出提供。使用者只需给出该工具所需的查询条件和获准使用的资料，就能直接委托 Q01 核验。宿主先取得报表行，再调用 Q01 的主体实现。Q01 单独使用或作为 M02 专家的一步，都沿用同一份绑定。

## 一、现有设计缺什么

Carbon 的方法契约用 `procedure.kind` 区分两种实现形态。`direct` 工具绑定一个主体实现，声明它需要的输入和能够交付的输出。`orchestration` 专家用步骤、输入连线和导出声明组合其他方法。现有编译器和递归执行计划遇到工具就结束该分支，将其计为一个叶子。KnowBench 已有 KnowBase 资料选择、版本绑定和受控读取能力。

缺口在于，工具的对外接口直接公开主体实现的输入槽。Q01 的脚本需要标准化报表行，于是调用方也被要求提供报表行。选择一份获准使用的原始报表，并没有告诉系统该由哪个方法把它变成 Q01 能使用的值。目前可以在专家图中显式安排取数和核验，但作者若希望 Q01 在各处都具备这个能力，就缺少一个能随 Q01 版本保存它的地方。[现行方法与递归编排方案](专家方法孵化与递归编排方案.md)

## 二、作者如何定义，用户如何调用

**一个槽仍然描述一种值。** “报表行”的类型、业务含义和校验要求由输入槽定义。作者在工坊选中该槽，另行登记它的取值方式。下表用 Q01 示意，取数工具及查询参数均为设计示例。

| 作者要确定什么 | Q01 示例 |
| --- | --- |
| 要填的输入槽 | Q01 的“报表行” |
| 谁能给这个槽供数 | 某个已冻结的取数工具，固定方法标识、版本及摘要 |
| 用什么查询 | 把调用方提供的公司、期间和授权资料引用分别传给取数工具的具名输入 |
| 取回什么值 | 将该工具的“标准化报表行”输出接入 Q01 的“报表行”槽，冻结前核对类型和业务含义 |
| 接受哪些来源 | 作者可以允许调用方直接供数，也可以要求报表行具备指定来源和资料版本的证据 |

绑定随工具方法的版本保存。运行账户、连接凭据和本次选中的资料归使用者管理。更换已冻结的取数方法版本，会改变 Q01 的执行依赖，需要生成新的 Q01 版本。

KnowLab 应从同一份定义生成对外可用的输入方式。若作者允许两条路径，KnowBench 和方法目录都应能表达“提供标准化报表行”**或**“提供查询条件及授权资料”。两组输入各自在相应路径内必填。这样只持有原始报表的用户也有机会匹配到 Q01，模型能根据已具备的条件判断可用性。取数工具已经由作者选定。

## 三、一次 Q01 调用怎样执行

1. **确定本次输入来源。** 直接供数时，宿主校验报表行。指定来源是承诺的一部分时，还要核对产生该结果的方法、参数和资料版本。使用取数路径时，则先检查查询条件、执行许可和数据访问授权。来源不明或两种输入相互矛盾时，在准备页明确本次采用哪份数据。
2. **在确认前展开依赖。** 宿主把本次实际需要的取数调用和 Q01 主体执行列入同一份计划，并据此展示数据范围、权限和预计费用。对上层专家而言，这是一个 Q01 业务步骤；对执行账本而言，自行取数的路径有两次可核对的动作。
3. **取值、校验、核验。** 宿主按冻结版本调用取数工具，把具名输出按 Q01 的槽位契约校验后，再启动核验主体。取数失败或返回值不合格时，记录出问题的输入槽和原因。回执应能把最后的核验结果追溯到所用数据和取数调用。

例如，M02 对同一份报表分别做期初、期末核验。如果上层已经取得两步所需的数据，就可以将同一份有来源证据的结果显式传给两个步骤。若公司、期间或资料版本不同，应分别判断已取得的数据是否适用。仅凭相同的工具名称或槽名，无法认定两次查询等价。[M02 的实际核验结构](M02报表勾稽核验专家实施方案.md)

## 四、对 Carbon 架构的影响

| 位置 | 提议的改动 |
| --- | --- |
| KnowLab 方法契约与作者工坊 | 将绑定保存为工具输入的取值规则，保留一个 `direct` 主体实现。按作者选择派生可用输入和所需权限。已有无绑定工具继续使用现有输入契约。 |
| 方法编译与依赖检查 | 把取数方法纳入冻结依赖，校验版本、参数来源、输出槽兼容性和权限上界。沿取数依赖检查循环和展开上限，包括取数工具本身也有绑定的情形。 |
| KnowBench 目录与递归规划 | 向模型披露该方法接受的输入方式、资料条件和代价。模型仍负责选择业务方法和编排原语，作者绑定的取数来源由宿主解析。 |
| 执行、审批与计费 | 工具独立调用和专家内调用共用输入解析。宿主计入实际取数动作及其费用，保留资料版本和结果回执。执行重试时，能够识别该次调用已成功取得的结果和已发生的费用。 |
| KnowMart 公开契约 | 购买者能了解需提供的输入、资料授权和可能发生的取数费用。作者私有实现及使用者账户凭据留在各自的权限范围内。 |

这种设计保留了 `direct` 的业务含义，即只有一个主体实现负责兑现该工具的交付。需要修订的是“所有工具在运行时都只有一次实际调用”这个假设。每个取数依赖都必须对应一个明确的输入槽；由多步共同判断、分支或汇总才能完成的业务目标，仍由专家编排表达。

把取数写进主体脚本也能取得数据，但宿主很难在用户确认前完整报价和核权。为每种数据来源另建专家包装，能复用现有执行图，却会让作者反复发布同一核验能力。将绑定归属于方法版本、将调用展开到宿主计划，既支持单独使用工具，也支持专家显式共享上游数据。

## 五、验收怎样证明设计成立

以下是实施后的验收条件。使用同一冻结版本的 Q01，以来源、参数和数值已知的样例核对结果。

| 场景 | 应观察到的行为 |
| --- | --- |
| 允许直接供数，调用方传入合格报表行 | 取数 0 次，核验 1 次，回执标明调用方供数 |
| 单独调用 Q01，只给查询条件和授权资料 | 取数 1 次，核验 1 次。与直接传入同一份报表行所得的核验结果一致 |
| M02 已准备好同一份符合来源要求的报表 | 各核验步骤接收上游结果，Q01 内额外取数 0 次。回执都能追溯到该份报表 |
| 强制指定来源，调用方只给无来源证据的值 | 准备页说明所缺的来源条件。有合法取数路径时展示范围和费用，经确认后取数 |
| 无权读取、取数失败或输出与槽位不兼容 | 失败可定位到相应的取数依赖或输入槽，Q01 主体核验 0 次 |
| 取数形成循环，或运行因中断而重试 | 循环在冻结检查时可定位。重试能复用同一次执行已完成且仍适用的结果，调用记录与实际费用相符 |

第一轮以工具独立调用和嵌入专家两条路径为实施范围。专家自身的公开输入能否复用同一机制，可以据此评估。已有版本的摘要兼容、冻结依赖、最坏费用上界与实际回执，应与上述业务场景一同验证。
