## 一、结论

1. **工程论证部分（Opus 稿第一至四节）吸收得准确。** 三处硬阻塞、两处“按原写法不可行”的纠偏、重排后的阶段顺序，都已落到主稿 §2.3、§3.2.1 和 §4.3.1。没有发现被误读或被反向使用的情况。
2. **主稿对 Opus 稿有两处合理的改写：**
   - 不把模板简化成“带空位的草图”；
   - 业务判断点沿用现有的澄清与 Interaction 机制，不新增“人工确认步骤”节点类型。
   这两处我认为主稿是对的。
3. **漏掉或只吸收了一半的，主要是治理和落地细节：**
   - `meaning` 词表和积木目录的治理流程；
   - `ValueSlot` 预设编辑界面；
   - “单个非 MCP 工具今天还无法测试冻结”这一现状事实；
   - 常驻例程的命名与接口；
   - Opus 稿第五节 6 项待拍板决定的去向。
4. **整合稿自身还需要完善的地方集中在三处：**
   - 两套路线表并存且互相没有映射；
   - 新设计字段与现有 `formal_method.py` 契约之间缺对照表；
   - 新旧两条代码线（`formal_method_*` 与旧 `method_plan.py`）的现状写在一起，读者分不清。

### 2.3 主稿有意不采纳、且我认为它对的一处

- **Opus 稿 3.7：“模板实现为带空位的草图”。** 主稿 §3.2.1 L988 写的是“模板仍可约束五要素中的任一项；‘待选方法’只是其中一种变量”。按 §3.1 的定义，模板变量可以落在能力声明、权限、校验、审批上，不只是步骤候选。把模板压成草图空位会丢掉这些变量。所以主稿只把“待选方法”这一类变量交给草图，是更准确的处理。
- **据此修正同目录评审的一条建议**：《吸收与整合评审》3.2 第 2 条建议写“专家模板直接以带空位草图承载”，应收窄为“**步骤结构类变量**以草图空位承载；其它要素上的变量仍按 §3.1–3.2 表达”。

## 三、问题二：整合稿还需完善的地方

按对后续实施的影响排序。

### 3.1 两张路线表并存，缺映射（影响最大）

§4.3 的 M0–M6 表（L1143–1151）与 §4.3.1 的“C2 之后的工程顺序”表（L1163–1170）是两套切法：前者按里程碑，后者按能力范围。两者之间没有对应关系，而且内容已出现不一致：M2 行写“供给基础方法”，§4.3.1 写“示例定义导入、各自冻结”。实施方和 qwen 评审方会不知道以哪张为准。
**建议**：保留 M0–M6 作为唯一里程碑编号，在 §4.3.1 每行标注所属里程碑（主稿已部分标注），并同步修订 M2、M3 行的交付描述。

### 3.2 设计字段与现有契约之间缺对照表

§2.1 的步骤建议字段（`step_id`、`goal`、`run_condition`、`scope_narrowing`、`clarification_policy`、`failure_policy`/`recovery_policy` 等）与现有冻结契约 `MethodStep` / `Orchestration` 的字段（`select_when`、`required_when` 自由文本、`always_required`、`depends_on`、`on_failure`、`max_replans` 等）是两套命名。
主稿 L1121–1135 为**旧** `StepContract` 写了详细的字段去向表，却没有为**新** `formal_method.py` 写。M0 “契约先行”最需要的恰恰是这张表：哪些字段沿用、哪些改名、哪些新增（结构化谓词、角色、允许变化声明）、哪些改变 digest。
**建议**：在 §4.2 增加“现有 `formal_method` 契约 → 目标字段”对照表，并注明每项是否改变冻结摘要。

### 3.3 新旧两条代码线的现状混在一起

§4.2 前三段（L1101–1105）描述新的 `formal_method_*` 递归候选；其后的 2026-11-14 基线表（L1109–1115）、`validate_composition` 说明及代码链接（L1117–1119）描述的是旧的 `method_plan.py` / `method_catalog.py` 路线（两文件在 KnowBench 当前仍存在）。L1107 只用一句“以本节上方较新的核对范围为准”区分，读者容易把旧路线的缺口当成新路线的缺口。
**建议**：把 §4.2 拆成“目标代码线（`formal_method_*`）现状”和“待退役代码线（旧固定专家与 `method_plan`）”两小节，后者注明在 M6 随旧财务专家一起退出。

### 3.4 §3.2.1 信息密度过高

§3.2.1 用 5 段、约 12 行承载了草图、候选快照、展开器、往返无损、差异包、缺口分流、覆盖审阅七项规则，却没有像 §2.1、§3.1.6、§3.2 那样的字段表。开发时仍需回头翻 Hydrogen 稿和 Opus 稿。
**建议**：补一张“编辑草图 / 候选快照条目 / 差异包”的最小字段表，只列字段名与约束，不必展开实现。

### 3.5 未吸收的四项，补成短段即可

1. **词表与目录治理**（B6）：新增键的申请与审批、积木的推荐/废弃状态、官方积木的维护责任。可放在 §3.5 方法市场建设表中加一行。
2. **`ValueSlot` 预设编辑**（Opus 稿 3.6）：工具方法孵化页需要按预设类型（数值 + 单位/期间、表格、文本、枚举）和受控词表配置槽位。没有它，展开器的自动连线没有可用的 `meaning` 来源。可写入 §4.3.1 “作者编辑与积木供给”行。
3. **现状事实补齐**（A1）：§4.2 写明单个 `skill_instruction`、`skill_script`、`platform` 工具当前无法测试冻结，并给出代码依据链接。
4. **常驻例程**（B12）：确定沿用“职责”还是改称“常驻例程（Routine）”，并说明“上次成稿作为本次输入”在方法对外输入中如何声明（例如一个指向产出区引用的输入槽）。

### 3.6 小白引导流的作者确认底线（与 B4 相关）

主稿没有单独描述“只有一句创意的作者”的流程；按 §1.10.2 允许批量确认，AI 起草量最大的场景反而审定最薄。
**建议**：在 §3.2.1 末尾加一句：期望答案、金融口径与阈值、外部数据源不进入批量确认，必须逐项采用。

### 3.7 回炉派生分支标注依赖

§2.8.3 表中“获准派生的使用者”一行加注：依赖市场派生许可模型，在 M3 之后开放；当前只开放另外两条去向。
