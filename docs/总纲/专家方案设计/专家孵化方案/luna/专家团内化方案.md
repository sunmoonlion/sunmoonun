## 一、目标与核心判断

**专家是方法；专家的每个步骤调用一个方法，因此一个专家可以通过多个步骤调用多个专家，并将协作整体封装为另一个采用五要素两视图的方法。专家团由此成为方法的一种内部组织与使用形态。**

内化的目标是：用户仍能获得多专家分工、独立分析、交叉复核、汇总交付等能力；方法定义、模板、注册、运行、授权与记账使用同一套体系。产品可保留“专家团”这一名称或展示方式，但不由此派生另一套能力契约、工具中心或任务引擎。

这不是说所有方法组合都要展示为专家团。调用两次计算工具通常没有展示成员角色的必要；当独立能力、职责与交接关系有助于用户理解时，可以展示为协作专家及其成果。展示方式不改变底层方法身份。

本方案以三项条件判断是否内化成功：

1. 原专家团的实际需求能在统一方法架构中明确表达，不能依靠“模型自行协调”填补缺项。
2. 执行、权限、状态与成果能由程序管理和核验，不只在文档中换名。
3. 同一能力继续参与更高层组合时无需改用另一种契约，也不绕过原有权利和资源边界。

## 二、统一对象：定义、步骤、调用与实例

### 2.1 方法和步骤保持原来的边界

| 对象 | 统一定义 | 与原专家团概念的关系 |
| --- | --- | --- |
| 方法定义与版本 | 采用五要素两视图的原子方法或专家，引用确定的实现及依赖规则 | 专家及协作整体都可作为方法发布 |
| 步骤 | 专家内部安排一次方法调用，持有输入绑定、条件、依赖、输出与恢复规则 | 分析、质询、复核、汇总通过相应方法调用完成，步骤不独立注册 |
| 编排机制 | 平台按声明校验、绑定、调度和恢复，值处理限主稿的封闭清单 | 不在步骤中嵌业务代码；计算、转换、汇总内容及成稿调用方法 |
| 调用位置与选择规则 | 定义此处需要什么能力、怎样选择和绑定 | 原成员槽位可以归入方法模板中的待选调用位置 |
| 方法调用 | 某个步骤请求某一方法完成明确工作 | 原委派行为的一种实现，须记录输入、选中版本及实际绑定 |
| 方法执行实例 | 某次方法执行的状态、上下文、资源和成果 | 原成员子任务或团长运行的执行身份；不产生新的方法版本 |
| 模板 | 五要素作者定义的固定内容、变量与变量约束，两视图随定义生成 | 协作模板仍是普通方法模板，可逐级赋值具体化 |

“成员角色”是本次组合中的职责，例如分析者、复核者；方法身份是可复用能力的身份。一个方法可以承担不同组合中的不同角色，一个角色也可由满足约束的不同方法承担。

同一个专家方法对三个项目执行，形成三个独立执行实例。三个实例可以使用相同方法版本，但输入、上下文、授权、预算消耗和成果分别记录。不能把并行实例混成同一段会话，也不需要复制出三个方法资产。

### 2.2 统一契约，不把全部运行信息塞进方法定义

五要素及程序生成的两视图统一引用[主稿 §1.2](方法、步骤、组合与模板.md#12-五要素两视图)，本稿不另维护字段定义。协作方法的能力声明只承诺整体能够完成的工作；做法声明分工、候选、步骤输入与产物、交接和导出；校验落实成员结果接收、整体覆盖、分歧处理及最终验收；权限和审批继续受父子范围与具体动作规则约束。对外输入、对外返回由定义生成并校验，不能另行编辑。

身份、版本、作者和发布许可属于资产管理信息；连接与凭据属于受保护的运行绑定；具体执行状态、预算使用和调用记录属于运行账本。它们引用方法契约，不扩充作者要素，也不因统一字段而混存。

方法输入仍是对外要求，各步骤输入通过内部映射取得。无须设置统一的“输入第一步”，也不要求用户分别填写每个成员的中间输入。

### 2.3 内部保留边界，外部提供统一调用契约

组合不等于把所有成员正文拼成一段提示词。被调用方法继续保有自己的版本、输入输出契约、执行上下文及授权范围；调用者通过其接口使用能力，并按自身验收规则接受成果。

各级已实现并验证的方法均可按统一公共结构注册到 tools 中心。调用方可以请求执行一个完整专家方法，也可以调用较小方法；具体执行绑定决定它由程序、模型参与的流程或其他服务完成。

较长的方法执行需要可追踪的进度、等待、取消和成果取得机制，具体同步或异步接口须对齐现有任务协议。不能因为注册成工具，就要求把整个专家执行硬塞进一次短时 RPC，也不能仅返回任务编号就宣称业务已完成。

## 三、原专家团要求的逐项归位

下表是内化清单。左侧沿用旧稿措辞以便核对，右侧是目标归属，不代表已实现。

| 原要求 | 统一架构中的归属 | 必须保留的语义 |
| --- | --- | --- |
| 团级能力声明和交付 | 上层方法的能力声明、验收和返回契约 | 成员全部结束不等于整体完成 |
| 团长拆解与派工 | 作者规则内的计划生成及协调方法调用 | 计划生成与实际执行分开，程序检查依赖和权限，不在专家步骤嵌业务代码 |
| 成员槽位与角色 | 步骤内的调用位置、角色说明及候选约束 | 不凭角色名字生成能力或默认授权 |
| 固定成员、动态选人及替换 | 固定方法引用或完整的运行时选择策略 | 记录实际版本；替换重新检查契约、权利、费用与批准 |
| 成员独立上下文 | 方法执行实例的上下文与资源策略 | 同一方法多次运行不混淆输入和成果，不强制每次新建独立 Pod |
| 并行、接力与多对象分析 | DAG 依赖、汇合及受控的多实例执行 | 无依赖不等于资源一定可并发 |
| 交叉质询、意见冲突 | 复核步骤、证据比较、补充工作及裁决规则 | 保留不同结论，不默认多数投票或汇总模型总是正确 |
| 团长严格委派 | 某类协调模板的步骤权限与职责限制 | 可限定只能派工和汇总；不强制全部组合采用相同团长模式 |
| 成员成果交接 | 输入输出映射、版本化产物和来源记录 | 交接结果不自动赋予读取底层原始数据的权利 |
| 看板和“等谁、等什么” | 统一任务及嵌套执行的可视化 | 状态来自真实运行事件，能区分等待、失败和部分交付 |
| 用户、作者、执行者交互 | 统一交互请求及路由、审批和恢复机制 | 区分澄清、数据确认、作者选数和动作审批 |
| 作者按题挑数据 | 方法的数据需求与供给规则，衔接既有数据机制 | 最小暴露问题信息，保留预设规则、离线等待与超时处理 |
| 成员隔离与并发文件写入 | 执行资源、工作目录、写入权限及汇总责任 | 不允许多个实例无协调地覆盖同一成果 |
| 团级总预算和成员额度 | 调用树的预算分配、预留及消耗记录 | 重试、复核及汇总计入总预算；换方法不能绕过上限 |
| 跨作者组装和责任 | 方法依赖的组合许可、作者归属与来源记录 | 组合者无权修改被调用方法或扩大资料授权 |
| 成员版本、升级及撤回 | 版本依赖、执行快照及可用性治理 | 不静默换版；下架、撤权和历史留存分别处理 |
| 团级报价和分账 | 方法市场对组合依赖的交易与结算规则 | 使用资格、运行消耗和商业价格分别记账，不在本方案预定价格 |
| 成员桩测试和整团测试 | 被调用方法替身测试与组合方法端到端验收 | 子方法通过测试不能替代上层方法验收 |
| 长期目标或持续协作 | 通用任务的触发、状态保留和终止策略，见 6.6「职责」 | 方法定义可复用，但跨次执行的记忆和授权必须有明确生命周期 |

上述要求既适用于多个专家，也适用于一个方法调用多个程序工具或多个其他方法。这是将协作能力推广为通用机制的依据。

## 四、组合与协调的执行设计

### 4.1 团长是职责，不是强制的新对象

对于固定流程，由 runtime 按依赖调度即可。例如两项独立分析完成后进入复核和汇总，不必让一个模型反复决定哪个节点现在能够启动。

需要按问题拆解、挑选能力或解释冲突时，可以调用具备这些能力的协调方法。协调方法与其他方法采用相同契约，也可以被更高层方法复用。上层方法对整体交付负责，不要求总有一个常驻模型扮演人格化团长。

模型提出计划和调用请求，宿主程序校验并执行。模型不能通过一段“新分工”文本扩大权限、预算、候选范围或已批准的交付变更。

### 4.2 几种常见协作模式

| 模式 | 组合表达 | 需要额外确定的条件 |
| --- | --- | --- |
| 多方向并行分析 | 多个独立分支，汇合后校验和形成成果 | 分支上下文、共享证据范围、必要分支完成条件 |
| 接力处理 | 后续步骤显式依赖前序成果 | 口径、类型、版本、缺项与失效传播 |
| 独立分析后交叉复核 | 先隔离执行，再按规则交换成果、回应和复核 | 什么时候可见对方结果、最大轮数及保留分歧的方式 |
| 同一方法处理多个对象 | 按对象建立独立调用实例，再聚合 | 实例数量、资源并发、单项失败和整体覆盖要求 |
| 动态分工 | 先生成并检查候选计划，再执行或受控展开子图 | 选择约束、图版本、审批边界与重规划条件 |

DAG 适合表达依赖与汇合，但不直接容纳循环回边。有限的质询轮次可以展开为有界阶段；需要返工时，建立有记录的新尝试或计划修订，并标记受影响的旧结果。不能无限递归调用自身来模拟讨论，也不能把任意重试都算成安全重放。

### 4.3 调用层级与限制

上层方法可以调用内部还有组合的下层方法。旧稿提出的“团队只能嵌套单专家、最大两层”不再作为能力类型的永久限制；容量、递归和复杂度仍须受控。

建议由 runtime 施加调用深度、实例数量、时间、并发和预算上限，拒绝不可终止的调用循环。限额是运行政策，不要求用两种不兼容的资产类型表达。实例间的成果依赖也须检查，不能在调用层次看似无环时引入互相等待。

主任务完成必须满足必需成果与验收；可选分支未执行时，按契约披露范围。局部等待原则上只阻塞依赖它的工作，但共享资源或整体一致性约束可能要求进一步暂停，不能承诺所有其他分支都可继续。

## 五、模板和方法市场

**协作模板仍然是“五要素作者定义中的固定内容＋变量＋变量约束”，两视图随定义生成。**不用额外定义一种与方法模板并列的专家团模板协议。

例如一个模板固定“独立处理→交叉复核→汇总交付”的流程，将处理方法、复核方法、对象数量、数据范围和交付格式作为变量。逐级赋值可以形成某类项目评审模板，再形成采用确定方法或确定选择策略的具体方法定义。

步骤是主要结构变量，但选择范围不能只写成“从方法市场挑一个专家”。每个待选调用位置至少要表达：

- 所需能力、输入输出兼容条件和本次职责。
- 候选来源、可用版本及使用资格。
- 由程序、模型还是作者选择，以及选择时间和规则。
- 连接、执行环境、资源范围与预算约束。
- 无候选、调用失败和替换时的处理；何时需要用户确认。

未完成创作的选择与运行时有规则的选择分开。后者可纳入具体方法定义，但本次实际选中什么、依据什么、用哪个版本和绑定，必须进入运行记录。

**方法市场建设仍是重要工作。**它提供能力发现、契约、版本、组合使用资格与发布信息；工具中心提供可调用绑定及实际可用状态。候选选择须同时考虑市场资格、本次授权与环境可用性，不能用一个工具名称或 MCP 的工具列表替代。

组合可以保持被调用方法内部私有。调用者获得必要的公开契约和结果，不因组合、购买或成为“团长”就自动取得方法正文、作者知识库或其他用户凭据。

## 六、运行机制：方法定义之外仍须落实的工程能力

### 6.1 任务、调用实例与账本

沿用 knowbench 的任务、尝试、调用和成果机制扩展，不新增独立 TeamTask 引擎。以下是逻辑记录要求，不代表要立即新建同名表或字段：

| 记录内容 | 用途 |
| --- | --- |
| 根委托与上级调用关联 | 汇总进度、权限、预算和取消范围 |
| 方法版本、步骤及调用位置、实例身份 | 区分定义与运行，支持相同方法多次执行 |
| 图版本、尝试与实际执行绑定 | 记录重规划、重试和实际调用路径 |
| 输入引用、授权依据和输出引用 | 追溯交接、来源和本次使用范围 |
| 校验、交互、审批及其版本 | 判断结果是否可接收、等待什么以及能否恢复 |
| 费用与副作用结果 | 区分成功、失败、未知及不可撤销的外部影响 |

调用层次与成果依赖分别记录：一个实例属于某个上级调用，但可以消费获准的其他分支成果。方法定义之间的依赖、执行实例之间的关系、DAG 的步骤依赖不能混用一个 ID。

现有 `current_step` 和单个 `active_attempt_id` 等串行假设需要具体核对和适配。新机制未通过之前，不能直接并发启动多个旧任务并宣称已支持协作。

### 6.2 上下文、成果与资源隔离

每次调用声明传入什么，不默认复制整个父会话、所有兄弟成果或方法正文。独立分析场景应在首次分析时隔离其他成员结论；交叉复核阶段再按定义开放指定成果。

隔离粒度由实际需求决定，可以是独立线程、受限工作目录或独立执行环境。独立上下文不等于每个成员都必须拥有一个新沙箱；共享环境也不意味着可以共享全部资源和权限。

交接产物应能追溯提供方实例、方法版本、产物版本、输入口径、证据、业务状态、局限与使用范围。成果引用不自动变成标准化事实；需要入库或进一步加工时继续走既有数据链。

汇总必须保持原证据强度：缺项不能被润色为完整支持，分歧不能被消失，部分结果不能冒充整体结论。明确哪些内容可机械校验、哪些需要模型评估或人工判断，不承诺程序能自动证明所有专业结论正确。

### 6.3 权限、审批和交互

方法声明需要什么权限；本次委托授予什么；实际动作是否需要审批，三者分别处理。被调用方法得到的操作范围应同时受上级允许范围、自己的需求及实际资源授权限制。兄弟实例不继承彼此凭据，协调职责不产生额外授权。

审批绑定具体动作、参数或成果版本和有效范围。替换方法、修改收件对象、改变数据范围、增加费用等变化，依既有批准条件判断是否需重新确认；不能只凭“父任务已批准”一律放行，也不对已覆盖动作重复索批。

统一交互记录至少关联根任务、来源实例、尝试、问题类型与内容版本。澄清、数据确认、作者选数和行为审批在同一待办入口呈现，但保留不同决定权；协调方法只能依据已知事实补齐衔接信息，不能代用户新增授权或替作者作专业决定。

数据需求在语义、版本、权利与使用范围一致时才允许复用或合并请求。相同主体和期间并不必然代表可以跨账号共享，不能沿用旧稿“绝不重复查询”的无条件承诺。

### 6.4 作者按题选数据

这一需求归入通用方法的数据供给规则，单个专家与协作方法都可以使用：先按作者预设规则匹配，规则不足时产生明确工单，由有权处理的人补充。

工单只暴露完成选择所必需且获准提供的信息。作者不能因被调用而看到用户全部会话、本机文件或其他方法成果。等待、离线、超时、改选与缺项的处理须预先约定，不自动用无权访问的来源替代。

选择结果须落到可验证的数据版本和本次使用授权，再交给后续步骤。knowbench 不另建一份事实或许可主档。

### 6.5 预算、停止与恢复

总预算约束覆盖规划、所有调用、重试、复核和汇总。可按调用位置预留额度并保留收尾资源，但只有实际费用按确定规则入账；父层汇总子层消耗时不能再次作为新的消费重复扣除。

达到额度后停止相关新动作或进入明确决定流程，不能通过更换成员、递归调用或新建子实例绕开限制。共享计算或数据的费用如何归集，需要真实交易规则，不能由任务树结构自动推导价格或分账。

取消应传播到适用的未开始和运行中实例；已发生的外部动作单独记录，不能因父任务取消就标为已撤销。上游产物修订后，标记受影响的下游成果并决定重验或重跑范围，不能静默沿用旧版本。

恢复需核对方法与图版本、资源可用性、授权和审批有效性，并防止重复认领。外部写入已发生但未收到回包时保留结果未知，按幂等或查验能力处理，不依靠通用节点重试再次执行。

### 6.6 职责：长期交代、到时候自己醒

> 所有者 2026-11-10 定「要做，并进专家方案」，默认值同日定「1小时，不用问我；不是必须填」。原写在 Opus《请专家与执行》第 5.12 节；2026-11-12 所有者定以 Luna 稿为主稿，按本文的统一对象改写后并入这里（原文见 sunmoonun 提交 `d0e6d1831`）。仍是方案，未实施。

**为什么要做**：Grok Bot、WMA 都强调 Agent 的"持久责任"：它长期管一摊事，有身份和记忆，自己会醒，要人时才回来（[四家产品对照](../../参考资料/agent-team-opus.md)）。我们的委托一次一结：一个问题、一份交付，中途可以等数据、等人，但不会自己反复跑。按所有者 11-10 提出的对应关系逐层对，缺的是中间那一层：

| 层 | Grok Bot | WMA / WorkBuddy | 我们 |
| --- | --- | --- | --- |
| 定义：冻结的配置 | Bot 的指令、技能、规则（用户在对话里交代，不带版本） | Agent 版本里的 Manifest：系统提示词、编排的技能与专家、外部服务；生产版本不许原地改 | **方法的发布版本**（专家也是方法）：五要素作者定义、生成视图及依赖随版本冻结，实际账号和授权在运行时绑定。和 Manifest 不同的是不钉模型，模型是用户自己的 |
| 执行环境 | 每个用户一台常驻云电脑，同一用户的几个 Bot 共用 | 一个会话独占一个沙箱 | 云端沙箱：一个账号一个，加上 link 接用户电脑；粒度接近 Grok |
| 长期在的那个"它"：定义 + 环境 + 交代 + 记忆 + 自己醒 | Bot 本身，带例程 | 下发给员工长期用的 Agent 及其会话 | 以前没有，**本节的「职责」** |
| 一次运行 | 一次例程运行或一轮对话 | 会话里的一轮 | 委托（根任务）及其下的方法执行实例 |

**不改的**：委托照旧一次一结，费用、授权、留痕、验收都按一件委托算；不做长期运行的任务。职责在委托上面一层：每次醒来生出一件普通委托，也就是所钉方法版本的一次根执行，照本文和[方法、步骤、组合与模板](方法、步骤、组合与模板.md)的统一机制跑。第三节表里「长期目标或持续协作」那一行由这里承接。

**职责是什么**：用户自己的一份配置，归用户本人，存在 knowbench；配置带版本，每件委托钉住当时那一版。

| 项 | 写什么 |
| --- | --- |
| 谁来管 | 哪个方法（专家）的确切发布版本，或者通用模式；作者出新版不自动换，职责页提示"有新版"，用户点了才换 |
| 长期交代 | 一段话，比如"每季报出来就跑一次财务分析，和上一期比，有异常写在开头"；每次醒来连同这次的新东西一起，当这件委托的问题 |
| 数据范围 | 管哪些主体、要哪类资料；按 knowfeed 订阅的范围写，一份职责可以带一份订阅 |
| 什么时候醒 | 定时、订阅取到新资料、连接器触发，可以有几条 |
| 哪些事不用问我 | 默认什么都要问；只能放开下面「不用问我」那一类 |
| 费用上限 | 每次多少、每月多少，**可以不填**；填了，到了就不再醒、等用户续；不填就不按钱停，职责页照样显示累计花费 |
| 结果交到哪 | 默认进这个项目、在 web端「待我看」里出一条；以后可以加邮件、IM（连接器） |
| 状态 | 启用、暂停、停用；停用以后不再醒，正在跑的那一件照常收尾 |

**醒的来源**（并进[连接器方案](../../../连接器方案.md)「触发」那一层，一套实现）：

1. **定时**：按日、周、月或固定间隔，**最短间隔 1 小时**。每次醒都是一件付费委托，宁长勿短。
2. **订阅取到新资料**：knowfeed 订阅看到新公告、取回新资料，就叫醒这份职责。
3. **连接器触发**：邮箱来了符合条件的信等。

同一个来源同一个东西只叫醒一次，按来源给的唯一编号去重。叫醒时上一次还没跑完，就排在后面，不并发跑同一份职责。

**每次醒来做什么**：

1. 生成一件委托：问题是长期交代加这次叫醒带来的东西（哪份新公告、哪封信、"到点了"）；方法是钉住的版本；项目是这份职责所在的项目。
2. **记得上次**：上一次委托写进 knowbase 产出区的成稿，作为这一次的一项输入，钉确切版本。这就是职责的"记忆"，不另造记忆存储；跨次的记忆和授权因此都有明确的生命周期（第三节最后一行的要求）。
3. 照常跑、照常验收。要数据确认、要审批的，按「不用问我」放过的就过；没放过的照常停下等人，并在「待我看」里出卡片。
4. 交付后在职责页记一笔：哪次叫醒、哪件委托、花了多少、交了什么、有没有停下等人。

**不用问我**（所有者 11-10 定照这个收法）：只能放开这份职责里、同一方法同一版本、同一个数据范围里**已经批过的那一类**。

- 数据确认：数据范围内、同一类资料的新一期（比如同一家公司的新季报）可以不再确认；范围外的、新主体、新类型照样要确认。
- 审批：只能放开方法审批要素中标明且平台允许预先批准的动作；写操作（发邮件、改外部文件）一律要问。
- 新的权限（新连接器、新外部 Agent、新数据授权）一律回来问人。
- 自动确认照样写进这件委托的记录，写明"按职责某某、配置第几版的事先确认"。这和 6.3 一致：父任务或职责批过，不等于一律放行。

**跟现有规矩怎么对上**：

- 合规边界：交代、范围、放行规则都是用户本人写的，"逻辑和数据来自用户"照守；方法照旧是作者的，职责只是"用户让这个方法长期替自己管一件事"。
- 每件委托照旧走定数据、签运行授权、读数留痕；用户的模型、用户出钱。
- 预算、取消、恢复照 6.5：一件委托的调用树不能靠职责绕过上限；停用职责不撤销已经发生的外部动作。

**页面**：项目里加「职责」一栏，列出各份职责、下次什么时候醒、最近几次的结果和花费、启用和暂停；新建职责从专家详情页或项目里点「交给它长期管」；web端「待我看」汇总各份职责停下等人的卡片。

**怎么验**（远程真库、假驾驶器）：三种来源都能叫醒且只叫醒一次；叫醒生出的委托带上一次的成稿；范围内的新一期自动确认、范围外照样停下；填了上限的到上限不再醒；暂停、停用、方法出新版都按上面走；同一份职责不并发。

组合作者负责其编写的分工、选择、交接、校验与交付规则；被调用方法的作者继续负责自己的方法版本。组合者不能替换或改写成员内部逻辑而仍声称使用原版本。

调用某方法的权利、组合并发布的权利、读取底层数据的权利和查看方法正文的权利分别核对。具体价格、分账、退款和下架缓冲期仍按后续确认的市场规则实施，本方案不作新的商业承诺。

固定依赖不得随被调用方法升级而静默变更；动态选择依照已发布策略并记录本次解析结果。版本钉住能固定部分依据，但模型、外部服务和数据变化仍可能影响运行，不能承诺仅钉版本就百分之百复现。

撤销使用权、普通下架、服务暂不可用和强制停止是不同事件，分别决定新调用与在跑实例的处置。保留历史证据不等于继续拥有读取或执行权；重启和恢复仍须检查。

## 八、工具中心、MCP 与 Agently 的关系

内化专家团不改变此前确定的两端接入方向：后端维护统一目录及受管理绑定，后端 runtime 与 Codex 环境各有真实的工具注册与调用机制。

上层方法的步骤既可以由后端直接调用确定方法，也可以启动 Codex 轮次，让模型在允许范围内提出工具请求。专家方法可通过合适的工具接口被调用，但不要求所有方法都包装成 MCP，也不要求把所有内部步骤发布到模型工具列表。

Codex 直连 MCP 与后端接入分别落实授权和观测，不能因为整体已经是一个方法就推断两端自动同步工具、凭据或批准。同一能力的不同绑定仍有不同环境和账号边界。

Agently 可作为步骤 DAG 和后端 Action 分发的实现候选。其图状态、默认校验和审批字段不能直接替代本方案的业务验收、运行账本及动作审批。框架节点结束不等于某位专家交付合格，子图完成也不等于父方法成功。

## 九、贯穿示例：项目方案的编制与交叉复核

以下是结构示意，不是已发布的方法或可执行配置。上层方法承诺根据获准资料形成项目方案及复核记录；采用五要素两视图，输入与交付视图由做法中的声明和导出映射生成。

```text
             ┌─ 调用方案编制方法：实例 A ─┐
获准项目资料 ┤                           ├─ 交叉复核 ── 必要补充 ── 汇总并验收
             └─ 调用约束检查方法：实例 B ─┘
```

1. A、B 从方法输入取得各自所需资料和授权引用，初次处理时不看对方结论。
2. A 可以在内部再调用多个方法；B 可以主要由程序规则与模型检查共同完成。上层不因此改变调用契约。
3. 交叉复核步骤映射两份明确版本的成果，调用复核方法并整理分歧。该步骤本身不必注册为方法。
4. 需要补充时，按有界规则形成新尝试；涉及新增资料或超出已有批准的动作时，生成对应交互请求。
5. 汇总只使用实际取得且符合接收条件的成果。必要成果缺失时返回未完成或按契约允许的部分成果，不生成虚假的一致结论。

若把“编制方法”和“检查方法”留作有约束的待选变量，就得到协作模板；赋值后形成更具体的方法。若上层又调用三次该方法分别处理三个项目，则产生三个执行实例，再由更高层方法进行比较。整个过程不需要增加专家团专属类型。

## 十一、内化完成的验收条件

| 验收场景 | 必须证明什么 |
| --- | --- |
| 一个方法调用另一个复杂专家方法 | 同一契约可解析和执行，内部结构不要求调用者换用团队专属接口 |
| 同一方法处理多个对象 | 实例、上下文、权限、成果与费用可分别追溯，无交叉污染 |
| 三层以上的有界组合及非法递归 | 合法组合可执行，循环与超限被阻止，不靠固定两层类型限制 |
| 固定或动态选择方法 | 候选约束、实际版本与绑定可核对，无候选或无权限时明确失败 |
| 独立分析与交叉复核 | 前期隔离生效，后期只交接获准成果，分歧保留并按规则处理 |
| 必要分支失败或可选分支跳过 | 影响范围与交付状态真实，不能仅凭框架 completed 判成功 |
| 用户或作者等待 | 交互对象、内容版本和授权可追溯；不依赖的工作按资源规则继续 |
| 替换方法、上游修订、版本升级 | 重新检查影响范围，不静默更换已运行依据，不沿用失效结果 |
| 撤权、审批失效与预算耗尽 | 子调用和恢复不能绕过限制，也不由协调者自行扩权 |
| 取消、重启和重复恢复 | 不丢失已知状态，不盲目重复外部写入，未知结果如实保留 |
| 跨作者组合与市场下架 | 调用、组合、数据和源码查看权分开；历史记录与新调用资格分别处理 |
| 无独立专家团协议的端到端交付 | 孵化、发布、调用、看板和验收均由统一体系承接；协作展示只投影真实记录 |

上述验收尚未执行。方案上的内化以要求完整归位为准；工程上的内化以真实执行和故障场景的证据为准，不能把写完本文当成能力已经上线。
