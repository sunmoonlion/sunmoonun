# 专家及专家团孵化模板

日期：2026-11-14。原名《方法、步骤、组合与模板》，按所有者要求改名为《专家及专家团孵化模板》；文中统一方法定义、工具方法基础、步骤、组合及模板规则继续有效。本文合并原独立实施稿与分类稿，吸收所有者与 qwen、Luna 的讨论及复核，作为方法定义、步骤、组合、模板和方法实施要求的唯一主稿。C1–C6 的任务状态仍在接入实施方案维护；本稿规定共同契约及落地依赖，不另建进度账。以下为已确认的目标规则，尚未因合稿完成协议、资产、代码或部署切换。

**方法分为工具方法、专家方法、专家团方法，统一采用五要素两视图。三类都须孵化、冻结版本后进入可调用目录。专家方法与专家团方法共用编排，每步调用一个方法；工具方法直接派发实现，且不调用其它方法。步骤不是方法。**

2026-11-14 最新决定以三类取代此前“原子方法与专家两类”“不设专家团类型”的分类。原子方法更名为工具方法；专家团是同一方法契约中的组合类别，不另建契约或执行引擎。此前对步骤边界和五要素两视图的决定继续有效。财务专家按所有者最新决定以新身份重新孵化第一版，删除原财务专家的全部版本及专用旧路径，不再要求等价迁移后清理。历史成果和必要运行证据保留，不恢复旧执行入口；具体范围见[首版孵化方案](新财务专家孵化方案.md)。只有一种合法计划仍按依赖归类，不另立固定专家类型。旧财务算法与审查内容仅作为可重新采纳的素材，模板逐级具体化和市场建设规则继续有效。

[原20个财务方法的工具方法提炼](原20个财务方法的工具方法提炼.md)只说明提炼思路和边界示例，具体 M01—M20 提炼另行开展。旧详细目录与审查资料从该稿第七节所列 Git 版本查阅；本稿 C01—C15 也仅是历史组合示例，不能作为已孵化资产。

## 一、统一方法对象与契约

### 1.1 方法三类，步骤与编排不是方法

| 方法类别 | 定义及边界 | 执行路径 |
| --- | --- | --- |
| 工具方法 | 原称原子方法；在平台可治理的执行边界内不调用其它方法，固定职责、实现流程与停止条件 | 直接派发到其实现 |
| 专家方法 | 调用工具方法和零种或一种专家方法，不调用专家团方法；至少有一次下层方法调用 | 统一编排执行 |
| 专家团方法 | 调用两种或以上专家方法，或者调用已有专家团方法；可以同时调用工具方法 | 与专家方法共用编排执行 |

“一种”按不同的方法身份（方法 ID）计数，不按调用次数、实例数、版本数或角色名称计数。同一专家分析十个对象仍是一种；同一专家的两个版本仍是一种，但各自精确版本和使用资格必须核对。只组合多个工具方法的属于专家方法。调用已有专家团的方法仍归专家团方法，不能套一层调用就退回专家方法。

分类依据是孵化时冻结的做法及允许依赖：对直接专家依赖按身份去重，出现专家团依赖则归专家团；候选范围中允许调用多个不同专家身份时按专家团孵化，即使本次只选择其中一种，也不临时变类。工具方法的实现中不得出现平台方法调用。身份或依赖类型未确定的候选保持未完成，不能猜分类进入可调用目录；运行时选择必须符合冻结的分类边界。依赖循环另行拒绝，不能用相互声明类型代替循环检查。

| 示例 | 分类 |
| --- | --- |
| 固定公式或固定模型判断，不调用其它方法 | 工具方法 |
| 读取工具方法 → 计算工具方法 → 成稿工具方法 | 专家方法 |
| 同一财务专家处理多个对象，再调用成稿工具方法 | 专家方法 |
| 财务专家与法律专家分工，再调用汇总工具方法 | 专家团方法 |
| 调用一个已有专家团，再调用成稿工具方法 | 专家团方法 |

| 其它对象 | 定义及边界 |
| --- | --- |
| 步骤 | 专家方法或专家团方法中的一次方法调用安排，持有输入、条件、依赖、输出和恢复规则，没有独立方法身份 |
| 编排机制 | 平台负责计划校验、绑定、调度、确认、验收推进和恢复，受作者规则约束；两种组合类型共用同一机制 |
| 实现代码 | 工具方法内部的函数、脚本或固定处理逻辑，随实现版本验证；专家和专家团步骤不嵌业务代码 |
| 模板 | 五要素作者定义的固定内容、变量和约束；生成视图随定义派生，未完成模板不可直接调用 |

三类共用五要素两视图、登记、权限、调用账和版本机制；执行仍只有“工具直接派发”与“组合编排”两条路径。“组合”表示组织下层方法的行为，不新增第四类方法；MCP 的“工具”是技术接口，可承载三类方法，不能把所有 MCP 工具直接判为工具方法。聊天、工作是会话，可调用三类方法，会话本身不登记为方法。

**方法之间的调用必须经过统一调用机制。** 绕过工具中心调用另一方法属于违规，不能因此宣称是工具方法。外部 MCP 工具或 A2A 整体接入可被孵化为工具方法，只是相对平台治理边界，不代表远端内部没有编排。平台若将其内部方法显式纳入受管组合，则按实际契约重新分类。固定实现使用程序库、通用引擎或隔离容器不算调用另一注册方法；读取或发送可以是该工具方法自身职责，但不能扩展为任意访问。其它工具方法所需资料从输入传入，不再调用读数方法。

工具方法可以包含固定的内部程序步骤、分段模型判断和有界修复；模型轮次不决定类别。首版只支持一个模型节点是实现限制，不是永久分类标准。凡需调用另一方法，就按依赖归为专家方法或专家团方法。唯一合法计划可以由程序生成，不另设固定专家类型；两种组合都执行 §2.9 的循环、深度、展开次数和预算限制。

方法库与知识库在资产职责上并列：知识库提供事实、资料和证据，方法库提供处理能力。方法定义归 KnowLab，市场及使用资格归 KnowMart，tools 中心解析可调用版本与执行绑定；平台基础方法同样必须孵化。后文关于专家的编排、步骤、授权、确认、验收及恢复等共同规则均适用于专家方法与专家团方法；涉及分类、登记和市场时分别列明三类。

### 1.2 五要素两视图

2026-11-14 所有者确认采用“五要素两视图”，替代“六要素”称呼。原结构借鉴[agent-team-argon 调研稿](../../参考资料/agent-team-argon.md)的作业指令组织方式，现按本项目决定统一用于工具方法、专家方法和专家团方法，不声称外部 Skill 标准也强制这些字段。

| 作者维护的五要素 | 工具方法 | 专家方法与专家团方法 |
| --- | --- | --- |
| 能力声明 `capability_declaration` | 本层用途、适用与排除范围、结果承诺 | 本层目标及承诺，引用直接候选/被调用方法的精确版本，不抄全部后代 |
| 所需权限 `access_requirements` | 资源角色、可信操作、范围、外发和缺项处理；纯计算明确无外部需求 | 声明可达分支需求及条件，运行时按本次范围绑定，并执行父子授权收窄 |
| 做法 | 固定流程、实现引用及环境、输入和输出声明、停止条件 | 候选方法、必做/条件必做、依赖及选择规则、步骤输入/产物声明、导出映射；步骤结构见第 2 节 |
| 校验 `how_to_validate` | 职责、输入口径、结果、边界与失败语义的检查及证据 | 计划合法性、各层产物、承诺覆盖和整体结果的检查及证据 |
| 审批 `what_requires_approval` | 动作、条件、预览、范围、等待和拒绝行为 | 计划确认及具体动作审批规则，确认计划不替代数据授权或写操作批准 |

| 程序生成的两视图 | 工具方法来源 | 专家方法与专家团方法来源 |
| --- | --- | --- |
| 对外输入 | 固定做法中的输入声明，规范化并校验 | 从步骤、候选和绑定规则归纳外部所需输入，内部前序产物不重复列为外部必填 |
| 对外返回 `what_to_return` | 固定做法中的输出声明，规范化并校验 | 从声明的产物、条件和明确导出映射生成，内部资料不自动交付 |

三类具有同一公共调用接口，runner 根据类型选择执行方式，不是调用方维护两套权限或记录。做法内区分固定实现与专家编排；现有 `sequence_of_work` 等字段应按第 4 节统一设计和生成，不把本文建议直接当作已生效 Schema。

两视图不能独立编辑。选用前必须有发布版本的接口范围、所有合法计划共同的需求/产物及条件；计划确认时形成本次具体接口，执行时固定实际输入、来源版本和产物。三层各有版本或计划依据，不能等排完计划才有承诺，也不能恢复时按最新定义重建而漂移。全部候选需求不能自动变为本次必填。

权限和审批没有方法自身要求须显式说明“无”，缺字段是未完成，不是无限权限；“无额外审批”不能取消平台和资源方要求。每个必需输入有来源或缺项处理，每项承诺有生成路径及验收；子方法成功不自动代表上层专家履约。孵化测试集和运行验收按同一规则留证，但不是把运行记录写回作者定义。

### 1.3 步骤声明输入，程序生成方法输入

专家作者为需要输入的步骤声明变量名称、类型、必需/可选、来源约束、业务口径和缺失处理；步骤也可以没有输入。工具方法在固定做法中声明输入输出，沿同样规则生成、检查和绑定视图；其内部处理不是专家的方法调用步骤。变量事先未赋值不等于变量没有定义。财务值按实际业务需要核对主体、期间、单位、币种、合并口径；不能仅因都是数字就判为相容。

| 内容 | 谁维护 | 含义 |
| --- | --- | --- |
| 步骤输入声明 | 作者随方法版本维护 | 本步骤需要什么，哪些来源有效，缺失怎么办 |
| 步骤绑定规则 | 作者定义规则，程序按实际计划解析 | 前序产物、调用方传值或授权资源如何接入输入槽；需要语义判断时由模型提出，程序校验 |
| 方法对外输入视图 | 程序生成 | 当前定义或计划尚需外部供给的输入及适用条件；不要求作者再填一份 |
| 本次输入绑定 | 运行程序固定并留痕 | 实际值或资料引用、精确版本、来源步骤/调用、口径及授权依据 |

| 输入来源 | 示例与边界 |
| --- | --- |
| 调用方传值 | 本次问题、期间、明确传入的数值或资料引用；按生成接口映射，不能把整段历史对话当作已核实输入 |
| 前序产物 | 已验收的季度序列、分析结果及证据；固定来源步骤或内部动作和版本 |
| 固定配置 | 作者已定的窗口、阈值、算法选项属于定义，不变成每次运行必填参数 |
| 有效授权资源 | 在本次允许范围中按声明选择资料或连接器资源，实际获取经受控动作并留痕；继承范围本身不读取内容 |
| 执行中补充 | 缺项、分支确定或明确变更后提供；按规则等待、核权并记录版本 |
| 受控环境信息 | 宿主提供与当前调用相关的可信信息，不接受模型自报授权或身份 |

输入视图按阶段生成：孵化/选用时展示共有要求和候选分支的条件需求，不将全部候选都列为必填；顶层计划确认时列出已选范围的已满足及待补项，明确未展开部分；下层展开后解析精确槽并固定绑定。同名但主体、期间、单位或授权条件不同的输入不能直接合并。

上层不必知道每个后代将使用哪份资料；须知道可调用接口、可能需求及影响范围。下层可在父调用可委派的有效授权与自身需求交集中绑定资料，不限于上层显式传值。共享同一任务的数据目录不等于可随意读取整件委托的资料；继承、收窄、补授权及撤权规则以 1.6.4 为准。实际选定的值与资料版本始终显式记账，恢复不得重新猜选。

进入方法、步骤或内部动作时检查输入类型、口径及范围，必需缺项按定义等待或失败，不能改成可选、填零或从模型复述中补造证据。已有相容数据时直接使用；只有实际存在取数、提取、转换或整理工作，才安排相应方法调用步骤，不人为增加统一的首个输入步骤。

### 1.4 调用来源、实现与 MCP、Skill

| 维度 | 回答的问题 | 表达方式 |
| --- | --- | --- |
| 调用来源 | 谁决定发起本次方法调用 | 宿主业务程序；模型提出工具调用请求后由宿主处理 |
| 执行实现 | 程序怎样完成方法 | 函数、命令行程序、脚本，或组织步骤的流程实现；需要推理时由宿主组织模型交互 |
| 接入方式 | 宿主怎样找到并访问实现 | 直接绑定函数、进程、HTTP 接口或现有流程入口；通过 MCP 注册调用代理 |
| 面向模型的呈现 | 模型怎样了解并使用能力 | 直接工具描述、MCP 工具描述、按需加载的 Skill 作业指令；这些形态可以配合使用 |

同一个方法可以允许宿主和模型两种调用来源，不能因此复制为两份方法。**模型提出请求，程序执行工具**；宿主直接发起的调用同样经过参数、版本和权限检查。

脚本是实现载体，命令行是启动方式。例如 `python cagr.py` 通过进程执行 Python 脚本；函数、脚本和命令行也都可以由 MCP 服务封装。MCP 工具的内部实现不一定对调用方公开，不要求调用方猜测其服务端使用什么语言或脚本。

MCP 提供工具发现与调用协议，Skill 承载作业指令及相关资源，两者不是互斥的调用协议。宿主加载 Skill 后，模型可以按指令提出工具请求，再由宿主经 MCP 或直接绑定执行；普通工具也可以不经过 Skill。Skill 须按 1.10—1.11 完成孵化、确认分类及契约，才可在聊天、工作或专家中使用；安装记录本身不授予调用资格。参考 [MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)与 [Agent Skills 说明](https://agentskills.io/home)。

代码逻辑只进入工具方法的固定实现，不嵌入专家步骤。孵化须固定实现边界及验证依据，不因使用脚本就允许模型临时生成并执行任意代码。

#### 1.4.1 实现载体与执行责任

载体不决定类型。下表描述目标支持边界，已交付范围以接入实施方案状态为准；通用公式引擎与 A2A 适配不能仅凭列入本表就视为可用。

| 载体 | 位置与责任 | 边界 |
| --- | --- | --- |
| 公式 | 经验证的通用计算引擎执行，确定性、不增加模型轮次 | 公式是作者定义的数据，适用域及业务判断由作者负责；不声明通用公式引擎已经实现 |
| 脚本 | 隔离容器运行作者代码，保持无凭据、无直接网络 | 工具方法脚本不能调用其它方法；需连接器方法时在专家计划另排步骤，业务输入由前序方法提供；开关验收前保持关闭 |
| 指令及参考资料 | 用户沙箱组织模型交互，使用用户配置的模型 | 不调方法的固定职责可为工具方法；需调用方法的 Skill 按 1.11 转为专家规则及计划 |
| 外部 MCP | KnowBench 共同治理入口核权、审批、记账，适配器访问远端 | 一个已孵化的远端工具绑定可作为工具方法；凭据不进入沙箱 |
| 外部 Agent（A2A） | 经共同治理的适配器访问外部 Agent | 相对平台边界作为整体接入，按外发及委托结果核验，不声称冻结了远端内部实现 |
| 平台后端函数 | 平台通用基础实现 | 平台作为作者孵化；不执行作者不受信代码，不内置作者的财务投资判断 |

工具方法之间可以共享有版本和验证依据的程序库或公式，但不通过隐藏调用复用另一方法。三类方法均可由任意符合要求的作者孵化；只有平台基础实现代码进入平台后端，不是只有平台才能创作确定性方法。

需要模型推理的工作由用户沙箱承接，API/runner 不另开后端模型推理通道。确定性实现可以位于后端、隔离容器或外部服务，不因模型在沙箱就全部搬入沙箱。

#### 1.4.2 方法依赖的来源、许可与公开边界

安装、执行、随方法交付是不同权利。方法发布时须冻结依赖来源、精确版本、规范文件清单摘要、许可及必要声明；ZIP 摘要只用于传输校验。交付前按许可检查是否允许向使用者提供内容，无交付权则阻止打包，或使用许可允许的独立获取方式；仅填写一个许可证名称不算通过。

公开上架仍由 knowmart 后端执行发布主体与服务类目的资质规则，依据项目 `C-L4`；默认自用及原有禁止导出、转让等边界不因支持 Skill 改变。公开资格、依赖许可、用户数据授权分别核验，任何一项不能替代另一项。公开可请不自动授予跨作者嵌入或转授权，相关市场规则留在其独立设计中，不借本轮打包功能默认开放。

### 1.5 三类方法统一注册与两条执行路径

工具中心只将已孵化、冻结的工具方法、专家方法或专家团方法版本纳入可调用目录；安装和发现快照先保存为候选，不能从 `tools/list` 直接进入模型可调用集合。字段拼写仍须映射现有协议并生成消费者视图。

| 部分 | 建议表达 | 职责 |
| --- | --- | --- |
| 身份与类型 | 方法 ID、版本、摘要、名称、作者、`method_kind`（工具方法/专家方法/专家团方法） | 类型固定在版本上，不按单次是否进入分支变化 |
| 公共契约 | 五要素两视图 | 同一用途、输入输出、权限、审批及验收约定；做法按类型表达 |
| 孵化与资格 | 孵化记录引用、验证范围/未覆盖项、发布资格 | 说明为何准入，不把孵化通过当作本次已授权 |
| 调用来源 | `allowed_callers`：宿主、模型或两者 | 不替代用户授权；模型提出请求，宿主执行 |
| 工具方法绑定 | 实现、适配器及环境引用；MCP 可含服务引用、工具名和映射 | 解析到固定实现直接派发；接入方式与方法类型分开 |
| 专家及专家团做法与执行器 | 冻结的候选、编排规则、输入/产物/导出声明及通用执行器 | 原则上使用时形成计划；唯一合法计划由程序生成，不另存一份可独立修改的流程 |
| 本次连接与范围 | 用户连接、资源、当前授权和审批引用 | 运行时绑定，秘密不进入方法版本或 Skill 包 |

```text
安装包 / MCP 发现 / 作者创作
        ↓ 生成候选、配置、孵化验证并冻结
KnowBench 可调用目录：工具方法、专家方法、专家团方法版本
        ↓ 宿主直接请求 / 模型请求由宿主处理
共同核验：版本资格、真实上下文、输入、授权、审批、预算
        ├─ 工具方法 → 绑定实现 → 结果与验收
        └─ 专家方法 / 专家团方法 → 形成并确认计划 → 逐步调用方法 → 本层验收
```

注册、暴露和授权分别处理。模型在聊天中请求工具方法无需专家计划确认，但写操作仍逐次批准；请求专家则进入一件委托的编排和确认流程。工具方法是实际的方法调用，也使用共同 call_id；不为聊天本身伪造专家父节点。

`tools/list` 是技术发现，`tools/call` 是 MCP 请求执行；既不能以同名认定等价，也不能以远端自报只读放行。安装、启用、线程加载和本次可调用是不同事实。当前平台内建工具也必须补齐平台作者的孵化证据，不能凭代码内置免检。

登记项与一次调用分开；调用记录关联 method_ref、绑定、输入、直接父调用、结果和验收，见 2.9。所有平台内方法调用使用统一治理，不另开放聊天里的未孵化原生工具旁路。执行位置与模型接入位置仍按 1.8、1.9 分别表达。

### 1.6 权限要求、审批与运行授权

本节为 2026-11-12 方案稿，明确方法结构；连接器、凭据、授权记录和执行检查的实现设计统一见[连接器方案第十节](../../../连接器方案.md#十权限与连接器实现方案2026-11-12-讨论稿)。本次只写方案，不表示字段已进入运行协议。

2026-11-13 补充：聊天、普通工作和各级方法（包括专家）共用连接器、用户连接及执行检查；方法只声明所需能力和资源角色，运行时绑定用户已有连接，不另保存方法专用凭据。进入方法、调用子方法或返回聊天均须按实际执行范围核权，不自动继承更大的权限。统一连接语义见[连接器方案 10.13](../../../连接器方案.md#1013-聊天工作和方法的统一连接器接入2026-11-13-补充)，前端接入和能力选择见 [MCP 与 Skill 接入方案 11.2](../../专家使用方案/luna/mcp和skill接入实施方案.md#112-前端三个入口及交互闭环)。

#### 1.6.1 权限要求与审批各负责什么

`access_requirements` 独立说明执行需要访问什么资源、进行什么操作及允许的范围；`what_requires_approval` 说明哪些动作必须取得怎样的批准后才能执行。用户已经接好服务，不表示任何任务都可以使用；第三方令牌允许发送，也不表示用户批准了某次发送。

| 内容 | 定义位置 | 示例 |
| --- | --- | --- |
| 所需访问能力 | `access_requirements` | 读取选定邮箱文件夹的邮件；发送本方法产出的报告 |
| 动作审批规则 | `what_requires_approval.rules` | 发出前展示发件账号、全部收件人、正文与附件，核本次批准 |
| 实际连接和资源 | 本次运行绑定 | 用户选的邮箱连接、具体文件夹和收件人，而不是作者的账号 |
| 授权及批准事实 | 运行授权与现有审批记录 | 谁在何时允许这件任务读取哪些邮件、批准了哪份待发送内容 |

能力声明向使用者解释这些条件，引用上述规则；不另存一套授权条件。方法定义不保存具体用户的密钥、连接身份或批准结果。可公开的服务类别与必要权限随能力声明展示，私有执行内容仍按原边界管理。

#### 1.6.2 权限要求的建议字段

第二项独立维护 `access_requirements[]`，不再保留 `required_inputs_and_access` 包装或重复的手写输入 Schema；输入按 1.3 生成，环境要求归实现与环境声明。仅做纯计算的方法显式填写空列表；空列表表示无外部访问需求，不能被解释为无限权限。此为新契约设计，未声称已有运行协议完成迁移。

| 字段 | 含义与约束 |
| --- | --- |
| `requirement_id` | 本方法版本内稳定编号，供步骤、审批及运行绑定引用；不是授权令牌 |
| `resource_kind` | 资源责任域，例如 `connector`、`knowbase`、`local_workspace`、`external_agent`；与函数、脚本、MCP 等实现或接入方式分开 |
| `resource_role` | 本方法内的用途名称，如 `source_mailbox`、`report_destination`，供运行时绑定具体资源 |
| `capability_ref` | 所需操作契约及版本，例如邮件读取契约；兼容连接器按已验证契约匹配，不能只因都叫“邮箱”就互换；确需指定供应商时显式限制 |
| `operations` | 明确允许请求的操作，如搜索、读取、创建草稿、发送；由适配定义映射到具体工具及外部 scope，不由模型猜测 |
| `resource_constraints` | 文件夹、目录、数据版本、期间、收件范围等条件；动态值引用已确认的方法输入或已验收步骤产物，执行时解析后再核授权 |
| `required_when` | 总是必需或仅特定分支必需；分支依赖和条件须可解析，不能靠模型临时把必需动作改为可选 |
| `data_transfer` | 是否外发、发往哪个资源角色、哪些输入或产物、用途；无外发显式说明，不能把远端查询隐含的数据传递略去 |
| `on_unavailable` | 缺连接、缺授权、资源不可用时的处理；必需项等待、失败或变更，只有预先定义的可选项才可跳过并记录未完成 |

范围表达采用有类型的资源选择条件，不允许任意代码作为授权谓词。值来自模型提议时，仍须按资源权限和用户确认范围验证。创建资源时可以约束父目录、目标空间及名称；发送时约束收件人和具体内容，不要求所有操作都先有资源 ID。

#### 1.6.3 审批字段与绑定

`what_requires_approval` 保留 `mode: none` 或规则集合。每条规则建议有 `rule_id`、`requirement_refs`、`operations`、`condition`、`approver_role`、`approval_scope`、`preview_fields`、`on_reject` 和 `on_timeout`。按次动作批准与已有任务范围批准须明确区分；不支持的条件或缺失字段不能默认为放行。

例如“整理邮件并发送报告”：读取要求绑定指定邮箱、文件夹和期间；发送要求绑定发件连接与获准收件范围。发送审批引用发送要求，预览全部收件人、正文和附件版本。阅读权限不推导发送权限；批准后更换账号、增加抄送或修改附件内容，必须重新核对批准是否覆盖。

运行时由宿主把 `requirement_id` 绑定到用户连接、knowbase 运行授权或本地执行目录等具体资源，并关联本次授权依据。原始凭据只由对应执行端按权限使用，不作为方法输入或步骤产物传递。专家步骤及工具方法实现可以引用所需权限编号，步骤不因此成为独立方法。

#### 1.6.4 组合、检查与验收

注册不等于允许使用，展示给模型也不等于已经授权。实际可用范围由方法声明、任务授权、用户资源权限和当前环境共同限制；工具方法实现同样受这些限制，不能成为绕过方法调用检查的路径。

专家需声明可达分支的权限需求及条件，创作时检查来源覆盖，运行时只为当前所需范围绑定授权，不把全部候选需求自动并成一次授权。**授权范围与输入传值分开：子调用以父调用允许向下委派的有效范围为上限，与子方法当前分支需求取交集；父调用可进一步收窄，不能放大。**

```text
子调用有效权限
  = 父调用当前可委派范围
  ∩ 子方法当前分支声明的需求
  ∩ 本次附加收窄条件
  ∩ 当前用户资源权限与平台策略
```

这是语义约束，不要求将异构资源简单做字符串集合运算。可信策略服务须比较连接账号、操作、资源选择条件、用途、数据去向及有效期；不支持的条件拒绝，缺少授权不当作无限范围。没有附加收窄条件不额外减权；方法无外部需求则不取得外部访问权。当前必需需求不能在交集中满足时等待补授权或按规则失败，不能悄悄省略必做项。

例如父调用获准读取甲公司 2021—2025 年报，下层回测方法声明需要 2023—2025 年报，可以在范围内自动选定并记录具体资料版本，不需要父方法逐份传参。它不能因此读取乙公司资料、跨用途使用或发送邮件。搜索与列表本身也受授权过滤；不是先看到整个委托或用户账号的目录再让模型自律。

继承的是执行范围，不是账号的全部权限、父调用的凭据或所有动作批准。作者自带数据、仅限特定方法/用途的同意和跨作者使用限制必须由资源方认可委派；原同意不允许下传时不能复制运行授权来绕过。父调用收窄、撤权、到期或取消后，尚未派发的后代动作立即失去相应资格，恢复和每次资源访问重新核验；已产生副作用如实保留，撤权不承诺回滚。

本次授权记录保存父范围引用及其修订/撤销依据，实际输入另保存值或资源版本绑定。继承范围不自动下载资料，不将所有内容注入模型上下文，也不取消输入绑定。未来父授权新增范围不自动扩张已固定的子范围，必要时以明确变更重新解析并留痕。

权限约束适用于宿主直接调用、模型请求及工具方法实现。连接器工具方法统一经 knowbench 的授权入口；纯计算实现不需要连接器。已有直接 HTTP、脚本或命令行如果绕过此入口使用第三方凭据，在改为受控执行并验证前不得视为满足本方案。knowbase 继续裁决数据使用权，link 继续检查本地目录、网络与执行上限，工作台不能代替它们放宽限制。

`what_requires_approval` 必填不等于每次运行必须审批。`mode: none` 只表示方法没有额外审批要求，不能覆盖平台或被调用方法的必要审批。宿主检查已有批准是否仍覆盖动作、对象和范围；满足时继续执行，不因进入另一方法或步骤重复请求。范围扩大或批准失效时按规则等待，模型不能自行批准。

允许某工具被调用，不代表必做动作已经执行。固定算法、必要检查和证据要求必须在流程及验收中落实。HTTP 成功、进程退出码为零或收到 MCP 结果，只能证明技术执行状态，不能替代业务验收。正确产出“不适用”可以是有效业务结果，不能与技术失败混淆。

运行记录保留精确版本与证据。目录刷新不能无记录地替换正在运行的实现；MCP 目录快照也不能证明远端代码被冻结，缺少版本依据时应如实说明可复现范围。

#### 1.6.5 安装、Skill 依赖与连接器绑定共用本契约

2026-11-13 补充：连接器与 MCP、Skill、方法步骤一起设计。安装包声明有哪些能力及依赖，方法第二要素声明本方法允许请求哪些操作和资源；本次运行才选择使用者的账号并取得授权。安装记录、工具注册、方法声明和用户授权是连续的四个环节，不能合并成一个“已启用”状态。

方法中的 MCP／Skill 实现选择引用本节的 `requirement_id`，不另存一份独立权限真源。Skill 的结构化依赖使用相同的资源角色、操作契约及约束语义，可放在平台安装元数据中，不要求修改标准 `SKILL.md`。方法作者校验依赖是否被五要素两视图覆盖；运行时按当前步骤和父调用范围再收窄。普通聊天本身不是方法，但调用的能力须有已孵化的方法契约；调用关联会话用途、账号和授权，不为会话虚构专家。

例如“读取邮件并生成周报”专家声明 `source_mailbox` 的读取要求和 `report_destination` 的发送要求，用户可绑定同一账号或不同账号。计划分别安排读取、脚本处理/模型成稿、发送方法，步骤之间绑定产物。读取或发送由连接器工具方法承担；脚本只消费已提供的输入，不运行中再调用连接器。批准启动脚本不批准发送成果。

统一安装不改变执行隔离：连接器凭据由后端持有，Skill 包可在沙箱物化，模型看到的是本次允许的描述和工具入口。脚本通过受控输入通道获得本次已绑定资料，不获得方法调用令牌或外部账号凭据。具体对象关系、脚本等待与恢复、当前实现差距见[连接器方案 10.14](../../../连接器方案.md#1014-连接器mcpskill-与安装一起设计2026-11-13-实施纠偏)。上述字段为实施目标，不能将当前候选中仅有 URL／工具名的 `MethodCapabilities` 视为已经实现本节权限契约。

### 1.7 能力声明就是五要素两视图的第一项

**能力声明替代原第一项 `when_to_use`，建议字段为 `capability_declaration`。它直接定义作者承诺的方法用途与适用边界，不是五要素两视图之外的第七项，也不是从完成后的方法契约另行推导的声明对象。**作者可以先写能力声明，再设计实现；也可以依据已有实现整理后确认。两种创作顺序都须核对承诺与实现是否一致。

能力声明回答“什么问题可以选择这个方法，预期得到什么结果，什么情形不应选择”。其内容统一如下，作为专家使用的方法也采用相同结构：

| 内容 | 声明要求 |
| --- | --- |
| 目标与结果 | 说明解决什么问题、产生什么直接结果；用动作、对象和结果表达，避免“全面分析”等无限承诺 |
| 适用范围与情境 | 明确对象、期间、口径、触发条件等影响选择的边界；只列与该方法相关的维度，前提引用输入与权限要求 |
| 方法与方法边界 | 说明影响选择的做法概要、固定内容和允许调整的范围；不在此重复完整步骤、程序块或私有正文 |
| 不适用与不承诺 | 明确排除的任务、方法、对象、结果和局限；未声明的能力不能默认存在 |
| 适用与不适用示例 | 用典型问题及近似反例解释边界，必要时说明需澄清的情形；示例不是测试通过记录 |

“预期结果”表达业务承诺，“返回产物”规定具体交付要求。例如前者声明“预测未来两个季度的收入并提供区间”，后者明确返回哪些期间、点值、上下界、单位、证据和文件格式。二者必须一致，但不重复维护完整输出 Schema。

原[能力声明规范（§10.1）](../../参考资料/动态专家实施方案.md)的八栏按五要素两视图重新归位：目标、适用范围、方法边界、排除项及示例由本项定义；详细数据前提归步骤输入并生成对外输入视图，权限前提归 `access_requirements`，交付内容与格式由步骤产物和导出映射生成 `what_to_return`，校验归入 `how_to_validate`，授权条件归入 `what_requires_approval`。条件不足时的具体处理在相关要素中定义，并由 `sequence_of_work` 落实；能力声明引用这些规则，不再另写一份。

一个方法可以在同一能力声明中列出多个具名能力项，各项明确适用条件、预期结果及所引用的要求。能力项编号用于引用和追溯，不是步骤编号，也不自动成为独立方法注册项。详细输入或交付因能力项而异时，须有明确对应关系，不能把不同条件混为无条件承诺。

组合后的能力由作者明确声明，必须反映本方法整体能够完成的工作，不能直接合并被调用方法的能力清单；内部调用 CAGR 不自动表示该专家接受所有独立 CAGR 请求。能力只引用第一层直接候选/被调用方法及版本，区分可能使用与实际选中，不递归抄写全部后代声明。数据、外发、账号和预算影响仍须沿依赖跨层核算；规划前披露可能边界，确认时展示本次范围，下层展开补齐精确绑定，未确定部分明确标出。子方法能力只能按其真实承诺引用，不能夸大；专家新增整体承诺须由组合逻辑和本层验收支撑。输入及权限等前提仍须在本次调用中检查，匹配结果不是保证完成的证明。

面向用户的能力卡、简介和模型选择材料，展示同一声明及所引用的必要条件；它们是展示形式，不另建可独立修改的承诺。公开展示不下发完整内部流程、私有代码或秘密。声明经作者确认随方法版本发布，边界改变形成新版本；测试结论与发布批准单独记录，不作为声明字段，也不以先有测试记录为填写声明的前提。

本节定义目标结构；既有表单、协议、市场声明和正式资产须同批切换。未使用格式直接替换，有数据做一次性迁移并对账，不保留旧格式读取、执行或双写分支。历史原件只作审计证据；字段建议和文档修订不代表代码已经完成。

### 1.8 MCP 的两种接入路径及工具中心的位置

**区分谁发起调用与谁负责治理。runtime 可以直接请求工具，Codex 也可以处理模型的工具请求；正式方法的两种发起方式都经过 KnowBench 可强制检查的调用入口。**工具实际执行在后端、隔离容器或外部服务，由绑定决定。聊天/工作使用同一已孵化可调用目录，不因原生配置绕过孵化和治理。

#### 1.8.1 先区分驱动、接入与执行

| 概念 | 本文含义 | 当前责任与边界 |
| --- | --- | --- |
| 任务 runtime | 推进步骤、验收、等待与恢复的宿主机制 | KnowBench 的 runner、advisor 等协作；不是用户沙箱或 Codex app-server 本身 |
| Codex app-server | 组织模型轮次、接收工具请求的模型运行环境 | 当前在用户沙箱 Pod 中；模型提出请求，宿主程序执行工具 |
| 平台调用入口 | 登记解析、当前上下文核验、权限、审批和调用记录 | KnowBench API 持有连接与外部凭据；runner 提供范围及可信上下文，不持有外部秘密 |
| MCP 客户端与适配器 | 建连、发现并请求远端工具 | Codex 可连接平台 MCP，API 的适配器再访问外部服务；网络请求来源与业务执行位置分别记录 |
| 工具实现 | 完成实际计算、读写或其他操作 | 可在平台、隔离容器、外部服务或经授权的本机执行端；不能从模型或客户端位置推断 |

现有专家主链由 `advisor.py` 的 `drive()` 与 `run_turn()` 组织模型轮次，runner 负责连接和驱动衔接。已有平台 MCP 的 `compute` 在后端计算，数据读取通过 `data_relay.py` 访问 knowbase。受管外部 MCP 已经由 API 转发，但两套权限判断和调用记录还未收敛；这些事实不表示任意新方法流程、程序块或五要素两视图核权已经实现。

#### 1.8.2 两条路径及适用方式

| 发起方式 | 正式方法的路径 | 适用情形 |
| --- | --- | --- |
| A：runtime 直接发起 | runner/步骤宿主 → API 共同调用服务 → 执行适配器 → 工具 | 已确定的动作，无须为调用已知工具额外开启模型轮次 |
| B：Codex 处理模型请求 | 用户沙箱 Codex → 平台 MCP 入口 → 同一共同调用服务 → 执行适配器 → 工具 | 模型在步骤允许范围中选择工具，平台核验真实轮次和调用身份 |

聊天/工作同样可以使用 A、B 的平台能力，不需要伪装成专家任务。两条路径共享安装资产、连接、权限规则和调用事实；模型发现目录、当前授权及实际调用仍是不同环节。API 经过请求路径不等于在 API 进程运行所有工具代码，也不要求全部结果经模型再解释一次。

Codex 原生直连外部 MCP 是技术形态，不是平台聊天/工作的孵化豁免。未接入共同核权、审批和记录的直连不能作为平台可调用能力开放；只做原生发现或文件加载时，也须限定为已孵化版本及当前范围，不向沙箱下发平台外部凭据。

#### 1.8.3 “给 Codex 安装 MCP”具体放入了什么

| 形态 | 安装或配置内容 | 实际执行位置 |
| --- | --- | --- |
| 平台受管远程 MCP | 服务登记、用户连接与平台网关入口；凭据留在 API | 外部服务或其下游；沙箱只看到获准的入口与描述 |
| Codex 原生远程 HTTP MCP | Codex 环境中的地址和其独立管理的认证配置 | 对应服务；登记地址不等于将程序装进沙箱，也不表示平台已支持任意服务 |
| stdio MCP | 服务程序、依赖、启动命令与受控工作目录 | 被启动的进程所在环境；在沙箱启动才属于沙箱执行 |

脚本包安装与远端服务登记分开处理。平台目前的外部服务目录为空，任意 stdio 安装不在已交付范围；这些形态是位置解释，不是功能已开放的声明。

#### 1.8.4 工具中心统一管理，多处接入

KnowBench API 负责受管工具登记、用户连接、凭据及共同调用服务；runner 按聊天用途或方法步骤选择范围，并准备 Codex 可发现的工具。Codex 负责加载、向模型提供描述、按请求调用。API 与 runner 即使来自同一后端仓，也可能是两个 Deployment，不能把内存对象视为跨进程共享。

绑定至少分别表达：能力身份/版本、实际执行适配器、服务引用、调用环境、用户连接引用、输入输出映射、可信操作映射和环境要求。业务权限要求来自五要素两视图，通过 requirement_id 引用；URL 和工具名不承担账号、操作和资源范围声明。外部凭据、账号秘密不进入方法版本或 Skill 包。

后端有登记不等于当前模型已看到工具，模型能看到也不等于获得授权。运行时选择必须真正加载到 Codex 当前执行范围；无法证明范围隔离时，不能用提示词声称“仅允许当前步骤工具”。

#### 1.8.5 权限、记录和后续验证

正式方法从 A、B 两条入口进入同一策略和调用语义：校验身份、版本、连接、操作、资源范围、数据去向及审批，然后派发。每次派发和回包均关联同一 call_id；原有数据所有者仍检查自身责任域，平台批准不替代 knowbase 的数据使用权。

结果区分发送前未执行、收到明确结果、结果未知；明确失败也不承诺已发生副作用回滚。请求可能发出后失去回包不得自动重发或改走另一绑定。恢复必须核查持久记录与当前授权，不靠模型自述或 runner 内存推断完成。

验证覆盖两个入口、聊天/工作/方法范围、无能力会话、缺依赖、撤权、换账号、断线重启及审批后的参数变化。实现、契约切换、独立复审和线上生效分别记录；具体顺序只维护在接入实施方案 §17.6。

### 1.9 工具中心的职责、部署位置与两端协同

工具中心是职责集合，不要求新建一个独立服务。方法定义归 KnowLab，发布与使用资格归 KnowMart；KnowBench API 管受管工具登记、连接与调用治理，runner 管执行选择，Codex 管模型侧工具发现和请求处理。

#### 1.9.1 “工具中心”包含哪些职责

| 职责 | 负责者 | 必须区分的事实 |
| --- | --- | --- |
| 能力登记与技术发现 | API 登记服务与适配器 | MCP tools/list 只是技术描述；可信业务操作映射来自核定连接器定义 |
| 场景选择与绑定 | runner 和现有 session/task/attempt | 用户安装一次；每个用途独立选择范围，不另造聊天和方法的资产库 |
| 模型暴露与加载 | Codex 所在环境，由 runner 准备配置 | 配置写入、线程已加载、模型可见、当前获准分别核验 |
| 账号与凭据 | API 连接服务 | 长期连接状态不等于本轮授权；连接可刷新、过期和撤销 |
| 权限与审批 | API 共同调用服务和现有 Interaction | 父范围只可收窄；命令前缀不能代替邮件/目录资源授权 |
| 调用记录与证据 | 共同调用记录及各领域证据 | 共用 call_id、结果语义；保留计算与读数证据的业务含义，不重复产生批准事实 |

#### 1.9.2 部署选择及本方案的取舍

本轮选择“API 统一受管登记和治理＋runner 选择与两条执行路径＋沙箱 Codex 加载”。聊天、工作和专家中，无论程序或模型发起的方法调用都走共同治理。原生发现/加载只是实现方式，不能产生未孵化的可调用旁路，也不另建直连授权账。

```text
KnowLab 方法契约 / KnowMart 版本与使用资格
                    ↓ 引用
        KnowBench API：登记、连接、凭据、治理
                    ↑           ↑
    runner 确定动作请求       平台 MCP 请求 ← 沙箱 Codex
                    ↓
        已核准调用 → 执行适配器 → 工具实现
                    ↓
        调用结果与证据 → runner 验收/恢复
```

工具实现可以在远端，后端无需复制其代码。用户电脑或沙箱内独有的工具，只有接通经过治理的执行委托路径后才能作为正式方法绑定；当前不能调用时说明缺环境或缺适配，不因目录存在就假定可用。

#### 1.9.3 身份相同，不代表绑定与运行实例相同

| 对象 | 含义 |
| --- | --- |
| 方法身份 | KnowLab 的统一五要素两视图、版本和摘要；原生工具技术描述不直接冒充正式方法 |
| 登记身份 | 工具来源、契约和版本；静态平台工具可投影登记，不另复制易漂移的主档 |
| 安装与内容 | 用户安装记录与不可变包；内容摘要和下载包摘要分别保存 |
| 用户连接 | 某用户的具体账号和凭据引用；同服务两个账号不得按工具名合并 |
| 本次绑定 | 当前用途、能力版本、连接、操作和资源范围，关联方法需求或聊天选择 |
| 运行时视图 | 某个 Codex 环境实际加载的描述、版本与观测时间，不是主登记表 |
| 单次调用 | 受信宿主的调用身份、父调用、输入、批准、派发和结果；相同参数不意味着同一次调用 |

远端工具代码不可验证时，只保存服务声明和发现快照，不能声称冻结了对方实现。沙箱销毁不删除用户安装和方法定义；市场下架、账号撤权和停止执行进程是不同动作。

#### 1.9.4 从目录到真实可用，必须经过哪些衔接

1. 安装完整内容并保存技术发现候选，核定业务操作映射及许可，按 1.10—1.11 完成孵化；只有通过并冻结的版本进入可调用目录。未支持或验证失败的保留工作稿及原因。
2. 根据聊天用途或步骤需求选择精确版本和范围；检查当前用户连接与环境，不把发布当作登录或授权。
3. 为 Codex 准备可发现集合，验证实际加载；稳定配置只承载连接身份，每轮授权独立保存。
4. 请求时核受信宿主的 session/thread/turn/call 或 task/attempt；读取 Skill 正文和附件也不得绕过范围检查。
5. 更换账号、停用、撤权或进程接管后重核授权；不能用旧描述缓存维持已失效的调用权限。
6. 返回明确状态和恢复入口；普通聊天可排除失效能力继续交流，方法缺必需依赖则等待，不静默替换绑定。

界面区分“已安装、已启用、需要账号/配置、可更新”和本次不可用原因。底层还需区别已登记、已加载和当前可调用，但不要求普通用户理解 Pod、API 或 thread。

#### 1.9.5 调用路由、权限与恢复怎样统一

正式方法先按契约选能力，再选满足要求的受管绑定。业务权限判断、动作审批与执行状态彼此分开：权限允许不等于写操作已批准；远端自报只读不成为批准依据；账号、资源或附件改变后旧批准不沿用。

同一调用重试按受信调用身份返回既有记录；另一次合法调用即使参数相同也有独立身份。派发前持久记录，派发后丢失结果记未知。已有精确审批的恢复须核原有效期及当前撤权状态，不因恢复线程产生第二次外发。

普通聊天和专家沿同一机制调用连接器工具方法。脚本需要连接器结果时由专家前序方法提供；脚本作为工具方法实现不能再发起方法调用，原 C5 的脚本直调目标须按此调整。停止执行不撤销已产生的外部副作用，结果未知不重放；不通过原生直连绕过治理。

#### 1.9.6 三个场景说明中心与执行位置的关系

| 场景 | 路径与责任 |
| --- | --- |
| 方法某步已确定要读取数据 | runner 直接请求共同调用服务；不额外开启模型轮次，结果进入步骤验收 |
| 普通聊天或方法中模型选择工具 | Codex 获得当前描述并请求平台 MCP；共同服务核权后调适配器，安装和账号可复用，授权范围分开 |
| 某工具只在用户电脑或沙箱可用 | 检查对应执行端和受管委托路径；不具备时明确不可用于正式方法，不自动换环境或复制秘密 |

#### 1.9.7 与方法市场、模板和后续建设的关系

方法市场提供有身份、版本、许可和契约的候选；模板固定候选范围或选择规则，runner 在真实运行时绑定账号和资源。选择不授予使用权，安装不授予外部动作权限，模型暴露不代替审批。

MCP、Skill、连接器的实施任务顺序与状态只维护在[接入实施方案 §17.6](../../专家使用方案/luna/mcp和skill接入实施方案.md#176-本次先发布发布后补齐的工作单所有者-2026-11-13-确认)，具体共同服务分解见该文 §17.7；方法契约、递归和现有财务专家迁移的跨仓依赖与验收见本文第 4 节，C2 公共机制是共用前置项，不安排两次实现。本节是已确认的目标规则：当前已有平台和受管 MCP 入口，但共同核权、业务连接器契约、稳定配置及完整依赖交付仍待实施，不把文档收敛写成代码完成。

### 1.10 孵化、可调用目录与当前可用

平台作为特殊作者孵化通用基础方法，其它作者孵化自有工具方法、专家方法和专家团方法，所有方法都走孵化流程。没孵化不能在聊天、工作或专家中调用。孵化验证通过受控测试入口执行候选，保留测试身份、版本、范围和证据，不把候选暴露为业务可调用方法；任何真实外部副作用仍须先满足准入检查并获得批准。

| 事实 | 保存位置与约束 |
| --- | --- |
| 安装、待配置、待验证、验证失败 | 安装记录或孵化工作稿，允许保存并继续处理，不进入可调用目录 |
| 孵化通过、版本冻结 | 关联定义、实现或发现快照、验证证据和适用范围，才能注册可调用版本 |
| 本次可用 | 再核版本资格、连接、授权、环境和批准；过期或撤权不改写历史孵化结论 |

自用孵化在安装流程中完成，用户确认系统起草的声明和范围；公开孵化须满足公开验证标准、依赖交付许可和发布主体资质，后端强制。自用转公开补齐要求并形成相应新发布版本。远端描述不能授予可信只读身份，须由核定定义及平台策略判定。

#### 1.10.1 未覆盖项与准入失败

自用可有条件通过的未覆盖项，是缺少安全测试目标而未验证真实服务上的业务效果，不是执行治理未验证。必须识别账号、操作、对象和参数，验证核权及审批绑定、结果未知不重放、执行环境及凭据隔离等必需准入条件。必需条件缺失或失败不可调用，逐次批准不能代替实现验证。

记录具体未覆盖场景、原因、适用范围、已有证据和首次运行的提示要求。首次相关调用前提示未覆盖项，写操作逐次批准；真实获批运行可以补充相应证据，不自动证明其它场景通过。不为安装通过强行向真实对象制造副作用。

公开须满足该类方法的发布验证标准，可用安全账号、服务商测试环境等有依据的证据，说明它与实际绑定的差异；必要验证无法满足则不能公开。不要求在生产环境制造所有副作用，也不能把模拟测试冒充真实端到端验证。工具方法按职责、边界和失败语义测试；专家测试方法池加规则及实际计划、结果，不以一次成功作为通用证明。

#### 1.10.2 作者采用、来源与派生证据

原创、原样引用、派生修改和 AI 辅助起草进入同一孵化工作稿。来源记录覆盖五要素中的关键规则，包括能力边界、算法与口径、权限要求、做法、验收和审批，不只记录模板变量的赋值。每项记录关联稳定规则标识、定义修订、来源及作者采用依据；导入保留源文件或技能包的版本依据与摘要，引用已有方法须能追到其精确版本；AI 提议须能追到提议及作者接受或修改后的内容。

AI 可以提出规则，未获作者采用的提议不能进入发布定义。作者可以在看清变更及影响后批量确认，不要求逐字段点击；采用记录必须绑定所确认的具体修订，不能用过去的一次确认覆盖后续自动改动。确认采用只证明作者选择了这项规则，不代替许可、孵化验证或运行授权。

原样引用保留被引用版本及其证据适用范围，上层组合仍须验证整体承诺。修改算法、适用条件、权限或验收标准时，形成带来源关系的新定义并标明受影响证据；旧版通过不能直接证明新版通过。未受影响的证据只有在适用依据可核对时才能复用，其余须重验。沿用现有工作稿、版本和验证记录，不新增三档成熟度体系，也不把真实任务的数据或授权带进派生方法。


### 1.11 Skill 孵化与专家计划转换

包内脚本在不调用其它方法时是工具方法；纯指令在固定职责内不调用方法时是工具方法；调用其它方法的技能按 §1.1 的依赖分类为专家方法或专家团方法。一个包可含多个实现文件，不按文件数自动注册方法。声明和扫描只能得到候选分类，须在孵化时确认依赖、类型及范围，运行时由宿主限制实际调用。

首版专家方法及专家团方法的 Skill 转换流程：

1. 解析原文和依赖，把候选绑定到已孵化、使用权有效的精确方法版本；缺失依赖先补齐。
2. 原文作规划指导；提取明确必做、条件必做、顺序、校验、审批及交付要求，形成结构化规则，作者确认。作者可补标必做；不能把原文明示必做因未勾选而忽略。
3. 背景与表达指导保留为指令；执行要求落实到方法调用或封闭编排操作；校验、审批和交付落实到对应契约。无法落实的要求列明，由作者补依赖、修订承诺或暂不启用，不能静默降为无约束提示。
4. 用户沙箱内模型在这些规则内生成标准专家计划，宿主校验，用户确认后执行。计划包括稳定步骤标识、方法版本、输入/导出映射和依赖，不是一串自由文字。
5. 持久保存规则版本、转换确认、实际计划及修订、输入绑定、调用和审批记录；恢复以这些记录和当前授权为依据，不靠重新阅读原文重新排一份计划。

验证既检查计划合法，也检查转换后仍符合原技能确认过的职责和承诺。前端保持“安装 → 配置 → 启用”；系统在内部完成孵化，必要时展示缺项供用户确认，不要求普通用户理解内部分类。启用后按简介按需发现，不把所有正文注入每次会话。聊天调用专家类技能进入计划确认，可在原聊天内完成短计划确认；已确认范围内的子专家不用重复确认，越界和具体写操作仍按规则处理。


### 1.12 市场、版本、作者数据与费用边界

KnowMart 使用一套机制，按工具方法、专家方法和专家团方法提供三个分类入口，共用声明、版本、使用权、许可、价格及匹配。工具方法供组合及聊天/工作直接使用；专家和专家团方法供用户请用、上层组合及会话调用。入口或筛选展示不得形成三套市场服务。只能引用有权使用的已孵化方法，公开可见不自动授予跨作者嵌入或转授权。

工具方法变为专家或专家团、专家变为专家团，以及其它分类变化，均须按新依赖重新孵化并发新版本；输入输出形状相同也要复核权限、费用、审批、数据外发和验收差异。旧引用继续钉旧版，不因升级自动换用。普通下架停止新获取，已有合法使用按许可继续；安全撤销、凭据撤销或相关资格失效则按影响阻断。依赖不可用按规则等待、改候选并重校验或失败，不静默换版本；已完成证据保留。

依赖变化须形成可查询的影响清单：从冻结的直接引用及候选规则追溯受影响的上层方法版本，再结合实际计划和调用树定位已选分支、未开始及正在运行的调用。发布版本的潜在依赖与本次实际依赖分别标明，不能因为可能选中就判定所有委托都已使用。动态候选按其已冻结的资格规则检查，实际选中后保留精确版本；反向查询由这些记录派生，不另存可独立修改的依赖真源。

影响清单记录变化原因、范围、处置及依据，按可见权限通知相关作者或使用者，不向被依赖方法的作者泄露调用方的私有计划或资料。普通下架仍按既有合法使用权处理；安全撤销或授权失效阻断受影响的执行与恢复，不能仅依赖异步通知作为核权措施。可选依赖不可用也不能静默从已确认计划删除：先核对是否已成为本次承诺，按规则等待、替换重验或请求范围变更；已发生的外部动作及结果未知状态保留，不因停止上层任务而假定撤销。

作者自带数据绑定其所属方法版本和使用同意；不把原始数据或未许可内容自动交给上层。输出本身也须核披露范围，衍生产物许可沿调用树传播，以所有输入许可的共同限制封顶；可调用方法不等于可再分发其数据。授权范围仍按主稿父子收窄规则，不复制方法特定同意。

费用分模型规划、模型执行、确定性执行、外部服务与方法使用费；唯一计划可由程序生成，工具方法也可能有模型费用。边界按职责和复用确定，不为减少调用数把合理的方法塞进大脚本。所有层计入同一根预算，展示估算与未确定项，实际费用另记。


## 二、步骤与组合

### 2.1 步骤的定义与最小结构

**专家步骤安排一次方法调用；步骤不是方法，没有独立发布身份。** 同一方法可在不同步骤以不同参数调用；工具方法内部固定实现逻辑不作为专家步骤再次登记。

| 步骤建议字段 | 职责 |
| --- | --- |
| `step_id`、`goal` | 稳定标识与本段目标，用于计划、确认及恢复 |
| `inputs`、`input_bindings` | 可为空的输入槽、口径、来源约束、缺项行为及实际映射；方法返回或当前授权资源引用均须有依据 |
| `dependencies`、`run_condition` | 数据与质量依赖、必做/条件必做/可选及受限条件，禁止任意代码谓词 |
| 方法选择及调用 | 一个精确方法版本或已定义的候选范围；实际派发前固定选择，不在同一步隐藏多次方法调用 |
| `outputs`、`output_bindings` | 从被调用方法返回映射本步骤产物，记录类型、口径、版本及证据；方法对外导出另有映射 |
| `failure_policy`、`recovery_policy` | 缺项、错误、重试、审批等待、结果未知和恢复行为 |

候选可以包括三类方法，但须符合所属方法的冻结分类边界，但必须已经孵化并具有使用资格。字段名是设计建议，正式契约与生成物一起调整。步骤、调用实例与方法版本分别标识，不能用显示名代替。

### 2.2 编排可做什么：封闭的值处理清单

首版编排值处理仅允许以下四项，不能泛称为开放的“数据处理”：

| 操作 | 允许行为 | 不允许混入的行为 |
| --- | --- | --- |
| 字段选择 | 从已取得且允许使用的结构选择已声明字段 | 读取新文件/连接器、执行查询或计算新值 |
| 重命名 | 改变映射目标字段名，原值及来源不变 | 改单位、类型或业务含义 |
| 引用绑定 | 把已确认值或版本化产物引用接入声明输入槽 | 绑定动作隐式取数、执行模型或扩大授权 |
| 引用集合构造 | 按声明顺序收集多个返回引用 | 内容汇总、去重推断、排序计算或改写资料 |

流程依赖、必做条件、状态推进和预算检查属于宿主控制机制，条件使用契约限定的可解析表达，不接受作者任意脚本；它们不扩充值处理清单。运行时需要新的业务计算、转换、汇总或成稿，应安排对应方法调用。清单若需扩展，先修改契约、明确语义和验证，再开放。

专家步骤不嵌业务代码，是为了统一治理并简化创作；并非代码无法随版本测试。代码放在工具方法实现中，按其职责孵化。平台可以孵化通用转换、合并及“按交付结构成稿”等工具方法；作者定义交付结构和业务规则，不要求平台内置投资判断。仍未孵化的基础方法不能用候选名称冒充现有实现。

### 2.3 专家组合与 DAG

组合表示专家方法或专家团方法组织下层调用，不另设“组合方法”第四类。专家规则只引用有权使用的已孵化版本；类型随冻结定义固定，实际计划选择不能把专家临时改成工具方法。

```text
专家〔五要素两视图〕
├─ 步骤 A：调用资料读取工具方法
├─ 步骤 B：绑定 A 的返回，调用分析专家
│            └─ 按其规则展开自己的方法调用步骤
└─ 步骤 C：绑定 B 的导出，调用成稿工具方法
```

步骤依赖采用 DAG，首期按依赖串行执行；并行能力另行验证。直接引用随方法版本钉版，候选选择在实际调用前解析并钉版。唯一合法计划由程序生成，不新增专家类型。模型只在作者允许范围提出选择，不改公式、验收或权限。

单个计划的 DAG 检查与方法祖先链循环检查分别执行；同一方法不同分支的合法重复调用不算循环。必做步骤有执行证据，未选分支记为未执行；迭代按有界规则展开，不拿循环依赖代替。方法调用次数、步骤数、模型轮次分别计数，确定性调用不增加模型轮次。

### 2.4 输入、校验、审批与恢复怎样贯穿步骤

步骤先声明输入，方法对外视图按 1.2—1.3 生成。实际参数或资料引用来自调用方、前序产物及有效授权范围；获得资源引用不等于已读到内容，读取需要相应方法调用。计算工具方法只接收输入，不另行调用读数方法。

检查输入格式和权限后才能访问或执行；口径和业务完整性由约定检查负责。步骤不预设统一的首个输入准备环节，只有确实需要取数或整理才安排方法。

| 情况 | 必须明确的处理 |
| --- | --- |
| 输入缺失 | 等待补充、失败，或按事先约定完成允许的部分 |
| 返回不适用 | 作为业务结果，由专家规则决定停止、合法分支或披露局限 |
| 技术失败 | 重试适用条件、次数、退避及超限去向；不得凭失败标签假定没有副作用 |
| 校验未过 | 阻止交付、受限返工或上报；不能临时降低阈值 |
| 需要审批 | 影响发生前等待；绑定精确动作、账号、对象和内容 |
| 副作用结果未知 | 核对真实结果后决定恢复或补偿，不自动重放步骤 |

计划确认不代替具体动作批准。上层不能用“无额外审批”取消下层限制；工具方法实现须通过相同治理。步骤重试沿同一调用及尝试记录恢复；返工另记新调用，输入或版本变化使受影响结果失效，不覆盖已完成证据。

方法验收、步骤完成条件和专家整体承诺分别检查。公共调用记录关联现有 Task/Attempt、产物版本和 Interaction；不增加独立步骤账本。子调用通过不自动代表专家完成。

#### 2.4.1 可选分支与条件验收

分支是否必须执行及验收，由作者规则、触发条件和已确认计划共同决定，不能仅以返回槽是否有值判断。保留分支选择依据、业务结果和执行状态，以下语义须能区分；它们映射现有计划、调用和验收记录，不要求新增同名任务状态枚举。

| 情形 | 验收与交付要求 |
| --- | --- |
| 本题未选择该可选分支 | 记录未选及依据，不索取该分支专用输入；仅免除契约明确以该分支选中为条件的检查，并披露本次范围 |
| 条件不触发，或方法有效返回不适用 | 记录条件依据或不适用证据，按原规则判断可接受结果；不冒充完成了相应分析 |
| 已选且当前需要，但缺少资料 | 等待或按缺项规则失败；无输入不能使其自动变成未选 |
| 已选分支执行失败或验收未过 | 保留失败及对上层承诺的影响，按规则返工、失败或请求范围变更；不能跳过检查后标为完整成功 |
| 已执行并通过验收 | 绑定验收过的产物版本，继续检查本层覆盖与整体承诺 |

例如，用户本题不需要预测，报告可以不包含预测并注明范围；计划已承诺预测但预测失败时，报告不能利用“预测槽为空”免除检查。允许的部分交付仍须按契约标明缺项和局限，不能以部分交付替代原承诺的完整成功。恢复或修订后按持久计划版本重新判定，不把旧分支的免检结论套到新计划。

### 2.5 示例：增长分析专家的逐步调用

下表仅说明结构，所有引用都须另有已孵化版本；不新增业务算法。已有相容年度数据可直接绑定，缺少数据才调用读数方法。

| 步骤 | 输入及依赖 | 唯一方法调用 | 输出 |
| --- | --- | --- | --- |
| 读取年度数据（按需） | 已确认的资料引用、主体及期间 | 读数方法 | 相容年度数据及证据 |
| 收入增长 | 选择年度数据中的收入期初/期末字段 | CAGR 工具方法 | 收入增长或不适用结论 |
| 利润增长 | 选择年度数据中的利润期初/期末字段 | 同版 CAGR 工具方法 | 利润增长或不适用结论 |

两个增长步骤各有调用身份；字段选择与引用集合构造是编排允许操作，不另登记成方法。若需要业务计算或内容合并，另排一次对应方法调用，不能藏进映射表达式。整段流程注册为专家，步骤本身仍不是方法。

### 2.6 C07：季节性预测与回测专家示例

以下保留原 C07 的算法、窗口、依赖与验收要求，旧编号来源及查阅方式见[工具方法提炼示意第七节](原20个财务方法的工具方法提炼.md#七历史审查与来源边界)。按新分类，C07 如组织下层方法，应按允许依赖区分专家方法或专家团方法，不另称“季节性预测组合”类型。以下业务说明尚非已孵化资产。

1. 作者先接受预测公式、允许的指标、4/8季窗口、回测范围及数据质量规则，形成组合的固定语义。
2. 实际题目给出目标季度。计划反推上年同季基数、同比所需的前期季度，以及每个回测起点的独立窗口；不是仅检查“总共有16个季度”就认为足够。

4. P02在四个历史起点分别调用已钉版的P01逻辑，所有起点禁止读取当时不可得的输入。P02是对指定预测方法的受限回测，不是允许运行模型传入任意新算法。
5. P01对本题目标季度计算点值与上下界。保留原作者方法：上年同季乘以一加近4季同比中位数；上下界使用近8季同比最小／最大值。回测合格与否、能否继续，服从作者明确规则，不由模型临时降门槛。
6. 最终成果按“指标×目标期×点值/上下界”和“指标×回测期×预测/实际”验覆盖；缺哪一格就说明哪一格，不能把有个horizon=2当作交齐。

上述第 1 项是创作时确认规则，不是每次运行都重批。其余业务过程拆成每步一个方法调用；窗口推导、数据整理等须有已孵化方法，不在专家中嵌程序块。

| 业务阶段 | 拆分为的方法调用步骤 |
| --- | --- |
| 窗口与资料准备 | 调用窗口推导方法；需要时另调用取数/整理方法，各自声明输入输出与证据 |
| 季度序列准备 | 按需调用 A03；另一步调用 A04；相容可信单季不重复差分 |
| 历史回测 | 调用 P02；若 P02 通过四次调用 P01 实现，它是下层专家，各起点有独立输入和调用记录 |
| 目标期预测 | 满足作者固定继续条件后，调用已钉版 P01 |
| 核验与交付 | 各项必要 Q 检查分别安排方法调用；引用映射不执行业务计算；需要内容整理或成稿时调用对应方法 |

P02 若在固定实现内使用共享公式库而不调用其他方法，可归工具方法；若调用 P01 则按 P01 的类别和其它依赖判定为专家方法或专家团方法，须在其孵化版本上明确，不按本次执行临时切类型。两种实现都须满足原回测窗口与禁止未来数据的业务规则，不把内部库调用伪记为平台方法调用。

### 2.7 能力承诺、产物与导出映射

动态编排不意味着所有产物都事先不可知。方法应声明所有合法计划必须交付的公共产物，以及按条件或分支交付的产物；这些承诺关联步骤产物或子方法返回，不能仅靠一段文字和最后的模型总结判断完成。

| 时点 | 应给出的信息 | 谁使用 |
| --- | --- | --- |
| 孵化与选用 | 解决的问题、必交产物、条件产物及排除范围 | 用户、方法选择模型及作者测试 |
| 计划确认 | 本次交付项及负责生成的步骤/子调用，尚未展开处的条件边界 | 用户与计划校验程序 |
| 执行结束 | 已验收的实际产物、版本、证据、未完成项和局限 | 上层方法、用户和验收程序 |

步骤声明产物名称、类型、业务口径、证据及产生条件；方法的导出映射明确对外名称、来源步骤/子调用、来源字段和条件。本次执行再绑定实际来源实例与产物版本。调用者使用生成的返回接口；未标记为导出的资料和中间结果不自动返回，不能把最终步骤的全部产物拼在一起交付。

需要汇总、计算或改写时，显式安排对应方法调用并验收；生成视图不暗中运行模型或业务计算。程序核对引用、类型、分支覆盖和计划是否履约，业务文字承诺仍需内容验收。技术上的成功、失败、结果未知，与业务上的完成、不适用、部分完成分开表达；允许上层继续的条件须由方法规则定义。

### 2.8 按题编排、统一确认与用户修改

作者在孵化阶段固定候选方法及版本规则、必做和条件必做、先后依赖、可选范围、输入和交付约束、权限及验收。使用时，用户沙箱内的模型按问题提出顶层计划；宿主检查引用、依赖、输入来源、承诺覆盖、权限和预算，不为迁就模型输出修改作者规则。规则仅允许一种计划的专家由程序生成计划，不额外开启规划轮次；这是效率规则，不是另设类型。

#### 2.8.1 一张初始确认页，分别保存确认事实

计划、定数据和连接绑定共用一张执行前确认页。用户能在同一处查看及修改以下内容，已有有效选择直接带入；程序校验后一次提交，不要求重复进入三个确认流程。

| 页面内容 | 展示与修改 | 持久记录及边界 |
| --- | --- | --- |
| 计划与交付 | 顶层步骤、必做/可选、预计成果、未展开部分与可能影响 | 方法版本、计划版本/摘要及确认者；不是之后每次外发的批准 |
| 数据清单 | 已选资料及版本、已有授权、缺项、条件需求和允许下层选择的范围 | 实际数据绑定与资源授权分开；不能把全部候选资料自动列为获准 |
| 账号绑定 | 所需连接用途、实际账号、可沿用偏好及需重新授权项 | 保存具体连接及修订；沿用偏好不沿用失效授权，不默换账号 |
| 费用上限 | 已知费用、估算及不确定部分、整棵调用树预算 | 根预算及变更记录；估算不是实际费用，子调用不能重复取得完整预算 |

后端以同一确认批次关联计划、数据授权、账号绑定和预算事实，但各自按职责核验。只有必需条件完整有效才派发；提交期间计划、数据或连接修订发生变化时指出差异，不能悄悄按新版本执行。第三方 OAuth 登录可能需要跳转，返回同一确认流程；不能承诺所有服务均只需一个按钮。

下层在已确认的目标、交付、资料、权限和费用范围内自动规划、绑定与执行。尚未确定的精确输入按规则延后绑定，不因合法展开再确认一次顶层计划。需要新账号、额外资料、扩大权限、改变交付或超预算时，仅对变更补充确认；拒绝后按预先定义的条件停止或交付明确标识的部分结果。

统一确认不覆盖具体动作审批。发送邮件等动作仍按规则绑定发件账号、收件人、正文、附件和批准；审批卡使用公共 Interaction，不能在此新造另一种批准事实。职责等无人值守运行也不能越过这些边界。

#### 2.8.2 修改、退出专家约束与复用

用户可增删可选项、在依赖允许范围调顺序；每次修改重新核对必做、条件必做、候选范围和承诺。若坚持删除必做项、破坏依赖或加入专家范围外方法，须明确退出原专家的执行承诺，另存为用户自行修改的计划；不能在原专家调用上偷偷改规则后仍宣称成果来自该专家并满足其承诺。

退出时保留原方法版本、原计划、修改内容和已完成执行事实，界面与成果明确标识“用户修改计划，未按原专家完整要求执行”。重核新计划的数据、授权、预算及验收，已发生的外部动作不得因新计划而重发。此路径未实现前明确拒绝不合法的专家计划，不以后台去掉标记代替用户选择，也不为完成该路径擅自开放方法转授权或包导出。

用户可保存并复用合法计划；复用前核方法版本、适用问题、数据口径、连接状态、授权与预算。复用的是计划及仍适用的确认事实，不是复制旧凭据或延长写操作批准。

### 2.9 递归、展开与同一调用记录

#### 2.9.1 首期沿现有任务按需展开、串行执行

递归描述方法调用关系，展开描述调度落地。首期沿用现有 Task/Attempt 和任务账本，将到达的子方法计划展开到当前可执行范围；步骤依赖用 DAG 表达，按满足依赖的顺序串行运行，不把串行实现写成只能有直线流程。

执行顺序：确认顶层范围 → 到达子方法调用 → 在其范围内形成并校验下层计划 → 解析精确输入绑定 → 执行并验收下层 → 按导出映射返回 → 上层继续并独立验收。规划自上而下、用到哪层排哪层，沿可执行路径深入，结果逐层返回。

子调用需要持久记录，不意味着新建独立任务引擎；单个计划的 DAG 检查与方法祖先链循环检查分别执行。正常展开与纠错重排共用必要的计划版本、已执行事实保护和恢复机制，但分别记事件、分别计数，合法展开不消耗纠错重排额度。

#### 2.9.2 方法与实现派发共用公共调用身份

本节的方法调用记录，就是接入实施方案 17.7 要演进的通用调用记录，不新建第三本调用账。三类方法共用 `call_id`、直接父调用、根上下文、状态、范围和幂等身份；外部工具或脚本属于具体实现派发，细节和尝试记录引用相应方法调用，不将同一次执行重复记为两次方法或重复收费。必要的实现派发记录可单独保存，不要求字段挤在一张表。

| 持久信息 | 用途 |
| --- | --- |
| 调用标识、直接父调用、根任务/会话上下文 | 区分同一方法的不同调用，按实际派发关系恢复、核权、取消；根身份由宿主确定 |
| 方法或工具标识、精确版本与绑定 | 不因市场、目录刷新改变正在执行的目标 |
| 所属步骤/内部动作、计划版本 | 关联本次选择、展开、确认和实际派发；显示名不替代稳定标识 |
| 输入绑定、来源及版本 | 恢复实际使用的数据；参数相同不等于同一次调用 |
| 导出映射、结果引用及验收证据 | 正确逐层返回；技术状态与方法业务验收分开 |
| 父授权依据、本次有效范围、审批引用和预算归属 | 继承只收窄，撤权可传播，所有后代计入同一根预算 |
| 执行状态、尝试与宿主幂等身份 | 识别未派发、已完成、待批准和结果未知；重试沿既有记录恢复 |

专家步骤发起的方法调用，其直接父调用是该专家；被调用的专家继续记录自己的子调用。普通聊天请求工具方法也记真实方法调用，根上下文是会话轮次，不伪造一个专家父节点。脚本实现只关联所属工具方法及派发尝试，不能再调用连接器方法；专家应另排相应步骤。步骤、实现内部代码均不因记账自动注册成方法。

API 的共同调用服务管理身份、核权、审批引用及执行状态，runner 负责计划调度与方法验收推进；领域计算/读数证据引用 `call_id`，批准事实仍归 Interaction，Task 仍负责任务状态。不能只靠“预测.回测.第三期”这样的名称恢复层级，也不能让子方法通过自动替父方法完成业务验收。

#### 2.9.3 上限、撤销与恢复

- 分别限制调用深度、累计展开数量、总步骤数、方法调用次数及纠错重排次数；现有“一张计划最多 100 步”不能替代深度和整棵树累计限制。
- 按当前祖先链拒绝循环引用；同一方法在不同分支合法重复调用按独立调用、次数和预算约束，不能误判为循环。
- 整棵树共用根预算，子预算只是分配，规划、执行、重试都计入；不能逐层重置额度或重复记费。
- 已完成事实不能改写；重排或返工生成新记录并标记依赖失效范围。正常展开保留独立事件，不伪装成返工。
- 取消、撤权、到期和预算耗尽须传到待执行后代；恢复从持久计划、调用、尝试和当前授权重建，不依赖 runner 内存或模型自述。
- 外部请求可能发出但结果未知时不自动重发，批准等待不持长数据库事务；显式拒绝和不可恢复缺项按规则结束或形成有依据的部分结果。

### 2.10 协作执行的共同要求

本节承接原《专家团内化方案》的通用执行要求，专家团方法沿同一契约与编排机制，不另建团队引擎。AI 形成计划和人审定计划可参考[协作编排参考模式](协作编排参考模式.md)；模式是组织工作的参考，不能替代本稿契约、当前授权或实际计划。方法固定规则只允许一种计划时仍由程序生成，不强制设置常驻“团长”模型。

#### 2.10.1 上下文、成果与资源隔离

调用只取得按规则传入或在有效范围内绑定的资料，不默认复制整个父会话、兄弟成果或方法正文。独立分析先隔离对方结论，交叉复核时再开放获准的指定成果。独立上下文不等于每次新建 Pod；线程、工作目录和环境边界须由实际执行能力保证，不能仅靠提示词声称已隔离。

交接产物关联提供方调用、方法版本、产物版本、输入口径、证据、业务状态、局限与使用范围。成果引用不自动成为标准化事实，不自动授予读取底层原件的权利；入库及加工仍走既有数据链。汇总不得抹掉分歧、将缺证写成支持或将部分结果冒充完整结论；分歧按作者规则复核、补证、保留或交有权的人判断，不默认多数投票或汇总模型总是正确。

每个实例的工作目录、可读成果和写入范围须明确，禁止无协调地覆盖同一成果。未来启用并行时，还须验证资源竞争、汇合条件和互相等待；旧实现的单个 `current_step`、`active_attempt_id` 等串行假设须核对，不能直接同时启动旧任务就宣称支持协作。首期继续按 DAG 串行执行。

#### 2.10.2 交互、作者选数与进度

统一交互至少关联根任务、来源调用、尝试、问题类型和内容版本。澄清、数据确认、作者选数和动作审批可进入同一待办入口，但决定权分开；协调方法可使用已有事实补齐衔接，不能代用户扩权或代作者作专业决定。状态和“等谁、等什么”由真实运行记录投影，不能依赖模型自行宣布完成；局部等待是否影响其它分支须检查依赖、资源及一致性约束。

作者按题选数据属于通用供给规则：先按作者预设规则匹配，规则不足时交给有权处理的人。工单只暴露完成选择所必需且获准的信息，不暴露用户全部会话、本机文件或其它方法成果。等待、离线、超时、改选与缺项按既定规则处理，不自动换成无权使用的数据；选择结果固定为资料版本和本次授权，不在 KnowBench 另建事实或许可主档。

数据需求只有在语义、版本、权利与使用范围相容时才可复用或合并请求；同主体、同期间不足以证明可跨账号共享。长期交代、定时唤醒与跨次记忆属于[连接器方案的职责机制](../../../连接器方案.md#职责长期交代与周期唤醒)，每次生成普通委托，不是协作模式或无限期方法调用。

#### 2.10.3 预算、收尾与验证

根预算覆盖规划、各层执行、重试、复核及汇总，可分配子额度并预留收尾资源；只按实际费用及确定规则入账，不在父层重复扣除子层消耗。预算不足不得靠换方法或新建实例绕过，预留也不保证所有任务一定完成。取消传播到适用的未开始及运行中调用；已发生副作用单独保留，恢复按 §2.9 核对计划、版本、当前授权及审批，结果未知不自动重放。

子方法替身测试可验证组合的绑定、分支和交接，但证据须标明模拟范围，不能代替组合整体端到端验收。机制验证与真实模型质量验证仍按 §4.4—4.5 分开；子方法通过不代表上层履约，不从调用树自动推导价格、分账或效果提升。

## 三、方法模板

### 3.1 模板的定义与边界

**方法模板＝五要素作者定义中的固定内容＋变量＋变量约束。** 输入和返回两视图随定义生成，不另设可手改的同义变量。给部分变量赋值得到更具体的模板；所有可达定义变量确定、约束满足且契约完整，形成方法工作稿，再经孵化成为可调用版本。工具方法模板确定固定实现，专家模板确定候选、规则及步骤映射，均遵循同一公共契约。

本定义及逐级具体化方向由所有者确认；以下字段、派生规则和验证方式为 2026-11-12 的细化设计建议，尚未实施。可用逻辑表达 `T = (D, V, C)`：`D` 是带有明确变量引用的五要素作者定义，字面内容为固定部分；`V` 是定义变量集合；`C` 是变量及跨要素约束。模板身份、来源、版本及模板自身的访问与复用权限是管理信息，不改变这三个部分的含义；方法执行所需权限仍属于五要素两视图。

| 概念 | 回答的问题 | 内容与使用阶段 |
| --- | --- | --- |
| 方法通用结构 | 所有方法都应怎样描述 | 五要素两视图、步骤与执行体、输入映射、权限等共同规则及 Schema；约束创作、发布与调用 |
| 方法模板 | 哪些定义已经确定，哪些仍可选择 | 五要素作者定义的固定部分、定义变量及约束，视图随定义生成；赋值后可得到下级模板或具体方法定义 |
| 方法定义 | 这个具体方法承诺什么、怎样实现 | 作者维护的定义与程序生成的调用视图；工作稿可未完成，发布时须完整并钉版 |
| 本次运行 | 这个方法这次处理什么 | 在确定的方法版本上绑定业务输入、资源与授权，按定义执行并交付结果 |

方法通用结构规定字段与合法表达。把五要素作者定义中待确定的内容显式声明为变量及约束，才形成模板；仅有几个空标题或任意“待补”文字，不能据此生成完整方法。可以有很抽象的上层模板，也可以有已固定大量内容的领域模板，均遵循同一方法结构。

模板可以覆盖简单计算、复合分析或完整专家。专家也是方法，不需要另一套专家模板格式；模板可预置步骤集合及映射，但每步仍只有一次方法调用。模板可以引用已发布方法的精确版本，也可以保留候选范围或固定完整的运行时选择规则。创作阶段待选而未选的引用仍是未完成定义；运行时选择规则已完整定义，则不因本次尚未选出具体方法就判定定义不完整，实际执行仍须核验候选并钉住选中版本。

模板具有自己的来源与版本。未闭合的模板不能作为承诺完整业务结果的方法直接注册；若将来需要工具辅助生成方法，可另定义具有完整五要素两视图的“生成方法”能力，不能把模板对象和生成工具混为一体。本方案不因此新增生成工具或运行引擎。已有方法可以经来源与复用权限核对后，把部分固定内容重新抽象为变量来提炼模板；这是抽象过程，不是沿原模板向下具体化，也不自动继承原方法的验证结论。模板不携带某次运行的私人数据、用户连接、凭据或批准事实。

#### 3.1.1 固定内容、变量、默认值与约束

| 内容 | 定义 | 在逐级具体化中的行为 |
| --- | --- | --- |
| 固定内容 | 在当前模板版本中已经确定的定义 | 下级沿用；要改变已固定内容，另行修订或分叉，不冒充该版本的合法具体化 |
| 变量 | 有稳定标识、类型和作用位置，尚待确定的定义内容 | 可部分赋值；同一变量在多处被引用时，赋值一致作用于所有引用 |
| 默认值 | 给变量提供的建议选择 | 未被明确采用前仍是变量；采用后形成有记录的赋值，不能悄悄成为固定业务规则 |
| 变量约束 | 类型、允许范围、依赖和跨要素一致性要求 | 每次赋值都检查；下级可收窄但不能放宽上级约束，冲突不得静默覆盖 |

变量可以表示文字、数值、枚举、输入输出声明、精确方法引用、候选集合及步骤映射。工具方法模板还可有固定实现引用；专家模板不能通过“程序块”变量嵌入代码。结构变量须有类型及边界，赋值不等于允许模型任意生成并执行代码。操作、审批和数据外发相关变量仍受 1.6 的权限边界约束，不能通过赋值消除平台及资源端限制。

各要素均可逐步具体化；输入和返回通过工具方法做法中的声明，或专家步骤及导出规则生成，不可同时编辑视图。作者维护的结构块可同时包含固定内容、未定变量与约束，支持局部赋值，不要求整块一次填完。固定内容与变量应在同一份定义中区分，不让模型猜哪些可改。

步骤是主要的结构变化来源，可以把“最大的变量”理解为其结构变化通常最丰富：步骤数量、依赖、条件、候选方法和映射均可待定，但每步仍只调用一个方法。这不是所有方法都成立的数量定律，也不把其它要素降为附属字段。能力声明规定解决什么问题，输入与权限、校验、产物和审批共同限定步骤的选择空间；不能先任意选步骤，再悄悄改承诺来迁就执行结果。

| 作者定义或生成视图 | 可变量化内容示例 | 必须联动检查的内容 |
| --- | --- | --- |
| 能力声明 | 目标、对象、适用范围和业务结果 | 实际输入、步骤与产物是否支持承诺，排除项是否仍成立 |
| 所需权限 | 资源角色、可信操作、资源和用途范围 | 父子授权收窄、输入实际来源、外发范围与审批 |
| 做法 | 工具方法固定实现及输入输出声明；专家的步骤、导出、方法引用、候选、依赖及条件规则 | 生成接口一致、输入输出相容、必需检查和停止条件 |
| 结果校验 | 检查方式、阈值和证据要求 | 产物是否可检查，验收标准是否符合已承诺目标 |
| 返回产物视图 | 随步骤产物声明及导出映射的赋值重新生成，不独立赋值 | 生成路径、分支覆盖、输入来源及未导出内容不泄露 |
| 审批要求 | 动作、触发条件、预览内容和批准范围 | 所需权限、实际副作用及上级不可放宽的限制 |

#### 3.1.2 分级是逐步收窄选择空间

下级模板由父模板的精确版本派生：保留固定内容和已有约束，增加部分赋值或收窄未定变量的范围，得到剩余变量及约束。一次可以赋值一个或多个变量，不规定必须逐层填完某个要素。上级可派生多个不同分支，模板层级不限于“通用—行业—专家”三层。

判断下级是否更具体，要看它允许形成的方法定义是否仍在上级允许范围内。如果把所有符合一个模板的完整方法定义称为“合法补全集合”，则合法下级的该集合应是上级的非空子集；真正增加确定性的派生会进一步缩小这个集合。变量改名、换显示顺序或只复制模板不构成更具体的一层。这是设计上的判定标准，不声称系统能自动证明任意程序和自然语言约束。

**变量个数只是辅助信息，不能作为等级尺。**例如上层有一个“数据获取执行体”结构变量，选为邮件获取流程后，可能展开文件夹选择规则、分页上限等几个子变量；变量数增加了，但获取方式已经被限定，定义更具体。展开规则须来自父模板允许的结构或已选引用，不能趁展开新增上级不允许的行为。普通标量赋值时，则表现为固定内容增加、未定变量减少。

约束收窄也能构成具体化，例如把报告格式从多个允许值收窄为其中两种，虽然尚未唯一赋值，选择空间已缩小。不保证所有模板都能横向比较；共享父模板的两个分支可以各有侧重，不必强排谁更高级。

模板派生和方法组合是两种关系：派生回答“定义怎样逐步确定”，组合回答“专家运行时调用哪些方法”。下级模板不因为派生自上级，就在运行时调用上级模板；模板树深度也不等于步骤层数或方法调用深度。

#### 3.1.3 赋值、依赖与派生规则

1. **明示赋值**：每次赋值记录变量标识、值或精确引用、来源及作者采用记录。AI 可以提出候选，不能以默认值存在为由宣称作者已确认业务规则。
2. **类型与关系检查**：先检查值的类型和范围，再检查已知的跨变量、跨五要素两视图约束。缺少关联值时记录尚不能判断的约束，不能把“待判断”当作通过。
3. **确定推导**：允许用明确规则从已赋值内容推导其他定义，推导项保留依据且不可独立改写。例如选定某个方法后，引入其已声明的输入要求，再明确映射或补充来源；不能推导出用户已经授权。
4. **结构展开**：选定结构变量后，为展开的步骤、内部动作和子变量保留稳定且不冲突的标识，核对输入映射、权限和依赖。多处使用同一模板时默认具有独立变量作用域，需要共用的变量显式映射。
5. **冲突处理**：不兼容的赋值指出具体变量和约束，不自动改算法、丢输入、放宽校验或减少审批。依赖循环且无法确定求值的推导不能展开；需由作者修正。
6. **撤销与改值**：在未冻结工作稿中可撤回本稿赋值，并使相关推导和验证失效；不能撤回父版本固定内容。改动父版本已有固定值或放宽约束，另建修订/分叉并保留来源，不继续声称是原版本的合法下级。
7. **版本隔离**：父模板修订不改变既有下级。迁入新版时比较固定值、约束与引用差异，重新检查整个相关依赖；不能自动把旧子模板接到新父版本上。

同一组兼容赋值应产生同一确定定义，不应因为编辑器先填哪一栏而改变业务语义。派生时约束不可满足的模板可以保存为未完成工作稿，但不能标为可用模板供自动展开；不存在合法补全不是“最具体的方法”。

#### 3.1.4 定义变量、运行输入与方法形成条件

创作变量用来决定将生成的方法定义，例如采用哪些步骤、选择哪个被调用方法、输出哪种报告结构。运行输入在方法定义已经确定后提供，例如本次公司、目标季度、财报引用及收件人。区分依据是是否改变方法定义，不是某个字段名称天生属于哪一类。

| 情形 | 应如何处理 |
| --- | --- |
| 作者从 C07 样板选定方法引用、补齐输入映射及交付定义 | 创作或修订方法，形成待验证的工作稿 |
| 使用已发布的季节性预测方法，传入本次公司和目标季度 | 运行该方法，保持已定算法、4/8 季窗口及最近 4 季回测要求 |
| 模型按已发布方法允许的条件选择步骤或被调用方法 | 在已定义范围内生成本次执行计划，不因此生成新模板或新方法版本 |
| 把 C07 的预测算法、固定窗口或允许的方法范围改掉 | 修改方法定义，需重新确认与验证；不能作为普通运行参数替换 |

参数若允许在运行时选择算法或输出形式，其可选范围和校验规则必须预先定义在方法契约中。模板不允许以“填写参数”为名临时改变业务承诺，也不把每一步自动展开为独立对话或工具注册项。

未定的定义变量不能仅被改名为“运行参数”来绕过闭合检查。若有意把某个选择交给运行时，必须先把该输入的类型、允许范围、选择规则、分支、校验和权限完整定义；此时已经固定的是“如何允许选择”，而不是偷偷留下未完成设计。运行时模型在这个范围内制定执行计划，符合定义，不需要每次生成新模板。

方法形成有三个不同的检查点：

| 检查点 | 成立条件 | 不可混淆的事实 |
| --- | --- | --- |
| 模板可继续具体化 | 已赋值内容合法，剩余变量明确，没有已知不可解冲突 | 仍可有待绑定变量和待判断约束，不能宣称已能完成业务任务 |
| 具体方法定义闭合 | 所有可达定义变量已确定，推导完成，五要素两视图完整且定义约束检查通过 | 运行输入可以未提供；实现、部署和真实验证仍可能尚未完成 |
| 方法可调用 | 闭合定义、实现绑定、适用范围验证及孵化通过，版本冻结并注册 | 本次运行还须有输入、资源、有效授权和所需批准 |

“所有可达定义变量”不包括已被固定选择明确排除的分支占位，但排除依据必须可核对；运行时仍可能进入的分支都必须定义完整。五要素两视图某项不需要特殊内容时显式声明，如无外部访问或无额外审批，不能用未填写代表无要求。

没有剩余定义变量的模板可以作为完整方法定义的复用起点；逻辑上它已经闭合，保存为“完整样板”不产生另一套运行身份。闭合也不意味着实现正确或已经可调用。

#### 3.1.5 贯穿示例：资料摘要与交付

以下仅用于说明逐级赋值，假设引用的业务方法规格另行提供；表格不是可执行资产，也不改写 C01—C15 的财务规则。

| 阶段 | 本层固定或收窄的内容 | 仍待确定的定义 |
| --- | --- | --- |
| 资料摘要与交付模板 | 五要素两视图结构、摘要保留来源、外发需有授权依据 | 来源方式、摘要执行方法、交付方式及与这些选择关联的细节 |
| 邮件摘要模板 | 来源方式选为邮件连接器，固定邮件读取的操作契约和来源格式 | 摘要方法、交付方式；展开后的范围选择规则及获取限制 |
| 邮件摘要报告模板 | 选定摘要方法精确版本，交付方式选为生成 Markdown 报告，固定报告包含摘要和来源索引 | 选定实现所要求的输入映射、校验判据及剩余处理规则 |
| 具体邮件摘要方法定义 | 补齐映射、判据和获取限制；明确从运行输入选择账号、文件夹和期间；定义缺项处理，声明不发送邮件 | 定义变量已闭合；本次账号连接、文件夹、期间和实际邮件仍是运行输入与资源绑定 |

“生成并发送邮件报告”可以是邮件摘要模板的另一分支：需要固定发送步骤、接收人输入要求、发送权限和审批规则，不能把已固定“仅生成报告”的下级模板直接改为发送并仍声称保持原定义。两个分支的用户连接和实际批准都在运行时取得，不随模板下传。

#### 3.1.6 步骤赋值：具体内容、候选范围与选择规则

**模板逐步具体化，既可以固定“用哪个方法”，也可以固定“如何选择方法”。**这是步骤赋值的两种重要形式。赋值对象可以是整个步骤集合、某一步的执行体，或执行体中某次方法调用的目标；不因此把步骤等同于方法。每个专家步骤只能安排一次方法调用，复杂组合可调用下层专家。

“选择向量”在讨论中表达的是可供选择的范围，方案统一称为“候选集合＋选择规则”，避免误解为必须有顺序或数值维度的向量。候选集合可以直接列举，也可以由指定方法市场的查询及筛选条件产生；推荐顺序或评分只是选择依据，不能代替契约与权限检查。

| 形式 | 具体确定的内容 | 模板与运行含义 |
| --- | --- | --- |
| 直接赋值 | 固定步骤结构及唯一调用的精确方法版本，并补齐映射与结果去向 | 对应定义变量已确定；是否完整仍需检查关联要素 |
| 创作时限定候选 | 规定作者可选哪些方法，或去哪个市场按什么条件查找，作者尚未采用具体选择 | 收窄定义变量范围，仍须继续赋值；模型可辅助推荐 |
| 固定运行时选择规则 | 规定候选来源、选择主体、时机、兼容条件、权限边界和失败处理 | 已确定的是选择机制；本次选中哪个方法留给运行时，不是未完成模板 |

三种表达必须有明确类型。原变量若只接受“精确方法引用”，不能直接塞入一段市场查询就称为完成赋值；父模板须允许“具体引用或有边界的选择规则”，才能采用后一种。改变父模板已固定的方法引用仍属于修订或分叉，不能靠改成动态选择绕过继承约束。

选择发生的阶段与选择主体是两个独立维度：创作时作者可接受模型建议形成定义；运行时可由宿主按确定规则选择，也可由模型提出候选，宿主检查后执行，契约还可要求用户确认。模型不执行工具，也不因可以选择就取得授权。调用方式、方法实现机制与选择策略分别表达。

**只给一个方法市场地址，不足以定义一个步骤。**以某次方法调用为例，建议在其 `method_selection` 内至少表达以下内容；这是待实施字段设计，不新增独立业务要素，也不另存一份独立流程。

| 建议字段 | 应明确的内容 |
| --- | --- |
| `candidate_source` | 固定候选引用列表，或指定市场、目录范围、查询条件；区分固定候选快照与按规则运行时发现，不默认检索全市场 |
| `selection_phase` | 创作时或运行时选择；创作待选项在方法发布前须完成，不得混入可运行定义 |
| `selector` | 作者、宿主规则或模型建议；需要用户决定的条件；运行时最终核验与执行由宿主负责 |
| `required_contract` | 本调用要完成的能力、适用边界、输入输出 Schema、必要校验和运行环境；引用所属方法已定义的约束，不另造相互冲突的承诺 |
| `selection_policy` | 必须满足的条件、候选比较依据、多项同等适合时的处理，以及选择数量；单次调用只选一个目标；若选多个，须展开为多个具名步骤，每步调用一个方法，并声明依赖和导出规则 |
| `binding_rules` | 输入来自哪里、候选输出如何接入后续步骤；异构接口须有明确且版本化的适配，不能只凭名称相似判兼容 |
| `access_and_limits` | 方法使用权及必要费用条件、外部连接与操作范围、数据外发、预算和审批边界；引用五要素两视图中对应要求，查询和推荐本身不授权调用或购买 |
| `version_policy` | 发布版本与可用状态要求；直接引用随定义固定，动态发现允许的版本规则随定义固定，选中后锁定精确版本及摘要 |
| `on_no_match`、`on_unavailable` | 无候选、缺输入、无权使用、候选下架或调用不可用时如何等待、补充、重新选择或失败；不得静默扩大范围或降低验收 |
| `record_requirements` | 定义应记录的候选来源、查询条件、候选版本、采用理由及检查结果；实际记录归本次创作或执行，关联步骤与动作，区分采用者与执行者，不把本次选择结果存成模板字段 |

动态候选不要求模板作者提前知道市场未来所有方法，但必须预先给出可检验的能力与输入输出要求、风险范围和候选准入规则。自然语言适配判断不能伪装为程序证明；必要时保留人工核对。宿主先筛选可见范围，再核对候选契约、资源与调用资格，才提供受限候选供选择；模型提出目录外或不符合契约的引用不能直接执行。运行状态或权限在选定后变化，调用时仍须复核。

实际选择结果记录在本次执行中，不回写模板固定内容。任务恢复沿用已锁定的版本和已生效动作记录；确需重选时按原规则记录变更、检查受影响映射和授权，不自动改用市场最新版本，也不重复已生效的副作用。动态选中不证明方法适合整个任务，本级仍须按自身验收规则检查交付。

以“邮件资料摘要”中的摘要调用为例，父模板可以允许两条分支：

- **具体绑定分支**：作者选定摘要方法 A 的某个精确版本，固定邮件正文与来源标识的映射，接收约定的摘要和来源索引。
- **运行时选择分支**：作者固定“从指定市场中查找满足同一输入输出契约、保留来源、在许可及数据使用范围内的方法”的规则，由模型提出选择，宿主核验并锁定版本后调用；无合格候选时按规则等待或失败。

两条分支都可以形成完整方法定义。若作者只是写了“去市场找个摘要方法”，没有约定契约、映射、选择责任和缺项处理，则仍是待完善的工作稿。摘要方法的选择也不自动增加发送邮件步骤或发送权限。

### 3.2 模板字段、派生与应用过程

| 建议字段 | 含义 |
| --- | --- |
| `id`、`version`、`purpose` | 模板身份、版本及适用的创作目标 |
| `method_schema_ref` | 所遵循的方法通用结构版本；用于展开与兼容检查，不能引用漂移的“最新结构” |
| `definition` | 带明确变量引用的五要素两视图定义；固定内容、步骤及其执行体都在这里表达，不另存一套流程 |
| `variables` | 每个定义变量的稳定标识、类型/Schema、作用位置、可选范围、默认建议、依赖、来源和说明；结构变量还声明允许的展开契约 |
| `constraints` | 变量及跨五要素两视图约束、推导依据和检查责任；区分可解析检查与需要作者或人工核对的业务判断 |
| `base_template_ref` | 可选的直接父模板精确版本与摘要，记录具体化来源；根模板为空，不用可手填的等级数字决定关系 |
| `bindings` | 本模板已明确采用的变量赋值及来源；值可为具体内容或变量类型允许的完整选择规则。规则内部字段仍未定时须保留为子变量，不能整体标为闭合；派生时继承父赋值，新增赋值不得覆盖父固定内容 |
| `constraint_refinements` | 本层新增或收窄的约束，明确指向上级变量及规则，禁止静默删除上级限制 |
| 来源与验证说明 | 模板及引用实现的来源、版本、候选状态、已验证范围与限制 |

建议根模板维护 `definition`、`variables`、`constraints`，派生模板维护父引用及本层赋值、约束收窄；父版本与本层变更解析为有效定义。展开快照与摘要由此生成，只读且可重建，不能与父引用及赋值各自编辑。新增结构来自允许的变量展开，不通过任意覆盖定义绕过固定内容检查。方案字段仍需对齐现有方法存储，未要求新增一套模板服务。

第一版建议一个模板只有一个直接派生父版本，便于核固定内容和冲突。复用其他模板可通过有类型的结构变量引入并显式映射，记录引用版本、避免变量重名；不依赖隐式多父继承或“后者覆盖前者”。派生引用必须无环；祖先深度仅为展示信息，不是质量、复杂度或可调用资格。

原建议字段 `method_contract_defaults` 改为 `definition`，以免把已经固定的内容仍当成可随意替换的默认值；`author_options` 的变量部分归入 `variables`，约束部分归入 `constraints`，实际采用的选择归入 `bindings`。旧 `parameter_defaults` 不恢复：定义变量默认建议只在变量声明处维护，运行默认值只在步骤输入声明中维护并投影到生成的输入 Schema；实际已绑定值有独立来源记录。编辑表单由这些字段生成，不再存一份独立创作规则。

模板应显式标出未定变量、已赋值、默认建议、已推导内容、未决约束及无效赋值，不能只显示“填完百分比”。不以演示数据填充必需业务输入。模板和下级定义中的权限均为需求声明，实际授权仍另行取得。

流程图、所需数据摘要、交付清单和审批点视图从公共契约及步骤定义派生，不再维护一套独立的 `default_composition` 或交付要求真源。模板保存步骤输入声明及绑定规则，程序生成方法对外输入视图；输入声明变更时重建视图并检查受影响的映射，内部新增中间结果不自动扩大调用者的输入责任。实际需要数据获取或整理时再设置相应步骤，不预设所有模板都从输入准备开始。

```text
选择模板版本
  → 读取固定内容、剩余变量、约束与已绑定来源
  → 作者部分赋值或收窄范围，执行类型、依赖及一致性检查
  ├─ 仍有定义变量：保存为下级模板，可再次派生
  └─ 定义变量闭合：形成具体方法工作稿，检查完整性和语义约束
       → 补齐实现与执行绑定，验证业务结果及失败恢复，冻结方法版本
       → 登记 tools 可调用项
       → 本次任务按参数和授权解析实际绑定并执行
```

上面的“保存为下级模板”和“形成具体方法工作稿”是按剩余定义变量分出的两条路径；不是每次赋值都必须发布模板。用户可以在同一工作稿中连续赋值，仅在需要复用某个中间层时保存版本。无需通过模板也可直接创作方法，仍遵守相同五要素两视图及验证要求。

模板应用后保留来源版本与赋值链，作者修改自己的工作稿，不能回写他人的模板。发布时解析为可审阅、有限且无未决定义变量的方法快照；运行只取该方法版本，不递归读取模板“最新版”；若其中固定了运行时市场选择规则，按该规则发现候选，并把选中方法的精确版本及摘要记入执行快照。通用结构变更需显式迁移，不能假装只增加一层赋值。复用 knowlab 的现有创作与方法版本机制，执行仍沿 Task/Attempt，不另建模板执行服务。

结构与赋值检查可由程序完成；涉及方法正文或业务含义的约束不能假装已经自动证明。应逐项记录通过、失败或待审及依据。模板展开一致、定义闭合、业务测试通过和发布批准分别记录，任意一项不能代替其余各项。

为衔接旧稿，`applicability` 和旧建议字段 `when_to_use` 的内容归入 `capability_declaration`，按 1.7 补齐用途和边界，不并列保留两个创作字段，也不能仅改键名就认定声明完整。旧 `input_schema` 的有效内容迁入相应步骤输入声明，重新生成方法输入视图；权限独立归入 `access_requirements`，算法与处理规则归入 `sequence_of_work`，`acceptance` 对应 `how_to_validate`，旧 `output_schema` 的承诺落实为步骤产物及导出映射，再生成 `what_to_return`。旧稿的混合步骤须拆为每步一次方法调用；业务代码纳入相应工具方法孵化，纯映射限于 2.2 的封闭清单。具体字段切换须按第 4 节验证：未使用结构直接替换，有数据一次性迁移并对账，之后只运行新结构；历史原件仅作证据，不保留旧格式读取或执行分支。

### 3.4 验证要求

以原四式核验、CAGR、累计转单季—原预测—回测链作为贯穿样例，再扩充当前财务专家需要的指标、证据核对和报告组织。方法或模板数量不作为成熟度依据。

| 验证对象 | 必须检查 |
| --- | --- |
| 模板表示 | 五要素两视图固定内容、定义变量和约束可区分；默认建议不冒充已赋值，原始定义与展开快照不各自编辑；运行默认值在做法或步骤输入声明维护并生成视图 |
| 逐级具体化 | 父版本固定内容和约束保留；合法赋值使选择范围收窄，类型错误与跨要素冲突可定位；相容赋值顺序不改变结果，不按变量数量断言等级 |
| 结构与作用域 | 结构变量展开有依据，引用无环、变量不重名、映射与依赖可追溯；模板派生不产生运行调用，方法组合不自动产生模板父子关系 |
| 闭合与验证 | 可达定义变量全部确定、定义完整且约束核对完成后才形成闭合定义；实际可达分支不能留空；实现、业务验证和运行授权另行检查 |
| 派生版本 | 父模板升级不改既有子模板；撤回本稿赋值会使依赖结果失效；改父固定内容作为修订或分叉，不伪称合法具体化 |
| 步骤选择 | 直接引用、创作待选和运行时选择规则可区分；规则类型获父模板允许，候选及输入输出兼容，无法匹配时不扩大范围；选中多个方法时组合与合并规则明确 |
| 工具中心协同 | 方法身份、绑定、期望配置、实际注册及单次调用分开；两端工具可用性分别核验，旧线程和撤权未生效可识别；缺少调用能力不能仅凭目录代执行，跨绑定恢复不重复副作用 |
| MCP 接入路径 | 后端 runtime 与 Codex 接入分别验证，配置位置、实际请求环境、服务执行位置可区分；目录与线程可用性不混淆，正式方法不采用绕过平台治理入口的直连绑定 |
| 市场与调用衔接 | 可见、可选择、可调用分别核验；选择前后状态变化、撤权、下架和重选有处理，选中版本可追溯；恢复不偷换版本、不重复副作用，市场选择不泄露私有实现 |
| 方法契约 | 三类共用五要素两视图；工具直接派发，专家与专家团共用编排；三层接口与孵化版本可追溯 |
| 能力声明 | 第一项为能力声明，不与 `when_to_use` 并列；目标和边界明确，所引用输入、交付、校验及审批要求一致；公开展示不另存独立承诺，不以子方法能力并集替代作者声明 |
| 步骤结构 | 每步一次已孵化方法调用，步骤仍有独立映射与恢复；拒绝多调用执行体、任意脚本和清单外映射计算 |
| 方法与步骤输入 | 方法输入表达对外要求，步骤按需映射多种来源；数据齐全时允许直接执行，不人为增加首个输入步骤；缺项及后续分支需要的补充内容按声明处理 |
| 数据与依赖 | 每项输入有来源，每项承诺产物有生成路径；数据依赖和质量依赖不混淆，内部动作依赖也能核对 |
| 权限与审批 | 权限要求与批准事实分开，方法调用与其实现受相同边界约束；按实际连接、操作、范围及内容匹配批准，有效批准可复用，子调用不扩权；更换账号或内容不能沿用不匹配的批准 |
| 验收与结果 | 技术成功不代替业务验收；部分完成、不适用和失败明确区分；内部动作全部成功但整体交付缺项时不得通过 |
| 失败与恢复 | 工具方法实现或专家计划部分完成后中断，恢复不得重复已生效副作用；输入或版本变化后失效范围正确 |
| 复用与版本 | 同一方法可在不同步骤以不同输入使用；层级不固定；工具方法实现随方法版本冻结；类型变化重新孵化，接口相同仍复核权限、费用及副作用；远端代码不可冻结时披露证据边界 |
| 记录与计数 | 步骤、内部动作、方法调用和模型轮次分别可追溯，不伪造未调用方法或未执行分支的成果 |

CAGR 应覆盖不同专家中的复用及适用域边界；单调用步骤及封闭映射应覆盖第二次调用失败、结果合并失败和恢复；C07 应核对每个回测起点的数据可得性及最终指标、期间、点值和上下界覆盖。具体业务判断及阈值来自作者，验证不擅自补入投资规则。

### 3.5 方法市场是重要建设内容

**方法市场建设是这套方法与模板体系的重要组成部分。**步骤允许通过“候选集合＋选择规则”赋值后，需要持续提供可发现、可理解、可筛选、可核验的方法供给。市场建设既要有满足统一五要素两视图的实际方法资产，也要有目录、选择接口和与调用体系的衔接；只有展示页面或方法名称列表不能支撑上述机制。

市场面向工具方法、专家方法和专家团方法三类完整方法；模板可以作为创作资产被发现和复用，但须与可调用方法明确区分。方法库与知识库继续并列，市场不把知识条目或未闭合模板当成可调用方法。这里的“市场”也不意味着每次发现都收费或自动购买，私有、共享、公开及商业使用范围由相应规则决定。

| 建设内容 | 需要形成的能力 |
| --- | --- |
| 方法供给与契约 | 逐项补齐五要素两视图、精确版本、来源及实现绑定，标明候选稿、验证范围和发布状态；专家和其他方法遵循统一结构，名称或标签不能代替契约 |
| 能力发现与筛选 | 为作者和运行宿主提供检索入口，按能力声明、输入输出要求、适用边界、运行环境和可见范围查找；支持指定子集，不要求将整个市场一次性注入模型上下文 |
| 候选详情与比较 | 提供足以判断适用性的契约视图、版本、限制和验证证据；公开信息由方法定义派生，私有正文、代码、用户数据和凭据不因可检索而暴露 |
| 使用资格与调用条件 | 区分看得见、允许选用和本次可调用；核对方法使用权、许可或价格条件，运行宿主另行核用户连接、资源范围和动作审批；不得把上架当成获得数据访问权 |
| 版本与可用状态 | 可解析到精确发布版本和摘要；处理更新、停用、撤回、暂不可用及历史追溯，目录变更不偷偷修改已经锁定的任务 |
| 选择与 tools 衔接 | 将通过检查的市场候选解析到 tools 中心的注册项及执行绑定，宿主再按相同调用检查执行；方法不能只在目录中存在而没有可验证的调用路径 |
| 质量与运行反馈 | 保留适用范围内的验证证据、选择及失败原因，支持评价与改进；排名、热度或模型推荐不替代业务验收，不自动扩大能力承诺 |

建议职责按现有架构衔接：knowlab 负责方法创作、五要素两视图与版本；knowmart 承接市场目录、发布与使用资格；tools 中心按 1.9 分担统一目录与两端实际注册、连接和调用职责，并按 1.8 表达后端 runtime 与 Codex 两种接入路径；knowbench 负责本次选择编排、输入映射、资源授权、审批、执行与恢复，正式方法的工具调用均经过 KnowBench 治理入口，实际执行可交给绑定指定的适配器与环境。作者在 knowlab 的模板编辑中也可使用市场候选。各方引用同一方法身份和版本，不复制出相互独立的能力声明与流程真源，也不因本节另建一套市场服务或执行引擎。KnowMart 使用一套实现提供工具方法、专家方法与专家团方法三个分类入口，共用许可、价格、匹配和版本机制，具体生命周期见 1.12。

现有市场衔接见[财务专家能力声明与版本方案](../../专家市场方案/luna/财务专家能力声明与版本方案.md)（Opus《能力声明与版本》第一稿已删，原文见 sunmoonun 提交 `7a1d33854`），现有应用说明见[knowmart 说明](../../../../project-guide/repos/knowmart-app.md)。这些文档中的专家目录与选择入口可作为承接位置；本节提出将其扩展为面向统一方法、支持步骤赋值的能力，不表示现有系统已具备通用方法检索、契约匹配和运行时选择的全部能力。

后续实施建议先以有限的已验证方法集跑通“查候选—读契约—选定并钉版—解析 tools 绑定—核权执行—验证结果—中断恢复”，覆盖无候选、接口不兼容、无权使用和选中后不可用；再扩大方法供给与开放范围。先完成方案和契约评审，本轮不实施市场、支付或运行协议，也不把财务候选清单直接上架为已验证方法。

#### 3.5.1 检索完整性与选用依据

聊天找方法、用户请专家和步骤选择方法共用以下规则。检索记录须明确本次有权查询的目录范围、查询条件、目录版本或可核对依据、分页完成情况及异常。分页截断、服务异常或部分目录未查完，只能报告“查找未完成”或给出明确标注的部分候选；不得报告“市场上没有合适方法”。查询完成后的无匹配结论，也只适用于本次获准检索的范围和条件，不据此推断不可见目录。

用户明确指定的方法或算法属于选用硬约束，不能降为可选或用名称相似的方法替代。需要改变要求时由用户明确确认；方法名称与版本相同也不能免除适用范围和排除条件检查。

选用依据沿用共同选择记录，关联问题内容摘要及修订、调用上下文、目录依据、选择约束、精确方法版本和宿主核验结论。正式创建委托或派发前，宿主重核用户及项目归属、当前问题修订、版本资格、授权和费用条件；前端不能只提交一个方法名就绕过已核验选择。问题或条件改变时，按影响重新匹配或校验并记录，扩大已确认范围须重新确认；创建和派发沿现有调用身份保证幂等，不增加独立调用账。选择过程不授予执行权，查找完成也不自动开跑扣费。

作者流程见[新财务专家孵化方案](新财务专家孵化方案.md)，运行与验收衔接见[财务专家执行与验收方案](../../专家使用方案/luna/财务专家执行与验收方案.md)。本文明确目标结构，既有资产和代码是否满足这些要求须逐项验证，不将文档重写等同于实现完成。

### 4.4 两层组合的机制与模型验证

先验证机制，再检验模型规划质量。使用“财务专家 → 季节性预测与回测 → 单季还原、同比、预测、回测”的例子，其中包含两次向下调用层级；该例用于机制验证，不将财务算法写成平台专用特权代码。

#### 4.4.1 无付费模型的机制验证

使用合成输入、假驾驶器和受控工具适配器，至少覆盖以下情况：

| 验证点 | 通过条件 |
| --- | --- |
| 分类判定 | 只组合工具归专家；同一专家多次调用或多个版本仍算一种；两个不同专家身份或任何专家团依赖归专家团；候选分支按冻结的允许依赖分类，不随本轮选择变化 |
| 分类与派发一致 | 三类共用契约和调用记录，只有工具直接派发与组合编排两条路径；分类改变必须重新孵化并发布新版本，旧引用仍钉原版本；不得绕过统一调用机制伪装工具方法 |
| 展开与执行 | 顶层计划确认后按需展开；执行遵守依赖；正常展开不误耗纠错重排次数 |
| 输入绑定 | 主体、期间、单位及版本匹配；缺项明确暂停；内部可满足输入不重复向用户索取 |
| 返回与验收 | 下层验收后按导出映射返回；上层仍独立验收；不暴露未导出的中间资料 |
| 权限 | 父未逐份传入但在可委派范围内的资料可绑定；范围外、无委派依据和跨用途读取拒绝；父撤权/到期/收窄后后代停止新访问；新增外发须审批 |
| 限制 | 拒绝循环、超深度、超次数和超预算；合法重复调用可以被区分 |
| 用户修改 | 可选项可修改；删除必做须退出专家承诺并记录新计划；不能仍以原专家完整成果交付 |
| 确认流程 | 计划、数据、账号和费用同页提交，分别记录；OAuth 回跳与提交修订冲突可恢复；下层范围内展开不重复确认，扩大范围必须补充确认 |
| 公共调用 | 三类方法共用 call_id/父子体系，实现派发关联方法且不重复记费；聊天不虚构专家；工具方法越级调用拒绝，取消和撤权可追溯后代 |
| 恢复 | 展开提交、审批等待、派发后断线均可恢复；未知副作用不重放；取消传到下层 |
| 复用 | 计划可复用，但版本、数据、账号或授权变化后重新校验 |
| 孵化准入 | 未孵化版本在聊天/工作/专家均不可调用；安装失败可继续处理；过期不改写历史孵化结论；必需检查失败不能靠用户批准放行 |
| Skill 转换 | 依赖钉版，原文明示必做和交付未被丢弃；无法落实有明确缺项；转换前后职责一致；恢复沿持久计划，不重新解释原文 |
| 编排边界 | 字段选择/改名/引用绑定/引用集合通过；任意表达式、隐藏取数及专家步骤嵌代码拒绝；工具方法调用另一方法拒绝 |
| 市场与许可 | 已许可使用不因普通下架误停；安全撤销按影响阻断；类型升级重核权限费用；作者资料及输出许可沿调用树生效 |
| 条件验收 | 未选、不适用、缺项、失败和完成可区分；已承诺分支失败后不能因产物为空而免检；部分交付不冒充完整成功 |
| 检索与选用 | 分页截断、目录异常不产生无匹配结论；指定方法不能被降为可选；改题或资格、费用变化后重核，重复提交不重复创建委托 |
| 作者来源与派生 | 批量采用绑定具体定义修订；未接受的 AI 提议不能发布；派生改动使受影响证据失效，不自动继承旧版通过结论 |
| 依赖影响 | 能追到上层版本、候选分支和实际调用；潜在与实际依赖分开；撤权即时核验，不等待通知；未受影响分支不被一律停止 |
| 测试集与授权 | 方法升版不自动改题或资料；原件与加工版本均固定；资料缺失或撤权不偷换输入，重测使用新核验的运行授权 |
| 判分隔离 | 预期答案不进入规划上下文；中间断言正确区分重复调用，漏选或匹配歧义失败；诊断性补计划不计入独立规划通过 |
| 协作隔离与交接 | 独立分析阶段不见对方结论，复核阶段只读获准成果；产物版本和分歧可追溯；多个实例不覆盖同一成果 |
| 协作交互与收尾 | 卡片来源及决定权正确，作者选数工单最小披露；预算计入复核和汇总，取消及恢复保留副作用事实；进度来自运行记录 |
| 组合验证证据 | 替身测试明确模拟边界，独立于整体端到端结果；引用参考模式不视为方法通过孵化或运行验证 |

#### 4.4.2 真实模型的质量验证

机制验证通过后，在已授权的模型与费用范围内，对代表问题运行真实规划。记录候选方法、作者规则、输入口径、实际计划及版本、调用树、模型轮次、费用和各层验收结果。

检查该选的是否选中、不该选的是否排除、必做和条件必做是否满足、最终结果是否正确，并与可用的单层或固定计划比较。不能凭一个成功案例声称通用递归质量已验证，也不预先承诺一定节省费用。

原讨论提到 11-02、11-03 的单层动态专家联调，历史记录位于平台 `scripts/results/第二轨联调/`；本轮没有重新执行，也没有多层质量实验。该历史经验只能说明部分单层机制曾验证，不能替代本节验收。

### 4.5 作者孵化测试：测方法池和规则，记录实际计划

机制测试验证执行系统，作者测试验证这份方法能否解决其承诺的问题，两者不能替代。作者为方法版本维护测试问题、预期产物、业务验收条件和所选资料；测试对象是冻结的方法池、编排规则、权限需求及验收规则，不是只跑一次已经挑好的顺序。

每个用例至少记录根方法版本、候选方法池/准入规则快照及所选精确版本、作者规则版本、数据及输入口径、实际计划与修订、调用树和导出结果、模型与必要配置、轮次/费用、各层验收和失败原因。记录可核对的选择依据与证据，不要求模型提供隐藏思维链。

#### 4.5.1 测试集版本与方法版本分别冻结

测试集由作者按题确认，独立于被测方法版本维护。方法升级时可用原测试集对比，不能自动替换题目、资料或预期结果；作者修改这些内容或判分规则时形成新测试集版本，并记录变化依据。跨方法版本测试须核对用例仍适用；接口或承诺变化导致不可比时明确标注，不能静默改题后继续宣称同题改进。

每份输入资料固定内容身份、精确版本与摘要；使用解析、分页或表格提取等加工结果时，同时固定实际读取的加工版本、读法及摘要。重测不得悄悄重解析或切到最新披露资料。仅引用外部地址不能证明内容被冻结；无法提供既定输入时记录不可重放及原因，不以新资料替代旧证据。

冻结资料不冻结访问权。每次测试重新核对当前数据许可并建立本次运行授权，不复用过期授权；资料撤回或无权读取时暂停或判为无法开展本次测试，保留既有证据与原因。作者可有意移除必需或可选资料，甚至提供空输入集，验证缺项、等待和拒绝行为；用例期待被测方法正确拒绝时，测试可通过，但不能把方法本次未执行记成业务执行成功。

#### 4.5.2 判分断言不反向决定计划

规划器使用题目、获准输入、已冻结方法池及作者的执行规则。测试专用预期答案、预期方法命中和产物断言由评测端持有，不作为规划或执行上下文；作者方法本身的必做、权限、审批和业务校验规则仍须正常提供，不能为隔离答案而隐藏执行约束。预设的用户答复按实际交互时机提供，与测试答案分开。

测试可以对最终产物及中间调用产物作断言。中间目标以调用位置、方法精确版本、输入条件或明确的匹配范围识别，关联实际调用及产物版本；同一方法可以多次出现，不沿用“最多调用一次”限制。多个结果如何匹配或逐个检查由用例声明，匹配歧义或应有产物缺失如实失败，不能任取一次通过的结果冒充目标。

用例要求某方法应被选中而实际漏选时，按缺少调用或产物判失败；不得因为断言存在就强迫规划器补选、修改已存计划或放宽判分标准。为诊断主动给定计划或反馈答案的运行须另标用途，不能计作独立规划通过。运行期验收与用例判分分别留证，避免用评测端的补救掩盖实际规划质量。

#### 4.5.3 覆盖与回归

用例覆盖必做、条件必做触发与不触发、不同问题下的可选分支、缺资料、范围不足、不适用及失败恢复；检查该选的是否选中、不该选的是否排除，公共产物和条件产物是否兑现。具体覆盖门槛由作者业务标准及验收要求确定，不能把一次生成计划的成功推广到全部合法计划。

重放同一实际计划用于诊断和回归；重新规划用于检验方法池与规则在不同问题或模型输出下是否稳健，两种结果分别记录。模型或候选版本变化需要重评的范围有依据，不偷换测试输入或验收标准。只有一种合法计划的专家同样保留数据、实际调用和业务验收证据，不增加模型规划轮次，也不另设类型。
