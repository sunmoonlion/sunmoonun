# 原子方法和组合及模板

日期：2026-11-12。本文整理关于方法、工具注册和调用的讨论，并承接原《财务方法原子化与组合模板》的组合内容；按所有者本轮决定，将六项作业要素作为任意一级方法的必备契约。

本轮确定的设计出发点是：**原子方法就是工具，专家也是方法，是下级方法的集成；各级方法采用同一套公共契约，完成实现与验证后注册为 tools 中心的可调用项。**方法的业务定义和程序调用契约属于同一个能力对象；执行绑定、组合内部结构和创作模板分别表达。六项必备内容是本方案的设计要求，具体字段拼写及运行映射仍是候选设计，尚未实现或完成契约验证。

原 M01—M20 的工具契约、提炼去向、完整样例及历史审查证据，见[原20个财务方法的原子化提炼](原20个财务方法的原子化提炼.md)；该稿按 2026-11-11 的要求编写，仍需按本次六要素逐项补齐和核对，不能视为已满足新增要求。本文的 C01—C15 仍是候选模板，不因文档整理成为已发布专家或已注册能力。

## 一、原子方法

### 1.1 原子方法就是工具

原子方法是可独立调用、具有明确用途、输入、输出和验收规则的能力。在本方案中，它作为工具进入统一注册中心，不再另建一个同义的“工具对象”，要求每个原子方法再关联它一次。

方法库与知识库在资产职责上并列：知识库提供事实、资料与证据，方法库提供解决问题的能力。方法可以引用获准使用的知识；这种并列不要求新增两个独立服务。

同一公共契约适用于原子方法、组合方法和专家。上层只需按契约提供输入并取得结果，下层可以执行一个算法，也可以组织多个方法。专家的业务身份和组合结构不改变它作为方法的可调用性；tools 中心的注册项也不同于每次运行产生的调用实例。

“原子”表示在当前业务层面有独立用途、能够复用和验收，不表示程序内部只有一条语句、一个公式或一次模型请求。例如 CAGR 原子方法包含输入相容性检查、年间隔确定、适用域检查、计算和证据输出，不拆成相除、乘方、减一三个业务方法。

同一原子方法可以有不同执行实现；这些实现须满足同一份业务契约。通用计算、文件读取等基础能力也可进入工具注册中心，是否纳入某个专家的方法范围由该专家的定义决定，不能因为平台有工具就宣称专家具备全部能力。

只有一段方法正文、没有明确调用入口和可验证输出的候选，仍需工程化才能成为可用的原子方法。对于需要模型推理的做法，由宿主程序提交指令与输入、处理模型输出及工具请求，并按约定交回结果；不能把“有一段提示词”直接等同于已完成实现。

### 1.2 分开实现方式、接入方式和调用来源

| 维度 | 回答的问题 | 分类及边界 |
| --- | --- | --- |
| 实现方式 | 程序实际怎样完成工作 | 函数、HTTP 接口、命令行程序、脚本等；内部可组合使用，也可由程序组织模型推理 |
| 接入方式 | 当前宿主程序怎样注册和访问该能力 | 直接注册；通过 MCP 查询工具目录并注册调用代理 |
| 调用来源 | 本次调用由什么发起 | 业务程序直接发起；宿主程序处理模型生成的 Tool Call 后发起 |

这三个维度不合并为一个 `Tool/MCP/CLI/Script` 枚举。函数、HTTP 接口、命令行和脚本既可直接接入，也可在 MCP 服务中封装为工具。

直接接入按宿主程序的执行入口配置：

```text
直接注册
  ├─ function：调用已注册函数
  ├─ http：请求指定 HTTP 接口
  ├─ process：启动进程
  │    ├─ 可执行程序及参数
  │    └─ 解释器、脚本及参数
  └─ composition：进入现有执行器组织下级方法

MCP 接入
  └─ MCP 服务引用、远端工具名及调用映射
```

脚本是实现载体，命令行是启动方式；使用 `python cagr.py` 时，执行入口是进程，实际载体是 Python 脚本。MCP 工具的内部实现可以不对当前宿主公开，不要求作者猜测服务端是函数还是脚本。

### 1.3 注册与调用机制

注册中心保存各级方法的调用契约与绑定关系，执行器完成调用。注册中心首先作为逻辑模块设计，不据此新增独立注册服务或第二套任务运行器。直接绑定可以指向函数、HTTP、进程或现有组合执行入口；MCP 绑定可以代理原子方法或组合方法。组合方法和专家不因层级不同而另建执行体系。

```text
直接登记契约和执行入口 ─────────┐
                              ↓
MCP tools/list → 登记调用代理 → 统一工具注册中心
                              ↓
                    按任务授权与环境解析绑定
                              ↓
业务程序直接调用 ─────────→ 统一执行入口
模型 → Tool Call → 宿主程序 ────┘
                              ↓
              直接执行 / MCP 请求 / 组合执行
                              ↓
                     执行结果、证据及验收
```

模型生成工具名称和参数，不执行工具。宿主程序根据请求找到注册项，再调用函数、启动程序或发送 MCP 请求。业务程序直接发起的调用也经过同样的参数、权限和版本检查。

MCP 接入时，`tools/list` 用于发现工具名称、描述及参数定义等；注册的是描述与调用代理，执行时通过 `tools/call` 请求服务端。MCP 服务可以是本地进程或远端服务；接入协议不等于部署位置。协议依据见 [MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)和[架构说明](https://modelcontextprotocol.io/specification/2025-06-18/architecture)。

外部目录条目只有技术描述时，仍需核对它是否满足原子方法要求的业务输入、输出和验收，不能仅凭名字相同认定实现等价。模型端使用的工具名可以是受接口命名限制的别名，运行时须能准确映射回注册标识和绑定，处理不同服务的重名。

### 1.4 契约与绑定字段

所有级别使用同一公共结构：身份与版本、六项作业契约、调用范围及执行绑定。六项作业契约的完整定义见 1.6，以下不另造一套同义字段。实施时先映射现有方法契约，验证缺口后再决定变更，不直接宣布新增协议版本。

| 对象 | 建议字段 | 含义 |
| --- | --- | --- |
| 各级方法契约 | `id`、`version`、`digest` | 稳定身份、业务契约版本及冻结摘要 |
| 各级方法契约 | `name`、`description` | 名称与用途摘要，不代替六项完整声明 |
| 各级方法契约 | 六项必备字段（见 1.6） | 适用、输入与权限、步骤、校验、产物、审批 |
| 各级方法契约 | `allowed_callers` | 可允许 `host`、`model` 或两者；实际执行均由程序完成 |
| 执行绑定 | `binding_id`、`method_ref`、`kind` | 绑定身份、精确方法版本、`direct` 或 `mcp`；是否为组合不属于接入方式 |
| 直接绑定 | `handler.kind`、类型专属配置 | `function`、`http`、`process` 或 `composition`，分别校验注册函数、请求映射、进程参数或现有组合执行入口 |
| MCP 绑定 | `server_ref`、`remote_tool_name`、映射配置 | 对应服务、工具名及必要的参数／结果映射 |
| 直接组合执行配置 | `composition_ref`、执行入口引用 | 钉版组合定义与现有执行器；包含子方法调用映射，不另建专家专用引擎 |
| 执行绑定 | `implementation_ref`、`environment_requirements` | 实现版本依据、依赖及允许的执行环境 |
| 调用记录 | `call_id`、`origin`、`method_ref`、`binding_id` | 本次调用身份、来源及实际采用的方法和实现 |
| 调用记录 | 输入输出引用、执行状态、验收结果、证据 | 保存实际发生的事情；业务结果与技术错误分别表达 |

身份与业务契约保持统一，部署绑定可随环境不同而分别配置。作者确认方法含义和规则，工程配置执行入口；服务地址、工作目录、凭据引用不混入业务方法正文，凭据值不进入方法资产。

例如 A05 CAGR 可以绑定一个 Python 脚本，也可以绑定 MCP 服务中的 CAGR 工具。两种实现都必须核对主体、期间、单位和口径，遵守同一公式与适用域，交付规定的结果及证据。仅返回一个数值、未满足完整契约的通用计算工具，还不足以直接作为 A05 的等价实现。

### 1.5 可用范围、版本与验收

注册不等于获准使用，展示给模型也不替代执行时检查：

```text
已经注册的能力
  → 专家与方法声明允许的能力
  → 用户授权且当前环境可执行的能力
  → 本轮提供给模型的工具集合
```

允许调用某工具与要求必须完成某操作要分开。模型看到工具不代表一定调用；必做计算、必要证据和检查必须在方法规则或组合规则中明确，并在交回时验证。程序直接调用也不能绕过这些要求。

同一任务记录精确方法版本和实际绑定。目录刷新不能无记录地替换正在运行的实现；MCP 目录快照不等于服务端代码被冻结，服务端缺少实现版本依据时应如实标明可复现范围。

HTTP 成功、进程退出码为零和 MCP 返回结果只是执行层依据，不能替代业务验收。正确计算出“不平”“缺项”或“不适用”可以是有效结果；是否继续由组合或专家规则决定。超时、取消、重试和副作用沿现有任务机制管理，不能为得到期望数值而盲目重试。

### 1.6 任意一级方法的六项必备作业契约

本节借鉴[agent-team-argon 调研稿](../../参考资料/agent-team-argon.md)中 Skills 与 Routines 一节整理的六项作业要素，按所有者要求用于本项目所有级别的方法。这里采纳的是六要素结构，不将调研稿关于方法、专家和专家团必须分成独立契约的判断作为本方案约束；本方案坚持专家也是方法。本节不据此宣称所有 Skill 标准都强制这六个字段。

六项都必须存在且有明确内容，不能靠方法名称、正文中的暗示或模型自行补足。内部可使用结构化对象、说明文字与钉版引用共同表达；可检查的条件、Schema 和审批规则须能被宿主解析，不能全部埋在自由文本里。

| 必备内容 | 建议字段 | 必须说明什么 |
| --- | --- | --- |
| 何时使用（When to use） | `when_to_use` | 要解决的问题、适用前提、触发条件及不适用边界；用于选择方法和调用前检查 |
| 所需输入与权限（Required inputs and access） | `required_inputs_and_access` | 输入 Schema、必需与可选数据、证据和来源要求，以及所需工具、资源访问范围和环境；缺项如何处置。只声明权限需求与资源引用，不携带秘密，也不等于已经取得授权 |
| 执行步骤序列（Sequence of work） | `sequence_of_work` | 固定算法或工作步骤、顺序与依赖、条件分支、允许的选择范围及失败处理；组合方法还要有下级方法版本引用和输入输出映射 |
| 结果校验方式（How to validate） | `how_to_validate` | 检查项、检查方式、通过标准、证据及失败处置；明确哪些由程序校验、哪些需模型评估或人工判断，不能只写“结果正确” |
| 返回产物格式（What to return） | `what_to_return` | 输出 Schema、文件或成果引用格式、证据及校验结果；明确成功、部分完成、缺项、不适用等业务结果怎样表达，避免只交一段无法验收的回答 |
| 何处必须审批（What requires approval） | `what_requires_approval` | 需要审批的动作或步骤、触发条件、审批人角色、批准范围、等待或拒绝后的行为，以及已有批准的适用条件；没有方法自身额外审批要求时显式声明 `mode: none` |

**必备字段不等于每次都要人批。**`mode: none` 只表示方法没有追加审批点，不能覆盖平台、用户授权或下级方法已有的限制。运行时由宿主核对有效授权与审批记录；在同一批准范围内继续执行，无需因进入下一层方法重复请求。出现新动作、扩大范围或已有批准失效时，才按规则等待补充批准。模型不能自行批准自己的请求。

**各级填写同样六项，但内容对应本级职责。**原子方法写明本身怎样处理输入；组合方法写明怎样组织子方法；专家写明怎样完成整个问题并验收交付。下级全部成功不自动等于上级目标完成，上级仍需核对整体覆盖、相容性与交付要求。

以已经讨论的财务方法为例，以下是填写尺度的示意，不替作者增加业务判断或验收阈值：

| 六要素 | 原子方法：CAGR | 组合方法：增长分析 | 专家方法：财务分析专家 |
| --- | --- | --- | --- |
| 何时使用 | 比较相容期初、期末值的年化增长，满足既定适用域 | 题目要求历史增长分析 | 题目落在专家声明的财务分析范围内 |
| 输入与权限 | 期初值、期末值、年间隔、口径和证据引用；纯计算不要求额外外部访问 | 所需历史序列、期间口径及所选子方法需要的数据与授权 | 本题范围、获准使用的数据和可执行的下级方法 |
| 步骤序列 | 核对口径与适用域，按已定公式计算并组织证据 | 按规则选用同比或 CAGR 等子方法，映射输入并汇总 | 按题形成受约束的计划，组织分析方法，整合交付 |
| 结果校验 | 输入边界、公式复算与证据完整性 | 子结果有效、期间和主体相容、所需指标覆盖完整 | 本题必做目标覆盖、结论与证据一致、局限披露完整 |
| 返回产物 | 结构化增长率或不适用结果，以及期间、口径与证据 | 结构化增长分析成果及子结果引用 | 本题约定的分析成果、报告及证据索引 |
| 必须审批 | 已授权输入上的纯计算可声明无额外审批 | 遵守子方法及本级的审批规则，无新增要求则声明无额外审批 | 列出本专家实际涉及的审批点；不能因叫“专家”就默认每步审批 |

为衔接现有文稿，`applicability` 对应 `when_to_use`；`input_schema` 归入 `required_inputs_and_access`；`rules` 归入 `sequence_of_work`；`acceptance` 归入 `how_to_validate`；`output_schema` 归入 `what_to_return`。输入权限和审批声明须单独补齐，不能从“只读”或“没有副作用”等描述中猜测。以上是语义映射，实施时采用嵌套或保留既有字段由契约评审确定，同一规则只维护一个真源。

Skill 可以承载这些作业指令；函数、脚本、命令行和 MCP 工具也必须补齐同样六项才能成为本方案的完整方法。六项完整不代表执行绑定已经可用，导入 Skill 或发现 MCP 工具后仍需映射、实现验证和注册。无需把确定性计算改成模型对话，也无需把方法全文无差别展示给调用模型。

## 二、组合

### 2.1 组合是什么

组合是在一个目标下组织若干下级方法，明确选用哪些方法、输入从哪里来、成果怎样传递、什么条件下执行，以及最终交付什么。下级可以是原子方法，也可以是其他已经定义的组合方法。工作稿补齐六项公共契约、执行绑定并通过验证后，组合本身成为可注册、可调用的方法；专家是其中面向完整领域问题的一种组合方法。具体任务再根据问题和授权数据形成有限执行计划。

组合不仅是方法清单，也不等于把方法正文顺序拼接后交给模型。至少要表达以下关系：

| 内容 | 需要明确什么 |
| --- | --- |
| 节点 | 节点标识、下级方法精确版本、选定配置；同一方法可有不同参数实例 |
| 输入映射 | 本题输入、授权事实或上游成果分别进入哪个输入槽 |
| 数据依赖 | 哪个结果可用后才能执行后续方法 |
| 质量依赖 | 核验结果对后续执行有什么限制；核验摘要不能代替业务数值 |
| 选择规则 | 必做、条件必做、可选的条件，以及选择依据 |
| 参数约束 | 主体、期间、单位、版本、公式变体等怎样保持相容 |
| 异常处置 | 缺项、不适用、验收失败时等待、停止或按已定规则交付局限 |
| 交付与验收 | 哪些结果必须覆盖，如何证明没有漏做或引用未执行成果 |

### 2.2 方法选择与实际执行

组合可以预先指定方法，也可以在冻结的候选集合和规则内，由模型提出选择与参数建议。宿主程序校验选择、依赖、输入和授权后执行。模型提出调用建议不能扩大专家已经声明的能力或改变作者规定的公式。

固定与动态组合共用运行机制。对必做节点，不能只写“模型可以调用”；对条件节点，保存实际触发条件与采用依据；未选节点不伪装成已执行结果。

组合节点数量、工具调用次数、模型轮次是不同数量。相容的独立计算可以批量处理，并逐项保留结果与证据；有数据或质量依赖的节点须等待前置条件成立。无需为每个原子方法强制开启一轮对话，也不能为了减少轮次跳过验收。

原子方法的程序实现可复用内部函数或基础工具；当需要让作者选择、替换或审阅多个业务方法及其依赖时，应显式表达为组合。多级组合按钉版引用形成有限、可检查的计划，验证时拒绝循环依赖；运行时保留父子调用关系、权限范围及预算约束。统一方法契约不等于允许运行时无限递归调用，也不要求为每一级建立新执行引擎。

### 2.3 组合字段

组合沿用 1.4 与 1.6 的公共字段，不另建一套与原子方法不同的对外契约。下表是 `sequence_of_work` 的组合结构；本级输入、输出、验收与审批分别归入六项公共字段。

| 建议字段 | 含义 |
| --- | --- |
| `nodes` | 节点标识、精确方法引用、选定配置、参数 |
| `input_bindings` | 每个必需输入的供应者及映射 |
| `dependencies` | 数据依赖和质量依赖，分别标明 |
| `selection_rules` | 必做、条件必做、可选的规则 |
| `failure_policy` | 缺项、子方法失败或不适用时怎样处理，与本级验收规则一致 |

这些是逻辑职责，不要求实现为新的存储表。执行记录复用现有 Task/Attempt、输入版本、成果和验收机制；方法被调用成功，不等于整题已经交付完成。上级汇总本次所选子方法的输入与权限需求，保留其必要审批条件；不能用上级“无额外审批”消除下级限制，也不能把未选择分支的权限一概索取。

### 2.4 C07：原季节性预测与回测的组合实例

以下内容从原文的 C07 详细示例迁入，保留原算法、窗口、依赖与验收约束；编号含义见[原子化提炼稿](原20个财务方法的原子化提炼.md)。

1. 作者先接受预测公式、允许的指标、4/8季窗口、回测范围及数据质量规则，形成组合的固定语义。
2. 实际题目给出目标季度。计划反推上年同季基数、同比所需的前期季度，以及每个回测起点的独立窗口；不是仅检查“总共有16个季度”就认为足够。
3. 原始累计数据先经A03产生单季，已有可信单季则不重复差分；A04构造相容的同比序列。
4. P02在四个历史起点分别调用已钉版的P01逻辑，所有起点禁止读取当时不可得的输入。P02是对指定预测方法的受限回测，不是允许运行模型传入任意新算法。
5. P01对本题目标季度计算点值与上下界。保留原作者方法：上年同季乘以一加近4季同比中位数；上下界使用近8季同比最小／最大值。回测合格与否、能否继续，服从作者明确规则，不由模型临时降门槛。
6. 最终成果按“指标×目标期×点值/上下界”和“指标×回测期×预测/实际”验覆盖；缺哪一格就说明哪一格，不能把有个horizon=2当作交齐。

在工程上，P01/P02的关系可先使用明确的输入输出及共享确定性预测实现，不需要支持任意方法调用任意方法的递归运行。模板展开后的任务计划仍是有限、可检查的计划。

## 三、模板

### 3.1 模板是什么

模板是可复用、可编辑的组合起点。它保存一类问题的默认方法、配置、连接关系和规则，作者应用后得到自己的组合工作稿，可以增删、替换和补入原创方法。

三者关系是：**原子方法提供基础能力，组合形成更高一级的方法，模板保存可复用的方法契约与组合结构的创作起点。**模板不是已发布专家；一位专家可采用多个模板形成自己的定义，也不因此成为专家团。

方法调用时传入公司、年份等具体值，属于运行参数；模板应用时选择方法、调整依赖和规则，属于创作配置。两者不能混为一套允许模型任意改写业务规则的参数。

### 3.2 模板内容与应用过程

组合模板保存：六项公共契约的默认内容或明确待填写项、默认选中的方法与配置、依赖映射、必做／条件选规则、由方法输入派生的数据需求摘要。作者能删改和补入原创方法；模板应用后进入创意工作稿。首版复用现有创意／模板机制，不建设递归组合市场或独立组合运行服务。

| 建议字段 | 含义 |
| --- | --- |
| `id`、`version`、`purpose` | 模板身份、版本及适用问题 |
| `method_contract_defaults` | 1.6 六项公共契约的默认内容或明确待填写项；待定内容补齐前不能将生成的方法冻结为可用版本 |
| `default_composition` | 默认节点、精确方法引用、配置及依赖映射 |
| `author_options` | 作者可编辑的选项及约束；业务规则变更需显示差异 |
| `parameter_defaults` | 默认配置及适用边界，不预填虚构业务事实 |
| 交付要求视图 | 从公共契约中的 `what_to_return` 与 `how_to_validate` 派生，不重复维护一份交付规则 |
| 来源与验证说明 | 原始依据、适用限制、候选状态和已验证范围 |

`default_composition` 是公共契约默认值中 `sequence_of_work` 的组合定义引用，不重复维护两套节点与规则。数据需求摘要从已选方法的输入派生，不单独维护一份可能与实际组合冲突的清单。模板可以保留待作者填写的位置，但注册为可用方法前，六项必须完整；没有额外审批也必须显式声明。模板应用时保留模板来源版本；修改后的工作稿有自己的状态，不能把作者改动写回他人的模板。

```text
选择模板版本
  → 展开默认组合
  → 作者调整方法、参数和规则
  → 补齐六项公共契约，检查依赖、输入、权限、审批及交付覆盖
  → 测试并冻结专家版本
  → 本次任务按问题形成计划和实际绑定
```

模板可以引用其他模板作为编辑便利，但孵化时须展开成可审阅、有限的专家定义，检查去重、依赖、参数冲突和权限。运行阶段不再递归拉取模板“最新版”。若首版没有模板嵌套编辑能力，直接展开保存，避免新增一套兼容负担。

### 3.4 模板怎样验证

先用三个贯穿样例检验契约：原四式核验、CAGR、累计转单季—原预测—回测链；再按原方案扩充当前专家需要的指标、证据核对与报告组织。模板数量和方法数量不作为成熟度依据。

验证至少覆盖：每个必需输入有供应者；数据与质量依赖类型正确；选项变化后必做要求和交付范围同步变化；缺项及不适用不会被伪造为成功；各项业务规则仍符合作者接受的定义。

按六项公共契约增加文稿与实现验证：原子、组合、专家三个级别均有完整声明；缺少任一项或仅有待定占位时不得注册为可用方法；纯计算方法声明无额外审批时不会无故弹出确认；上级不能绕过子方法的权限和审批要求；步骤与执行绑定相符；子结果全部通过但整体交付缺项时，本级验收仍不能通过。

对同一个 CAGR 原子方法，可验证它在年度财务分析与研发投入增长两种组合中的复用；执行绑定的替换须另证实输入、结果和证据契约等价。对 C07，重点核对每个回测起点的数据可得性及最终指标、期间和点值／上下界覆盖。
