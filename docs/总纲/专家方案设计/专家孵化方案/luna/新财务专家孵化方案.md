# 新财务专家孵化方案（Luna，knowlab）

日期：2026-11-09。状态：讨论稿，未定稿、未实施；由 11 月 8 日《新财务专家改造方案》整理，结合 qwen 现有目录和 Opus 11 月 9 日方案补充边界。

本页负责作者如何形成同一财务专家的新版本。详细方法清单见[财务方法原子化与组合模板](财务方法原子化与组合模板.md)，任务执行见[执行与验收](../../专家使用方案/luna/财务专家执行与验收方案.md)，对外声明和历史版本见[市场方案](../../专家市场方案/luna/财务专家能力声明与版本方案.md)。来源与拆分去向见[本目录说明](README.md)。

## 一、目标与已经明确的方向

保留同一位「财务分析与预测」专家，给它形成按问题选择方法的新版本。方法库、单个专家、专家团是不同对象；这次财务专家改造不以先完成专家团为前提。

依据 [11 月 3 日架构决定](../../../../design/SDD/architecture/methods.md) 与 [Opus 记录的 11 月 8 日讨论](../opus/模板与方法.md)：

- 财务专家产品保留，固定计划与动态计划共用执行体系。
- 原八步混合了通用流程和专业方法，不能直接改名为八个原子方法。
- 勾稽属于方法；是否被规则要求必做，是另一维度。
- 对照管理层讨论属于可挑方法；具体触发条件、逐条支持判据及变更范围仍需作者定型。
- 通用组织机制可以共用；带专业判断的范围解释、方法选择和成稿规则由作者确定。Opus 提出的具体五段模板仍是待讨论方案。

11 月 8 日旧稿中将“管理层讨论是否可选”混在待定项里的表述在此收敛：可挑方向已有记录，待定的是何时选择及选中后怎样执行，不能把它重新解释为每题必做，也不能任意省略。

## 二、作者如何从想法走到可测试版本

作者可以自己写、让 AI 提出建议、导入自己的材料，也可以选有使用权的方法或可编辑组合。这些方式都回到同一份工作稿，不强迫每个原创想法先进入成熟方法库。

建议过程：

1. 确认改造对象：作者身份、专家身份、当前发布版本、包摘要和旧验收依据。本文未查询线上主档，不填写推测版本号。
2. 将原专家要求逐项映射到方法、选择规则、数据条件和交付承诺。每项标保留、拆分、拟改或待定。
3. 作者查看 AI 建议与差异，修改、接受或拒绝。投资判断、阈值及预测口径不能因工程拆分自动成为作者原话。
4. 方法定义冻结后，工作稿引用精确版本；组合模板作为编辑起点，展开后能审阅，不在运行中追随模板最新版。
5. 出准专家版本，用作者确认并钉住的数据测试；失败回工作稿修改，再出新版本。
6. 内容接受、测试、审核、上架各保留自己的依据，不互相代替。

这里沿用[已定的自助孵化流程](../opus/专家孵化方案.md)。方法库复用范围仍服从所有权和许可：可查看公开声明，不等于能复制另一作者的方法正文或绑定数据。

## 三、五类内容分别由谁负责

| 对象 | 内容 | 负责边界 |
| --- | --- | --- |
| 方法定义 | 独立目的、输入、适用域、做法、结果和验收 | 作者确认专业含义，knowlab 工程化并冻结 |
| 创意组合 | 选哪些方法、怎样接输入、参数怎样协调 | 作者可编辑，不自动成为已发布专家 |
| 专家规则 | 何时必做、何时可选、缺项如何处理、交付什么 | 作者定型并随专家版本冻结 |
| 通用执行机制 | 调度、等待、授权、审批、预算、存储和交付动作 | knowbench 统一提供，不冒充财务方法 |
| 本次任务 | 问题、具体计划、实际授权、绑定和运行证据 | knowbench 按冻结能力与用户授权执行 |

方法输入描述业务所需事实，不是要求作者预先列出每件委托的公司和数据清单。实际数据需求由本题和所选方法提出，再由数据主人确认。

## 四、原八步的内容去向

| 原步骤 | 建议拆分 | 改造时应保留的边界 |
| --- | --- | --- |
| 定范围 | 平台的确认与超范围处理机制，加专家自己的范围解释规则 | 主体、期间、交付目标需明确；合并/母公司等领域口径不能全部写进平台通用步骤 |
| 数据摸底 | 实际输入就绪检查，加财务数据期间、版本与口径核对 | 提出数据需求不等于已有可用事实；确认和下载都不能替代实际检查 |
| 勾稽 | 原四式核验方法，加作者规定的触发条件和核验范围 | 保留真实公式、1 元阈值、未核验与不平的区别；不能用替代公式冒充原式通过 |
| 取数 | 累计转单季等业务转换方法；与外部取数、原件加工分别表达 | 时点数不差分；已是单季的数据不重复差分；使用一致的来源和重述口径 |
| 算指标与分析 | 按实际职责整理增长、盈利、人均创收等计算与解释做法 | 不能把固定指标大全设为每题必算，也不能把计算和文字解释的验收混为一谈 |
| 对照管理层讨论 | 可复用的证据对照做法，加作者规定的选择条件 | 保留结论原文；仅在指定章节核对；未提及、只支持部分或口径不一致时按作者规则处理 |
| 预测 | 作者规定的季节性同比预测与回测组合 | 选择预测后落实全部必要依赖；不能擅自改成 DCF、三表预测或另一算法 |
| 成稿 | 平台的文件保存交付机制，加作者规定的报告组织规则 | 可复用的报告编排规则也可成为方法；不能一概固化到平台，或引用未执行分析的成果 |

数据需求与实际就绪不能混为一项：前者说“要什么”，后者说“拿到什么、能否使用”。界面可以连续展示，记录和判据仍应分开。

首版先完整承接现有年度分析、人均创收、单季还原、原季节性预测与回测及选中的管理层讨论核对。DCF、三表预测、股权治理等保留为方法候选或其他创意，不自动增加当前专家的能力。

## 五、原子方法与组合模板怎样进入工作稿

详稿保留 M01—M20 审查、45 个首轮职责定义、7 个待补规格候选和 15 个组合模板。它们是候选建议，不是平台给用户预制的投资结论，也不是本轮正式导入的资产。

作者入口建议分成“选方法”和“从组合开始”。两者都展示用途、所需数据、适用边界、来源、验证依据与待确认内容；作者可以增删并加入原创做法。应用模板后，展示新增的必做要求、能力变化与冲突，不能仅展示一个保存成功提示。

组合中所谓数据需求，是方法输入派生的需求摘要，不另加一份要求作者事先填写的整专家数据需求声明。下载、解析、授权、等待与写文件沿通用机制执行。

孵化验收至少回答：一个方法能否用于另一份创意；拆分后是否保留原义；每个输入是否有供应者；用户看到的定义是否与编译结果一致。方法数量不作为完成标准。

## 六、与 Opus 初稿的共识和差异

| 议题 | Opus 初稿 | Luna 建议／待解决处 |
| --- | --- | --- |
| 财务专家产品 | 同一专家出新版 | 一致，不拆成两个给用户区分的产品 |
| 通用模板 | 定范围、排计划、定数据、做方法、成稿 | 组织职责可共用；阶段次序和模型轮次须分开讨论 |
| 方法粒度 | 五个对作者可挑的方法 | 可以作为作者入口分组；内部复用职责可更细，不能因此强制增加模型轮次 |
| 数据摸底 | 并入定数据 | 可以并入同一界面，但保留“已确认／已获取／已核验”的区别 |
| 勾稽选择 | 按报表与预测条件触发 | 需逐题列依赖和检查范围；不能由优化默改原四式、阈值或排除条件 |
| 管理层讨论 | 可挑 | 一致；具体触发条件和全结论支持判据需要单独写清 |
| 新契约 | 统一格式，部分旧格式拟清理 | 先以样例证明现有结构不足，再决定最小变更；不能把未对外运行视为没有历史引用 |
| 内容与工程次序 | 分批补模板和格式，再出内容稿 | 先用代表性内容校准契约，避免先实现一套无法承载真实方法的格式 |

比较依据：[模板与方法](../opus/模板与方法.md)、[请专家与执行](../../专家使用方案/opus/请专家与执行.md)、[能力声明与版本](../../专家市场方案/opus/能力声明与版本.md)。这些差异是讨论输入，不是对其他助手稿件的定稿或替换。

## 七、建议先完成的三个贯穿样例

先把原四式核验、CAGR、累计转单季—原预测—回测链写成可核对的完整定义。它们分别验证质量规则、简单参数化计算、跨期依赖与组合。随后补当前专家需要的指标、人均创收、证据对照和报告组织，再扩充其他候选。

每个样例交回：作者核对的含义、输入与缺项、固定公式及适用域、输出、独立正反例、引用版本、调用结果和差异。工程承载不足时才提出契约变化，不先写几十个只有名称的空壳方法。

## 八、待讨论与后续审阅

| 事项 | 需要交付的决定 |
| --- | --- |
| 方法粒度与界面分组 | 五类入口与原子职责怎样对应，哪些配置独立冻结 |
| 四式范围、管理层讨论触发 | 逐题选用与必做规则，不改变未获接受的原义 |
| 比率异常与代理口径 | 逐配置决定零负分母、平均／期末、缺项和代理，不用全局默认代替 |
| 模板边界 | 平台组织文字、作者判断和可选报告方法分别放在哪里 |
| 首版能力范围 | 保底题和原专家承诺逐项覆盖，新增能力另行确认 |
| 工程与清理 | 样例承载证据、真实引用盘点、迁移和历史读取验证 |

定稿后再形成 SDD、决定记录和实施任务。Opus 后续审阅应区分作者接受、工程可实现性、测试证据和发布条件。本次仅归位整理，没有发送审阅任务，也没有执行模型回归或发布。
