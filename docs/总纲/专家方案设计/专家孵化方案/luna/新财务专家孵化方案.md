# 财务分析与预测专家首版孵化方案

日期：2026-11-14。状态：重新孵化方向已由所有者确认；首版具体能力、工具规格、实现、孵化测试和旧资产清理尚未完成。本文保留原文件路径，整体替代“改造同一财务专家新版”的方案。

**按新架构、新思路创建“财务分析与预测专家”的新身份，从第一版开始孵化；删除原财务专家的所有版本，不延续旧版升级与兼容路线。** 新专家以自己经作者确认的能力声明和验收要求为准，不以复刻旧版或通过等价迁移验收为完成标准。

统一方法契约见[方法主稿](方法、步骤、组合与模板.md)，从原 20 项提取工具的思路见[工具方法提炼示意](原20个财务方法的工具方法提炼.md)，执行见[执行与验收](../../专家使用方案/luna/财务专家执行与验收方案.md)，新身份与旧版退出见[能力声明与版本](../../专家市场方案/luna/财务专家能力声明与版本方案.md)。

## 一、重新孵化的出发点

从用户要解决的财务分析与预测问题出发，先确定首版承诺什么、需要什么事实、用哪些做法处理、如何验证和交付，再组织工具方法及专家规则。原八步、原固定包及旧接口不作为新定义必须适配的框架。

原方法正文、算法、业务纠偏、资料口径和测试题可以作为创作素材。是否采用，由作者逐项确认并留下来源；旧版已有不等于新首版必做，旧版测试通过不等于新定义已经验证。已采纳的公式、阈值和判据不能在运行时被模型擅自更改。

新架构不是重写所有平台设施。统一身份、数据访问、工具登记、权限审批、调用记录、计划调度与恢复等通用能力按主稿复用和完善；不为新财务专家另建运行器，也不为维持旧财务版本增加兼容分支。

## 二、先确定首版要解决的问题

以下是作者定范围时的讨论提纲，不是已经确认的首版能力清单。

| 需要确定 | 应明确的内容 |
| --- | --- |
| 目标问题 | 哪些财务分析和预测问题属于首版，哪些暂不承诺 |
| 适用范围 | 主体、期间、资料条件、指标或预测对象及排除范围 |
| 结果承诺 | 每类问题必须交付什么，哪些结果取决于数据和条件 |
| 做法依据 | 采用哪些分析与预测思路，判断和假设由谁提出、何时接受 |
| 数据与权限 | 实际需要的资料、来源、可用性、资源权限与外发限制 |
| 验收依据 | 数值、证据、预测评价和报告质量怎样独立核验 |
| 费用与停止 | 规划、取数、推理及验证的预算，缺项、失败和停止条件 |

“财务分析与预测”是产品名称，不自动承诺原 20 项全部能力。年度分析、人均创收、原季节性预测等旧内容可供评估，但不因旧版包含而自动进入新首版。选择哪些题及采用哪些算法，在专项孵化中明确。

## 三、工具方法先按需要提炼和孵化

从已确定的问题与结果承诺反推所需工具。原 20 个财务方法是工具提炼的素材来源，可以复用有权使用且已孵化的现成工具，也可以创作新的工具方法。

工具提炼只产出工具方法：固定职责、明确输入与返回、可验证且不调用其他方法。本文不预先给原 20 项分配类别、方法数量或实现入口，具体提炼另行开展。

按新契约补齐能力声明、所需权限、做法、校验、审批，由程序生成输入与返回两视图。公式、隔离脚本、用户沙箱中的模型指令及外部服务分别遵循主稿的载体和治理规则；财务投资判断不进入平台通用后端代码。

工具通过孵化后冻结精确版本。专家依赖这些可调用版本，不把未验证的候选名称、目录分组或旧 `fin_*` 名称当作已存在的工具。

## 四、用统一方法结构孵化专家

首版首先围绕工具方法组织做法，形成专家方法。若后续确实需要调用其他专家，则按主稿的允许依赖规则重新核定类别；本方案不为满足分类而人为加入专家依赖。

| 五要素 | 首版需要形成的定义 |
| --- | --- |
| 能力声明 | 用途、适用与排除范围、共同交付承诺和条件性交付 |
| 所需权限 | 可达需求、可信操作与资源范围；实际授权按调用层级收窄 |
| 做法 | 已孵化工具候选、必做与条件必做规则、选择依据、步骤依赖、输入及产物声明、导出映射 |
| 校验 | 计划合法性、工具结果和专家整体承诺的独立验收 |
| 审批 | 计划确认、数据与账号授权、具体动作审批及范围变化处理 |

专家输入与返回视图从定义生成。使用时依据问题和规则形成计划；只有一种合法计划时可由程序生成。每一步安排一次方法调用，步骤不嵌业务程序块。

计划、资料清单、账号绑定和费用上限在同一确认页呈现，分别留存依据。正常展开与纠错重排分开，恢复使用持久计划和调用记录。具体权限、确认、取消和未知副作用规则直接遵循主稿。

## 五、以新首版的声明验收

作者选择测试问题和数据，固定版本与授权，并独立给出预期、限制与判据。测试覆盖方法池和选择规则，证据记录实际计划；不要求模型复现原八步或旧版本固定顺序。

| 验证层次 | 要证明的内容 |
| --- | --- |
| 工具验证 | 输入、口径、算法或判断、结果依据及缺项处理符合已确认定义 |
| 机制验证 | 计划选择与约束、绑定、授权、审批、调用记录、导出、取消与恢复正确 |
| 真实模型验证 | 在实际模型与获准资料上，规划、证据判断及输出质量满足首版声明 |
| 专家整体验收 | 必须交付的成果齐全，条件结果说明明确，预算与停止规则有效 |

测试不让预期答案进入规划输入，不把模拟通过冒充真实模型效果。历史测试题可复用为素材，但须核对新定义下的预期；旧失败记录不被改写。

首版满足自身验收要求即可进入发布流程，不设“旧财务专家等价迁移通过”的额外门槛。

## 六、新身份与旧版本清理

新专家创建新的身份，从该身份的第一版开始。可继续使用“财务分析与预测专家”这一显示名称，但不得复用旧身份并把版本号重置，也不得把新内容覆盖到旧版本摘要之下。

旧财务专家全部版本的退出与新首版孵化分别推进。旧版不再作为保底产品等待新首版等价迁移；新首版未通过孵化期间，不把旧版或空壳冒充新专家提供。

| 清理对象 | 已定处理 |
| --- | --- |
| 旧专家定义、工作稿、发布版本与包 | 精确核定旧专家身份及归属后清理所有版本，不保留可运行旧版 |
| 市场条目、请入与安装引用 | 停止旧版获取和启动，清除可调用引用；不自动指向新专家 |
| 未结束委托与排队任务 | 纳入清理清单，按已有取消机制停止并核对在途副作用；不转换为新专家任务 |
| 历史成果、调用证据、费用与成交依据 | 保留可追溯记录和既有下载能力，不据此保留旧执行器或恢复运行入口 |
| 独立工具、共享能力与用户原始资料 | 不因清理专家版本级联删除；复用须重新核对资格和业务含义 |
| 旧专家专用代码、种子与夹具 | 核明专用部分及引用后移除；通用机制与仍有效的通用测试保留 |

运行记录需要的版本标识、摘要和必要证据应与可执行资产分离保存。保留历史证据不是旧格式执行兼容；不能借重试、恢复、旧安装或历史快照重新运行被清理版本。

静态代码核对发现，KnowLab 的 `knowbot_expert` 关联工作稿及测试，交付记录又引用专家；KnowMart 的 `knowbot_version` 引用专家主档，相关外键使用 `RESTRICT`。因此，保留历史证据与移除可执行资产须按实际引用设计清理顺序，不能假设删除主档会自动正确清理各端。本次只核对了模型定义，未取得线上对象清单。

实际清理须先形成精确身份、版本、引用和任务清单，按依赖顺序执行并记录前后数量。按名称模糊匹配或批量清空所有 expert 会话都不属于本次删除范围。当前尚未完成线上清单，也尚未执行版本删除。
