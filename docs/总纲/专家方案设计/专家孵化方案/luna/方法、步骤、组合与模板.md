# 方法、步骤、组合与模板

日期：2026-11-12。本文以“方法”为统一能力对象，整理其公共契约、步骤执行结构、组合与创作模板；承接原《原子方法和组合及模板》，保留财务方案的 C07 示例和 C01—C15 候选模板。文中字段是设计建议，尚未变更运行协议、正式方法资产或部署实现。

核心约定：**方法具有统一的六要素契约；专家也是方法。步骤是方法流程中的工作单元，不是方法，不要求具备方法的六要素。步骤的执行体可以组织一个或多个方法调用、程序块，以及两者的混合。**

输入分为两个层面：**方法输入是对外要求，步骤输入是内部执行所需的内容及来源映射。步骤可以直接使用方法输入，也可以使用前序产物、固定配置或其他明确来源；输入本身不规定为第一个步骤。**

[原20个财务方法的原子化提炼](原20个财务方法的原子化提炼.md)保留原 M01—M20 的提炼去向、候选契约和历史审查证据；该稿仍需按本文补齐六要素及步骤结构，不能视为已经通过新要求。本文也不因定义齐全而宣布候选方法已实现或可发布。

## 一、方法的统一结构

### 1.1 以方法为统一对象

**方法是具有独立用途、统一六要素契约和可调用实现的可复用能力。**候选稿按同一结构表达需求，补齐实现与验证后，作为工具注册到 tools 中心；不再以“原子方法”为整个体系的总称，也不额外建立一个同义工具对象要求每个方法关联一次。

| 概念 | 所处层面 | 职责与边界 |
| --- | --- | --- |
| 方法 | 能力对象 | 对外有用途、输入、交付及约束，对内有执行流程；具备独立身份、版本和调用契约 |
| 步骤 | 方法内部执行单元 | 安排有明确完成目标和执行边界的工作，不要求独立方法身份或六要素 |
| 程序块 | 具体实现内容 | 执行本方法内部定义的代码逻辑，随所属方法版本管理，不自动注册 |
| 组合 | 组织方式 | 编排步骤、方法调用和程序块；内部编排只有独立封装为完整能力后，才成为可注册的方法 |
| 专家 | 方法的业务身份 | 面向某类完整问题提供能力，是方法的一种使用形态；可以通过组合实现，也可以被另一方法调用 |
| 模板 | 方法定义的变量化表达 | 六要素中的固定内容、变量与变量约束；部分赋值形成更具体的模板，定义变量确定后形成具体方法定义 |

“组合方法”用于描述通过组合形成的方法，“专家”用于描述面向用户的业务身份，二者可以同时成立，不与“原子方法”组成三选一类型。方法结构、注册和调用不按这些称呼分成多套契约。

“原子”仅保留为相对的拆分描述：在当前业务设计中，这项能力无需再拆成多个独立复用的方法。它不表示只有一条语句、一个步骤或一次模型请求，也不禁止内部复用函数、程序块或其他能力。暂不设置强制 `atomic` 类型或永久层级；层级来自本次组合关系，使用“被调用方法”表达调用关系。

是否提炼为独立方法，依据独立用途、完整契约及独立调用和复用的需要。简单逻辑可以只是步骤内的程序块，复杂分析也可以封装为一个方法；不能凭代码长度或内部调用数量决定身份。CAGR 可以保留完整计算与证据交付，不必拆成相除、乘方、减一；一段专用结果拼接也不因具有输入输出就必须注册。

方法库与知识库在资产职责上并列：知识库提供事实、资料和证据，方法库提供处理问题的能力。方法执行时可以引用获准使用的知识。这种并列不要求新建两个独立服务；方法库负责定义与版本，tools 中心负责可调用注册项和绑定的解析。

原20个财务方法的“原子化提炼”仍用于描述该批内容的审查、拆分与复用边界，不再承担整个架构的类型划分。步骤和程序块不自动注册，步骤内部使用多个方法也不自动产生新方法；专家被另一方法调用时，身份和公共契约仍保持不变。

### 1.2 所有方法统一采用六要素

六要素借鉴[agent-team-argon 调研稿](../../参考资料/agent-team-argon.md)中 Skills 与 Routines 一节的作业指令结构，按所有者决定用于本项目所有方法。2026-11-12 按所有者进一步决定，第一项由“When to use”改为“能力声明”，它们是同一个要素，不并列维护两个对象。调研稿将方法与专家分为独立契约的判断不作为本方案约束，也不据此声称所有 Skill 标准均强制这些字段。

| 必备内容 | 建议字段 | 声明要求 |
| --- | --- | --- |
| 能力声明（Capability declaration） | `capability_declaration` | 能解决的问题与预期结果、适用范围与触发情境、影响选择的方法边界、不适用与不承诺、适用及不适用示例；用于用户和模型判断是否选择本方法，具体输入、交付和审批要求引用其余要素 |
| 所需输入与权限（Required inputs and access） | `required_inputs_and_access` | 面向调用者的输入 Schema、必需与可选内容、证据和来源要求、资源与操作范围、环境要求及缺项处理；权限要求结构见 1.6，用户连接与本次授权在运行时绑定；内部中间结果不自动成为对外必填输入，权限需求不等于已获授权 |
| 执行步骤序列（Sequence of work） | `sequence_of_work` | 按目标组织的执行流程，包括步骤、依赖、分支、选择规则和停止条件；步骤执行体可包含方法调用与程序块，不强制以输入准备开始 |
| 结果校验方式（How to validate） | `how_to_validate` | 检查项、检查方式、通过标准、证据和失败处理；明确程序校验、模型评估或人工判断的责任 |
| 返回产物格式（What to return） | `what_to_return` | 输出 Schema、成果引用或文件格式、证据与校验结果，以及部分完成、缺项、不适用等结果的表达 |
| 何处必须审批（What requires approval） | `what_requires_approval` | 需要审批的动作、触发条件、审批人角色、批准范围、已有批准的适用条件及等待或拒绝后的行为；没有方法自身额外审批时显式声明 `mode: none` |

六项都必须有明确内容，不能用名称、模糊正文或模型自行推断代替。可采用结构化对象、说明文字与钉版引用共同表达；宿主需要执行检查的输入格式、依赖和审批条件须有可解析表示。

所有方法按自身职责填写相同六要素。计算方法可以说明算法与证据处理，采用组合的方法说明内部组织关系，作为专家使用的方法说明整个问题的完成与交付。六要素不因内部复杂度或业务身份而改变；步骤不填写另一套六要素。

六要素相互约束：每个必需输入有来源或缺项处理，每个承诺产物有生成步骤，每项交付要求有对应验收。被调用方法全部成功，不代表调用方已经完成整体目标；本级仍须检查范围覆盖、结果相容性与交付完整性。

### 1.3 方法输入对外，步骤输入对内

方法输入描述调用这个方法时，对调用者提供或绑定的内容有什么要求。调用者可以是用户所在的宿主程序，也可以是另一方法的执行流程；输入可以是问题、参数、数据或资源引用。它属于方法的对外契约，不是流程中的执行动作。

步骤输入描述本方法内部某一步执行时需要使用什么，以及这些内容从哪里取得。每个步骤按自身工作需要声明输入映射，不要求把全部方法输入传给每一步，也不要求用户逐步重新填写。

| 内容 | 含义 |
| --- | --- |
| 方法的输入声明 | 六要素中的 `required_inputs_and_access`，定义面向调用者的输入要求 |
| 步骤的输入映射 | 流程内部的 `input_bindings`，把不同来源的值或引用接入本步骤 |
| 输入处理步骤 | 存在实际取数、提取、转换、整理或补充工作时设置的步骤；按依赖安排位置，并非必备的第一步 |

步骤输入可以有多种来源，必须能按定义取得并追溯：

| 来源 | 示例与约束 |
| --- | --- |
| 方法输入 | 分析期间、调用者提供的期初期末值或资料引用；步骤可以直接引用所需字段 |
| 已完成步骤的产物 | 取数步骤得到的年度序列、分析步骤形成的结果；须声明数据或质量依赖 |
| 固定配置与常量 | 方法版本中已定的窗口、算法选项；与本次传入的业务事实分开 |
| 授权资源取得的结果 | 已授权资料、服务或文件中的内容；通过明确的获取动作取得并记录来源，不能用映射暗中执行取数 |
| 执行中补充或绑定的内容 | 缺项时补充的数据、分支确定后绑定的资源；按规则等待并记录新增输入版本 |

步骤内部的方法调用与程序块还可以使用本步骤输入和已完成内部动作的结果。调用另一方法时，将当前可用内容映射到被调用方法的对外输入；进入该方法后，再由它自己的步骤完成内部映射。对外与对内是相对于当前方法而言的，不是两份需要用户重复提供的数据。

例如一个计算步骤可以直接从方法输入取得期初值和期末值，从固定配置取得单位规则，从前序步骤取得已核对的年间隔。参数已符合要求时，不为“统一结构”再造输入准备步骤。方法边界仍须执行参数和权限检查，这些检查不必各自成为显式业务步骤。

只有确实存在数据处理工作时，才按流程设置相关步骤或内部程序块。例如读取财报可以在某个财务模板的开头，补充特定指标可以发生在分析分支确定之后。内部能够产生的中间结果不一律要求调用者预先提供；缺项处理和来源范围须在契约中说明，不能从其他任务的对话上下文中无记录地猜出依赖。

### 1.4 调用来源、实现与 MCP、Skill

| 维度 | 回答的问题 | 表达方式 |
| --- | --- | --- |
| 调用来源 | 谁决定发起本次方法调用 | 宿主业务程序；模型提出工具调用请求后由宿主处理 |
| 执行实现 | 程序怎样完成方法 | 函数、命令行程序、脚本，或组织步骤的流程实现；需要推理时由宿主组织模型交互 |
| 接入方式 | 宿主怎样找到并访问实现 | 直接绑定函数、进程、HTTP 接口或现有流程入口；通过 MCP 注册调用代理 |
| 面向模型的呈现 | 模型怎样了解并使用能力 | 直接工具描述、MCP 工具描述、按需加载的 Skill 作业指令；这些形态可以配合使用 |

同一个方法可以允许宿主和模型两种调用来源，不能因此复制为两份方法。**模型提出请求，程序执行工具**；宿主直接发起的调用同样经过参数、版本和权限检查。

脚本是实现载体，命令行是启动方式。例如 `python cagr.py` 通过进程执行 Python 脚本；函数、脚本和命令行也都可以由 MCP 服务封装。MCP 工具的内部实现不一定对调用方公开，不要求调用方猜测其服务端使用什么语言或脚本。

MCP 提供工具发现与调用协议，Skill 承载作业指令及相关资源，两者不是互斥的调用协议。宿主加载 Skill 后，模型可以按指令提出工具请求，再由宿主经 MCP 或直接绑定执行；普通工具也可以不经过 Skill。Skill 的说明需要补齐本方案的六要素并接入执行与验收，才能作为完整方法使用。参考 [MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)与 [Agent Skills 说明](https://agentskills.io/home)。

程序自定义块指方法定义中已有明确边界和实现依据的代码逻辑，不因名字中有“自定义”就允许模型临时生成并执行任意代码。需要运行时生成代码的能力，应另有明确授权、执行约束和验证规则。

### 1.5 统一注册契约与执行绑定

各级方法采用同一公共结构；身份、六要素和执行绑定不混为一段提示词。字段拼写与存储形式尚需映射现有契约，不直接宣布新协议已经生效。

| 部分 | 建议字段 | 职责 |
| --- | --- | --- |
| 身份与管理 | `id`、`version`、`digest`、`name`、`description`、所有者与发布状态 | 标识能力、版本及生命周期 |
| 业务契约 | 1.2 的六项必备字段 | 声明用途、输入、流程、校验、产物和审批 |
| 调用范围 | `allowed_callers` | 允许 `host`、`model` 或两者，不替代用户与资源授权 |
| 执行绑定 | `binding_id`、`method_ref`、`kind` | 精确方法版本与 `direct` 或 `mcp` 接入方式 |
| 直接绑定配置 | `handler.kind` 及类型配置 | `function`、`http`、`process` 或 `composition`，后者指现有流程执行入口 |
| MCP 绑定配置 | `server_ref`、`remote_tool_name`、参数与结果映射 | 远端工具的可调用代理 |
| 实现与环境 | `implementation_ref`、`environment_requirements` | 代码或流程的冻结版本、依赖、工作目录要求及所需资源角色；具体用户连接与凭据在运行时绑定，不进入方法发布定义 |

组合流程位于方法的 `sequence_of_work`；执行绑定引用这份冻结定义和相应执行器，不另存一份可独立修改的流程。远端 MCP 方法也可以是组合方法，组合与否不属于接入方式。

```text
直接登记契约和执行绑定 ───────────┐
                                ↓
MCP tools/list → 核对契约 → tools 中心的可调用注册项
                                ↓
宿主直接发起 ───────────────→ 解析版本、权限与绑定
模型提出工具请求 → 宿主处理 ───────┘
                                ↓
                 执行实现或流程 → 结果、证据与验收
```

`tools/list` 用于发现工具，`tools/call` 用于请求 MCP 服务执行。目录条目只有技术描述时，还需补齐六要素、映射并验证业务契约，不能凭工具名字相同认定实现等价。模型端工具别名须准确映射回注册标识与绑定，避免重名。

tools 中心的注册项表示某个方法版本的可调用能力；一次运行另有 `call_id`，记录实际 `origin`、方法版本、绑定、输入输出引用和验收结果。流程中的调用还要记录所属步骤及内部动作，不能把注册项、步骤和调用记录混为同一个实例。

### 1.6 权限要求、审批与运行授权

本节为 2026-11-12 方案稿，明确方法结构；连接器、凭据、授权记录和执行检查的实现设计统一见[连接器方案第十节](../../../连接器方案.md#十权限与连接器实现方案2026-11-12-讨论稿)。本次只写方案，不表示字段已进入运行协议。

#### 1.6.1 权限要求与审批各负责什么

`required_inputs_and_access` 说明执行需要访问什么资源、进行什么操作及允许的范围；`what_requires_approval` 说明哪些动作必须取得怎样的批准后才能执行。用户已经接好服务，不表示任何任务都可以使用；第三方令牌允许发送，也不表示用户批准了某次发送。

| 内容 | 定义位置 | 示例 |
| --- | --- | --- |
| 所需访问能力 | `required_inputs_and_access.access_requirements` | 读取选定邮箱文件夹的邮件；发送本方法产出的报告 |
| 动作审批规则 | `what_requires_approval.rules` | 发出前展示发件账号、全部收件人、正文与附件，核本次批准 |
| 实际连接和资源 | 本次运行绑定 | 用户选的邮箱连接、具体文件夹和收件人，而不是作者的账号 |
| 授权及批准事实 | 运行授权与现有审批记录 | 谁在何时允许这件任务读取哪些邮件、批准了哪份待发送内容 |

能力声明向使用者解释这些条件，引用上述规则；不另存一套授权条件。方法定义不保存具体用户的密钥、连接身份或批准结果。可公开的服务类别与必要权限随能力声明展示，私有执行内容仍按原边界管理。

#### 1.6.2 权限要求的建议字段

`required_inputs_and_access` 保留输入 Schema、来源和环境说明，在其中增加 `access_requirements[]`。它是第二要素内部的结构，不是第七要素。仅做纯计算的方法显式填写空列表，并说明运行环境；不能从空列表推导任意外部访问权。

| 字段 | 含义与约束 |
| --- | --- |
| `requirement_id` | 本方法版本内稳定编号，供步骤、审批及运行绑定引用；不是授权令牌 |
| `resource_kind` | 资源责任域，例如 `connector`、`knowbase`、`local_workspace`、`external_agent`；与函数、脚本、MCP 等实现或接入方式分开 |
| `resource_role` | 本方法内的用途名称，如 `source_mailbox`、`report_destination`，供运行时绑定具体资源 |
| `capability_ref` | 所需操作契约及版本，例如邮件读取契约；兼容连接器按已验证契约匹配，不能只因都叫“邮箱”就互换；确需指定供应商时显式限制 |
| `operations` | 明确允许请求的操作，如搜索、读取、创建草稿、发送；由适配定义映射到具体工具及外部 scope，不由模型猜测 |
| `resource_constraints` | 文件夹、目录、数据版本、期间、收件范围等条件；动态值引用已确认的方法输入或已验收步骤产物，执行时解析后再核授权 |
| `required_when` | 总是必需或仅特定分支必需；分支依赖和条件须可解析，不能靠模型临时把必需动作改为可选 |
| `data_transfer` | 是否外发、发往哪个资源角色、哪些输入或产物、用途；无外发显式说明，不能把远端查询隐含的数据传递略去 |
| `on_unavailable` | 缺连接、缺授权、资源不可用时的处理；必需项等待、失败或变更，只有预先定义的可选项才可跳过并记录未完成 |

范围表达采用有类型的资源选择条件，不允许任意代码作为授权谓词。值来自模型提议时，仍须按资源权限和用户确认范围验证。创建资源时可以约束父目录、目标空间及名称；发送时约束收件人和具体内容，不要求所有操作都先有资源 ID。

#### 1.6.3 审批字段与绑定

`what_requires_approval` 保留 `mode: none` 或规则集合。每条规则建议有 `rule_id`、`requirement_refs`、`operations`、`condition`、`approver_role`、`approval_scope`、`preview_fields`、`on_reject` 和 `on_timeout`。按次动作批准与已有任务范围批准须明确区分；不支持的条件或缺失字段不能默认为放行。

例如“整理邮件并发送报告”：读取要求绑定指定邮箱、文件夹和期间；发送要求绑定发件连接与获准收件范围。发送审批引用发送要求，预览全部收件人、正文和附件版本。阅读权限不推导发送权限；批准后更换账号、增加抄送或修改附件内容，必须重新核对批准是否覆盖。

运行时由宿主把 `requirement_id` 绑定到用户连接、knowbase 运行授权或本地执行目录等具体资源，并关联本次授权依据。原始凭据只由对应执行端按权限使用，不作为方法输入或步骤产物传递。步骤及内部动作可以引用所需的权限要求编号，但不因此成为独立方法，也不新增一套六要素。

#### 1.6.4 组合、检查与验收

注册不等于允许使用，展示给模型也不等于已经授权。实际可用范围由方法声明、任务授权、用户资源权限和当前环境共同限制；程序块同样受这些限制，不能成为绕过工具检查的路径。

组合方法需声明其可达分支对外需要的权限，并核对被调用方法的要求是否有对应来源。创作时检查覆盖，运行时仅绑定实际分支所需范围；不把所有子方法的权限直接并成用户必须一次授予的范围。子调用取得父调用已获准范围内的必要子集，不能因为子方法声明更宽就扩权；多个子方法共享同一连接也不共享所有操作权限。

权限约束同时适用于宿主直接调用、模型请求调用和程序块。连接器操作统一经 knowbench 的授权入口；纯计算块不需要连接器。已有直接 HTTP、脚本或命令行如果绕过此入口使用第三方凭据，在改为受控执行并验证前不得视为满足本方案。knowbase 继续裁决数据使用权，link 继续检查本地目录、网络与执行上限，工作台不能代替它们放宽限制。

`what_requires_approval` 必填不等于每次运行必须审批。`mode: none` 只表示方法没有额外审批要求，不能覆盖平台或被调用方法的必要审批。宿主检查已有批准是否仍覆盖动作、对象和范围；满足时继续执行，不因进入另一方法或步骤重复请求。范围扩大或批准失效时按规则等待，模型不能自行批准。

允许某工具被调用，不代表必做动作已经执行。固定算法、必要检查和证据要求必须在流程及验收中落实。HTTP 成功、进程退出码为零或收到 MCP 结果，只能证明技术执行状态，不能替代业务验收。正确产出“不适用”可以是有效业务结果，不能与技术失败混淆。

运行记录保留精确版本与证据。目录刷新不能无记录地替换正在运行的实现；MCP 目录快照也不能证明远端代码被冻结，缺少版本依据时应如实说明可复现范围。

### 1.7 能力声明就是六要素的第一项

**能力声明替代原第一项 `when_to_use`，建议字段为 `capability_declaration`。它直接定义作者承诺的方法用途与适用边界，不是六要素之外的第七项，也不是从完成后的方法契约另行推导的声明对象。**作者可以先写能力声明，再设计实现；也可以依据已有实现整理后确认。两种创作顺序都须核对承诺与实现是否一致。

能力声明回答“什么问题可以选择这个方法，预期得到什么结果，什么情形不应选择”。其内容统一如下，作为专家使用的方法也采用相同结构：

| 内容 | 声明要求 |
| --- | --- |
| 目标与结果 | 说明解决什么问题、产生什么直接结果；用动作、对象和结果表达，避免“全面分析”等无限承诺 |
| 适用范围与情境 | 明确对象、期间、口径、触发条件等影响选择的边界；只列与该方法相关的维度，前提引用输入与权限要求 |
| 方法与方法边界 | 说明影响选择的做法概要、固定内容和允许调整的范围；不在此重复完整步骤、程序块或私有正文 |
| 不适用与不承诺 | 明确排除的任务、方法、对象、结果和局限；未声明的能力不能默认存在 |
| 适用与不适用示例 | 用典型问题及近似反例解释边界，必要时说明需澄清的情形；示例不是测试通过记录 |

“预期结果”表达业务承诺，“返回产物”规定具体交付要求。例如前者声明“预测未来两个季度的收入并提供区间”，后者明确返回哪些期间、点值、上下界、单位、证据和文件格式。二者必须一致，但不重复维护完整输出 Schema。

原[能力声明规范（§10.1）](../../参考资料/动态专家实施方案.md)的八栏按六要素重新归位：目标、适用范围、方法边界、排除项及示例由本项定义；详细数据与权限前提归入 `required_inputs_and_access`，交付内容与格式归入 `what_to_return`，校验归入 `how_to_validate`，授权条件归入 `what_requires_approval`。条件不足时的具体处理在相关要素中定义，并由 `sequence_of_work` 落实；能力声明引用这些规则，不再另写一份。

一个方法可以在同一能力声明中列出多个具名能力项，各项明确适用条件、预期结果及所引用的要求。能力项编号用于引用和追溯，不是步骤编号，也不自动成为独立方法注册项。详细输入或交付因能力项而异时，须有明确对应关系，不能把不同条件混为无条件承诺。

组合后的能力由作者明确声明，必须反映本方法整体能够完成的工作，不能直接合并被调用方法的能力清单；内部调用 CAGR 不自动表示该专家接受所有独立 CAGR 请求。输入及权限等前提仍须在本次调用中检查，匹配结果不是保证完成的证明。

面向用户的能力卡、简介和模型选择材料，展示同一声明及所引用的必要条件；它们是展示形式，不另建可独立修改的承诺。公开展示不下发完整内部流程、私有代码或秘密。声明经作者确认随方法版本发布，边界改变形成新版本；测试结论与发布批准单独记录，不作为声明字段，也不以先有测试记录为填写声明的前提。

本节定义目标结构；既有表单、协议、市场声明和正式资产仍须实施兼容迁移，不能把字段建议或文档修订视为代码已经完成。

## 二、步骤与组合

### 2.1 步骤的定义与最小结构

**步骤是方法执行流程中具有明确完成目标和执行边界的工作单元，其执行体可以组织方法调用与程序块。步骤不自动具有独立方法身份，也不要求满足方法的六要素契约。**

方法回答“这项能力解决什么问题、承诺什么”，步骤回答“本流程中这一段工作何时执行、使用什么、成果交给谁”。同一方法可以在不同步骤中以不同参数被调用，一个步骤也可以包含多个方法调用。

| 步骤建议字段 | 职责 |
| --- | --- |
| `step_id`、`goal` | 标识本方法内的步骤及其完成目标，不赋予独立发布身份 |
| `input_bindings` | 本步骤所需内容从方法输入、先前成果、固定配置、已取得的授权资源结果或明确补充来源中的何处取得 |
| `dependencies`、`run_condition` | 数据和质量依赖、执行条件；区分必做、条件必做和可选 |
| `body` | 有明确结构的执行体：方法调用、程序块或混合编排 |
| `output_bindings` | 将内部结果映射为该步骤对后续流程可用的成果 |
| `failure_policy`、`recovery_policy` | 缺项、错误、中断后的等待、停止、重试或恢复方式 |

这些字段服务于调度和执行记录，不要求步骤另有独立适用范围、六要素或 tools 注册项。完成条件与校验、审批点引用所属方法的声明及被调用方法的契约；只在确有步骤特有要求时补充，不复制整套方法契约。

步骤定义与运行记录分开。每次执行记录步骤实例、所用输入版本、内部动作结果和最终状态，以便恢复与追溯；逻辑步骤不必机械对应一个 Task、Attempt 或模型轮次。

### 2.2 步骤执行体：方法调用、程序块及其组合

步骤的执行体允许以下结构：

| 结构 | 示例 |
| --- | --- |
| 调用一个方法 | 调用某个已钉版的 CAGR 方法 |
| 编排多个方法 | 分别计算收入 CAGR 和利润 CAGR，再等待两个结果 |
| 执行程序块 | 整理字段、检查格式、选择分支、拼接已有成果 |
| 方法调用与程序块混合 | 程序块提取两组输入 → 两次 CAGR 调用 → 程序块合并结果 |

内部以 `method_call` 和 `program_block` 两种动作表达执行内容；动作可以按顺序、依赖和条件编排，不要求步骤二选一，也不把一次方法调用等同于一个完整步骤。

- 方法调用动作声明局部 `action_id`、精确 `method_ref`、输入映射及结果引用；同一方法可以有多次参数不同的调用。
- 程序块动作声明局部 `action_id`、冻结的代码或实现引用、输入输出及执行环境。程序块随所属方法版本管理，不要求独立六要素，也不自动注册为工具。
- 多动作执行体须明确动作之间的数据依赖、分支和完成条件。内部执行顺序不能只藏在一段含糊指令里；允许模型作选择时，必须声明候选范围与约束，并记录实际决定。

方法调用边界按被调用方法契约检查输入并取得结果；程序块没有独立方法契约，其正确性由所属方法的规则、步骤完成条件与实现测试负责。方法的权限、审批、预算和运行环境限制对两类动作都生效。

程序块需要跨方法复用时，可以提炼成独立方法：为其补齐六要素、版本和执行绑定后注册。这个提炼动作是设计选择，不因代码长度或被使用次数自动发生。

### 2.3 流程内组合与组合方法

流程内组合是对步骤、方法调用和程序块的组织。它本身可以只是某个方法的内部实现。只有为它赋予独立用途与对外契约，补齐六要素并通过实现验证，才成为可注册的组合方法；专家属于这种方法。

```text
方法〔统一六要素；可通过组合实现，可作为专家使用〕
└─ sequence_of_work
   ├─ 分析步骤：直接接收所需方法输入，调用方法 A ＋ 程序块
   ├─ 后续步骤：组合前序产物、方法输入和配置，调用方法 B
   ├─ 校验步骤：程序块或校验方法
   └─ 交付步骤：组织产物

分析步骤中的方法 A
└─ 自己的六要素与执行流程
```

因此，步骤的组合不自动等于方法资产的组合发布。一个步骤内部调用了两位专家，也不意味着该步骤必须注册为第三位专家。

方法的流程建议保存 `steps`、数据及质量依赖、条件选择规则和最终结果映射。步骤里的方法引用放在 `body` 的调用动作上，不给所有步骤强加一个必填的 `method_ref`。同一条依赖和映射只保留一个真源，其他图表或摘要从中派生。

固定流程与动态选择共用现有执行体系。模型可在声明的范围内提出方法选择、参数与有限计划，宿主校验后执行；不能临时改公式、放宽验收或扩大权限。必做步骤和动作必须有执行证据，未选分支如实记为未执行。

嵌套方法引用须钉版、可检查并防止无界递归；显式循环必须有停止条件和次数或资源上限，不能用循环依赖代替迭代定义。并行执行以依赖、资源和当前运行策略允许为前提，文档支持表达并行不等于现有环境已经启用。

步骤数、方法调用次数、程序块数量与模型轮次是不同的计数。输入检查、计算和拼接可以由程序连续完成，不必为每个动作开启一轮对话；需要模型推理的环节才按执行机制组织模型交互。

### 2.4 输入、校验、审批与恢复怎样贯穿步骤

方法输入是对外契约，步骤输入通过内部映射取得；具体来源见 1.3。步骤可以直接使用方法输入，也可以组合不同来源，不必经过一个统一的输入准备步骤。步骤内部的调用还要映射到被调用方法的对外输入契约。传递的是结构化值或带版本和证据的成果引用，不以“方法正文加此前全部对话”替代输入约定。

输入的技术格式校验发生在相关访问或执行前；业务完整性、适用域等检查按方法规则落实到相应步骤或实现中。缺少某项可补充数据，可以按声明进入等待；不合法调用或无权访问不会因为设置了后续数据准备步骤而被放行。输入、校验、交付都有约定，但不要求每一项独占一个步骤。

| 情况 | 必须明确的处理 |
| --- | --- |
| 输入缺失 | 拒绝、请求补充并等待，或按已定规则完成允许的部分 |
| 被调用方法返回不适用 | 作为业务结果处理，由调用方决定停止、选分支或披露局限 |
| 方法调用或程序块技术失败 | 哪些错误可重试、次数与退避、超限后的去向 |
| 校验未通过 | 阻止交付、受限返工或上报；不能为了通过临时改阈值 |
| 需要审批 | 在相关动作产生影响之前等待；有效批准到位后从相应位置继续 |
| 中断且副作用结果不明 | 先核对实际结果，再决定恢复或补偿，不能直接重放整个步骤 |

审批绑定具体动作、对象和范围，可在步骤中设置执行前检查点，但规则来自方法契约及任务授权。调用方不能用“无额外审批”抹掉被调用方法的限制；程序块发出的对外动作同样执行检查。

步骤可以包含多个动作，所以恢复必须能识别哪些动作已完成。输入或方法版本变化时，应按依赖关系使受影响结果失效并重新执行；有效结果可以在规则允许时复用，不能混用不同版本的成果。幂等键、请求标识和恢复记录按已有运行机制实现，不新增独立的步骤账本服务。

方法级验收检查整体交付；步骤完成条件检查本段工作；被调用方法按自己的契约验收。三者可以复用检查结果，但不能把“内部动作都执行过”当成“问题已经解决”。执行记录沿用现有 Task/Attempt、输入版本、成果和验收机制，实施时核对缺口，不声称当前代码已经支持全部结构。

### 2.5 示例：一个步骤同时调用方法并执行程序块

以下仅演示结构，不新增财务算法、业务阈值或已发布方法版本。以已确定分析范围中的收入和利润增长为例，方法输入约定允许传入相容的年度数据，或绑定可供获取这些数据的授权资料引用：

| 步骤 | 输入来源 | 执行体 | 步骤产物 |
| --- | --- | --- | --- |
| 数据获取与整理（按需） | 方法输入中的资料引用、分析期间 | 需要时调用已授权的取数或核验方法，并由程序块整理；已经提供相容数据则不执行该步骤 | 相容的年度数据及证据 |
| 增长分析 | 方法输入中的分析期间；年度数据和证据来自方法输入，或来自已执行的数据整理步骤，按声明条件选择 | 程序块提取两组期初期末值 → 分别调用已钉版 CAGR → 程序块合并结果 | 两项增长结果及证据，或各自不适用说明 |
| 结果校验 | 增长步骤产物、方法输入中的分析范围及实际采用的证据 | 执行程序校验或调用校验方法，检查适用域、期间、指标覆盖与来源 | 校验结论及问题清单 |
| 成果交付 | 已通过校验的结果与约定的局限信息 | 程序块或已定义的报告方法组织产物 | 符合本方法返回约定的分析成果 |

增长分析步骤内部示意：

```text
prepare_values〔程序块〕
   ├─ revenue_growth〔调用 CAGR 的确定版本〕
   └─ profit_growth〔调用同一 CAGR 版本，使用另一组输入〕
                ↓ 两个调用均有明确结果后
merge_results〔程序块〕
```

这里有一个增长分析步骤、两次 CAGR 调用和两个程序块，不是四个新方法。CAGR 仍保留完整六要素；步骤只维护自己的目标、输入输出映射、执行体及失败恢复规则。如果以后要将这一整段增长分析独立复用，再封装为具有完整六要素的组合方法。

### 2.6 C07：原季节性预测与回测的组合实例

以下内容从原文的 C07 详细示例迁入，保留原算法、窗口、依赖与验收约束；编号含义见[原子化提炼稿](原20个财务方法的原子化提炼.md)。

1. 作者先接受预测公式、允许的指标、4/8季窗口、回测范围及数据质量规则，形成组合的固定语义。

3. 原始累计数据先经A03产生单季，已有可信单季则不重复差分；A04构造相容的同比序列。
4. P02在四个历史起点分别调用已钉版的P01逻辑，所有起点禁止读取当时不可得的输入。P02是对指定预测方法的受限回测，不是允许运行模型传入任意新算法。
5. P01对本题目标季度计算点值与上下界。保留原作者方法：上年同季乘以一加近4季同比中位数；上下界使用近8季同比最小／最大值。回测合格与否、能否继续，服从作者明确规则，不由模型临时降门槛。
6. 最终成果按“指标×目标期×点值/上下界”和“指标×回测期×预测/实际”验覆盖；缺哪一格就说明哪一格，不能把有个horizon=2当作交齐。

上述第 1 项是创作时接受业务规则，并不表示每次运行都重新审批。此例的对外输入包括目标季度、允许的指标及授权数据引用；窗口推导和取数整理是这个具体流程的实际工作，可以安排在开头，并非所有方法都要有同样的首步。其余内容可按步骤组织如下，步骤划分不改变原算法：

| 步骤 | 执行体与边界 |
| --- | --- |
| 窗口推导与数据整理 | 使用方法输入中的目标季度、指标和授权数据引用；程序块反推预测及各回测起点所需窗口，检查缺项并整理数据 |
| 季度序列准备 | 按需调用 A03，调用 A04，配合程序块组织期间和证据；相容的可信单季不重复差分 |
| 历史回测 | 调用 P02，按原定义使用已钉版 P01 逻辑；程序块整理各历史起点的独立输入及结果 |
| 目标期预测 | 满足作者已定的继续条件后调用 P01，程序块组织目标期输入与结果 |
| 核验与交付 | 按作者声明的位置安排必需 Q 检查，质量检查不能拖到受其约束的动作之后；最终检查指标、期间、点值和上下界覆盖并组织交付 |

P01/P02 的复用可以通过明确的方法调用或共享确定性实现完成；采用哪一种须在实现与记录中写清，不能把内部函数调用伪记为一次注册方法调用。此例不要求为窗口整理、结果合并等程序块单独建立方法资产。

## 三、方法模板

### 3.1 模板的定义与边界

**方法模板是方法六要素的变量化表达：方法模板＝六要素中的固定内容＋变量＋变量约束。**给部分变量赋值，可以得到更具体的下级模板；定义变量全部确定、约束满足且六要素完整时，形成具体方法定义。模板服务于创作，但“创作样板”只是用途，固定内容、变量及约束才是它的结构。

本定义及逐级具体化方向由所有者确认；以下字段、派生规则和验证方式为 2026-11-12 的细化设计建议，尚未实施。可用逻辑表达 `T = (D, V, C)`：`D` 是带有明确变量引用的六要素定义，字面内容为固定部分；`V` 是定义变量集合；`C` 是变量及跨要素约束。模板身份、来源、版本及模板自身的访问与复用权限是管理信息，不改变这三个部分的含义；方法执行所需权限仍属于六要素。

| 概念 | 回答的问题 | 内容与使用阶段 |
| --- | --- | --- |
| 方法通用结构 | 所有方法都应怎样描述 | 六要素、步骤与执行体、输入映射、权限等共同规则及 Schema；约束创作、发布与调用 |
| 方法模板 | 哪些定义已经确定，哪些仍可选择 | 六要素的固定部分、定义变量及约束；赋值后可得到下级模板或具体方法定义 |
| 方法定义 | 这个具体方法承诺什么、怎样实现 | 作者填写的六要素和执行定义；工作稿可未完成，发布时须完整并钉版 |
| 本次运行 | 这个方法这次处理什么 | 在确定的方法版本上绑定业务输入、资源与授权，按定义执行并交付结果 |

方法通用结构规定字段与合法表达。把六要素中待确定的内容显式声明为变量及约束，才形成模板；仅有几个空标题或任意“待补”文字，不能据此生成完整方法。可以有很抽象的上层模板，也可以有已固定大量内容的领域模板，均遵循同一方法结构。

模板可以覆盖简单计算、复合分析或完整专家。专家也是方法，不需要另一套专家模板格式；步骤内部的局部组合只是可以被模板预置的内容，不因此成为独立方法。模板可以引用已发布方法的精确版本，也可以保留明确的候选引用；候选引用未完成前，生成的工作稿不能标为可运行。

模板具有自己的来源与版本。未闭合的模板不能作为承诺完整业务结果的方法直接注册；若将来需要工具辅助生成方法，可另定义具有完整六要素的“生成方法”能力，不能把模板对象和生成工具混为一体。本方案不因此新增生成工具或运行引擎。已有方法可以经来源与复用权限核对后，把部分固定内容重新抽象为变量来提炼模板；这是抽象过程，不是沿原模板向下具体化，也不自动继承原方法的验证结论。模板不携带某次运行的私人数据、用户连接、凭据或批准事实。

#### 3.1.1 固定内容、变量、默认值与约束

| 内容 | 定义 | 在逐级具体化中的行为 |
| --- | --- | --- |
| 固定内容 | 在当前模板版本中已经确定的定义 | 下级沿用；要改变已固定内容，另行修订或分叉，不冒充该版本的合法具体化 |
| 变量 | 有稳定标识、类型和作用位置，尚待确定的定义内容 | 可部分赋值；同一变量在多处被引用时，赋值一致作用于所有引用 |
| 默认值 | 给变量提供的建议选择 | 未被明确采用前仍是变量；采用后形成有记录的赋值，不能悄悄成为固定业务规则 |
| 变量约束 | 类型、允许范围、依赖和跨要素一致性要求 | 每次赋值都检查；下级可收窄但不能放宽上级约束，冲突不得静默覆盖 |

变量可以表示文字、数值、枚举，也可以表示输入 Schema、方法引用、程序块引用、步骤执行体、步骤集合及其映射等结构。结构变量必须有类型和边界，程序块赋值引用有版本的实现或待审稿，不等于允许模型任意生成并执行代码。操作、审批和数据外发相关变量仍受 1.6 的权限边界约束，不能通过赋值消除平台及资源端限制。

六要素都可以变量化，但并非全部都要留空。固定内容与变量应在同一份六要素定义中明确区分，不用一段自由提示词让模型猜哪些可改。

| 六要素 | 可变量化内容示例 | 必须联动检查的内容 |
| --- | --- | --- |
| 能力声明 | 目标、对象、适用范围和业务结果 | 实际输入、步骤与产物是否支持承诺，排除项是否仍成立 |
| 输入与权限 | 输入结构、来源要求、资源角色和操作范围 | 内部映射、被调用方法要求、外发范围与审批 |
| 执行步骤 | 方法引用、程序块、步骤集合、依赖及分支规则 | 输入输出兼容、依赖完整、必需检查和停止条件 |
| 结果校验 | 检查方式、阈值和证据要求 | 产物是否可检查，验收标准是否符合已承诺目标 |
| 返回产物 | 内容、Schema、格式及证据组织 | 生成路径、输入来源、校验与交付覆盖 |
| 审批要求 | 动作、触发条件、预览内容和批准范围 | 所需权限、实际副作用及上级不可放宽的限制 |

#### 3.1.2 分级是逐步收窄选择空间

下级模板由父模板的精确版本派生：保留固定内容和已有约束，增加部分赋值或收窄未定变量的范围，得到剩余变量及约束。一次可以赋值一个或多个变量，不规定必须逐层填完某个要素。上级可派生多个不同分支，模板层级不限于“通用—行业—专家”三层。

判断下级是否更具体，要看它允许形成的方法定义是否仍在上级允许范围内。如果把所有符合一个模板的完整方法定义称为“合法补全集合”，则合法下级的该集合应是上级的非空子集；真正增加确定性的派生会进一步缩小这个集合。变量改名、换显示顺序或只复制模板不构成更具体的一层。这是设计上的判定标准，不声称系统能自动证明任意程序和自然语言约束。

**变量个数只是辅助信息，不能作为等级尺。**例如上层有一个“数据获取执行体”结构变量，选为邮件获取流程后，可能展开文件夹选择规则、分页上限等几个子变量；变量数增加了，但获取方式已经被限定，定义更具体。展开规则须来自父模板允许的结构或已选引用，不能趁展开新增上级不允许的行为。普通标量赋值时，则表现为固定内容增加、未定变量减少。

约束收窄也能构成具体化，例如把报告格式从多个允许值收窄为其中两种，虽然尚未唯一赋值，选择空间已缩小。不保证所有模板都能横向比较；共享父模板的两个分支可以各有侧重，不必强排谁更高级。

模板派生和方法组合是两种关系：派生回答“定义怎样逐步确定”，组合回答“运行时调用哪些方法、执行哪些程序块”。下级模板不因为派生自上级，就在运行时调用上级模板；模板树深度也不等于步骤层数或方法调用深度。

#### 3.1.3 赋值、依赖与派生规则

1. **明示赋值**：每次赋值记录变量标识、值或精确引用、来源及作者采用记录。AI 可以提出候选，不能以默认值存在为由宣称作者已确认业务规则。
2. **类型与关系检查**：先检查值的类型和范围，再检查已知的跨变量、跨六要素约束。缺少关联值时记录尚不能判断的约束，不能把“待判断”当作通过。
3. **确定推导**：允许用明确规则从已赋值内容推导其他定义，推导项保留依据且不可独立改写。例如选定某个方法后，引入其已声明的输入要求，再明确映射或补充来源；不能推导出用户已经授权。
4. **结构展开**：选定结构变量后，为展开的步骤、内部动作和子变量保留稳定且不冲突的标识，核对输入映射、权限和依赖。多处使用同一模板时默认具有独立变量作用域，需要共用的变量显式映射。
5. **冲突处理**：不兼容的赋值指出具体变量和约束，不自动改算法、丢输入、放宽校验或减少审批。依赖循环且无法确定求值的推导不能展开；需由作者修正。
6. **撤销与改值**：在未冻结工作稿中可撤回本稿赋值，并使相关推导和验证失效；不能撤回父版本固定内容。改动父版本已有固定值或放宽约束，另建修订/分叉并保留来源，不继续声称是原版本的合法下级。
7. **版本隔离**：父模板修订不改变既有下级。迁入新版时比较固定值、约束与引用差异，重新检查整个相关依赖；不能自动把旧子模板接到新父版本上。

同一组兼容赋值应产生同一确定定义，不应因为编辑器先填哪一栏而改变业务语义。派生时约束不可满足的模板可以保存为未完成工作稿，但不能标为可用模板供自动展开；不存在合法补全不是“最具体的方法”。

#### 3.1.4 定义变量、运行输入与方法形成条件

创作变量用来决定将生成的方法定义，例如采用哪些步骤、选择哪个被调用方法、输出哪种报告结构。运行输入在方法定义已经确定后提供，例如本次公司、目标季度、财报引用及收件人。区分依据是是否改变方法定义，不是某个字段名称天生属于哪一类。

| 情形 | 应如何处理 |
| --- | --- |
| 作者从 C07 样板选定方法引用、补齐输入映射及交付定义 | 创作或修订方法，形成待验证的工作稿 |
| 使用已发布的季节性预测方法，传入本次公司和目标季度 | 运行该方法，保持已定算法、4/8 季窗口及最近 4 季回测要求 |
| 模型按已发布方法允许的条件选择步骤或被调用方法 | 在已定义范围内生成本次执行计划，不因此生成新模板或新方法版本 |
| 把 C07 的预测算法、固定窗口或允许的方法范围改掉 | 修改方法定义，需重新确认与验证；不能作为普通运行参数替换 |

参数若允许在运行时选择算法或输出形式，其可选范围和校验规则必须预先定义在方法契约中。模板不允许以“填写参数”为名临时改变业务承诺，也不把每一步自动展开为独立对话或工具注册项。

未定的定义变量不能仅被改名为“运行参数”来绕过闭合检查。若有意把某个选择交给运行时，必须先把该输入的类型、允许范围、选择规则、分支、校验和权限完整定义；此时已经固定的是“如何允许选择”，而不是偷偷留下未完成设计。运行时模型在这个范围内制定执行计划，符合定义，不需要每次生成新模板。

方法形成有三个不同的检查点：

| 检查点 | 成立条件 | 不可混淆的事实 |
| --- | --- | --- |
| 模板可继续具体化 | 已赋值内容合法，剩余变量明确，没有已知不可解冲突 | 仍可有待绑定变量和待判断约束，不能宣称已能完成业务任务 |
| 具体方法定义闭合 | 所有可达定义变量已确定，推导完成，六要素完整且定义约束检查通过 | 运行输入可以未提供；实现、部署和真实验证仍可能尚未完成 |
| 方法可调用 | 闭合定义具有实现和执行绑定，并完成适用范围内的验证及注册 | 本次运行还须有输入、资源、有效授权和所需批准 |

“所有可达定义变量”不包括已被固定选择明确排除的分支占位，但排除依据必须可核对；运行时仍可能进入的分支都必须定义完整。六要素某项不需要特殊内容时显式声明，如无外部访问或无额外审批，不能用未填写代表无要求。

没有剩余定义变量的模板可以作为完整方法定义的复用起点；逻辑上它已经闭合，保存为“完整样板”不产生另一套运行身份。闭合也不意味着实现正确或已经可调用。

#### 3.1.5 贯穿示例：资料摘要与交付

以下仅用于说明逐级赋值，假设引用的业务方法规格另行提供；表格不是可执行资产，也不改写 C01—C15 的财务规则。

| 阶段 | 本层固定或收窄的内容 | 仍待确定的定义 |
| --- | --- | --- |
| 资料摘要与交付模板 | 六要素结构、摘要保留来源、外发需有授权依据 | 来源方式、摘要执行方法、交付方式及与这些选择关联的细节 |
| 邮件摘要模板 | 来源方式选为邮件连接器，固定邮件读取的操作契约和来源格式 | 摘要方法、交付方式；展开后的范围选择规则及获取限制 |
| 邮件摘要报告模板 | 选定摘要方法精确版本，交付方式选为生成 Markdown 报告，固定报告包含摘要和来源索引 | 选定实现所要求的输入映射、校验判据及剩余处理规则 |
| 具体邮件摘要方法定义 | 补齐映射、判据和获取限制；明确从运行输入选择账号、文件夹和期间；定义缺项处理，声明不发送邮件 | 定义变量已闭合；本次账号连接、文件夹、期间和实际邮件仍是运行输入与资源绑定 |

“生成并发送邮件报告”可以是邮件摘要模板的另一分支：需要固定发送步骤、接收人输入要求、发送权限和审批规则，不能把已固定“仅生成报告”的下级模板直接改为发送并仍声称保持原定义。两个分支的用户连接和实际批准都在运行时取得，不随模板下传。

### 3.2 模板字段、派生与应用过程

| 建议字段 | 含义 |
| --- | --- |
| `id`、`version`、`purpose` | 模板身份、版本及适用的创作目标 |
| `method_schema_ref` | 所遵循的方法通用结构版本；用于展开与兼容检查，不能引用漂移的“最新结构” |
| `definition` | 带明确变量引用的六要素定义；固定内容、步骤及其执行体都在这里表达，不另存一套流程 |
| `variables` | 每个定义变量的稳定标识、类型/Schema、作用位置、可选范围、默认建议、依赖、来源和说明；结构变量还声明允许的展开契约 |
| `constraints` | 变量及跨六要素约束、推导依据和检查责任；区分可解析检查与需要作者或人工核对的业务判断 |
| `base_template_ref` | 可选的直接父模板精确版本与摘要，记录具体化来源；根模板为空，不用可手填的等级数字决定关系 |
| `bindings` | 本模板已明确采用的变量赋值及来源；派生时继承父赋值，新增赋值不得覆盖父固定内容 |
| `constraint_refinements` | 本层新增或收窄的约束，明确指向上级变量及规则，禁止静默删除上级限制 |
| 来源与验证说明 | 模板及引用实现的来源、版本、候选状态、已验证范围与限制 |

建议根模板维护 `definition`、`variables`、`constraints`，派生模板维护父引用及本层赋值、约束收窄；父版本与本层变更解析为有效定义。展开快照与摘要由此生成，只读且可重建，不能与父引用及赋值各自编辑。新增结构来自允许的变量展开，不通过任意覆盖定义绕过固定内容检查。方案字段仍需对齐现有方法存储，未要求新增一套模板服务。

第一版建议一个模板只有一个直接派生父版本，便于核固定内容和冲突。复用其他模板可通过有类型的结构变量引入并显式映射，记录引用版本、避免变量重名；不依赖隐式多父继承或“后者覆盖前者”。派生引用必须无环；祖先深度仅为展示信息，不是质量、复杂度或可调用资格。

原建议字段 `method_contract_defaults` 改为 `definition`，以免把已经固定的内容仍当成可随意替换的默认值；`author_options` 的变量部分归入 `variables`，约束部分归入 `constraints`，实际采用的选择归入 `bindings`。旧 `parameter_defaults` 不恢复：定义变量默认建议只在变量声明处维护，运行默认值只在方法输入 Schema 中维护；实际已绑定值有独立来源记录。编辑表单由这些字段生成，不再存一份独立创作规则。

模板应显式标出未定变量、已赋值、默认建议、已推导内容、未决约束及无效赋值，不能只显示“填完百分比”。不以演示数据填充必需业务输入。模板和下级定义中的权限均为需求声明，实际授权仍另行取得。

流程图、所需数据摘要、交付清单和审批点视图从公共契约及步骤定义派生，不再维护一套独立的 `default_composition` 或交付要求真源。模板分别保存方法的对外输入声明和各步骤的内部输入映射；对外输入变更时核对受影响的映射，内部新增中间结果不自动扩大调用者的输入责任。实际需要数据获取或整理时再设置相应步骤，不预设所有模板都从输入准备开始。

```text
选择模板版本
  → 读取固定内容、剩余变量、约束与已绑定来源
  → 作者部分赋值或收窄范围，执行类型、依赖及一致性检查
  ├─ 仍有定义变量：保存为下级模板，可再次派生
  └─ 定义变量闭合：形成具体方法工作稿，检查完整性和语义约束
       → 补齐实现与执行绑定，验证业务结果及失败恢复，冻结方法版本
       → 登记 tools 可调用项
       → 本次任务按参数和授权解析实际绑定并执行
```

上面的“保存为下级模板”和“形成具体方法工作稿”是按剩余定义变量分出的两条路径；不是每次赋值都必须发布模板。用户可以在同一工作稿中连续赋值，仅在需要复用某个中间层时保存版本。无需通过模板也可直接创作方法，仍遵守相同六要素及验证要求。

模板应用后保留来源版本与赋值链，作者修改自己的工作稿，不能回写他人的模板。发布时解析为可审阅、有限且无未决定义变量的方法快照；运行只取该方法版本，不递归读取模板“最新版”。通用结构变更需显式迁移，不能假装只增加一层赋值。复用 knowlab 的现有创作与方法版本机制，执行仍沿 Task/Attempt，不另建模板执行服务。

结构与赋值检查可由程序完成；涉及方法正文或业务含义的约束不能假装已经自动证明。应逐项记录通过、失败或待审及依据。模板展开一致、定义闭合、业务测试通过和发布批准分别记录，任意一项不能代替其余各项。

为衔接旧稿，`applicability` 和旧建议字段 `when_to_use` 的内容归入 `capability_declaration`，按 1.7 补齐用途和边界，不并列保留两个创作字段，也不能仅改键名就认定声明完整。`input_schema` 归入 `required_inputs_and_access`，算法与处理规则归入 `sequence_of_work`，`acceptance` 对应 `how_to_validate`，`output_schema` 归入 `what_to_return`。旧稿把节点直接视为方法引用的结构需拆为步骤及内部调用动作；确实只有一次调用的步骤可以保留为单动作步骤，无须人为填入程序块。具体字段迁移须另行验证现有契约，旧发布版本仍按其原契约读取。

### 3.3 财务方法模板候选 C01—C15

以下保留原候选模板的业务范围和算法边界。准确地说，这 15 项目前是拟制作的模板清单和组合摘要，尚未达到 3.2 的完整模板定义；保留 C 编号用于追溯，C01—C15 是候选标识，不是 15 个具体化等级。制作时须明确六要素固定部分、定义变量、约束、引用版本及必要的派生关系；不能把表格一行视为已经可展开的模板资产。生成方法后仍须补齐输入映射、执行体与恢复规则并验证。它们不表示已实现、已发布或已经进入当前专家的能力范围。

A/Q/O/V/R/E/P 编号及候选状态见[原子化提炼稿](原20个财务方法的原子化提炼.md)。A06、O03、V06 仅为目录分组，展开时必须选择具体具名方法和确定版本，不能把分组名当作调用名；其他待定契约补齐前也不能执行。表中多个方法相加不意味着各占一步，同一步骤可以编排多次调用和程序块。

### 3.4 验证要求

以原四式核验、CAGR、累计转单季—原预测—回测链作为贯穿样例，再扩充当前财务专家需要的指标、证据核对和报告组织。方法或模板数量不作为成熟度依据。

| 验证对象 | 必须检查 |
| --- | --- |
| 模板表示 | 六要素固定内容、定义变量和约束可区分；默认建议不冒充已赋值，原始定义与展开快照不各自编辑；运行默认值只归输入 Schema |
| 逐级具体化 | 父版本固定内容和约束保留；合法赋值使选择范围收窄，类型错误与跨要素冲突可定位；相容赋值顺序不改变结果，不按变量数量断言等级 |
| 结构与作用域 | 结构变量展开有依据，引用无环、变量不重名、映射与依赖可追溯；模板派生不产生运行调用，方法组合不自动产生模板父子关系 |
| 闭合与验证 | 可达定义变量全部确定、定义完整且约束核对完成后才形成闭合定义；实际可达分支不能留空；实现、业务验证和运行授权另行检查 |
| 派生版本 | 父模板升级不改既有子模板；撤回本稿赋值会使依赖结果失效；改父固定内容作为修订或分叉，不伪称合法具体化 |
| 方法契约 | 所有方法使用同一套六要素，不按“原子／组合／专家”分配不同契约；缺项或占位不得注册为可用方法 |
| 能力声明 | 第一项为能力声明，不与 `when_to_use` 并列；目标和边界明确，所引用输入、交付、校验及审批要求一致；公开展示不另存独立承诺，不以子方法能力并集替代作者声明 |
| 步骤结构 | 步骤不强制六要素或独立方法身份；纯程序块、多方法调用和混合执行体均能明确表达 |
| 方法与步骤输入 | 方法输入表达对外要求，步骤按需映射多种来源；数据齐全时允许直接执行，不人为增加首个输入步骤；缺项及后续分支需要的补充内容按声明处理 |
| 数据与依赖 | 每项输入有来源，每项承诺产物有生成路径；数据依赖和质量依赖不混淆，内部动作依赖也能核对 |
| 权限与审批 | 权限要求与批准事实分开，方法调用与程序块受相同边界约束；按实际连接、操作、范围及内容匹配批准，有效批准可复用，子调用不扩权；更换账号或内容不能沿用不匹配的批准 |
| 验收与结果 | 技术成功不代替业务验收；部分完成、不适用和失败明确区分；内部动作全部成功但整体交付缺项时不得通过 |
| 失败与恢复 | 多动作步骤中部分完成后中断，恢复不得重复已生效副作用；输入或版本变化后失效范围正确 |
| 复用与版本 | 同一方法可在不同步骤以不同输入使用；层级不固定；程序块随所属方法版本冻结；替换绑定须证明契约等价 |
| 记录与计数 | 步骤、内部动作、方法调用和模型轮次分别可追溯，不伪造未调用方法或未执行分支的成果 |

CAGR 应覆盖不同组合中的复用及适用域边界；混合步骤应覆盖第二次调用失败、结果合并失败和恢复；C07 应核对每个回测起点的数据可得性及最终指标、期间、点值和上下界覆盖。具体业务判断及阈值来自作者，验证不擅自补入投资规则。

作者流程见[新财务专家孵化方案](新财务专家孵化方案.md)，运行与验收衔接见[财务专家执行与验收方案](../../专家使用方案/luna/财务专家执行与验收方案.md)。本文明确目标结构，既有资产和代码是否满足这些要求须逐项验证，不将文档重写等同于实现完成。
