## 二、总览：两档现在走到哪

10-28 分了两档。到 11-09：

| | 第一档 | 第二档 |
| --- | --- | --- |
| 专家的逻辑 | 写死：作者孵化好的步骤（固定专家，已上线） | 可以活：作者给方法，按题挑——**11-02 提前到本轮**，代码已在 qwen 分支，对外关着；11-08 定财务专家改成这种（第五节） |
| 用户的数据 | 用户挑：模型按专家逻辑和问题提出，用户确认（已上线） | 同左 |
| 作者挑选的数据 | 交付时一次挑定，全带上，或者没有（已上线） | 作者按每件委托的问题挑、作者确认——**后期** |
| 谁挑专家 | 用户自己挑，或交给 AI 按声明找（第四节，已做） | 团长拆解、提议谁做哪块，用户确认——**后期** |
| 几位专家 | 一位；同一项目一次一位，其余排队（10-11） | 专家团——**后期** |
| 工作机制 | 一件委托一条线 | 任务看板、统一交互——**后期**（第九节） |

**贯穿始终的原则：谁的数据谁挑。** 用户的数据由用户挑；作者的数据由作者挑。模型可以替人提议，最后由数据的主人确认；系统只按他们定的去找、去取，不替任何一方挑。

## 三、几个词

| 词 | 指什么 |
| --- | --- |
| 作者、孵化者 | 在 knowlab 孵化、测试专家的人 |
| 用户、请的人 | 在 knowbench 请专家做事的人 |
| 委托 | 用户请专家做的一件事，knowbench 里的一条任务 |
| 清单 | 逻辑 + 作者挑选的数据，交付时冻结。逻辑包括模板参数、方法目录（或固定步骤）、验收、规则出处；作者挑选的数据只记引用，数据本身留在 knowbase。用户挑的数据不进清单 |
| 模板 | 每位专家执行时共用的流程骨架：定范围、排计划、定数据、做方法、成稿交付（第五节，新提） |
| 定数据 | 模型按问题（和选中的方法）提出这件委托要哪些数据，交用户确认；现在叫「第 0 步」 |
| 数据清单 | 定数据提出、knowbase 解析过的那张单子：每一样用哪份、为什么、缺什么 |
| 委托的输入 | 一件委托实际用的：清单的哪一版，加上这次两路各用的哪几份（用户确认的、作者挑定的），确认时钉住 |
| 匹配收据 | AI 找专家那一轮的结果：原问题、选了哪位哪一版、依据的声明、已知限制，存在任务上 |

## 四、请专家

### 4.1 两种请法（11-04 实施方案 6.1）

首页"专家"模式和项目"请专家"共用一个入口：先写问题，再点

- **「ai去knowmart请回专家」**：AI 按问题去 knowmart 找（第 4.2 节）；
- **「自己去knowmart请专家」**：到市场自己挑一位，带着确切版本回来。

两种请回来的专家都在同一个列表里高亮；用户提交问题才开始分析，找到专家不自动开跑。不填代码、不填参数、开跑前不列数据清单。空问题、沙箱没就绪、项目被占用这些不能请的原因，直接写在按钮旁边。列表里每位专家可以"删除"，只从本人工作台拿掉，市场上的专家、已有的委托和报告不受影响。

普通聊天还是普通聊天：用户点了「ai去knowmart请回专家」才发起查找，不会把每句话偷偷变成付费找专家。

### 4.2 AI 按声明找专家（原第 4.9 节，11-03 改）

```
写问题，点「ai去knowmart请回专家」
找专家：一件不带专家的内部小委托（FIND_EXPERT），用户自己的模型读问题和 knowmart 上专家的公开声明
  ├─ 按声明合理适合、不用另付钱 → 请回并高亮，写明依据和已知限制；用户提交问题才建委托
  ├─ 好几位都合适 → AI 选一位、写理由，用户可以换
  ├─ 合适的要另付钱 → 给用户看候选和价格，用户点了才请
  ├─ 声明里明确不做用户要的、或只做得了一部分 → 照实说差在哪，不装作适合；用户改题、另挑或走第 4.3 节
  ├─ 有影响选择的关键歧义 → 简短问一句；没答不当同意
  ├─ 没有合理合适的 → 第 4.3 节
  └─ 目录或模型服务出故障 → 照实报错和已花的钱，不当成"没找到"，不自动计费重试
```

逐条说：

1. **在哪跑**：在用户的项目里，用用户自己的模型和 key；knowbench 后端不调模型。挂成一件不带专家的内部小委托（方法包 `FIND_EXPERT`，这一轮费用上限默认 2 元），模型用 `find_expert` 工具查 knowmart 目录。
2. **看什么**：只看公开信息——名称、一句话介绍、能力声明（[能力声明与版本](../../专家市场方案/opus/能力声明与版本.md) 第二节）、接什么 / 不接什么 / 不接的去哪问、版本、价格、这位用户有没有授权。看不到别人的方法和数据。
3. **按声明合理选，不证明一定能做完**（11-03）：判断用户的目标和明确的要求落不落在某位专家声明的范围里，不要求事先推导完整的方法、证明方法组合一定可行、或先把数据取齐。用户承担合理选择的不确定，执行中能纠偏（第 5.7 节的行为审批、停下、换），作者负责声明真实，平台负责忠实执行和如实记录。平台不排序、不加权、没有推广位。
4. **后端再核一遍**：候选必须真在目录里、版本和摘要对得上、声明的引文是真的、用户请得动、价格以目录为准；模型的判断不能当执行授权。目录不完整、分页截断时说"没查完"，不说"市场没有"。
5. **花钱的由用户定**：不用另付钱的直接请回，写明"AI 替你请了某专家，理由……"，用户可以换；要另付钱的先停下给用户看，点了才请。

### 4.3 没有合适的专家时（原第 4.9 节第 4–7 条，11-04 改）

给用户一张卡，两件都不自动跑，用户点哪件做哪件，可以都点；另可改题、自己挑、结束：

```
没有合适的专家
  [通用模式]       用我自己的模型直接答；适合一次性的问题；花我的模型费用；回答标「不是专家」
  [提出孵化申请]   会反复问、要固定口径和验收、想给别人用的适合；建申请不花钱
  推荐：……（附一句理由）
```

- **通用模式**：在这个项目里开一段聊天（10-29：「直接答按聊天」），用用户自己的模型和 key，平台在这里只是工具，不往里塞自己的分析方法；回答照实标明「这是你的模型直接答的，不是专家，方法没经过测试」。
- **提出孵化申请**：knowlab 里以用户的名义建一个种类为「问题」的申请，带原问题和来自哪个项目；申请只有用户自己看得到、建了不花钱；先点过直接答的，那份回答可以附进去当参考，只算提议、作者接受才算（⑮）。往下照 [专家孵化方案](../../专家孵化方案/opus/专家孵化方案.md)。用户原有的数据授权和费用不因转去孵化而扩大。
- **标推荐**：找专家那一轮模型顺手判断哪件更合适，写一句理由，不另调模型。一次性的、问个事实的推荐直接答；会反复问、要固定口径的推荐孵化。只是标出来，由用户点。
- **不再有"在 knowmart 挂需求"**（11-04 删）：原稿让用户点「发布」挂需求，现在卡上没有这一项。

### 4.4 从选中到委托（实施方案 6.4、6.5）

- 建委托的请求带匹配收据的编号与版本、问题修订号、确切的专家版本和幂等键；后端从收据恢复问题和授权对象，重核用户、项目、版本、授权，不接受前端自己拼的结果。重放返回同一件委托，异载荷同键拒绝。
- 匹配依据存在任务上（`selection_basis`），不再只记在浏览器里（原第 4.9 节"实施"那段写的是记在浏览器，已改）。手选的直接钉原题和专家版本，不发起匹配模型。
- **本次委托**保存：原问题及修订、选定的专家版本、预期成果、已明确的条件和关键假设、费用上限、需要用户决定的事项。执行中发现要缩小范围或改假设，形成委托修订并绑定用户的决定，保留原目标和没满足的项。

## 五、执行：一个模板，前后固定、中间放方法（11-09 新提，等你定）

### 5.1 现在怎么跑

- **固定专家**（「财务分析与预测」现行版就是）：先走平台的第 0 步「定数据」，再照作者定的八步依次做：定范围、数据摸底、勾稽、取数（累计转单季）、算指标与分析、对照官方披露（管理层讨论）、预测、成稿。不管问什么都走八步；只问"营收多少"也要做勾稽、单季、预测、对照。0050 让固定专家受理时由平台按作者顺序写一份计划回执，之后和动态专家走同一段"按计划做"（已写、等价测过，开关名单只放你本人，没发版）。
- **动态专家**（代码在 qwen 分支，对外关着）：请来以后先**排计划**（用户的模型在作者给的方法里挑、排顺序、绑输入，平台逐条校验），再**定数据**，再按计划一步步做；前面的成果失效可以在上限内重排。
- 八步里混着三种东西：通用的组织工作（定范围、数据摸底、成稿）、财务方法（勾稽、单季、指标、预测、对照）、平台通用的规矩（每一步正文开头都抄同一段一千多字的话）。

### 5.2 现有的动态契约能不能表达"共享模板 + 可挑方法"

这是 [opus-qwen](../../../opus-qwen.md) 第八节要先核清的问题。**能表达一半。**

- 在**一位专家内部**，`dynamic-methods/v3` 能把定范围、成稿设成必做方法（`selection.required`），别的方法按题挑，靠输入依赖保证定范围在前、成稿在后。
- **不能表达"共享"**：定范围、成稿只能作为方法放进每一位专家自己的目录，每个作者各写一份；独立方法的复用现在只限同一作者。定数据不在专家目录里，是平台的一步。v3 是先排计划、再定数据、再做方法，定范围作为方法要等排完计划才做，模型排计划时手里还没有整理好的范围。

所以要么每位专家各抄一份通用步骤（和现在每步抄一千字是同一个毛病），要么把通用步骤从"方法"里拿出来，变成平台按固定顺序跑的模板阶段。本方案选后者。

### 5.3 模板

```text
① 定范围 ──▶ ② 排计划 ──▶ ③ 定数据 ──▶ ④ 按计划做方法 ──▶ ⑤ 成稿交付
（模板）     固定专家：作者顺序   （模板）     作者的方法        （模板）
             动态专家：按题挑
```

| 阶段 | 做什么 | 平台写的（固定文字） | 作者填的（[模板与方法](../../专家孵化方案/opus/模板与方法.md) 第三节） |
| --- | --- | --- | --- |
| ① 定范围 | 把问题整理成本次的范围：对象、期间、要回答什么、交付要求、明确的限制；不在范围里的照实说 | 怎么读委托、不重写用户的问题、出了范围就停 | 范围要素；接与不接 |
| ② 排计划 | 定这次用哪些方法、什么顺序、谁的成果喂给谁 | 固定专家照作者顺序生成回执（0050）；动态专家由用户的模型按规划原文挑，平台校验 | 方法目录、规划原文、必做、上限 |
| ③ 定数据 | 按①的范围和②选中方法的输入需求，提出要哪些数据，用户确认，缺的补取 | 就是现在的第 0 步（第 5.6 节） | 方法声明的输入 |
| ④ 做方法 | 一个方法一轮，确定性验收，返工、退回 | 现成的"按计划做" | 方法正文、输出、验收 |
| ⑤ 成稿交付 | 把选中方法的成果组织成交付物，写局限，交文件 | 每个选中方法的结论都要进成稿、没选的不编、算不出来照实写、数字只引用前面已验的成果 | 交付结构 |

**每一轮都要守的通用规矩**（只用授权数据、数字必须来自数据或计算工具、地址写法……）由平台统一加在每一轮前面，作者不再抄。

**好处**：
1. 通用步骤真正共用：模板是平台的执行机制（和现在的第 0 步一样），所有作者、所有专家自动用上，不需要"跨作者复用方法"。模板对所有专家一视同仁，不是平台账号专用的通道（"平台也是用户"）。
2. 固定和动态只差第②步：其余四段一模一样，0050 的"按计划做"、G-1 那 10 处分开走的地方大多随之收掉。
3. 数据要得更准：现在第 0 步只能读整位专家的逻辑去猜要什么数据；改成先选方法，再按选中方法声明的输入去要。只问营收就不会去要现金流量表。
4. 简单题少走几步（第 5.9 节）。

和 decisions ⑮「预先做好的方法模板不做」、实施方案 5.5「不把准备/成稿一概搬入平台写死」的关系，见 [模板与方法](../../专家孵化方案/opus/模板与方法.md) 第三节：模板只管流程骨架和组织，带专业判断的部分作者填。

### 5.4 ① 定范围

- 一轮，用户的模型、在用户的沙箱里。输入：本次委托（原问题及修订、预期成果、条件）、专家的范围要素和接与不接。
- 输出：本次的范围（对象、期间、要回答的、交付要求、限制）；不在专家范围里的，照实说，委托按第 4.2 节"只做得了一部分"的出路走。
- 有验收：范围要素都要有值或写明"问题里没说"；不得改写用户的原问题。
- 找主体用「查主体」工具，不自己编代码。

### 5.5 ② 排计划

- **固定专家**：平台按作者顺序确定性生成计划回执，不调模型、不花预算（0050 第二节）。
- **动态专家**：用户的模型按规划原文、①的范围、方法目录（用途、输入输出摘要、允许的工具）排计划；平台按原 `validate_plan` 校验——只能用冻结目录里的方法、必做的不能漏、输入绑得对、没有循环和孤立成果、步数和调用次数不超上限、可选输入只能因上游没选而省略（实施方案 7.1）。
- **顺序改一处**：现在 Advisor 是"先排计划、再定数据"（实施方案 7.2，照留），本方案在计划之前加了①定范围，让模型排计划时手里有整理好的范围（第十一节第 2 条）。
- 重排照现有：只在步骤边界、上限内，保留已开始的前缀，新计划记父版本和理由。

### 5.6 ③ 定数据（原第 4.3 节）

```
③ 定数据：模型按①的范围和②选中方法的输入需求，用工具提出要哪些数据
  ├─ 一样都不要 → 直接进④
  └─ knowbase 在用户能用的范围里解析 → 委托停下，等用户确认数据清单
       用户在委托页或看板卡片上：确认、换一份、改主体或期间、去掉、自己加一样
       → 本人签运行授权、钉住
       ├─ 都齐了 → 进④
       └─ 有缺的要去取 → 交 knowfeed，委托「等数据」→ 齐了自动接着跑（⑫）
            └─ 有没取到的 → 停下问用户：照现有的接着做（产出标「数据不全」），还是取消
④ 开跑以后还要新数据 → 同一个工具提出 → 停在步骤之间等用户确认；用户也可以选不要
```

1. **在委托的沙箱里跑**，用用户自己的模型和 key，knowbench 后端不调模型。模型读到的是：①的范围、②选中的方法及其输入声明、专家自带资料的份数（看不到内容）。
2. **两个工具**：
   - **查主体**：按名字查证券代码、机构编号（「宁德时代」→ `300750.SZ`），免得模型自己编代码。
   - **提出数据**：两种要法（[数据拓扑](../../../数据拓扑.md) 第 7.2 节）——要资料按描述写，要数按主体、期间、科目编码、口径写；外加「为什么要」「是不是必需」。**只说要什么，不写渠道、不写取法**（11-07；knowbench 的提示里不再写"优先用 Wind"，0051 第 8 步）。不设作者的范围（第 16 条），只设防滥用的上限：一次最多 20 样、展开后最多 200 条。
3. **knowbase 解析**：要数的先在标准化层找，要资料的按描述找，每一样回已定、有歧义、待确认（要去取）、取不来、没放开、不能用。
4. **用户确认数据清单**：确认面板在委托页上，看板卡片上也能直接确认。每一样写用哪份、哪一版、为什么。用户能换、选、改主体或期间（改了重新解析）、去掉、自己加。确认时本人在场，当场签运行授权；要等补取的，齐了由 knowbench 凭这次确认续签（7 天内），自动接着跑（⑫）。
5. **没取到的**：停下问用户，照现有的接着做（产出标「数据不全」，不算完整的成功），或者取消。
6. **开跑以后还要新数据**：同一个工具，要别家公司的、不限主体的都行；委托在步骤之间停下等用户确认。专家读不到用户没确认过的数据。

**两路数据**：

| | 用户的数据 | 作者挑选的数据 |
| --- | --- | --- |
| 谁挑 | 用户：模型提议，用户确认 | 作者：交付时一次挑定 |
| 怎么找 | 提出的描述，knowbase 在用户能用的范围里解析 | 不找，清单里冻结的引用原样带上 |
| 用户能做什么 | 确认、换、改、去掉、加；确认去取 | 看到份数，不能换、看不到内容 |
| 运行授权的依据 | 用户放开给 knowbench 的、名下的引用、公开原件 | 冻结的绑定同意 `expert:<专家>@<版本>` |
| 运行中新要 | 专家提，用户确认 | 本期不能新要（第二档） |

两路合成一份运行授权，knowbase 逐项核依据。

**合规**：定数据的模型是用户自己的，系统不替用户挑；清单由用户确认，正好是「用户发起任务，系统在约定范围内自动选择和补充」（数据拓扑第十八节）。「用户指定」落在：用户确认过的数据清单（连同提出的原样、用户改了什么）、一次确认的取得清单（确认编号、任务编号、清单快照、供给条件快照）、运行中新要的、作者的冻结同意。

### 5.7 ④ 做方法、审批与验收（实施方案 7.3、7.5）

- 一个方法一轮，沿用现成的开步、验收、返工、退回、断线恢复、预算。同一方法要的多期事实批量查，计算交给计算工具（一次 1–50 项），每个结果留收据。
- **行为审批是执行中的纠偏点**：已授权、预算内的分析和工具操作自动做、留记录；新的数据范围或费用、改变关键假设或交付范围、文件修改这些有影响的操作，给用户看"要做什么、为什么、影响什么"，可批准、拒绝、调整、停止；没回答不等于同意。专家能力不适合的，不靠一次审批扩展能力，保留成果、给通用模式或孵化的入口。
- 批准只说明允许这个行为，不代表数据对、公式对、成果合格；原验收照做。

### 5.8 ⑤ 成稿交付

- 一轮。输入：选中方法已验收的成果、专家的交付结构；不调数据工具（写文件是唯一的工具）。
- 验收：每个选中方法的结论都进了成稿；没选的方法不出现结果（写"本题未做"或干脆不写那一节，按交付结构）；"算不出来"照实写原因；成稿里的数只引用前面已验的成果；交付结构里不许写的不出现。
- **完整成功**要同时满足：用户的必要要求、作者的必做验收、有效的最终成果、文件交付验证。部分成果可以保存下载并列清缺口，但不算完整成功（实施方案 7.4）。
- 交付那一刻取成稿的指纹，替用户写一份进 knowbase 产出区（`WORKBENCH_OUTPUT_WRITE_ENABLED`，随下次发版打开；数据拓扑第十四节）。

## 九、以后（第二档剩下的）

### 9.1 要做成什么样

- **专家团**：一位团长加几位成员，参照 WorkBuddy：团长拆解任务、分配给成员、成员执行、团长整合交付。设想：用户写问题 → 团长拆成几张卡、提议谁做哪张 → 用户确认分工 → 各张卡由成员做，要停下时等人 → 团长整合，交给用户。
- **任务看板**（所有者的设想）：一件任务一张大卡，成员的子任务是小卡；列：排队、在跑、等你、等别人、完成、失败；卡上写谁在做、等谁、等什么、花了多少钱；等你的在卡上直接答。
- **统一的交互**：一套交互记录，记谁问、谁来答、问什么、答了什么；答的人可以是用户、作者、专家；答了那张卡自动接着跑。现有的反问、审批、数据确认都收进来。
- **作者按问题挑数据**：用户请专家 → 作者收到这件委托要挑数据的请求 → 作者在 knowlab 待办里从自己给出的可挑范围里挑 → 这期间卡停在「等作者」→ 挑完钉住、续签、接着跑。清单里冻结的是可挑范围，每次挑定的记在委托的输入上。

## 十一、要你定的

1. **模板这条路对不对**：通用步骤从"方法"里拿出来，做成平台按固定顺序跑的①③⑤；作者只填范围要素和交付结构。另一条路是继续把定范围、成稿当方法，每位专家自己带一份——我不建议，理由见第 5.2 节。
2. **①定范围放在②排计划前面**：现在是先排计划。放前面每题多一轮、多一点钱，但模型排计划时有整理好的范围，范围也能单独给用户看、单独验收。
3. **①和②要不要合成一轮**：合成一轮省一轮，但范围就不能单独验收了。我倾向分开。

另两份方案里待你定的：[模板与方法](../../专家孵化方案/opus/模板与方法.md) 第八节（方法怎么分、作者填的够不够），[能力声明与版本](../../专家市场方案/opus/能力声明与版本.md) 第七节（老用户怎么换版本、固定格式要不要也换、能力声明怎么写）。

## 十二、市面参照

- WorkBuddy 的专家是「人设 + 方法论 + 工具链」，不是写死的步骤；只处理用户在对话里给的和上传的文件；要连外部服务时弹授权卡片，授权后任务自动继续。见 [专家中心（官方文档）](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Expert-Center)、[WorkBuddy Enterprise 专家（腾讯云）](https://cloud.tencent.com/document/product/1831/134393)。
- WorkBuddy 的专家团由团长拆解、分配、并行执行、整合交付；用户中途能取消、追加要求。官方文档里没有「任务看板」，看板是所有者的设想。见 [专家与专家团完整指南](https://github.com/KimYx0207/AI-Coding-Guide-Zh/blob/main/docs/workbuddy/WB-03-WorkBuddy%E4%B8%93%E5%AE%B6%E4%B8%8E%E4%B8%93%E5%AE%B6%E5%9B%A2%E5%AE%8C%E6%95%B4%E6%8C%87%E5%8D%97.md)。
- WorkBuddy 企业版的「项目」：人和数字员工在同一个项目里共享上下文。见 [量子位报道](https://www.qbitai.com/2026/06/430758.html)。
- 「先由模型出计划、人确认再动手」是常见做法（编码智能体的计划模式），定数据照这个思路：模型提清单，用户批准再取、再跑。凭记忆，未逐一核实。
- 以下也凭记忆，第二档动手前再核：Linear 把任务单派给智能体，人在任务单评论里和它来回；GitHub 的编码智能体接任务单后交 PR；Vibe Kanban 把智能体的任务放在看板上按列推进。
