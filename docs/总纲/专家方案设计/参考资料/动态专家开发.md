## 一、目标与本文的位置

第一目标是长期可维护、跨专家复用的工程。在此基础上，争取用动态专家完成演示，保留实际验收通过的固定专家作为演示备用。

第二轨要实现三件相互衔接的事：

1. **按方法需求匹配专家**：AI 根据用户问题判断所需的方法，只有这些需求落在某位专家声明的方法范围内，才直接请入该专家；否则提示缺口并让用户选择后续出路。
2. **按匹配结果执行**：已请入的专家依据其冻结方法落实任务计划；这属于执行过程，不另设独立的“第二层选择”。
3. **按计划准备和使用数据**：主体、期间、指标、资料及来源随任务确定，充分利用 Wind 的数据能力和年报证据能力。

动态专家的完成判据必须覆盖从提问到交付的全过程。用户只输入问题、没有先选专家的路径，是首要验收路径。

本文是这次讨论与分步开发的入口，不另起一套需求和完成账。确定后的规则回写原设计，实施结果回所属仓与既有待办：

- [请专家方案设计](../专家使用方案/opus/请专家方案设计.md)：AI 找专家、用户指定和无匹配出口，尤其第 4.9 节。
- [专家孵化方案](../专家孵化方案/opus/专家孵化方案.md)：作者方法、创意、工作稿、测试与交付。
- [财务智能体双轨交付计划](财务智能体双轨交付计划.md)：第二轨总体范围、原待办核对与真实业务验收。
- [方法架构决定](../../../design/SDD/architecture/methods.md)：统一执行体系与演示后的固定体系退役。
- [专家待办账](../../../design/knowbot-todolist.md)：包括 K29 测试展示归属、K30 归档、K31 固定体系退役。

## 二、已经确定的要求

| 事项 | 已确定的要求 |
| --- | --- |
| 方法范围匹配 | 不按“两层选择”设计：问题的方法需求落在专家声明的方法范围内才直接请入，否则提示并给用户出路 |
| 选择专家的入口 | 支持 AI 根据用户问题查找，也支持用户直接指定 |
| 不匹配或不能确认覆盖 | 说明原因，提供孵化、用户指定专家、通用模型直接回答、结束等出路；不擅自请入或自动提交孵化申请 |
| 方法来源 | 方法在 knowlab 整理、由作者接受并版本化；Skill、AI 草稿和候选模板可以是素材 |
| 专家装配 | 作者明确专家服务范围、引用哪些方法版本、选择条件、必经方法、工具及交付标准 |
| 运行时边界 | 模型选择、组合已配置的方法；不得任意调用整个方法库、创造方法或改验收标准 |
| 组合与版本 | 方法是独立可复用资产，专家引用其确切版本；方法更新不自动改变旧专家和旧任务 |
| 真实专家 | 只有真实可用、对该用户可请的专家参与选择；20 张展示占位卡不参加匹配 |
| 数据 | 不写死公司、年份或数据类型；作者预置绑定可为空，用户任务数据独立授权 |
| Wind | 要接入服务端数据路径，既考虑结构化财务数据，也考虑年报、公告和原文证据；不能只有财务数值一条专线 |
| 数据不足 | 按既定确认流程补足；可通过 Wind 查询、已有资料加工或外部采集解决，不把“补数据”一律解释成巨潮重新下载 |
| 工程优先 | 不用演示专线、假数据、假引用、弱化验收或直接改数据库来换取表面跑通 |
| 实施分工 | Luna 开发与验收准备，Qwen 通过已有 Jenkins 流程发版 |
| 演示备用 | 固定专家实际通过后才冻结；后续共用软件发布仍须回归备用链路 |
| 长期架构 | 实际演示结束后按 K31 退役独立固定运行及临时兼容；固定顺序可表达为统一引擎中的完全约束计划 |

以上是已有决定，后续讨论以此为基础。若所有者修改其中一项，追加说明并同步原设计，不静默改写历史。

## 三、用户从哪里开始，最后得到什么

```text
用户提出问题
  ├─ 让 AI 找专家
  │     ↓
  │   判断该问题的方法需求，查询本人可请的真实专家
  │     ↓
  │   核对需求是否落在专家声明的方法范围内
  │     ├─ 能覆盖 → 直接请入符合条件的专家（沿用既定费用/授权规则）
  │     └─ 不能覆盖或无法确认 → 提示原因，由用户选出路
  │                              ├─ 提出孵化请求
  │                              ├─ 自己指定专家
  │                              ├─ 通用模型直接回答
  │                              └─ 结束
  └─ 用户直接指定专家 → 核对确切版本，说明适用范围与缺口
                              ↓
                   钉住专家版本，保留原问题与匹配依据
                              ↓
                   落实本次任务计划，准备授权数据
                              ↓
                    执行方法 → 验收 → 交付成果
```

方法需求匹配发生在请入之前。任务内部怎样组织工具、数据与方法执行，另在执行契约
中明确；不把先请入一位名称相近的专家、再发现方法不够当成匹配成功。

用户应当能看懂：为什么请这位专家、准备用哪些方法、为何需要这些数据、现在在等什么、最后交付了什么。

## 四、以方法范围决定能不能直接请入

### 4.1 问题的方法需求与专家声明相匹配

2026-11-03 所有者明确纠正：没有“两层”。AI 针对问题的方法需求落在专家声明的
方法范围内，才直接请这位专家；否则提示，并提供孵化、指定、直接回答等出路。
本条取代前稿“先选专家、再选方法”的两层表述。

AI 读取用户原问题及必要上下文，判断完成问题所需的方法能力；这份需求描述是
匹配依据，不是临时创建新方法，也不等于已冻结的执行计划。候选来自 knowmart
对当前用户可请的真实专家；匹配必须依据作者声明的方法范围、适用条件和边界。

名称相近、主题相关或只能覆盖问题的一部分，不足以直接请入。不能确认覆盖时也
要说明不确定处，不能先执行再把不适用包装成成功。方法范围的声明格式、与确切
方法版本的对应关系、匹配如何校验，尚待讨论；不据本条提前规定另一套技术实现。

选定后保留原问题、专家版本与匹配依据，不替换成固定演示题。费用、模型预算和
数据授权沿原规则，方法匹配成立不代表已取得额外付费或数据使用授权。

### 4.2 不满足匹配条件时的出路

先说明哪些方法需求没有被覆盖，或哪些条件无法确认，再提供用户选择：

- 提出孵化请求，让作者补齐或形成适合的专家；
- 用户自己指定专家，并看清其能力范围与缺口；
- 使用自己的通用模型直接回答，按普通对话规则继续；
- 结束本次请求，保留已有记录。

不自动替用户选其中一条。用户指定也不会自动扩展该专家的冻结方法或把未覆盖
部分判为通过；是否缩小问题等具体交互在问题 1 中继续讨论。

### 4.3 请入后的计划属于执行过程

专家依据原问题和作者既定方法组织任务、绑定输入和工具、准备数据并验收。
这不另构成一次独立的“选专家之后再看方法够不够”的决策层。

作者仍决定可用方法、必经约束、适用条件和验收标准；模型不能在运行中增造方法。
数据缺项、授权未就绪与方法能力不足需分清：补数据可解决的缺口走原数据流程，
不能用补采掩盖方法范围不覆盖的问题。

方法库、专家和任务的关系是：

```text
独立方法版本
    ↓ 作者选择、组合、明确使用条件
专家版本
    ↓ 用户问题进入该专家，模型按规则形成计划
任务计划与执行记录
    ↓ 读取授权数据、计算、验收
本次成果及可追溯证据
```

方法库不是 Codex 的 Skill 安装库。创意可以引用候选或已有方法，但进入正式专家前须完成作者接受、版本引用和装配核对。

## 六、接下来逐项讨论的问题

### 问题 1：提问入口怎样把“AI 找专家”真正接起来

**先讨论这一项。** 原需求已经确定支持 AI 找与用户指定；需要把实际页面行为核清：

- 用户进入哪个页面、在哪个输入框提问，怎样表达“让 AI 找”或“直接使用通用模型”？
- 现有“让 AI 找”是否要求另点按钮？默认输入问题走哪条通道？不能把本次讨论自行解释成“所有普通聊天都自动查商城”。
- 方法需求能够被专家声明范围覆盖时，怎样直接请入；有多个满足条件的专家时如何处理？
- 方法需求的表达、范围覆盖和无法判断的提示，怎样让用户看懂并可追查？
- 范围歧义、需要额外收费分别如何展示和继续？
- 不匹配时，孵化、指定、通用模型直接回答、结束等出口如何保留原问题；选择孵化后，怎样追踪请求并回到原问题？
- 用户明确指定专家但问题超出范围时，如何说明并让用户决定下一步？

讨论产物：一条从真实页面出发的交互流程及各分支例子。先核原第 4.9 节和代码，已有决定不重复要求用户选择；发现矛盾再明确裁决。

### 问题 2：首个动态专家采用哪些已接受的方法

- 20 项候选中哪些可供作者参考，哪些仍需实质修订？方法名称、出处与通过 Schema 校验都不能代替可实战验证。

### 问题 3：可选方法怎样进入最终报告

当前固定 2.8 的成稿依赖全部上游，依赖闭包是八步。仅把预测标成“非必选”，最终成稿仍会把它强制选回来。

- 必需和可选输入怎样由作者声明？
- 已选方法的成果怎样保证被最终交付消费，并绑定确切实例与版本？
- 未选方法、缺数据无法做、执行失败，怎样清楚区分？
- 调整计划后，旧成果哪些可以复用、哪些必须失效重做？

已有[装配提案](../../../../scripts/results/第二轨联调/2026-11-03-批量计算与动态装配准备/动态财务专家装配提案.md)仅供讨论。具体输入契约尚未定稿，不以删除依赖或隐式读对话历史绕过它。

### 问题 4：计划和数据准备如何相互配合

- 初始计划允许依靠哪些数据目录和供应商能力信息？何时才进行真实收费查询？
- 已有授权数据、已有原件但缺读法、可由 Wind 查询、必须外部采集，应如何分别处理？
- 结构化事实与年报原文怎样关联；某渠道只有文字或链接时，如何如实表达，避免冒充 PDF 页码证据？
- 数据不足时，是补数据、选择作者允许的其他方法、等待用户还是结束？不能由平台私自降验收要求。

讨论产物：按任务动态取得数据的流程与状态定义。Wind 服务端接入授权沿用，实际许可范围、数据授权、费用与额度边界继续明确记录。

### 问题 5：执行速度、费用和验收怎样兼顾

- 哪些计算能一次批量完成，哪些结果可在同一任务内复用？
- 哪些步骤需要模型判断，哪些由确定性代码执行，避免每个指标都重新推理一次？
- 如何显示当前实际进展、已花费用和等待原因，而不是仅显示“在跑”？
- 怎样区分格式错误、工程错误、数据缺项和方法结论不成立，避免无意义返工？

已完成的批量 compute 可以复用，但不能据此许诺动态任务必然很快。验收不降低，耗时和费用需从真实运行记录测量。

### 问题 6：测试、用户使用与演示怎样衔接

- 作者自测、平台人员测试和普通用户使用，分别显示在哪个入口、用谁的模型与数据、落在哪个工作区？
- knowlab 如何呈现完整测试过程，knowbench 如何隐藏测试项目但复用执行服务？沿 K29 实施，不另造测试引擎。
- 固定备用冻结哪些专家、软件与证据版本；第二轨发布如何回归它？
- 演示结束后，按 K31 删除哪些旧执行路径，怎样保留历史记录和统一引擎下的固定计划？

## 七、讨论完成后按什么顺序开发

以下是**建议顺序，尚待本轮讨论确认**。每一步先形成可核对结果，再进入下一步；发现依赖问题可明确调整顺序，不把编号当作不能修改的流程。

| 阶段 | 工作 | 本阶段交回什么 |
| --- | --- | --- |
| 1 | 核对原需求与当前提问入口，定 AI 找专家的实际交互 | 页面路径、匹配/选择/无匹配分支、原问题传递及验收例子 |
| 2 | 准备作者的方法与专家装配方案 | 方法版本、适用条件、必经约束、输入输出、工具与交付标准；明确作者接受记录 |
| 3 | 补通用计划和成果依赖机制 | 正式契约、生产者/消费者一致实现及正反例回归；不写财务演示分支 |
| 4 | 串起动态数据与执行链 | 已有数据、Wind、原文证据、补采、拒绝/等待/取消的真实记录 |
| 5 | 完成首条端到端真实验收 | 原问题→方法需求覆盖专家声明范围→直接请入真实专家→授权数据与执行→验收成果 |
| 6 | 换问题和主体验证，整合发布与演示 | 同一专家得到适当不同计划；固定备用回归；明确可演示范围和未完成项 |
| 7 | 实际演示结束后执行 K31 | 移除独立固定执行及临时兼容，统一引擎回归，历史仍可追溯 |

当前先讨论第 1 阶段。固定测试继续；不因为编写本文就启动额外付费测试、修改专家内容或变更正在运行的发布版本。

## 八、最终验收不能少的场景

| 场景 | 必须证明 |
| --- | --- |
| 用户只提问，没有选专家 | 明确问题的方法需求，核对真实专家声明范围能够覆盖后直接请入，保留依据并完成任务 |
| 名称相近但方法不覆盖，或无法判断覆盖 | 不直接请入，提示方法缺口或不确定处，不把部分匹配冒充完整覆盖 |
| 用户直接指定 | 使用指定确切版本；范围不符如实处理 |
| 多候选或额外收费 | 按已定交互交用户决定，不擅自购买 |
| 找不到能覆盖需求的专家 | 孵化、指定、通用模型直接回答、结束等出口可走，保留原问题，由用户选择 |
| 同一专家，问题不同 | 计划遵守作者规则，能省去不适用的方法，不强制全方法库运行 |
| 可选方法参与交付 | 选中的成果被消费、未选不伪造、缺项不冒充完成，引用版本正确 |
| 换公司、年份和资料来源 | 不修改运行代码，不依赖写死的茅台数据或本机文件 |
| Wind 数值与年报证据 | 实际权限、来源、版本、计算与引用可核；不支持的能力如实说明 |
| 工程异常和预算到限 | 明确失败或等待，费用可核，不空跑成稿、不偷偷继续收费 |
| 测试与普通任务 | 身份、入口、数据和工作区归属清楚；实现 K29 后测试不出现在普通用户任务列表 |
| 演示备用与后续清理 | 备用有实际通过证据；演示后单一引擎能执行确定计划和动态计划，旧历史保留 |

每个通过结论应能追到：用户问题 → 方法需求与范围匹配依据 → 专家及方法版本 → 任务计划 → 数据授权与版本 → 执行/验收 → 成果。
