## 一、总结论

1. **整体可实现，不需要引入新框架**；H 稿最核心的“薄草图 + 确定性展开器 `elaborate()`”是**全稿可行性最高**的部分——它依赖的约束全部是现有代码里的本地纯函数，可以先于一切 AI 工作独立交付。
2. **H 稿低估了三处硬阻塞**，按原写法排期会在 Stage 0 就卡住：
   - **阻塞 ①（最大）**：不只是“编排的叶子只能是 MCP”，而是**单个工具方法本身也只能是零模型轮次的 MCP**——`skill_instruction` / `skill_script` / `platform` 三种实现今天连测试都跑不了，因而无法冻结、无法进目录。H 稿的“Skill 封装成积木（路径 B）”“常规分析配 `skill_instruction`”“平台公式积木”都建立在这个不存在的能力上。
   - **阻塞 ②**：“平台基础积木对所有作者开放引用”不是改一下 `listing` 的事。KnowLab 依赖解析、KnowBench 目录准入、叶子 MCP 来源绑定**三处都按“本人 + 私有”硬校验**，跨所有者引用等于新建一套授权模型。
   - **阻塞 ③**：正式编排今天**只能在 KnowLab 测试单里跑**（`test_run_for_task` 已扩散到 4 个运行模块），KnowBench 普通会话尚无“用户任务里跑编排”的入口；H 稿第二、三段都压在这条还没修的路上。
3. **H 稿有两处按原写法不可行、需改设计**：
   - §3.1 “AI 在同一轮内发起一次目录二次检索确认”——`INCUBATE` 回合明确“不读文件、不跑命令、不调工具”，单轮内无法检索；
   - §4 “以拓扑就绪度动态图调度取代定长下标”——方向对，但并行调度与现有“一次只开一个叶子 Attempt”的账本模型冲突，**第一版应保留串行游标，只加 `skipped`**。
4. **建议重排阶段**：把“非 MCP 工具可执行 + 积木冷启动”从 Stage 0 的附属项提成独立前置；即时编排（第三段）推迟到剪枝分支稳定之后；`MemberRole` 与公开上架随 M3 契约窗口一起做（并按两类 `tool` / `expert` 收口）。

## 三、逐项论证

### 3.1 展开器：✅ 可行性最高，但 H 稿的草图结构不够“无损”

**为什么可行**——`elaborate()` 要推导的每一项，代码里都已有确定性的判定函数，展开器只是把“判定”改成“生成 + 判定”：

| 推导项 | 现有判定（源码事实） |
| :-- | :-- |
| 步骤输入输出槽 | `formal_method_compiler.py:110-144` `_step_interface`：输入键 ⊆ 候选输入、覆盖必填；`schema_` 与 `meaning` 逐字相等；输出必须是候选的原样输出 |
| 连线与依赖 | `formal_method.py:217-239` `Orchestration.valid`：`StepValue` 上游必须在 `depends_on`，两端 `schema_` / `meaning` 相等（“cannot perform an implicit business conversion”），可选输出不能满足必填输入 |
| 权限上界 | `formal_method_compiler.py:147-173` `_permission_ceiling`：父声明须逐条覆盖子需求（能力、版本、操作、去向、目的、资源角色） |
| 对外输入输出 | `formal_method.py:317-364` `interfaces()`：由 `CallerValue` 汇总，同名不同槽直接报错 |
| 限额 | `formal_method_plan.py:121-128`：按子树实际深度 / 展开数 / 步数核对 |

**H 稿需要补的四个工程细节**（不补会导致展开器在真实数据上不稳定）：

1. **空 `meaning` 不能参与自动连线。** `ValueSlot.meaning` 允许为空字典（`formal_method.py:49`，`max_length=20`，无最小长度）。两个 `{"type":"string"}` + `meaning={}` 的槽会互相“唯一匹配”，展开器会自动连出语义错误的线。规则应为：**仅当 `meaning` 非空且命中受控键时才自动连线，否则一律视为歧义交作者指定。**
2. **“可达上游”必须定义为清单中排在前面的步骤**，否则自动连线可能反向连出环。这与 H 稿“作者在清单排好顺序”一致，但要写进展开规则。
3. **`decompile` 要保留“非规范选择”，否则往返不等。** 真实 JSON 里存在：步骤只绑定了候选的部分可选输入、只暴露部分输出、作者手写了比子需求更宽的 `access_requirements`、限额留了余量、显式多写了纯顺序依赖。H 稿的 `SketchStep` 没有字段承载这些。建议草图增加 `bound_optional_inputs`、`exposed_outputs`、`access_overrides`、`limits` 四类“钉住项”；验收标准写成“`elaborate(decompile(o)).digest() == o.digest()`”，用全部已冻结编排做回归。
4. **派生权限的 `requirement_id` 必须稳定。** `ApprovalRule.requirement_id` 和 `ResourceValue.requirement_id` 都引用它（`formal_method.py:288-310`）；每次重新展开如果重新编号，作者写过的审批规则就会失效。建议按子需求内容哈希命名。

**放置位置**：KnowLab 域层纯函数，不调模型、不访问数据库。第二段要在 KnowBench 复用时，需加入 `scripts/export_formal_method.py` 的生成集合（KnowBench 的 `formal_method_plan_generated.py` 头部即“Generated by KnowLab scripts/export_formal_method.py; do not edit.”），并随契约锁一起升级。**第一版只在 KnowLab 使用，不碰 KnowBench，因而与 luna 当前 C2 工作零冲突，可最先开工。**

### 3.2 积木目录：本人方法 ✅；跨所有者引用 🔴，建议改为“官方定义导入、各自冻结”

- **本人方法投影可直接做**：冻结时的 `provenance` 已写入 `method_kind`、`interfaces`、`dependencies`、`allowed_callers`（`formal_methods.py:633-650`），投影就是读出来再裁剪。
- **跨所有者引用在三处被硬拦**：
  1. KnowLab 依赖解析 `_dependencies` 通过 `self.get(owner, …)` 取子方法（`formal_methods.py:360`），而 `get` 要求 `found.owner_subject == owner`（`formal_methods.py:85-89`）；
  2. KnowBench 目录准入要求方法属于本人且 `frozen.visibility == "private"`（`formal_method_catalog.py:358-373`，报错文案“This entry supports only the author's private methods”）；
  3. 叶子 MCP 来源要落到**调用者本人**的连接资产（`formal_method_catalog.py:500` `capability_asset(owner, source.asset_id)`）。
  
  所以“平台账号孵化的积木被作者 A 直接引用”需要回答：谁的连接去调 MCP、谁承担费用、平台方法升级时引用方怎么办、撤回如何传播——这是 M3 市场授权模型的范围，不适合压在 Stage 0。
- **建议的冷启动做法（现有代码即可支撑）**：`ImplementationRef` 本来就是“可移植来源，不含作者凭据或私有连接 ID”（`formal_method.py:92-100`）。平台发布的是**官方方法定义包**（含 `ValueSlot`、正反例测试集），作者一键导入成自己的工作稿，用自己的连接跑测试、冻结为本人私有版本。代价是每个作者各有一份 digest，但正好满足“真实验证后才可用”的现有原则；真正的跨所有者引用留给 M3。
- **`method_kind` 字段**应直接按两类 `Literal["tool", "expert"]` 设计（见 [advisor现在使用建议和以后改名.md](./advisor现在使用建议和以后改名.md) 第五节），H 稿 §3.1 仍写着三类，需同步。

### 3.3 非 MCP 工具执行：🟡，这是全稿真正的关键路径

**源码事实（比 H 稿描述更严）**：

- KnowLab 执行请求校验：`ToolProcedure` 只要 `implementation.kind != "mcp"` 或 `max_model_turns != 0` 就拒绝，文案“Execution supports direct MCP methods without internal model turns”（`formal_method_execution.py:286-297`）；编排则只允许 `host` 调用（同文件 `:300-301`）。
- KnowBench 执行侧：`direct_mcp_procedure` 同样只接受零轮 MCP（`domain/workbench/formal_execution.py:186-194`）；递归展开要求叶子为零轮 MCP（KnowLab `formal_method_plan.py:84-90`，KnowBench 生成副本同步）；递归准入要求“Sealed leaf has no MCP source”则拒（`formal_orchestration_admission.py:93`）。
- 契约本身允许四种实现并强制“只有 `skill_instruction` 可分配模型轮次”（`formal_method.py:95`、`:112-120`）；KnowBench 的来源扫描也已能产出 `skill_instruction` / `skill_script` 来源（`application/workbench/formal_methods.py:89-108`）。**即：能起草、能扫描，但不能测试、不能冻结。**

**结论**：H 稿 Stage 0 第 3 项“`FormalOrchestrationExecution` 合流 `TurnDriver`”顺序反了——必须先让**单个** `skill_instruction` 工具方法能跑测试、出回执、被冻结，编排叶子才有东西可接。

**为什么判定为可实现**：KnowBench 已有两块可复用的现成部件——
- `FormalModelExecution`（`formal_model_execution.py`，文档串“One real model turn proposing one approved direct candidate invocation”）已经在正式 Task 内打通“开模型轮次 → 用量记账 → 独立核对”的链路；
- 旧 `advisor` 的 `TurnDriver` 协议（`application/workbench/turn.py:52`）已支撑多轮、预算、确定性验收与返工。

**需要新增的工程量**（L）：无工具的隔离模型轮次（不得再调任何 MCP，否则叶子越界）、`max_model_turns` 计数、按 `outputs` 的 JSON Schema 解析结构化产物、模型费用入共同调用账、新的回执类别与完成器核对；以及 KnowLab ↔ KnowBench 执行请求 / 结果契约及锁文件升级。模型叶子不确定，测试需靠现有 `repetitions`（`formal_host_calls.py:219` 已校验）做多次重复。

**另外两种实现的建议**：
- `platform`（平台公式）：**不要另建平台函数执行器**，改为平台托管一个计算类 MCP 服务（CAGR、勾稽核验等），直接复用 MCP 路径——成本最低，且冷启动积木马上可用。
- `skill_script`：要在作者电脑上执行作者脚本，涉及沙箱与供应链安全，**建议推迟**，不进入本轮任何阶段的验收标准。

### 3.4 共享 `meaning` 词表：✅，但必须“只增不改”

- 门禁可只在 KnowLab 冻结服务层做（`meaning` 键不在词表即拒），**不需要改契约**。
- 硬约束：`meaning` 参与冻结 digest，且连线要求逐字相等。词表一旦改名或改单位写法，所有旧方法与新方法就再也连不上。因此词表必须**版本化、只追加**；改口径只能新增键并配口径转换工具方法，不能就地修改。
- 建议首批只规范通用维度（指标、单位、币种、期间、口径、主体），领域键按需追加。

### 3.5 孵化通道升级：🟡；“单轮内二次检索”🔴

**可行部分**：
- 拦截点明确：`knowbot_incubation.py:325-330` 遇 `body.formal_method` 直接报 `formal_method_requires_validation`；工作稿已有 `formal_method: FormalMethodDraft` 字段（`workdraft.py:356`），新增 `formal_sketch` 存草图即可。
- 草图格式错误的有界返工一次，可沿用宿主现有确定性验收 + 返工机制。

**H 稿未提的工程约束**：
1. **契约命名冲突**：KnowBench 已锁定 `knowlab/runtime-incubation/v2`（`contracts/knowlab-runtime-incubation-v2-lock.json`），H 稿提议的 `knowbot-incubation/v2` 极易与之混淆。孵化契约在两侧各有锁（`contracts/knowlab-incubation-lock.json`），升级必须双仓同步提交。建议新起名如 `knowbot-incubation-formal/v1`。
2. **`ProposalBundle` 不能复用现有 `Suggestion`**：`Suggestion` 是单格改动，且明令“不得触碰工程层”（`incubation.py:319-349`，`_engineering` 检查在 `:347-348`）。提议包需要新的 Handback 类型，而不是放宽旧校验。
3. **请求体积上限**：孵化请求上限 `MAX_REQUEST_BYTES = 1_000_000`（`incubation.py:51`），而单个 `ValueSlot.schema_` 允许到 64 KB（`formal_method.py:81-82`）。Top 20–50 个积木、每个多输入多输出，最坏情况会超限。目录投影应只给“`meaning` + 精简 schema 摘要 + schema digest”，完整 schema 由展开器在 KnowLab 侧补回。

**不可行部分**：H 稿 §3.1 第二层“首轮未命中时允许 AI 发起一次目录检索确认”。`INCUBATE` 方法正文明确“Read no files, run no commands, call no tools.”（`packs.py:404`），回合内模型没有检索手段；而另开一轮又违反“每轮都由作者点了才发、不自动续轮（钱是他的）”。**改法**：检索全部前移到 KnowLab 的确定性预处理（硬过滤 + 按 `meaning` / 关键词召回）；模型找不到就交回 `Gap(missing_method)` 附接口草案，由作者决定是否“扩大检索再来一轮”。

### 3.6 前端渐进式编辑器：✅，量大但无技术未知数

- 现状：`formal-method-editor.tsx` 731 行，导入入口为 `type="file"`（`:364`）；`knowlab-web-frontend/app/components` 下**没有任何文件出现 `meaning`**，即 `ValueSlot` 编辑界面完全空白——H 稿判断属实。
- 可行性要点：
  - `ValueSlot` 表单不要做成通用 JSON Schema 编辑器（成本高、小白不可用）。做**预设类型**（数值 + 单位 / 期间、表格、文本、枚举、文件引用）+ 词表下拉选 `meaning` + “原始 JSON”折叠兜底。
  - Diff 叠加依赖稳定步骤 ID——草图 `SketchStep.id` 已满足。
  - 只读拓扑图：步骤上限 100（`formal_method.py:191`），分层 SVG 自动排版足够，不需要画布库。
- 无后端阻塞，可与 3.1 并行，但**有用的 Diff 必须等 3.5 的提议包**，所以前端第一版先做“清单 + 展开器诊断 + 手工编辑 + 导入反解”。

### 3.7 方法模板 `T=(D,V,C)`：✅，不要新建运行时概念

代码里没有任何“模板 / 变量”实体。最省的实现是**把模板定义为“带空位的草图”**：`candidates=()` 的步骤即变量 `V`，步骤上的 `meaning` 约束即 `C`。展开器对空位报“待赋值”诊断，人工选或 AI 选都只是在填空位。这样模板不进入冻结契约、不影响运行时，只是 KnowLab 编辑层的数据。

### 3.8 第二段剪枝执行：🟡（XL），并行调度第一版 🔴

**前置 ①：用户任务通道。** `test_run_for_task` 绑定已从 H 稿写的一处扩散到 4 个模块：`formal_host_calls.py:164`、`formal_recursive_runtime.py:49`、`formal_model_execution.py:53`、`ledger.py:1057`；`formal_host_calls.py:164-173` 要求存在 `caller == "knowlab"` 的活动测试单才放行。KnowBench 普通会话目前只开放“用户手选已验证的直接工具方法”（见 `knowbench-app/CHECKPOINT.md` 2026-11-15 各段），C2 段落也写明“普通聊天/工作中的专家选用与计划确认……均未由本片开放”。因此需要一个与测试单并列的**正式用户任务来源**，并把上述 4 处改成“测试单或用户任务二选一”的统一校验。

**前置 ②：分支与 `skipped`。** 现有计划辅助函数全部按“全部必做”写死：`unique_plan` 拒绝 `max_replans != 0`、非 `fail`、非必做、多候选、`ResourceValue`（`formal_method_plan.py:160-179`）；`bind_step_inputs` 要求所有前驱都有已接受产物（`:254-255`）；`export_outputs` 要求产物恰好覆盖每一步（`:294`）。

**前置 ③：游标。** `leaf_nodes[index]` 定长下标在 KnowBench 有 9 处使用：`domain/workbench/formal_execution.py:153`、`formal_host.py:91,95,107`、`formal_recursive_runtime.py:256,368,420`、`formal_host_calls.py:301`、`formal_orchestration_execution.py:44`；任务的 `current_step` 是整数列（迁移 `20260924_0008_workbench.py:176`）。

**可行的收敛做法**：
- **第一版保持串行**：仍按稳定拓扑序逐叶推进，只为每个节点增加 `taken | skipped` 判定记录；跳过的生产者让下游按 `on_missing` 处理。这样游标、“一次只开一个叶子 Attempt”（`CHECKPOINT.md` C2 段“仅当前叶子操作开 Attempt”）和审批模型都不用动，改动集中在计划函数与验收器。
- **好消息**：C2 递归模式已把 Attempt 槽位改为路径哈希（`formal_execution.py:152-156`，`"node:" + digest(list(node.path))`），节点身份已不依赖全局下标，后续做 `Plan v2` 时能复用。
- **并行调度不进第一版**：并行意味着同一 Task 同时开多个 Attempt、审批并发、预算预留竞争，与现有账本锁序假设冲突，收益（缩短墙钟时间）不足以覆盖风险。
- **条件判定**：建议采用 H 稿决策 2 的推荐项——结构化谓词。需给 `MethodStep` 新增可选字段（例如受限的 JSON-Logic 子集，只能读对外输入与上游产物），这是契约变更：只影响新冻结版本的 digest，旧版本按“全部必做”继续运行。模型判定分支作为第二步再开。
- **跨仓成本**：计划函数在 KnowLab 编写、经导出脚本生成到 KnowBench 并有锁文件；每改一次都要双仓同步与全量回归。这部分应**等 luna 当前 C2 未提交改动落地后**再开工，否则必然冲突。

### 3.9 第三段即时编排：🟡（XL），建议推迟

- **授权并非新难题**：`method_authorization.py` 禁止直授可再委派（`:44-45`）、可委派须带 `resource_authority`（`:46`），实际子调用只拿“不可再委派、绑定唯一调用”的权限（`:174-177`）。现有体系本来就是“每个动作由本人分别批准”，H 稿的“叶子级授权确认单”与之相容，属于展示与汇总层工作。
- **真正的难点**：
  1. 临时根图没有 KnowLab 准入回执，而现有正式 Task 的身份是 `pack_source == FORMAL_SOURCE` + 快照 digest（`formal_execution.py:163-183`）。需要第三种任务来源（“用户自组计划”），并保证它**永远拿不到**正式专家资格。
  2. 叶子目录只能是用户本人私有、已验证的工具方法（见 3.2），积木少时即时编排的实际覆盖面很窄。
  3. `Plan v2` 重排依赖 3.8 的 `skipped` 与节点身份，必须排在其后。
- **建议**：对应 H 稿决策 1，**Stage 2 只做正式专家的剪枝与分支，不对用户开放即时自组**；即时编排在积木目录足够丰富后再开。

### 3.10 第四段回炉：🟡；派生分支 🔴

- 回传通道可复用：`IncubationRequestV1` 已有 `reference`（KnowBench 转来的问题申请携带用户模型的回答，`incubation.py:238-243`）与 `test_report` 字段，扩展携带“原方法引用 + 草图差异 + 缺口诊断”即可，属 M 级。
- “原作者新修订”“仅使用权者提需求 / 另起孵化”两条去向不依赖新授权，可做。
- “获准派生者”依赖市场许可模型，而正式方法目前没有任何派生许可概念（仅限私有，见 3.12），**本轮不可实现**，应在 H 稿中标为 M3 之后。

### 3.11 `MemberRole` 与隔离上下文：🟡

- 契约现无 `role` / `MemberRole`；`Strict` 模型拒绝多余字段，所以**任何阶段的草图或 AI 产物都不得提前输出角色字段**，否则直接校验失败。
- 按两类收口后，角色是 `expert` 内部的步骤属性，不再影响方法分类；`classify_dependencies` 的“直接引用两种以上专家即专家团”（`formal_method_compiler.py:36-39`）应随之删除。
- 隔离上下文（独立模型会话与目录）的实现我未在本轮核对 KnowBench 会话与线程的绑定方式，**工作量与风险待专项评估**，不在此给结论。

### 3.12 解除仅限私有：🟡，门禁在三处

H 稿只提到 KnowLab `formal_methods.py:619`。实际至少三处：
1. KnowLab 冻结：编排方法 `visibility != "private"` 即拒（`formal_methods.py:618-625`）；
2. KnowBench 目录准入：只认本人私有（`formal_method_catalog.py:372-373`）；
3. KnowMart 交付与目录：仍停在 `knowbot-delivery v1` / `knowmart/expert-directory/v2`，没有正式方法与 `method_kind`（见 advisor 文档第五节）。

三处必须在同一契约窗口一起改，单独放开任何一处都没有实际效果。

## 六、撇开工程可行性：方案设计需完善的方面

> 本节不讨论能否实现，只讨论 H 稿作为方案本身还缺什么。按对专家方法质量的影响排序。

### 6.1 决定专家方法质量的缺口（优先补）

1. **重结构，轻承诺与验收。**
   H 稿主要篇幅在步骤、连线与积木拼装上，但专家方法的价值在“承诺什么、怎么验收、哪里停下问人”。`promises`、`ValidationRule`、`ApprovalRule` 由谁起草、如何与步骤对应、小白作者如何填写测试期望答案，均未展开。
   **建议**：新增“承诺—验收—测试”一节，要求每条承诺明确落到哪些步骤的产出、用什么检查、由哪条测试覆盖，并在编辑器中以“承诺覆盖矩阵”展示未覆盖项。

2. **“允许变化”没有被定义清楚。**
   第二段剪枝建立在“基准图 + 允许变化”上，但变化目前只能靠 `candidates`、`required_when` 隐式表达。缺三样东西：
   - 可选步骤之间的组合约束（互斥、至少选一、相互依赖）；
   - 参数取值范围；
   - 每种变化下哪些承诺仍然成立（变化 → 承诺的映射）。
   **建议**：把“允许变化”作为作者显式声明的一等对象，第二段剪枝只能在该声明内取值；剪枝结果若使某条承诺失效，必须在计划确认页明示。

3. **缺少“业务判断确认点”。**
   `ApprovalRule` 只管权限类操作。专家流程真正需要停下问人的是业务判断（口径选 A 还是 B、异常值剔不剔、结论是否可对外）。
   **建议**：在编排中引入“人工确认步骤”作为正式节点：有输入、有选项、有默认与超时策略，可在测试中用固定答案回放，在执行记录中可追溯。

4. **AI 代劳过多，作者确认了什么不清楚。**
   “小白无感引导 + 提议包整包接受”容易产生作者并未实际审定、却由作者承担承诺与责任的专家。
   **建议**：定义“必须由人确认项”——口径、阈值、外部数据源、期望答案、关键判断点。这些项不得随整包一键接受，冻结前须逐项留下确认记录；其余结构性改动可整包接受。

### 6.2 治理机制缺口

5. **依赖升级的下游传播未设计。**
   编排钉死积木精确版本。积木出新版、被撤回或来源失效时，上层编排作者如何得知、是否批量重测、使用中的任务如何处理，H 稿只讲了“回炉”（下游 → 上游），没有“上游变化通知下游”。
   **建议**：增加依赖变化通知、受影响方法清单、一键用新版重跑测试并生成新修订的流程；撤回与来源失效沿用“阻止未执行动作、保留已完成事实”的既有原则。

6. **积木目录与词表的治理流程空白。**
   H 稿提出了需要平台基础积木与共享 `meaning` 词表，但未规定：谁可新增词表键、审批流程、重复积木如何合并、积木如何废弃、质量由谁背书、官方积木的维护承诺。
   **建议**：单列“目录与词表治理”章节，至少包括词表只追加的版本规则、新增键的申请与审批、积木的推荐 / 废弃状态及其在目录投影中的展示。

7. **跨作者内容进入模型上下文的安全问题。**
   目录投影会把其他作者撰写的 `purpose`、`applies_when` 等文本送入起草模型，存在提示注入风险。
   **建议**：规定投影文本的长度上限、字符与格式过滤，以及在模型输入中与指令的结构化隔离；积木描述只作为“数据”出现，不得作为指令。

### 6.3 体验与闭环缺口

8. **第二段缺少使用者视角。**
   H 稿第二段篇幅全在运行时改造，未描述用户剪枝时看到什么。
   **建议**：补“计划确认页”设计：本次选了哪些可选步骤与候选、相对基准改了什么、哪些承诺因此不再成立、预计费用与耗时、需要用户授权的操作清单。

9. **缺费用与耗时预估。**
   **建议**：作者冻结前、用户运行前均展示单次运行预估（模型轮次、费用区间、耗时）及预算在各步骤间的分配；测试运行积累的实际数据回填预估。

10. **最终交付形态未定义。**
    `exports` 是结构化 JSON，但用户需要的是报告、表格等成稿。
    **建议**：补“交付层”设计——从结构化产出到成稿的呈现方式；以及结论级溯源：每个结论可追溯到哪一步、哪个积木版本、哪份数据。金融等需证照类目对此有刚性要求。

11. **即时编排结果缺少轻量保存形态。**
    H 稿规定“想复用一律回炉”，对普通用户门槛过高。
    **建议**：增加“个人保存的自组计划”：明确不是正式专家、不可上架、不带专家承诺，但可以下次直接再跑；想变成正式方法时再走回炉。

### 6.4 与其他文档的一致性

12. **与已定口径对齐。**
    - **方法分类**：H 稿 `MethodCatalogEntry.method_kind` 仍为 `tool` / `expert` / `expert_team` 三类，应按 [advisor现在使用建议和以后改名.md](./advisor现在使用建议和以后改名.md) 第五节收口为 `tool` / `expert` 两类，“多角色协同”改为派生展示标签。
    - **常驻例程**：编排方法作为常驻例程（`Routine`）运行时，“上次写入产出区的成稿作为本次输入”如何在方法对外接口上声明，需补充。
    - **文档结构**：设计内容与带行号的现状核查混写，行号会随开发快速过时。建议把现状核查拆成附录并注明核查日期与提交号，正文只保留设计。
