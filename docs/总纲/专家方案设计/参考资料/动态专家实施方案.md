> 本项目分类更新（2026-11-14）：[方法主稿](../专家孵化方案/luna/方法、步骤、组合与模板.md)采用工具方法、专家方法、专家团方法三类，共用契约；专家与专家团共用编排。本文的竞品术语与历史材料保留原义，早期本项目映射不替代主稿，不能据此恢复独立团队契约。


> **2026-11-03 最新实施口径：创作回归用户与 AI。** 创意有三个可混用的起点：用户原创、从方法库挑选组合形成的 idea 模板、AI 提供的初稿；都由用户加工定型后孵化。需求侧由用户指定专家，或 AI 按市场中专家的能力声明合理选择，不以证明方法组合完全覆盖问题作为请入前提。使用中通过专家行为审批、执行反馈和用户纠偏补救匹配误差；无合适专家时由用户选择通用模式或提出孵化申请。
> 本口径覆盖本文此前“先推导完整方法需求、证明组合可行再匹配”和“先建设独立组合产品”的安排。固定或动态执行方式由用户与 AI 的创意确定，平台共用一套执行机制，不预设两类产品。
> 文件名沿用历史名称，“动态专家”不再表示平台预设的独立产品类别。本文是开发依据。方案确认不代表代码、作者资产或线上验收已经完成；第3节保留实际工程记录，原8步与20项候选不自动转为成熟方法。预算及活动任务授权继续有效，不由文档修改追加。
> 需求依据：[请专家与执行](../专家使用方案/opus/请专家与执行.md)、本轮所有者决定及[双轨交付计划](财务智能体双轨交付计划.md)。讨论历史见[动态专家开发](动态专家开发.md)，本文件承接实施，不另建完成账。

## 1. 实施目标、边界与完成定义

第一目标是长期可维护。创作方法、组织方法、决定专家如何响应问题的主体是用户与 AI；
平台提供创意加工、孵化、测试、版本发布和忠实执行的工具。方法库保存经过实践检验的
常用方法，挑选组合的直接产物是可编辑的 idea 模板，经过用户加工才能成为定型创意。
机械拼接不证明方法衔接合理，也不自动成为专家执行清单。

需求侧匹配按已发布专家的能力声明做合理选择，接受语义判断可能不准确。这是明确的
产品取舍：不要求在请入前推导完整算法、验证所有组合或取齐数据以证明一定能完成。
用户承担合理选择的不确定性和试用成本，通过行为审批、停止、调整、通用模式或孵化
申请纠偏；作者负责真实声明，平台负责权限、预算、忠实执行和如实记录，不能把平台
故障、明显违背声明的推荐或虚报成功归为用户的匹配风险。

本轮交付一位真实专家的完整使用闭环：

```text
用户原创 ──────────┐
方法库挑选组合 → idea模板 ├→ 同一创意稿 → 用户与AI加工 → 用户定型
AI提供初稿 ─────────┘                              ↓
                                    孵化准专家 → 测试/正式发布 → 能力声明

用户问题 → 自己指定专家 / AI按市场声明合理选择
                         ↓
本次委托：原问题、预期成果、条件、预算与需决定的事项
                         ↓
按专家定型规则形成执行安排 → 数据准备及必要确认
                         ↓
执行中的行为审批与纠偏 → 执行与验收
                         ↓
成果与局限、费用、实际执行记录 → 用户反馈 → 作者改进新版本

无合适专家 / 执行中发现不适合
             → 用户选择通用模式，或自己提出孵化申请
             → 可携带原题、条件、已有成果及仍获授权的数据引用
```

三种创意起点可混用、编辑和往返，不建立三套孵化服务。固定或动态只是作者创意决定的
执行方式：允许依问题选择方法时才选择，要求固定流程时照约定执行。平台只维护一套
编排、权限、预算、审批、验收、恢复和交付机制。

本轮不建设专家团、运行时任意跨专家拼接方法、独立组合商城或平台自创财务规则。
不把“20张卡”“模板列表”“计划通过Schema”当作业务闭环，也不把手选成功冒充AI选
专家已验。逐任务作者选择私有数据等原第二档需求保留在第15节。

固定财务专家保留供用户和AI选择；既有任务的包、数据、预算和验收不随开发改变。
K31在同一引擎等价迁移和回归通过后清理旧执行代码，演示结束不自动退役专家。

### 完成必须拿出的记录

1. 三种起点进入同一创意稿 → 加工与用户定型 → 准专家/发布版本及能力声明；零库引用有效。
2. 用户指定或只输入问题让AI选择 → 真实可请版本、声明依据与不确定项 → 本次委托；不伪造准确率或成功承诺。
3. 委托目标 → 专家允许的执行安排 → 实际行为与审批依据 → 数据授权、版本和供应状态。
4. 工具/计算收据 → 规则验收 → 交付成果与指纹；审批不替代结果验收。
5. 不适合、缺数据、平台故障分别处理；通用模式与孵化由用户选择，可保留已获成果而不扩大权限或预算。
6. 原问题、缩小后的范围、未满足项、费用和实践反馈都可追溯；反馈不自动改写专家或把方法晋为成熟。

| §4.9 | AI 使用用户模型，依据作者公开范围找专家；用户也可指定 | 记录声明依据和已知限制，按声明合理选择；不在匹配时证明方法组合或保证结果正确 |
| §4.9.2 | 找专家只读公开信息 | 公开能力说明与内部方法绑定分开，找专家阶段不读完整方法和私有数据 |
| §4.9.3 | 无额外专家费用可直接请；额外收费由用户选择 | 目录复核费用与可请性；模型费用仍受用户预算约束，“免费专家”不等于免费执行 |
| §4.9.4–7 | 无匹配可直接答或申请孵化；都不自动执行；公开需求另行确认 | 两条主要补救路径为通用模式和本人孵化申请；另可返回改题、重新指定或结束，故障不冒充无匹配 |
| §4.9 实施说明 | 后端复核候选与费用，网页在用户在场时请入 | 匹配依据从浏览器临时记录改成任务持久证据；重复提交不能重复建委托 |
| §5 | 方法可动态，作者数据选择是另一维度 | 创建何种执行方式归用户与AI；模板加工、声明选择和行为审批构成主线，数据仍独立授权 |

匹配识别用户目标、交付要求和明确约束即可；明确指定的方法不能忽略，AI也不能凭空规定唯一算法。依据声明合理选择不等于完整覆盖证明：没有已知冲突时可以在原授权下进入委托；关键歧义才澄清，实际数据和方法适用性在执行中核对并按审批机制处理。

### 3.3 按最新机制调整实施顺序与交付门

先把创意、声明、委托、行为审批和补救接起来；复用已有方法版本与执行器，不以完整
独立组合产品、全方法库或匹配精确证明为前置工程。

| 顺序 | 工作包与开发范围 | 可核交付 |
| --- | --- | --- |
| 1 创意基座与用户定型（G1/G2） | 原创、方法库挑选组合、AI初稿进入同一创意稿；保留来源、编辑差异、定型修订；原引用可解除为加工内容 | 三种起点及混合使用均可保存重开、修改、孵化；零引用有效，库升级不覆盖加工稿；组合模板不自动成为准专家 |

## 5. 作者侧：方法、专家能力和输入契约

### 5.1 三种创意基座进入同一加工与孵化流程

knowlab的创意入口提供“自己写”“从方法库组合”“请AI起草”，共享现有创意/工作稿
主档、作者权限、修订和定型操作，可随时混合使用。用户无需认识方法ID、选择执行
契约或先创建独立方法，才能表达自己的想法。

方法库选择器返回真实可用版本及适用说明，用户挑选、调整顺序后形成idea模板。
生成时保留素材来源及版本，检查已知的输入/输出冲突并提示缺项；不宣称机械组合
已有业务正确性。模板可增加、删除、改写方法、数据条件和交付要求，AI可协助补充，
最终由用户加工定型，再孵化准专家。只有明确选择原样复用的内容才沿不可变引用；
改写引用时生成作者派生内容及差异，不修改原方法，也不因引用锁而禁止编辑创意。

实际开发沿`idea-methods.tsx`、创意编辑/保存、AI起草和现有孵化服务：增加基座选择、
模板生成预览、来源/差异和定型修订；不新增模板运行器或强制组合管理后台。将来源
保存在本创意修订内，不另造第二份接受记录。重复生成、保存冲突与重放沿既有机制。

原8步、Skill、AI草稿与20项候选都可按真实状态供参考，不自动表示成熟或被作者接受。
成熟库与个人候选须区分。版本升级显式进行，原方法变化不覆盖加工稿、专家或历史任务；
运行引用禁止`latest`。零库引用、混合来源和修改后采用统一孵化、测试与执行。

### 5.2 公开能力与内部支撑对应

沿现有 `scope.does / does_not / elsewhere` 与已实现的 `public_capabilities[]` 整理作者确认的声明，随专家版本冻结：

| 字段 | 语义 |
| --- | --- |
| `id` | 本专家版本内稳定的能力标识，不是全平台方法分类码 |
| `statement` | 能完成的任务，如“历史营收与利润走势分析” |
| `conditions` | 适用条件与口径；只能写能力前提，不能要求公司预置在绑定里 |
| `exclusions` | 不覆盖的任务或方法 |
| `delivers` | 可交付成果说明，如带来源的数据表、Markdown 报告 |

声明由孵化过程根据定型创意、实际做法及交付整理，作者确认后随版本发布；测试记录可标注已验证的适用范围，但不能推导为所有同类问题都已验证。`conditions`应说明输入/数据条件，主要做法可以写进声明；不要求先取得本次数据才可入选。

与之配套的既有私有 `planning.capability_bindings` 将能力 ID 绑定到作者方法别名 `required_units` 和成果字段 `evidence_outputs`。每项绑定引用的单元、字段必须实际存在，已声明依赖需通过编译检查；这些内部绑定不出现在找专家目录，也不作为选择时证明问题完整可解的依据。

第一版采用明确的必需单元绑定，不引入任意布尔表达式、平台自建行业能力分类或评分权重。若用户与AI创作时允许不同算法按条件使用，可以在声明中说明；是否选用及如何调整由定型规则决定，平台不为所有专家预设必需的动态选择。

作者 UI 增加“公开给请专家者看”预览与“由哪些方法支持”绑定。生成文字只是建议，沿现有出处链接受后才能发布。保存做结构检查，发布沿既有测试、审核或正式特批流程，明确所验范围和未验事项；不新增要求作者证明所有问题都可匹配的发布门。结构一致性不冒充语义可靠性。

字段形状固定如下：`public_capabilities` 为 1–30 项数组；ID 沿现有方法标识字符规则，版本内唯一；`statement` 为非空文字，`conditions / exclusions / delivers` 为文字数组。`capability_bindings` 的键必须与公开能力 ID 完全一致；`required_units` 为非空且不重复的方法别名数组；`evidence_outputs` 为 `{method, field}` 数组，指向该能力能够产出的真实字段。字段长度和总载荷沿工作稿现有上限约束，契约生成测试覆盖上限拒绝。

例如仅表示结构、不作为正式财务资产：

```json
{
  "public_capabilities": [{
    "id": "historical_trend",
    "statement": "分析历史营业收入和归母净利润走势",
    "conditions": ["明确期间和可核对的报表口径"],
    "exclusions": ["本能力不包含未来预测"],
    "delivers": ["带来源的年度指标和分析报告"]
  }],
  "planning": {
    "capability_bindings": {
      "historical_trend": {
        "required_units": ["inventory", "reconcile", "indicators", "writeup"],
        "evidence_outputs": [
          {"method": "indicators", "field": "annual_metrics"},
          {"method": "writeup", "field": "report"}
        ]
      }
    }
  }
}
```

没有新公开能力字段的旧专家保留原 `scope`，不自动编造能力和内部支撑。目录标明其声明格式；匹配可引用原作者的 scope 文本作合理判断。关键歧义才澄清，一般不确定性可说明后进入委托，不因缺少内部方法映射就一律拒绝。旧固定任务仍由冻结的原方法执行，不能借目录升级把它改造成动态专家。

### 5.3 可选输入与最终报告

已有方法定义v2的可选输入机制继续保留，独立定义v3沿用明确的输入必需性。它们服务于定型创意的孵化编译与执行，不要求每个用户先配置槽位。原v1输入仍视为必需，不改写旧定义或摘要。

- 作者装配时仍将每个槽位绑定到本专家的上游别名；每个槽第一版只接一个实例，不引入任意聚合 DAG。
- 必需槽：计划必须选择上游并绑定确切实例；派发时绑定已验收成果版本。
- 可选槽：上游未选时，计划明确列 `omitted_inputs`，原因只能是 `not_selected`。上游已选时必须绑定，不能省略它的失败或不利结论。
- 可选不等于可忽略失败：选中后未通过的上游，不能以空值、未选或旧成果继续成稿。
- `covers` 等依赖可选槽的规则必须由作者显式声明 `when_input_present`；绑定存在就完整执行。普通 required/computed/quoted 规则不得被运行器擅自跳过。
- 未选槽向当前方法提供明确“本题未选”信息，不伪造空成果，也不允许从对话历史补入未绑定结果。

第一版保持 `planning.final_units` 表示**始终必需的最终交付方法**。财务专家以报告方法为最终交付，趋势、预测等作为显式可选输入。暂不增加“可选 final_units”的第二种语义：这已经可以解决当前成稿把八步全部拉回的问题。

计划中已选的分析成果必须沿绑定链进入至少一个最终交付；校验器拒绝与交付无关的孤立计算，及报告故意漏接已选上游的计划。

### 5.4 首位动态财务专家的具体装配

> **2026-11-03 方法边界复核：本节八步方案暂缓正式资产化。** 所有者指出这些单元
> 混合了工作流阶段与可复用方法。原接受记录与正文摘要保留，不改写历史；下表现在
> 只作为旧流程迁移和执行契约的工程样例，不能据此宣布正式方法库内容成立。重新设计
> 采用下方5.5的检查标准，内容修订完成后交作者整体核对。固定专家的独立特批发布继续。

采用已确认的财务专家方法作为整理起点，不整批导入 20 项候选。以下是需作者接受的新装配方案；旧 2.8 不就地改变。

| 单元 | 动态版职责及依赖 | 选择边界 |
| --- | --- | --- |
| scope | 确定公司、题定期间、指标、预测时点与交付要求；消费匹配/手选请求上下文 | 必经；不重复查市场，不重写用户问题 |
| inventory | 核实际授权数据、口径、期间和来源，消费 scope | 需要数据的分析必经；不得把需求清单当作已读到的事实 |
| reconcile | 原四条恒等式、原阈值与未核验项；消费 inventory | 财务分析能力的必需支撑；按本题用到的期间核验，不任意查全部库 |
| series | 累计转单季，绑定通过核验的数据链 | 需要单季或预测才选；资产负债表时点数不差分 |
| indicators | 题目要求的指标、计算收据与缺口；消费核验成果，series 为可选输入 | 历史指标能力必需；不把平台固定指标列表当作所有任务必须计算的清单 |
| official | 按目录定位管理层讨论，逐条保留上游结论，按已确认支持规则核对 | 作为公开的“管理层讨论对照”能力；是否每题必选由作者明确，不能擅自把旧第 6 步改为可跳过 |
| forecast | 原季节性同比、区间与四季回测，消费 reconcile、series 与所需指标 | 要求预测且方法适用才选；数据不足不能用替代算法冒充通过 |
| writeup | 消费本题已选分析成果，写报告文件与局限 | 必经；indicators/official/forecast 等输入按其作者声明绑定，未选章节不编结果 |

首版不扩入估值、评级、目标价或新的商业判断。人均创收等已存在用例所需计算，仍需在相应方法的适用范围、输出与容差中明示。新增能力、可选条件、对照步骤的选择边界与指标选择方式一起生成差异，作者一次核对，不拆成多轮零碎提问。

作者接受前，G1/G3 用合成方法验证机制，G2/G4/G5/G7 可继续开发；不能因为内容待接受就停止所有工程，也不能拿候选内容直接发布。

### 5.5 方法边界纠偏与内容准入检查

本次错误在于把“旧专家步骤可以独立冻结并接入运行器”当作“内容已经适合跨专家
复用”，让迁移便利先于业务边界。6/7/8步的合成计划通过，只证明引用、可选槽和
依赖校验，不能证明方法划分合理，更不能证明真实财务语义、速度或费用已验收。

方法不按名字专业程度或数量认定，也不追求每个公式一个模型轮次。可复用方法应能
独立回答：解决哪类问题、何时适用/不适用、必须给哪些事实和参数、采用哪套规则、
交付什么结果、缺项/异常怎样处理、怎样核验。数据转换、证据对照、报告编排也可能
成为方法；关键是有独立职责和可复用输入契约，不把“准备/成稿”一概搬入平台写死。

责任归属仍沿原架构：平台拥有鉴权、运行状态、数据供应协议、计费与工具执行机制；
作者拥有分析规则及口径、专家能力和方法选择约束；任务计划绑定本题范围、具体方法
实例、数据与交付。作者的方法需要何种数据由方法声明与本题决定，平台不硬编码
财务报表清单；方法输入不绑定某个专家名字或固定上游步骤。

以下是原8步/20候选作为可复用方法的内容审查要求，保留用于库内素材纠偏；不是每份
用户原创意都必须通过的成熟库准入，也不要求普通孵化先冻结所有内容为独立方法。
涉及正式财务示范的内容变更再形成作者核对稿：

1. 建原8步骤与20候选的逐项映射：独立方法、组合方法、专家规则、运行/交付机制，
   或仍不明确。每条记录当前代码/正文、真实输入、输出、必需依赖、待修问题；不是
   一次简单改名，也不预设最终必须8个或20个。
2. 先抽出原演示题所需的职责：期间/口径对齐、原四式核验、累计转单季、历史走势与
   增长计算、题定盈利指标、作者指定的季节性预测/回测、管理层讨论对照、成果组织。
   这是待设计的职责集合，不是已批准的新方法名单；是否组合及依赖范围逐项给依据。
3. 逐项对齐“文字承诺—输入—算法—输出—验收”。例如当前20方法夹具M12文字支持
   3/5年，输出与CAGR检查固定3年；M20固定要求勾稽、杜邦、偿债、收益质量和DCF。
   前者不能作为通用增长方法直接使用，后者最多是特定综合研报的编排方案，不能作为
   所有专家通用成稿。M13三表联动也不能替代作者已定的季节性同比预测。
4. 复用性工程门：同一冻结方法在两份不同专家装配中复用，方法正文/digest不变；
   上游替换为另一合法数据产物后仍可绑定；只问增长不引入无关估值，问预测具备
   该算法所需历史窗口与回测；缺数据与缺方法分开处理。
5. 交付完整的内容差异和正反例给作者确认，再正式生成独立版本。机制测试、数值/
   证据校验与真实模型财务验收分别报告，任何一项不能替代其余项。

现有方法版本、编译绑定、可选依赖、匹配收据、执行和验收代码继续复用；若新内容
揭示契约表达缺口，再提出最小契约修订，不预先发明一套新运行器。原8步的接受记录、
20方法合成夹具和历史测试保留原状；都不自动变成重新设计后的生产方法。

### 5.6 方法、模板组合与流程：服务创意加工的实现边界

**最新决定**：概念仍分清，产品入口收敛到用户与AI创作。同一创意可以来自原创、库内
方法组合模板、AI初稿或混合；本轮不先建设独立组合产品，再要求用户用它构造专家。
3.4的独立定义/执行策略代码继续复用，本节替代此前独立组合主档与版本服务的必做安排。

#### A. 概念与存储责任

| 对象 | 负责回答 | 实现方式 |
| --- | --- | --- |
| 方法 | 对什么输入、在什么条件下、按什么做法获得什么结果 | 可由人或AI原创，或参考库内确切版本；已存在的独立定义保存输入、做法、输出及验收 |
| 模板中的组合 | 为这个创意挑了哪些素材，如何衔接，有什么待加工之处 | 保存在同一创意稿内的来源、顺序、连接和参数意图；可编辑，不作为独立运行资产强制发布 |
| 专家的流程 | 定型后如何开始、选择做法、等待、审批、返工和交付 | 孵化成专家发布快照的执行规则；固定或按问题调整由作者与AI决定 |
| 本次任务 | 对这个问题实际做什么、使用哪些数据、批准了什么 | 复用现有委托、计划、数据绑定、Interaction/Approval和执行账 |

依赖校验、来源引用与版本追溯保留，但方法来源关系不等于不可编辑的创意内容。
原样复用可钉版本；修改后采用保留来源和差异，生成作者自己的定义。方法更新不自动
传播到已定型创意、专家或任务。需要复用整个模板时复制为新创意稿并留来源，不强制
引入递归组合、独立组合商城或组合运行服务。

#### B. 创建与执行边界

用户与AI在加工创意时决定服务范围、数据条件、采用的做法、是否允许按问题选择或
调整、哪些行为需要审批、怎样交付。平台检测已知结构冲突、记录接受修订并完成孵化；
不替作者补写财务公式或为了优化而改变关键规则。

任务中执行模型按已定型规则安排工作。用户审批可以同意本次已有规则允许的行为或
调整范围；它不能给当前专家凭空增加未有的能力，不能绕过数据权限和费用限额。确需
创造或改变专家方法的内容，回到创意加工及新版本流程；通用模式则按其自身规则执行。

固定安排直接构造计划；允许按问题选择时才调用规划模型。两者都编译到原Ledger、
Attempt、工具、验收和交付机制，不因本次产品调整再造一套运行器。

#### C. 输入与数据

方法输入描述它真正需要的字段、参数、口径和证据，不冻结某个旧步骤的完整输出。
创意稿可由用户/AI描述这些需求，孵化编译时处理必要连接、类型检查和受限字段映射。
同一产物多个字段的复用按真实用例补齐，不为了输入槽制造假步骤，也不把复杂映射
编辑器设为所有创意的必经页面。计算或业务口径转换必须有明确规则与证据。

数据主档和权限仍归knowbase，查询/加工/采集沿knowfeed；Wind与巨潮是来源。模板
携带数据需求，不携带前一个用户的运行授权；方法和流程的分离不替代数据维度，见5.7。

#### D. 代码改造与保留

| 位置 | 当前开发目标 | 明确不作为本轮前置 |
| --- | --- | --- |
| knowlab创意/工作稿、`idea-methods.tsx`与AI起草 | 三入口共享编辑稿；选取真实方法生成可加工模板，来源、差异、定型修订可见 | 独立组合后台、要求先冻结方法才能孵化原创专家 |
| knowlab `methods.py`、`atomic_methods.py`、`knowbot_methods.py` | 复用独立定义与版本；明确原样采用/修改后采用；成熟方法显示实践依据 | 自动把所有冻结方法收进成熟库 |
| knowlab `method_composition.py`、`compile.py` | 从用户定型创意及其素材来源生成自足专家快照，核真实依赖及执行政策 | 独立组合主档、递归组合发布链；不强制所有模板保持运行时库引用 |
| knowmart目录与knowbench匹配 | 提供确切版本的公开声明，按声明选择、给依据和已知限制 | 查看私有组合图、事前求解所有方法和数据是否联合可行 |
| knowbench委托/计划/审批/数据/运行 | 本次目标、行为及影响可审；沿原引擎执行、等待、拒绝、调整和恢复 | 逐指标人工审批、用审批替代结果验收、未经授权自动改方法 |

跨应用新语义由提供方确定契约版本及消费者锁；当前已发布定义和活动任务不改摘要。
模板编辑与源引用的持久字段优先复用现有工作稿JSON和出处链，若确需迁移走所属应用
单链迁移；不因文档有新名词就新建同名数据库服务。

#### E. 首个示范与开发门

用同一增长方法生成两份idea模板：一份只做历史增长，一份由作者加工加入原预测方法。
另做完全原创和AI初稿入口。核模板可改、源版本不变、原方法升级不覆盖加工稿；作者
定型后按各自实际规则孵化并声明能力。原四式、阈值、管理层讨论和预测口径沿已确认
内容，任何内容变更仍形成作者差异。

原8步骤继续作为历史迁移样例，20候选逐项审查并标真实成熟度，不以数量定完成。
工程先完成三入口与声明/审批/补救闭环，再对实际样例补输入绑定和数据条件；顺序见3.3。
真实财务数值、证据、模型行为与耗时另验，模板组合成功不等于专家质量已验收。

### 5.7 数据作为独立维度的补充方案

**状态：所有者要求补充数据维度，以下为与5.6配套的开发提案，尚未实现。** 数据不是
第四种方法，也不是流程里一次性的“取数步骤”。方法决定所需输入的含义，组合形成
输入依赖，流程管理取得与使用的关口，数据提供本次可授权、可核验、可追溯的事实。

#### A. 数据与另外三者怎样连接

| 对象 | 应持有的数据信息 | 不应承担 |
| --- | --- | --- |
| 方法 | 输入语义契约：所需字段、口径、期间/窗口规则、质量条件与证据要求 | 某家公司的一套数、写死的本机路径、某用户授权、默认供应商API参数 |
| 组合 | 把方法的逻辑输入接到组合输入或上游成果；汇总各节点所需数据及使用去向 | 重复抄数，假设每个方法都重新取一遍数据，静默统一冲突口径 |
| 流程 | 何时确认数据使用、补充、等待、重核与恢复；什么数据未就绪时阻止哪些节点 | 判断“有PDF就有结构化数据”，把已确认当成已取得，替用户默许新增费用 |
| 本次数据绑定 | 已授权来源、内容/读法/查询版本、事实或证据引用，与方法输入槽的明确对应 | 改写作者输入要求，凭数值相同视为同一事实，把旧授权永久固化 |

专家可以有作者自带的数据引用和允许的来源限制，但它们是可选的数据配置，不应
成为方法正文中固定公司/年份的逻辑。自带资料、用户上传、已有授权知识库资料、
Wind查询与公开披露采集最终都必须满足同一个输入契约及本次权限检查。

#### B. 区分逻辑需求、供应结果和实际绑定

需要三个明确的记录，优先扩展已有结构，不再造第二个数据主档：

1. **逻辑数据需求**：由作者方法冻结输入要求，本题再填主体、题定期间、预测时点等。
   记录哪些方法槽位需要它、必需程度、原文/表格/页码等证据要求。不能只记“取若干年报”。
2. **需求解析与供应计划**：knowbench汇总本题已选方法需求，knowbase核本人可用数据，
   knowfeed提供真实查询/采集/加工能力与作业回执；保留已确认修订、来源候选和费用信息。
3. **执行数据绑定**：将槽位绑定确切数据/读法/事实版本和证据地址；记录绑定修订与
   当时采用的口径。每次读取仍核授权，冻结数据快照不等于冻结永久访问权。

云端原件与事实以knowbase为主档；knowbench只持授权引用、任务内计算收据及有效
方法成果。本地资料仍按本人授权的文件通道读取，记录内容指纹和实际读取证据；路径
不是版本，文件变化须重新核绑定，不因引入本方案就默认上传全部本地资料。
方法输出不自动成为全库公开事实，需按既有产出入库和权利流程另行登记。跨专家复用
时不能顺带复制前一个用户的私有数据授权。

#### C. 输入合格不止是字段和数字

财务示范采用领域输入配置，不能把这些财务字段强塞给所有领域的方法：

- 主体与指标含义；营业收入/营业总收入、归母净利润/净利润等不同科目不能混用。
- 报告起止期间与时点，累计/单季/年度/时点数；预测基准日与当时可获得的信息边界。
- 合并或母公司范围、币种和单位、人数等指标的统计口径。
- 报告/事实版本及原披露或重述政策；同值不代表同口径、同版本。
- 原始来源、技术加工与业务推导路径，以及对应方法版本和compute收据。
- 所需证据形态：可计算事实、原文引文、PDF页码、表格单元格、供应商查询响应等。

回测尤其要区分报告期、披露/可获得时间和修订版本；不把后来取得的重述值无标记地
回填为当时已知事实。作者若允许事后重述口径回测，必须明示该口径和局限。

技术单位转换、已核词表映射沿knowbase现有版本化标准化机制复用；扣非调整、单季
差分、会计重述政策等分析处理由作者方法规定。两者都留派生依据，不能在输入绑定
阶段悄悄做业务转换。数据加工质量检查的阈值也不能替代专家方法的验收阈值。

#### D. 不能再把补数据一律叫采集

| 实际情况 | 处理路径 | 可以怎样显示 |
| --- | --- | --- |
| 已授权且所需事实/原文读法就绪 | 核输入语义后钉版本并复用 | 已有，可使用；标用途与版本 |
| 原件已有，但缺text/table/pages等所需读法 | 走现有加工能力；记录真实加工任务 | 原件已有，正在加工/加工失败 |
| 可由Wind等供应商查询满足 | 沿source_query和本人确认，查询后按许可范围保存响应及标准化引用 | 待确认查询/查询中/已取得/额度或授权失败 |
| 所需原文尚未入库，可由公开披露等取得 | knowfeed采集原件并加工，交付knowbase | 待确认采集/采集中/交付失败 |
| 来源存在但本人未获授权 | 显式取得授权或由用户提供其他可用数据 | 尚未授权；不能报成不存在或已可读 |
| 来源不支持、口径未明或多源冲突 | 澄清、由用户选择或报告缺口 | 不可取得/口径待定/来源冲突；不能无限“正在取” |

这些是对真实供给状态的展示要求，不另起一套Task状态。只有存在对应的活跃作业
或可追踪请求，才可显示正在处理。确认记录只证明用户同意，不证明后台已派单、
仍在运行或已成功。失败、未知结果和迟到回执沿既有幂等与对账处理，不自动重复计费查询。

Wind能交回数值并不证明它交付了原报告或PDF页码。某方法要求管理层讨论原文时，
必须有真实原文证据；链接、新闻摘要不能冒充原文。满足原文条件的合法渠道可用，
不强制所有输入来自同一供应商，也不静默混合互相矛盾的数据版本。

#### E. 计划与数据双向约束，但不能互相冒充

执行闭环调整为：题目与专家能力匹配 → 形成受作者约束的初始方法组合 → 展开本题
数据需求 → 核已有数据/授权/供应能力 → 确认必要变化 → 绑定就绪数据 → 执行与验收。
初始计划尚未取齐数据也可以保存，但不能把它当成所有节点已可执行。

数据反馈允许调整计划的未执行部分，仍复用现有重规划次数和有效前缀保护：

- 缺数据但可补：保留所需方法，等待补齐其输入；不因为暂时没数就判断专家不会做。
- 有作者允许的替代方法：先核其适用性与是否仍满足用户要求，再形成可追溯计划修订。
- 用户指定算法/必要验收无法满足：不能为了成稿换算法或删回测；按流程澄清、等待或结束。
- 方法不覆盖问题：补数据不能补出不存在的方法，回到缺能力的分流。

聚合需求以主体、期间、口径、版本政策、读法及授权范围兼容为条件，不只按文件名
去重。同一份年报的表格与分页原文可以共用原件，但分别记录读法就绪程度和使用目的。
已选方法的需求一次汇总、允许时批量查询/计算；不能每个指标独立重复付费取数。

例：CAGR计算方法需要同口径端点与实际间隔；完整年度走势需要各年序列；预测方法
还会要求作者规定的单季窗口和回测数据。其他必经核验方法的额外数据也须合并列明。
只问历史增长不应因模板写死而取未来季度或跑DCF；是否需要额外核验由该专家的
公开承诺、组合与流程决定，不能由平台悄悄加上或模型自行省去。

#### F. 数据变化后的有效性

任务成果需能追到：方法版本、组合/计划修订、输入绑定修订、实际使用的事实与读法
版本、参数、验收和计算收据。换资料、补加工、采用重述版本、修改预测基准或口径，
都先形成新的数据绑定修订，不覆盖历史。

按实际消费关系把受影响成果及其下游标为失效，再受控重算；无关且证据仍有效的
成果保留。授权撤回先阻止后续读取/使用，保留依法允许留存的审计信息，不因有缓存
继续执行。旧报告保持原版本可追溯，不无声更新为另一套数。

第一版只在同一任务内复用确切输入签名相同且验收有效的成果；不新增跨用户计算
缓存。后续跨任务复用必须另核授权、版本、方法参数和新任务的适用性。

#### G. 现有代码缺口和实施增量

已核事实：`knowbase/interfaces/schemas/data_request.py`的`caliber`及
`domain/user_resolution.py`的口径字段当前只展示、不参与资料匹配；它是材料需求
契约，不是完整的方法事实输入契约。`domain/user_facts.py`已有期间类型、合并范围、
币种、来源行与标准化规则，必须复用，不能另造一份科目表或事实主档。

| 位置 | 新工作 | 不重复建设 |
| --- | --- | --- |
| knowlab方法定义与组合编译 | 方法输入显式声明语义、数据窗口、证据要求；组合对外输入及需求使用去向可核 | 不把任务具体公司/数据ID固化到通用方法；自带数据配置另存 |

其它领域不用被迫填财务字段。跨应用由对应提供方生成新契约和锁，不向旧extra=forbid

数据修订只失效相关成果、撤权后缓存不绕行、缺数据与缺方法走不同出口、回测不静默
用未来披露版本。以上通过才称输入链可用，不以“下载了文件”代替数据维度验收。

### 5.8 创意是方法来源，方法库是实践沉淀，装配服务于创意

**所有者明确的原则**：方法本质上由人和AI提供，创意（idea）就是作者提出的方法；
方法应尽量原子化。方法库保存历史和生产实践中经过检验、可反复使用的常用方法。
装配是人借助这些方法更好实现自己的创意，不是从一个封闭方法清单里拼出专家。

此前把“人和AI提供方法”解释为“谁批准使用方法库”答偏了。来源、组织形态、实践
成熟度、执行授权是不同问题，不能拿审批或运行限制替代对方法本身的定义。

#### A. 创意到专家与方法沉淀的关系

主线为：用户原创 / 从库挑选组合形成idea模板 / AI初稿（可混用）→ 同一创意稿中
人与AI加工、明确流程和数据要求 → 用户定型 → 孵化准专家、测试发布 → 执行与改进。
实践中证明常用且可复用的原子方法，再由有权作者整理、记录实践依据并沉淀入库，
供后续创意参考。不是所有创意都要入库，也不是所有专家都必须引用库内方法。

原子化是职责划分原则：一个方法解决一个明确、可独立解释和验证的问题，具有清楚
的输入、做法、输出与适用边界。不能把一个完整创意硬认成一个原子，也不能机械地
按一句提示词、一条算式或一个模型调用拆分。创意可以包含多个方法及其组合意图；
原始创意保留，提炼后的定义与组合应能追溯它在实现原意中的作用。

#### B. 采用方式与版本不能混淆

- 直接复用成熟方法：引用确切版本，保留来源、适用边界和实践依据。
- 修改成熟方法：保留来源引用与差异，形成新的定义；原方法的实践记录不自动证明
  修改版成熟，不继承未做过的验证结论。
- 原创方法：从创意直接形成可执行定义，不强制引用库中ID或虚构成熟度。

三者统一编译和执行，不建立“库内”和“原创”两套运行器。专家发布所需的确切方法
定义/摘要与成熟方法库的收录资格分开；冻结只证明版本确定，工程测试只证明所测
性质，真实实践记录才支持相应适用范围内的成熟判断。合成20方法不能因已有列表、
冻结版本或探针通过就显示为经过生产检验的常用方法。

#### C. 对开发方案的具体约束

1. 创意编辑、孵化与编译必须支持零方法库引用；同时支持自有方法与库内引用混合。
   输入槽、数据语义、组合与流程校验一致，不能把“来自库”当成免检依据。
2. 方法存储复用现有主档/版本机制，但区分具体定义、来源关系、实践依据和是否收录。
   不为每个创意强制创建公共条目；成熟方法的可见与使用范围仍服从作者权利。
3. 方法库挑选组合可以先形成idea模板，再由用户与AI补充目标、适用条件和修改内容；
   同一编辑器允许从原创或AI初稿起步，三种来源可混用，不能强制先填完创意才准选模板。
4. 找专家仍核该已发布专家实际承诺的能力；库里缺少某方法不能否定原创专家能力，
   库里存在某方法也不能冒充某专家已经采用。执行版本边界不否定后续创作新方法。
5. 实践反馈可以产生方法改进稿和入库建议，不自动改写原创意、专家版本、历史结果，
   也不自动公开用户数据。数据证据与授权继续按5.7处理。

验收至少覆盖：不引用方法库也能完成孵化与执行；混合原创和成熟引用；修改引用保留
原版及差异；未验证内容不冒充成熟方法；方法沉淀后被另一创意复用且不带走原用户
数据；方法数量不决定模型轮次。这些是开发验收要求；已做代码事实见3.4/3.5，模板加工已实现但完整业务验收仍待完成，生产资产不因文档更新而改变。

### 5.9 创作回归用户与AI，匹配不承担再次设计专家

作者侧由用户与AI从三种基座形成创意，孵化时把服务声明与实际规则对齐。需求侧用户
可以指定专家，或让AI根据市场中的声明选择。平台不在匹配阶段重新设计一套方法，
不要求公开声明附带内部组合图，也不以“证明一定能完成”作为启动任务的前提。

这是可操作性与准确性的明确取舍。合理匹配仍可能选错，专家也可能到执行时才发现
不适用；用户承担这部分选择不确定性和实际试用成本。不得因此忽略已知的明确排除
条件、删除用户指定方法、伪造覆盖或宣称保证成功。作者承担声明真实性，平台承担
忠实执行、权限预算控制、故障处理与如实报告，不把这些责任转嫁给用户。

完整机制为：**声明匹配 → 本次委托 → 行为审批与执行 → 反馈纠偏 → 必要时通用模式
或本人孵化申请**。行为审批是使用中的补救，按实际影响设置，非逐个内部计算确认。
用户批准行为不等于验收正确；自动测试通过也不证明专家适用于所有同类问题。

原问题、显式方法/口径和交付约束沿原记录传递；AI可以概括目标和指出关键歧义，
不强制输出完整方法需求、联合可行方案及全数据计划。建议有来源但不成为未授权义务。
选择成功后按专家定型规则展开任务，数据不足仍走数据准备，不自动判为没有专家。

无合适专家时的两条主要补救路径是由用户选择通用模式、或由用户提出孵化申请。
返回改题、重新指定和结束属于始终可用的操作；不静默转通用模式、不自动申请或公开
需求。执行中发现不适合也复用这两条路径，并在原授权范围内转交已完成的工作。

参考原[专家孵化方案](../专家孵化方案/opus/专家孵化方案.md)和[请专家与执行](../专家使用方案/opus/请专家与执行.md)的
身份、来源、计费及发布规则；最新产品取舍以本节为准。原供需分析v3等工程记录保留，
按3.4收简其新使用语义，不伪造旧收据。

## 6. 用户入口与找专家的可执行设计

### 6.1 一个入口组件，两种请法

首页“专家”模式与项目“请专家”共用问题输入和请法组件：先写问题，点击“ai去knowmart请回专家”，或通过“自己去knowmart请专家”到市场选择。去掉“自己指定”切换按钮；两种入口请回的专家都在同一列表高亮，用户提交问题才启动分析。首页尚无项目时沿现有项目选择/创建流程，不另创项目体系；从商城返回保留专家确切版本、原问题和项目。

找专家不要求先选专家。空问题、沙箱未就绪、项目占用等禁用原因直接显示在按钮附近，不能只放 `title`。浏览商城、读历史不要求本机重新配对；执行按所选项目电脑与当前用户的既有通道判定，不能把浏览器所在电脑等同执行电脑。

普通聊天继续是普通聊天，不将每句话偷偷转为付费找专家任务。用户进入专家模式并点击“ai去knowmart请回专家”，才发起查找。查找成功不自动开始分析。

每位专家旁提供“删除”，只移除本人工作台列表项，服务端按账号保存。已选专家被删除时清空选中，保留问题和项目；刷新后不重新出现。从市场再次请回恢复列表。市场专家包、已有任务与报告不删除，其他账号不受影响。

### 6.2 按声明合理选择并保留收据

继续使用内部FIND_EXPERT任务、用户沙箱及用户模型。3.4所列v3实现保留历史兼容，
新判断流程收简为问题目标/明确约束与公开声明的合理对应；提供方先审查现有严格校验，
若新语义不兼容则修订契约及消费锁，不通过伪造covered或补一套虚假方案适配旧接口。

| 收据内容 | 用途与边界 |
| --- | --- |
| 原问题、修订与明确要求 | 保留用户目标、指定方法、交付、范围等；概括不能替换或漏掉原文，不强制推导完整方法需求 |
| 专家ID、确切版本与声明依据 | 指向真实可请目录及作者声明，说明为何认为适合；不读取私有方法或证明内部组合可行 |
| 已知限制与待澄清项 | 明确冲突不能掩盖；影响选择的关键歧义才澄清，一般语义不确定性允许说明后试用 |
| 选择结果与费用 | 沿现有summon/candidates/none/clarify或其兼容投影，区分合理入选、需选择、无合适及关键澄清；不增加Task状态 |
| 目录和服务核验 | 保留目录版本/完整性、可请性、授权及价格的检查，不把模型判断当执行授权 |

如保留`requirements/coverage/solution`供旧结果展示，其含义仅按原版本读取；新UI
不能把“covered”展示为结果保证。执行计划来源是委托及专家规则，不是匹配器临时设计
的方法方案。匹配测试核已知冲突、遗漏及解释质量，不设全语义100%覆盖的工程门。

目录不完整、分页截断或服务不可用时明确说明“未完成查找”；不能说“市场没有专家”。
已读到的真实候选可展示给用户另行指定，但不伪装为全市场最佳选择。首版沿现有目录，
不为此新增向量服务、商业排序或第二个Agent。容量不足时提示缩小查找/手选。

后端确定性核身份、版本、声明引用真实性、可请性、授权、价格和幂等，不尝试证明
业务可解性。目录文本是业务内容，不是可执行指令，不能改变工具权限、预算或平台规则。

### 6.3 结果与用户动作

| 结果 | 行为 |
| --- | --- |
| 根据声明合理适合，且在既有请入及费用授权内 | 请回并高亮，展示声明依据与已知限制；用户提交问题才创建分析委托，不新增逐方法证明/确认 |
| 多位都合理适合 | AI选择一位并给理由，允许用户更换；不宣称最优或保证成功 |
| 有适合者，但有额外专家费用 | 展示候选和价格，由用户选择并走现有交易授权；模型与数据费用仍单列 |
| 声明明确排除用户必需的任务/算法，或已知只支持部分目标 | 不伪装完整适合并自动请入；说明差异，用户可调整目标、另指定或走两条补救路径 |
| 存在影响选择的关键歧义 | 简短澄清，保留问题修订；未答不当同意，不为一般不确定性反复阻塞 |
| 没有合理合适的专家 | 提供“通用模式”“提出孵化申请”；均由用户选择，另可改题、手选或结束 |
| 目录或模型服务故障 | 报工程错误、已有费用与重试方式；不当成无匹配，也不自动计费重试 |

“自己去knowmart请专家”请回市场确切版本并高亮，用户提交后进入委托，不额外跑一次全目录匹配或要求证明覆盖。
执行中依专家规则核范围，发现实际不适合再说明、审批调整或分流；手选不能绕过权限、
费用和专家明示的不可执行边界。匹配误差允许存在，错误结果不得冒充成功。

### 6.4 从匹配到委托的事务边界

匹配 Artifact 保存原问题摘要、目录公开快照/摘要、模型结果及后端核验结果。委托请求带匹配任务/收据版本与幂等键；后端重核当前用户、项目、问题修订、专家版本/摘要与授权，不能接受前端自己拼的覆盖结果。

相同请求重放返回同一委托；异载荷同键拒绝。匹配结束与正式委托之间如项目被占用，显示已有任务，不绕过占用锁。用户更换专家、改问题或价格/可请状态改变时重新核相关版本、声明依据和授权；必要时重做选择判断，不能把每次变化都扩大为全方法证明，也不能复用已失效收据。页面刷新只恢复记录，不再次自动发起模型调用或重复购买。

接口沿现有查找、取结果、委托、直接答和孵化路由扩展，不新建平行控制面。G4 的请求/响应必须包含 `match_task_id`、`match_artifact_version`、`question_revision`、确切专家版本及幂等请求 ID；由服务端从收据恢复实际问题和授权对象。查找返回故障时使用工程错误；旧收据、版本变化或项目冲突使用可识别冲突码，前端重新呈现原因，不循环重试。访问不存在和无权对象沿现有防枚举行为。

### 6.5 本次委托：给执行和纠偏一个共同依据

复用原委托输入、TaskRequirements、版本和关联，不新增第二个委托主档。保存：原问题
及修订、选定专家版本、预期成果、已明确条件和关键假设、费用上限、需用户决定的事项。
已有用户表达和授权直接沿用，不把查看摘要增加成每次必点的新审批。只在关键歧义、
新增费用或权限变化时请求相应决定。

匹配理由可以辅助说明，但不能替代用户目标；缺数据先列待备条件，不给“已就绪”的
假结论。执行后发现需求须缩小或假设须改变时，形成委托修订并绑定用户决定，保留原
目标及未满足项。作者方法变化须回孵化版本流程，本次审批不能暗改已发布专家。

## 7. 任务规划、执行与交付

### 7.1 计划输入与校验

初始执行安排读取本次委托、原问题及修订、专家已定型的执行规则、冻结方法和能力绑定、预算与次数边界及已授权数据元信息。找专家只读声明；请入后才展开具体做法。固定安排不额外调用规划模型，作者允许按题选择时才规划。

沿已有 `knowbench/method-plan/v2` 的实例、工具、输入、最终成果、可选槽及未选理由机制。用户明确要求映射到成果；AI推导建议不自动成为必须执行的方法。槽名与专家别名分开。已声明为动态但计划实际固定的专家也按作者规则处理，平台不强迫为展示动态而改变计划。

在原 `validate_plan` 扩展确定性校验：

1. 只能引用任务冻结目录中的方法，不能读全库选新版。
2. 对已承接的明确要求记录执行成果去向，相关必需单元和依赖存在；发现无法承接时产生明确不适合/调整路径，不编造覆盖以通过校验。
3. 输入类型、顺序、实例与结果版本正确；无循环、悬空、文件冲突或孤立成果。
4. 必经单元、最大调用数、工具子集、最终成果和规划次数不被放宽。
5. 可选槽符合第 5.3 节；不允许拿“未选”掩盖失败。
6. 重规划保留已开始前缀；被返工失效的成果不能继续使用。所有新计划有父版本与调整原因。

实际适用性由执行模型依据专家规则与本次数据继续判断；代码验证真实引用、依赖、权限和可执行性。计划检查是已选执行安排的工程门，不倒推为匹配阶段的准确性证明，也不凭关键词在后端自创财务选择器。

### 7.2 计划与数据的先后

保留现有 Advisor 的“先形成计划，再定本次数据”顺序。初始计划不假定资料已经存在，也不为了选方法先付费取数。定数据轮只按已选方法及用户问题提出必要数据；作者所有可用方法不等于全部取数范围。

数据发现之后，如需要改用作者已经允许的其他方法，可在边界申请有限次重规划。改变证据要求、用户指定方法或交付范围时必须明确告知并取得对应决定；新数据仍需新确认，不能随重规划自动扩大授权。

完全确定的计划由作者约束直接构造并经过同一个校验器，不为固定顺序额外调用规划模型。这是 K31 后保留固定行为的方式。

### 7.3 执行效率

- 同一方法需要的多期事实批量查询；批量 compute 使用现有实现的 1–50 项请求及同批前向引用约束。
- 查询、公式计算、结果复用由确定性工具完成，不为每个指标创建独立模型任务。
- 计算收据仍逐项保存，批处理不能抹掉每个结果的输入、公式、单位和来源。
- 方法间按当前线性计划执行，不为演示速度临时引入多 Agent 并发。
- 同任务、相同输入版本/表达式/舍入规则允许复用既有已验收计算；跨任务不复用他人数据或授权。
- 每步提供实际工具调用数、已读取期间数、最近活动、模型费用与等待原因；没有足够样本不编 ETA。

### 7.4 成功与不完整交付

完整成功必须同时满足请求中的必要要求、作者必需验收、有效最终成果与文件交付验证。部分成果可以保存、下载，并列清缺口，但不能计为完整成功。

不新增 `PARTIAL_SUCCESS` Task 状态：沿现有合法状态转换记录结果与原因。用户选择缩小任务时产生明确的要求修订，再按修订验收；保留原请求未满足项。没有缩小请求而必要项无法完成，则在受理校验阶段按既有 REJECTED 路径拒绝，已执行的任务按 FAILED 路径收尾并保留部分产物；不得从 RUNNING 直接跳到没有合法边的 REJECTED。

### 7.5 专家行为审批：执行中的纠偏点

复用既有Interaction/Approval、作者的`ask_before`、工具权限、数据确认和费用机制。
审批按影响设置，沿用户既有授权自动执行常规分析/查询/计算，不逐指标弹窗，不新建
平行审批服务。不同审批点各司其职，同一行为不重复收集相同同意。

| 行为 | 处理方式 |
| --- | --- |
| 已授权范围、预算内的分析和工具操作 | 按专家规则自动执行并留记录；作者另有明确审阅要求的遵守其规则 |
| 新数据范围、补取/查询费用或新的外部使用授权 | 展示数据用途、取得方式、费用和范围，复用数据/交易确认；无新增变化不再说“去取” |
| 改变关键假设、必要交付、用户指定方法或分析范围 | 展示原约定与拟改内容及影响，由用户批准/调整/拒绝；只允许专家已有能力及规则内的调整 |
| 文件修改及其他有影响操作 | 依现有工具策略、授权和作者交付约定审批；已有明确文件交付授权不逐次重问 |
| 专家能力不适合或需创造新方法 | 不靠一次审批扩展专家能力，保留成果并给通用模式/孵化入口 |

审批卡说明“要做什么、为什么、影响什么”，提供批准、拒绝、调整及停止入口。
技术内部字段留在审计，不要求用户理解compute ID或每条算式。审批对象绑定任务、
当前尝试、具体行为内容及其版本/影响；相关内容变化、授权撤回或任务取消后，旧批准
不能复用。用户调整后重新核对应约束；延迟批准和重复点击沿现有幂等机制处理。

用户未回答、关闭或过期不等于同意；拒绝后只可继续无依赖且仍获授权的工作，依赖
该行为的部分等待调整或结束，不能绕道调用相同工具。已发生费用如实记账。

批准只说明允许该行为，不代表数据真实、公式正确或成果合格；原验收继续执行。
用户也可在工具运行过程中停止后续派发；已发生的外部操作或费用不能假称撤销。
审批使用户能在使用中纠偏，不保证每项适用性误差都能事前发现。

## 8. 数据与 Wind：接入现有供应链，不另开捷径

### 8.1 统一供应判断

| 实际情况 | 实施路径与可证明结果 |
| --- | --- |
| 已有已授权资料，目标读法就绪 | 确认使用、钉住确切版本，直接进入执行 |
| 已有原件，缺文本/页图/表格读法 | 创建或复用加工需求，关联原件版本；不重复下载，不把 confirmation TTL 当作正在加工 |
| 可通过 Wind 获取结构化结果 | 发现可用渠道和参数 Schema → 提出查询需求 → 用户确认 → knowfeed 调用 → knowbase 保存响应与派生事实 |
| 需要年报、公告原文或管理层讨论 | 查询实际支持的公告/原文能力；返回仅为链接或摘要时按实际类型交付；需要 PDF 页码而渠道未给原件时继续走可用原件渠道 |
| 缺数据且供应已失败/额度耗尽 | 显示失败及缺项，允许正式重试、改来源、缩小任务或停止；不能永久显示“正在取” |

不限制业务数据只能是财务：通过供应商工具 Schema 与通用数据描述表达股票、公告、新闻等能力。但是每种返回形态只有经过适配和验证，才能声明支持对应读法；“不写死数据类型”不等于“所有响应自动都能当结构化事实”。

### 8.2 Wind 具体开发范围

复用 knowfeed `provider_query.py`、Wind adapter、来源发现及现有用户确认链。核定并实现以下缺口：

1. 工具发现按实际所有者渠道返回，保留服务名、工具名、参数 Schema 与版本摘要；规划不得捏造接口名。
2. 供应执行绑定用户确认的规范化参数摘要；已确认后改主体/期间/字段必须新修订。
3. 原始响应先作为供应商证据保存；结构化转换逐项保留主体、期间、指标、币种、单位、累计/单季、报表口径、查询时间及响应位置。缺失元数据明确未知，不能猜。
4. 为已验证返回结构提供可维护的转换器，生成 knowbase 原有事实引用。未知形状保留原件并报告无法结构化，不动态执行模型生成的解析代码。
5. 公告与年报分别验收“检索结果”“原件下载”“分页文本”“可计算事实”，不能只验证查询 200 就全标支持。
6. 当前模型不能读取供应商 Key；Key 留在正式服务配置，日志与回执脱敏。
7. 额度耗尽/鉴权失败持久暂停该渠道。无人工次数上限不等于无限自动重试；不确定是否计费的请求不自动重发，不默默切换别人的凭据或收费渠道。

用户已授权服务端接入、取消此前 5 次限制；实际渠道许可与数据使用权仍按配置和 W0 证据，不能把用户授权解释成供应商许可。软件开发与离线测试不需要等待真实额度调用；真实验收记录其实际能力与限制。

### 8.3 读数和来源对照

报告 PDF 引文继续要求可追到材料版本和页码；Wind 数据引用供应商回执和响应字段，不伪造年报页码。两源冲突时并列期间、单位、合并口径、重述版本和取得时点，由作者方法决定采用原则；平台不得静默择一个更方便通过的值。

报告期、披露日、取得时间与预测时点分别保存。历史回测按当时可得数据构造窗口，不能把之后披露的比较期重述值无说明地当作当时已知数据；供应商不支持历史时点版本时明确标明局限，不宣称已完成无前视偏差回测。该缺口不能由提高模型预算消除。

供给等待必须关联 `confirmation/revision → demand → job → delivery/失败`。旧确认未到期只证明授权仍有效，不证明有活作业。消费方使用幂等状态事件，失败清除“正在供应”的推断，取消专家任务不会擅自删除已确认供应记录；独立供应是否继续由原任务语义处理并明确显示。

## 9. 测试归属、页面、身份与文件

按 K29 复用执行服务，测试过程显示在 knowlab：用例进度、计划、工具活动、交回物、失败原因、数据确认、反问、停止、费用与文件下载均可在测试详情完成。knowbench 不另做一个用户可见的测试入口。

执行来源使用已有 `knowlab-test` 及正式测试关联记录。所有列表、搜索、最近活动、项目统计都在后端过滤测试对象；不仅前端隐藏卡片。直接访问旧测试链接由后端识别后给出 knowlab 测试详情去向，权限仍按作者/获授权测试人员核对。

knowlab 通过服务契约获取测试只读过程与授权动作；不开放任意 task_id 代理。服务凭证只证明应用身份，数据确认仍需本人身份、既有签署依据及修订检查。模型 Key 不经过前端或 knowlab 测试投影。

作者自测、平台人员代测、普通用户使用分别保存执行归属与操作者；`zymun`、`sig-am` 或“knowbot-test”这样的名称不能用于猜角色。登录账号、用户沙箱、执行电脑与本机 link 分开，不因在另一台电脑浏览就强迫重新配对。

K30 在同一页面增加终态测试归档/恢复；归档只整理展示，保留专家版本、测试题、费用、数据授权、成果与文件引用。活动测试不以归档替代停止，先核既有删除接口实际语义，不承诺“删除只影响列表”。

文件仍落在该执行任务获授权的工作区并保存已交付证据。knowlab 下载读取该次已归档/已验证成果，不凭文件同名读取后续任务的新内容，不因为测试移出 knowbench 就另造一套文件执行服务。

旧数据不回填为无法证明的新能力/作者接受/用户同意。历史页面可标旧格式，不能为了统一展示重写旧成果。

### 10.1 专家能力声明的统一格式（2026-11-04所有者要求，能力声明不含测试状态）

所有者指出，能力声明不能继续依赖几段任意发挥的简介。此处确定所有专家共用的填写、展示与匹配格式。声明表达作者承诺的服务，不把流程步骤当作能力，也不要求作者必须引用方法库。固定执行与按题选择方法使用同一格式。

**2026-11-12 所有者修订**：专家也是方法，能力声明直接作为方法六要素的第一项，替代原“When to use”，不再作为六要素之外的另一对象。下文按此重写；通用结构见[方法、步骤、组合与模板](../专家孵化方案/luna/方法、步骤、组合与模板.md)。旧八栏中的详细输入、交付和处置规则分属其余要素，展示时引用，不重复填写。

**实施状态**：本节是已落盘的统一规范。现有 `scope/v1` 仍是三段文字；现有 `PublicCapability` 已有 statement/conditions/exclusions/delivers，但当前作者端把它与动态 planning 的 capability_bindings 绑定。本节要求解除这种产品耦合，尚不代表作者表单、目录接口和匹配器已完成迁移。财务准专家4.11已将四项规范能力投影到现有scope三字段，移除声明中的测试状态，八步流程未变，见[正式修订回执](../../../../scripts/results/第二轨联调/2026-11-04-财务专家规范声明/README.md)。它尚未上架；不能把文本分项当作全平台结构化契约已上线。

#### A. 平台自动记录的信息

| 项目 | 来源与规则 |
| --- | --- |
| 专家标识、名称、确切版本及声明摘要 | 与同一不可变专家包关联；版本与摘要由平台产生，作者不能手填覆盖 |
| 作者及声明确认记录 | 作者确认后才能随版本发布；AI起草和方法库模板均不能直接成为正式承诺 |
| 专家费用 | 来源为当前版本的市场价格，独立于能力和验证状态；免费不表示适用，亦不等于模型及数据费用为零 |

这些信息在作者表单中只读。**能力声明不包含测试状态、测试结论或“未测试”占位，也不以存在测试记录为填写声明的前提**。已有测试及正常发布/人工特批记录归属独立的测试、审核与发布记录，按原权限和流程保留；本条不删除历史记录，不改发布门禁，也不能把没有记录解释成已经验证。

#### B. 作者填写能力声明及关联要求

每个方法都填写能力声明，建议字段为 `capability_declaration`；作为专家使用时采用同一结构，不另设 `when_to_use` 对象。可以先声明再实现，也可以依据已有实现整理后确认。每位专家可在同一声明内列出多项能力，每项独立编号；编号用于引用与追溯，不等同方法库ID或步骤编号，也不自动创建独立方法。

| 必填栏 | 应写什么 | 写法要求 |
| --- | --- | --- |
| 能解决什么、交回什么结果 | 一个明确目标及直接结果，例如“计算一家公司的历史营收CAGR” | 用“动作＋对象＋结果”表达；避免“全面分析”“解决任意问题”等无限承诺 |
| 适用范围与情境 | 对象、数量、领域/市场、期间、口径、触发条件等实际边界 | 只列影响该能力适用性的维度；跨领域通用，不强制所有专家填金融字段；所需数据及权限引用对应要求 |
| 方法与方法边界 | 本能力实际采用的做法概要；是否固定、允许调整哪些部分 | 公开足以判断适用性的概要，不暴露私有方法正文、组合图或系统提示；用户明确指定的不同方法不得偷偷替换 |
| 不适用与不承诺 | 明确排除的任务、方法、对象或结果，以及必须披露的局限 | 未提及的能力不能默认存在；某字段未填写是声明不完整，不表示无限适用 |
| 适用/不适用示例 | 至少一条典型适用问法和一条近似但不适用问法；必要时附澄清例 | 示例是声明解释，不是测试通过记录；不把示例公司、年份固化为唯一可用输入 |

详细要求由其余五要素负责，能力声明引用同一方法版本中的对应内容，不再维护另一份独立规则：

| 要素 | 与能力声明的衔接 |
| --- | --- |
| 所需输入与权限 | 定义输入 Schema、信息、证据、窗口、口径、资源权限及缺项处理；区分需要什么和当前是否具备，不把可申请补取写成保证可得 |
| 执行步骤序列 | 实现所声明能力，组织方法调用、程序块及条件不足时的处理；公开方法概要不代替内部流程 |
| 结果校验方式 | 定义承诺如何验收、证据与失败处理；校验规则属于定义，实际测试结论仍单独记录 |
| 返回产物格式 | 定义结果、证据、单位、口径、文件及输出 Schema；不能只写“报告”，须与声明的预期结果对应 |
| 何处必须审批 | 定义授权触发条件及等待、拒绝后的处理；无回答不算授权，不得静默换题、换方法或增加预算 |

作者可先让AI起草，再修改确认；无需先有方法库引用或测试记录。共用要求集中定义后引用，能力项的特有窗口、口径及交付必须明确对应，不能要求用户自行拼出边界。专家简介和能力卡是同一声明及相关要求的展示形式，不是另一个可独立编辑的承诺对象。组合能力由作者明确声明，不自动取内部所调用方法的能力并集。

#### C. 财务分析与预测专家的示范格式

以下是依据准专家4.10实际规则整理的展示示范，尚未写入新的线上结构化契约，也不是新一轮测试证明。其中目标、适用范围、方法边界、排除项及示例来自能力声明；数据前提、详细交付及条件不足的处理引用其余要素。表格展示完整选择信息，不表示要在能力声明中重复存储这些详细规则。

| 栏目 | 能力：营业收入、归母净利润的季度同比预测 |
| --- | --- |
| 目标与结果 | 测算一家中国A股上市公司未来两个季度营业收入、归母净利润的点预测及区间 |
| 适用范围 | 单公司、明确预测起点；金额口径可比；仅上述两项指标和两季度期限 |
| 方法 | 上年同季数乘以1加近四季同比中位数；区间用近八季同比最小/最大值；先回测最近四个单季 |
| 数据前提 | 支持单季还原的累计报表及比较期、同比和回测所需历史窗口；数据经用户确认；预测所用期间满足作者原四式核验要求，版本重述与口径差异另列 |
| 交付 | 两季度点预测、上下界、最近四季回测结果、计算依据、数据出处与局限，纳入Markdown报告 |
| 不适用/不承诺 | 不做DCF、股价或目标价、整套报表联动、五年预测、用户指定的其他模型；区间不是统计置信区间，不保证未来实际业绩落入区间 |
| 条件不足 | 预测起点或方法要求不明先澄清；缺数据走用户确认；历史窗口或核验不足如实说明，不能缩短回测窗口冒充完成 |
| 适用例 | “按季节性同比法预测未来两季度营收和归母净利润，并回测最近四季” |
| 不适用例 | “用DCF给出公司的合理股价”或“预测未来五年的三张报表” |

历史核心指标计算、累计转单季、管理层讨论对照等分别写能力卡；不是把“定范围、摸底、成稿”等执行步骤机械翻成独立能力。某能力若只有依附其他分析结果时才能执行，须明确其输入前提，不能据此自动承接一个缺失必要上游的独立任务。

#### D. 三处共用与质量检查

1. **knowlab**：能力声明作为六要素第一项按B填写，其余要素填写详细要求并建立对应关系；AI协助和用户手写使用同一对象，不同时维护独立的 `when_to_use`。定型时核完整性、重复编号和明显冲突。内部可以核方法/输出的支持关系，但公开声明不强制绑定方法库，也不能仅因绑定存在就认定承诺真实。
2. **knowmart**：按能力卡展示；简介从同一声明生成摘要，不维护另一份自由文案。能力卡不显示测试状态；测试和发布记录不混入能力声明。
3. **knowbench**：AI取得相同的确切版本声明及引用的必要输入、交付等要求，逐项核用户所需结果、明确方法及适用条件，引用具体能力项并说明限制。只读数据能力不能替代分析方法；免费/唯一不构成适用依据。匹配仍是有依据的判断，不宣称数学证明或保证完成。
4. **执行与验收**：本次要求和用户明确接受的调整保留原文与版本；交回结果逐项对应。声明中的数据条件仍需在运行时核验，缺项和不能完成的要求如实保留；审批不替代结果验收。
5. **变更**：修改能力边界随专家新版本发布，旧任务仍引用旧声明。旧三段文字可由AI整理为待确认草稿，不能未经作者确认自动变成已验证能力，也不能为了统一显示改写旧包摘要。

#### E. 实施交付边界

先在knowlab提供方审查并扩展已有声明对象，将其归为六要素第一项并建立与其余要素的引用关系，解耦“有结构化声明”与“使用动态planning”，不为格式整齐引入第二套专家运行器。采用哪一个契约版本由实际兼容性决定，由Pydantic提供方生成Schema并更新knowmart/knowbench消费锁和前端Zod。旧声明保持可读，新声明按上述结构编辑、冻结、展示和匹配；旧八栏或 `when_to_use` 内容经整理和作者确认后进入新版本，不改写旧发布包，也不能靠前端标题分段冒充已完成结构化契约。

验收至少包含：固定专家可编辑六要素第一项能力声明；无需方法库引用亦可声明；方法边界、排除项及所引用的数据前提和交付要求保存重开不丢；不重复维护 `when_to_use` 或独立能力卡承诺；匿名/普通用户只能看到声明及获准公开的必要条件，不能取得私有执行内容；旧包摘要不变；声明不要求测试记录，也不接受作者填写测试状态；AI遇到唯一免费但方法不符的专家仍不自动请入；声明缺字段不能被解释为无限能力。

## 11. 失败、恢复、预算与质量门

不增加 Task/Attempt 状态词，沿现有状态机与等待原因工作：

| 场景 | 落地行为 |
| --- | --- |
| 等澄清/用户决定 | 既有 WAITING + INPUT/APPROVAL；说明具体行为及影响，支持拒绝/调整，取消或超时不等于同意 |
| 专家能力不适合 | 明确不适合及未满足项，保留成果；用户可调整范围、转通用模式或提出孵化申请，不假装完整成功 |
| 等数据 | WAITING + DATA，展示真实供应记录和缺项 |
| 预算不足 | WAITING + RESOURCE；不自动加预算或新建测试轮次 |
| 执行电脑断开 | ENVIRONMENT 等待或现有中断处理；不将临时离线判成方法不合适 |
| 验收不通过 | 按作者允许返工次数，反馈具体字段/规则，不重复整条已验收前缀 |
| 模型服务/解析/平台异常 | 区分工程错误与方法不通过，保存原文和已发生费用 |
| 进程重启/重复回执 | 从已提交的计划/Attempt 恢复，不能重复派发已结算 turn |
| 供应商返回不明/超时 | 留请求摘要与结果未知原因，不自动重复可能计费的查询 |

报价、模型预算、数据供应费用分别呈现。找专家现有预算也不是免费；在提交前显示本次查找上限。找专家与正式委托建立关联并汇总费用，不能用新任务规避用户本次操作的总上限。正式执行启动前核预算已设定；查找余量不自动变成新的授权额度。

若用户一次设置了查找及执行总额，该额度与提交载荷一并留在查找任务的原始输入和委托关联中；创建执行任务时在关联锁内扣除已记查找费用及未结算预留，只能分配剩余额度。后续每次派发重核关联总额。费用尚未知时标待核并保留预留，不记为零；供应商迟到结算可能造成实际超额，照实补记，停止后续派发，不能宣称能够撤销已发生费用。用户后续另行授权的新额度有独立记录，不静默滚动续用。

工具计算结果与报告显示精度分开，沿已确认金额/比率容差；不强迫正文携带无限小数。引文核引用版本与原文依据，计算核收据及值，财务语义核作者原式与口径；三类检查不能互相替代。

性能验收测完整墙钟时间、模型耗时、工具耗时、供应等待、人工等待、费用与返工次数。与固定基线比较时使用同一题、同一数据快照和模型配置，单独报告等待；不承诺动态必然更快。

### 11.1 三类困难与成果转交

- **缺数据**：沿原查询/加工/采集/授权链补齐，显示真实作业；不能因此直接认定专家不适合。
- **能力不适合**：说明声明判断与实际执行间的差异，按7.4收尾或等待用户调整；提供通用模式和本人孵化申请。
- **平台故障**：显示故障及恢复方式，保留记录与费用；平台负责修复，不归为用户选择风险。

用户选择补救后，可预览并携带原题、已确认条件、预算使用情况、已完成成果、失败原因
及仍可使用的数据引用。沿现有通用任务/孵化接口传递原任务关联，不建立第二个成果库。
转交不等于对旧任务结果背书；未验或失效内容标明状态，接收方不能把失败计算当已验事实。

只转交获准内容，重新核引用访问权，不复制他人私有授权或把数据默认公开。剩余预算
仅在原授权明确涵盖新操作且已有账支持时延续，否则由用户设定新预算；不因切模式自动
增加费用。点击出口不自动提交申请、公开需求或启动计费模型；最终动作沿对应页面明确
提交。重复点击、刷新或迟到回执不能重复建任务、扣费或重新派发已经完成的取数。

### 11.2 实践反馈回流与责任

允许用户将选错专家、不适用问题、拒绝的行为、有效调整及结果反馈给作者。反馈复用
任务/成果引用和已有申请/工作稿机制，生成待审改进材料；用户选择分享内容，默认不带
私有数据全文。作者审阅并修改后产生创意/专家新版本，旧任务保持原版本。

成熟方法收录记录实践对象、版本、验证范围、已知局限及有权作者决定；自动生成改稿、
一条好评、冻结或合成绿灯都不足以自动晋级。若现有机制不支持反馈关联，仅补所属领域
最小记录及契约，不建设独立评分排名系统。

| 主体 | 承担的责任 | 不能转嫁的部分 |
| --- | --- | --- |
| 使用者 | 选择/合理匹配的不确定性、获知后的试用成本和授权决定 | 不承担平台权限失控、故障或虚报成功的责任 |
| 作者 | 定型内容、声明的真实范围、修改及版本发布 | 不以用户批准行为代替方法和声明质量 |
| 平台 | 忠实执行、权限预算控制、真实状态/费用/结果、故障恢复与补救入口 | 不承诺匹配绝对正确，也不把工程缺陷包装为匹配误差 |

### 13.2 真实业务门

1. **原 c1 全题**：2021～2024 营收、归母净利润、毛利率、三年 CAGR；以题定时点预测 2026Q4/2027Q1，最近四个已披露单季回测，Markdown。预测方法、勾稽原式及阈值沿作者已确认版本；实际执行时不得借系统当前日期改题。
2. **轻题**：在作者定型允许按问题选择的专家中，只问历史营收走势不选无关预测/回测；数据需求相应减少。另验固定安排忠实执行，不能为显示动态而暗改固定专家。
3. **人均创收**：员工人数及口径具备时算，缺失时如实处理；不能为了问员工数强制跑季度预测。
4. **另一主体**：沿原 c3 五粮液题，按实际授权数据供应；不能预设“它一定不在数据里”。
5. **声明已知不适合**：用户明确算法与声明冲突，说明差异且不自动冒充适合；通用模式、本人孵化两出口可用，改题/手选/结束仍可操作。
6. **不同来源**：结构化 Wind 回执与年报原文分别核；缺失的供应商能力如实记录，不把其他来源的成功标作 Wind 成功。
7. **普通用户闭环**：sig-am只提问，经声明合理选择取得可用版本，核本次委托、行为审批与自身数据，取得报告；不得借用zymun的私有授权证明跑通。
8. **创意三起点**：用户原创、挑方法组合模板、AI初稿各经实际编辑定型并孵化；补混合来源和解除引用后修改，核源版本不变、声明与加工结果一致。
9. **允许匹配误差并可补救**：选取声明看似适合、实际执行发现条件不满足的用例；如实显示局限和已有费用，由用户拒绝/调整后转通用模式或孵化。成功标准是纠偏可操作，不能通过篡改匹配为“从未选错”过关。
10. **反馈改进**：用户选择分享不适用原因和获准成果，作者收到待审材料；旧专家不变，作者加工后另出版本，原实践记录不自动覆盖新版本。

## 14. 发布、回滚与演示备用

1. **代码准备**：从已发布基线构造可审候选，纳入所需开发提交及线上修复；子仓先提交、父仓再钉 gitlink，三方契约锁与源码一致。开发 HEAD 不等于发布候选。
2. **迁移顺序**：先兼容读取和扩展 Schema，再消费者支持，再新写入/新专家准入；在双方就绪前不向旧接口发送新字段。活动旧任务继续原契约。
3. **准入**：复用 `KNOWBOT_DYNAMIC_TEST_OWNERS`、`KNOWBOT_DYNAMIC_MARKET_OWNERS`，以真实 subject 配置；作者测试与市场使用分别验证，不凭昵称或 HTTP 参数开门。市场可请还须原授权/交易/发布资格，开关不能替代。
4. **维护窗口**：Qwen 发布前核全部活动任务和 app-server turn；当前固定测试或普通付费任务仍运行时，不滚动影响其 Runner。作者/用户确认由本人操作。
5. **正式流程**：仅使用现有 Jenkins → Make/Ansible → 渲染声明 → Flux。模板变更必须连生成声明入库，尤其 MCP 路由、服务关系与开关；不再出现模板已改、实际声明未改。
6. **上线核验**：API/Runner/Worker/Scheduler 镜像一致；实际 tools/list、工具 relay、旧线程刷新、回调、外部电脑 SSO 与路由均核；localhost/本机 hosts 成功不能代替公网验收。
7. **备用冻结**：冻结实际通过的专家包、软件源/镜像、测试集/数据版本、模型配置标识和已验报告。后续共享服务发布都回归备用链；手选专家只能避免匹配路径，不能天然隔离共享服务故障。
8. **回滚**：先关闭新动态准入；已接受任务仍可查/停/按支持版本收尾。必要时经维护窗口回退到已验证候选，保留扩展数据库结构与历史；不能把新任务塞给不识别契约的旧 Runner。供应商已经发生的查询与费用不可通过软件回滚撤销。
