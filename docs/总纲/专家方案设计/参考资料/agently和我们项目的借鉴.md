# Agently 和我们项目的借鉴

日期：2026-11-12。本文研究 Agently 的 DAG 编排和 Action 工具体系，说明它们如何承接 SunMoonAI 的方法、步骤、模板与工具中心设计。本文是方案研究，尚未接入框架、修改业务实现或部署。

研究对象是本机 `/home/zym/repo/Agently`，提交 `d21445f7e02f20956a5734eceb922616b5f7e669`，`pyproject.toml` 声明版本 `4.1.4.11`、Python `>=3.10`。以下“源码事实”仅针对这个版本；已阅读实现、文档和相关测试代码，未安装缺失依赖，未运行框架测试、模型调用或真实 MCP 联调。源码中存在测试不等于本轮测试通过。

我们的概念以[专家及专家团孵化模板](../专家孵化方案/luna/专家及专家团孵化模板.md)为准，特别是六要素、模板逐级具体化，以及第 1.8、1.9 节的 MCP 双路径和工具中心部署。本文提供实现候选，不以框架现有字段反向改变这些概念。

## 一、结论与采用范围

**值得借鉴，建议优先验证 TaskDAG 作为步骤编排内核、Action 作为后端运行时工具注册与分发机制。方法契约、模板和方法市场仍由我们定义；现有 knowbench 任务账本与 Codex 模型运行链继续承担各自职责。**

Agently 有助于解决“依赖满足后运行哪个步骤”和“通过什么执行器调用哪个工具”。它没有直接交付我们需要的完整方法市场、多用户工具管理中心，以及连接、授权、审批与任务账本的整合。

| 处理方式 | 对象 | 本项目中的位置 |
| --- | --- | --- |
| 优先验证直接复用 | TaskDAG 的图结构、依赖检查、解析与执行；TriggerFlow 的事件、汇合和暂停恢复基础 | knowbench 既有任务执行体系内部的编排能力 |
| 经适配后复用 | ActionRegistry、ActionDispatcher、Executor、ExecutionResource 及 MCP 发现和调用 | 后端 runtime 的有效工具表、分发和连接生命周期 |
| 借鉴设计，仍须自己落实 | 分层工具范围、调用记录、审批中断、资源需求与运行资源分离 | 我们的连接授权、动作审批、账本和恢复机制 |
| 由我们继续定义 | 方法六要素、模板变量与约束、方法市场、版本绑定、业务验收、统一目录与两端协同 | knowlab、knowmart、knowbench 按现有职责承接 |
| 不作为首期接入前提 | Agently 自带模型规划器、完整 Agent 循环、DAGActionFlow、另一套任务服务 | 避免为采用 DAG 同时替换现有 Codex 链路 |

“复用”仍需通过后文的离线验证和迁移验收；目前不是已经完成兼容性、性能或生产可靠性评估。优先验证组件组合，不先复制整个框架进项目，也不先建独立的 Agently 任务服务。

## 二、先分清 Agently 的几个层次

### 2.1 编排层

| 组件 | 源码中的职责 | 对我们的意义 |
| --- | --- | --- |
| TaskDAG | 定义节点和依赖，检查图，解析处理器，执行提交的任务图 | 与方法内部的步骤 DAG 最接近 |
| TriggerFlow | 事件触发、并发与汇合、子流程、状态、暂停和恢复 | TaskDAG 背后的执行基础，也有比 TaskDAG 节点 Schema 更丰富的流程机制 |
| DynamicTask | 围绕任务规划与执行提供便捷入口 | 可选封装；采用 TaskDAG 不要求重新定义我们的任务生命周期 |
| TaskDAGPlanner | 根据需求产生候选任务图 | 可以以后研究，首期先执行已确定的方法图 |
| DAGActionFlow | 在模型的 Action 循环中，按 DAG 组织一批动作 | 面向一次模型动作规划，与专家方法的业务步骤图不是同一层 |

TaskDAG 可以直接接收程序提交的图，再由 resolver 为节点找处理器，不必先让模型规划。默认执行链可以从 TaskDAG 直接进入 TriggerFlow，不要求引入 Blocks。

因此，**使用它的 DAG，并不意味着每一步都让 Agently 调一次模型，也不意味着把我们的专家执行权交给其 Agent。**模型参与选择方法或执行某个步骤，是我们在节点处理器中明确安排的行为。

### 2.2 工具层

当前版本应重点看 Action 体系，而不是围绕旧 ToolManager 设计接入。

| 组件 | 作用 | 不能混同的对象 |
| --- | --- | --- |
| ActionRegistry | 在内存中保存工具规格、执行器、可选函数及标签 | 不是持久化、多租户的方法市场或平台统一目录 |
| ActionDispatcher | 解析调用，处理输入和策略，检查审批，准备资源，调用执行器并归一结果 | 不是我们全部业务授权规则的现成实现 |
| ActionExecutor | 对接函数、MCP 等具体执行方式 | 执行器类型不自动决定工具代码实际位于哪里 |
| ExecutionResourceManager / Provider | 建立、复用、检查和释放运行资源，例如 MCP 客户端 | 活连接不是凭据主档，也不能直接写进恢复快照 |
| Action 门面及 Agent 扩展 | 组合上述能力，提供注册和调用入口 | 全局 Action 与 Agent 自身的 Action 注册表并非一个分布式共享中心 |

注册、分发、执行、资源管理分开，是最值得借鉴的结构。调用方可以是程序，也可以是模型循环接收到的调用请求；实际执行者始终是宿主程序和对应执行端。

## 三、我们的步骤怎样映射为 DAG

### 3.1 方法、步骤与节点的对应

**方法保持六要素完整结构，DAG 主要承接其中的 `sequence_of_work`。步骤映射为图中的执行单元；步骤不因此成为方法，也不因此自动注册为一个工具。**

| 我们的对象 | 建议映射 | 约束 |
| --- | --- | --- |
| 具体方法版本 | 方法主档与已解析执行计划 | 六要素不全部塞进 TaskDAGNode |
| 步骤及其依赖 | TaskDAGNode 与 `depends_on` | 保留业务步骤 ID，不用数组下标充当长期身份 |
| 步骤输入映射 | 节点 `inputs` 与受约束的结果引用 | 方法输入、前序产物、常量等来源分别表达 |
| 步骤执行体 | 受信任的节点处理器或子流程 | 可以包含一个或多个方法调用、程序块及其混合 |
| 被调用方法 | 解析到确定方法版本及调用绑定 | 可以是程序实现，也可以继续执行子图 |
| 程序块 | 所属方法版本内的实现或处理器 | 不要求独立方法身份，不自动上架或注册 |
| 业务验收及交付 | 明确的校验逻辑、输出组装与方法完成判定 | 框架节点完成不能替代六要素中的验收承诺 |

一个步骤可以多次调用工具、组织多个模型轮次，也可以完全不调用模型。一个被调用方法可以有自己的步骤图。两者都不要求“一个节点＝一个方法＝一个工具调用＝一次对话”。

复杂步骤若需要内部并行、独立失败定位或恢复，可以编译为子图或内部节点；但应保留它们与业务步骤的归属关系，不能让框架的执行粒度改变方法资产身份。

### 3.2 输入与依赖

源码支持 `${INIT...}`、`${DEPS...}`、`${STATE...}`、`${TRIGGER...}` 等引用：分别取初始输入、依赖结果、状态和触发数据。整个值是引用时可以保留其类型，嵌入字符串时则用于字符串组合；缺失路径会报错。

可借鉴其表达式解析，但我们的输入来源规则应更窄、更明确：

1. 方法输入是对外契约，直接成为执行上下文的授权输入；不强制增加一个“输入步骤”。
2. 步骤分别声明需要哪些输入，来源包括方法输入、前序产物、固定配置和有记录的补充内容。
3. 引用前序产物时同时检查对应依赖。**输入中写了引用，不代表框架会自动补出依赖边。**
4. `STATE` 只暴露本次执行允许使用的命名空间，不能用它绕过依赖、版本和权限检查。
5. 输入映射只映射已有值或引用；实际读取外部资料是调用动作，仍须通过连接和授权检查。

图启动前应检查必需输入的可达性、类型兼容、依赖关系与最终产物覆盖；运行时还要检查实际返回值。Agently 的基础图检查只解决其中一部分。

### 3.3 DAG、分支、循环与重试

TaskDAG 检查重复节点 ID、缺失依赖和环。TriggerFlow 还有条件、匹配、遍历等机制，但 TaskDAGNode 当前没有通用的条件字段；不能把底层全部能力视为已经可以在 DAG JSON 中直接声明。

建议首期支持明确的无环依赖和汇合，分支单独定义编译规则：未选择分支如何结束、汇合等待哪些分支、分支产物缺失怎样表达，都必须先写清。不能让汇合永久等待未执行的节点。

需要区分三种行为：节点内有界重试、有限集合上的重复执行、验收失败后跨步骤返工。DAG 不能直接画回边；返工应由既有任务机制建立新执行轮次或受控的新图版本，记录已采用和失效的结果。不能把“重试当前处理器”当成全部返工能力。

现有财务专家已有返工行为，迁移时必须保留其业务语义并做等价验收；不能为满足无环要求悄悄删除。

### 3.4 结构有效不等于业务成功

有三个源码细节需要在适配层明确处理：

- 默认 `validate` 处理器直接返回 `ok: True` 等信息，不会自动检查我们的业务规则。必须绑定真实校验器，或调用有明确责任和证据的评估流程。
- 节点失败后采用 `skip` 时，会产生跳过结果并走完成记录，节点状态可记为 `completed`，随后触发下游。我们必须区分执行结束、业务成功、允许跳过和交付缺项。
- 某些不需要的、无法解析的可选节点可以被裁剪并留下诊断。方法契约所需的工作不能被静默删除；发布和运行检查必须证明承诺产物仍能完成。

方法最终完成，须依据本级 `how_to_validate` 与 `what_to_return`；不能只看图已结束或子工具全部成功。

## 四、模板与方法市场怎样接入 DAG

Agently 提供执行结构，我们仍须建设“方法模板到可执行计划”的解析与检查能力。

```text
六要素中的固定内容＋变量＋变量约束
            ↓ 部分赋值、约束收窄
更具体的模板
            ↓ 定义闭合、实现与验证完成
具体方法版本
            ↓ 解析步骤、输入映射、调用绑定和选择策略
受检查的执行计划／TaskDAG
            ↓ 本次输入、连接授权及实际运行环境绑定
既有任务中的执行实例
```

六要素是六个可变量化的结构块，步骤通常具有最大的结构选择空间。Agently 的 `kind` 或 `binding` 只是执行端的解析入口，不能代替模板变量、变量约束和市场中的候选选择规则。

某一步可以固定调用一个方法，也可以固定一个完整的选择策略：候选来源、能力与契约条件、选择主体、选择时机、版本依据、权限和环境要求、无候选及失败处理。选择范围变窄后形成更具体模板，不按变量数量机械判定层级。

创作时仍未确定的选择与“定义已经确定、运行时按规则选择”不同。后者可以成为具体方法的一部分，但每次实际选择都应记录候选依据、选中版本、输入适配和绑定；模型选出一个名称后仍须由程序检查并解析。

**方法市场建设是重要内容，不能被 `list_tools` 或注册表查询替代。**市场解决方法供给、能力发现、发布版本、适配与可选资格；运行时注册表解决本次环境中实际加载和可调用的工具。候选还须与本次授权和实际可用环境求交，不能把市场上的全部方法直接展示给模型调用。

若选择会改变图结构，应在执行前形成并记录解析后的图；确需执行中展开时，须另行规定子图身份、版本、审查与恢复规则，不能无记录地原地改写正在恢复的图。

## 五、Action 工具体系的具体借鉴

### 5.1 规格、调用与结果分开

ActionSpec 包括 `action_id`、名称描述、参数和返回描述，以及 `side_effect_level`、`approval_required`、`sandbox_required`、`replay_safe`、`concurrency_mode`、`expose_to_model`、执行器类型和资源需求。ActionCall、ActionResult 则承载单次调用及结果。

建议借鉴这种分离，但正式方法仍使用我们的统一六要素：方法主档是契约真源，注册规格从明确版本投影生成，执行器和连接绑定承接实现。不要让 ActionSpec 成为第二份可独立修改的方法契约。

| 方法六要素 | 与执行层的关系 |
| --- | --- |
| 能力声明 | 提供选择与模型可见说明；名称和简短描述不能替代完整适用边界 |
| 所需输入与权限 | 生成参数检查及资源需求；具体连接、凭据和授权在运行时绑定 |
| 执行步骤序列 | 形成图和处理器；单个工具实现也按自身职责说明执行方式 |
| 结果校验方式 | 绑定实际校验逻辑与证据要求；不使用默认通过充数 |
| 返回产物格式 | 形成返回契约及产物引用；保留部分完成和未知结果的表达 |
| 何处必须审批 | 形成动作审批条件；一个布尔字段不足以表达审批人、范围和有效期 |

当前 Registry 使用进程内字典；普通重复 ID 注册会覆盖原规格和执行器。其注册修订也不能当作我们不可变的方法发布版本。平台需要稳定身份、命名空间、版本和配置代次，运行时表按这些依据生成和核对。

### 5.2 MCP 如何进入注册表

该版本的 `async_use_action_mcp` 大致按以下流程工作：

1. 规范化服务 transport 和配置，用临时 FastMCP Client 建连并调用 `list_tools()`。
2. 把工具的输入输出 Schema、名称和说明转换为 Action 注册规格。
3. 为工具创建 MCPActionExecutor，并声明 MCP 运行资源需求。
4. 同批工具共享该服务的资源标识，调用时由资源管理层建立或复用 MCP 客户端。
5. 执行器通过客户端 `call_tool()` 调用远端工具，并转换返回内容和错误；批量注册失败时有回滚逻辑。

这正好对应此前讨论的“查询 MCP，将发现的工具注入运行时注册表”。它是工具发现及调用适配，不是模型执行 MCP 协议。

需要修改或约束的细节：

- 直接用远端 `tool.name` 作为 `action_id`，没有自动给每个服务加命名空间。两个服务同名时存在覆盖风险；我们必须区分能力身份、服务身份和调用绑定，模型别名另外映射。
- 该入口默认 `side_effect_level="read"`、`approval_required=False`、`replay_safe=True`。这些是注册参数默认值，不是对远端工具行为的证明；发送邮件、修改文件等必须逐项声明和核验。
- 列表发现与实际调用是不同时间的连接行为。发现成功不保证之后凭据、网络、工具版本和权限仍有效。
- MCP 执行器本身不提供通用沙箱隔离保证；HTTP 客户端所在位置、stdio 服务进程所在位置和工具最终执行位置必须分别确定。

### 5.3 宿主调用与模型请求共用分发，但授权不能想当然

程序可经 `Action.async_execute_action()` 进入 Dispatcher；Agently 自带模型 ActionRuntime 的常规执行路径也会调用这个入口。它支持把实际执行尽量收敛到共同分发机制。

不过，模型本轮“可选工具列表”的检查位于 ActionFlow 等模型侧路径，不能据此认定程序直接调用自动拥有同样的范围限制。我们的资源授权须在实际执行前检查，使程序调用和模型请求都受约束。

其分层范围收窄机制值得借鉴：上层允许范围与本层选择范围求交，子层不能扩权，交集为空不能回退到全部工具。还要注意 `.use_actions([])` 表示清除本层限制，不是“拒绝所有工具”；接入时不能用错空集合语义。

展示给模型的工具描述与执行器、活连接等宿主配置分开，也值得保留。连接秘密不进入模型参数 Schema，模型提出的策略字段不能提升宿主授权。

### 5.4 DAG 节点不会自动经过 ActionDispatcher

TaskDAG 支持直接执行 callable 或 TriggerFlow 处理器。**仅同时使用 DAG 和 Action，不会使所有节点调用自动统一到工具分发和审批。**

建议明确三类适配行为：已注册方法或工具调用进入受管理的分发入口；程序块按所属方法的受信任实现运行，并对其外部动作应用同样授权要求；需要模型的步骤继续使用现有 Codex 驱动。处理器中的直接网络调用不能被当成已经过 Dispatcher 检查。

这些是待实施的适配职责，不预先要求新建微服务或另一套命令入口。

## 六、工具中心的位置与 Codex 的关系

Agently 的 Action 体系最适合承接我们设想中的**后端运行时工具注册与调用部分**。它不能替代平台统一管理目录，也不会自动替代或同步 Codex 自己的工具体系。

```text
方法与模板主档（knowlab）──发布与候选供给（knowmart）
                       ↓ 契约、版本、使用资格
               后端统一工具目录与绑定管理
                 ↙ 配置与状态关联 ↘
knowbench 后端运行时                 Codex 所在运行环境
既有 Task / Attempt                 现有线程与模型轮次
  → 步骤 DAG                         → Codex 原有工具注册与调用
  → 节点执行体                       → 已获准的 MCP 接入
  → Action 分发（候选实现）
         ↓ 实际调用                         ↓ 实际调用
        绑定指定的服务、后端、沙箱或本机执行端
                       ↓ 可信调用证据
                关联既有任务或会话记录
```

图中的管理联系不代表所有调用都由后端代理。两条路径仍保留：

| 路径 | 谁持有客户端与有效工具表 | 采用 Agently 后的影响 |
| --- | --- | --- |
| 后端步骤直接调用 MCP | 后端 runtime | 可以验证用 Action 的 MCP 注册、分发与资源管理实现 |
| Codex 内模型请求 MCP 工具 | Codex 对应运行环境 | 继续使用其原生机制；需要单独配置、加载确认及授权和观测衔接 |
| Codex 经后端 MCP 网关调用 | Codex 持有网关工具视图，后端持有下游连接 | 是可选绑定，需要显式建设网关和调用关联，不因后端注册了 Action 自动出现 |

在 Agently 注册工具，不等于 Codex 已能选择它；在 Codex 安装 MCP，也不等于后端已有直接调用它的接口。一个工具既可走后端路径，也可走 Codex 路径，但账号、环境、版本、权限与数据去向须分别核验。

聊天、普通工作和专家步骤均可使用 Codex 路径；专家步骤也可直接由后端调用确定的工具。不能按界面名称把工具固定分配到某一端。

统一目录需管理期望配置，并核对各端实际加载状态；工具只在某端可用时如实标明。外部原生工具可以作为获准的技术工具接入，成为正式方法前仍需补齐六要素。两端不因为同名就合并身份，也不因为统一管理就自动复制凭据。

## 七、任务、权限、资源与恢复：我们必须补齐的部分

### 7.1 保留一套业务任务账本

本次核对的 knowbench-backend 提交为 `3cb341f`。`advisor.py` 的 `drive()` 通过 `current_step` 定位步骤、调用 driver 的 `run_turn()` 并推进或返工；`runner.py` 仍使用任务的 `active_attempt_id` 等状态。这说明引入 DAG 不是简单把列表换成图：现有游标、活动执行记录、线程与结果关联要一起适配。

建议保持 knowbench 的 Task / Attempt 为业务记录入口，明确图执行、节点尝试和工具调用与其关系。Agently 的 execution、snapshot 和事件服务于这套账本，不独立维护第二套用户任务真源。

至少要能关联：方法版本、图版本或摘要、业务步骤 ID、节点尝试、调用 ID、实际绑定、输入输出引用、校验与审批结果。框架里的 task ID 是图节点 ID，不能不加区分地当作平台 Task ID。

先确定既有 Attempt 在 DAG 下的粒度和兼容方式，再设计并行写账；不能让多个并发节点争用同一个 `active_attempt_id` 并互相覆盖。

### 7.2 权限要求、运行授权和动作审批分开

| 内容 | 责任 | 与 Agently 的衔接 |
| --- | --- | --- |
| 方法所需权限 | 声明需要什么连接类型、操作和资源范围 | 可投影为资源需求与策略检查输入，不能直接产生授权 |
| 用户连接及凭据 | 管理账号、凭据引用、有效期、更新和撤权 | Provider 获得受保护的运行绑定，不把秘密存进方法或公共注册规格 |
| 本次任务授权 | 决定本次可以使用哪个连接、执行什么操作、触达哪些资源 | 每次真实调用前检查，恢复和换绑定时重新核对 |
| 动作审批 | 对需要确认的具体动作，决定是否允许执行 | 对接既有审批卡和暂停恢复；不能只依赖 `approval_required` 布尔值 |

方法要求不等于用户已经授权，用户授权也不等于所有动作都已审批。发送邮件应按连接、收件范围、正文或产物版本等实际动作确认，不能直接套命令前缀批准。

审批等待期间若连接撤权、参数改变或有效期届满，恢复后必须重新判断。子方法和子流程只能获得需要且允许的权限；传递运行资源对象不意味着权限自然收窄。Codex 直连路径也要有真实可执行的检查点，后端提示词不能替代它。

### 7.3 快照不等于生产级持久执行

TriggerFlow 提供可序列化状态、暂停记录、恢复请求去重、汇合进度、指纹及资源需求等基础能力。暂停后恢复是从明确的执行边界继续，不是保存任意 Python 协程的中间栈帧；某些继续方式会重新进入处理器。

其分布式恢复文档明确将 durable storage、原子认领、CAS／租约、外部副作用去重等责任交给宿主。我们还需要落实：

- 恢复快照、业务状态与待审批事件的一致性；不能先展示可恢复的审批卡，后发现快照未持久化。
- 防止两个 worker 同时恢复同一执行，以及重复恢复请求引发重复动作。
- 从受保护的绑定重建 MCP 客户端等活资源；快照不保存活连接和长期凭据，也不保证原进程仍存活。
- 校验图、处理器版本及资源需求；运行环境变化时不能静默换账号、换服务或改变方法实现。
- 区分失败、取消、审批拒绝、结果未知和可安全重试；外部已执行但回包丢失时不能记作“没有执行”。

### 7.4 并发与副作用

TriggerFlow 有执行级并发控制；源码只有配置正值时才创建相应信号量。因此不能把未配置理解为已有合适的容量上限，也不能把单次 execution 的限制当作全平台限流。

本项目需要按用户、任务、执行资源和外部服务约束并发。首期验证宜串行起步，再有限开放互不冲突的只读分支；共享一个 Codex 线程或同一个可变工作区时，必须明确串行或隔离，不能因 DAG 节点无依赖就直接并发。

节点异常重试只是重跑处理器。读取通常可以在条件满足时重试；写入要结合幂等键、服务查询能力和已经产生的效果判断。`replay_safe` 声明、恢复请求去重和执行器的 exclusive 模式，都不能单独证明跨进程的外部动作“恰好一次”。

## 八、一个贯穿示例

以下仅是方案示意，不是可直接执行的 Agently 配置。设方法为“根据获准资料整理项目周报并在批准后发送”，六要素事先定义用途、输入、流程、验收、交付和审批。

```text
读取项目资料 ──┐
              ├── 形成周报草稿 ── 校验 ── 请求批准并等待 ── 发送 ── 核对回执
读取进展记录 ──┘
```

两个读取步骤可直接使用方法输入里的项目范围与连接引用，无需再造“接收输入”节点。它们分别调用已授权的读取方法；草稿步骤可调用 Codex 并包含格式整理程序块，所用方法可以固定，也可以依据已定义的候选选择策略确定。

校验既检查输出格式，也检查方法承诺的内容和证据覆盖。审批绑定收件范围和已校验的产物版本；用户修改内容后须判断原批准是否仍适用。发送步骤选择一个明确绑定，不同时通过后端和 Codex 发送同一封邮件。

若发送超时，先保留“结果未知”并按服务能力查验，不能直接依靠节点通用重试再次发送。若审批期间授权过期，恢复到调用前重新检查。最终成果包含周报、校验结果和真实发送回执；流程结束不能补造发送成功。

这展示了 DAG、方法调用、程序块、模型参与、连接授权及审批的分工；不要求每个框内的步骤都成为独立方法。

## 九、建议的验证与接入顺序

以下为待确认方案，不是本轮实施记录。

| 阶段 | 范围 | 通过依据 |
| --- | --- | --- |
| 1．固定图的离线验证 | 用无外部副作用的处理器验证输入映射、依赖、汇合、错误与取消 | 结果和记录符合预期，缺依赖、环、缺输入被拒绝；记录实际资源占用 |
| 2．方法到图的适配 | 将小型非财务方法的六要素、步骤和调用绑定解析为提交图 | 不丢失契约；步骤可包含方法调用及程序块；真实验收可以使方法失败 |
| 3．Action 与 MCP 适配 | 用测试服务验证发现、命名冲突、只读调用、写入审批及错误归一 | 无权限、撤权、过期被阻止；同名不覆盖；默认 read 不误放行写入 |
| 4．账本与恢复 | 接既有任务、审批卡和持久化机制，注入断线、进程退出和重复恢复 | 已发生的副作用不盲目重做，未知结果保留，审批及节点记录可追溯 |
| 5．Codex 两端协同 | 保留原生模型链，分别验证后端 MCP、Codex 直连和必要时的网关 | 当前有效工具、真实绑定和证据能核对，不要求所有调用转发后端 |
| 6．既有专家迁移验收 | 先对固定财务专家验证原步骤、返工、成果和验收语义 | 按项目既有等价迁移要求通过后，才清理旧执行代码 |

方法市场和模板编辑不是最后才考虑的 UI 工作：前几阶段就要明确候选、版本和绑定接口，避免用临时工具名固化接口；完整市场建设再按业务优先级推进。

首期不把模型自动规划全图作为成功条件。先证明已知方法可以可靠执行，再研究模型选方法、动态展开和更复杂的编排；后续扩展继续使用同一任务体系。
