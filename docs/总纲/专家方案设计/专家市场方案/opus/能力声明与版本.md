> 状态：**第一稿，等所有者提要求**（Opus 以 qwen 身份 2026-11-09 写）。从 11-09《专家方案》第一稿拆出来的 knowmart 部分。没动代码。
> 同一套设计的另两份：作者怎么装见 [模板与方法](../../专家孵化方案/opus/模板与方法.md)（knowlab），请专家与执行见 [请专家与执行](../../专家使用方案/opus/请专家与执行.md)（knowbench）。
> 上位决定：[动态专家实施方案](../../参考资料/动态专家实施方案.md) 5.2、10.1（能力声明的统一格式）；[方法与专家包](../../../../design/SDD/architecture/methods.md) 11-03（保留固定财务专家、统一执行体系）。

## 一、要做的

财务专家从"固定八步"改成"模板 + 可挑方法"以后，knowmart 这边要管三件事：

1. 新版本对外说清**能做什么、不做什么**（能力声明），AI 找专家只读这个；
2. **同一位专家出新版本**：旧版本怎么留、用户怎么换；
3. 清单换成新格式以后，knowmart **认得、存得、交得**。

## 二、能力声明（初稿）

沿用已有的 `public_capabilities`（对外，随版本冻结）和 `planning.capability_bindings`（对内，哪个能力由哪些方法支撑，不进目录）：

| 能力 | 对外怎么写（`statement`） | 由哪些方法支撑（`required_units`） |
| --- | --- | --- |
| 历史财务数据与指标 | 营收、利润、现金流等历史数据，毛利率、归母净利率、ROE、现金比率、同比 | 指标与走势；用到三表时加勾稽 |
| 单季数据 | 由累计数换算的单季营收、归母净利润等 | 累计转单季 |
| 季度预测 | 营收、归母净利润的下几个季度预测（季节性同比，带区间与回测） | 累计转单季、勾稽、季节性预测与回测 |
| 结论对照管理层讨论 | 分析结论逐条到年报的管理层讨论里找原文，判支持或不支持，带页码 | 指标与走势、对照管理层讨论 |

**不接**（`exclusions`、`scope.does_not`）：银行、保险、证券（⑱）；估值、评级、目标价；A 股以外。

**条件**（`conditions`）：要明确期间和可核对的报表口径；预测要求历史单季不少于 12 个。只写能力前提，不要求公司预先绑定。

- 能力声明是作者的话：由孵化过程从定型的方法整理，作者确认后随版本发布（实施方案 5.2）。上面是我的初稿，你改。
- AI 找专家时只读公开声明和 `scope`，不读方法、不读绑定；按声明合理选，不证明这位专家一定能把题做完（[请专家与执行](../../专家使用方案/opus/请专家与执行.md) 第四节）。
- 测试记录可以标"这一项已验证到什么范围"，不推成"同类问题都已验证"。
- **用到需要登录的连接器的也要写明**（11-09 定）：要连哪类服务、读写什么、用户要自己有账号；取来的是用户自己的数据，只给这件委托用（[请专家与执行](../../专家使用方案/opus/请专家与执行.md) 第 5.11 节）。
- **用到外部 Agent 的要在声明里写明**（11-09 定）：写哪个外部 Agent、做哪一部分、会把哪类数据交给它、**用户要自己有它的账号、费用由用户付**（11-09 定）；它交回的只当资料，声明里不能把它的结果说成本专家核过的（[请专家与执行](../../专家使用方案/opus/请专家与执行.md) 第 5.10 节）。

## 三、同一位专家出新版本

照所有者 11-08「改造」的意思，不退役、不新建：在 knowlab 给「财务分析与预测」出一个新版本，经审核上架；上架以后新请的都给新版本。

| 情形 | 怎么办 |
| --- | --- |
| 已经在跑、已经跑完的委托 | 不动，照它钉住的旧版本看、照旧跑完（11-03「不静默改钉正在执行的任务」） |
| 用户工作台列表里请过、钉住旧版本的 | 下次请时提示"有新版本"，由用户选；不自动换（第五节第 1 条） |
| 旧版本本身 | 不删，留作历史；新的请入默认给新版本 |
| 买过旧版本授权的 | 照交易时的依据；新版本要不要另付钱，按 knowmart 现有的标价与成交规则算（现在这位专家免费） |

审核和特批放行不能是作者本人（11-08）。所以新版本上架，要另有一位有审核权限的账号来审。

## 四、清单格式

| 项 | 现在 | 改成 |
| --- | --- | --- |
| 固定专家 | `knowbot-manifest/v2`，里面是 `workflow`（八步） | 新的运行契约：固定和动态用同一个格式（模板参数 + 方法目录；固定 = 作者给出顺序、不排计划） |
| 动态专家 | `knowbot-manifest/v3` 外层，内层 `dynamic-methods/v1–v3`（从没对外请过、跑过） | 同上，旧的几版删（G-3，删前核线上库，见 [模板与方法](../../专家孵化方案/opus/模板与方法.md) 第六节） |
| 已发的 v2 | 线上「财务分析与预测」等 | **只留着读**：已有委托和历史记录要能打开；不再出新的 v2 版本（第五节第 2 条） |

- 外层清单由 knowmart 生成 schema，运行契约由 knowbench 生成，knowlab 锁两者（照现在的做法，0052「不手抄」）。
- knowmart 只存、只交清单，不编辑方法；方法主档仍只在 knowlab。
- 新运行契约里再加"连接器绑定"一项：服务类别、MCP 地址、工具清单摘要、准许的工具、鉴权方式（不含凭据）。
- 新运行契约里加"外部 Agent 绑定"一项：对方地址、名片摘要、准许的技能、鉴权方式（不含密钥）；外层清单校验它和能力声明对得上。

2026-11-12 衔接[权限与连接器方案](../../../连接器方案.md#十权限与连接器实现方案2026-11-12-讨论稿)：上述发布绑定是方法的资源要求和适配定义引用，不包含使用者的具体连接、scope 授予事实或动作批准。方法权限与审批分别进入统一六要素第二项、第六项，运行时由 knowbench 绑定用户资源。连接器也可直连外部 API，不一律要求 MCP 地址；方法明确限定的服务不能静默替换。具体契约仍为待实施设计，旧发布版本与摘要不因本次文档修订而改变。

## 五、上架与被请的开关

- knowbench 有一张名单 `KNOWBOT_DYNAMIC_MARKET_OWNERS`：名单里的作者，他的新格式专家上架后才能被请。部署里现在没配，等于全关。
- 照现有做法，先只放你本人，你用新版本跑通保底题再放开。

## 六、knowmart 要改什么

| 地方 | 改什么 |
| --- | --- |
| 清单 | 外层认新运行契约；v2 只读、不再收新的 v2 版本；删动态 v3 的旧内层分支 |
| 目录 | 能力声明的公开投影沿用；目录里每位专家带格式、版本、价格、这位用户有没有授权（已有） |
| 版本 | 列表里"有新版本"的提示要的字段（这位用户钉的版本、当前可请的最新版本）随目录一起回 |

## 七、要你定的

1. **请过旧版本的用户怎么换**：建议下次请时提示有新版、由用户选；也可以直接默认换新版。
2. **固定格式要不要也换**：建议新格式固定和动态共用，线上已发的 `knowbot-manifest/v2` 只留着读、不再出新的 v2 版本；也可以 v2 继续能出版本。
3. **能力声明这四项**对不对、怎么写。
