## 二、两档总览

第 7 条里所有者说了三种情形：逻辑和数据都写死、逻辑写死数据活、逻辑和数据都活。中间那种并进后面那种（第 5.1 小节），分两档：

| | **第一档（本期做）** | **第二档（后期做）** |
| --- | --- | --- |
| 清单（逻辑 + 作者挑选的数据） | 逻辑写死，作者的数据挑定 | 逻辑可以只写方法论，作者的数据只给范围；怎么做、用哪几份，到每件委托上才定 |
| 专家的逻辑 | 写死：作者孵化好的步骤、验收、底稿形状 | 可以活：方法论（做法、判断规则、出处）加工具，临场决定怎么做；也可以照旧写死 |
| 用户的数据 | 用户挑：第 0 步由模型读专家逻辑和问题提出，用户确认 | 同左 |
| 作者挑选的数据 | 交付时一次挑定，全带上，或者没有 | 作者按每件委托的问题挑，作者确认 |
| 几位专家 | 一位；同一项目一次一位，其余排队（10-11 定） | 专家团：团长拆解、成员分工、整合交付 |
| 谁挑专家 | 用户自己挑，或交给 AI 找（第 4.9 节）；找不到就提交孵化请求 | 团长拆解、提议谁做哪块，用户确认 |
| 工作机制 | 一件委托一条线：定数据、确认、开跑、等数据、接着跑 | 任务看板：一件任务一张大卡，成员的子任务是小卡，按列推进 |
| 交互 | 用户确认数据、回答专家的反问和审批 | 统一的交互：谁问、谁来答（用户、作者、专家）、答了自动接着跑 |

**贯穿两档的原则：谁的数据谁挑。** 用户的数据由用户挑；作者的数据由作者挑。模型可以替人提议，最后由数据的主人确认；系统只按他们定的去找、去取，不替任何一方挑。

## 三、几个词

| 词 | 指什么 |
| --- | --- |
| 作者、孵化者 | 在 knowlab 孵化、测试专家的人 |
| 用户、请的人 | 在 knowbench 请专家做事的人 |
| 委托 | 用户请专家做的一件事，knowbench 里的一条任务 |
| 清单 | 逻辑 + 作者挑选的数据，交付时冻结（`knowbot-manifest/v2`）。逻辑包括步骤、验收、底稿形状、规则出处；作者想提示「这一步一般要什么数据」，就写在步骤说明里，是给模型看的文字，不是限制。作者挑选的数据只记引用，数据本身留在 knowbase：第一档是挑定的那几份，第二档是作者给出的可挑范围。用户挑的数据不进清单：清单是所有请这位专家的人共用的（在 knowmart 上架、随版本冻结），用户的数据每件委托不同、只归他自己 |
| 定数据（第 0 步） | 委托开跑后的第一步：模型读专家逻辑和用户问题，提出这件委托要哪些数据，交用户确认 |
| 数据清单 | 第 0 步提出、knowbase 解析过的那张单子：每一样用哪份、为什么、缺什么。用户在上面确认、换、改、去掉、加 |
| 一样数据的描述 | 数据清单上的一行怎么写：类型、主体、期间、版本形态、事项、格式、读法（0049 的维度）。原来是作者声明的格式，现在是第 0 步模型提出的格式 |
| 委托的输入 | 一件委托实际用的：清单的哪一版，加上这次两路各用的哪几份（用户确认的、作者挑定的），开跑时钉住（0043 第 2.9 节「钉住的输入组合」） |

## 四、第一档（本期）

### 4.1 knowlab 和 knowbench 各管什么

所有者第 15 条：「在knowlab里逻辑是孵化来的，数据应该是孵化者挑的。在knowbench里，逻辑是写死的」，数据由用户挑。

| | knowlab（孵化、测试） | knowbench（请专家） |
| --- | --- | --- |
| 逻辑 | 孵化出来，还在改 | 写死：交付的那一版清单 |
| 谁挑数据 | 作者 | 用户 |
| 怎么挑 | 作者写测试问题，第 0 步模型提数据，作者确认、改，钉成测试集（第 4.4 节） | 用户写问题，第 0 步模型提数据，用户确认、改（第 4.3 节） |
| 作者自己的数据 | 在 knowbase 总栏「绑给专家」，交付时随清单冻结 | 原样全带，用户看到份数、看不到内容 |

两边走同一个第 0 步，只是确认的人不同。

### 4.2 清单里写什么

| 部分 | 本期 |
| --- | --- |
| 逻辑（pack） | 照旧：步骤、验收、底稿形状、规则出处 |
| 作者挑选的数据（绑定） | 照旧：交付时挑定的那几份的引用，全带上；也可以没有 |
| 数据需求声明 | **去掉**。作者不知道用户会问什么，限不了（所有者第 16 条）；要提示模型，写在步骤说明里 |

清单 v2 还没推、没发版，就地改，不升 v3。

### 4.3 用户请专家：怎么走

```
请专家页：选专家、写问题 → 建委托（专家自带的资料只写「专家自带 N 份」）
第 0 步「定数据」：沙箱里的模型读专家逻辑和问题，用工具提出要哪些数据
  ├─ 一样都不要 → 直接进第 1 步
  └─ knowbase 在用户能用的范围里解析 → 委托停下，等用户确认数据清单
       用户在委托页或看板卡片上：确认、换一份、改主体或期间、去掉、自己加一样
       → 本人签运行授权、钉住
       ├─ 都齐了 → 进第 1 步
       └─ 有缺的要去取 → 交 knowfeed，委托「等数据」→ 齐了自动接着跑（decisions ⑫）
            └─ 有没取到的 → 停下问用户：照现有的接着做（产出标「数据不全」），还是取消
第 1 步起：照写死的逻辑做
开跑以后还要新数据 → 同一个工具提出 → 停在步骤之间等用户确认；用户也可以选不要，照现有的做
```

逐步说：

1. **请专家页只剩选专家、写问题**（项目、沙箱照旧）。选专家也可以交给 AI（第 4.9 节）。不填代码、不填参数、开跑前不列清单。从首页来的带首页写的那句，从对话来的带对话里最近一句。
2. **第 0 步「定数据」**：在委托的沙箱里跑，用用户自己的模型和 key，knowbench 后端不调模型。模型读到的是：这一版清单的逻辑、用户的问题、专家自带资料的份数（看不到内容）。它用两个工具：
   - **查主体**：按名字查证券代码、机构编号（「宁德时代」→ `300750.SZ`），免得模型自己编代码；名录用 knowfeed 从巨潮取的证券列表（现在只记了代码和 orgId，要加记简称、全称），机构用 knowbase 登记的编号。
   - **提出数据**：每一样按「一样数据的描述」写，外加「为什么要」和「是不是必需」。不设作者的范围（所有者第 16 条），只设防滥用的上限：一次最多 20 样、展开后最多 200 条。
3. **knowbase 解析**：跟现在一样，在用户能用的范围里找（他自己的、买来的、公开原件），每一样回已定、有歧义、待确认（要去取）、采不来、没放开、不能用。主体不限的那几样不按主体筛；找不到就回「暂不能补采」。
4. **用户确认数据清单**：委托停在「等数据」，等谁是用户。确认面板在委托页上，看板卡片上也能直接确认。每一样写用哪份、哪一版、为什么。用户能做的：
   - 已定的换成候选里的另一份；
   - 有几份对得上的选一份；
   - 改主体或期间（改了重新解析）；
   - 去掉；
   - 自己加一样。

   确认时本人在场，当场签运行授权。
5. **去取、等数据、自动接着跑**：照块 6 已经做好的（decisions ⑫）。确认 7 天内有效。
6. **没取到的**：停下问用户，照现有的接着做，或者取消。接着做的，产出标「数据不全」，写明缺什么。这条按 decisions ④ 后半句「必填缺了不算成功」：标了「数据不全」就不算完整的成功。
7. **开跑以后还要新数据**：同一个「提出数据」工具，专家要别家公司的、不限主体的都行；委托在步骤之间停下等用户确认。专家读不到用户没确认过的数据。
8. **作者挑选的数据**：建委托时原样全带，跟用户的数据合成一份运行授权（knowbase 逐项核依据，0043 第 2.7 节）。

### 4.4 knowlab：孵化者挑数据

0043 第 4.2 节「测试集的主体一律由作者给」（E3）改为「**测试集的数据由作者挑**」：

1. 作者写几个测试问题；
2. 每个问题走同一个第 0 步：模型提数据，knowbase 在作者能用的范围里解析，作者确认、换、改、去掉、加，缺的确认去取；
3. 作者确认过的那几份钉成测试集。之后重测，用的是钉住的这几份，不再让模型重提，这样同一测试集测第 1 版、第 2 版才比得出好坏；作者要换，就出测试集的新版本；
4. 第 0 步提了什么、作者改了什么，记进测试证据，供审核看，本期不单独打分；
5. 作者自己的数据照旧在 knowbase 总栏「绑给专家」，测试时一起钉。

孵化过程中试跑也是这样：作者给问题、确认数据。

### 4.5 两路数据怎么进委托

| | 用户的数据 | 作者挑选的数据 |
| --- | --- | --- |
| 谁挑 | 用户：模型提议，用户确认 | 作者：交付时一次挑定 |
| 怎么找 | 第 0 步提出的描述，knowbase 在用户能用的范围里解析 | 不找，清单里冻结的引用原样带上 |
| 用户能做什么 | 确认、换、改、去掉、加；确认去取 | 看到份数，不能换、看不到内容 |
| 运行授权的依据 | 用户放开给 knowbench 的、名下的引用、公开原件 | 冻结的绑定同意 `expert:<专家>@<版本>` |
| 运行中新要 | 专家提，用户确认 | 本期不能新要 |

### 4.6 合规口径

- 第 0 步的模型是用户自己的（用户的 key、在用户的委托里跑），系统不替用户挑；提出的清单由用户确认，正好是 decisions 10-26 第 ⑧ 条的「用户发起任务，系统在约定范围内自动选择和补充」。
- 「用户指定」落在这几处（改数据拓扑第十八节第一处「任务参数里的主体」）：
  - 第 0 步用户确认过的数据清单（连同提出的原样、用户改了什么，留痕）；
  - 一次确认的取得清单（确认编号、任务编号、清单快照、供给条件快照）；
  - 运行中新要的、用户确认过的；
  - 作者挑选的：作者的冻结同意。

### 4.9 请专家的两种方式：用户自己请、AI 请（10-28 定）

所有者第 20 条：请专家可以用户自己请，也可以 AI 请；AI 先拿用户的问题去 knowmart 匹配专家，合适就请，都不合适就自动提交孵化请求。第 21 条同意 Opus 的三点补充（见下面第 3、4 条和「什么时候做」）；第 23–25 条定了找不到时怎么处理（第 4–7 条）。

**用户自己请**：照第 4.3 节。

**AI 请**：

```
请专家页：写问题，选「让 AI 找」
找专家：在用户的项目里，用户自己的模型读问题和 knowmart 上专家的公开信息
  ├─ 有合适的、不用另付钱（作者是用户自己、已买过授权、标价为零）→ 直接请，建委托，进第 0 步
  ├─ 有合适的、要另付钱 → 停下，给用户看候选（最多 3 位）、理由、价格；用户点了才请
  └─ 都不合适 → 给用户一张卡，两件都不自动跑，用户点哪件做哪件，可以都点：
       ├─ 让我的模型直接答（用户自己的模型，回答标「不是专家」）
       └─ 孵化一个专家（knowlab 里以用户的名义建申请；同时提议挂 knowmart 需求，用户点「发布」才挂）
     卡上把更合适的那件标「推荐」，附一句理由
```

逐条说：

1. **在哪跑**：在用户的项目里，用用户自己的模型和 key，同第 0 步；knowbench 后端不调模型。具体挂成一件不带专家的小委托，还是工作对话里的一个工具，实现时按 runner 定。
2. **看什么、按什么匹配**：给模型一个「找专家」工具，查 knowmart 的目录，每位专家回：名称、一句话介绍、接什么 / 不接什么 / 不接的去哪问（清单的 `pack.scope`）、版本、价格、用户有没有授权。只给公开信息，看不到别人的清单内容和数据。匹配只按专家自己写的范围和用户的问题，平台不排序、不加权、没有推广位。模型交回的每位候选都写理由：问题的哪一部分落在它的「接什么」里。
3. **花钱的由用户定**：不用另付钱的直接请，委托页写明「AI 替你请了某专家，理由……」，用户可以换；要另付钱的先停下给用户看，点了才请。道理同「谁的数据谁挑」。
4. **找不到时给用户一张卡，两种处理**（第 23、25 条）：

```
没有合适的专家
  [让我的模型直接答]   一次性的问题适合；花你的模型费用；回答标「不是专家」
  [孵化一个专家]       会反复问、要固定口径和验收、想给别人用的适合；建申请不花钱
  推荐：孵化一个专家。理由：你问的是「每季度……」，是会反复用的方法
```

   两件都不自动跑：直接答要花用户的钱；孵化申请若每个找不到专家的问题都自动建，用户的 knowlab 会堆满一次性的问题。用户点哪件做哪件，可以都点（先直接答，再孵化）。
5. **让我的模型直接答**：在这个项目里开一段聊天（knowbench 10-11 定的三种对话之一；10-29 所有者：「直接答按聊天」），用用户自己的模型和 key，平台在这里只是工具，不往里塞自己的分析方法。回答照实标明「这是你的模型直接答的，不是专家，方法没经过测试」。（Opus 前一轮说「通用模型直接答就碰 C-L1」说重了：模型和 key 是用户的，方法不是平台写的。）
6. **孵化一个专家**：knowlab 里以用户的名义建一个种类为「问题」的申请，种子是这句问题，记着从哪个项目、哪件事来；申请只有用户自己看得到、建了不花钱；往下照 [专家孵化方案](专家孵化方案.md) 第十三节。用户先点过直接答的，那份回答可以附进申请当参考，但它是模型写的，进工作稿只能算提议，作者接受才算（decisions ⑮）。同一步提议把需求挂到 knowmart 上，让别的作者来供给：需求会公开展示，问题原文是用户的，外发即公开，所以 AI 先写一段描述，用户看过点「发布」才挂出。
7. **标推荐**（第 24、25 条）：找专家的那一轮模型没找到合适的，顺手看一眼问题，判断哪件更合适，写一句理由一起交回，不另调模型。一次性的、问个事实或看一眼的，推荐直接答（如「宁德时代 2025 年的营业收入是多少」）；会反复问、要固定口径和验收、想给别人用的，推荐孵化（如「每季度按固定口径对比几家电池公司的毛利率并预测下季」）。推荐的按钮高亮、下面一行写理由，只是标出来，由用户点。

**合规**：「不选、不推荐」（C-L1，第 5.3 节第 2 条）。找专家由用户发起，用用户自己的模型，只按专家自述的范围匹配，平台不给排名；要另付钱的由用户点。这一段和 [专家孵化方案](专家孵化方案.md) 第四节那段一起补进 0026「五、合规分析」。

**第二档接着用**：团长挑专家就是这个的多位版；「找专家」工具和匹配依据第二档照用（合第 4.8 节「本期就有真用处」）。

**什么时候做**：设计本期定；实现排在自助孵化之后（专家孵化方案第十五节第 6 步）。孵化通路有了，找不到时提交的请求才有地方落。

## 五、第二档（后期）

### 5.1 为什么把「作者按问题挑数据」并进来

1. **它是第二档的一部分。** 第二档里数据是活的，按「谁的数据谁挑」，团里每位专家的作者照样要按问题挑自己的数据，这套机制第二档本来就要做。
2. **底下用的是同一套东西。** 作者挑数据时，委托要停下等作者、看板上要显示「等作者」、作者要有地方答，这正是看板和交互要做的。单独先做，就得先搭一套小的、到第二档再拆，是「分开做要返工」的情形。
3. **两个维度各管各的。** 第二档出新版本清单时，「逻辑方式」（写死 / 方法论）和「作者的数据怎么用」（挑定 / 每件委托由作者挑）是两个独立的维度；逻辑写死、只让作者挑数据的专家照样能用。

### 5.2 要做成什么样

**专家**：作者写方法论（做法、判断规则、出处）和工具，可以带写死的步骤，也可以只给方法、由模型临场决定怎么做。

**专家团**：一位团长加几位成员。参照 WorkBuddy：团长拆解任务、分配给成员、成员执行、团长整合交付。设想的流程：

```
用户写问题 → 团长拆成几张卡、提议谁做哪张 → 用户确认分工
  → 各张卡由成员做；卡要停下时等人：用户确认数据、作者挑数据、回答反问、成员之间交接
  → 团长整合，交给用户
```

**任务看板**（所有者的设想）：

- 一件任务一张大卡，成员的子任务是大卡下的小卡；
- 列：排队、在跑、等你、等别人、完成、失败；
- 卡上写：谁在做、等谁、等什么、花了多少钱（10-04 定的随时跳动的金额与停止按钮，I9）；
- 等你的那几张，在卡上直接答。

**交互机制**：一套统一的交互记录，记谁问、谁来答、问什么、答了什么；答的人可以是用户、作者、专家；答了，那张卡自动接着跑。现有的反问、审批、数据确认都收进来。

**作者按问题挑数据**：

1. 用户请专家；
2. 作者收到这件委托要挑数据的请求（能看到什么见第 5.3 节第 3 条）；
3. 作者在 knowlab 的待办里，从自己给出的可挑范围里挑这次用哪几份；
4. 这期间那张卡停在「等作者」；
5. 作者挑完，钉住、续签授权、接着跑。

清单里冻结的是作者给出的可挑范围，每次挑定的那几份记在委托的输入上，不进清单。授权多一个依据：作者对这件委托的那次挑选，签发人记作者挑选的编号；knowbase 照样核「只能是冻结绑定里的」。

### 5.3 动手前要先定的问题

1. **逻辑活了，专家这份资产是什么？** knowlab 现在测的是固定步骤，第二档要改成按结果测；knowmart 卖的、版本号怎么定，都跟着变。
2. **谁拆解、谁挑专家？** 平台的团长替用户挑哪位专家、怎么组合，碰「不选、不推荐」（C-L1）和「方法来自用户」。本稿倾向：团长跑在用户自己的会话里、用用户的模型，分工由用户确认。挑一位专家的做法第一档已定（第 4.9 节）；要定的是多位怎么拆、怎么组合。
3. **作者挑数据时能看到什么？** 用户的问题现在只给用户自己（数据拓扑第十八节「结果给谁：用户自己」）。作者要看问题才能挑，就得在请专家时告诉用户「作者会看到你的问题」并征得同意；或者作者只看第 0 步确认过的数据清单（问的是哪家公司、哪几期），不看原问题。
4. **作者不在线、迟迟不挑怎么办？** 超时以后是不带那几份接着跑，还是委托失败。
5. **作者能不能事先写好挑选规则，由系统照规则代挑？** 所有者第 5 条说的是「还要作者确认挑选」；代挑算不算作者确认，要定。
6. **同一项目一次一位（10-11）怎么改？** 那条的理由是两位同时改同一文件夹会互相覆盖。团里并行，要么成员各写各的子目录、由团长合并，要么成员只读、只有团长写。
7. **团里成员之间传的产出算什么？** decisions 10-26 第 ⑥ 条：产出不进解析，转为数据由用户做。团内交接是不是例外，要定。
8. **费用**：多位专家、多轮调用，费用会是单个专家的几倍（WorkBuddy 说 3 到 5 倍）。上限、显示、谁付，要定。

2. **要另付钱的专家先给用户看候选和理由，用户点了才请**；不用另付钱的直接请，用户可以换；
3. **找不到时给用户一张卡：「让我的模型直接答」「孵化一个专家」，两件都不自动跑、可以都点，卡上标推荐与理由**；直接答用用户自己的模型、标「不是专家」；孵化申请只有用户看得到、不花钱，可附直接答的回答作参考（算提议）；挂需求要用户看过描述点「发布」（第 23–25 条）；
4. **设计本期定，实现排在自助孵化之后**。


第二档的八个问题（第 5.3 节）不用现在定，第一档验收后逐条过。

## 八、市面参照

- WorkBuddy 的专家是「人设 + 方法论 + 工具链」，不是写死的步骤；只处理用户在对话里给的和上传的文件；要连外部服务时弹授权卡片，授权后任务自动继续。见 [专家中心（官方文档）](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Expert-Center)、[WorkBuddy Enterprise 专家（腾讯云）](https://cloud.tencent.com/document/product/1831/134393)。
- WorkBuddy 的专家团由团长拆解、分配、并行执行、整合交付；用户中途能取消、追加要求；教程建议先让团长列任务树再开跑。官方文档里没有「任务看板」，看板是所有者的设想。见 [专家与专家团完整指南](https://github.com/KimYx0207/AI-Coding-Guide-Zh/blob/main/docs/workbuddy/WB-03-WorkBuddy%E4%B8%93%E5%AE%B6%E4%B8%8E%E4%B8%93%E5%AE%B6%E5%9B%A2%E5%AE%8C%E6%95%B4%E6%8C%87%E5%8D%97.md)。
- WorkBuddy 企业版的「项目」：人和数字员工在同一个项目里共享上下文，任务在流水线里由人和 AI 接力推进。见 [量子位报道](https://www.qbitai.com/2026/06/430758.html)。
- 「先由模型出计划、人确认再动手」是常见做法（编码智能体的计划模式，先列计划、用户批准后执行），第 0 步照这个思路：模型提数据清单，用户批准再取、再跑。凭记忆，未逐一核实。
- 以下也凭记忆，第二档动手前再核：Linear 把任务单派给智能体，人在任务单评论里和它来回；GitHub 的编码智能体接任务单后交 PR，人用评审意见推着它改；Vibe Kanban 把智能体的任务放在看板上按列推进，中间有人审一步。
