# 采集讨论记录：需求、供给、切合

> 2026-10-26 起。所有者发现第四版漏了一大块：「无论是用户还是应用，它提出的采集请求，我们怎样满足或者说后端怎么处理？……用户给个网址不是东方财富网咋办？采集的内容如何分门别类的存储，这个涉及到数据库和向量数据库的设计吧」。和数据拓扑那次一样，逐条讨论、记下所有者原话，讨论完再改进 [数据拓扑](../数据拓扑.md) 第七、十六节与 SDD 0043、0045。

## 总的规矩（所有者 10-26）

- **需求和供给分开**：「我觉得你把需求和供给混在一起，根据我们上面讨论好的架构，这其实是分开的，当然最后要切合。但首先要分开」。按三步谈：先需求侧，再供给侧，最后切合。需求只用统一词表说「要什么」，不知道渠道；供给用同一套词表说「能取到什么」，不知道是谁要的；两边共用的只有词表（0043 归 knowbase 管的那一套）。
- **写通用的结构，不以巨潮为框架**：「你上面老是巨潮，不要再这样，那时以前留下来的，它只是一个需求实例而已，我们在写同样架构（你说的原代码中的证券专线，根本不应给存在，等通用写好后，它仅仅是一个具体需求实例而已）」。现在代码里的证券专线（巨潮、东方财富 F10 两个写死的采集器、证券请求与关注清单）不再单独存在：通用的需求与供给写好后，「某公司某年年报」只是一条需求实例，巨潮只是供给侧登记的一个渠道。

## 1. 四种需求都要做（10-26 定）

所有者：「不，都要做。我们一个问题一个问题解决」。

| 种类 | 是什么 | 例子 |
| --- | --- | --- |
| 精确描述 | 主体、类型、期间都说清楚 | 某公司某年年报、最近 8 个季度的三张报表 |
| 给网址 | 用户指着某个页面或文件说「取这个」 | 某政府网站的一份政策 PDF、某篇网页 |
| 订阅 | 一次说好，以后有新的就自动取 | 某公司以后的临时公告、某栏目页有更新、某 RSS 源 |
| 按主题找 | 用户只给话题，先列出候选、用户勾了再取 | 「2024 年以来新能源汽车补贴的政策文件」 |

（「按主体」要数据属于精确描述；「按主题」是按话题、关键词找。）

## 2. 需求单里写什么（10-26 定，提出主体一节待所有者确认）

所有者：「都按你的建议，记下来」。

**公共部分**（四种都有）：需求单编号；种类；提出主体（见下）；确认（knowbase 记的确认编号与时间）；要的读法（原件、正文文字、抽好的表，可多选，决定怎样算办成）；最晚什么时候要；说明（选填，只给用户自己看、留作审计）；需求项（一张单可以有多项，每项按种类写）。

**一张单对应一次确认**：一件任务缺的几份合成一张单、几个需求项，用户点一次；每项各有状态，可以单独取消。

**各种类的需求项**：

| 种类 | 写什么 |
| --- | --- |
| 精确描述 | 主体（证券代码含市场；不是上市公司的，如发文机关，也用词表里的主体编号）、类型（词表）、期间（报告期或日期区间）、版本要求（最新、截至某日已披露、指定某一版）、口径（报表类：合并或母公司） |
| 给网址 | 网址（一个或几个）；范围（只这一页，或这一页加它直接链到的文件，同一网站、只往下一层，不爬整站）；用户声明「公开页面、不用登录」；预填的描述（选填，入库后用户确认，以后能被解析到） |
| 订阅 | 订阅什么（三选一：按描述订，只有主体与类型、不写期间，从订阅那天起往后新发的；按网址订，栏目页或 RSS 源有新的；按主题订，定期重新找）；多久查一次（用户希望的，供给侧有最快下限）；起止（必须有截止日，最长一年，可以续）；上限（每月最多多少份，按用户配额）；有新的怎么办（直接取并通知；按主题订的见下）；落到哪（展示给哪个应用，默认是提这条订阅的应用） |
| 按主题找 | 主题（一句话或几个关键词）；范围（时间、来源类型如政府 / 交易所 / 媒体、可指定几个网站、语言）；要多少候选（如最多 20 条） |

- **订阅的确认**：建订阅时确认「这个范围内往后新的都要」，范围内每次取不再逐份确认。**按主题订阅每一轮的候选都要用户勾**（候选是平台找出来的）。
- **按主题找的结果是候选清单，不是数据**：用户勾了哪几条，每条变成一个新的需求项（给网址或精确描述），再确认一次才去取。
- **需求单里不写**：渠道、采集器、作业（归供给侧）；许可档（供给侧按渠道定）。

**提出主体**（所有者：「好像缺少一个重要的：提出需求的主体」；下面是 Opus 拟的，待所有者确认）：

| 字段 | 写什么 | 为什么 |
| --- | --- | --- |
| 提出方 | 谁发起：① 用户本人在 knowfeed web端亲手提；② 应用代用户提（哪个应用、哪件任务或草稿）；③ 专家运行中提（哪位专家哪一版、哪件委托；专家是特殊的应用）；④ 订阅按期自动生成（哪条订阅） | 审计在什么场景、谁提的；提出方不同，确认规矩不同 |
| 归属用户 | 数据给谁、谁确认、配额算谁的；永远是一个用户（平台账号也是用户） | 「用户指定」的证据落在他身上；配额、空间、通知按他算 |
| 代办链 | 提出方到归属用户之间的每一层，如「专家 X 第 3 版 → 委托 123 → 用户甲」 | 谁替谁提、该通知谁、谁能撤 |

确认规矩随提出方：用户本人亲手提的，提交即确认；应用代提的，列清单、用户确认一次；专家运行中提的，必须经用户确认，专家不能替用户确认；订阅生成的，建订阅时已确认范围，范围内不再确认（按主题订阅的候选每轮仍要勾）。

## 待谈

- 需求侧：需求从哪里来、提的时候带什么；需求的一生（提出、确认、受理、等待、完成、取消、失败，订阅多出来的）；需求方拿到什么、怎么知道办成了。
- 供给侧：来源目录、适配器、调度、原件留存、加工、质检、交付 knowbase；东方财富 F10 怎么处理（评审回执 E1，Opus 建议停掉）。
- 切合：一份需求怎么找到能满足它的供给，找不到怎么回。
- 存储：怎么分门别类地存；关系库与向量库（现在向量在 RAGFlow，数据拓扑第 16.2 节写的是 PostgreSQL，要定）。
- 评审回执 E2–E4 待所有者定。
