# 采集讨论记录：需求、供给、切合

> 2026-10-26 起。所有者发现第四版漏了一大块：「无论是用户还是应用，它提出的采集请求，我们怎样满足或者说后端怎么处理？……用户给个网址不是东方财富网咋办？采集的内容如何分门别类的存储，这个涉及到数据库和向量数据库的设计吧」。和数据拓扑那次一样，逐条讨论、记下所有者原话，讨论完再改进 [数据拓扑](../数据拓扑.md) 第七、十六节与 SDD 0043、0045。

## 总的规矩（所有者 10-26）

- **需求和供给分开**：「我觉得你把需求和供给混在一起，根据我们上面讨论好的架构，这其实是分开的，当然最后要切合。但首先要分开」。按三步谈：先需求侧，再供给侧，最后切合。需求只用统一词表说「要什么」，不知道渠道；供给用同一套词表说「能取到什么」，不知道是谁要的；两边共用的只有词表（0043 归 knowbase 管的那一套）。
- **写通用的结构，不以巨潮为框架**：「你上面老是巨潮，不要再这样，那时以前留下来的，它只是一个需求实例而已，我们在写同样架构（你说的原代码中的证券专线，根本不应给存在，等通用写好后，它仅仅是一个具体需求实例而已）」。现在代码里的证券专线（巨潮、东方财富 F10 两个写死的采集器、证券请求与关注清单）不再单独存在：通用的需求与供给写好后，「某公司某年年报」只是一条需求实例，巨潮只是供给侧登记的一个渠道。

## 1. 四种需求都要做（10-26 定）

所有者：「不，都要做。我们一个问题一个问题解决」。

| 种类 | 是什么 | 例子 |
| --- | --- | --- |
| 精确描述 | 主体、类型、期间都说清楚 | 某公司某年年报、最近 8 个季度的三张报表 |
| 给网址 | 用户指着某个页面或文件说「取这个」 | 某政府网站的一份政策 PDF、某篇网页 |
| 订阅 | 一次说好，以后有新的就自动取 | 某公司以后的临时公告、某栏目页有更新、某 RSS 源 |
| 按主题找 | 用户只给话题，先列出候选、用户勾了再取 | 「2024 年以来新能源汽车补贴的政策文件」 |

（「按主体」要数据属于精确描述；「按主题」是按话题、关键词找。）

## 2. 需求单里写什么（10-26 定）

所有者：「都按你的建议，记下来」。

**公共部分**（四种都有）：需求单编号；种类；提出主体（见下）；确认（knowbase 记的确认编号与时间）；要的读法（原件、正文文字、抽好的表，可多选，决定怎样算办成）；最晚什么时候要；说明（选填，只给用户自己看、留作审计）；需求项（一张单可以有多项，每项按种类写）。

**一张单对应一次确认**：一件任务缺的几份合成一张单、几个需求项，用户点一次；每项各有状态，可以单独取消。

**各种类的需求项**：

| 种类 | 写什么 |
| --- | --- |
| 精确描述 | 主体（证券代码含市场；不是上市公司的，如发文机关，也用词表里的主体编号）、类型（词表）、期间（报告期或日期区间）、版本要求（最新、截至某日已披露、指定某一版）、口径（报表类：合并或母公司） |
| 给网址 | 网址（一个或几个）；范围（只这一页，或这一页加它直接链到的文件，同一网站、只往下一层，不爬整站）；用户声明「公开页面、不用登录」；预填的描述（选填，入库后用户确认，以后能被解析到） |
| 订阅 | 订阅什么（三选一：按描述订，只有主体与类型、不写期间，从订阅那天起往后新发的；按网址订，栏目页或 RSS 源有新的；按主题订，定期重新找）；多久查一次（用户希望的，供给侧有最快下限）；起止（必须有截止日，最长一年，可以续）；上限（每月最多多少份，按用户配额）；有新的怎么办（直接取并通知；按主题订的见下）；落到哪（展示给哪个应用，默认是提这条订阅的应用） |
| 按主题找 | 主题（一句话或几个关键词）；范围（时间、来源类型如政府 / 交易所 / 媒体、可指定几个网站、语言）；要多少候选（如最多 20 条） |

- **订阅的确认**：建订阅时确认「这个范围内往后新的都要」，范围内每次取不再逐份确认。**按主题订阅每一轮的候选都要用户勾**（候选是平台找出来的）。
- **按主题找的结果是候选清单，不是数据**：用户勾了哪几条，每条变成一个新的需求项（给网址或精确描述），再确认一次才去取。
- **需求单里不写**：渠道、采集器、作业（归供给侧）；许可档（供给侧按渠道定）。

**提出主体**（所有者：「好像缺少一个重要的：提出需求的主体」；Opus 拟的；所有者：「可以」）：

| 字段 | 写什么 | 为什么 |
| --- | --- | --- |
| 提出方 | 谁发起：① 用户本人在 knowfeed web端亲手提；② 应用代用户提（哪个应用、哪件任务或草稿）；③ 专家运行中提（哪位专家哪一版、哪件委托；专家是特殊的应用）；④ 订阅按期自动生成（哪条订阅） | 审计在什么场景、谁提的；提出方不同，确认规矩不同 |
| 归属用户 | 数据给谁、谁确认、配额算谁的；永远是一个用户（平台账号也是用户） | 「用户指定」的证据落在他身上；配额、空间、通知按他算 |
| 代办链 | 提出方到归属用户之间的每一层，如「专家 X 第 3 版 → 委托 123 → 用户甲」 | 谁替谁提、该通知谁、谁能撤 |

确认规矩随提出方：用户本人亲手提的，提交即确认；应用代提的，列清单、用户确认一次；专家运行中提的，必须经用户确认，专家不能替用户确认；订阅生成的，建订阅时已确认范围，范围内不再确认（按主题订阅的候选每轮仍要勾）。

## 3. 需求从哪里来、提交带什么、收到先核什么（10-26 定）

所有者：「都按你的建议，记下来」。

**入口只有两个**（所有者最早定的）：knowfeed web端、各应用调 knowfeed 的接口；另有 knowfeed 内部按订阅生成。

| 入口 | 场景 | 提出方 | 通常是哪种需求 |
| --- | --- | --- | --- |
| knowfeed web端 | 用户自己来提 | 用户本人 | 四种都有 |
| 应用接口 | knowbench 请专家，解析发现缺数据 | 应用代提 | 精确描述 |
| 应用接口 | knowbench 聊天、工作里用户说「把这个网页取来」「找找关于某某的政策」 | 应用代提 | 给网址、按主题找 |
| 应用接口 | knowbench 委托运行中专家发现还缺 | 专家（经 knowbench） | 四种都可能，必须经用户确认 |
| 应用接口 | knowlab 生成测试集，作者给了公司、按声明展开后缺的 | 应用代提 | 精确描述 |
| 应用接口 | 项目里用户说「以后这家公司的公告都跟着取」 | 应用代提 | 订阅 |
| knowfeed 内部 | 订阅到期该查，按订阅生成本轮需求 | 订阅 | 由订阅的内容定 |

- 专家的需求由 knowbench 代为提交，提出方记专家、代办链记到委托和用户；专家不直接调 knowfeed，不能替用户确认。
- knowbase web端不是入口：用户在总栏想订阅，给链接跳到 knowfeed web端去提。
- knowmart 的「需求条目」（买家在市场上发的想买什么，由卖家响应）不是这里的采集需求。
- 不能提的：平台运营不能替用户提（平台账号作为用户可以给自己提）；knowbase 不提；knowfeed 只在执行订阅时生成，不凭空生成。

**提交时带什么**：

| 带什么 | 用户在 knowfeed web端亲手提 | 应用代提（含专家） | 订阅生成 |
| --- | --- | --- | --- |
| 证明谁、谁同意 | 本人登录令牌；提交即确认，knowfeed 凭本人令牌请 knowbase 记确认 | 应用服务身份（按关系校验，同 knowbase、knowmart 现做法）+ knowbase 的确认编号 | 订阅编号（建立时已确认范围） |
| 提出方、代办链 | 用户本人 | 应用、任务或草稿；专家提的加专家哪一版、哪件委托 | 哪条订阅 |
| 需求单内容 | 全部字段 | 同左 | 本轮需求项 |
| 幂等钥匙 | 页面生成 | 应用生成，同一件任务重发不成两张单 | 订阅编号 + 轮次 |
| 进度通知给谁 | 用户本人（knowfeed web端、站内信） | 提需求的应用与那件任务 | 用户本人 + 订阅的「落到哪」 |

**收到先核什么**（只核需求这一侧）：① 格式（字段、词表版本、需求项数上限）；② 凭证（确认编号真、没过期、条目对得上，问 knowbase；应用服务身份能不能替这个用户提；订阅在不在有效期）；③ 配额（请求频率、在途需求单数、订阅条数）；④ 重复（同一幂等钥匙回原单）。渠道有没有、能不能取属于供给侧，到切合再查。

## 4. 需求的一生（10-26 定）

所有者：「都按你的建议，记下来」。只讲需求方看得到的状态；作业怎么跑归供给侧。

**需求项的状态**（一张单的各项各走各的）：

```text
待确认 ──确认──▶ 已提交 ──核过──▶ 已受理 ──找到供给──▶ 取数中 ──▶ 已就绪
   │               │                 │                    │
   └─不确认作废    └─核不过：已拒绝   └─没有供给：无法满足  ├─▶ 部分就绪（原件到了，表没抽出来）
                                                          ├─▶ 失败（附原因）
                                                          └─▶ 超时
   任何没结束的状态 ──用户或应用取消──▶ 已取消
```

| 状态 | 意思 | 需求方看到 |
| --- | --- | --- |
| 待确认 | 应用列好清单，等用户点 | 确认清单 |
| 已提交 | knowfeed 收到，正在核格式、凭证、配额 | 「已提交」 |
| 已拒绝 | 核不过 | 一句原因（如「确认已过期，请重新确认」「本月配额用完」） |
| 已受理 | 核过，交给切合 | 「已受理」 |
| 无法满足 | 切合找不到能满足的供给 | 原因（如「渠道里没有这一份」「这类数据还取不到」）和能怎么办（如「可以自己上传」） |
| 取数中 | 找到供给，正在取 | 进度、预计时间 |
| 已就绪 | knowbase 回执：已入库、要的读法都有了 | 「已就绪」，附资料链接 |
| 部分就绪 | 要的几种读法只到了一部分 | 哪种到了、哪种没到、为什么 |
| 失败 | 供给侧重试后仍不行 | 原因 |
| 超时 | 到最晚时间还没就绪 | 「超时」；之后数据到了照样进他的栏、另发通知，不自动重启任务 |
| 已取消 | 用户取消，或任务取消由应用撤 | 「已取消」 |

规矩：
1. 只往前走，不改不回退：迟到的事件不能把「已取消」「超时」改成「已就绪」（评审 L2-06）。
2. 不能改，只能撤了重提：换期间、换网址就取消这一项、提新的一项，新旧关联、历史都留（同 0037「结果定了不改」）。
3. 「再试一次」：失败、超时、无法满足的可以再试，生成挂在原项下的新项；确认还在有效期（7 天）内不用再确认，过了要重新确认。
4. 需求单的状态由各项汇总：每项都结束才算结束，结果是「几项就绪、几项失败……」。

**订阅多出来的**：
- 订阅的状态：生效中、暂停、已到期、已取消、被停用（来源没了、许可变了、账号被停等，附原因）。
- 每一轮：到点查一次，记查的时间、发现几份新的、取了几份、因超上限没取几份；取的那几份生成提出方为「订阅」的需求单，照上面走。
- 到每月上限：本月停取、通知用户，下月自动恢复。
- 快到期：提前通知（拟提前 14 天）；续订 = 重新确认一次范围。
- 按主题订阅：每轮候选列给用户勾，每轮候选有期限（拟 7 天），过期没勾作废。

**按主题找多出来的**：状态是正在找 → 候选已出 → 已结束。候选清单有期限（拟 7 天）；用户勾的每条生成一个新的需求项（给网址或精确描述）走确认；勾完或候选过期，这条主题需求结束。

**需求方怎么知道进展**：
- 应用：每次状态变化，knowfeed 经发件箱通知提需求的应用，应用据此恢复任务或报失败；也可以按需求单编号随时查。
- 用户：站内信；knowfeed web端「我的需求」一页列出全部需求单与订阅，能看状态、取消、再试。
- 办成以后：数据在 knowbase、归他名下（公开披露是第二区的一条引用，其他是第一区的一份资料），按需求单的「落到哪」展示给对应应用。

期限（候选 7 天、续订提前 14 天、确认有效期 7 天）先按拟的写，实现时再调。

## 5. 供给侧：渠道（10-26 定）

所有者：「都按你的建议，记下来。但是，我认为规矩可以不用那样：它和其它一样，可以通过审核来解决，而采集本身不用管」。

供给侧按五点谈：渠道；适配器；作业与调度；原件留存与加工；质检与交付。

**渠道是什么**：能取到数据的地方，加上取的方式和规矩；供给侧的基本单位，登记在「来源目录」里，由 knowfeed 管理端维护。加渠道是登记一条记录，不改代码；只有全新的取法才写新的适配器。

**按取法分四大类**（不按网站分）：

| 大类 | 是什么 | 举例 |
| --- | --- | --- |
| 有目录的披露渠道 | 有可查询的目录：按主体、类型、期间能列出有哪些文件 | 各国交易所与证监会指定的披露网站、政府统计数据接口 |
| 订阅源 | 本身按时间发布新条目 | RSS、Atom、栏目页 |
| 通用网页 | 没有目录，只能按网址取 | 用户给的任意公开网址 |
| 搜索服务 | 输入话题，返回候选网址 | 搜索引擎接口、站内搜索 |

**登记一个渠道写什么**：名称、大类；能提供什么（用统一词表写：类型、主体范围、期间、能给的读法，切合时靠它和需求对上）；怎么取（用哪个适配器加配置，不写进代码）；条款与许可（条款链接、审核结论、取来的数据属于哪一档许可）；规矩（限速、每日上限、能否用无头浏览器渲染等，审核时定、写进配置）；状态（待审、白名单、停用附原因）；审核记录（谁、何时、凭什么，第一道关按渠道审一次）。

**通用网页是兜底渠道，规矩和别的渠道一样由审核定**（所有者）：
- 按网站（域名）审，一个网站审一次：用户给的网址落在没登记的网站上，自动建一条「待审」渠道；管理端审过后定能不能取、许可哪一档、限速多少，以后同一网站照这条走。
- 采集这一层只管取，不管合规；限速、渲染等是审核定下的渠道配置，不在采集代码里写死。
- 用户给的网址落在已登记渠道上，按那个渠道的规矩与许可走。
- 没审过的网站，需求**等审核**（所有者：「等审核，按你的建议，记下来」）：需求项停在「已受理」、附「这个网站还在审核，审过就取」，审不过转「无法满足」并写明原因；管理端多一个按网站审的「待审网站」队列。

（Opus 原来拟的「通用网页只取公开页、不登录、守 robots、许可固定只许本人用」作废，改由审核定。）

## 6. 供给侧：适配器（10-26 定）

所有者：「都按你的建议，记下来。东方财富作为一个实例吧」。

**统一四个动作**（每个适配器只做它会的，对外样子一样）：

| 动作 | 输入 | 输出 | 谁用 |
| --- | --- | --- | --- |
| 列 | 一条描述（主体、类型、期间） | 渠道里符合的条目：渠道内编号、标题、发布时间、网址、版本线索（如是否更正版） | 精确描述；确认前查「渠道里有没有」 |
| 取 | 一个条目或一个网址 | 原件：内容、内容类型、取回时间、来源网址 | 所有需求 |
| 看新的 | 上次看到哪里（游标） | 游标之后新出的条目、新游标 | 订阅 |
| 搜 | 话题和范围 | 候选：标题、网址、摘要、日期 | 按主题找 |

**四类通用适配器，对应渠道四大类**：

| 适配器 | 会哪几个动作 | 渠道登记时配什么 |
| --- | --- | --- |
| 目录型 | 列、取、看新的 | 查目录的接口与参数模板；主体怎么换成渠道自己的编号；词表类型对应渠道的哪个分类 |
| 订阅源型 | 看新的、取 | RSS、Atom 地址；或栏目页地址加列表在页面上的位置 |
| 通用网页型 | 取 | 要不要用无头浏览器渲染、怎么抽正文；需求要「往下一层」时跟哪些文件链接 |
| 搜索型 | 搜 | 用哪个搜索接口（钥匙在密钥库） |

- 大多数渠道只靠配置接上；目录格式特别的，写一个**渠道插件**，只管这个渠道的映射与解析（换编号、解析列表），排队、限速、留存、交付由框架统一做。
- 无头浏览器渲染在 knowfeed 自己的工作进程里跑，不另养外部爬虫。

**现有代码怎么收进来**：
- 通用采集里的 RSS、Atom、API、网页变化监测收进订阅源型与目录型；Scrapy、Playwright 两个空壳改为通用网页型的渲染能力。
- 证券专线不再单独存在：巨潮变成一条目录型渠道的登记加一个插件（证券代码换机构编号、解析公告列表）；**东方财富 F10 也作为一个渠道实例**（所有者，取代评审回执 E1 里 Opus「停掉」的建议），和别的渠道一样过渠道审核、由审核定许可档；取来的数据进提需求的用户（含平台账号）的第一区。现有 F10 数据集照数据拓扑第十九节第 8 条迁进平台账号第一区。

## 7. 供给侧：作业与调度（10-26 定）

所有者：「都按你的建议，记下来」。

**作业分几种**：

| 作业 | 做什么 | 按什么去重、共享 |
| --- | --- | --- |
| 列 | 到目录型渠道查「有哪些」 | 渠道 + 描述，短时缓存，所有人共用 |
| 下载 | 把一个条目或网址取回来 | 渠道 + 渠道内编号 + 版本；通用网页按规范化后的网址；跨用户共享 |
| 加工 | 正文抽取、按页文字、抽表、自动生成描述 | 原件版本 + 加工器版本与配置；跨用户共享 |
| 看新的 | 订阅的一轮查看 | 渠道 + 订阅对象；订同一个东西的人共用一次查看，结果分给每条订阅 |
| 搜 | 按主题搜一次 | 每个需求一次；同样的话题与范围短时缓存 |

需求依据挂在合流的请求上，请求挂在共享的作业上；所有需求依据都撤了才取消作业，还有别人要就照跑。

**一次执行（尝试）**：每次都记开始、结束、结果、出错原因。出错分几种：渠道临时出错、网络断了 → 隔一段重试，间隔逐次拉长，有次数上限；被限流 → 等到能取再取，不算失败；渠道明说没有 → 不重试，需求项转「无法满足」；取回的内容不对（不是 PDF、是错误页）→ 不重试，转「失败」附原因。中途被打断（工作进程挂了）→ 记「被打断」，调度按规矩重新排队、计入尝试次数，不悄悄重跑。每次尝试有时限。

**调度**：
- 每个渠道一条队列，按渠道登记的限速与并发取。
- 先后四档：① 有任务在等数据的（如委托卡在「等数据」）；② knowlab 测试集这类成批的；③ 订阅；④ 后台补加工。同一档里按用户轮流，一个人一次要 50 份不挤掉别人。
- 预计时间按队列长度与渠道限速算，回给需求方。
- 渠道停用（审核撤销）：它的作业暂停或取消，对应需求项转「无法满足」附原因。

**订阅怎么排**：查的频率取「用户希望的」与「渠道允许的最快」里慢的那个；订同一个东西的人共用一次查看，查到新的分别按每条订阅的上限生成需求单。

**管理端**：各渠道队列长度、在跑的、失败的与原因；可手动重新排队、暂停某个渠道。

## 8. 供给侧：原件留存与加工（10-26 定）

所有者：「都按你的建议，记下来」。

**原件留存**：取回的原件一个字节不改先存下，按内容摘要存、相同内容只存一份，记出处（渠道、渠道内编号或网址、取回时间、对方返回的状态与响应头摘要）。真源在 knowbase：原件交给 knowbase 成为原件版本、拿到回执才算交付完成；knowfeed 那份在拿到回执后再留 30 天便于排查，然后删内容、只留出处与摘要；以后重新加工从 knowbase 取原件。

**加工的分工**：knowfeed 做加工，把原件变成人和专家能直接读的形态（正文、按页文字、抽好的表、描述），作为派生版本交 knowbase；knowbase 做检索索引（切段、算向量），属于「knowbase 管存储、检索、统计」，谈存储时细说。

**加工器：通用的加上插件**（和适配器同一个思路）：

| 加工器 | 做什么 | 对什么内容 |
| --- | --- | --- |
| 正文抽取 | 去导航、广告，抽正文转文本或 Markdown；顺带取标题、发布日期 | 网页 |
| 按页文字 | 按原件的页切开，每页一段文字带页码 | PDF；扫描版的文字识别（OCR）这一轮留出位置不做 |
| 表格整理 | Excel、CSV、网页表格转成统一的表结构 | 表格类 |
| 描述识别 | 先用渠道列表给的信息（主体、类型、期间、披露时间），不够再从内容里认 | 所有 |
| 领域插件 | 某一类内容的专门加工，如财报抽表：认三张报表、统一科目名、认单位与口径、核勾稽、每格带原件页码 | 插件自己声明接哪类内容；财报抽表只是一个实例 |

规矩：
1. 每个加工器有版本；派生版本记来自哪个原件版本、哪个加工器哪一版；升级后重新加工产生新派生版本，旧的保留，钉旧版的照旧读旧的。
2. 从渠道列表来的描述记「入库质检过」，可直接参与解析；从内容里猜的记「自动识别未确认」，用户确认后才参与解析。
3. 加工没成功：原件照样交付，没成功的读法写明原因，需求项转「部分就绪」（如「原件已到，表没抽出来：扫描版，暂不支持文字识别」）。
4. 加工作业和下载作业走同一个调度，属第四档「后台补加工」；有任务在等这份数据，就跟着那件任务提到第一档。

## 9. 供给侧：质检与交付（10-26 定）

所有者：「都按你的建议，记下来」。

**质检分三层**：

| 层 | 核什么 | 核不过 |
| --- | --- | --- |
| 取回检查（每次下载） | 内容类型；是不是错误页（太小、文件头不对、标题是「404」）；取完整没有；算摘要 | 这次尝试失败，按出错分类重试或结束 |
| 加工检查（每个加工器） | 正文非空、长度说得过去；按页文字页数与原件对得上；表格结构完整；领域插件自己的检查（如财报勾稽、科目、单位、两种读法逐格互核） | 不挡原件交付，没过的照实标出交用户看 |
| 对得上需求吗（精确描述） | 取来的和需求说的是不是同一份：主体、类型、期间（如标题里的公司名与年份） | 不算就绪，需求项转「失败」附原因 |

质检结果作为这份数据的质检报告随交付给 knowbase，用户看得到。

**交付给 knowbase**：交原件版本与派生版本、描述（带确认状态）、出处与加工器版本、质检报告、许可档（渠道审核定的）、关联的需求依据（归属用户、从哪个应用哪件任务来、落到哪）。knowbase 收到后：
- 公开披露的进公开原件层、只存一份，给每条有效需求依据在对应用户名下记第二区引用；
- 非公开的（如审核定为只许本人用的网站）内容只存一份，每个提需求的用户各得一份自己名下的资料，各算各的许可与删除（评审 L2-05「去重不合并许可依据」）；
- 按需求单的「落到哪」展示给对应应用，依据是用户确认需求单那一次（knowbase 记引用了哪个确认编号）；
- 第一区的算用户空间，第二区引用不算。

**回执**：knowbase 对每项回一张回执（资料或引用的编号、版本、哪几种读法已就绪），knowfeed 凭回执把需求依据标「已就绪」或「部分就绪」；交付可安全重试，重复交不多出一份；knowbase 拒收的（如用户空间满了）需求项转「失败」附原因。

**需求状态只由 knowfeed 通知**：knowbase 只给 knowfeed 回执，由 knowfeed 统一通知应用和用户，状态来源只有一处。0043 第 3.4 节「knowbase 按需求来源通知应用」照此改。

## 10. 切合：需求怎么找到供给（10-26 定）

所有者：「都按你的建议，记下来」。

**切合在 knowfeed，做两次**：
1. **确认之前先预切合**：应用列清单之前问 knowfeed 这几项能不能满足、大概多久、取来属于哪一档许可；用户确认时看得到预计时间与许可（如「取来后只许本人用」），明显满足不了的直接标出（评审 F 3.5）。预切合只看供给侧（有没有渠道、渠道里有没有这一份），不看 knowbase 已有什么，不泄露「平台以前取过」（评审 F 2.1）。
2. **受理后正式切合**：定用哪个渠道，建作业或挂到已有作业上。

**四种需求怎么切合**：

| 种类 | 怎么切合 |
| --- | --- |
| 精确描述 | ① 先问 knowbase 原件与要的读法是不是都有：都有直接记引用、就绪；原件有缺某种读法，只建加工作业（L2-05）。② 没原件，在来源目录找「能提供什么」覆盖这条描述的渠道，按登记的先后排。③ 对第一个渠道「列」，确认有这一份、版本合要求（截至某日已披露、更正版）；有就建下载作业、按读法挂加工作业，没有换下一个。④ 都没有转「无法满足」，分「渠道里没有这一份」和「这类数据我们还取不到」 |
| 给网址 | 网址规范化看落在哪个网站：属于已登记渠道，用那个渠道的取法与许可；不属于，走通用网页渠道看网站审核状态：审过照取，待审等审核，审不过转「无法满足」 |
| 订阅 | 建订阅时切合：找会「看新的」的渠道（目录型或订阅源型；按网址订的，是 RSS 或栏目页用订阅源型，都不是用网页变化监测）；找不到订阅建不起来、转「无法满足」。以后每轮查到新的，生成的需求项已知渠道，直接建作业 |
| 按主题找 | 按范围挑搜索渠道（指定的网站有站内搜索用站内搜索，否则用通用搜索接口）；每条候选先预切合，标上由哪个渠道取、许可哪一档、网站审没审过，再列给用户勾；勾的每条变成网址或精确描述的需求项照上走 |

**渠道先后**：登记「能提供什么」时写这项能力的先后；官方渠道在第三方前，许可档宽的在窄的前；第一个取不到自动换下一个。

**缺口清单**：「这类数据我们还取不到」的需求记进管理端「缺口清单」（什么类型、多少人要过），管理端据此补渠道，供给跟着需求长。
