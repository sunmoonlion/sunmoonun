**支持这次把 Knowfeed 改成通用的需求、供给、匹配体系，也支持继续用 RAGFlow 作为派生索引。** 巨潮、F10 降为渠道实例，业务应用表达需求、Knowfeed 负责取得和加工、Knowbase 负责主档与访问，这个职责划分已经比第二轮完整。

## L3-01 [P1] 上传加工和重新加工，缺少受限的作业授权与提交接口

**位置：[0044 第 30、41 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0044-knowbase-web.md:30)；[0045 第 132–144 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0045-knowfeed-supply.md:132)；0043 §2.3、§2.7、§10。**

用户上传的私有 PDF 现在也交给 Knowfeed 加工；Knowfeed 暂存原件保留 30 天，之后重新加工要从 Knowbase 取回。两条路径都需要 Knowfeed 读取用户资料并写入派生版本，但新稿没有定义对应的作业授权。

`app:knowfeed` 目前写的是“平台账号的资料给 Knowfeed 质检用”，不能自然扩大为所有上传者都同意 Knowfeed 读取其全部资料。普通上传默认展示的也只是 Knowbench、Knowlab。0045 还规定 Knowbase 不是采集需求入口，所以不能简单伪造一张“用户采集需求”绕过去。

**建议补一条内部加工契约**，与用户采集需求分开：用户上传并采用页面说明的加工选项，Knowbase 记录依据；提交一个只指向指定原件版本的加工作业；Knowfeed 凭限定作业、处理目的、版本和时限的授权读输入，只能把派生结果挂回该原件，不得自行改所有者、许可或数据区。重新加工复核这条依据及版本状态。

Knowbase → Knowfeed 的加工提交、Knowfeed → Knowbase 的受限读取／派生写入也要进入服务关系表。上传动作可以一次覆盖该用途，不需要为了实现而另加逐次弹窗。

**验收反例**：加工甲的一份文件的授权，不能换成甲的另一份，也不能读乙的文件；加工中撤销或清除后，晚到结果不能重新建立可读版本。

## L3-02 [P1] 一年期订阅不能只拿订阅编号替代 Knowbase 的可验证同意

**位置：[0045 第 35–56 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0045-knowfeed-supply.md:35)；[0043 第 138–139 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0043-data-v4.md:138)。**

普通确认是“具体清单修订、具体条目、7 天内有效”；订阅却最长一年，范围内新条目无需逐份确认，提交证明只有订阅编号。新条目在订阅建立时尚不存在，不能匹配原来那张有限条目的确认清单；第 8 天以后也不能沿用普通确认期限。

需要保留所有者已经定下的“一次订阅、范围内自动取”，同时为它明确不同的依据类型。否则实现只能在“第 8 天全部拒收”和“相信 Knowfeed 报的用户名及条目”之间选一条，后者破坏 Knowbase 统一裁决的原则。

**建议**：订阅生命周期归 Knowfeed，Knowbase 保存本人建立的长期、可撤销、带修订的范围同意。它至少包含用户、订阅编号与修订、描述或网址范围、起止、用途与允许的自动取得方式。每轮需求关联该依据以及本轮发现记录；Knowbase 接收入库时验证仍有效且没有超范围。续订建立新修订，暂停／取消／停用的效果明确同步，不能自动滚动延长普通七天确认。

按主题订阅仍每轮勾候选，这一例外要保留；不要给它套上“凡搜索命中都自动授权”。0043 的确认契约和“确认不能跳过”应明确区分逐项确认与订阅范围确认，而不是互相矛盾。

**位置：[0043 第 138–145 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0043-data-v4.md:138)；[0045 第 154–168 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0045-knowfeed-supply.md:154)。**

0045 已经区分“原件有、读法缺”并安排补加工，这是正确的；但 0043 仍写：已有原件立即记引用，只有要新取的才把需求交 Knowfeed。

直接后果是：PDF 已有、表格缺失时，没有需求进入负责补加工和通知的 Knowfeed，应用却等待 Knowfeed 的就绪事件。另一个问题是通用采集已包含 F10 等第一区资料，0043 仍把待取得的数据全部描述为“引用”，不能把它们一律送进公开原件层。

**建议统一入口分支**：

2. 本人尚未取得，但内容及读法完整：按确认结果取得对应的第一区关系或第二区引用，并返回立即完成结果；应用无需等待不存在的采集任务。

通用网页按规范化 URL 去重也只能用于同一次获取或明确的新鲜度窗口。URL 是资源身份，不是内容版本：栏目更新、同址替换文件、重复订阅检查都可能需要新一次获取，再按内容摘要决定是否新增版本。

## L3-04 [P1] 预匹配显示的许可，不能在自动切换渠道后无声变成另一档

**位置：[0045 第 160、165、170 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0045-knowfeed-supply.md:160)；0043 §3.3。**

用户确认时看到许可档，但正式匹配在之后才选渠道，取不到会自动换下一个，且渠道优先策略允许从宽许可切到窄许可。比如用户确认的是可随公开专家使用的数据，执行时换到只许本人用的来源；取得内容虽然相似，已不能完成原来的用途。

需求单不写渠道、许可档的分层决定可以保留。缺少的是**确认对应的供给条件快照和接受边界**，而不是让用户填写采集器。

建议确认记录关联预匹配结果的修订、可接受的来源限制／用途条件；正式匹配与入库均核条件。切到同等且满足条件的来源可自动继续；不满足原用途时返回“当前供给条件不满足”，让用户选择调整用途或确认新条件，不能把更窄许可静默当成原需求已满足。渠道审核记录发生变更也走同一检查。

对按网站审核的场景，域名通过审核与页面一定属于某类公开披露，是两件事。数据区和许可应由实际来源记录及审核规则确定，不能仅凭“允许给别人用”就把任意公开网页自动归入法定披露原件层。

## L3-05 [P1] 真正运行浏览器后，必须继承现有 HTTP 采集的出站隔离

**位置：[0045 第 93、110–113 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0045-knowfeed-supply.md:110)；0043 第 288 行。**

这次不是简单换适配器名称：Scrapy、Playwright 从空壳变为实际渲染，网页脚本会自行发起重定向、子资源和后台请求。只审核入口域名、只允许 Knowfeed 工作负载出站，不能保证浏览器后续请求仍在允许范围内。

当前 [crawl_http.py](/home/zymun/worktrees/qwen/knowfeed-app/knowfeed-backend/app/app/infrastructure/external/crawl_http.py:55)已有 URL 协议、端口、公开 IP、DNS、重定向及体积／时间限制；`fetch` 还隔离不同来源的凭据与连接。新浏览器不能绕过这些已有边界。

**建议**：渠道审核决定允许哪些业务来源、是否渲染、限速；执行层负责不可绕过的网络与资源隔离。所有重定向和浏览器请求都经过受控出口，禁止转向集群内部、回环和元数据地址；隔离浏览器作业的 Cookie、凭据、下载目录，给页面、附件总量、时间和内存设上限。插件不能使用任意网络客户端逃逸框架约束。

这是工程执行边界，不是恢复已经被所有者否定的“逐请求合规审批”，也不要求新增人工确认。这里指出的是新渲染路径必须保留现有防护，并非声称当前 HTTP 路径没有防护。

## L3-06 [P2] 主题订阅接不上“看新的”，共享游标也不能代替每个订阅的进度

**位置：[0045 第 35、38、103–111、122、128、167 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0045-knowfeed-supply.md:103)。**

按主题订阅已列入四种需求，但建立订阅统一要求渠道支持“看新的”。搜索型适配器只有“搜”，因此按现有判据主题订阅会在建立时被拒。

建议订阅分两种执行计划：目录／RSS 等走“看新的”；主题走定时“搜 → 本轮候选 → 用户勾选 → 确认需求”。两者共用调度和订阅状态，不强迫搜索适配器伪造目录游标。

共享查看还需要两层进度：渠道发现游标和各订阅的消费／选取记录。甲本月配额已满、乙还能继续取，不能因为共享游标推进就丢掉甲未处理的条目；刚加入的订阅也不能收到超出约定起始范围的历史条目。至少明确超额条目是跳过还是待下月补，重试如何避免重复计费／计额，暂停恢复从哪里继续。

**验收场景**：同一来源两个不同起始时间、不同配额的订阅；再加一个按主题订阅。三者的确认与进度各自正确，共享查看仍然只执行一次。

## L3-07 [P1] RAGFlow 的“删除同步”必须区分移除个人引用与清除共享版本

**位置：[0043 第 90–94 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0043-data-v4.md:90)与[第 219–221 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0043-data-v4.md:219)；0045 第 132 行。**

一方面，逻辑删除后买家、已冻结测试和专家版本仍可读；另一方面，RAGFlow 四条规则笼统要求“删除与清除”同步删除文档。一个共享派生版本可能被多份使用权引用，卖家从自己的栏里删除，不能导致所有买家的文字检索一起失效。

**建议**：删除事件要表达操作对象和原因。取消展示、删除个人引用只改变该主体的访问依据，不删除仍被合法引用的共享索引；禁用先由 Knowbase 拒绝后续读取；真正清除内容才删除相关原件、派生数据及索引，并等所有必要回执。不能把任意 `deleted` 事件直接映射成“删 RAGFlow 文档”。

同样，Knowfeed 新增的 30 天暂存原件及 RAGFlow 加工阶段副本，应纳入明确的清理范围；不能把“Knowbase 那份已清除”当成所有受管副本都不存在。共享内容清理需区分撤掉某人的关系与清除整个内容版本，避免误删其他仍有效的引用。

## L3-08 [P2] RAGFlow 作为加工器与索引，两条链需要各自的产物及归属

**位置：[0045 第 133–144 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0045-knowfeed-supply.md:133)；[0043 第 211–224 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0043-data-v4.md:211)。**

选 RAGFlow 不需要重开讨论，但目前只写了它“做扫描与表格解析”和“作为检索索引”，中间的持久产物没有说完整。

现有 [RAGFlow 客户端](/home/zymun/worktrees/qwen/knowbase-app/knowbase-backend/app/app/infrastructure/external/ragflow.py:219)包含上传、触发解析、读取文档状态和检索；[provider 封装](/home/zymun/worktrees/qwen/knowbase-app/knowbase-backend/app/app/infrastructure/external/ragflow_provider.py:132)也是这条路径。它不等于已经存在一个“返回完整逐页文字、完整逐格表及坐标、可独立入库”的加工接口。

建议先定义并验证一条小链路：原件 → 指定版本／配置的 RAGFlow 解析 → 完整导出加工结果与页码／坐标 → Knowbase 固定派生版本 → 对这一派生版本建立检索文档。明确解析阶段的临时文档由谁创建、保存多久、由谁清除，以及检索文档如何映射回已提交的派生版本。不要以检索 `top_k` 返回的片段替代完整加工结果。

“索引丢了从原件重建”也应优先写成“从已经固定保存的派生内容重建”；否则新版本解析器再次处理同一原件，可能生成不同文本，却仍声称属于旧派生版本。需要重抽时应创建新派生版本。

这是核对现有封装与目标契约的差距，不是断言 RAGFlow 产品不支持这些能力。具体部署版本能导出什么，应在接入验证中给出真实样例。0044 第 30 行把“检索切段”算进 Knowfeed 加工，也应与“切段索引归 Knowbase”统一。

## L3-09 [P2] 通用表格存储不能把行固定成科目、列固定成期间

**位置：[0043 第 215 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0043-data-v4.md:215)；0045 第 140 行。**

现在要接收任意 CSV、Excel、网页表格，表格单元模型却仍按“行＝科目标准名、列＝期间”描述。政策表的列可能是地区、条件、补贴上限；明细表可能有重复行名、重复列标题和多级表头。按科目与期间来定位，会丢掉顺序、重复项或原始坐标，无法准确返回用户上传表的格子。

**建议**：单元的基础地址用版本、表／工作表、物理行列；保存原始值、值类型、解析值以及来源位置。科目标准名、报告期间、单位、口径是领域插件提供的语义标注，不是所有表格必须有的主键维度。原始值与规范化数值分开，避免百分比、缺失符号、文本、日期等被不可逆地统一成数字。

这样仍是一套通用表结构，不需要每类内容建表，也不会把证券专线换个位置重新写进 Knowbase 的基础模型。

## L3-10 [P2] 小店需要持久的处置状态，不能只批量下架当前条目

**位置：[0018 第 298–311 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0018-advisor-market.md:298)；0043 §4.3。**

“每个用户一家小店”的页面分组清楚，但新增处置只写“违规小店下架其全部在架条目”。如果只是执行一次批量下架，店主随后创建新条目、把待审核条目转公开，或者异步交付在批处理后完成，小店会重新出现可交易内容。

建议店铺至少有稳定身份、唯一的用户归属及可查询的处置状态。公开列表、条目发布、审核转公开、下单／请专家都核店铺当前状态；恢复店铺不自动恢复被独立下架的条目。无须创建新审批体系，可以复用现有运营处置入口。

“我的小店”同时含自用专家、待上架资料、订单；公开店铺只包含获准公开的供需及店主公开资料，两者应是不同的后端投影，沿用现有公开／私有校验，不把整个“我的小店”返回后交前端隐藏。

还需区分两种后果：停店阻止新的公开交易；已有知识使用权是否撤回，要按对应内容／交易的处置原因决定，不能因为市场入口停用就顺带撤销所有历史订单权益。请过的专家在 Knowbench 展示历史，也不代表可以绕过 0018 §11.9 已定的“专家下架后不能再请”。

## L3-11 [P1] 许可改低时“停一切新读取”，与买家已有使用权不动冲突

**位置：[0043 第 93 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0043-data-v4.md:93)；[0044 第 29 行](/home/zymun/worktrees/qwen/sunmoonun/docs/design/SDD/modules/0044-knowbase-web.md:29)；数据拓扑 §11。**

新表把禁用、许可失效、主动改低、违规下架合在一行：资料禁用或改档，停一切新读取、撤运行授权；同一行又说改低时买家已有使用权不动。

卖家把许可从可出售调低，如果把整个资料标成不可读，买家的权益记录虽然还在，下一次下载或运行却读不到。这没有兑现已定的“买家不受影响”。

**建议拆开**：卖家主动收窄未来供给，只影响新的销售／公开用途，以及明确被收窄的其他依据；已成交且仍有效的版本使用权按交易时的范围继续判断。真正的内容禁用或违规处置，可以按已定规则收回受影响权益并停止读取。授权检查要按本次使用的依据判断，不能只看资料主档当前的许可档。

与小店处置一起给一个反例测试：甲买过某版资料；卖家改低许可或关店，甲的既有合法使用仍可读；随后该版本被明确违规禁用，甲才按处置规则不能继续读。

## 还应在本轮顺手统一的几处

这些不用再提所有者决策，由 SDD 整理即可：

- **发版顺序仍有自相矛盾**：0043 第 276 行把 Knowbase web 放在关闭旧上传的应用更新之后，第 278 行又要求替代入口先可用。写成可执行的两阶段切换：先部署兼容 API 与新入口，再开新路径、关旧入口；不要靠一句原则让发版人员自行重排。
- **实施依赖漏项**：0043 块 6 包含会话小授权和输入组合，却未依赖定义它们的 1c；0044 上传加工、0045 调度作业也需要对应加工接口和授权，不能只依赖资料表建好。
- **主题搜索与给网址的普通确认**目前只在 0045 有需求结构，0043 仍围绕专家解析清单记确认。确认接口应覆盖四种需求的规范化内容，而不要求每张用户需求都先有一位专家和一份财务声明。
- **有限确认的幂等顺序**：0045 先核七天有效、配额，再按幂等钥匙返回原单。已受理后客户端丢响应，七天后查询式重发不应被当成新请求拒绝。先认证归属并核相同请求摘要；已经受理的幂等请求回原结果，只有真正的新受理才扣配额、核确认时效。相同钥匙不同内容须拒绝。
- **“部分就绪”的收尾**要写明：哪些属于暂时还在加工，哪些是当前尝试终止、可发起补加工；同一需求只要求原文时，不因额外表格加工失败而被降成部分就绪。

## 建议增加的验收，不只跑原来的两条财务／交易链

原有两条端到端测试应保留。0045 这次已从一种数据扩展为四种需求，新增能力至少各走一次真实闭环：

| 场景 | 必须观察到的结果 |
| --- | --- |
| 网址：同址内容更新 | 能重新获取并生成新版本；旧绑定不变 |
| 浏览器：入口公开但子请求指向内网 | 子请求被拒，页面不能利用渲染器访问内部服务 |
| 订阅：运行超过七天 | 不要求逐份确认，也不绕过长期范围依据；取消后不再新增授权关系 |
| 主题订阅 | 搜索候选能产出；未勾的不取，勾的按新需求确认 |
| 两个订阅共享来源、配额不同 | 一人的限额／暂停不丢另一人的记录，补取或跳过语义明确 |
| 私有上传 → 扫描解析 → Knowbase | 加工凭受限授权；完整页／表产物已存主档，断开 RAGFlow 仍能按版本读已有结果 |
| 已有 PDF、缺表 | 触发补加工、收到对应完成事件，不重复下载、不永远等待 |
| 渠道回退带来许可变化 | 不静默越过已确认的用途条件 |
| 共享版本删除个人引用 | 其他合法使用者仍可检索；真正清除才删除共享索引及必要副本 |
| 店铺停用与既有交易 | 新公开交易被挡，私有管理和已有合法权益按各自规则保留 |

建议优先补 L3-01～05、L3-07、L3-11，再把两类订阅执行计划、RAGFlow 加工产物契约和通用表格地址定下来。四种需求都做的范围保持不变；按同一套契约逐条实现和验收，比继续扩充抽象的“支持哪些渠道”列表更能推进落地。
