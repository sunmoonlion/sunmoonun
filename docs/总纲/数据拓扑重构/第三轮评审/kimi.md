# Kimi 评审（第三轮）：数据拓扑第四版定稿、0043 / 0044 / 0045、knowmart 小店

读了：数据拓扑第四版（重点第七、十一、16.2 节）、0043 与 0045 重写稿、0044 改稿、0018 第十一节第 7 之二小节、采集讨论记录 12 条、第二轮处置回执。

总体：需求 / 供给 / 切合分开、渠道登记不改代码、确认不能被跳过、预切合不泄露命中、请求 / 作业 / 依据三层、存储按读法分表、RAGFlow 守四条——这些都对，上一轮我提的点也全部有处置。这轮的意见集中在采集放开到任意网址以后的新暴露面，和几处文档间对不上的缝。按轻重排。

## 一、要处理的

1. **「给网址」开了一扇 SSRF 的门，整套文档没人提**（采集讨论记录第 1、5 条；0045 第 2.2、3.1 节）。四种需求里三种能带网址（给网址、按网址订、按主题搜出的候选）。通用网页型适配器对「用户给的任意网址」发起取回：用户（或搜索结果）指向内网地址、云元数据地址（169.254.169.254）、环回地址，knowfeed 的工作进程就成了内网探测器。渠道审核管的是合规，挡不住这个——网址是逐条不同的。建议写成硬规矩：通用网页型只许 http/https；取之前解析域名，拒私网、环回、链路本地、保留地址；**每次重定向都重核一次**；连上后核对端地址不在拒收范围。这一条不做，「给网址」就不能开。

2. **发版顺序里 knowbase web端排在 knowbench 之后，但 knowbench 那一批删上传入口**（0043 第七、九节）。第九节顺序：…→ knowbench（删选数据与本地来源、云端知识库页去掉上传）→ knowlab → knowbase web端。同页那句「旧上传入口关闭前 knowbase web端必须可用」与此矛盾；实施分块表里块 6（knowbench）也不依赖块 5（knowbase web端）。改法二选一：(a) knowbase web端提到 knowbench 之前发；(b) knowbench 那一批分两小步：先接解析，删上传入口单独留到 knowbase web端上线之后。我倾向 (b)，knowbase web端的工作量不挡解析主线。

3. **0018 第八节残留旧模型**：「知识的内容不存 knowmart，存 knowbase 的 knowmart 分区（0042）」——第四版已经没有按应用分区，知识是 knowbase 里的一份资料经 `market` 展示交给 knowmart（第 7 之二小节与 0043 第 4.3 节都是这么写的）。这一句改掉，顺手把 0018 里其余按「分区」说的地方扫一遍。

4. **RAGFlow 一身二任的边界没写清**（数据拓扑 16.2、0043 第五节、0045 第 3.4 节）。规矩②是「任何应用不直接碰 RAGFlow，检索一律经 knowbase」；同时「RAGFlow 的文档解析作为 knowfeed 的一个加工器」。RAGFlow 的解析和它的文档库是耦合的，knowfeed 调它的解析能力就是在碰 knowbase 管的派生系统。建议写明一种：(a) 解析调用也经 knowbase 转（knowbase 多一个内部「加工解析」接口，knowfeed 仍是「应用不直接碰」）；(b) 明说 knowfeed 是这个规矩的唯一例外，且只用解析、读写库都经 knowbase。我倾向 (a)，规矩不用开洞。

5. **配额清单缺了「每周期新取份数」**（0045 第 2.4 节）。现在列的是请求频率、在途单数、订阅条数；订阅有每月上限。但没有「每人每月新取多少份」这条总闸：有人用精确描述或给网址批量提，就能绕过订阅上限把渠道当搬库工具。knowfeed 完善第 4 题本来有「每人每日新取 30 份」，建议把这个配额补回需求侧核验清单，按需求单的需求项计。

## 二、建议改的

6. **通用网页「往下一层」要加份数上限**（采集讨论记录第 2 条）。「这一页加它直接链到的文件」——一个页面可以链几百个文件。建议需求项带「最多 N 份」（拟 20），取回时逐份核网址与内容类型，超出的列给用户看「还有 M 个没取」。

7. **小店列表别列空店**（0018 第 7 之二小节）。「每个登录用户都有自己的小店」+ 首页列所有小店 = 首页会被没有任何在架供给、没有开着需求的空店淹没。建议首页只列有内容的店（有在架条目或开着的需求），空店只有自己进「我的小店」时可见；或按所有者意思确认。

8. **会话小授权建议能批量签**（0043 第 2.7 节）。「每首读一份签一条」在高频会话里是一次一往返；模型常常会一次决定要读好几份。接口上收一个清单、一次签多条（每条仍是一份一条授权），语义不变、少绕圈。不挡实施，记一句。

9. **「最晚什么时候要」的默认值**（0045 第 2.2 节）。需求项的超时状态靠它，但没写没填时怎么办。建议：用户亲手提的必填；应用代提的由应用按任务时限填（委托就是委托的时限）；都没给时按渠道保守预计时间加一个系数。

10. **待审网站队列要防运营积压**（0045 第 3.1 节）。每个新域名自动建待审，等审核期间需求停在「已受理」。建议管理端这个队列有数量与等待时长提示（进缺口清单同一页也行），并给审核一个目标时限；否则第一批真实用户用「给网址」时体验是「提了就没下文」。

## 三、核过、认为对的

- 预切合只看供给侧、确认清单只给总数与保守预计，确认后命中秒到——和已接受的「快慢看得出」口径一致，没有按份泄露命中。
- 确认编号 7 天、只对那张清单修订的条目有效、确认不能被账号设置 / 应用默认 / 模型调用跳过——闭环了。
- 请求 / 作业 / 依据三层 + 取消只摘自己的依据 + 完成事件只推进仍有效依据 + 迟到事件不复活任务——状态机的坑都预先堵了。
- 渠道审核按渠道一次、通用网页按网站一次、采集层只管取不管合规——分工干净；「缺口清单」让供给跟着需求长，好。
- 原件 knowfeed 留 30 天再删内容、以后重新加工从 knowbase 取——既留排查窗口又守唯一真源。
- 存储按读法分表、不按类别建表，新加类型不改表结构；表格单元通用结构同时装财报与统计数据——对。
- 测试集主体一律作者给（E3）、公开索引只回「这家公司有哪些报告」不开「列公司」——把「平台替用户挑公司」的口子堵了。
- 小店把「我买到的」拆到 knowbase 总栏与 knowbench、订单留 knowmart——归属对。
- 0043 第八节的两条端到端真跑和反例清单，覆盖面够（偏好不串、三种所有者共用、迟到事件、更正版不被旧命中吞、迁移后删过的仍不可读都在）。

## 四、小的

- 数据拓扑 7.2「订阅必须有截止日、最长一年、可续」好；建议订阅到期不续时把这条订阅生成的、还在途的需求项一并标「已取消（订阅到期）」，免得孤儿项。
- 0045 第 2.5 节「再试一次生成挂在原项下的新项」与「同一幂等钥匙回原单」并存：建议写明再试用新幂等钥匙，别和原单撞上。
- 0044 第 2.2 节「买来的有『绑给自用专家』」——按钮语义是「绑给专家、但该专家只能自用交付」，和 0043 第 4.3 节两种许可检查对得上，好；页面文案别把话说反（用户可能以为买来的可以绑给公开专家）。
- 采集讨论记录第 11 条「向量模型实施时拿真实数据比过再定」——建议比的时候把「钉住版本限定」也列入验收（换个模型要重建索引，重建期间检索降级不挡读数，这条规矩正好用上）。
