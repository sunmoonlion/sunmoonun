# Kimi 评审：数据拓扑第四版与 0043 / 0044 / 0045（第二轮）

读了：数据拓扑第四版全文、SDD 0043 / 0044 / 0045、C-L2 新口径、0037 与 0026 开头的标注、上一轮处置回执（`149d6353`）。

总体：上一轮的洞基本都接住了——引用是唯一入口且带任务与确认出处、按描述查只答「有没有」+ 限流、描述确认状态、绑定清单进版本摘要、自助测试的执行位置与证据拆半、供给完成判据、统计边界，都落进了正文。第四版我整体认可。下面是这轮新发现的，按轻重排。

## 一、要定的

1. **自助承诺与「过门重跑」之间有一道缝**（数据拓扑第 9.2 节表与「过两道门」行）。自助那一列写「谁会看到数据：只有用户本人和机器（他自己的模型 key、他自己的沙箱）」；但过两道门时「平台在测试电脑上凭测试授权，按钉住的测试集机器重跑一遍」——这时用户的测试集在**平台的测试电脑**上被平台的机器读了。机器不是人，但数据确实离开了用户的沙箱、进了平台的执行环境，产出还进 knowbase 产出区。这和自助卖点（数据不出我的地盘）有张力。建议二选一、写死：(a) 自助的过门重跑也在用户自己的 link 上做（慢、占用户机器，但边界干净）；(b) 承认重跑在平台测试电脑上做，把自助的表述改成「平台运营（人）看不到；平台的测试电脑会为审核重跑一次，没人看数据、产出只进你的产出区」，并在用户选自助时照实写明。我倾向 (b) 加照实写明，但这是一条承诺，该所有者定。

2. **自助模式落不进 0037 的现有数据结构，0037 改版要把自助路径的填法写死**。0037 刚定稿的约束是：建准专家「只能选受理了的版本」（`knowbot_acceptance` 一版一张）、专家有用户同意门（`user_accepted`）。第四版里自助孵化不受理、自助专家「提交交付即过用户同意门」。那么：自助创意的草稿建在哪一版上（没有受理单，0037 的拦截怎么开洞——是自助版本回填一张「自助」受理单，还是拦截只对平台模式生效）？`user_accepted` 由「提交交付」动作填，这个动作为什么算用户本人同意、在哪留痕？轻受理的受理单和正式受理单同一张表吗（`trial` 列之后又要多一种）？这些不定，knowlab 后端 0012 那套迁移和约束很快要再动一次。建议在 0037 的改版节里加一小张「自助 / 平台 × 受理、同意门、审核门怎么填表」的对照表。

3. **测试要记测试集版本**（0043 第 4.2 节、数据拓扑第 9.1 节）。测试集钉在草稿上、有独立版本号、声明变了才重解析；0037 的测试只有编号。复现和审核（「这次测试用的是哪版测试集」）都要能直接回答，不能靠时间先后推断。建议 `knowbot_test` 记测试集版本号；同一测试集版本测出的结果才可直接比。

## 二、建议改的

4. **确认编号要有有效期**（0043 第 3.3 节、0045 第三节）。现在 knowfeed 核「确认是真的、条目对得上、用户是同一人」，能防编造和改内容，防不了「拿三个月前的一次确认再提一次同样的请求」。同描述未决请求会合流，所以这个洞不大，但补一个有效期（拟 7 天）和「确认只用于这张清单的条目」更稳。

5. **大批量补采与「等数据」超时的算术要过一遍**（0043 第 3.4 节、knowfeed 完善第 4 题）。一件委托解析出 50 份年报缺失，每人每日新取限额若为 30 份，排队就要两天，逼近委托默认 3 天超时。确认清单上除了「预计多久」，建议支持用户取消部分条目（可选的直接降级、必填的取消即变更需求）；超时时「已定的部分带着走」已写，好。

6. **会话授权动态增长的面要有一句护栏**（数据拓扑第 12.3 节）。模型在会话里按需读「展示给 knowbench 的」任何一份，首次读即钉版本加进授权。这是正确方向，但模型被诱导（prompt injection）时可以在一段会话里把展示范围整个读一遍。「这段话读了哪几份」已是事后可见的缓解；建议再加一条便宜的：单段会话累计读取份数到软上限（拟 50）时在界面上对用户提示一次。不挡，只让人看得见。

7. **许可档「改高勾一句我有权」要单独留痕**（0044 第 2.2 节）。声明制 + knowmart 第二道关兜底，方向可接受；但升档这个动作本身（谁、何时、从哪档到哪档、有没有勾那句话）建议作为一条留痕，第二道关和事后审计都用得上。

8. **买家注销时买来的使用权怎么办，补一句**（数据拓扑第十一节只写了卖家注销）。买家注销 → 第一区真删 → 他对买来的数据的使用权应随注销终止、卖家空间随之释放；内容本身不因此清除（别人可能也买了）。一行即可。

9. **knowbase 向 knowlab 读「名下专家」建议用推不用拉**（0044 第三节）。拉（凭本人令牌查 knowlab）有一致性窗口：专家改名、删除后 knowbase 缓存里还能绑。knowlab 经发件箱把「我名下专家」的编号、名字、最新版本推给 knowbase，绑定时只认已推来的，窗口反过来收。成本相仿，二选一时我建议推。

10. **自助测试证据的上传链路写明一句**（0043 第 4.2 节）。自助测试在用户 link 上跑，「结论、数值、判定理由上传进产出区」——从 link 到 knowbase 产出区中间经过谁（link → 会合点 → knowbench → knowlab → knowbase？）、凭哪条授权、防伪靠什么（我理解是平台重跑兜底，用户自报不作数）？一句链路说明即可，免得实现时各家猜。

## 三、核过、认为接住了的

- 引用行带「任务 + 声明确认编号」出处，守则 1 的接缝闭合；确认由应用凭本人令牌转交、清单本身是 knowbase 产的，应用编不了内容。
- 「没有目录」的四条检验条件（精确键、候选来自渠道公开索引、检索只在钉住版本里、限流）齐了。
- 请求 / 作业 / 尝试三层、请求不合并但同用户同键未决合流，表述自洽；失败中止的记录留着。
- 删除按动作分那张表把「取消展示 / 逻辑删 / 禁用 / 真删」分开了，违规下架收买家使用权也写了。
- 「受益人不是所有者」的授权形态 + 留痕记两人，专家绑公开原件按请的人名下引用读，请的人确认清单里会列出专家要用的公开原件（公开信息，不泄露私有绑定），自洽。
- 实施分块把解析放最后、先只读契约测试，排序对；0043 块 1 先落地 + 默认展示开关开着，意味着 0044 没上线时老用户也基本不受影响，这个组合好。
- 迁移节按生产现状（10 条上传、无成交无授权）把第 2、4 条标成不用写数据迁移，诚实且省事；`source='local'` 停写、CHECK 放宽、列不删，对。

## 四、小的

- 数据拓扑第 5.2 节「第二区引用状态：已确认等采」——若 knowfeed 最终拒收（渠道不支持、配额超），引用转「采集失败」已有；建议状态里补一个「已取消」（用户在等数据期间改主意），审计线更完整。
- 0044 总栏对迁移来的「未确认描述」资料，建议首次登录给一次引导（筛选已有「未确认描述」，但用户未必找得到）；不然第 0043 第五节那 10 条资料永远不进解析。
- 数据拓扑第 8.2 节结果表「暂时判断不了 → 任务停下等，或者报错」与第十五节「解析接口不可用 → 停在等数据、不触发补采」一致，好；建议统一用「等数据」一个说法。
- 第三节 SSO「会话 12 小时」：确认动作落在应用页面上、凭令牌交换转交 knowbase，这条链已在 0042 验证过，第四版只是扩用途，无新风险，但 knowbase 的 `user_token_apps` 要把 knowfeed web端也登记上（0045 第一节 knowfeed web端自己提需求也要 knowbase 记确认）。
