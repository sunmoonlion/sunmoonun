## 一、同意的，不再展开

| 定的 | 为什么对 |
| --- | --- |
| 删 knowbench 本地知识库（第 1 条） | 它是唯一不在 knowbase 的知识库，为它多出一整套钉住、核摘要、link 目录权限；项目目录本来就能放本地文件 |
| 真源在 knowbase、knowfeed 是供给的门、应用先找 knowbase 要不到再经 knowfeed 补（第 2 条） | 读的路上没有 knowfeed，knowfeed 故障只影响补数据；这是现行第九节「一级服务」思路的自然延伸 |
| 一份数据只存一份、买卖只加使用权、一律逻辑删（第 3 条） | 符合 C-D1、C-D14；0042 的「成交复制」本来就和 C-D14 别扭 |
| 不再有选数据、按声明自动解析（第 4 条） | 用户手挑数据是现行最繁琐的一步；解析可留下比手挑更完整的证据（声明、解析时刻、选中的版本） |
| knowlab 孵化、测试各自可选自助或平台，平台看数据按过程授权、留痕、到期即止（第 5 条） | 比现行 0042「传进 knowlab 栏即整栏同意测试」严，方向对 |
| 产出不进解析，转为数据由用户做并带出处（第 6 条） | 挡住 AI 产出的错一路往下传 |
| 大纲「重写不打补丁、沿革压成一张表」 | 现行稿四层改定叠着，确实要重写 |

## 二、四处冲突：我的意见

### 冲突 1：公共区 vs「只经引用」「没有目录」

同意 Opus「两头都要」：原件只存一份，读之前用户名下要有一条引用，引用在他的任务解析到这份数据时自动记上。补三点，缺一条这个方案就会把 C-L2 捅破：

1. **不要再叫「公共区」，也不要写「所有应用都能用、不用勾」**。叫法决定读者怎么理解：「公共区」听起来就是一个所有人可浏览的库，正好是 C-L2 否定的东西。实际机制是：公开原件层只是**存储层**，读的单位始终是「某个用户名下的一条引用」，引用由他的任务自动记。建议新稿写成「公开原件层 + 自动引用」，不出现「公共区」。
2. **解析器的候选不能来自「我们库里有什么」**。第 4 条 knowlab 那段写「解析器按声明把能用的候选都找出来，提议一组测试集」；如果候选是从公开原件层里列出来的，那就是在给用户看目录（「分不出是谁要的」也守不住：列表本身就暴露了平台取过哪些）。应当和现行第七节一样：候选来自披露渠道的公开索引（巨潮），命中与否在列表上看不出来；用户确认后才解析、才记引用。
3. **检索不能跨过引用**。公开原件层的文字检索索引如果是一份共享索引，「按意思找段落」就等于在整个原件层里搜，又成了目录。规矩要写死：检索的范围 = 这个用户名下已钉住的那几版（和现行 5.1「第一区内容不能从检索口漏给别人」同一条逻辑，只是对象换成公开原件）。

### 冲突 2：应用代提采集 vs「只能由用户发起」

Opus 的「免费的直接提、要花钱或要审核的先问」我不建议。理由：

- 合规上要的是「用户指定」这个事实，不是「有没有花钱」；按费用分叉会让「谁发起的」这条线在免费数据上变得说不清。
- knowlab 一次要一批（10 家公司 × 3 年 = 30 份），自动提会一口气打满渠道限速和每人配额，用户事后才知道。

建议统一成**一次确认、批量提**：解析器算出缺什么，弹一张清单「要为这件任务取回这 N 份：……（预计多久）」，用户点一次「取回」，这一次点击连同清单、任务编号、声明快照一起留痕，就是「用户指定」的证据；knowfeed 收到的每条请求都带这条确认的编号。免费、收费、要审核的差别只体现在清单上的标注，不改流程。用户体验上只多一次点击，而且他看得到要等多久。

运行中临时冒出的需求（大纲第 8 节第 4 点）同样走这一步：任务停在「等数据」并把清单推给用户，他点了才提。

### 冲突 3：会话里的数据

同意「模型可用的范围就是 knowbench 栏，不再逐份选」，加两条：

- 第一次读某份时**钉版本**，这段会话后面都读这一版；会话结束授权撤（和现行「会话」授权一样，只是范围从「用户选的几份」变成「栏里的、模型查到的」）。
- 聊天界面要**随手列出这段话读了哪几份**。用户没逐份选，就更要看得见模型拿了什么；这也是留痕的用户侧一半。

### 冲突 4：逻辑删 vs 注销、个人信息删除权

同意 Opus：平时逻辑删，注销或依法要求时真删，真删前照旧阻止新运行、在跑的跑完。补两点：

- 真删的清单要把**产出区**和**解析记录里的描述字段**也算进去（产出可能带个人信息；描述字段里有「为某用户采集」）。留痕只记编号不记数值，可以留。
- 买家已买的那一版：建议不等律师，先按「买家那一版照旧可读、卖家的名字在条目上换成『已注销的卖家』」写进去，律师意见来了再改。买卖只加使用权的设计下，真删卖家的原件就是删买家的东西，这一条不能含糊。

## 三、大纲里没写到、会出问题的（按重要性）

### 3.1 专家绑数据 + 上架 = 「专家随数据」回来了，要把 10-23 作废的那条守则接回来

第 3 条让专家可以绑数据、knowmart 可以卖专家、绑的数据只要「可以经专家给别人用」就随专家给买家读。这正是 10-20「公开专家随专家提供一套数据」、10-23 为合规作废的那条，现在以「许可档」的形式回来了。可以这么做，但新稿要把跟着作废的两条接回来：

- 现行守则 5「授权给别人要有作者的同意」（10-23 作废）：作者在 knowbase 把数据绑给专家，这个动作就是同意，要写明它是同意依据的一种。
- 运行授权现在的模型是 `owner_subject`（数据归谁）+ `reader_app`（哪个应用读），默认读的是归他自己的数据。专家绑的数据是**作者的**，读的是**请专家的人的委托**：授权要多一个「受益人 ≠ 所有者」的形态，留痕里两个人都要记。这是 knowbase 授权模型的一处实质扩展，不是加个字段。

### 3.2 买来的数据能不能绑专家再卖：一条转卖的绕道

买来的数据进个人区，个人区的数据可以绑给自己的专家，专家可以上架公开。连起来：买一份「不许转卖」的知识，绑进专家，卖专家。两道关里 knowmart 核的是「可以经专家给别人用」这一档，但买来的数据的许可档是谁写的？新稿要定死：

- 买来的数据的许可档**继承卖家条目的转卖设置**，不由买家声明；`no_resale` 的，许可档只能是「只许本人用」。
- 绑了「只许本人用」数据的专家只能自用，上架公开时 knowmart 后端拒（这是第二道关要核的第三样）。

### 3.3 公开原件层的许可档应由系统定，不由用户声明；公开原件不能当「知识」卖

第 3 条说代采来的数据「看字段有没有『可以出售』」。公开披露原件和我们抽的表：许可档应固定为「可以经专家给别人用」，**不许出售**。原因：（一）原件人人可取，卖它没有标的；（二）抽好的表是平台加工的，拿它上架等于平台在市场上卖数据，正碰 C-L2。用户声明许可档只对**他自己上传的**成立。

### 3.4 「声明」现在是文字，解析器解析不了：要先定声明的结构，并分清「专家写定的」和「任务给的」

现在 `data_needs` 每样写的是名字、说明、格式、份数、表与列（knowmart 清单 `manifest.py`）。它能告诉人「要 5 份年报」，不能告诉机器「哪家公司、哪几期」。自动解析成立的前提是声明可机读，而「主体」在专家里通常是空的：请专家的人每次「换公司、换一期」（0026 原话）。所以要分两层：

| 层 | 谁定 | 内容 |
| --- | --- | --- |
| 声明模板（在专家里） | 作者在 knowlab 写定 | 类型（年报 / 季报 / 公告……）、期间规则（「最近 3 个完整年度」这类相对规则，或固定期间）、格式、份数、来源限制（只要公开披露原件 / 也接受上传）、表与列 |
| 任务参数（每次任务） | 请专家的人在发起任务时给 | 主体（公司、证券代码），必要时覆盖期间 |

knowlab 测试集则是一组显式的（主体、期间）组合，由作者确认后钉在草稿上。大纲第 8 节没有说「主体从哪来」，这是解析流程里最大的一个洞；没有它，「按描述查」没有可查的东西。

顺带：期间规则要能表达「截至任务日期已披露」——否则 2025 年 1 月跑的任务会解析到 2024 年报，但那时年报还没出，「最新一版」就是错的。

### 3.5 统一描述是一套受控词表，要有人管，上传的描述要用户确认过才能被解析到

自动解析把信任从「用户挑的」挪到「描述对的」。两个风险：

- 用户上传一份草稿 Excel，描述填成「茅台 2023 年报」，从此每次解析都优先拿到它。建议：解析时**公开原件层优先于上传**；上传的描述要有「用户确认过」的标记才进解析范围；声明可以写「只要公开披露原件」。
- 「类型」「主体」要有一套词表（报告类型枚举、主体用巨潮 `orgId` 加证券代码），由 knowbase 管；上传的自动识别只是提议，用户确认才写入。描述和内容要分开版本化：改描述不产生新的内容版本，但要留改动记录。

### 3.6 「统计」要先划界，不然会变成选股

第 2 条留的「统计指哪类」不是小事。如果 knowbase 给应用一个「在全部公开原件层上按指标筛公司」的统计接口，那就是平台在做选股，C-L1、C-L2 同时碰。建议写死两条：统计只在**这个用户名下已引用的那几版**上做；第一版不做任何跨全市场的筛选、排序、排名。要做全市场统计，先过律师那 9 问。

### 3.7 「资料」和「版本」要在 knowbase 里分成两层，不然使用权、钉住、展示挂不对地方

现在 knowbase 的 `UserDataItem` 一条就是一份内容（一个 sha256），没有版本链；卖家更新、更正公告出新版本、「买家拿交易那一版」、「专家钉某一版」都要求同一份资料有多版。建议模型上分：

| 层 | 挂什么 |
| --- | --- |
| 资料（逻辑的一份） | 描述、许可档、展示范围 / 用途、使用权（买家）、逻辑删 |
| 版本（一份内容，sha256） | 钉住（委托、测试集、专家绑定、会话）、留痕、原件 / 派生关系 |

现行第 4.2 节「原件版本和派生版本分开固定」就是这一层，新稿要把它推广到上传和买来的。

### 3.8 解析放在哪：建议 knowbase 解析，应用编排，knowfeed 供给

大纲把解析逻辑放 `common/backend` 给 knowbench、knowlab 共用。我建议把「按声明找数据、核范围、钉版本」做成 knowbase 的一个接口（它拥有描述、索引、授权，三样都在手里），应用只做编排：拿到「找到的 / 用户有但没放开的 / 缺的」三种结果后，决定问用户、提 knowfeed、进「等数据」。好处是一份实现、一处留痕，也避免 knowlab 和 knowbench 的解析器日后各自演化出两套口径（knowlab 测试集那几处特殊只是编排不同，不是查法不同）。

### 3.9 展示按钮会变成新的「繁琐」，要有默认值和批量操作

每份数据 × 每个应用 × 名下每位专家一个按钮，1000 份上限下没人点得完。大纲已有「代采来的按需求来源自动展示」；建议加：从应用的直达链接上传的默认展示给那个应用；账号级「新数据默认展示给我的全部应用」开关；栏里能批量勾。再看第四节的另一种做法。

### 3.10 第一道关不要重建运营审批队列

第 3 条「采时审有权采，资格审核由管理端做」如果落成「每条代采请求等运营看一眼」，就是把 10-18 取消的「运营审批」原样请回来。建议：渠道白名单就是第一道关的全部（巨潮的公开披露，有权采是显然的），管理端的资格审核只对白名单之外、付费、或需证照的渠道，按**渠道**审一次，不按请求审。

### 3.11 「真源两个」的说法要收紧：项目目录不是真源，是另一套世界

本地项目目录里的文件没有描述、没有版本、没有钉住、没有留痕，也不参与声明核对（第 1 条已说）。它和 knowbase 不是同一意义上的「真源」。建议新稿写：云端真源只有 knowbase；本地文件归用户自己管，专家就地读，平台不钉、不核、不验收（0042 第五节第 4 项的数值验收对本地文件不再成立，要明说）。标题里「两个真源」可以保留作口号，正文要把这层差别写出来。

### 3.12 需求与作业分开记

knowfeed「受理前查重、同样的请求并到一起」是对的，但并到一起的是**作业**（下载这一份），不是**请求**（谁为哪件任务要了它）。两样要分开存：请求不可合并（它是「用户指定」的证据，取消一条请求不等于取消作业），作业可共享。luna 那份采集体系稿第八节把这个拆成 Request / Job / Attempt，可以直接采。

### 3.13 空间与费用

使用权代替复制以后，一份被多人买走的资料只占卖家一份空间；卖家逻辑删了它还在；谁的配额算它？建议：算卖家的，直到最后一个使用权失效；公开原件层不算任何人的（现行第九节已这么写）。

## 四、两种不同的做法（供思想风暴）

### 4.1 个人区对本人的应用默认全开，展示按钮只管「给第三方看」

10-23「三个应用独立、不互相拿」的理由是「大多数时候是不同的人」。但不同的人就是不同的账号，隔离天然存在；同一个账号在 knowbench 和 knowlab 之间隔离，从隐私上什么都没保护，只是多了一道勾。真正需要用户点头的读取只有三种：平台的人看（第 5 条）、请专家的人经专家读作者绑的数据（第 3 条）、买家读（knowmart）。所以可以反过来定：

| 读的人 | 要不要用户动作 |
| --- | --- |
| 本人的任何应用（knowbench、knowlab、自己的专家自用） | 不要：个人区全部可解析，栏只是按用途过滤的视图 |
| 平台（孵化、测试、受理） | 要：按过程授权 |
| 别人（经专家、经购买） | 要：绑定 / 上架 |

这样展示按钮从「每份 × 每应用」缩成「每份 × 三种第三方用途」，第 3.9 节的繁琐消失，第 4 条「用户有但没展示给本应用 → 请用户去放开」这个分支也没了。代价是推翻 10-23 的「展示上独立」。这是所有者的决定，我只提出来。

### 4.2 「展示范围」就是同意依据，不另立概念

大纲第 12 节已经写「同意依据 = 用户在 knowbase 点展示按钮」。建议更进一步：在模型上就用现有的 `UserDataConsent(purpose, ref, items)` 表达展示范围（purpose = `knowbench` / `knowlab` / `expert:<id>` / `platform:<process>` / `market`），各应用的栏 = 按 purpose 过滤的查询。这样不新增一个「展示」概念，0042 已做的同意、授权、留痕三层直接续用，改动最小，而且「点展示按钮必须是本人登录动作」这条守则自动成立。
