## 三、六条一句话

1. knowbench 本地知识库删掉：云端要用的数据进云端，本地用的放项目目录。
2. 真源两个（本地项目目录、云端 knowbase）；knowfeed 管供给（采集），knowbase 管存、检索、统计；应用先直接找 knowbase，要不到再经 knowfeed 补。
3. 根本原则：应用是使用者，知识库栏和 knowmart 是展示者，真源在 knowbase，一份数据只存一份。上传只在 knowbase web端；knowbase 总栏有各应用、各专家的展示按钮；买卖只是给买家加使用权；专家可以绑数据；采时审有权采、卖时审有权卖；一律逻辑删。
4. 不再有「选数据」：应用按专家声明的数据要求自动解析（统一数据描述、公共区与个人区、查不到向 knowfeed 提、等数据）；knowlab 用测试集，谁的任务谁解析。
5. knowlab 的孵化、测试各自可选自助或平台；平台看数据要本人按每次过程授权、留痕、到期即止。
6. 专家的产出：本地在项目目录，云端进 knowbase 产出区、不进解析，转为数据由用户做并带出处。

## 四、特别想听意见的

1. **大纲第三节四处冲突**，Opus 都给了建议，看建议站不站得住：
   - 公共区与「只经第二区引用」（合规地基「平台不提供数据」）；
   - 应用代提采集与「代采只能由用户发起」；
   - 会话里的数据（聊天、工作不再逐份选）；
   - 逻辑删与注销、个人信息删除权。
2. **自动解析做不做得出来**：统一数据描述够不够认准「要什么」；查不到时会不会白白触发采集；「等数据」对委托、测试的时限和授权有什么影响。
3. **一份真源、买卖改使用权**：和 knowbase 现有的分区、成交复制（`user-data-purchase`）、不许转卖（`no_resale`）、运行授权怎么接；卖家下架、逻辑删以后买家那一版的读路。
4. **knowlab 自助与平台的数据访问**：「给平台」按每次过程授权、留痕、到期即止，能不能落到现有的同意依据与运行授权上；自助的专家过门时机器重跑、审核员不看原始数据，够不够审。
5. **漏了什么**：有没有没讨论到、但重构 `数据拓扑.md` 前必须定的（例如配额与费用、检索索引分区、备份恢复、knowfeed 故障时的表现）。
