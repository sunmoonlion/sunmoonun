# Luna 评审：数据拓扑重构大纲

评审日期：2026-10-26。对象：[重构大纲](../数据拓扑重构-opus/重构大纲.md)及其引用的[讨论记录](../数据拓扑重构-opus/讨论记录.md)第 1–6 条。qwen 的 sunmoonun 检出为 `38cded79`。本文件提交到评审目录后，上述相对链接生效。

## 结论

**支持这次重构的方向，但建议先补齐下面的架构规则，再据此重写正式总纲。** 当前问题主要是几项已认可的产品行为之间尚未闭合，而不是章节不够多，也不是缺少采集技术栈。

保留：Knowfeed 负责供给，Knowbase 负责云端数据权威存储与访问控制，应用负责自己的业务过程；应用先找 Knowbase，缺数据再请求 Knowfeed；测试集与专家输入钉版本；产出默认不混入来源数据；具体采集框架留给 SDD。

这次按 **qwen 当前代码和 10 月 26 日讨论**评审，不把我此前在 luna 上看到的旧状态当成现状。SDD 0042 和 qwen 代码已具备用户令牌交换、四类运行授权、Knowlab 数据迁入 Knowbase 的接入及交易复制逻辑。这里的任务是演进既有模型，不是从零建立授权。发布 #28、#29 已上线是评审请求提供的背景，本次未访问集群独立核验。

以下 P1 表示正式总纲定稿前应解决的架构冲突；P2 表示需要补入总纲原则、由 SDD 展开的设计缺口。它们不是对尚未实现的新方案进行运行故障断言。

## 1. [P1] 展示、绑定、解析不能代替 Knowbase 的授权裁决

**定位：大纲第 28、45 行，§12 与冲突 3；关联第 24、25 行。**

“展示给应用 = 同意该应用使用”可以作为新的产品规则，但“委托改由解析签”容易把依赖解析器变成授权签发者。解析器负责找出候选数据，不能仅凭自己生成的需求为应用、人或专家增加权限。

例如：用户允许 Knowlab 使用一份数据，随后把测试交给平台。若只沿用 Knowlab 的展示范围，平台运营就可能获得用户只给机器的访问权；反过来，用户撤回平台授权后，已经钉住的测试也不能据此继续读取。

建议在总纲明确四个不同对象：

- **使用权**：用户基于上传、采集、购买等依据能如何使用数据。
- **应用可用范围**：展示按钮控制哪些应用可以发现、申请使用；如按钮同时表达同意，应明确用途与作用范围。
- **版本绑定**：任务、测试、专家明确依赖哪些不可变版本。
- **运行授权**：Knowbase 校验前述依据后，授予特定执行主体在特定过程、期限内读取指定版本的能力。

把“委托改由解析签”改成“解析得到绑定后，由业务应用向 Knowbase 申请运行授权；Knowbase 统一校验与签发”。平台过程还要区分运营人员和机器执行者，不能只有一个笼统的“平台身份”。

会话无需恢复逐份选择，但要补两个规则：新增展示数据何时进入已有会话范围；关闭展示是仅阻止新申请，还是同时撤销已有授权。应给出确定语义，不能由各应用自行解释。

代码依据：当前 [UserDataService.grant_test](/home/zymun/worktrees/qwen/knowbase-app/knowbase-backend/app/app/application/services/user_data_service.py:217)已经在 Knowbase 核同意范围并签发；[运行读取检查](/home/zymun/worktrees/qwen/knowbase-app/knowbase-backend/app/app/application/services/user_data_service.py:281)还会核过期、撤销和版本。应保留这个权威边界。

## 2. [P1] “专家能读、使用者看不到”必须区分界面隐藏与内容保密

**定位：大纲第 26 行，§10；讨论记录第 92–102 行。**

目前承诺包括：调用者看不到绑定资料、不能下载，但专家可以读、产出可以引用。如果原文进入调用者可控制的模型上下文、沙箱文件、工具响应或运行轨迹，隐藏知识库入口不能保证这些内容保密。

需先定义承诺是哪一种：

1. **不提供原始资料浏览和下载入口**：允许在授权范围内经专家输出引用。文档就应这样写，不能泛称“看不到”。
2. **调用者不得取得受保护原文**：必须建立独立的受控执行与输出边界，原文不能送进调用者可读取的上下文、文件和轨迹；单靠提示词约束无法兑现。

这会直接决定专家运行架构，不能全部留给实现时补。任务页“列出每份所用数据”也应区分内部审计清单与调用者可见清单，后者只展示允许披露的绑定信息。

另外，“能采”只说明获取资格。绑定阶段可以不新增人工审核，但首次用于他人任务、交平台测试、输出引用时仍应自动核对应许可；不能仅等专家在 Knowmart 上架时才检查。个人孵化与给别人运行是不同用途。

## 3. [P1] 逻辑删除不能覆盖撤权，依法删除不能统一等待运行结束

**定位：大纲第 29、46 行，§13 与冲突 4。**

“还在用的照旧可读”把保留历史、履行购买权益、继续运行混为一件事。若用户撤回一次平台测试授权，而该测试仍因钉版本被认定“还在用”，就与讨论记录第 5 条“撤回即止、转回自助立即撤权”冲突。

建议分开定义：

| 动作 | 规则应表达的效果 |
| --- | --- |
| 从个人列表移除、取消展示、普通逻辑删除 | 按约定停止新的发现或使用；已有合法引用是否继续有效，由引用类型决定 |
| 撤回某过程授权 | 后续读取立即受限；保留审计和证据不等于允许继续处理 |
| 卖家下架、删除自己的展示引用 | 不自动撤销买家已经取得且仍有效的独立使用权 |
| 数据被禁用、许可失效、依法删除 | 依适用依据处理，不能被历史绑定或正在运行自动豁免 |

第 46 行“只有注销或本人要求时真删、在跑的跑完”不宜作为通用规则。个人信息保护法第 47 条还规定了需要主动删除的情形；法定保存期限未届满或技术上难以删除时，允许的处理也受到限制，并非可以继续完成一般业务运行。应写成“停止不再有依据的处理，按适用保留与删除规则执行”，具体分类进入合规设计。[法条原文](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)

现有代码也不能直接复用为新语义：[delete](/home/zymun/worktrees/qwen/knowbase-app/knowbase-backend/app/app/application/services/user_data_service.py:156)会删除对象，授权读取会拒绝已删条目。新的“保留被引用版本”需要显式迁移，不是只改界面文案。

## 4. [P1] 必需数据缺失与可选数据缺失必须有不同的运行结果

**定位：大纲第 24 行，§8；讨论记录第 143 行“补不上就先做”。**

假设财务专家声明必须有连续三年的现金流量表，第三年获取失败。如果统一“先做、产出注明缺什么”，模型可能用两年完成三年趋势判断，任务仍被记成成功，测试与数值验收也失去共同标准。

建议总纲写明：**声明为必需的数据未满足时，依赖它的阶段不得进入成功状态；可以等待、失败，或经明确变更需求后继续。只有声明允许缺失的输入可以降级，并记录不完整状态。** 独立于缺失数据的步骤可以先执行。

运行中新增的需求也分必需、可选，不能由模型一句“补不上”静默修改专家原声明。对 Knowlab 的固定测试集，缺数据不能自动换另一家公司或另一版后继续计算同一个测试结果。

这不是新增概念：当前 [data_needs](/home/zymun/worktrees/qwen/knowbench-app/knowbench-backend/app/app/domain/workbench/data_needs.py:51)已经有 `required`、`min_count`、`max_count`，自动解析需要保留这些约束。

## 5. [P1] “一份真源、交易不复制”需要独立的使用权和引用模型

**定位：大纲第 21、27、29 行，§5、§11、§13。**

当前代码把条目归属表示为“用户 × 应用”，成交时为买方复制对象和条目。改成共用一份内容后，不能只是给卖家条目加一个买家列表：卖家删除、更正、取消展示或账户变化，可能连带影响买家及旧测试。

总纲至少应把下列概念分开，数据库设计留给 SDD：

| 对象 | 权威与职责 |
| --- | --- |
| 数据及不可变版本 | Knowbase 保存内容、摘要、来源、修订关系 |
| 用户使用权 | Knowbase 保存主体、权利依据、允许用途、适用版本、有效条件 |
| 应用展示引用 | Knowbase 管理展示关系，不复制数据主档 |
| 任务／测试／专家绑定 | 业务应用拥有绑定业务记录，引用 Knowbase 版本 |
| 交易 | Knowmart 拥有订单与履约记录，通过受限接口使 Knowbase 建立使用权 |

建议补三条不变量：同一交易重试只产生一次有效权益；成交完成以对应版本权益可用为前提，失败可恢复；内容去重不合并不同用户的许可依据和删除责任。

“一份”宜解释为**一个权威版本**，允许备份、受控缓存和可重建索引，不应解释成只能有一份物理字节。内容哈希相同也不意味着来源与权利相同。

代码依据：[purchase](/home/zymun/worktrees/qwen/knowbase-app/knowbase-backend/app/app/application/services/user_data_service.py:323)目前按交易编号幂等并复制对象。这是需要替换的已存在机制，不是尚未发生过交易即可忽略的旧文案。

## 6. [P2] 自动解析缺少“确定匹配”和“截至何时”的规则

**定位：大纲第 21、24、25 行，§5、§8、§9。**

主体、类型、期间、格式可以找到一批候选，但不总能唯一确定输入。同一公司、同一年度可能同时有母公司与合并口径、原披露与更正版、不同币种单位的表格。默认“最新”也无法支持按历史时点重现的研究和测试。

总纲应明确：

- 数据需求声明须能表达影响结论的口径和时间约束，具体字段由各数据类型的契约定义。
- 存在多个等价性未确认的候选时，不能任意取第一份。可由显式优先策略解决；不能解决时返回歧义，不恢复每次手挑数据的常规流程。
- 首次解析形成可追查的清单，记录需求、匹配理由、版本、时间条件；重试读取同一清单。
- “默认最新”只适用于明确允许的需求，且要写清按何时可获得的最新版本。
- 运行中新增依赖形成清单的新修订；已冻结的测试结果和输入不能被覆盖。

Knowlab 的测试集确认机制很好，应保留。还应把**测试集版本**与**专家版本**分别标识：同一专家可以在不同测试集上验证，同一测试集也可比较不同专家版本。

## 7. [P2] 找不到、暂时不可用、无权限不能都触发补采

**定位：大纲第 23、24、31 行，§7、§8、§15。**

三种结果覆盖了正常路径，但未覆盖 Knowbase 不可用、资料正在导入、描述不完整、候选歧义、版本被禁用等情况。若把这些情况归入“都没有”，应用会向 Knowfeed 重复提交，并把系统故障误报成缺数据。

总纲不必枚举 HTTP 状态码，但应区分“确定缺失”“暂时无法判断”“存在但当前不可使用”。只有确定缺失且请求在授权范围内才补采。权限不足的响应不得泄漏其他用户的私人目录；“你有但未展示”的提示只针对本人的数据。

还应定义供给完成的判据：**所需原件或数据已经由 Knowbase 接管，版本可定位、权限可校验、任务要求的读法已就绪，才能恢复相应步骤。** 下载完成、登记了 URL、通知投递成功，都不能单独算完成。

普通原文读取不应等待全文索引；需要表格的步骤则应等待对应表格可用。处理失败和索引失败不撤销已保存的原件。具体幂等、重试、通知补偿和暂存清理留给 SDD。

## 8. [P2] `common/backend` 的落点混淆了业务共享和部署共享

**定位：大纲第 24 行，§8。**

当前仓内对应目录是 [app-platform/common/backend](/home/zymun/worktrees/qwen/sunmoonun/gitops/components/app-platform/common/backend)，内容是部署准备、数据库、存储、服务身份和工作负载模板，并非各应用共同加载的业务运行库。

“共用解析规则”值得保留，但建议大纲改为职责描述，不先指定这个目录：

- Knowbase 统一执行目录查询、确定匹配、版本定位和权限裁决。
- Knowbench、Knowlab 各自编排自己的需求、等待、取消和恢复；Knowlab 定好的测试输入交给 Knowbench 执行时不再二次解析。
- 必要时通过有版本的契约／客户端库共用描述结构与纯校验，不共享数据库，也不把业务生命周期放入部署模板目录。

若这里本意是新建另一处公共业务库，需明确与现有部署目录不同，并在 SDD 决定位置及发布兼容方式。

## 9. [P2] 产出转为数据需要保留许可约束，测试证据需要明确本地例外

**定位：大纲第 25、26、30 行，§9、§10、§14；讨论记录第 208–212 行。**

“转为数据”会建立可被后续专家解析的新入口。如果产出含作者绑定的受限原文或购买数据的摘录，仅记录来源并默认“本人用”仍不足以说明之后能否展示给平台、绑定另一个专家或上架。新增数据身份不能自动产生超出原许可的使用权。

建议转换时创建新的来源引用／版本关系，保留原产出和测试证据的不可变性；将上游限制带入新的使用判断。这里不是断言所有衍生结果都必须继承所有输入限制，而是要求受限内容披露、再利用与独立生成结果有可执行的区分规则，不能仅凭用户点击转换升级权限。

“审核员只看测试产出、不看原件”同样不能替代数据授权：产出可能包含原文或敏感值，需要明确授权是否覆盖这些结果，或提供允许披露的审核视图。

另有一个直接冲突：本地执行产出“不存云端内容”，而 Knowlab 测试产出“一律进 Knowbase”。应明确本地自助测试的证据是否为例外、上传哪些内容、何时进入冻结证据。也要区分最终文件的权威存放位置与对话、工具响应、运行日志是否经过云端，避免把文件存储承诺写成整个执行过程不传内容。

## 10. [P2] 自动公共引用是产品机制，不是现有合规边界已经不变的证明

**定位：大纲第 42–45 行，冲突 1–3。**

我赞成在确定的任务范围内自动解析，不要求恢复手动逐份选择。但“先自动记一条个人引用”只能说明访问归属于谁，不能单凭这条技术记录证明“平台不提供数据”的原有论证仍然成立。

应如实记录变化：从用户逐项指定，转为用户委托任务后系统在约定范围内自动选择与补充。让 C-L2 与真实行为一致，再判断原合规论证哪些仍成立，哪些需要更新；不要用引用表把实质变化藏起来。本评审不代替该业务模式的法律定性。

建议自动请求至少绑定用户、任务、数据种类、主体／期间范围和资源上限。免费的公开来源也可能触发大批量采集，免费不等于无限范围。无需为每次合规范围内的补采新增确认；超出已有任务范围、费用上限或资格时才按既定规则处理。

平台模式下“运营不能代用户提”的约束也应落到主体校验：用户任务内的自动补采，与运营或模型任意扩大用户需求，不是同一行为。

## 11. [P2] 需要保留迁移原则，不能只列“哪些文档跟着改”

**定位：大纲第 35、38、50–55 行，沿革、删掉的内容及关联文档。**

删除已完成的旧步骤合理，但本次改变的是已经存在的条目归属、交易副本、授权范围、测试绑定与本地来源。只写沿革不能保证切换以后旧数据还能读、旧测试还能复核。

建议新稿补一小节“兼容与迁移约束”，只写结果，不写部署脚本：

1. 旧“用户 × 应用”条目迁成统一数据与展示引用时，不扩大可见范围。
2. 已成交副本迁成版本使用权时，保持买家独立权益、原交易和版本可追查，不能仅按哈希合并权利。
3. 已冻结测试、运行引用和专家版本的标识、摘要持续可定位；无法复现的旧记录明确说明原因，不伪装成可复现。
4. 关闭本地知识库入口与移除旧执行路径分开；旧委托只读和仍在执行的委托分别处理。
5. 旧运行授权到期或显式撤销后退出，不因新展示规则获得更宽范围。
6. SDD 给出兼容期、切换验证与回退边界；在切断旧读取路径前验证上述不变量。

这些是新旧架构的连续性要求，不要求总纲包含完整实施方案。

## 建议补入大纲的最小内容

不必推翻 21 节结构。建议在现有位置加六组架构结论：

| 位置 | 增补 |
| --- | --- |
| §5 | 数据版本、使用权、展示引用、业务绑定的区分；权威一份与物理副本的区别 |
| §8、§9 | 确定解析、必需／可选依赖、歧义与故障、固定清单、等待与恢复条件 |
| §10、§12 | 专家数据暴露边界；Knowbase 唯一授权裁决；人和机器的不同主体 |
| §11、§13 | 独立购买权益；删除、撤权、禁用、依法清除的区别 |
| §14 | 产出转换不自动升级许可；本地测试证据的存储例外 |
| 沿革之后 | 兼容与迁移原则；不把旧文档变更当成已完成迁移 |

建议在 SDD 用以下场景验证这些原则：同一需求重试不重复采集；Knowbase 暂不可用不触发补采；缺必需数据不成功；测试过程中撤权即停止后续读取；卖家删除展示不损害有效买家权益；上游更正不改旧测试输入；受限专家原文不经轨迹或产出转换绕过披露规则；本地自助测试能够按明确规则提交冻结证据。
