## 1. 自助孵化：用户怎么做出准专家（10-26 定）

所有者：「都按你的建议，记下来」。

**三种做法，可以混着用**：

| 做法 | 怎么做 | 规则的出处 |
| --- | --- | --- |
| 自己写 | 在 knowlab web端编辑器里一步一步填：步骤、每步的规则、交回物、验收、数据声明模板；有模板可套 | 他写的就是用户原话 |
| AI 帮着写 | 用 0029 的孵化方法，跑在他自己的 knowbench 沙箱里、用他自己的模型 key：从创意（六问或 skill）抽结构、列缺口附提议、工程化出清单；缺口直接问他，答完再来一轮 | AI 起草的每条规则都要他确认，确认了才算用户确认 |
| 导入 | 已有写好的 skill 或专家包，直接导进来 | 导入的内容算他的原话 |

**规矩**：
1. **出处把关照旧，由程序做**：每条规则必须有用户出处（原话或确认过的），对不上的不能拿去测（C-L1：方法只来自用户），自助也不能绕开。
2. **没有受理**：草稿直接建在创意版本上；创意改了出新版本，照常往下孵。
3. **钱和资源是他自己的**：AI 帮着写时用他的模型 key、他的沙箱、他的电脑，费用记在他名下；每轮的费用上限由他自己设。
4. **平台的人看不到**：创意、草稿、问答，只有他自己和机器能看到。
5. **和平台孵化的关系**：0029 的手工、辅助、自动三种以后都算「平台孵化」（都有运营参与）；自助是用户自己做。「AI 帮着写」和 0029 的自动孵化用同一套孵化方法，区别只是最后没有运营核。

## 2. 自助测试：用户怎么测（10-26 定）

所有者：「都按你的建议，记下来」（含「自己如何选」电脑的答复）。

**流程**：
1. 准备测试集：作者给主体，解析器按声明展开类型、期间、口径，作者确认后钉在草稿上；缺的公开披露照常预切合、确认一次、交 knowfeed。
2. 写验收用例：期望值只能由他自己填或确认（0029：平台代填期望值就等于平台给了标准答案）。
3. 发起：在 knowlab web端点「测试」，选在哪台电脑上跑；knowlab 凭 `app:knowlab` 签测试授权，交 knowbench 执行。
4. 运行：knowbench 在他的工作台里按用例逐条开委托跑，用他自己的模型 key；测试中专家要问人的问题直接转给他本人答。
5. 结果：一次测试一个编号，「通过 / 没通过 / 平台出错」附报告；结论、数值、判定理由作为测试证据经服务写入路进产出区，原始产出留在他电脑的项目目录；记下测试集版本、准专家版本、模式是自助。

**怎么选电脑**：
- knowlab 后端凭本人令牌向 knowbench 要他接入过的电脑（knowbench「我的电脑」里那几台），测试页列出电脑名、系统、在线与否。
- 默认：上次测试用的那台在线就是它；只有一台在线就是那台；离线的灰着不能选；一台都不在线不能发起，显示「去 knowbench 接入或打开电脑」。
- 第一次在某台电脑上测，让他从这台电脑的白名单目录里选一个放测试项目，以后记住；每次测试在里面建自己的子目录（如「测试-名称-编号」，同现在平台测试的做法）。
- 模型 key 用他在 knowbench 设置里填的；没填不能发起，显示「去 knowbench 填模型 key」。
- 跑的途中电脑掉线：停在「等电脑」，回来接着跑；等太久超时记「平台出错（电脑离线）」，可以重测。
- knowbench 要加一种运行方：现在测试只认配置里固定的测试账号与测试电脑，自助测试跑在用户本人的账号、他选的那台电脑上。

**规矩**：
1. 自助测试通过即出专家第 n 版（同 0037「通过即是专家」）；可以自用，要公开，交付时平台重跑。
2. 费用与资源是他自己的：每次测试的费用上限由他自己设，到了就停，记「超预算」结束。
3. 平台出错就重测（新编号、同一个准专家）；专家自己没做对，就改草稿出新准专家（照 0037）。
4. 要有一台在线的电脑；没有就停在「等你接入电脑」并写明缺什么。
5. 平台的人看不到：测试集、用例、报告、证据只有他自己看得到；交付交审时由本人另外授权给审核员（已定）。

| | 自助测试 | 平台测试 |
| --- | --- | --- |
| 谁发起 | 用户自己 | 运营（只请平台测试的先过轻受理） |
| 在哪跑 | 用户自己的电脑 | 平台的测试电脑 |
| 用谁的模型 key、谁出钱 | 用户自己 | 平台 |
| 谁看结果 | 用户自己 | 运营和用户 |
| 测试中的问题转给谁 | 用户自己 | 运营看过后转给用户 |

## 3. 两种模式怎么组合、中途怎么切换（10-26 定）

所有者：「都按你的建议，记下来」。

模式按每一次过程选（每一轮孵化、每一次测试各选各的）；同一位专家的不同版本可以用不同组合做出来。

| 组合 | 怎么走 | 谁看得到什么 |
| --- | --- | --- |
| 自助孵化 + 自助测试 | 全程自己做；测试通过出专家；提交交付即过用户同意门 | 只有他自己；交审时另外授权给审核员 |
| 自助孵化 + 平台测试 | 把草稿交平台测：先过轻受理，本人授权平台测这一次（范围是这次的测试集），在平台测试电脑上跑 | 运营看得到这一版草稿、这次测试集与结果；看不到他之前的草稿与问答 |
| 平台孵化 + 自助测试 | 平台受理、孵化（照 0037），草稿交还给他，他拿自己的数据自己测 | 运营看得到孵化过程；看不到他的测试集与测试结果 |
| 平台孵化 + 平台测试 | 现在 0037 这一版 | 运营和用户都看得到 |

**中途切换**：

| 切换 | 怎么做 |
| --- | --- |
| 孵化：自助转平台 | 在当前这版草稿上点「请平台孵化」= 提受理申请、附这版草稿，同时本人授权平台看这个创意与这版草稿；受理后运营接着孵化 |
| 孵化：平台转自助 | 点「我自己来」：平台对这个创意的授权立即撤销，运营从此看不到；当前草稿归他继续改；原来的规则出处不变（确认过的仍算确认过）；他改出的新版本运营看不到 |
| 测试 | 每次发起时选模式，跑起来以后不能切；要换就取消这次、用另一种模式重新发起（新编号） |

**规矩**：
1. 每个准专家版本、每次测试都记下模式，历史上每一步谁做的都查得到。
2. 运营只看得到平台模式的那几步与用户另外授权的，看不到自助那几步的东西。
3. 过门怎么审，看测试通过的那一次是什么模式：自助测的公开时平台重跑，平台测的不用。
4. 默认：第一次让用户自己选，两边的说明并排给他看（谁看得到他的数据、用谁的 key、谁出钱）；以后默认用他上次的选择。

## 4. 页面（10-26 定）

所有者：「都按你的建议，记下来」。现在 web端是申请、审核、专家三栏（加名称详情页、问题页、知识库页、几个旧地址跳转）；管理端是受理、孵化、测试、交付四栏。

**web端：左边过程，右边结果**（照 0037「过程和结果分开」）：

| 位置 | 栏 | 放什么 |
| --- | --- | --- |
| 左（过程） | 申请 | 写创意、改创意出新版本（照旧） |
| | 孵化（新） | 按名称列，每条标当前模式。自助：编辑器（步骤、带出处的规则、交回物、验收、数据声明模板）、「AI 帮我写」（设费用上限、看第几轮）、「导入」；平台：看进度、在等你什么。切换按钮「请平台孵化」「我自己来」 |
| | 测试（新） | 测试集（给主体、展开、确认、钉住，有测试集版本）、验收用例（期望值）、发起（选模式；自助的选电脑、设费用上限）、历次测试（编号、模式、结果、报告、证据） |
| | 交付（新） | 选专家版本，定自用或公开，授权审核员看这次交付，看审核进度（自用的自动查结果；公开的审核结论与重跑结果），过了进 knowmart 小店 |
| | 待办（原「审核」改名） | 要你处理的都在这一处：平台转来的问题、请你审核的准专家、用户同意门、「AI 帮我写」列出的缺口 |
| 右（结果） | 专家 | 各版本：自用或公开、在架状态，链到 knowmart 小店 |
| | 知识库 | 只展示给了 knowlab 的数据，链到 knowbase 去管 |

- 名称详情页照旧一个骨架，时间线每一步标模式。
- 首页「在等你」：有缺口要答、测试通过了去交付、交审有结果了。旧地址照旧只做跳转。

**管理端：四栏照旧，只看得到该看的**：只列平台模式的条目与用户授权的；受理栏分正式受理（平台孵化）与轻受理（只请平台测试）；交付栏对自助测的显示平台重跑结果，对自用的显示自动查结果，查不过的才进人工队列。

**转平台、转回自助都不跳转**（所有者问「那如果转平台运营人员测试或孵化，页面跳转吗」，答复所有者认可）：用户始终在 knowlab web端同一页，运营始终在管理端，两边看同一条记录的两个视图。
- 转平台：先弹确认框，写明平台会看到什么（这个创意与这版草稿，或这次的测试集）、到什么时候、运营每看一次留痕，这一下就是本人授权；确认后留在原页，模式标签变「平台」，页面从编辑器换成平台视图（进度、在等你什么、运营问了什么）；这一条同时进管理端队列（请平台孵化进「受理」，只请平台测试进「轻受理」）；运营要用户答问题、确认或有了结果，进「待办」、首页「在等你」、发站内信，点进去回到这一条的页面。
- 转回自助：同一页换回编辑器，顶上提示「平台的授权已撤销，运营从此看不到这一条」。

**knowbench**：自助测试在用户自己的工作台里建项目，「AI 帮我写」沿用 0029 的「孵化」项目，他在 knowbench 里都看得到。

## 5. 交付放进组合里（10-26 定）

所有者：「都按你的建议，记下来」。

| 测试通过的那一次是 | 用户同意门 | 自用 | 公开 |
| --- | --- | --- | --- |
| 自助测的（不管孵化是谁做的） | 「提交交付」即过 | 轻审：能自动查的自动查（成稿里有没有目标价、评级这类内容，测试结果与受理单对不对得上），查不过才交人看 | 完整审核 + 平台在测试电脑上重跑（另签一条机器授权，审核员看结果、不看原始数据） |
| 平台测的 | 平台孵化的：用户在 web端确认要这一版（先用户、后运营）；**自助孵化 + 平台测试的：「提交交付」即过**（草稿是他自己做的） | 轻审，同上 | 完整审核，不用重跑 |

不管哪种组合（已定）：交出去的是清单 v2，绑定的数据留在 knowbase；交审时本人授权审核员看这次交付，审完撤销；自用转公开时许可重查；改绑定出新一版、重新交付，买家那一版不变。
