# 数据拓扑重构讨论记录

> 所有者把思路写在同目录上一级的 `数据拓扑重构准备`，逐条和 Opus 讨论；这里记每条的结论（所有者原话、谁做什么）和还没说到的。全部讨论完，再按这里重构 [数据拓扑](../../数据拓扑.md)。

## 1. knowbench 本地知识库：删（2026-10-26 定）

**所有者问**：「现在的knowbench的本地知识库好像没有啥用，可以删掉吗」

**Opus 意见**：同意删。
- 和项目目录重复：专家本来就在用户电脑的项目目录里读写，想让专家看的本机文件放进项目目录就行。
- 「原文件不进云端」分量轻：大脑在云端，选中的本地文件每次读都整份经会合点传到 knowbench 后端再给模型，只是不存进对象存储。
- 它是唯一不在 knowbase 的知识库，为它多一整套：钉住、核摘要、分块回读、兼容老 link、link 的目录设置与 Windows 权限、网页一页、选数据分两个来源。
- 委托跑多久，用户电脑上的 link 就得连多久。

**所有者定**：「对，如果远端要用数据，就上传进knowfeed，如果本地用，直接放进项目目录。」
- 云端要用的数据：用户上传进 knowfeed。（第 3 条改：上传从 knowfeed 剥离，改在 knowbase web端。）
- 本地要用的数据：用户直接放进项目目录。

**还没说到、待后面定**：
- ~~上传进 knowfeed 以后落在哪、谁能用~~：第 2、3 条定。
- 现在 knowbench、knowlab、knowmart 网页上各自的「上传」入口，是不是都改成经 knowfeed。
- 项目目录里的文件不算钉住的数据，不参与专家数据要求的核对：专家写了数据要求时，只能从云端选。
- 已上线的本地数据委托记录（knowbench 委托表允许 `source='local'`，随 #28、#29 与 link 0.5.3 发出）：Opus 建议新委托不再接受本地来源，老记录只读留着，不迁移、不删。生产库里有没有这种记录还没查，查要所有者授权。

**要改的**（不插进现在这批发版，随 knowfeed 那一轮）：
- knowbench 后端：选数据、钉住、回读里的本地来源；网页端：本地知识库页、选数据对话框的本地来源、设置里的目录一项。
- link 出 0.5.4：删本地知识库目录设置与服务流对它的只读范围、Windows 桌面界面那一栏；老配置里还有这一项时读了忽略，不报错。
- 文档：`数据拓扑.md` 第八节、第十六节第 2 条、第十七节「按用途分」、承诺清单第 10 条；SDD 0042 的 A 类。

## 2. 真源、供给与读：先找 knowbase，要不到再经 knowfeed 补（2026-10-26 定）

**所有者说**（按先后）：
- 「数据需求通过上传或采集后会存储在knowfeed，然后数据展示和使用都从knowfeed取。我们的云端知识库属于数据展示部分，它读取knowfeed的存储后在网页展示」
- `数据拓扑重构准备` 第 3–14 行：「数据存储的真源只有两个：一是本地的文件系统，一是云端的knowfeed」「用户需要可以把数据放到项目里，所以，只讨论云端knowfeed。」「knowfeed的web端主要是用户提出的采集需求入口和上传入口，knowfeed的后端负责前端和其它应用（比如knowbench knowlab等）的数据请求的处理」「knowbase则处理数据的存储，检索，统计等需求」「knowlab、knowbench和knowmart则提出数据的检索需求和统计需求」「数据分为数据的供给和需求，数据的需求有两个可以提出需求的入口：一个是knowfeed的web前端，一个是各个应用直接调用knowfeed的api。」
- 第 13–14 行的意思：「首先直接找knowbase的后端要，要不到再找knowfeed的后端提请求然后再从knowbase的后端要」；「knowfeed和knowbase有三个端，web端，管理端和后端，各自职责不同，这里要细分」。
- 对 Opus 下面三点与「对已有数据的操作留在 knowbase」：「可以，记下来」。

**定下来的**：
- 真源两个：本地是用户电脑上的项目目录（第 1 条）；云端是 knowfeed 这一套，对外收数据的是 knowfeed，存在 knowbase 里。
- 数据分供给和需求。供给是采集、上传，归 knowfeed；存、检索、统计归 knowbase。
- 读的流程（谁做什么）：
  1. 应用（knowbench、knowlab、knowmart）的后端要数据，先直接找 knowbase 后端检索、读、统计；
  2. 要不到，由用户明确提出，应用后端代他找 knowfeed 后端提请求；用户也可以在 knowfeed web端自己提；
  3. knowfeed 采集或收上传，入库到 knowbase；
  4. 应用后端再从 knowbase 后端要。
- 云端知识库页面属于展示：各应用 web端 → 自己的后端 → knowbase 后端，自己不存。前端只连自己的后端（数据拓扑第二节老规矩）。
- 解开了上面那处冲突：knowbase 仍是存数据的地方，各应用读数照旧直接找它；knowfeed 是供给的门。

**Opus 提的三点**（所有者认可）：
1. 要不到以后不干等：提请求时 knowfeed 先回请求编号；入库后通知应用，或由应用查进度。应用要有「等数据」的状态（例如委托停在「等数据」，到了再跑）。
2. 不自动去采：检索没结果不一定是缺数据；代采只能由用户发起（数据拓扑第七节）。第 2 步要用户明确点「请求采集」，应用后端不能见搜不到就自己提。
3. knowfeed 受理前先查重：先问 knowbase 有没有，再看有没有同样的请求在跑，有就并到一起。

另外：对已有数据的操作不是供给，留在 knowbase、不经 knowfeed，例如 knowmart 成交复制、knowlab 搬旧资料、签测试授权。

**各端分工**（现在代码里：knowfeed、knowbase 的 web端都只有模板页；knowfeed 管理端有采集任务、采集请求、证券、关注清单；knowbase 管理端有数据集目录、数据集、入库记录）：

| 端 | 职责 | 依据 |
| --- | --- | --- |
| knowfeed web端 | 用户提采集需求（上传第 3 条移到 knowbase web端） | 原话 |
| knowfeed 后端 | 处理 knowfeed web端和各应用后端的采集请求；受理前查重；入库到 knowbase；回请求编号、通知进度 | 原话加上面三点 |
| knowbase 后端 | 存储、检索、统计；各应用后端直接来读；收 knowfeed 的入库；对已有数据的操作（成交复制、搬旧资料、测试授权） | 原话加上面那句 |
| knowfeed 管理端 | 通常的管理职能，特殊的再说（第 3 条定）；代采的资格审核在这里（第 3 条） | 原话 |
| knowbase web端 | 用户上传；展示这个用户的全部数据，并给各应用、专家展示选择按钮（第 3 条定，取代 Opus 原建议「不给用户用」） | 原话 |
| knowbase 管理端 | 通常的管理职能，特殊的再说（第 3 条定） | 原话 |

**还没说到**：
- 「统计」指哪类。
- 专家按钉住的版本整份读原文（抽文字、翻页、按格子取数），Opus 理解算在「检索、读」里，待确认。
- 专家的产出在云端放哪。
- ~~存在一处以后，各应用、各用户的数据怎么分开~~：第 3 条定（集中存储，字段区分；展示按钮管出现在哪）。
- ~~各应用里的上传入口~~：第 3 条定，各应用没有上传入口。
- knowfeed web端要不要让用户看自己提过的采集请求、进度、质检结果：Opus 建议要；待定。

## 3. 根本原则：应用是使用者，知识库栏与 knowmart 是展示者，真源在 knowbase（2026-10-26 定）

**所有者说**（按先后）：
- 「knowfeed和knowbse的管理端就是通常的管理职能有特殊的再说。knowbase的web端应该负责用户的上传，上传功能应该从knowfeed里剥离出来。数据我认为集中存储，通过存储字段来区分需求来源是谁，可以为谁所用」
- 「有个根本原则：应用是使用者，知识库和knowmart是展示者，真源在knowbase。知识库的展示栏和knowmart的卖方的展示栏同类。根据这个原则：knowmart的买卖只是买家的知识库多了一份买来的知识，但其实真源只有一份。knowlab和knowbench的知识库也是如此。」
- 「knowbench knowlab和knowmart没有上传入口，它们只有展示，在knowbase为各用户添加一个它采集和上传的所有数据的展示栏」
- 「konwbase web端除了展示它的所有数据，还要为它的各个应用提供展示选择按钮。选择后数据直接在相应应用展示。」「应用还有一种特殊情形：专家。专家如果需要绑定数据，那么它是一种特殊的应用形式」
- 对 Opus 关于 knowmart 待上架与专家绑数据五条的建议：「可以，都按你的建议，记下来。但有一条例外：我认为代采来的也能绑，能代采就说明它有权采，所以真正限制的是代采时要求有权力，这里考虑进行资格审核，应有管理端做」

**定下来的**：
- 角色：各应用（knowbench、knowlab，以及专家）是使用者；各应用的知识库栏和 knowmart 是展示者，knowbench、knowlab 的知识库栏与 knowmart 卖方的展示栏同类；真源在 knowbase，每份数据只存一份。
- 集中存储：存在 knowbase 一处，用字段区分需求来源是谁、可以为谁所用；每次读由 knowbase 后端统一核。
- 上传：从 knowfeed 剥离，只在 knowbase web端。knowbench、knowlab、knowmart 没有上传入口，只展示。
- knowbase web端：给每个用户一个总栏，展示他采集来的、上传的全部数据；每份数据旁有各应用（和他名下专家）的展示选择按钮，选了就直接在那个应用展示。
- 两个管理端：通常的管理职能，特殊的再说。
- 买卖：买家的知识库栏多显示一份买来的知识，真源仍只有一份。knowlab、knowbench 的知识库栏同理。
- knowmart 上架（Opus 建议，所有者认可）：在 knowbase 选 knowmart 后，这份数据先进卖家在 knowmart 的「待上架」；卖家在 knowmart 填介绍、样张、价格、驻场规则后才真上架。
- 专家是一种特殊的应用：专家要绑数据时，作者在 knowbase 的展示按钮里选这位专家。五条（Opus 建议，所有者认可，第 1 条有例外）：
  1. 谁能绑：只有专家的作者能绑，绑他自己上传或代采来的数据。**例外（所有者）**：代采来的也能绑，「能代采就说明它有权采」；限制放在代采那一刻要求有权，由管理端做资格审核。
  2. 用专家的人看不到绑的数据：专家干活时能读，产出里可以引用；不出现在请专家的人的知识库栏里，也不能下载。
  3. 钉版本：每一版专家绑数据的固定版本，knowlab 测的就是这一版；作者改数据要出新一版专家，买家原来用的那一版不变。
  4. 和请的人选的数据并存：绑的是专家自带的（方法文档、行业词典等），数据要求是每次由请的人提供的。
  5. 删除：作者在栏里删只是拿掉；还有哪一版专家在用，真源就不删。

- 两道关，各在各的后端（所有者：「有权才不一定有权卖。对，应该在相应后端审核有权卖」；对 Opus 的整理：「对，记下来」）：
  1. 采的时候审有权采：knowfeed 受理代采时审，资格审核由 knowfeed 管理端做。审过后把这个来源许可的用法写进这份数据的字段，三档：只许本人用、可以经专家给别人用、可以出售。用户自己上传的，上传时由用户声明是哪一档。
  2. 卖的时候审有权卖：在 knowmart 后端审。卖家上架数据时核字段是否「可以出售」；专家上架时核它绑的每份数据是否「可以经专家给别人用」。必要时让卖家补证明，和 knowmart 现有的主体实名、类目证照审核同类。
  - 绑定本身不审：作者在 knowlab 绑来孵化、测试是自己用；专家要上架卖时才由 knowmart 后端把关。
  - 代采来的能不能上架：看字段有没有「可以出售」，过了 knowmart 后端这一关就能卖。

**推翻或改动的旧决定**：
- 10-23「四类相互独立，不互相读」：从存储上的独立改为展示上的独立，出现在哪由 knowbase 的展示按钮管。
- 10-23「专家不绑数据」（`数据拓扑.md` 第五节）：改为专家可以绑数据。
- 0042 成交复制（`user-data-purchase` 复制对象）：改为给买家加一条使用权，不复制。
- 第 1 条「上传进 knowfeed」：改为上传进 knowbase。

**还没定**：
- 一般的删除规则（不只专家）：Opus 建议在栏里删只是拿掉，没人再用（买家、钉住这一版的测试、正在跑的授权）时才真删。
- 卖家更新版本后，买家拿到买时那一版还是跟着更新。
- 买来的数据在不在 knowbase 总栏里：Opus 建议在，单列「买来的」，只看不改、不能上架。
- 从应用跳到 knowbase 上传：Opus 建议各应用在缺数据处放「去上传」，打开 knowbase 上传页并带上来源应用，传完回原页面、默认勾上来源应用；同一套账号不再登录。
