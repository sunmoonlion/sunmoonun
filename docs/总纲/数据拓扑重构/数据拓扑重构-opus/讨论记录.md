## 1. knowbench 本地知识库：删（2026-10-26 定）

**所有者问**：「现在的knowbench的本地知识库好像没有啥用，可以删掉吗」

**所有者定**：「对，如果远端要用数据，就上传进knowfeed，如果本地用，直接放进项目目录。」
- 云端要用的数据：用户上传进 knowfeed。（第 3 条改：上传从 knowfeed 剥离，改在 knowbase web端。）
- 本地要用的数据：用户直接放进项目目录。

**还没说到、待后面定**：

## 2. 真源、供给与读：先找 knowbase，要不到再经 knowfeed 补（2026-10-26 定）

**所有者说**（按先后）：
- 「数据需求通过上传或采集后会存储在knowfeed，然后数据展示和使用都从knowfeed取。我们的云端知识库属于数据展示部分，它读取knowfeed的存储后在网页展示」
- `数据拓扑重构准备` 第 3–14 行：「数据存储的真源只有两个：一是本地的文件系统，一是云端的knowfeed」「用户需要可以把数据放到项目里，所以，只讨论云端knowfeed。」「knowfeed的web端主要是用户提出的采集需求入口和上传入口，knowfeed的后端负责前端和其它应用（比如knowbench knowlab等）的数据请求的处理」「knowbase则处理数据的存储，检索，统计等需求」「knowlab、knowbench和knowmart则提出数据的检索需求和统计需求」「数据分为数据的供给和需求，数据的需求有两个可以提出需求的入口：一个是knowfeed的web前端，一个是各个应用直接调用knowfeed的api。」
- 第 13–14 行的意思：「首先直接找knowbase的后端要，要不到再找knowfeed的后端提请求然后再从knowbase的后端要」；「knowfeed和knowbase有三个端，web端，管理端和后端，各自职责不同，这里要细分」。
- 对 Opus 下面三点与「对已有数据的操作留在 knowbase」：「可以，记下来」。

**定下来的**：
- 真源两个：本地是用户电脑上的项目目录（第 1 条）；云端是 knowfeed 这一套，对外收数据的是 knowfeed，存在 knowbase 里。
- 数据分供给和需求。供给是采集、上传，归 knowfeed；存、检索、统计归 knowbase。
- 读的流程（谁做什么）：
  1. 应用（knowbench、knowlab、knowmart）的后端要数据，先直接找 knowbase 后端检索、读、统计；
  2. 要不到，由用户明确提出，应用后端代他找 knowfeed 后端提请求；用户也可以在 knowfeed web端自己提；
  3. knowfeed 采集或收上传，入库到 knowbase；
  4. 应用后端再从 knowbase 后端要。
- 云端知识库页面属于展示：各应用 web端 → 自己的后端 → knowbase 后端，自己不存。前端只连自己的后端（数据拓扑第二节老规矩）。
- 解开了上面那处冲突：knowbase 仍是存数据的地方，各应用读数照旧直接找它；knowfeed 是供给的门。

**Opus 提的三点**（所有者认可）：
1. 要不到以后不干等：提请求时 knowfeed 先回请求编号；入库后通知应用，或由应用查进度。应用要有「等数据」的状态（例如委托停在「等数据」，到了再跑）。
2. 不自动去采：检索没结果不一定是缺数据；代采只能由用户发起（数据拓扑第七节）。第 2 步要用户明确点「请求采集」，应用后端不能见搜不到就自己提。
3. knowfeed 受理前先查重：先问 knowbase 有没有，再看有没有同样的请求在跑，有就并到一起。

另外：对已有数据的操作不是供给，留在 knowbase、不经 knowfeed，例如 knowmart 成交（第 3 条改为加使用权）、knowlab 搬旧资料、签测试授权。

**各端分工**（现在代码里：knowfeed、knowbase 的 web端都只有模板页；knowfeed 管理端有采集任务、采集请求、证券、关注清单；knowbase 管理端有数据集目录、数据集、入库记录）：

| 端 | 职责 | 依据 |
| --- | --- | --- |
| knowfeed web端 | 用户提采集需求（上传第 3 条移到 knowbase web端） | 原话 |
| knowfeed 后端 | 处理 knowfeed web端和各应用后端的采集请求；受理前查重；入库到 knowbase；回请求编号、通知进度 | 原话加上面三点 |
| knowbase 后端 | 存储、检索、统计；各应用后端直接来读；收 knowfeed 的入库；对已有数据的操作（成交加使用权〔第 3 条改〕、搬旧资料、测试授权） | 原话加上面那句 |
| knowfeed 管理端 | 通常的管理职能，特殊的再说（第 3 条定）；代采的资格审核在这里（第 3 条） | 原话 |
| knowbase web端 | 用户上传；展示这个用户的全部数据，并给各应用、专家展示选择按钮（第 3 条定，取代 Opus 原建议「不给用户用」） | 原话 |
| knowbase 管理端 | 通常的管理职能，特殊的再说（第 3 条定） | 原话 |

**还没说到**：

- 专家按钉住的版本整份读原文（抽文字、翻页、按格子取数），Opus 理解算在「检索、读」里，待确认。
- ~~专家的产出在云端放哪~~：第 6 条定。

## 3. 根本原则：应用是使用者，知识库栏与 knowmart 是展示者，真源在 knowbase（2026-10-26 定）

**所有者说**（按先后）：
- 「knowfeed和knowbse的管理端就是通常的管理职能有特殊的再说。knowbase的web端应该负责用户的上传，上传功能应该从knowfeed里剥离出来。数据我认为集中存储，通过存储字段来区分需求来源是谁，可以为谁所用」
- 「有个根本原则：应用是使用者，知识库和knowmart是展示者，真源在knowbase。知识库的展示栏和knowmart的卖方的展示栏同类。根据这个原则：knowmart的买卖只是买家的知识库多了一份买来的知识，但其实真源只有一份。knowlab和knowbench的知识库也是如此。」
- 「knowbench knowlab和knowmart没有上传入口，它们只有展示，在knowbase为各用户添加一个它采集和上传的所有数据的展示栏」
- 「konwbase web端除了展示它的所有数据，还要为它的各个应用提供展示选择按钮。选择后数据直接在相应应用展示。」「应用还有一种特殊情形：专家。专家如果需要绑定数据，那么它是一种特殊的应用形式」
- 对 Opus 关于 knowmart 待上架与专家绑数据五条的建议：「可以，都按你的建议，记下来。但有一条例外：我认为代采来的也能绑，能代采就说明它有权采，所以真正限制的是代采时要求有权力，这里考虑进行资格审核，应有管理端做」

**定下来的**：
- 角色：各应用（knowbench、knowlab，以及专家）是使用者；各应用的知识库栏和 knowmart 是展示者，knowbench、knowlab 的知识库栏与 knowmart 卖方的展示栏同类；真源在 knowbase，每份数据只存一份。
- 集中存储：存在 knowbase 一处，用字段区分需求来源是谁、可以为谁所用；每次读由 knowbase 后端统一核。
- 上传：从 knowfeed 剥离，只在 knowbase web端。knowbench、knowlab、knowmart 没有上传入口，只展示。
- knowbase web端：给每个用户一个总栏，展示他采集来的、上传的全部数据；每份数据旁有各应用（和他名下专家）的展示选择按钮，选了就直接在那个应用展示。
- 两个管理端：通常的管理职能，特殊的再说。
- 买卖：买家的知识库栏多显示一份买来的知识，真源仍只有一份。knowlab、knowbench 的知识库栏同理。
- knowmart 上架（Opus 建议，所有者认可）：在 knowbase 选 knowmart 后，这份数据先进卖家在 knowmart 的「待上架」；卖家在 knowmart 填介绍、样张、价格、驻场规则后才真上架。
- 专家是一种特殊的应用：专家要绑数据时，作者在 knowbase 的展示按钮里选这位专家。五条（Opus 建议，所有者认可，第 1 条有例外）：
  1. 谁能绑：只有专家的作者能绑，绑他自己上传或代采来的数据。**例外（所有者）**：代采来的也能绑，「能代采就说明它有权采」；限制放在代采那一刻要求有权，由管理端做资格审核。
  2. 用专家的人看不到绑的数据：专家干活时能读，产出里可以引用；不出现在请专家的人的知识库栏里，也不能下载。
  3. 钉版本：每一版专家绑数据的固定版本，knowlab 测的就是这一版；作者改数据要出新一版专家，买家原来用的那一版不变。
  4. 和请的人选的数据并存：绑的是专家自带的（方法文档、行业词典等），数据要求是每次由请的人提供的。
  5. 删除：作者在栏里删只是拿掉；还有哪一版专家在用，真源就不删。

- 两道关，各在各的后端（所有者：「有权才不一定有权卖。对，应该在相应后端审核有权卖」；对 Opus 的整理：「对，记下来」）：
  1. 采的时候审有权采：knowfeed 受理代采时审，资格审核由 knowfeed 管理端做。审过后把这个来源许可的用法写进这份数据的字段，三档：只许本人用、可以经专家给别人用、可以出售。用户自己上传的，上传时由用户声明是哪一档。
  2. 卖的时候审有权卖：在 knowmart 后端审。卖家上架数据时核字段是否「可以出售」；专家上架时核它绑的每份数据是否「可以经专家给别人用」。必要时让卖家补证明，和 knowmart 现有的主体实名、类目证照审核同类。
  - 绑定本身不审：作者在 knowlab 绑来孵化、测试是自己用；专家要上架卖时才由 knowmart 后端把关。
  - 代采来的能不能上架：看字段有没有「可以出售」，过了 knowmart 后端这一关就能卖。

- 删除、版本、总栏（所有者：「1，都是逻辑删，不真删；2，当初交易的那一版；3，在，所以总栏要分类」）：
  - 删除一律是逻辑删，不真删（不只专家绑的；专家第 5 条随之统一）。
  - 卖家更新版本后，买家拿到的是当初交易的那一版。
  - 买来的数据也在 knowbase 总栏里，所以总栏要分类（Opus 建议分「我上传的」「为我采集的」「买来的」三类；买来的只看不改、不能上架）。

**推翻或改动的旧决定**：
- 10-23「四类相互独立，不互相读」：从存储上的独立改为展示上的独立，出现在哪由 knowbase 的展示按钮管。
- 10-23「专家不绑数据」（`数据拓扑.md` 第五节）：改为专家可以绑数据。
- 0042 成交复制（`user-data-purchase` 复制对象）：改为给买家加一条使用权，不复制。
- 第 1 条「上传进 knowfeed」：改为上传进 knowbase。

**还没定**：
- ~~从应用跳到 knowbase 上传~~：第 4 条已定（所有者：「第三条不是已经说了吗」）。不再有选数据；只剩采不来的私有资料，报错时附直达 knowbase 上传的链接，传完自动展示给这个应用。直达链接回跳的地址只限我们自己几个应用（白名单）。

## 4. 应用要数据时自动解析：不再有「选数据」（2026-10-26 定）

**所有者说**：
- 「在konwbennch和knowlab里，应该没有选数据这一说了：如果哪个步骤要数据，直接查它自己的知识库（展示知识库的原因就是为了应用到知识库选用，展示给用户看的其实在knowbase的展示总栏），如果没有直接到knowfeed提需求，没权利则直接报错/请求审批回复」
- 「首先，你对这个的看法，先完善方案，再回答你的细节」
- 对 Opus 完善后的方案：「可以，记下来，但你缺少knowlab，它们可能和knowbench不一样」

**Opus 看法**（所有者认可）：这是「声明依赖、自动解析」的做法（像装软件依赖：先在本地找，找不到去仓库取，再没有就报错）。用户不再手挑数据；knowfeed 成为供给主力。前提是「要什么」机器能准确认出来，靠按描述精确匹配，不靠模糊检索，所以要一套统一的数据描述。

**方案**：
1. 统一的数据描述。knowbase 每份数据带：
   - 是什么：主体（公司、证券代码）、类型（年报、公告、行情……）、期间、格式。采集来的由 knowfeed 入库时填；上传的由用户填，或自动识别后用户确认。
   - 从哪来：公开披露、为某用户采集、用户上传、买来的。
   - 许可用法：只许本人用、可以经专家给别人用、可以出售（第 3 条）。
   - 需求来源与展示范围：哪个应用提的需求，展示给了哪些应用。
   - 专家的数据要求用「是什么」同一套词写。
2. 两个区：
   - 公共区：交易所、巨潮等公开披露的，存一份，所有用户、所有应用都能用，不用勾。（第 7 条改：不叫公共区，读之前用户名下要有一条引用，任务解析到时自动记。）
   - 个人区：上传的、为他采集的、买来的，展示给哪个应用由 knowbase 总栏的展示按钮管。
   - 一个应用能用的范围 = 公共区 + 这个用户展示给它的个人数据。
3. 解析流程（任务开始前）：
   1. 应用后端按专家的数据要求问 knowbase「按描述查」，三种结果：在本应用能用的范围里 → 钉版本直接用；用户有但没展示给本应用 → 请用户到 knowbase 放开，不自动替他勾；都没有 → 下一步。
   2. 应用后端向 knowfeed 提需求，带用户与需求来源（本应用）。
   3. knowfeed 查重，核资格与费用：能采 → 回请求编号，任务进「等数据」；采到、质检、入库后按「需求来源」自动展示给这个应用，通知应用，任务接着跑。没资格 → 报错，或转 knowfeed 管理端审批，批复后通知应用。采不来（私有资料）→ 告诉用户去 knowbase 上传，附直达链接，传完自动展示给这个应用。
4. 运行中临时冒出的需求：走同一流程；很快能补就等，补不上就先做，在产出里写明缺什么。（第 7 条 D7 改：只对可选数据；必填的缺了不算成功。）
5. 任务页列出这次用到的每份数据（名字、版本、来源），能追查、能复现。
6. 钉版本照旧；专家绑的数据随专家带上，同样钉版本，不给用户看。

**对现有代码的影响**：knowbench 去掉 0042 的「选数据」对话框与后端选数据，换成解析，委托加「等数据」状态；knowbase 加描述字段、公共区、「按描述查」接口（回上面三种结果）；knowfeed 加受理需求接口、查重、资格与费用核对、完成通知；解析逻辑写成公共代码放 `common/backend`，knowbench、knowlab 共用。

**knowlab 与 knowbench 不一样的地方**（Opus 整理；所有者：「可以，都按你的建议，记下来」）：
- knowbench 是「用专家干活」：一件委托，用请的人的数据跑一次，自动解析合适。
- knowlab 是「做专家、测专家」，差在五处：
  1. 测试要的是一组特意挑的数据（测试集）：几家公司、正常的和刁钻的都要有，自动挑「最新的一份」不合测试的用意。Opus 建议：解析器按声明把能用的候选都找出来，提议一组测试集，作者确认或增删后钉住。
  2. 测试集要跨草稿版本反复用：同一组数据测第 1 版、第 2 版才比得出好坏。测试集钉在草稿上，改了草稿照样用；只有数据要求变了，才重新解析（现在已有 `data_binding_stale`）。
  3. 数据要求本身还在写：作者边写声明边测，声明变了，测试集要跟着重核。knowbench 用的是写定了的声明。
  4. 专家绑的数据在 knowlab 这一侧定：作者在 knowbase 总栏把数据绑给自己名下的专家（第 3 条）；测试时绑的数据和测试集一起读。
  5. 测试在 knowbench 上跑（`knowbot-test-run/v1`），但解析归 knowlab：knowlab 定测试集、签测试运行授权；knowbench 只照授权读那几份，不对测试再跑一遍自己的解析。原则是谁的任务谁解析。
- 辅助孵化（帮作者写数据要求）只看格式，从 knowlab 能用的范围里取样。
- 缺数据时向 knowfeed 提需求，knowlab 常常一次要一批（如 10 家公司的年报），需求来源记 knowlab，入库后展示在 knowlab 栏。

**还没定**（上一轮的细节，待方案定后回答）：
- 和第 2 条第 2 点「不自动去采」的冲突：Opus 建议用户发起任务就算提了要求，免费的公开数据应用直接提，要花钱或要资格审核的先问用户。
- 栏里有几份都符合时怎么挑：Opus 建议声明能唯一认出就自动选、默认最新一版，认不出才问用户一次（knowlab 测试集另按上面第 1 处）。

## 5. knowlab 的孵化、测试各自可选：自助或平台（2026-10-26 定）

**所有者说**：
- 「在knowlab中，我么现在做的可以说是平台代为孵化，但是，要做的一个重大改变是：现在的这一版的全部要有另一版：自助……目前我们基本属于平台（如果要改也可以调整），我们要新增自助。这里再数据方面显然自助和平台要求大不一样」
- 对 Opus 的分析与建议：「可以，都按你的建议，记下来。但是：无论是孵化还是测试，都是可选模式：自助/平台。所以我刚才说的向knowbench里的聊天/工作/专家那种模式好像不对，因为后者要换好像是整套换，这里好像可以部分换模式」

**定下来的**：
- 模式按过程选，不是整个 knowlab 一起换：孵化选自助或平台，测试也选自助或平台，可以组合（自助孵化 + 平台测试、平台孵化 + 自助测试等）。
- 平台：用户交创意，我们的运营受理、孵化或测试（现在这一版都归这里）。自助：用户自己写、自己测，可用辅助孵化（0037 第二节第 5 条「用户自编的走 knowlab 的简化流程」做成完整的一边）。
- 我们自己做「财务分析与预测」按普通用户身份，走自助。

**数据上的不同**（Opus 建议，所有者认可）：

| | 自助 | 平台 |
| --- | --- | --- |
| 谁会看到数据 | 只有用户本人和机器（他自己的模型 key、他自己的沙箱） | 还有我们的运营（人）和平台跑的测试 |
| 同意 | 不另外同意 | 用户明确同意「这几份给平台看、给平台测」，范围按这一次过程，不是整个 knowlab 栏 |
| 测试集谁定 | 作者自己确认（第 4 条） | 运营按用户的验收用例提议，用户确认 |
| 缺数据谁去提 | 用户自己，经解析流程向 knowfeed 提 | 运营不能替用户提（数据拓扑第七节），请用户提或请用户点头 |
| 能用哪些数据 | 用户能用的范围：公共区、个人区里展示给 knowlab 的、买来的 | 只用用户同意给这次过程的数据，加公共区；平台不拿自己的私有数据来测（合规：平台不带自己的逻辑和数据） |
| 留痕 | 照平时 | 运营每看一次、每测一次都留痕，用户看得到谁何时看了什么 |
| 结束以后 | — | 这次过程结束、用户撤回或不受理，平台即读不到，授权到期即止 |
| 过两道门 | 审核员看测试证据：平台用钉住的测试集由机器重跑一遍，审核员看结果、不看原始数据；要看原始数据另请用户同意 | 运营本来就看过，照现在 |

**原则**（Opus 建议，所有者认可）：
1. 数据栏不分两套：knowlab 一个知识库栏，自助、平台共用。差别在谁能读：自助只有本人；平台由用户另给一份「给平台」的授权，到期即止。
2. 平台的人看数据一律要本人同意、有范围、留痕。比现在严：0042 现在是传进 knowlab 栏就对整栏同意测试，平台模式收窄。
3. 能互转：自助做到一半请平台帮忙，转平台并请用户给授权；转回自助，平台的授权立即撤。

**按过程选模式带来的**（Opus 整理）：
- 「给平台」的授权范围从「按创意」细到「按这一次过程」：平台孵化给孵化用的那几份；平台测试给这次测试的测试集，按测试编号。
- 每个准专家版本、每次测试都记下是自助还是平台做的，过门时审核员据此决定要不要机器重跑（自助测的重跑，平台测的不用）。
- 页面上不做整套切换：孵化、测试这两步各有一个「自己做 / 请平台做」，左边栏的过程条目标出各自的模式。
- 平台孵化 + 自助测试：用户可以不把敏感数据给平台看，平台只照方法孵化，用户拿自己的数据测。

- 受理（所有者：「只请平台测试的也要轻受理，记下来。」）：平台孵化先受理（现在的受理单）；自助孵化不用受理（Opus 建议）；只请平台测试的也要过一道轻受理。

## 6. 专家的产出放哪（2026-10-26 定）

**所有者说**：「专家的产出放哪你的建议」；对 Opus 建议：「可以，都按你的建议，记下来」。

**前提**：产出是结果，不是来源（0042：产出不算知识库）。AI 的产出可能有错，自动混进数据会被下一位专家当事实读，错一路传下去。

**按在哪里干的活分三种**：
1. 在用户电脑上干的（用户自己的 link）：产出就在项目目录，真源是本地文件系统。云端只记一份清单（文件名、摘要、哪件任务产的），不存内容。
2. 在云端干的（例如平台测试跑在我们的测试电脑上）：产出存进 knowbase 的「产出区」，归这个用户；knowbase 总栏第四类「产出」，与「我上传的」「为我采集的」「买来的」并列。产出区不在解析范围里，应用自动找数据时不拿它当来源。
3. knowlab 的测试产出：是测试证据，钉在测试编号上，只增不改（0037「结果定了不改」），过门时审核员看它；存在 knowbase 产出区，knowlab 只记引用。

**产出转为数据由用户自己做**：在 knowbase 里点「转为数据」，才进个人区、才能被解析到。转时自动带出处（哪位专家哪一版、哪件任务、用了哪几份数据的哪几版），许可默认「只许本人用」。

**跟着改的**：第 3 条 knowbase 总栏的分类加第四类「产出」。
