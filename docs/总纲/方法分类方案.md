## 一、所有者原话（按先后）

1. 「是否同意将方法分为两大类：原子方法和专家，原子方法不能再被其它方法调用而专家则是调用原子方法和其它专家的方法？」（qwen 按「原子方法不能再调用其它方法」理解，所有者没有否认。）
2. 「有点不对。我们讨论：原子方法和专家都会注册到工具中心，但是方法只分两类：没有所谓工具方法。但模型调用会有所不同：两者虽然都通过注册中心调用，但是原子方法直接调用，而调用专家时会经过编排」
3. 「再次强调没有所谓的固定专家和季节性预测组合了，只要调用原子方法或其它专家，都是专家。补充两点：1，原子方法也要经过孵化，基本的方法由平台这个特殊作者孵化，其它作者需要的独立方法由作者自己孵化，没有经过孵化的方法不能使用；2，原子方法和专家各有自己的市场；两类市场被使用的机制一致」
4. 对 qwen 的补充意见：「都同意你的建议」。
5. 对第一稿：「你重改，都采用你的意见。另外，你再认真思考一下，进一步完善改稿，然后我提交给luna」。

## 二、一屏总览

- **方法只分两类**：不调用任何方法的是**原子方法**；调用了原子方法或别的专家的是**专家**。没有第三类。
- **都要孵化**：没孵化的方法哪里都不能用，聊天里也不能。平台孵化通用的基础方法，其它的由作者自己孵化；用户接外部工具、装技能，走自用的轻量孵化。
- **都进工具中心**：只收孵化过、冻结了版本的。原子方法被调用时直接执行；专家被调用时先编排、再逐步调用。
- **原子方法不调别的方法**，要的数据从输入进来。**专家的步骤只调用方法**，不嵌代码。
- **两个市场，一套机制**：原子方法市场、专家市场，knowmart 一套实现、两个入口。
- **五要素两视图**：五要素（能力声明、所需权限、做法、校验、审批）由作者写，两视图（对外输入、对外返回）由程序生成。不再叫「六要素」。

## 三、两类方法

| | 原子方法 | 专家 |
| --- | --- | --- |
| 判断标准 | 不调用任何方法 | 调用了原子方法或别的专家 |
| 内部 | 做法定死，可以有几步 | 步骤，每步调用一个方法 |
| 步骤怎么来 | 作者孵化时定好 | 使用时 AI 在作者规则内按题编排，用户确认 |
| 被调用时 | 直接执行 | 先编排，再逐步调用 |
| 谁孵化 | 基础的由平台孵化，其它由作者孵化 | 作者孵化 |
| 怎么测 | 固定用例：算得对不对 | 每道题选得对不对、结果对不对、计划守没守规则 |
| 市场 | 原子方法市场 | 专家市场 |

**没有第三类。** 不再有「固定专家」「组合方法」「季节性预测组合」「工具」这些另外的叫法：

- 只要调用了方法就是专家，不管步骤多少、规则松紧。现在的「财务分析与预测」是一位专家；原来叫「季节性预测与回测」的那种组合，也是专家。
- 「工具」不是一类。工具中心里登记的，不是原子方法就是专家；下文说「工具」，一律指已登记的原子方法。

**下面两样不是方法，也不登记：**

- **聊天和工作**：是用户自己的会话。模型在会话里调用方法，是替用户调用，会话本身不是一个方法。
- **编排机制**：排计划、出确认页、绑定输入和导出、调度、逐层验收、恢复，是平台的运行机制，不是一个方法。作者的规则约束它，它不由作者写。

## 四、什么算「调用方法」

**经工具中心发出的请求，才算调用方法。** 下面三样不算：

1. **实现载体**：原子方法的做法交给什么去执行（见 6.2），比如把公式交给平台的计算引擎、把脚本交给隔离容器，这是它自己的实现，不是调用了别的方法。
2. **访问外部资源本身就是这个方法的职责**：读数、发邮件、调外部 Agent，这些原子方法的工作就是访问资源，访问时按它自己声明的权限核权。
3. **编排机制**：在步骤之间搬运产物、绑定输入，是编排机制在做，不是步骤调用了方法。

除了第 2 种，**原子方法要的数据都从输入进来**，自己不去取。

## 五、现有的东西各归哪类

| 东西 | 归类 | 说明 |
| --- | --- | --- |
| 平台的计算、读数、查主体、提数据 | 原子方法 | 平台孵化的基础方法 |
| 外部 MCP 的每个工具 | 原子方法 | 一个工具一个原子方法，孵化后才能用 |
| 外部 Agent（A2A） | 原子方法 | 我们看不到它里面，当一个整体；交给它的数据按外发核权 |
| 技能包里的脚本 | 原子方法 | 在隔离容器里跑 |
| 只让模型按指令做、不调别的东西的技能 | 原子方法 | 一个范围固定的模型步骤 |
| 指令里要模型去调别的工具的技能 | 专家 | 它调用了别的方法；指令就是它的编排规则 |
| 财务分析与预测 | 专家 | |
| 聊天、工作 | 不是方法 | 用户自己的会话 |

技能是一种实现载体，按它调不调别的方法归类，不是一个单独的类。孵化时由程序按技能声明的依赖判定归哪类，作者确认。

## 六、原子方法

### 6.1 做法定死，数据从输入进来

- 内部可以有几步，但都是孵化时定好的，不在里面按题现排。
- 最多有一个范围固定的模型步骤，比如「核对管理层讨论」的判断。模型只判断，不调用方法；要读的材料和要用的数，都由专家的前一步准备好、作为输入传进来。
- 例子：「算 CAGR」不自己读财报。专家的计划先排一步「读数」，读出起止两年的营收，再交给「算 CAGR」。
- 要边做边调用别的方法的，就不是原子方法，是专家。

这样每条调用链最后都落到原子方法上，递归一定有底。

### 6.2 实现载体

| 载体 | 在哪执行 | 谁能用 |
| --- | --- | --- |
| 公式（交给平台计算引擎） | 后端，确定性，不开模型轮次 | 所有作者 |
| 脚本 | 隔离容器，无凭据、无网络 | 所有作者 |
| 指令（一个模型步骤） | 用户沙箱，用用户自己的模型；后端不调模型 | 所有作者 |
| 外部 MCP 工具 | 经 knowbench 统一入口核权后，由适配器访问外部服务；凭据不进沙箱 | 所有作者 |
| 外部 Agent（A2A） | 同上 | 所有作者 |
| 平台后端函数 | 后端 | 只有平台孵化的基础方法；作者的代码不进平台后端 |

### 6.3 复用与演进

- **原子方法之间不能互相调用。** 两个原子方法要用同一段算法，共用程序库或同一个公式，不互相调用。
- **原子方法可以升级成专家。** 作者想把一个原子方法拆开，就出一个新版本、改成专家。对外的输入和返回由程序生成，只要不变，调用它的地方不用改。
- **版本钉死。** 别人的专家钉的是确切版本，作者出新版不会自动改到别人那里；用到旧版的专家作者会看到「有新版」，自己决定换不换。

## 七、专家

### 7.1 步骤只调用方法，不嵌代码

- 每一步调用一个方法（原子方法或专家）。
- 步骤之间的字段对接（谁的产物给谁的输入），由编排机制按声明做，不写代码。
- 需要汇总、格式转换的，调用平台的基础原子方法（比如「合并结果」「转成表格」）。
- **成稿也是一步方法调用**：「按交付结构写成稿」由平台孵化成通用的原子方法，作者的交付结构作为固定配置传给它。
- 代码只出现在原子方法的实现里。

**为什么**：专家里再嵌一段没孵化、没测试的代码，就和「没孵化的不能用」冲突；专家的测试测的是「选得对不对」，测不到嵌在里面的代码。代价是平台要多孵化几个通用的小原子方法。

### 7.2 编排

- 作者在孵化时定候选方法、必做、条件必做、先后依赖、交付结构；使用时 AI 在规则内按题排计划，程序校验，用户在确认页确认。
- **规则只允许一种计划时，由程序直接生成，不开模型轮次。** 这只是一条效率规则，不是一种专家。
- 专家调专家：在已确认的范围内，下层自动编排，不再让用户确认；超出已确认的数据、权限、费用才停下问。

### 7.3 作者自带的数据

作者自带的数据，绑在它所属的那个方法版本上（原子方法或专家都可以）。被别人的专家调用时，数据不出这个方法，产出照现有的许可上限封顶。

## 八、五要素两视图

不再叫「六要素」，改叫**五要素两视图**（所有者 11-14 定）。**原子方法和专家都用这同一套**，调用的一方（专家的计划、聊天里的模型、市场的匹配）看到的形状完全一样，不用分两种处理。

| | 原子方法 | 专家 |
| --- | --- | --- |
| 能力声明 | 只有本层 | 本层的话，加直接下层的能力引用（钉版本）；可收窄、不可放宽 |
| 所需权限 | 写；纯计算的写「无」 | 写 |
| 做法 | 定死的做法和实现载体，含输入、输出的声明 | 候选方法、必做、条件必做、先后依赖、交付结构 |
| 校验 | 孵化时的固定用例，加运行时检查结果 | 每道题选得对不对、结果对不对；计划守没守规则 |
| 审批 | 写；不写外部的写「无」 | 写；用户确认计划算其中一种 |
| 对外输入（视图） | 作者在做法里写的输入，程序原样生成 | 程序从步骤输入汇总；按题现排的部分只能给出「可能需要」 |
| 对外返回（视图） | 作者在做法里写的输出，程序原样生成 | 程序从标为导出的产物汇总 |

**两视图怎么来，两类不一样**：专家的步骤是现排的，对外输入、对外返回只能由程序从步骤里汇总；原子方法做法定死，输入输出就是作者在做法里直接写的那几个，程序原样拿出来当视图，没有汇总这一步。

**「无」要明写。** 权限、审批没有要求时写「无」，不能空着；空着按未完成处理，不能当成「什么都允许」。

**能力声明只说第一层，但数据、外发、账号、费用要把所有层加起来给用户看**，由程序按依赖算（同日已定）。

## 九、注册与调用

- **两类都注册到工具中心，只收孵化过、冻结了版本的。** 登记项带上类型（原子方法或专家）和孵化版本。
- **原子方法直接执行。** 「直接」只是不编排、不需要用户确认计划；照样按它声明的权限核权，写操作照样逐次批准。
- **专家先编排。** 模型或上层专家调一位专家时，先在作者规则内排计划，再逐步调用。
- **在聊天里**：模型调原子方法，直接执行；调专家，进入编排、出确认页、成为一件委托，就是现在「请专家」的流程。
- **聊天里用到「专家类」的技能，也算调专家**，同样先出计划给用户确认。计划只有一两步时，确认就在聊天里完成；确认过的计划可以沿用，不必每次都确认。
- **按需找，不全塞。** 模型在聊天里找方法，按声明到工具中心或市场里检索，不把全部方法一次塞进模型的上下文。

## 十、孵化

### 10.1 谁孵化

- **平台孵化通用的基础方法**：计算、读数、查主体、提数据、格式转换、合并结果、按交付结构写成稿、通用的财务算术。带判断的（阈值、评级、「异常」怎么认定）一律来自作者（C-L1「平台不带投资逻辑」）。平台是特殊作者，但走同样的孵化流程，没有特权通道（「平台也是用户」）。
- **其它作者需要的原子方法和专家，作者自己孵化。**
- **没孵化的不能用，聊天和工作里也不能。** 不设「已登记、未审核」这种中间状态。

### 10.2 两种孵化

| | 自用孵化 | 公开孵化 |
| --- | --- | --- |
| 什么时候 | 用户接外部 MCP、装技能，或作者写给自己用的方法 | 要上架给别人用 |
| 声明怎么来 | 系统按工具描述起草，用户确认 | 作者写，平台工程化 |
| 测试 | 拿自己的数据跑一次 | 作者的测试集，按类型测（见第三节表） |
| 谁能用 | 只有自己 | 按市场许可 |
| 门槛 | 无 | 发布主体资质（C-L4），后端强制 |

自用孵化过的方法，以后要公开，再补走公开孵化，出新版本。

### 10.3 孵化时要注意的

- **外部 MCP 自报的描述不可信。** 系统起草的声明只是草稿，权限由用户确认；「这个操作是只读的」由可信的定义判定，不信对方自报。
- **写操作的测试要有安全目标。** 发邮件、改文件这类工具，测试时由用户指定一个安全目标（比如发给自己），并逐次批准；不能为了测试就向真实对象发出。
- **技能归哪类由程序判定。** 按技能声明的依赖判断它调不调别的方法，作者确认；依赖的方法也必须已孵化。

## 十一、市场

- **原子方法市场和专家市场，被使用的机制一致**：能力声明、版本钉死、许可、AI 按声明匹配、默认自用、公开按资质。收费照现有市场规则（C-L4、C-L5），本方案不另定。
- **knowmart 一套实现，两个入口**，不做两套。
- **使用者**：原子方法市场主要给两种人用：写专家的作者，从里面挑候选方法；聊天和工作里的模型，直接调。专家市场给请专家的用户。
- **专家的规则只能引用作者自己有、或从市场请来的已孵化方法。**
- **类型只说结构，不等于上架。** 凡调用了方法的都叫专家，市场上会有很多小专家；上不上架、给谁用，照旧按资质和作者的选择。
- **下架与撤回**：被引用的方法下架或撤回后，用到它的专家走「方法不可用」的规则（等待、换候选或失败），不悄悄换成别的方法；已经跑完的结果和证据保留。

## 十二、费用

- 原子方法直接执行，确定性的不开模型轮次；专家每编排一次就是一次模型规划。**所以能做成原子方法的，就不要做成专家。**
- 一件委托里所有层的费用记在同一个根预算上，由请专家的用户出；确认页上给出这次的估算。

## 十三、本稿新增、所有者还没看过的几条

下面几条是 qwen 改稿时补的，所有者说「都采用你的意见」时还没有这些，交 Luna 时请一并听它的看法：

1. 聊天、工作和编排机制不是方法，也不登记（第三节）。
2. 「什么算调用方法」的三种例外：实现载体、访问资源本身就是职责、编排搬运产物（第四节）。
3. 原子方法里的模型步骤只判断、不调用方法（6.1）；作者的代码不进平台后端（6.2）。
4. 成稿也是一步方法调用，平台孵化通用的「按交付结构写成稿」（7.1）。
5. 作者自带的数据绑在所属的方法版本上，被别人调用时不出这个方法（7.3）。
6. 聊天里用「专家类」技能也要先出计划确认，计划短时在聊天里确认（第九节）。
7. 自用孵化和公开孵化两档；写操作的测试要用安全目标（10.2、10.3）。
8. 被引用的方法下架或撤回后，用到它的专家不悄悄换方法（第十一节）。
9. 模型在聊天里按声明检索方法，不把全部方法一次塞进上下文（第九节）。

## 十四、对现有东西的影响

| 对象 | 要怎么改 |
| --- | --- |
| 工具中心（Luna 正在写登记） | 登记结构一开始就分原子方法和专家两类、带孵化版本，只收孵化过的；不要先按「方法或工具」写完再改 |
| 11-13 上线的连接和技能（#92、#93） | 「接了 MCP、装了技能就能在聊天里用」改为先走自用孵化；「专家类」技能在聊天里改为先出计划。线上那三张能力表是空的，直接切，不留兼容 |
| 平台现有的计算、读数、查主体、提数据 | 登记为平台孵化的原子方法，补上孵化记录和测试 |
| 平台要新孵化的基础方法 | 合并结果、格式转换、按交付结构写成稿 |
| knowlab | 加两档孵化（自用、公开），按类型测试；技能归类判定 |
| knowmart | 一套实现，加原子方法市场入口 |
| 方法主稿 | 「暂不设原子类型」「固定专家作为特例」「聊天里可用未孵化的原生工具」「步骤里可嵌程序块」「六要素」这几处照本方案改 |

**建议顺序**（Luna 按依赖再排）：工具中心分两类、只收已孵化 → 自用孵化（接 MCP、装技能）→ 平台基础方法登记和补孵化 → knowmart 原子方法市场入口 → 聊天里「专家类」技能先出计划。

动态专家按新定义改写，所有者说还没开始，不在本方案里排；财务各稿（原子化提炼、新财务专家孵化方案、C01–C15）的术语，等那时一起改。
