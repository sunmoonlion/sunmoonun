# 方法分类方案

> 2026-11-14，所有者与 qwen 讨论后整理。第二节是所有者已经定的，第三节是 qwen 自己的意见、还没定。决定也记在 [decisions.md](../design/decisions.md)「方法只分两类」一条。
>
> 这是方案，代码和现有文档都还没改。它建立在同日所有者定的四处方法修改之上（输入挪到步骤、递归执行、能力只声明第一层、步骤使用时由 AI 编排），那四处见 decisions.md 同日条目。

## 一、所有者原话（按先后）

1. 「是否同意将方法分为两大类：原子方法和专家，原子方法不能再被其它方法调用而专家则是调用原子方法和其它专家的方法？」（qwen 按「原子方法不能再调用其它方法」理解，所有者没有否认这一点。）
2. 「有点不对。我们讨论：原子方法和专家都会注册到工具中心，但是方法只分两类：没有所谓工具方法。但模型调用会有所不同：两者虽然都通过注册中心调用，但是原子方法直接调用，而调用专家时会经过编排」
3. 「再次强调没有所谓的固定专家和季节性预测组合了，只要调用原子方法或其它专家，都是专家。补充两点：1，原子方法也要经过孵化，基本的方法由平台这个特殊作者孵化，其它作者需要的独立方法由作者自己孵化，没有经过孵化的方法不能使用；2，原子方法和专家各有自己的市场；两类市场被使用的机制一致」
4. 对 qwen 的补充意见：「都同意你的建议」。

## 二、已经定的

### 2.1 方法只分两类

| | 原子方法 | 专家 |
| --- | --- | --- |
| 判断标准 | 不调用任何方法 | 调用了原子方法或别的专家 |
| 内部 | 做法定死 | 步骤调用方法 |
| 步骤怎么来 | 作者孵化时定好 | 使用时 AI 按题编排，用户确认 |
| 被调用时 | 直接执行 | 先编排，再逐步调用 |
| 谁孵化 | 基础的由平台孵化，其它由作者孵化 | 作者孵化 |
| 市场 | 原子方法市场 | 专家市场 |

**没有第三类。** 不再有「固定专家」「组合方法」「季节性预测组合」「工具」这些另外的叫法。

- 只要调用了方法，就是专家，不管它的步骤多少、规则松紧。现在的「财务分析与预测」也只是一位专家。
- 原来叫「季节性预测与回测」的那种固定组合，也是专家。
- 「工具」不是一类：工具中心里登记的，不是原子方法就是专家。

### 2.2 现有的东西各归哪类

| 东西 | 归类 | 说明 |
| --- | --- | --- |
| 平台的计算、读数、查主体、提数据 | 原子方法 | 平台这个特殊作者孵化 |
| 外部 MCP 工具 | 原子方法 | 孵化后才能用（见 2.5） |
| 外部 Agent（A2A） | 原子方法 | 我们看不到它里面，当一个整体 |
| 技能包里的脚本 | 原子方法 | |
| 只让模型按指令做、不调别的东西的技能 | 原子方法 | |
| 指令里要模型去调别的工具的技能 | 专家 | 它调用了别的方法 |
| 财务分析与预测 | 专家 | |

技能是一种实现载体，按它调不调别的方法归类，不是一个单独的类。

### 2.3 原子方法不调用方法，数据全部从输入进来

原子方法不能自己去调「读数」。它要的数据全部从输入进来；读数是另一个原子方法，由专家的计划安排在前面，产物绑给后面的输入。

- 例子：「算 CAGR」不自己读财报。专家的计划先排一步「读数」，读出起止两年的营收，再交给「算 CAGR」。
- 例子：「核对管理层讨论」要模型判断，仍是原子方法；它要读的那几章，由前一步读好、作为输入传进来，而不是让模型自己边读边查。
- 要边做边调用别的方法的，就是专家。

这样每条调用链最后都落到原子方法上，递归一定有底。

### 2.4 注册与调用

- **两类都注册到工具中心，只收孵化过、冻结了版本的。**
- **原子方法直接执行。** 「直接」只是不编排、不需要用户确认计划；照样按它声明的权限核权，写操作照样逐次批准。
- **专家先编排。** 模型（或上层专家）调一位专家时，先在作者规则内排计划，再逐步调用。
- **在聊天里**：模型调原子方法，直接执行；调专家，进入编排、出确认页、成为一件委托。这就是现在「请专家」的流程。
- 专家调专家：在已确认的范围内自动编排，不再让用户确认（同日四处修改已定）。

### 2.5 孵化

- **两类都要孵化，没孵化的不能用，聊天和工作里也不能。**
- **基础方法由平台孵化。** 只做通用的：计算、读数、查主体、提数据、格式转换、通用的财务算术。带判断的（阈值、评级、「异常」怎么认定）一律来自作者，不由平台孵化（C-L1「平台不带投资逻辑」）。平台是特殊作者，但走同样的孵化流程，没有特权通道（「平台也是用户」）。
- **其它作者需要的原子方法，自己孵化。**
- **自用的轻量孵化**：用户接一个外部 MCP、装一个技能，本身就是孵化的入口——系统按工具描述起草能力声明，用户确认权限，拿自己的数据跑一次测试，冻结版本，然后自己能用。
- **公开给别人用**，两类都要过发布主体资质（C-L4），由后端强制。

### 2.6 市场

- **原子方法市场和专家市场，被使用的机制一致**：能力声明、版本钉死、价格和许可、AI 按声明匹配、默认自用、公开按资质。
- knowmart 一套实现，两个入口，不做两套。
- 原子方法市场的使用者有两种：写专家规则的作者，从里面挑候选方法；聊天和工作里的模型，直接调。
- 专家的规则只能引用作者自己有、或从市场请来的已孵化方法。
- **类型只说结构，不等于上架。** 凡调用了方法的都叫专家，市场上会有很多小专家；上不上架、给谁用，照旧按资质和作者的选择。

## 三、qwen 的意见（未定）

### 3.1 程序块只放在原子方法里（建议，待定）

**问题**：步骤之间常要做些小处理，比如把两次计算的结果拼在一起、换个格式。这段代码放哪？

**建议**：专家的步骤只调用方法，不内嵌代码。

- 步骤之间的字段对接（谁的产物给谁的输入），由编排程序按声明做，不写代码。
- 需要汇总、格式转换的，用平台孵化的基础原子方法（比如「合并结果」「转成表格」）。
- 代码只出现在原子方法的实现里。

**理由**：「调用了方法就是专家、原子方法不调方法」推到底，专家里再嵌一段没孵化、没测试的代码，就和「没孵化的不能用」冲突了；而且专家的测试测的是「选得对不对」，测不到嵌在里面的代码。

**代价**：平台要多孵化几个通用的小原子方法；作者写专家时少了「顺手写两行代码」的自由。

### 3.2 作者写什么：按两类分开（建议，待定）

同日已定输入挪到步骤上、返回由程序汇总。照此，两类作者要写的不一样：

| | 原子方法 | 专家 |
| --- | --- | --- |
| 能力声明 | 只有本层 | 本层的话，加直接下层的能力引用（钉版本） |
| 所需权限 | 写 | 写 |
| 做法 | 做法和实现绑定（脚本、函数、MCP、A2A、指令） | 候选方法、必做、条件必做、先后依赖 |
| 校验 | 固定用例：算得对不对 | 每道题选得对不对、结果对不对；计划是否守规则 |
| 审批 | 写 | 写，用户确认计划算其中一种 |
| 对外输入 | 程序从步骤输入汇总 | 同左 |
| 对外返回 | 程序从标为导出的产物汇总 | 同左 |

**名称**：作者手写五项、程序汇总两项。我倾向改叫「五项作者定义加两个生成视图」，不再叫「六要素」；做出来的东西一样，区别只在叫法。「六要素」是你 11-12 定的名字，改不改你定。

### 3.3 其它意见

1. **原子方法内部可以有几步，但都是定死的。** 可以有程序、工具调用，也可以有一个范围固定的模型步骤（比如「核对管理层讨论」的判断）；不能在里面按题现排。
2. **原子方法之间不能互相调用，要复用就共用代码。** 两个原子方法要用同一段算法，共用程序库，不互相调用。
3. **原子方法可以升级成专家。** 作者以后想把一个原子方法拆开，就出一个新版本、改成专家。调用它的地方不受影响，因为对外的输入和返回是程序汇总出来的，只要不变，上层就不用改；专家的规则钉的是版本，作者升级不会自动改到别人的专家。
4. **外部 MCP 自报的描述不可信。** 自用轻量孵化时，系统起草的声明只是草稿，权限要用户确认；「这个操作是只读的」要由可信的定义判定，不信对方自报。
5. **撤回我之前提的「已登记、未审核」状态。** 你定的「没孵化的不能用」更干净，不需要这个中间状态。
6. **费用上两类不同。** 原子方法直接执行，确定性的不开模型轮次；专家每编排一次就是一次模型规划。所以能做成原子方法的，就不要做成专家。
