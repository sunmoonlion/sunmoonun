# 新财务专家改造方案 · Luna

日期：2026-11-08  
状态：讨论稿，供所有者与 Luna 持续讨论；定稿后交 Opus 审阅。  
本轮范围：整理方案，不修改专家包、不启动付费测试、不执行发布或旧契约清理。

## 一、目标和依据

保留同一位「财务分析与预测」专家，将现有按八步顺序执行的做法，改造为能根据问题选择必要分析方法、组织依赖和交付的新版专家。用户不需要在市场里区分两位“固定财务专家”和“动态财务专家”。

本次讨论明确了三个方向：

1. 财务专家产品保留；目标是改造它的做法，不是删除这个产品。
2. 按问题选择方法是所需能力，不是只把页面上的“固定/动态”名称删除。
3. 原八步混合了流程、方法、数据处理和交付要求，不能直接改名为八个独立方法。

此前决定与依据：

- [方法与专家包](../design/SDD/architecture/methods.md)：2026-11-03 撤销了“演示结束自动删除固定专家产品”的安排，保留统一执行体系方向。当前讨论进一步提出把同一位财务专家改造为按题选择做法的版本；具体改造尚未定稿。
- [动态专家实施方案](数据拓扑重构/动态专家实施方案.md)：其中“方法边界纠偏”“方法、模板组合与流程”“数据作为独立维度”已明确，八步拆分不能作为成熟方法资产直接发布。
- 所有者本轮转述的与 Opus 对话：提供了待讨论的八步分类和工程建议。本文不将其中“线上开关状态”“分叉数量”“代码已全部实现”等描述视为本轮重新核实的代码事实，实施前须检查实际候选。

本轮尚未查询线上专家主档，因此不在这里填写当前专家版本号或声明某个新版已经可用。正式改造前必须锁定作者、专家身份、已发布版本、包摘要和验收记录。

## 二、创意、方法库与专家的关系

创意可以由用户自己提出、参考方法库组合成模板、由 AI 提供初稿，三种来源可以混用。用户与 AI 加工后，由作者定型，再孵化成准专家。

方法库沉淀实践中成熟、常用、可复用的做法；它提供素材和工具，不规定每份创意都必须先拆成若干库内条目。人和 AI 可以提出新方法，但候选内容、冻结版本和经过实践验证的成熟方法必须区分。

本次以现有专家内容为改造起点，已有 20 项财务方法候选可作为参考，不能因已有列表、Schema 校验或合成测试，就整批纳入正式专家。也不预设最终必须有 8 个或 20 个方法。

需求侧仍由用户指定专家，或 AI 按市场公开能力声明合理选择专家。选专家不要求提前求解全部方法组合和数据可行性。具体计划和数据条件在委托中核实，匹配误差通过行为审批、反馈和纠偏补救；无合适专家时由用户选择通用模式或提出孵化申请。

## 三、必须分开的职责

| 对象 | 负责什么 | 例子 |
| --- | --- | --- |
| 方法 | 输入什么、适用什么条件、按什么规则得到什么结果、怎样核验 | CAGR 计算、累计转单季、会计恒等式核验、证据对照 |
| 创意中的组合 | 为实现作者的目标采用哪些做法、如何连接、参数和口径如何协调 | 季节性预测连接单季序列、同比窗口和回测 |
| 专家执行规则 | 哪些方法何时必做、何时可选、遇到缺项怎么办、哪些行为交用户决定 | 选中预测就必须完成规定回测；口径冲突先处理 |
| 平台执行机制 | 运行、授权、等待、审批、计费、返工、存储和交付的通用机制 | 数据确认卡、步骤状态、计算工具、报告文件交付 |
| 本次任务 | 本题实际目标、选定做法、输入绑定、审批与执行记录 | 指定公司和期间的一次分析计划 |

数据贯穿上述各项：方法声明所需输入，组合形成依赖，执行规则决定取得和核验关口，本次任务绑定实际授权数据。

**“是否必做”与“是否为方法”是不同问题。** 四式核验可以是方法，同时被作者规则要求在特定条件下必做；不能因为必做，就把方法改称流程或规则。

“原子化”按独立职责和复用边界划分，不等于把每一个公式都变成一次模型调用。多个互不依赖的计算可以批量执行，仍逐项保留输入、公式、结果和证据。

## 四、原八步如何重新整理

以下是 Luna 的分类建议，尚不是作者已接受的方法清单或选择政策。

| 原步骤 | 建议拆分 | 改造时应保留的边界 |
| --- | --- | --- |
| 定范围 | 平台的确认与超范围处理机制，加专家自己的范围解释规则 | 主体、期间、交付目标需明确；合并/母公司等领域口径不能全部写进平台通用步骤 |
| 数据摸底 | 实际输入就绪检查，加财务数据期间、版本与口径核对 | 提出数据需求不等于已有可用事实；确认和下载都不能替代实际检查 |
| 勾稽 | 原四式核验方法，加作者规定的触发条件和核验范围 | 保留真实公式、1 元阈值、未核验与不平的区别；不能用替代公式冒充原式通过 |
| 取数 | 累计转单季等业务转换方法；与外部取数、原件加工分别表达 | 时点数不差分；已是单季的数据不重复差分；使用一致的来源和重述口径 |
| 算指标与分析 | 按实际职责整理增长、盈利、人均创收等计算与解释做法 | 不能把固定指标大全设为每题必算，也不能把计算和文字解释的验收混为一谈 |
| 对照管理层讨论 | 可复用的证据对照做法，加作者规定的选择条件 | 保留结论原文；仅在指定章节核对；未提及、只支持部分或口径不一致时按作者规则处理 |
| 预测 | 作者规定的季节性同比预测与回测组合 | 选择预测后落实全部必要依赖；不能擅自改成 DCF、三表预测或另一算法 |
| 成稿 | 平台的文件保存交付机制，加作者规定的报告组织规则 | 可复用的报告编排规则也可成为方法；不能一概固化到平台，或引用未执行分析的成果 |

具体方法的粒度应以输入、输出、异常和核验能否独立说明为依据，再决定是否拆分。例如 CAGR 与人均创收可以分别使用；季节性预测则可能作为组合对外使用，内部计算不必让用户逐个装配。

特别需要纠正的三点：

1. 第 0 步列需求与数据摸底不能简单合并。前者回答“要什么”，后者回答“实际拿到了什么、能否使用”。产品上可以连续展示，但执行记录和判据要分清。
2. 不能默认“凡用报表数，就对全部已授权报告做全部四式核验”。应根据本题结果和依赖确定范围，明确哪些科目、期间、报告版本需要核验；是否改变原强制范围，须作者接受。
3. 统一执行引擎不等于改造无需迁移和验收。选择条件、数据依赖、输出和声明发生变化，仍需新版本和针对性验证；历史任务仍须能解释。

## 补充讨论：将既有候选整理为原子方法，供作者选择

2026-11-08，所有者提出：以方法原子化为基础，将现有库里的若干方案拆成真正的原子方法，供作者挑选。Luna 赞成该整理方向；以下为拆分建议，尚未批准成正式方法清单。

### 本轮实际核对范围

本机 knowlab-backend 的 `app/tests/financial_author_method_fixtures.py` 包含 M01–M20 共 20 项财务候选定义，文件明确标记为合成测试夹具。`docs/financial-methods-notes.md` 记录部分口径和历史确认，但不能据此把全部候选宣布为已经过生产实践验证。本轮未查询线上方法主档，不能把夹具数量当成线上可选方法数量。

`app/app/domain/knowbots/atomic_methods.py` 已有独立方法定义，表达目的、适用条件、输入、规则、输出和验收，并明确冻结版本不证明生产成熟度。这是可复用的工程基础，不代表现有内容已完成语义原子化。

### 什么叫真正的原子方法

原子方法是具有独立用途、输入、做法和核验边界的最小可复用业务单元。它应能脱离原专家的步骤编号，接收满足条件的数据或上游成果，被另一份创意使用。

拆分判断：某个子做法能否被单独要求、能否与其它内容独立变化、是否有独立输入和输出、脱离原方案后是否仍有完整意义。满足这些条件才拆；只有除法、求和等没有独立业务意义的运算保留为工具。多个必要动作共同构成一种完整分析逻辑时，可以作为组合模板保留。

### 已发现的混合内容与拆分样例

| 现有候选 | 待拆分的职责 | 应保留的组织形式 |
| --- | --- | --- |
| M03 扣非还原，正文同时包含单季还原 | 非经常性损益调整；累计流量转单季 | 两项方法分别可选，不能只想还原季度也必须做扣非 |
| M12 CAGR 与趋势外推 | 指定期间的 CAGR；采用明确规则的趋势拟合 | 历史增长分析可作为模板；不能因选 CAGR 自动预测未来 |
| M16 质押、减持与关联交易 | 质押情况分析；减持披露分析；关联交易分析 | 原整体内容可保留为治理分析模板，各子方法仍需口径和证据审查 |
| 原四式勾稽 | 各项恒等式核验与跨期余额衔接可以独立表达 | 作者可以在模板或专家规则里要求四项组合必做；拆分不自动放宽要求 |
| 预测与回测 | 明确算法的预测、窗口准备、对应历史回测等职责 | 允许组合使用，选择预测时由作者规则强制其必要依赖 |

M12 还有实际内容不一致：正文写 3 年/5 年，当前输出字段和计算判据却固定为 3 年。原子化时须同步修正输入、期间参数、输出和判据，不能只拆标题。现有候选 M02 的四层核验内容也不能直接等同现有财务专家的原四式，须逐条比对后再复用。

### 作者怎样使用

作者可以挑单项方法，也可以选由这些方法组成的模板，再与 AI 一起修改、增删、补充原创内容，形成自己的创意。平台展示各方法的用途、适用边界、数据要求、输出、来源与验证依据；不要让作者靠函数名、输入槽技术编号或复杂连线图猜用途。

原子方法是素材层，模板是方便使用的组合层，作者定型的专家是交付层。保留模板能避免把复杂度全推给作者；选模板并不意味着每次任务必须执行其中全部方法，具体选择规则仍由作者加工定型。

方法内部的输入合格要求与专家决定的必做政策要分开。例如可单独选择某项核验，不意味着已有专家可以绕过作者要求的四式检查；修改该要求仍需作者接受。

### 建议的整理次序

1. 盘点实际方法主档与 M01–M20 候选，区分已发布方法、原创方法、成熟参考方法和合成样例，记录来源及现有引用。
2. 建立“原方案 → 原子方法 → 组合模板 → 专家使用规则”的对应表，允许重复候选合并为同一语义方法，也允许同名不同口径保留不同定义，不按数量验收。
3. 首批用 CAGR、累计转单季和原四式核验验证边界；每项补齐数据口径、异常处理、独立输出、验收与正反例。作者确认后才生成正式新版本。
4. 让同一方法在两种不同创意里使用，验证它不依赖原来的专家、固定步骤编号或旧用户数据；原子粒度不增加逐指标模型调用。
5. 将能独立选用的做法和可加工模板交给作者，再整理其余候选；旧定义和引用历史保留，不就地改写。

本阶段是内容整理与最小接线，不要求先做完全部 20 项才能改造财务专家。优先完成当前专家与代表性问题真正需要的方法，剩余候选按相同标准逐批整理。

## 五、数据如何进入本次计划

建议沿既有数据链保存三类记录，不建立第二份数据主档：

| 记录 | 至少说明 |
| --- | --- |
| 逻辑需求 | 主体、指标含义、期间或时点、所需窗口、用途、证据形态与必要程度 |
| 供应与授权 | 用户确认的修订、已授权可用资料、需查询/加工/采集的缺口、实际作业与失败原因 |
| 执行绑定 | 具体事实或原文版本、单位、报表范围、期间性质、来源、证据位置、对应方法输入 |

沿用所有者此前要求的顺序：先确认本次需求与授权，再使用满足要求的知识库数据；缺项优先尝试适用且获准的 Wind 能力，再按适用范围走巨潮等已接入渠道。实际渠道能力和接线状态在实施前核对，不能因配置了来源就声称已经完成取数。

来源优先级不能替代输入要求：需要 PDF 页码和管理层原文时，仅有 Wind 数值不够；已有 PDF 也不代表所需结构化事实可读。已有原件而缺读法时，应区分内部加工与重新外部采集。

发生缺项、口径冲突或原文不足时，定位受影响的方法和成果。按已接受的规则补查、补取、等待、缩小范围或停止；新的授权或费用需求沿现有确认机制处理。不得把“已确认”“处理中”“已拿到”和“已核验”混成同一个状态。

回测要记录预测基准日、报告披露或可获得时间、重述政策，防止把后来披露的信息当成历史时点已经知道的数据。数据单位、比较期、合并范围、期末人数与平均人数也须明确。

## 六、按题选择的预期效果

以下用于讨论和后续设计验收，不代表目前代码已达到。

| 问题 | 应形成的分析范围 | 不应默认附带 |
| --- | --- | --- |
| 某公司指定年度的营业收入走势 | 题定期间和口径、必要数据核验、营收及同比等题定分析、结果交付 | 季度拆分、预测、估值、全部盈利指标 |
| 近三年人均创收 | 营收与人数口径核对、计算、变化说明及局限 | 全套季度数据、未来季度预测 |
| 历史营收/利润/毛利率、CAGR，加两季度预测和四季回测 | 历史分析、预测所需窗口和核验、必要单季还原、作者规定预测与回测、报告 | 未授权的新预测算法或无关估值 |
| 问题超出声明或指定的方法不在本专家能力内 | 说明不适用或需澄清，交用户选择后续路径 | 因“财务相关”就自动接单，或悄悄换问题 |

管理层讨论是否对上述每题必做，当前仍待作者明确。这里没有用示例替作者取消现有要求。

## 七、实施建议与交付顺序

先讨论内容边界和作者规则，再补工程缺口。沿现有计划、执行、工具、验收和交付体系实现，不另建一套运行器。

| 阶段 | 实际工作 | 可核对交付物 |
| --- | --- | --- |
| 1 盘点基线 | 从拟改造的真实专家包提取声明、八步正文、判据、数据要求和历史缺陷；核对实际代码候选 | 专家身份/版本/摘要，原要求到新职责的逐项映射；每项标保留、拆分、拟改、待定 |
| 2 整理作者内容 | 明确方法职责、适用条件、依赖、缺项处理、选择规则和交付要求 | 一份整体作者核对稿，包含内容差异和代表性题目计划；不预设八个方法 |
| 3 核对工程承载 | 检查既有结构能否表达上述内容；不能表达的提出最小契约改动 | 按仓列缺口、契约提供方与消费者、验证方式；不凭历史开关推断当前状态 |
| 4 实现和离线验证 | 完成必要契约、规划、数据绑定、验收和界面改造；先用可控样本验证 | 正反例、计划记录、证据与计算收据，错误与费用记录；不把合成测试称为业务通过 |
| 5 孵化与实际测试 | 作者接受定型内容后，为同一专家生成新版；按单独授权开展真实测试 | 原三题及必要跨公司样本的逐项结果、报告、耗时和费用，明确失败和未执行项 |
| 6 发布与收敛 | 满足正式发布要求后采用新版；确认依赖和历史读取范围后清理旧执行分支 | 发布依据、版本切换和历史追溯验证；无未经验证的旧格式批量删除 |

预计核对的仓及职责：

- **knowlab**：创意加工、素材来源、作者定型、方法与执行规则表达、编译、作者测试和版本发布。不得要求所有原创内容先进入成熟方法库。
- **knowmart**：同一专家新版的能力声明、版本交付与选择入口；声明不能超出实际做法。
- **knowbench**：按声明选择专家；受理后按专家授权形成计划，验证依赖和规则，绑定数据、执行、审批、验收和报告交付。执行选方法与市场选专家不能混为一个无限推理任务。
- **knowbase / knowfeed**：核对实际事实、读法和证据能否满足输入，以及缺口供应、加工、渠道选择与失败回执；按真实缺口决定是否改代码。
- **sunmoonun**：待方案定稿后同步架构决定、实施账和发布交接；本讨论稿不直接替代已经生效的发布规则。

是否保留旧契约读取、清理哪些迁移开关、是否需要数据迁移，待 Opus 对实际引用和历史记录核查后列出。不能由“现在只有一位财务专家”推导出平台其他流程和历史记录都不再依赖旧契约。

## 八、验证标准建议

1. **选择正确**：同一专家处理不同问题时，计划随题目变化；必要依赖不被删掉，无关分析不自动加入。应同时测应选与不应选的反例。
2. **方法正确**：实际公式、口径和窗口符合作者定型内容；四式核验不替代，未核验不算通过，预测不绕过原回测要求。
3. **数据正确**：实际绑定有权使用、版本明确、期间与单位一致；原文与计算事实满足各自要求，缺项真实反映，回测无未声明的未来信息。
4. **证据正确**：计算收据能对应输入与结果；引文支持完整结论，口径不一致不判支持。“不支持”不等于原计算错误。格式失败、平台失败、方法验收失败分别报告。
5. **交付完整**：报告覆盖本题要求和所有有效分析成果，未执行或不具备条件的部分明确说明；文件真实可读，不能仅显示“完成”。
6. **耗时和成本可接受**：记录规划、读数、计算、验收和交付耗时及调用数；批量确定性计算不拆成逐指标模型轮次。具体时间与预算目标另定，不自动重新加回此前被取消的时限。
7. **版本和权限可靠**：方法来源和修改可追溯；专家升级不改写旧任务包、授权、费用与历史结论。行为审批不能给现有专家凭空增加能力。

完整分析预测题保留为质量基准，但不能用它一次通过代替其它场景。无需逐条复制旧流程中的无关步骤来追求形式等价；需要保留的是作者要求和结果质量，而非旧的执行浪费。
