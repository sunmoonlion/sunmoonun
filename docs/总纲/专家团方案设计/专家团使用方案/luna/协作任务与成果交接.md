## 一、让用户交付目标，而非手工调度每个成员

建议流程：用户提交目标 → 团长提出分工及依赖 → 按授权规则确认成员与费用 → 创建成员任务 → 各成员沿单专家运行机制执行 → 复核交接成果 → 团长整合 → 整体验收。

团长负责组织不代表有权代替成员制造研究结论。必要成员失败、结果未核验或数据缺失时，要明确影响的交付项；多位成员各说“完成”不能自动使整团成功。

## 二、任务看板与人工交互

沿用所有者已提出的任务看板方向：主任务表示整体交付，成员任务显示负责人、依赖、状态、等谁、等什么及费用。数据确认、补充问题和动作审批可以在卡上处理，但保留各自的授权语义和决定记录。

| 用户看到的情况 | 运行记录必须说明 |
| --- | --- |
| 等数据 | 哪个成员、哪些输入、哪项真实供给作业或确认待处理 |
| 等作者 | 哪个作者决定什么，用户问题向其暴露了哪些部分 |
| 等用户 | 请求的动作、范围、价格或内容版本，拒绝后影响什么 |
| 部分完成 | 已可用成果、缺口、剩余必要工作，不能显示整团成功 |
| 取消 | 停止哪些未开始／在跑任务，供给与已发生外部动作分别怎样处理 |

同一项目当前的单专家执行约束如何扩成多成员，仍是待决项。必须先明确目录写入、资源占用和合并责任，再开放并发；不能仅把多个现有任务同时启动。

## 三、成员之间交接成果，不隐含共享原始数据

建议每份交接至少包含：成员及版本、任务与尝试、产物版本、输入口径、证据引用、计算收据、业务状态、已知局限、可见范围和消费者。接收方核对所需字段及权限后再使用。

产物不能直接冒充已入库的标准化事实。是否允许另一成员读取、是否需要新的使用权、是否需要加工和验证，应走既有数据与成果机制；knowbench 不另建事实主档，不因“同团”绕过 knowbase 的授权边界。

两种重要情形：一位成员报告勾稽不平，是有效发现，后续按作者规则决定能否预测；一位成员证据只支持半条结论，汇总不能把它升级为完整支持。交接状态要保留到最终报告。

## 四、恢复、分歧、预算与停止

- 中断后从明确任务和成果版本恢复，不把同名文件当成相同证据；重试保留尝试记录。
- 上游修订使下游结果失效时，标明受影响任务，决定重新执行范围，不能静默保留旧结论。
- 分歧先对齐主体、期间、版本和方法口径；仍无法解决时保留不同结论及依据，不默认多数投票正确。
- 建议整团总额与成员额度分开记录，含规划、重试和复核；达到上限按既有规则停止或请求决定，不能换成员绕开预算。
- 用户取消、成员失败、团长完成和长期目标终止是不同事件，应逐一明确对后续工作的影响。

## 五、最小验收与待定项

至少验证一次正常交付、一次必要成员失败、一次权限不足、一次上游修订、一次取消和一次恢复；同时对照单专家的质量、耗时、模型调用与成功交付成本。

待定：固定或动态分工、一次项目内的并发规则、作者挑数据的交互、成员产出使用权、全团与成员费用、分歧由谁裁决、何时用户确认。正式决定后再写契约和迁移，不先加没有当前用途的占位字段。
