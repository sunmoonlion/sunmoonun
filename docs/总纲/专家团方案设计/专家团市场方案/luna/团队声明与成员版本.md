## 一、团队声明要说明协作结果

不能把成员能力简单求并集后当作整团承诺。团队声明应描述共同交付、必要成员职责、输入条件、限制和不能处理的情况；确有整体测试的，写明实际覆盖范围。

选择团队仍依据公开声明合理匹配，不要求市场先执行整套规划。knowmart 提供真实的目录、版本、价格和许可信息；内部角色关系可以按发布政策展示，但不能自动公开成员私人方法及数据。

## 二、团版本、成员版本与任务绑定

| 对象 | 建议冻结或记录的内容 |
| --- | --- |
| 团队发布版本 | 协作规则、能力声明、必要角色、交接要求、许可与计价依据 |
| 固定成员团队 | 每位成员的确切身份、版本、摘要和组合授权 |
| 允许动态选人的团队 | 已批准的选择约束与替换规则；本次实际成员及版本在受理时另行钉住 |
| 本次整团任务 | 团版本、实际成员、各自授权、报价确认、输入与成果引用 |

固定或动态成员模式尚未定型，表中列出两种需要分别处理的情形，不要求首版同时支持。成员升级不能静默改写团队发布快照和已经运行的任务；更换成员后需要重新检查接口、许可、费用及整体交付承诺。

## 三、许可和费用不能从单专家推断

请得到某位专家，不必然意味着有权把它放进一个对外分发的团队。团队作者、成员作者、购买者之间的组合使用权、再分发权与数据访问分别核实；组合授权不授予查看成员方法原文的权利。

费用至少区分团队使用价格、成员授权价格与实际运行消耗。是否打包、重复购入怎样处理、失败怎样结算，需明确商业规则；本稿不设新价格或退款承诺。启动前向用户展示本次会产生什么费用，运行期预算沿 knowbench 管理。

成员下架、授权到期或不可用时，要区分停止新请入、历史可读和在跑任务处置。不能静默替换另一位成员继续收费，也不能因为停止销售而删除已有报告与证据。

## 四、职责和验收

knowlab 管团队作者内容与测试；knowmart 管可发布资产、声明、许可和版本交付；knowbench 管本次成员计划、运行、预算与成果。三者通过版本化契约接续，不互读数据库或复制彼此的主档。

验收重点：团声明不超过实际能力；成员版本与清单一致；缺许可不能请入；替换需重新核价与能力；成员升级不影响历史；团队报价和运行账能对上；故障不能冒充市场无供给。
