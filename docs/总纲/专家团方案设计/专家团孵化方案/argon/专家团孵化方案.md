## 一、核心定位：什么时候做「单个动态专家」，什么时候孵化「专家团」

在单个专家已经支持「共用流程模板 + 多领域方法按题动态组合」（`knowbot-manifest/v3`）的前提下，`knowlab` 为什么要引入「专家团（Expert Team）」？

借鉴对腾讯 WorkBuddy（`134393` 专家与专家团、`137017` Agent Teams）、OpenAI dots、Grok Bot 与 Meta Muse Spark 的第一手官方资料剖析，多智能体并行会带来显著的 Token 倍增与协调开销。因此，我们在架构上划定**单个动态专家**与**专家团**的清晰边界：

| 维度 | 单个动态专家（`knowbot-manifest/v3`） | 专家团（`knowbot-team-manifest/v1`） |
| :--- | :--- | :--- |
| **适用问题特征** | 单一专业领域、单一方法论视角下的按需步骤裁剪（如：对一家公司做财报勾稽、单季还原、核心指标或季节性预测） | **跨学科/多视角协同、多标的并行横比、或需要独立立场交叉质询**的复杂任务（如：财务基本面专家 + 行业竞争格局专家 + 法律合规审视专家联合尽调；或看多/看空双专家红蓝质询） |
| **作者与产权归属** | 单一作者拥有全部领域方法与绑定数据 | **支持跨作者组合**：团作者编写「团长（Lead）」拆解与统稿逻辑，成员槽位可引用团作者自己的专家，也可按公开能力声明引用 `knowmart` 上其他作者授权可组团的专家 |
| **上下文与沙箱隔离** | 单个会话上下文按步骤顺序推进 | **团长与各成员专家拥有各自独立的上下文窗口与运行子尝试（Sub-Attempt）**，成员内部几十轮读表与计算过程不塞入团长上下文，只向团长交回经确定性验收的结构化 `ArtifactRef` |
| **数据准备模式** | 单次委托统一解析、用户一次确认 | 支持**成员级独立数据解析**，且支持特定成员开启**「成员作者按题选数据 + 离线规则兜底」**（所有者 10-28 设想的第二档场景） |

## 二、专家团的架构模型：团长（Lead）+ 成员槽位（Member Slots）+ 协作拓扑

### 2.1 专家团的三层结构图

专家团绝不是让几个聊天机器人自由群聊，而是**「受确定性契约约束的团长（Team Lead）+ 钉死版本与能力接口的成员专家（Member Experts）+ 引擎强制推进的任务看板 DAG」**：

```mermaid
flowchart TB
  subgraph TEAM_DRAFT[knowlab 专家团工作稿 TeamWorkdraftBody]
    SCOPE[团级能力声明卡 PublicTeamCapability[]<br/>团的目标与结果 / 适用范围 / 协作拓扑概要 / 交付与排除项]
    
    subgraph LEAD[团长规格 TeamLeadSpec（严格委派与统稿模式）]
      DECOMP[1. 拆解与派工规则 DecompositionRules<br/>如何将用户母问题拆为成员子任务卡、何时激活可选成员槽]
      CROSS[2. 交叉核验与冲突裁决规则 CrossCheckRules<br/>成员结论矛盾或口径不一致时如何触发质询或披露]
      SYNTH[3. 收口统稿方法 SynthesisMethod<br/>汇总各成员已验收 ArtifactRef，写出全团总报告与局限披露]
    end

    subgraph SLOTS[成员槽位定义 MemberSlotSpec[]]
      S1[成员槽 1：如 fin_fundamental<br/>绑定专家：财务分析与预测 @v5 (sha256:...)<br/>调用能力卡：cap_indicators, cap_forecast<br/>数据模式：用户确认自动解析]
      S2[成员槽 2：如 industry_research<br/>绑定专家：产业链景气度专家 @v2 (sha256:...)<br/>调用能力卡：cap_supply_chain<br/>数据模式：成员作者按题选数据（带超时兜底）]
      S3[成员槽 3：如 forensic_auditor（可选槽）<br/>绑定专家：财报排雷审视专家 @v3 (sha256:...)<br/>激活条件 applies_when：存在勾稽异常或应收/存货激增]
    end
  end

  SCOPE --> LEAD
  LEAD -->|派发子任务 Brief + 上游 ArtifactRef| S1 & S2 & S3
  S1 & S2 & S3 -->|交回经各自确定性验收的 MemberOutputArtifact| SYNTH
```

### 2.2 团长（Team Lead）的职责边界：严格委派模式（Strict Delegate Mode）

针对多智能体系统中最常见的「团长自己越俎代庖干了成员的活，或者团长凭空编造数字篡改成员结论」问题，我们在孵化编译器中对团长施加**严格委派模式（Strict Delegate Mode）**：

1. **工具权限剥离**：
   - 团长在「拆解与派工阶段（Stage 0）」和「调度与交叉核验阶段（Stage M）」**只拥有主体识别工具（`find_subject`）与看板编排/派工原语**，不挂载底层财务事实读取（`query_facts`）或任意公式捏造工具，从机制上迫使团长必须将专业计算委派给对应的成员专家。
2. **收口统稿阶段（Synthesis Stage）的溯源硬约束**：
   - 团长在最后一步「收口统稿（`team_writeup`）」中引用的任何数值、指标或原文引文，**必须 100% 溯源至某个成员专家已通过验收的交回物（`MemberOutputArtifact`）**（通过扩展 `covers` 与 `sourced_from_member` 确定性验收模板核验），团长严禁自行发明未经成员专家验算的新数字。
3. **冲突必须显式裁决或并列披露**：
   - 当两个成员专家对同一事项给出不同结论或不同口径数值时，团长的统稿规则必须按团作者定义的 `CrossCheckRules` 处理（触发补充核对子任务，或在最终报告中并列展示双方的证据链与分歧原因），严禁静默抹平分歧。

### 2.3 成员槽位（`MemberSlotSpec`）的绑定与四种成团拓扑

团作者在 `knowlab` 中定义每个成员槽位时，填写如下结构化契约：

| 字段 | 类型与约束 | 作用说明 |
| :--- | :--- | :--- |
| `slot_id` / `role_title` | `Identifier` / `str` | 槽位唯一标识（如 `fin_analyst`）与看板显示角色名（如「财务基本面分析专家」） |
| `expert_ref` | `PinnedExpertRef` | 钉死成员专家的 `(knowbot_id, version, digest)`。**第一期强制采用「编译期钉死确切版本」**，不在运行期让团长去全市场盲搜未知的第三方专家，确保全团行为可测试、费用可预测 |
| `bound_capabilities` | `tuple[Identifier, ...]` | 声明本槽位仅调用该成员专家公开能力卡（`PublicCapability.id`）中的哪几项，作为子任务派工范围的边界 |
| `selection` | `MemberSelection` | `required: bool`（是否每次必上）、`applies_when: str`（可选成员的激活条件）、`max_parallel_instances: int`（同一成员针对多标的并行实例上限，如对比 3 家同业公司时设为 `3`） |
| `upstream_slots` | `tuple[Identifier, ...]` | 声明该成员依赖哪些上游成员槽位的交回物作为输入前提（无依赖的成员槽位可由看板并行派发） |
| `data_policy` | `Literal["user_auto", "author_curated"]` | 数据准备模式：`user_auto` 为标准「模型提议 + 用户一次确认」；`author_curated` 为「请该成员专家的作者按题选数据 + 离线预设规则兜底」 |

基于上述槽位模型，`knowlab` 原生支持孵化**四种标准专家团协作范式**：

1. **多维并行深潜型（Parallel Specialist Deep-Dive）**：多个不同领域的成员槽位 `upstream_slots` 均为空，团长拆解问题后同时派发，最后由团长汇总统稿。
2. **工序接力流水线型（Sequential Relay Pipeline）**：成员 B 的 `upstream_slots` 指向成员 A（例如成员 A 负责「多源财务数据清洗与四式勾稽还原」，成员 B 接收成员 A 已验收的标准序列做「行业可比估值与敏感性测算」）。
3. **红蓝对决与交叉质询型（Red-Blue Cross-Examination）**：槽位 A（正向逻辑挖掘专家）与槽位 B（风险排雷与质疑专家）并行独立分析同一批披露材料，再将双方产出互传做一轮定性/定量回应，最后由团长按证据强度收口。
4. **多标的同专家横比型（Multi-Entity Homogeneous Fan-Out）**：针对「对比白酒行业三家龙头公司的单季增速与现金流质量」类问题，团长将同一个单公司财务专家槽位实例化为 3 个并行子任务（`max_parallel_instances=3`，每家公司一个独立子沙箱上下文），跑完后由团长执行横向对比统稿。

## 三、作者身份、跨作者组装权利与逐格出处门禁（`C-L1`）

### 3.1 「谁是专家团的作者？」——双层作者责任切分

当用户甲（团作者）在 `knowlab` 中组建一个专家团，其中成员槽位 1 是甲自己孵化的专家，成员槽位 2 引用了用户乙在 `knowmart` 上公开且允许组团的专家时，权利与合规责任严格按**「团层归团作者、成员层归成员作者」**切分：

| 责任维度 | 团作者（组装并孵化专家团的人） | 成员专家作者（被引用单个专家的原作者） |
| :--- | :--- | :--- |
| **逻辑与出处归属（`C-L1`）** | 对**团长拆解规则、成员激活条件、成员间交接契约、冲突裁决规则、最终统稿规则**负责；这些格子全部进入团清单的 `team_rule_sources`（`user_text` / `user_confirmed`） | 对**该成员专家内部的原子方法、算式、单步验收规则**负责；保持原成员专家清单的 `rule_sources` 与 `digest` 原封不动 |
| **私有资产可见性（防扒取）** | 团作者引用乙的公开专家时，**只能看到乙在 `knowmart` 公开的 8 栏能力声明卡（`PublicCapability`）与输入/输出契约**，绝看不到乙专家内部的私有方法正文（`procedure`）与自带绑定数据内容 | 乙的私有方法与自带绑定数据仍封装在乙专家的不可变包内，不会因被甲组进专家团而向甲泄露 |
| **绑定数据许可责任** | 若团长统稿层绑定了团作者自带的模板或基准数据，由团作者承担许可责任 | 成员专家绑定的数据仍按该成员专家的 `FrozenBinding`（`expert:<member_id>@<ver>`）在运行时校验受益人授权 |

### 3.2 专家团的三种孵化入口

与单个专家一致，团作者在 `knowlab` 中也可通过三种起点创建专家团工作稿（`TeamWorkdraftBody`）：

1. **手工编排成团**：团作者自己从「我的专家」与「`knowmart` 已授权可组团专家目录」中挑选成员槽位，手写团长拆解规则、交接连线与统稿要求。
2. **从团模板起步**：选用平台沉淀的通用协作拓扑模板（如「多维并行尽调模板」「红蓝交叉审视模板」「多公司横比模板」），填入具体成员专家并修改团长规则。
3. **AI 辅助成团起草**：团作者输入成团想法（如「我想做一个结合财报勾稽和行业研报对照的半导体公司分析团」），AI 从 `knowmart` 目录检索候选成员专家的公开能力卡，生成成员槽位搭配与团长调度规则草稿；**团作者必须逐格点击确认（生成 `user_confirmed` 出处记录）后方可编译出准专家团版本**。

## 四、专家团测试方案：单成员桩回放与全团端到端联调

测试一个包含 $3 \sim 5$ 位成员专家的专家团，如果每次微调团长的统稿文案都要把所有成员专家从头重跑一遍，不仅耗时极长，而且模型与数据费用高昂。因此，`knowlab` 为专家团设计**「两阶段分级测试机制」**（契约 `knowbot-team-test-run/v1`）：

### 4.1 阶段一：成员固定桩回放测试（Member-Stub Replay Mode）

- **适用场景**：团作者正在调试团长的「问题拆解规则」「成员槽位激活条件」或「最终收口统稿与冲突披露规则」，而各成员专家本身均已是测试通过的冻结版本。
- **做法**：在首轮跑通某道测试题后，系统将各成员槽位已通过验收的交回物（`MemberOutputArtifact`）连同输入摘要缓存为测试集内的**确定性成员桩（Member Stub）**。当团作者仅修改团长规则重测同一道题且拆解出的成员子任务输入未变时，可选择「复用已验成员产出桩」，只重跑团长的拆解轮与统稿轮，成本降低 70% 以上。
- **强制全量门禁**：桩回放仅用于孵化迭代期的快速调试；**正式提交「要这一版」进入交付审核前，必须至少完整跑通一次「全团真实端到端测试（Full E2E Run）」**，禁止凭桩回放直接上架。

### 4.2 阶段二：全团真实端到端测试与四项确定性验收

在全团端到端测试中，每道测试题（`TeamRunCase`）钉住团级测试数据集（`TeamCaseData`，支持按成员槽位分配或全团共享已授权数据版本），并在作者本人的 `sunmoon-link` 环境上依次核验四道关卡：

1. **拆解与选槽验收（Decomposition Check）**：核验团长生成的看板子任务 DAG 是否覆盖了测试题要求的必选成员槽位、是否正确跳过了不该激活的可选成员、是否遵守了 `max_parallel_instances` 上限。
2. **成员内部验收（Member Acceptance Check）**：每个被激活的成员专家子任务必须 100% 通过其自身清单定义的确定性验收规则（`sourced`、`computed`、`identity`、`quoted`、`covers`）。
3. **跨成员交接与统稿溯源验收（Cross-Member Coverage & Provenance Check）**：核验团长终稿（`team_writeup`）是否完整纳入了所有已完成成员的核心结论（`covers`），且终稿中的每一个关键指标都能追溯到具体成员的交回物地址（`member:<slot_id>:<instance_id>.<path>`）。
4. **分歧与缺口诚实披露验收（Conflict & Partial-Failure Honesty Check）**：在专门构造的「成员结论冲突题」或「某可选成员缺数据降级题」中，核验团长是否按规则如实披露了成员分歧与未执行范围，而非强行编造统一结论。

## 五、待所有者拍板确认的事项

1. **第一期成员专家的绑定方式（静态钉死 vs 运行期候选池）**：
   - 本方案建议第一期专家团孵化统一采用**「编译期静态钉死成员版本（每个槽位唯一对应一个 `knowbot_id@version`）」**（但支持设为可选槽 `required=False` 由团长按题决定激不激活），暂不开放在运行期由团长从市场动态挑选未绑定的陌生专家，以保证测试可复现、责任边界清晰、价格确定。请确认第一期是否按「槽位钉死版本 + 按题条件激活」实施？
2. **专家团嵌套（团里再套团）的限制**：
   - 为防止任务看板层级过深、Token 预算失控及分成链路复杂化，建议明确规定：**专家团的成员槽位只能绑定「单个专家（`knowbot-manifest/v2` 或 `v3`）」，禁止专家团嵌套另一个专家团（即最大深度固定为「团长 $\rightarrow$ 单专家成员」两层）**。请确认是否定为硬约束？
