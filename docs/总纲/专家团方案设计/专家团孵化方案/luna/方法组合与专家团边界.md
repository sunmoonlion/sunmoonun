## 一、方法组合不是专家团

| 对象 | 组合什么 | 责任和交付 |
| --- | --- | --- |
| 原子方法 | 独立业务做法与明确输入输出 | 方法产生可验证结果 |
| 单专家内的方法组合 | 同一作者定型的若干做法与规则 | 同一专家承担本题交付 |
| 专家团 | 多位真实专家的能力与协作关系 | 团长组织，各成员按自己的冻结能力负责，整体还需验收 |

例如累计转单季、季节性预测、回测可以属于同一位财务专家的内部组合；不能为了展示三个人物就把它们包装成三位专家。只有存在独立能力、独立版本或责任、分别维护和复用的真实需求，才讨论多专家方案。

## 二、团队作者要写的内容

建议在既有创意—工作稿—版本流程中表达团队，不新增另一套作者来源规则。

| 内容 | 应回答的问题 |
| --- | --- |
| 团的目标与边界 | 哪类问题值得由多个专家共同做，哪些仍由单专家处理 |
| 团长职责 | 谁拆解、谁汇总、谁向用户提出问题，能否作专业结论 |
| 成员角色 | 每个角色要求何种公开能力，哪些必须参加、哪些按题选择 |
| 选择与替换规则 | 固定成员还是运行时按声明挑选；替换何时要用户确认 |
| 交接规格 | 传什么成果、口径、来源、局限和状态，不能传什么 |
| 复核与分歧 | 成员结论冲突时如何保留证据并决定下一步 |
| 交付与结束 | 必要成果、整团验收、部分完成与取消的含义 |
| 使用权和数据 | 团作者有没有成员的组合使用权；数据主人分别是谁 |

团队作者不能凭组织权替成员作者修改方法，也不能替数据主人扩大授权。公开声明用于选择，成员方法正文和绑定资料不因为入团就向全团公开。

## 三、从单专家方案复用什么

方法精确引用、作者接受、输入语义、成果验收和测试版本继续复用。团队新增的是协作关系及整体交付，不是另一套计算、事实库和执行引擎。

建议先选一项确需不同专业能力的任务，用两位实际专家和明确团长职责验证。对照同预算单专家，检查是否减少遗漏、提高复核质量；不能只以成员消息数或并行数量证明团队价值。

团队测试还需覆盖：缺少一位必要成员；成员版本升级造成接口不相容；一方正确报告缺项；双方结论冲突；某成员无数据权限；团长生成了成员未给出的结论。单个成员通过测试，不代表整团通过。

## 四、需要所有者明确的事项

1. 团作者与成员作者的关系、组合使用权和责任归属。
2. 首版固定成员还是按问题动态选择，允许哪些替换。
3. 团长使用哪个人的模型、预算和会话，用户确认分工的具体范围。
4. 作者按问题挑数据时能看到哪些信息、不在线如何处理。
5. 首批要交付的真实协作场景与验收，不用方法列表代替团队需求。

这些未定事项不阻塞单个财务专家的既有改造，也不意味着本轮获准启动专家团开发。
