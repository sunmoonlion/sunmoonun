# 多模型并行开发 · 登录、踩坑与纪律

> 2026-08-21 重写 ｜ 前一版把「模型」与「分支」耦合在一起，已废弃。
> 两者是正交的：worktree 按模型命名只是**对比实验的归类约定**，不是必然挂钩。
> 配套工具见本目录 README.md（mb：多仓批量 checkout / worktree）。

## 各身份的登录方式

| 身份 | 工具 | 配置家 | 登录 |
| --- | --- | --- | --- |
| kimi（或 cc-switch 当日模型） | codex CLI | `~/.codex`（cc-switch 管理） | `codex login`（ChatGPT 账号；模型凭据在 cc-switch 代理内部） |
| 官方 luna | codex CLI | `~/.codex-official` | `CODEX_HOME=~/.codex-official codex login` |
| Claude opus | Claude Code 扩展 / CLI | `~/.claude`（独立体系） | 首次启动引导登录 Anthropic 账号 |
| qwen3.8 | Qoder IDE | IDE 内部配置 | IDE 内登录 |

登录一次长期有效：每个配置家一条独立的轮换链，互不传染。

### 一、主目录各仓的模型 login

主目录（`~/master/k8s` 等，默认停 master）是单模型日常开发位。在那里用哪个模型，
取决于启动哪条命令：

```bash
cd ~/master/k8s && codex                                  # kimi / cc-switch 当日模型
cd ~/master/k8s && CODEX_HOME=~/.codex-official codex     # 官方 luna
```

登录态存在各身份的**配置家**里（`~/.codex`、`~/.codex-official`、`~/.claude`），
全局生效，与从哪个目录启动无关。

### 二、worktree 各模型的 login

我们的 worktree 按模型命名（`~/worktrees/kimi/` 等）——这是对比实验的归类
约定，**不是因为模型与分支有必然联系**。

因此 worktree 里的 login **不需要任何额外动作**：登录态跟配置家走、不跟目录走。
`cd ~/worktrees/luna/k8s` 后用 `CODEX_HOME=~/.codex-official codex`，用的还是
同一个家的同一条链。唯一与目录相关的坑见「坑 3」。

## 踩过的坑（病根各一句）

**坑 1：共享 token 链。** 复制 auth.json = 两家共用一条轮换链，一边刷新另一边
作废，服务端报 `refresh token was already used`，表现是反复弹登录。
修法：每个配置家独立 `codex login`，绝不复制。

**坑 2：VSCode 扩展重启弹登录。** 扩展自己存一份 token 副本；启动时 app-server
的刷新使副本变旧；旧副本递出触发服务端反盗用吊销整条链（还会连坐同家的
CLI）。修法：扩展保持禁用；要用就接受「重启后点一次登录」。
扩展登录成功后新链写回文件，CLI 再启动可自愈——顺序：先扩展登录，后开 CLI。

**坑 3：project-config 污染，以及 luna 下为什么要放 config。**

机制：codex 启动时会做「项目配置发现」——从当前目录向上找 `.codex/config.toml`。
**碰到 `.git`（仓根）就停**；没有 `.git` 挡路就一路向上，直到在家目录捡到
`~/.codex/config.toml`。而那份文件里写着 `model = "kimi-k3"`——它会被当成
「项目配置」叠加进来，覆盖掉 `CODEX_HOME` 里的官方模型，官方后端收到第三方
模型名直接报 400（实测报错：`The 'kimi-k3' model is not supported when using
Codex with a ChatGPT account`）。

配置层级（为什么官方「不用自己的 config.toml」——其实用了，只是被压）：
`-c` 命令行 > 项目层（上述发现机制）> 用户层（CODEX_HOME/config.toml）。
官方家的 config.toml 是用户层、确实生效（默认 luna、读 auth）；但项目层发现的
`model = "kimi-k3"` 优先级更高，把用户层的 luna 覆盖了。

为什么官方能在 `~/worktrees/luna/k8s`（仓内）正常：发现止于仓根，摸不到家目录。
为什么官方在 `~/worktrees/luna`（容器目录，**不是仓**）就会中招：没有 `.git`
结界，发现一路走到 `~/.codex`。

为什么要在 `~/worktrees/luna/.codex/config.toml` 放 `model = "gpt-5.6-luna"`：
我们要让官方 CLI 能在 luna 容器目录启动（覆盖五仓）。向上发现是**就近命中**——
在容器根放一份写对模型的项目配置，查找走到这里就截胡了，轮不到家目录那份。
这就是它的全部作用：一个放在正确位置的「就近拦截器」。
（这个目录不是 git 仓，该文件不会被误提交。）

显式兜底（任意目录、临时用）：`codex -c 'model="gpt-5.6-luna"'`（-c 优先级最高）。

**坑 4：cc-switch 浮动身份。** 裸 `codex` = cc-switch 当前激活模型，随切换漂；
kimi 无法钉死（协议转换在 cc-switch 代理里，与其当前态绑定）。对策：会话开头
问一句「你是什么模型」验明正身；官方身份不走 cc-switch，永久钉死。

**坑 5：跨机共享。** 别的机器上若有复制过去的 auth.json，同样构成同链竞用
（2026-08-21 实测 ECS 上为 4 月的空 token 旧文件，已排除；新机器注意）。

## 纪律

1. **落对工位**：写代码前 cd 到对应工位/目录；并行时期没有任何编辑器开着
   主目录写代码。
2. **验明正身**：新会话先问「你是什么模型」，以状态栏/配置为准（自述不可审计）。
3. **谁改谁提交**：提交前 `git status` / `git diff` 核对改动都是自己写的，
   不替别人打包提交。
4. **扩展保持禁用**；偶尔要用，先登录再干活。
5. **主目录/工位互斥**：被 worktree 占用的分支主目录切不过去，
   要拿回先 `mb worktree remove <名字>`。

## 排障速查

| 症状 | 先看 | 解法 |
| --- | --- | --- |
| 反复要求登录 | 是否有两处共用一条链（auth.json 被复制过） | 各家独立 `codex login` |
| 扩展每次重启要登录 | 扩展机制使然（坑 2） | 点一次；或禁用扩展 |
| `model is not supported when using Codex with a ChatGPT account` | 启动目录是否在非仓目录 | 到对应工位的仓内启动；检查钉模型文件 |
| 身份不对（答错模型名） | cc-switch 当前激活的是谁 | 切换 cc-switch；或换用钉死的 home |
| 切完模型突然要登录 | `stat -c %y ~/.codex/auth.json` | cc-switch 换了 auth 备份，重登一次 |

## 验证清单（改动后跑一遍）

```bash
# 链独立：两个指纹应不同
python3 -c "
import json, hashlib
for n, p in [('kimi', '/home/zymun/.codex/auth.json'),
             ('official', '/home/zymun/.codex-official/auth.json')]:
    rt = (json.load(open(p)).get('tokens') or {}).get('refresh_token') or ''
    print(n, hashlib.sha256(rt.encode()).hexdigest()[:12])
"

# 双通（各回一句话即活）
cd /tmp && codex exec --skip-git-repo-check "只回复：kimi好" </dev/null
cd ~/worktrees/luna && CODEX_HOME=~/.codex-official codex exec \
  --skip-git-repo-check "只回复：官ok" </dev/null
```
