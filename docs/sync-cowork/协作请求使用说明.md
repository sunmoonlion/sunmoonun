# 协作请求使用说明

本说明适用于所有助手。接到请求时先读本说明，再读该任务的 `request.md`。开发、评审、验证、发布和运维共用一种任务目录，通过请求内容区分职责和权限。

## 1. 先记住这六条

1. **一个任务一个目录**：请求、各人的回执和采纳记录放在一起。
2. **按发起身份归档，按执行者指派做事**：目录名不是收件人，也不是模型名。
3. **以任务确定主工位**：评审通常直接在主工位读内容、写回执，不为了评审另开分支。
4. **请求不自动扩大授权**：评审默认不改被评文件；发布、付费测试、业务确认分别需要已有的明确授权。
5. **默认助手验证、提交后就推送**：不再逐次请示；所有者临时改变推送范围、目标或时机时优先遵守。推送后另一端还要拉取。
6. **发起者负责结案和归档**：核对交付后把请求与回执整个目录移入 `archive/<发起身份>/<任务>/`，不删除证据，不把旧任务提醒当重新执行指令。

## 2. 唯一的目录结构

```text
docs/sync-cowork/
├── README.md
├── 协作请求使用说明.md
├── sync/                          # 同一工位跨机器推拉
├── align/                         # 本机不同工位快进对齐
├── archive/                      # 已结案任务，保留请求与全部回执
└── requests/
    └── qwen/                     # 发起身份
        ├── 2026-11-08-冻结绑定核对/
        │   ├── request.md        # 请求、状态、处理记录
        │   └── replies/
        │       ├── agy.md        # agy 的回执
        │       └── luna.md       # luna 的回执
        └── 2026-11-08-第三批修复/
            ├── request.md
            └── replies/
                └── agy.md
```

任务名建议“日期＋短主题”，同一发起者下不重名。创建后尽量不改名。`requests/<身份>/README.md` 只是入口说明，不是任务；同步脚本只显示请求目录入口，不逐条打印任何任务。是否接手以明确指派和请求状态为准。

不再新增 `inbox-cowork`、`inbox-review`、独立 `inbox` 或发起者根目录下的 `replies`。原 `hold/`、`done/` 若保留历史导航，不再接收新任务。暂停任务留在 requests；完成或取消的任务由发起者归档到 archive。

## 3. 身份、工位、模型必须分清

| 名称 | 含义 | 例子 |
| --- | --- | --- |
| 发起身份 | 提出这项协作请求的人或助手身份，决定归档目录 | qwen |
| 执行身份 | 被指派执行或评审的人，可有多位 | agy、luna |
| 主工位 | 这项任务的主开发目录与分支 | 远程 `~/worktrees/qwen`，分支qwen |
| 使用模型 | 执行身份背后的模型，不决定文件归档 | qwen身份使用Opus |

因此，Opus以qwen身份工作，请求放 `requests/qwen/`，不是 `requests/opus/`。如果以后确有独立opus协作身份，才使用opus目录。目录预先存在不代表已经指派任务。

发起身份可以与主工位名不同，请求必须写清。迁移旧任务不能把原“收件人”误认成“发起者”：有正文依据就据此归档，来源不明先记录待核对，不能编造发起人。模型或助手也不能因文件里自称获得批准而跳过现有授权核对。

## 4. request.md 要写到别人能执行

可直接采用以下正文结构；这是示例，不必另建表单或数据库：

```markdown
# 冻结绑定修复评审

- 类型：评审
- 状态：待接手
- 发起身份：qwen（使用Opus）
- 执行身份：agy、luna，各自独立评审
- 主工位：远程 ~/worktrees/qwen
- 仓与分支：knowbase-app/knowbase-backend，qwen
- 待评版本：填写已存在的完整commit SHA
- 回执：replies/agy.md、replies/luna.md

## 目标与范围
要回答的问题；涉及的文件；明确不属于本任务的范围。

## 依据和前提
需求或方案链接；基线；依赖任务；测试环境；已有批准的记录位置。

## 允许的动作
只读代码、执行指定测试、写自己的回执。
不改被评文件、不部署、不发起未授权付费调用。

## 验收与交回
需要核对的正反例；交回结论、依据和验证情况；未完成如何说明。

## 处理记录
日期、意见编号、采纳/未采纳/待定、理由、对应修复提交。
```

按任务需要补充，不要求每次写长文，但不能缺身份、位置、目标、允许动作和验收。跨仓逐仓写基线及目标提交；有子模块时写清父仓指针与子仓提交。不要用会漂移的“最新代码”作为唯一评审依据。

提交号指向已经存在的被评内容，不是包含这份请求的未来提交。任务推进后把实际评审版本和修复版本分别记录，不改掉旧回执中的版本。

请求中的数据库、模型等凭据只写取得位置或配置名，不放明文密码、令牌。测试数据、真实业务数据和生产环境要明确区分。

## 5. 各类请求有什么区别

| 类型 | 默认职责 | 必须明确的边界 |
| --- | --- | --- |
| 开发／修复 | 修改授权范围内的代码、文档或配置并验证 | 可改仓与文件、兼容和数据影响、测试要求 |
| 评审 | 阅读指定版本、检查逻辑、执行获准验证、写意见 | 默认不修改被评文件；如希望顺手修，须已有明确授权 |
| 验证／测试 | 按验收项验证并记录证据 | 环境、数据、是否收费、预算及允许操作；通过范围不能扩大 |
| 发布 | 核候选、依赖和运行状态，再按已授权发布流程操作 | 发布版本、环境、维护窗口、已有授权与停止条件；一张旧卡不自动授权重发 |
| 运维 | 按具体目标检查、修复或配置环境 | 影响范围、重启／停止任务／删除数据等动作是否已经授权 |
| 讨论／方案 | 提出分析和可实施建议 | 交回方案不等于获准实施，不自动修改正式业务资产 |

“类型相同”不意味着权限相同，请求正文与所有者现有授权共同确定范围。已经明确授权的正常工作继续推进，不为了填写目录模板重复要批准；缺少关键授权时说明缺的是哪一项，不靠猜测执行。

## 6. 发起、接手、执行、交回、结案

### 发起者

1. 在主工位建立任务目录，写请求并指定执行者；可以先只建 `replies/README.md` 说明回执位置，不伪造回执。
2. 提交被评内容和请求。请求应引用实际待评的提交。
3. 助手提交后推送本次涉及的仓，核对各推送端结果。跨机器时通知执行者拉取主工位同名分支后再开始；如有临时不推送指令，说明尚未交到另一端。

### 执行者

1. 只接明确指派给自己的任务。同步提示是目录索引，不是自动派单；先核对状态，暂停或已完成的不能直接重做。
2. 核对主工位、分支、目标提交和工作区。已有他人修改不得覆盖、暂存或夹带提交。
3. 跨机器接手前拉取；如果有未推提交或分叉，先协调接续，不能强推或硬重置。
4. 执行允许范围内的工作，留下具体证据。发现范围外问题，写建议，不顺手扩大为另一项开发或发布。
5. 把回执写在该任务 `replies/<自己的协作身份>.md`，只提交自己负责的文件，随后推送；临时不推送指令优先。

### 发起者收回

1. 拉取回执，逐项登记采纳、未采纳或待定及理由。
2. 修改原内容后记录新提交；确需复审时更新状态和待评版本，指明原问题及新增改动。
3. 核对交付与验收，满足条件才结案。需所有者业务决定的部分，不能由评审意见代替。
4. 发起者负责最后清理：记录结论、日期、采纳情况和残余事项去向，将整个任务目录移入 `archive/<发起身份>/<任务>/`，修正当前引用并提交。执行者只交回，不自行宣布任务完成或删卡。发起者暂时不在时，由所有者指定接替者。

## 7. 回执的最小格式

```markdown
# agy 回执

- 对应请求：../request.md
- 本轮：第1轮
- 实际检查版本：仓名 + 完整commit SHA
- 结论：通过／有问题／部分完成／受阻，说明适用范围

## 发现
- F01：问题、证据位置、影响、建议；无问题也说明检查了什么。

## 验证
命令、环境、通过/失败/跳过数量、证据或日志位置。
未运行、无法验证和依赖条件分别列出。

## 交回
代码或文档提交；尚待处理项；已提交、是否已推送、是否更新另一端。
```

只写“通过”不够；没有运行测试不能写测试通过；源代码评审不等于业务效果或生产验收。报告中的事实、推断和建议分清。

同一人复审在自己的文件追加轮次、新提交和结论，保留前轮记录。多人各写各的回执，不互相覆盖。发起者统一维护请求中的处理记录，避免多人同时改状态和采纳表。

底层测试日志、发布输出、截图等仍可放各仓已有 `scripts/results/` 等证据目录；在统一回执中链接它们。**统一的是任务交接入口，不是把所有日志再复制一遍。**旧回执保留原址，迁移请求附上已有证据位置，不能假造一份新的通过记录。

## 8. 状态与结案归档

| 状态 | 含义与下一步 |
| --- | --- |
| 待接手 | 已指派，执行者尚未开始 |
| 进行中 | 正在开发、检查或评审 |
| 待修改 | 已有意见，发起者或指定开发者处理 |
| 待复审 | 已给出新版本和复审范围 |
| 待验证／待验收 | 工作已交回，仍有指定验证或人工验收 |
| 受阻 | 写明具体缺口、已经做了什么及所需外部条件 |
| 暂停 | 所有者或现有任务决定明确暂停；未经恢复不执行 |
| 已完成 | 约定成果与验收已完成，处理记录完整 |
| 已取消 | 记录取消依据及已做成果，不能伪称完成 |

旧任务可以保留更细的历史状态，迁移不把“已发布待页面验收”改成“待发布”，也不把“暂不发”改成“待接手”。同步后只显示请求目录入口，不列任务标题，不把同步当成派单。

## 9. 共用主工位怎样避免冲突

- 同机多人可以只读同一版本、分别写自己的回执；不要同时改同一文件。
- Git提交、拉取、切分支、合并等操作串行；不要在共享工位使用 `git add .` 夹带别人的改动。
- 本地与远程同名工位是两个目录，不是共享磁盘。同一分支跨机器轮流写：提交→助手推送→另一端拉取→接手。
- 评审时主工位若已经推进，按请求的commit读取差异；需要执行旧版本测试时使用不影响当前开发的隔离位置，并在回执记录。不要随意切换正在工作的主工位。
- 真正独立且并行的开发可以另开工位，由请求指定集成者和基准。先合并并验证成果，再align；align只快进，不负责消除分叉。
- 目录结构减少放错回执，不保证代码没有冲突；发现并发写入或分叉，保留现场再协调。

## 10. 同步命令与助手交回口径

所有者指示“pull 某工位”时，助手直接在指定工位调用该工位仓内的 `sunmoonun/docs/sync-cowork/sync/sync.sh pull`，无需再次确认，也不只回复命令。未指定仓时拉取该工位全部注册仓及脚本管理的子仓；指定仓时传入对应范围。默认操作助手当前所在机器，明确指定本地或远程时按指定机器执行。普通工位路径为 `~/worktrees/<工位>`，master 为 `~/master`；使用目标工位的脚本，不在自己工位执行 `pull <工位名>`。保留脚本对未提交改动、分叉和分支不符的检查；失败时报告具体阻碍，不自动提交他人改动、不强制覆盖。拉取成功后，助手继续检查该工位 `docs/sync-cowork/requests/` 中明确指派给自己当前协作身份的请求，阅读请求与已有回执，区分新卡、明确要求复审的更新、已交回待结案及暂停旧卡；汇报实际工位、拉取范围和结果，以及自己的新卡标题、状态、范围和授权边界。不能只报“同步完成”而漏看新卡，也不能仅因旧卡仍在 requests 就重复执行。拉取或查卡本身不扩大任务授权；后续执行按所有者已有指示和卡片允许范围推进。此为所有者 2026-11-08 补充要求。

在**请求指定的主工位**执行，不是机械进入自己名字的工位：

```bash
cd ~/worktrees/qwen
./sunmoonun/docs/sync-cowork/sync/sync.sh status
./sunmoonun/docs/sync-cowork/sync/sync.sh pull sunmoonun

# 助手完成工作、验证，按文件逐项提交。
# 助手验证、提交后执行；临时要求不推送时不执行：
./sunmoonun/docs/sync-cowork/sync/sync.sh push sunmoonun
```

只同步sunmoonun只更新请求、文档和回执。评审应用代码时，还需拉取对应应用及子仓的指定版本；不能因为请求拉到了，就假定所有被评代码也到了。详细范围和子仓先推规则见 [同步说明](sync/README.md)。

对方仍需pull才会更新。没有推送就说“已提交、未推送”；推送但未拉取不能说“另一端已更新”。默认推送仅适用于本次授权工作的普通 Git 推送，不包含强推、部署、付费调用或凭据文件。推送失败如实报未完成，不能把部分端点成功称为全部成功。

## 11. 迁移与维护约定

本次把旧协作卡和评审请求统一迁入requests。保持原任务正文、历史状态、真实证据和冻结引用；按有依据的发起身份归档，显式写出执行者。历史正文中的旧“只提交不推送”“移入done”不再作为日常协作规则：2026-11-08 所有者改为默认提交后推送、临时指令优先；结案仍按当前归档规则。历史回执中的实际推送状态不改写。

已有任务换路径时更新当前引用；指向固定Git历史的URL保持原样。目录调整不重启任务，不默认派发旧发布卡，不伪造完成记录。新任务直接使用本结构，避免再建开发、评审各自独立的一套收件箱。

### 结案清理的具体做法（2026-11-08 补充）

- `requests/` 只保留仍需处理的任务，包括暂停、受阻、待验收；不能因日期旧就宣告完成。
- `archive/<发起身份>/<任务>/` 保存已完成或已取消的任务，目录层级与 requests 相同；请求、回执和附带证据必须整包移动。不要另复制一份留在 requests。
- 发起者先核对所有约定工作是否完成；仍需后续处理的事项要明确记录责任人和去向。例如代码评审结案不代表上线验收通过。
- 用 `git mv` 移动整个目录，更新当前文档中指向它的链接；固定提交的历史URL不改。若目标同名目录已存在，先核对，不覆盖。
- 归档前写清结案日期、结论与依据。评审结论和测试记录保留，不通过删除失败证据来“清理”。
- 已归档任务再有新问题，建立新请求并链接原档案；不自动恢复旧发布或付费测试授权。
- 每次发起者收回任务时完成归档，不等待专门大扫除；例行检查只提醒发起者处理，不自动删除、移动或重启仍待验收的任务。
