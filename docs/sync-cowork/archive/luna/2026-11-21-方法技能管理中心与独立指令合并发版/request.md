## 发布顺序

1. 核对发布分支包含以上候选或其经核对的等价集成，记录父子仓、部署与镜像 digest。备份当前配置，确认在办任务、待审批操作、已有 Skill 安装和 PVC 的保留方式。继续使用既定脚本和写入开关。
2. 按现有 prepare 流程生成两个 `knowbench-function-publish-identity` 阶段及各自的 SOPS 密文。KnowBase、KnowBench 各有独立 client 和 subject，接收端仅接受这两家的 `knowbench:function-publish` 身份。两份凭据均只给一次性发布进程。检查内部 HTTPS 路径 `/api/internal/v1/method-skill-center/functions` 以及对应 KnowBase 执行路由可达。
3. 在维护窗口暂停新的业务派发，完成迁移并先使新版 KnowBench API 可接收登记。用对应的 KnowBase、KnowBench 镜像各运行 `python -m app.bootstrap.publish_functions`。发布作业使用本服务的 CA、OIDC 配置和专属 Secret 引用；`DOWNSTREAM_BASE_URL` 填 KnowBench 内网 HTTPS 源站，`DOWNSTREAM_ALLOWED_PATH_PREFIXES` 限定为上述函数登记前缀，`DOWNSTREAM_CLIENT_ID`、`DOWNSTREAM_CLIENT_SECRET`、`DOWNSTREAM_SCOPE` 取本发布身份。回执仅记录身份名及摘要。
4. 两个发布者分别应返回 **10 项 v1**，KnowBench 为七项业务、两项 Skill 读取和一项会话操作结果查询。重复发布后逐项比对同一提供方、名称、版本和摘要。身份不符、同版冲突、缺登记或摘要不符时停止开放。发布许可与用户资料、外发、脚本收费或公开冻结许可分别核对。
5. 升级 KnowBench runner、KnowBase API、KnowLab、相关 Web、供给器及沙箱。先用测试身份验收，再恢复流量。重建沙箱保留用户卷和配对，新卷及保留配置的旧卷均应移除已退役的知识服务段。对切换前已开启的会话重新准备轮次；遇到在途调用结果未知时先对账。

## 现场验收与停止条件

| 入口 | 验证操作和须交回的证据 |
| --- | --- |
| 管理页与提供者 | 核两家登记明细、同名不同提供方隔离、普通用户看自己的安装与正式方法。登记与市场使用资格分别核。 |
| 工作台、KnowBase、KnowFeed | 合成任务查供应商和同名主体、提出一条资料需求，确认前保持待办。读已授权资料，试撤权后新读被拒；做带输入引用的计算，重放确认只一份底稿；查本账号专家目录。记录 task、调用 ID、提供端回执。 |
| 已安装 Skill 与会话结果 | 选本人测试 Skill，列文件、按页读正文，再查本会话中已完成操作的结果。换账号、撤销安装、跨会话读取应拒绝。用隔离验收环境中的测试登记验证撤登记后已准备轮次也拒绝；共享集群保留在用登记。 |
| 递归专家和市场 | 用本人的测试产物跑 `read_task_output`，核批准的字段、产物版本、调用路径和撤权。作者选源、获取者以自己的账号执行，并核撤权阻断新调用。合成独立指令验草稿试跑、私有冻结、固定和递归引用。需要模型或脚本的项目沿原有授权与计费条件执行。 |
| Link 与沙箱 | 用已配对测试设备核本机白名单和批准、保留工作目录、会话交付。列旧卷和新卷的 MCP 配置名，确认只出现本轮可见服务。 |

迁移、身份、登记、核权或回执异常时，保持业务暂停，按同一窗口恢复上一组相容的 API、runner、前端和供给器镜像及路由；保留中心表、来源版本、调用、批准和计量账本。不得以恢复旧知识直连、自动重发未知操作或清库作为修复。回执附实际构建号、镜像、环境、迁移前后版本、登记数、脱敏运行编号、各项实测和受阻条件。Luna 核对后结案。
