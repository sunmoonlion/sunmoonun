## 即时计划与孵化共用编排

发布 KnowBench API、Web 及驱动委托的工作进程，并核对 KnowLab 后端版本。新即时规划轮使用 FIND_EXPERT 第 7 版，旧第 6 版委托按原格式恢复。沿用 sig-am 原有规划灰度范围。

### 草图自动纠正与 P5 增量验收

- 孵化作者页和工作台「拟临时计划」各从新题发起一轮，在验收记录中区分首次直接成功、自动纠正后成功、业务需澄清和仍未通过。核对传给模型的 JSON Schema 有实际字段、类型和必填项。出现坏步骤标识、未知目录别名、分派声明与步骤不符等问题时，系统应在原轮反馈错误，最多再请求一次模型。真实模型首答正确时记为首次通过。稳定重现错答使用下方本地测试；不要通过篡改共享任务或正式版本制造错答。
- 在原轮回执核对模型尝试数、错误字段、耗时和费用。正常澄清直接交回业务问题。两次均错时无可采用的草图、无业务工具调用。工作台的自动纠正沿用该轮 2 元预算和 150 秒模型时间窗口；时间已用完时页面应显示本轮超时。
- 对照题 J 继续分别以 A、B 给出本题执行输入。在独立测试夹具中，将第二个候选改为一项声明需要两次模型调用的指令方法。验证 KnowLab 确认草稿和 KnowBench 计划预览均拒绝该版本。跨两个分派步骤时，核对共用同一标识只能选对应组合；独立标识可选择两个重分支。同时记录实际业务派发次数，草图核验应为零。
- 可复跑用例在 KnowLab 后端的 `app/tests/test_author_selection.py`，以及 KnowBench 后端的 `app/tests/test_knowbot_incubations_db.py`、`app/tests/test_temporary_plan_db.py`、`app/tests/test_temporary_plan_graph.py`。数据库测试使用隔离的 PostgreSQL 测试库。将共享环境真实结果、首轮可编译率、自动纠正回执与原有现场步骤一并写入本卡回执。

### 现场物料和入口

1. 使用 sig-am 登录 KnowBench，选择该账号已配置 Kimi 的电脑和私有验收项目。从项目「请专家」提交问题。对已有合格专家完整覆盖的题，代表普通匹配命中；要验本卡，请使用没有整位专家完整承接、但有已授权步骤方法的测试题。在原委托的未匹配结果下点「拟临时计划」。记录题目、委托编号和规划轮号。
2. 从[作者选型物料](#selection)取得四行样表、两轮样本及原盲测题。以项目内有权使用的确切版本建一张输入输出对照表。孵化作者能试跑某个方法、工作台账号在技能管理中心能看见某个来源，都不能代替买方已有正式版本使用资格。先核对 sig-am 在消费目录中的实际方法、版本、摘要及接口。缺少需要的方法时记录该题缺哪一项，保持旧 Q01–Q04 的撤回状态。
3. 对照题 J 为“先提取标准明细，再按原单上的 A/B 标识分别交给费用岗或税务岗”。用两条内容相同、原单标识分别为 A 和 B 的合成明细。目录需要一个明细提取方法和两个接收相同明细及必填字符串标识的分派候选。规划时不给模型模板答案。验收人另存预期路由：A 到费用岗，B 到税务岗。如果用户输入之外还需决定阈值，另用盲测题 I 验澄清。如果无法提供可执行目录，可验缺口，A/B 交付项单列待验。
4. 对单一已获权的回执或汇总工具验最小草图。提交改写前后的业务描述各一次；如须调整连线，补充要求后点重拟。草图采用与正式委托执行是两次操作。采用后刷新核对最终文字、版本及范围，按页面准备真实输入、账户、资料及预算，预览、确认执行，逐次完成实际需要的审批。四行题以样表 A 的 45.00、样表 B 的 17.00 核对结果。
5. J 题在两个入口各拟一份草图，记录模型首次建议和宿主核验结果。检查共同前序、明细的输入来源、两条分派方法的实际版本及各自授权。工作台选“需要”后逐行写入本题所有标识。漏填 B、多填 C 或对有分派的草图选“不需要”时均不能采用。重拟后旧草图应失效。对 A、B 分别走正式预览和执行，两个委托应各调用共同前序和本条分支。核对没有因采用草图产生业务调用，遇未知标识应停在选路校验。
6. 用无隔离可用的环境或不具隔离资格的候选验题 D 的能力缺口；有条件时另验两份独立结果交第三人复核。独立复核已含内部汇合。对未定阈值题应先澄清。另检查第 6 版已有委托能重开，以及新计划保存后用于另一题还会重新核对资格、确认步骤及准备本次执行资料。



### 本地证据

本次 P1 增量在隔离 PostgreSQL 和受控模型回复下通过。KnowLab 后端全量 1,140 项通过、5 项跳过；KnowBench 增量及相邻路径 60 项通过；工作台 Web 525 项通过、2 项跳过，生产构建通过。两端后端类型检查和生成契约一致性检查通过。首次答错后纠正成功、再次失败、预算内同轮以及即时轮超时分别留有回归。测试用两个分支各含 51 次工具调用的子树，验证共用标识时每次实际调用 52 次可通过，独立标识可产生 102 次调用的组合会被阻止。新增真实模型调用为零。

KnowLab 全量后端 1,138 项通过、5 项跳过。KnowBench PostgreSQL 及契约专项 40 项通过，工作台前端 525 项通过、2 项跳过，生产构建通过。J 题在两个独立后端进程以同一组冻结接口、同一份模拟 AI 答复分别编译；步骤、连线、版本、权限、审批和 A/B 选路相同。工作台 HTTP 链路验证缺确认不能采用、二次重拟令旧草图失效、保存复用、正式预览及逐次审批后实际调用测试工具。组件验证人工补写的分派标识集合与草图必须一致，改步骤需重新确认。两端静态类型检查、改动文件 Ruff 检查和契约生成核对通过。KnowBench 全仓 Ruff 仍有原有的 `test_connection_oauth_db.py` 导入排序提示。本轮未调用真实 Kimi；线上选法和真实交付按上面步骤验收。
