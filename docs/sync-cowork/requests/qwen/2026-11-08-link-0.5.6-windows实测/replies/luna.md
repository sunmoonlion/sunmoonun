## 4. 账187：失败以后再探测

两种模式都先创建WindowsFiles，但不给它启动exec-server。第一次getMetadata失败；随后启动官方exec-server，**复用同一WindowsFiles实例**再次调用成功，没有重建实例来绕开缓存。

|模式|首次错误|首次耗时ms|服务启动后同实例成功耗时ms|结果|
|---|---|---:|---:|---|
|elevated|executor connection failed|7.283|1310.587|通过，初次失败且后续恢复|
|unelevated|executor connection failed|4.889|676.087|通过，初次失败且后续恢复|

这验证了5c41d1f修复的失败Promise不会永久缓存。只覆盖“执行服务未就绪→就绪”这个要求的故障场景，不等于任意网络/权限错误都自动恢复。

## 5. 判断与建议

实测表明，当前生产使用的elevated模式里，元数据、4KB读写单次中位约1.06–1.08秒；50次元数据整批约54秒。普通模式对应约0.55–0.59秒。对于大量小文件调用，这部分耗时足以明显拖慢任务。

源代码显示每次WindowsFiles.call新起沙箱辅助进程；本轮观察与启动/隔离成本占主导的推断相符，但没有把创建进程、ACL、IPC和文件系统各部分单独剖析，不能宣称精确归因比例。

建议Opus据此评估受限批量文件操作或常驻辅助进程方案，需单独审查权限隔离、配置变化、取消、进程回收和故障重连。**是否改回常驻由所有者决定，本任务没有改代码。**
