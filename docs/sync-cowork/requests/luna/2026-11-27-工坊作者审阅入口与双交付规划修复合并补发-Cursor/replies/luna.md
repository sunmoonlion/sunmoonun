## 已填写承诺的专家能否采用这份编排

线上测试稿 revision 2 有两项承诺，尚无 procedure。隔离 PostgreSQL 中，通过工坊正式的草稿 HTTP 接口创建、保存、重读并确认相同的草稿。这里由测试作者明确给定图，单独检查工具组合和根专家契约。

- 使用现场 Q01、Q03 的 v1 冻结端口，两个 `check` 的结构匹配，但端口的业务含义都是空对象。草稿要求 `core.check.receipt`，故根专家契约拒绝采用。直接运行工具得出正确数值无法代替这一检查。
- 对照使用此前在隔离工坊中按五要素构建的两份 v2 候选，仍使用同一份脚本，各自的 `check` 明确声明 `core.check.receipt`。作者在隔离草稿中按子方法的真实要求填入父方法的权限和审批范围，确认待核实项后，保存、重读、生成正式定义、编译及展开为两个叶子均通过。没有向线上登记这些版本，也没有发起线上授权或冻结。
- 原语的选择只认规划轮次里被接受的 `action` 和 `operator`。手工图中两步均无前序依赖；工具调用次序和步骤在画布中的排列不能作为模型选择 `sequence` 的证据。工坊手动点击“添加编排步骤”默认把前一步填为依赖，是另一个操作路径。
