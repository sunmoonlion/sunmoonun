1. 从现场最新晋级线建立发布，包含已上线的 #117 和其后的 runner 核权配置。在该线上合入以上应用源码、子仓指针、KnowLab 提供方契约和 KnowBench 消费方锁。沿用现场 Kimi 路由、请专家名单、普通专家执行器 KnowMart 关系、已启用脚本和报价。
2. 按现有流程构建两端 Web 及后端，覆盖实际接收孵化、生成规划和驱动模型任务的 API、worker 与 runner。先停止旧 runner 领取新规划，待现有调用结算后切换消费者，再开放新入口。新建规划任务的原始请求带 `htn/v1`，旧任务仍按原契约继续。数据库沿用现场迁移版本。
3. 核对双方运行镜像、契约哈希、登录入口和 worker/runner 就绪。回执写入本卡 `replies/cursor.md`，列晋级指针、标签、两端实际源码与镜像。如需回退，先暂停新规划、排空或取消本版生成的在途任务，再按现有发布规程回退。
4. Luna 用 sig-am 的 Kimi 验收两条真实服务入口。KnowLab 从原行核验的能力声明新开一轮，审定六步和五个核验目标，再用留存的独立断言试跑。KnowBench 用新问题拟即时计划，审阅后执行并核对交付、版本、审批和实耗。补验资料缺失、只改一个目标和补入工具后续编。按 A、B 分两轮查候选，再提交含两者的分派；选中一个旧方法已撤权的子目标，替换后核对保留路线的版本与权限。另撤掉保留路线的资格时应要求重新确认。保留博物馆、茶厂、代取资料和待定版本题，现场另抽新题，限整题 150 秒，分别核对首次返回率和可行稿编译率。结果写入本卡 `replies/luna.md` 后归档。
5. Luna 在工作台首页「专家」模式选项目并填写一个新问题，点击一次「请专家」后应直接打开带 `formalMatch` 的项目委托。刷新应恢复同一问题和委托编号。另从项目请专家页直接提交一次，核对两个入口均只有一项匹配操作。以获准拟计划的账号验证未命中后可拟临时计划、去 KnowLab 或结束。点名市场版本、重开旧 `match` 链接时核对原版本及原有范围确认，检查匹配期间业务执行次数为零。对未命中的旧回执，从结果中的「孵化一个专家」进入 KnowLab 创意表。
