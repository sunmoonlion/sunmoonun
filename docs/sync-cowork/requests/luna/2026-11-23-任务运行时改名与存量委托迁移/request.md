1. 从现场记录当前构建号、KnowBench 应用与组件修订、镜像摘要、迁移头和部署副本数。取库内实际迁移头与待发布镜像的 Alembic 链核对，本次由 20261122_0060 升至 20261123_0061。在现场已晋级版本上合入本卡改动，保留其间其他修复，镜像按精确修订构建。配置源已登记迁移 Job v15；若发布线已占用此代次，按现有发布规范使用下一未占用代次，重新渲染新的不可变 Job。
将本卡同批的 ci/verify-contracts.py 纳入发布编排分支。按实际候选重新钉 sources 与镜像，运行镜像和精确指针预检。检查器逐个验证五份公共契约，以及有选型器时的 KnowLab 源文件和 KnowBench 生成文件。Luna 已验 #115 归档指针、本批组件精确指针，并验证篡改选型源文件或生成文件任一方都会使预检失败。
2. 请在旧版用获准的私有验收账号准备普通委托。优先选可执行的两步正式方法与可重复验证的私有测试资源，两步都设逐次确认。执行第一步，把第二步留在原审批上。可用的输入为合成收件标识和固定回执，现场选确实只作用于测试资源的方法。记录任务、会话、第二步调用及审批 ID、第一步回执、当前事件游标与控制权。不要将审批令牌、模型密钥或原始材料写入回执。如果现场没有合适的正式方法，记录物料缺口，保留此项待验，不用操作其他用户的委托来代验。
3. 留一段由用户自己驾驶的工作会话作对照。数据库备份及恢复点按既有运维规程准备。远程工位内存约 3.7 GiB，构建及重型回归串行。

## 切换、验收与回退

1. 进入维护窗口，暂停新写入和新派发，让已开始的写事务结束并停旧 API、runner 及其他 KnowBench 写入者。等待中的委托可保留。现场盘点会话控制权数量，用数据库只读查询记录两个控制方各自的数量。
2. 先运行新镜像的迁移 Job，成功后核验 Alembic 头、约束 ck_workbench_sessions_wheel 和会话计数。原 advisor 数量应等于迁移后的 runtime 数量，user 数量相等。原测试任务的 active_task_id、审批、调用和历史游标应能按原 ID 回读。先核好迁移，再启新 API、runner 和 Web，恢复流量。已打开的工作台重新加载。
3. 在测试账号打开同一委托。历史交接事件保留原 advisor 值，当前会话返回 runtime。旧审批只出现一次，用户可看进度并通过正常入口批准；普通发消息仍受控制权约束。批准后只派发第二步，核对两步回执、交付结果、终态和控制权归还。最终事件从 runtime 归还给 user，active_task_id 清空。核对对照会话可正常发消息。新建一笔私有测试委托，确认新交接事件写 runtime，专家页与工作页各按自己的路由和会话类型显示。
4. 如需回退，重新暂停写入和派发，停新写入者。用含 0061 的迁移镜像执行 alembic downgrade 20261122_0060，再按切换时的实时盘点核验当前持有人映射，恢复基线 API、runner 与 Web。两向迁移都保留既有历史事件、审批和交付记录。若实际库头已向前推进，先核对后续迁移依赖，本卡只有 0061 ↔ 0060 的验证证据。
