# 工位同步与协作

这里统一放日常同步工具和助手之间的任务交接。两端通过 Git 协作：**助手验证并提交 → 所有者推送 → 另一端拉取后接手**。

**默认分工：助手只提交、汇报，不执行 `git push` 或 `sync.sh push`；由所有者统一执行 `sync.sh push`。只有所有者明确授权助手推送时才例外。**本规则同样适用于远程助手；旧任务卡里的默认推送要求以此规则为准。

## 目录里有什么

| 目录 | 用途 |
| --- | --- |
| `align/` | 以指定本机工位为基准，对齐配置中的其它工位；见 [对齐说明](align/README.md)。 |
| `sync/` | 当前工位的拉取、推送、状态检查；详细操作见 [同步说明](sync/README.md)。 |
| `inbox-cowork/<助手>/` | 发给该助手、尚未完成的任务卡。 |
| `inbox-review/<发起助手>/inbox/` | 请其他助手评审的请求，留在任务主工位。 |
| `inbox-review/<发起助手>/replies/<任务>/` | 各评审助手的独立回执；按评审助手命名文件。 |
| `hold/` | 明确暂停的任务；恢复前不执行。 |
| `done/` | 已完成并验收的任务卡。 |

协作收件箱按**执行助手**命名，不一定等于工位名。比如 Opus 使用 qwen 工位，任务仍可放 `inbox-cowork/opus/`；任务卡必须另外写清实际工位和分支。评审目录按**发起助手**命名，具体评审人写在请求里。所需目录按交接需要建立，不能把目录不存在当成任务已经完成。

## 同一任务在主工位评审

以任务确定主工位，评审不另开开发分支。例如 Luna 在 luna 工位写方案，请 Opus 评审：请求放 `inbox-review/luna/inbox/财务方法原子化.md`，Opus 到该工位读指定版本，将回执写到 `inbox-review/luna/replies/财务方法原子化/opus.md`。多位评审者各写自己的回执，不直接修改被评文件。

开发助手根据回执修改原文件，并在请求里记录采纳、未采纳及待定事项。只有真正独立的并行开发才需要各自工位。详细字段、轮次和完成办法见 [评审协作说明](inbox-review/README.md)。

同机共享工位时不要并发提交、拉取、切分支或修改同一个文件，提交只包含自己负责的路径。本地和远程同名工位仍是两份目录：发起者提交并推送后，评审者拉取；评审回执提交并推送后，开发者拉取再修改。同一分支跨机器轮流写，不因共用目录名称而跳过同步。推送仍遵守所有者统一执行、明确授权才由助手代推的规则。

## 每次接手与交回

以 agy 工位为例：

```bash
cd ~/worktrees/agy

# 接手：拉取另一端已经推送的提交
./sunmoonun/docs/sync-cowork/sync/sync.sh pull

# 查看本机各仓状态（不联网）
./sunmoonun/docs/sync-cowork/sync/sync.sh status

# 助手：按任务卡开发、验证、写回执，逐仓提交并汇报
# 修改子仓时：先提交子仓，再提交父仓的子模块指针

# 所有者：收到助手交回后，统一推送已经提交的内容
./sunmoonun/docs/sync-cowork/sync/sync.sh push
```

需要缩小范围时，在动作后加父仓名（如 `push knowbench-app`，包含子仓）或子仓路径（如 `push knowbench-app/knowbench-backend`，不包含上级父仓）。省略范围则处理全部注册仓，推送仍由所有者执行。

在 master 使用时进入 `~/master`，命令相同。脚本根据自身所在工位识别同步范围，不需要另传工位名。

推送后，对方仍需在自己的机器拉取。`agy` 同步的是自己的同名分支，不会自动合入 `qwen`，也不会把其他工位全部对齐。同一工位在两端轮流接手，避免同时修改并推送同名分支。

需要让本机多个工位采用同一基准时，使用 `./sunmoonun/docs/sync-cowork/align/align.sh qwen`；目标工位在 `align/config.sh` 配置，参数 `qwen` 是基准。该操作不联网、不推送，默认不含 master。

同步遇到未提交改动、分支不符、分叉或网络错误会停下；先核对现场再处理，不用重置或强推掩盖问题。完整行为、配置和排错见 [同步说明](sync/README.md)。

## 任务卡要写什么

每条任务一个 Markdown 文件，放到 `inbox-cowork/<执行助手>/`，至少写清：

- 目标与范围：要完成什么，哪些仓可以改。
- 执行位置：本地或远程、工位、仓、分支、起始提交。
- 前提与操作：必要条件、执行命令、必须停下的情况。
- 验收标准：怎样算通过，哪些需要所有者参与。
- 交回要求：回执位置、提交号、验证结果及未推送状态；需要助手代推时由所有者明确授权。

执行者只接指定任务，不因同步时看到其他收件箱就自行执行。任务卡中的发布候选和前提须在执行前重新核对，不能把旧卡直接当作当前发布指令。

回执放在被测仓的 `scripts/results/`，写清最终提交、验证结果、失败原因和未验证项。助手交回时明确“已提交、未推送”，提醒所有者执行推送；不得把本地提交称为远程已更新。只完成代码、尚未完成真实验收时，任务仍然未结；不得提前移入 `done/`。明确暂停的移入 `hold/`，恢复时更新前提后再交回收件箱。

## 工位管理放在哪里

创建、删除工位及维护工位名单使用 `mb`，正式工具统一放在：

```text
~/toolboxes/Vlinux/utils/set-up-tools/model-switch/
├── model-branch.sh   # mb 入口
├── layout.conf       # 主目录、工位目录与工位名单
└── repos.conf        # mb 注册仓列表
```

本目录不保存 model-switch 副本。日常同步用本仓的 `sync/config.sh` 维护同步仓列表；工位创建与 Git 同步是两件事，不能混用。

旧脚本和旧任务记录保留在 Git 历史中。当前正式入口是 `docs/sync-cowork/`，不再使用 `sync-workertree` 或原来的 `human-local.sh`、`human-remote.sh`。
