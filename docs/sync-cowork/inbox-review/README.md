# 主工位评审

请求和回执都留在干活的主工位，按**发起助手**归类。目录不是评审人的收件箱；谁参与由请求指定。

```text
inbox-review/
└── luna/
    ├── inbox/
    │   └── 财务方法原子化.md
    └── replies/
        └── 财务方法原子化/
            ├── opus.md
            └── kimi.md
```

## 请求写什么

每个任务一份请求，至少填写：

- 状态：待评审／评审中／待修改／待复审／已完成／暂停。
- 发起者、评审人、主工位路径、仓和分支。
- 实际待评提交的完整 SHA、文件路径、评审范围与重点。
- 各评审人的回执路径，以及哪些验证可以做；涉及付费或业务操作另按授权。
- 采纳记录：每项发现如何处理、修复提交或未采纳理由，以及尚待决定的问题。

提交号应指向待评内容，而不是包含这份请求的未来提交。只有写明版本，才能判断修改后是否需要复审。跨仓评审逐仓列提交。

## 回执写什么

每位评审者写自己的文件：请求路径、实际阅读的提交、结论、按文件定位的发现、建议、已做验证及未验证项。发现没有问题也写清范围，不能把未运行测试写成测试通过。评审意见不等于作者接受、验收或发布批准。

同任务复审在自己的文件追加轮次和新提交，保留前轮发现与处理结果；不得覆盖他人的回执。发起者负责修改原文并登记采纳情况，评审者默认只读被评内容。

## 同步与完成

同机可读取同一工位，写入不同回执文件；Git 操作串行。跨机器采用提交、所有者推送、对方拉取后接手，同一分支轮流写。另一端尚未推回回执时，不在本端抢先提交同一分支。

评审完成后在原请求标记“已完成”，请求与回执原位保留，避免链接失效。`sync.sh pull` 分别显示协作待办和评审请求；请求目录内也可能包含已完成记录，须读状态，不按提醒自动领任务。回执不会当成新请求列出。

本次目录改造只建立协作机制，不自动发起评审，也不自动执行旧任务卡。
