# 主工位评审

请求和回执都留在干活的主工位，按**发起助手的当前协作身份**归类，不按底层模型名称。例如 Opus 以 qwen 身份工作，就归到 qwen。

**一个任务一个目录，请求和回执放在一起。**不再在发起者下面另设独立的 replies 目录。

```text
inbox-review/qwen/inbox/
├── 冻结绑定核对/
│   ├── request.md
│   └── replies/
│       ├── agy.md
│       └── luna.md
└── 第三批修复核对/
    ├── request.md
    └── replies/
        └── agy.md
```

## 请求：每个任务的 request.md

至少填写：

- 状态：待评审／评审中／待修改／待复审／已完成／暂停。
- 发起者、评审人、主工位路径、仓和分支。
- 实际待评提交的完整 SHA、文件路径、评审范围与重点；跨仓逐仓列提交。
- 回执位置：同目录 `replies/<评审助手>.md`；允许的验证范围，付费和业务操作另按授权。
- 采纳记录：每项发现的处理、修复提交或未采纳理由，尚待决定的问题。

提交号指向待评内容，而不是包含本请求的未来提交。相同任务名只对应一个目录；复审留在原目录，内容实质变成另一项任务时再建新目录。

## 回执：该任务的 replies/

每位评审者只写自己的文件，注明对应请求、实际阅读的提交、结论、按文件定位的发现、建议、已做验证和未验证项。不能把未运行测试写成通过；意见不等于作者接受、验收或发布批准。

复审在自己的文件追加轮次和新提交，保留前轮发现和处理结果，不覆盖他人的回执。发起者修改被评内容，在 request.md 登记采纳情况。评审者默认只读被评文件。

## 同步与完成

同机可以读取同一工位、写入不同回执文件；Git 操作串行。跨机器采用提交、所有者推送、对方拉取后接手，同一分支轮流写。另一端尚未推回回执时，不在本端抢先提交同一分支；助手代推仍需明确授权。

完成后在 request.md 标记“已完成”，整个任务目录原位保留。`sync.sh pull` 只扫描各任务的 request.md，不把 replies 中的回执或说明当新请求。提醒也可能包含已完成记录，应读状态；不自动领任务或执行旧卡。
