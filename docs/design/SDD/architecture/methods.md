## 2026-11-14 方法分类与统一执行目标

[方法主稿](../../../总纲/专家方案设计/专家孵化方案/luna/专家及专家团孵化模板.md)为当前定义真源：工具方法不调用其它方法；专家方法组合工具方法及零种或一种专家方法，不调用专家团；专家团方法调用两种或以上专家方法，或已有专家团方法。种类按方法身份、允许依赖判定，同一方法不同版本或重复实例不增加种类，分类随孵化版本冻结。

三类共用五要素两视图、登记、权限和调用账。工具直接派发；专家与专家团共用逐步编排、验收和恢复，每步一次方法调用。下文旧架构与历史验证按原日期阅读，不代表新契约已实现；财务专家例外按下述最新重建决定执行，原等价迁移后清理要求已撤销。

## 方法怎么到 Codex

```text
专家包（工作台）── 这一步的方法文本 + 工具清单 ──▶ turn 输入（②）──▶ 沙箱里的 Codex
                                                       └── MCP 工具（⑥）──▶ 知识服务
```

- **文本**随 turn 输入注入，只给这一步；
- **工具**在知识服务侧；这一步允许哪些工具写在 token 的范围里，**知识服务按调用鉴权**，越界回错误（不依赖 Codex 换步重取工具列表）；
- **判据、阈值、为什么**留在工作台的验收规则里，不进注入面；
- 注入文本不出现下一步的线索。

旧树"runtime 代理 MCP 回后端二次校验"那条链退役：循环在沙箱里，工作台是它的唯一客户端，本来就看得到每次调用。

## 编排就是逐步发 turn

顾问不调模型（`C-A9`）。它做的事：读游标，取步骤契约，组装 turn 输入，发 `turn/start`，等 `turn/completed`，取交回物，做确定性检查，需要语义判断的派验收 turn，按 `on_reject` 决定下一步。一个 Task 的全部 turn 在同一个 thread 上。

## 专家包

```text
pack_id + version（签名）
profile_ref                      对应的 Task Profile
workflow[]                       步骤序列与 step_contract
method_texts{step_id: ref}       版本化的方法文本
tools{step_id: [mcp_tool]}
auto_allow                       顾问驾驶时自动放行的工具级动作
acceptance_rules                 确定性检查 + 验收 turn 的提示
quality_signals[]                自驾时触发求助提示的规则
eval_set_ref                     发布门用的评测集
answers                          六问：解决什么、需要什么、不解决什么、何时完成、何时拒绝或交回、效果与成本
```

真人专家写包；包里只写研究步骤与计算方法，不写判断规则（`F-POS-02`）。改包必须过发布评测（`0007-eval`）。

## 编排不构成保密

每一步的文本在下发那次仍可见；重复观察能重建序列。真正抄不走的是数据、服务端计算与口径、评测闭环（[价值](../../PRD/value.md)）。

## 最小实例

第 23 到 25 课的问数五阶段做第一份专家包：`rewrite → sql_generate → sql_execute → normalize → final`。每阶段一步一个 turn；SQL 执行是知识服务上的 MCP 工具；真值是 `truth_queries` 加 `result_fingerprint`。它用来把机制跑通，之后换成勾稽切口。

### 方法版本与任务计划分开

- knowlab 的作者工作稿表达方法论、可选方法单元、适用条件、输入输出、工具范围、禁区及必须交回的成果。方法单元复用现有 `StepCell`/`StepContract` 的工程表达；它们是可选择的能力，不是必须依次执行的八步。
- 动态模式由作者显式选用，发布时冻结方法论、单元、工具权限、成果判据和规划上限。旧工作稿缺省仍按固定序列编译；不能把已经上架的专家自动改成动态模式。
- knowmart 仍存发布清单及摘要，knowbench 仍在 Task 中保存作者包快照。可变的是这件任务的执行计划，不能覆写 `pack_snapshot`、`pack_digest` 或冻结的验收规则。现有 `pack_for_task` 按作者摘要缓存，不能把任务计划放进这个共享缓存，否则不同任务会串计划。
- 清单外层与运行包各自承担版本检查。动态包必须有显式的运行契约版本/能力标识，knowlab 编译、knowmart 交付和 knowbench 受理同步识别；老运行方拒绝不支持的动态包，不能按固定序列悄悄执行。具体 schema 随实现生成并在生产者、消费者同步锁定。



### 方法组件、专家发布与任务计划三层

所有者 2026-11-02 在区分「专家版本化」与「方法单元组合化」后确认记账并继续。目标不止是专家包内部的动态步骤：

| 层次 | 唯一权威与版本 | 引用和变更规则 |
| --- | --- | --- |
| 方法单元 | knowlab 的作者方法主档；稳定身份、不可变版本、内容摘要、作者确认出处 | 正文、输入输出、验收或工具上限变更产生新版本；被引用版本不覆盖。先支持作者本人在不同专家中复用，不因此开放跨所有者读取或分发 |
| 专家版本 | knowlab 编译、knowmart 发布；钉住方法身份/版本/摘要和必要交付快照 | 专家决定组合用途、必经方法与整体交付要求；更新引用经作者确认并发布新版，不用 latest 或版本范围自动漂移 |
| 任务计划 | knowbench 的 Task/Artifact 运行记录 | 仅引用该任务冻结目录中的方法别名，选取、排序和绑定实例成果。别名由专家发布清单解析到确切方法版本，模型不能自行换方法版本 |

方法是作者主档；市场和运行方只持精确引用及只读快照，不建设第二个方法编辑库。方法元数据、授权与确认由 knowlab 现有作者隔离和出处机制管理。运行不用逐步回源取「最新方法」，因此方法作者后续编辑不会悄悄改变已开始的任务。撤回、失效与新任务准入使用显式状态及可追溯记录，不能通过覆盖历史正文处理。

复用还必须分开**方法自己的输入槽**与**专家中的方法别名/依赖连线**。当前 v1 目录把 `input_refs` 当作其他方法 ID，只能作为尚未发布的过渡契约；直接把另一个专家的单元复制进来并改 ID，会破坏摘要和依赖，不能当作组件复用完成。补充契约应保存不可变方法定义，在专家发布时绑定输入槽到本专家的方法别名；编译可生成现有执行表达，但必须能由引用、绑定及编译器版本复核，不能把编译产物当作第二份方法主档。最终字段与 schema 由提供方生成并同步消费者锁。

**实施状态与衔接**：单元 1 的 v3/`dynamic-methods/v1` 证明专家内目录可编译；单元 1a 已补独立主档、作者绑定/升级 API、编译引用及快照校验，新增 `dynamic-methods/v2` 并同步三方契约锁。作者选择/升级页面与动态运行准入仍待完成。单元 2 的 Task 计划、实例和事务记录已适配引用目录，只读取任务冻结快照，不复制作者主档；接执行仍需完成有效计划视图与实例派发。旧固定 v2 和保底专家不改，不把未发布开发契约冒充已支持的公共版本。

验收必须证明：两个专家引用同一方法版本但组合不同；发布方法新版后两个旧专家和已开始任务仍使用旧版；只升级一个专家不会影响另一个；引用不存在版本、摘要不符、无权方法、未确认改稿、输入槽不兼容时拒绝；旧固定专家摘要和执行回归通过。完整方法商城、自动升级与模型临时发明方法不在本次扩展内。

#### 精确引用与交付快照（单元 1a 第二段，未发布）

工作稿 `method_refs[alias]` 保存方法 UUID、确切版本、摘要和命名输入槽连接；`steps` 中对应格子是该引用的只读投影。`POST /api/web/v1/method-units/{id}/versions/{version}/bind` 沿用作者身份、CSRF、工作稿修订锁与出处记录，明确选择版本、输入连接及专家的必需/调用次数设置。升级只保存目标工作稿，随后仍按既有“出一版”流程生成新的专家版本，不修改旧发布清单。

普通编辑、AI 提议接受、孵化整稿写回均经过同一个保存守卫，不能改投影或删除引用后变成可编辑副本。整稿导入/复制保留引用，并回查作者自己的方法库；跨作者、缺版、摘要错误、输入不兼容或编译结果被改写均拒绝。绑定和逐格出处同事务写入，并发按 revision 拒绝过时写入。方法首次冻结把默认工具、额度、读入上限和输出结构解析为实际值；后续修改平台默认值不会扩大这些已冻结参数。

引用专家仍使用 `knowbot-manifest/v3` 外层，内部显式升级为 `knowbench/dynamic-methods/v2`，钉 `method_compiler=knowlab/workdraft-compiler/v1`，未知编译器拒绝：`method_units` 是 knowlab 唯一编译器生成的运行契约，`method_sources[alias]` 携带精确引用和 `knowlab/method-definition/v1` 只读定义。引用单元的 `step_version` 等于方法版本；整个专家清单摘要冻结编译结果及来源，运行时不查“最新方法”。knowlab 在出版本时回源核摘要、投影与连接；导入时重新编译，不能把更宽的工具/不同验收冒充同一引用。knowbench 校验引用摘要、别名/版本/槽连接、选择上限和上游输出，并保留完整快照；作者定义在消费端作为不可变证据，不复制 knowlab 编译器。knowmart 仍只保存/交付清单，方法主档仍只有 knowlab 一处。

`dynamic-methods/v1` schema 与旧固定 v2 字节保持不变；新增 v2 提供方 schema、knowlab 消费锁及 knowbench 的 author-method 消费锁。孵化请求工作稿 schema 新增可选引用字段，两端锁同步。旧运行方拒绝新 runtime；新运行方只可读取、验证并为合成任务保存计划，真实任务准入仍拒绝全部 v3。无新增数据库迁移，引用复用既有工作稿 JSON 和专家不可变清单，迁移 0025/0035 的历史保护照旧。写入引用后，旧应用不能解析这些工作稿；回退必须保留历史并恢复支持该契约的代码，不能删引用、改摘要或将 v3 改标为 v2。

本段验收包含两个已发布专家共用方法、只升级其中一个后旧版本/另一专家不变、引用导入复制、所有者隔离、并发与回滚、篡改拒绝、商城交付不改快照、Task 计划接受后快照原样保留。尚未完成真实执行、返工与断线恢复，也未完成作者选择页面或财务专家重新孵化；这些不能用上述工程测试代替。

#### 第一工作单元的具体契约

旧工作稿不带 `planning`，继续生成 `knowbot-manifest/v2` 固定 `workflow`，不增加默认字段改变旧清单摘要。作者明确填写 `planning` 后生成 `knowbot-manifest/v3`，未引用独立主档时 `pack.runtime_contract` 为 `knowbench/dynamic-methods/v1`（精确引用使用上一节的 v2），包含 `method_units` 与 `planning`，不含任务 `workflow`。外层由 knowmart 生成 schema；方法目录由 knowbench `method_catalog.py` 生成 schema，knowlab 锁定两者，knowbench 锁定外层；不跨仓导入运行模型、不复制整份 schema 充当另一个真源。

每个方法单元的 `contract` 复用步骤的正文、工具、输出和验收表达，`selection` 规定作者确认的适用条件、是否必经、最多调用次数。目录顺序不是执行顺序。目录内 `step_id` 是方法 ID，`output_artifact` 是同名输出槽，`input_refs` 是依赖方法的输出槽；不是“取某方法最新结果”的运行指令。单元 2 的任务计划必须把槽绑定到明确实例及成果版本，才能执行；`covers.source` 与 `back_to` 都只能引用已声明输入槽，再由运行计划解析。

`planning` 带作者规划原文、`final_units`、总步骤上限、重规划上限、每次规划预留额度和输入上限。`final_units` 指定最终必须有合格成果的方法，连同 `selection.required` 及其输入依赖都不能漏；有多次调用时不能仅凭任意一次早期成功就宣告完成，必须按接受计划指定的有效成果验收。方法正文、验收与权限不由运行模型改写。未知引用、依赖循环、无法覆盖必需方法的步骤上限、越权工具、删除基本验收或混入任务状态均拒绝。

规划整格、选择条件及动态单元的依赖/工具工程配置/失败策略进入现有作者编辑或接受记录。导入动态清单时，不能无提示丢掉无法表达的冻结约束后继续出版本。当前工作台另提供目录校验函数，执行入口仍明确拒绝 v3，直到计划落盘、Attempt、全部运行视图及最终验收接通；“能编译和存清单”不等于“动态专家可运行”。

#### 财务专家的重新孵化

所有者 2026-11-02 明确：既然运行时只能选择既定方法，财务分析与预测专家必须重新孵化出动态版本。复用已有财务方法作为候选素材，整理方法单元、适用条件、输入输出、工具与检查，由作者确认后冻结成新版本；不覆盖现有保底专家。通用引擎先完成，再用同一孵化流程建立新版专家，不在运行代码植入财务八步或平台发明的判断。

“回答任意问题”限定在专家声明且方法库实际覆盖的范围内。缺方法时说明能力缺口，补充方法要回孵化阶段经作者确认、发布新版；它不同于缺数据可以在已授权方法内请求补采。Wind 的数据查询能力或工作流 skill 只能作为方法候选与工程素材，不能自动变成作者已确认的方法。

### 规划使用现有执行体

初次规划在定数据之前，调整规划只在步骤边界发生。规划也是用户沙箱中的一个普通 Attempt/turn，沿用同一线程、预算预留、取消、断线和 runner 对账；服务端不另调一个模型，不引入第二个 agent 框架。

规划输入是用户问题、作者的规划方法、方法单元的用途和输入输出摘要、平台当前可用且获准的工具能力、已确认的数据范围及已通过的结果。只向执行 turn 下发选中单元的完整方法。尚未确认的数据请求只能作为缺口，不能伪装成已经取得的输入；供应商返回的文本不能改作者方法或工具权限。

规划输出是有界的线性步骤列表：实例 ID、引用的方法单元 ID、输入成果引用、所选工具子集与选择理由；调整时还带上一版计划编号和调整理由。模型不提交替代的方法正文、验收函数、预算上调或新权限。不是把平台写死的财务八步换成另一段固定提示词。

### 计划落盘与确定性校验

复用既有 Artifact 版本及 Task/Attempt。计划使用平台保留的成果名，Task 指向已接受的计划版本；作者不能使用该保留名称。计划版本、规划 Attempt、作者摘要、输入成果版本及预算记录关联，接受计划和切换指针在同一事务中完成，并写会话事件。不能只把计划存进模型上下文或内存。

接受前必须校验：

1. 所有方法单元来自冻结的作者包；实例 ID 唯一，工具为作者范围与平台许可的交集。
2. 输入只能引用已通过且仍有效的成果或本计划更早的输出；不能前向引用、伪造结果、形成循环或读取别的任务。
3. 重规划保持已完成前缀和正在运行的 Attempt 不变，只替换尚未执行的后缀。返工走现有回退路径并保留旧成果；已开始但失效的后缀只允许把显式输入版本重新绑定到同一上游已验收新版，另存计划收据，方法、顺序、依赖、工具及其他字段不改。后续不能继续引用失效结果。
4. 步骤数、调整次数、单元调用次数与预算有硬上限；规划本身计费，失败和重试不重置上限。超出预算沿用 `WAITING(RESOURCE)`，追加由用户决定。
5. 作者规定的最终成果必须齐备，并通过原验收规则；模型声称完成、空计划或省略必需步骤都不能直接把任务改成成功。
6. 乐观锁校验当前 Task 状态、计划版本和规划 Attempt；重复回执幂等，取消后的迟到结果不能复活任务。规划 turn 断线后沿现有对账收尾，不盲目再发一轮。

`advisor`、工具鉴权、步骤栏、底稿与最终验收统一使用这件任务的有效计划视图；作者包仍作为权限与方法真源。不能只有步骤栏动态、后台仍按 `current_step` 对固定包取下标。

单元 2 的实现落点（开发分支，未发布）：`method_plan.py` 只表达方法别名、实例、输入版本、工具子集和理由；`method_plans.py` 经既有 Ledger 开规划 Attempt、计预算、接受及读取计划。规划使用保留步骤名 `__method_plan__`，成果也使用同名平台保留槽；Task 的 `accepted_plan_version` 指向确切 Artifact 版本。计划成果、指针与事件同事务提交，重复回执按规划 Attempt 查原收据，只读返回而不回滚当前计划。失败规划占用轮次和已产生的费用；已开始的方法实例也受前缀保护。未来输入只能声明前置实例，已完成输入必须钉验收登记的确切版本；实例成稿文件重名、大小写冲突或文件/目录冲突拒绝。

迁移 `20261102_0035` 只新增可空正整数计划指针，固定任务无需回填；没有接受记录时可降级，有记录时拒绝删除指针，发布回退需保留扩展 schema。计划属 knowbench 运行数据，Artifact 是版本历史，Task 指针是当前选择；不新增作者主档、不新增模型服务、不跨库读写（C-D1/D2/D6/D7/D12/D14、C-A9）。以下分段保留落地时的边界；当前 Advisor/Runner、工具鉴权、读取面与页面进度见第三至第五段。目录集合校验不能替代每次调用的权限核验。动态执行入口继续拒绝 v3，直到作者孵化和真实沙箱联合验收完成。


### 单元 3 第一段：执行视图与原子开步（开发分支，未发布）

`domain/workbench/execution_plan.py` 将任务已接受计划投影为既有 `StepContract`：方法实例 ID、实例独有成果名、输入连接、`covers.source`、`back_to` 和已选工具子集由同一个视图解析；作者正文、输出结构、验收和预算保持不变。没有第二套方法编译器，不改作者快照，不把任务视图放进 `pack_for_task` 缓存。固定包仍原样返回。

`plan_receipts.py` 是规划和执行共用的只读收据入口，按 Task 的确切指针读取计划及历史版；`execution_plan.accepted_results` 通过游标前每个实例最近一次执行 Attempt 的验收登记读取确切成果 ID/版本，再核其计划身份、方法版本、工具和输入链。任意新写入但未被验收登记的同名 Artifact 不能替换它。重规划与开步共用该读取，已不各自按名称取最新。

`Ledger.open_method_step` 在 Task 行锁下复核版本、状态、方向盘、取消及其他未收尾轮次，解析当前实例及输入，按作者额度调用原 `open_attempt`。Attempt 引用记录计划版本/摘要、作者摘要、实例与方法版本、工具子集、输入槽和确切成果 ID/版本/摘要；并发开步仅成功一次，事件失败回滚预留与 Attempt。读活跃绑定的入口仍只是运行接线的准备，尚不能替代 MCP 每次调用的实际鉴权。

回退游标立即排除后缀成果；上游返工产生新版后，依赖旧输入的结果不能重新算有效。明确钉住旧版的输入发生失效时拒绝开步，不静默改为最新；第三段通过有界重规划生成重新绑定的收据，详见下节。计划指定的最终成果保留完整映射，不能用最后一轮或任意早期成功代替最终验收。

本段同时修复取消与开步的竞态：原取消先窥读活动 Attempt 再锁 Task，可能遗漏中间新开的轮次。开步、取消、轮次结算、无人推进收尾及迟到费用现统一按 Task → Attempt 加锁；旧实现的确定性并发测试残留 0.05 预留，修复后取消轮次并释放预留。属于原账房修复，不新增取消或计费机制。

### 单元 3 第二段：有界规划服务与固定输入验收（开发分支，未发布）

`MethodPlanner` 通过与 Advisor 共用的 `TurnDriver` 接口发起普通规划轮次，使用作者规划原文、冻结方法的选择条件/输入槽/允许工具以及当前计划和有效成果版本。严格解析既有 MethodPlan；模型不能夹带方法正文、验收或预算。重规划保留已开始前缀，已完成输入钉确切版本，失败提案也占用作者允许的规划次数，下一轮会得到拒绝原因。没有另建模型客户端、运行账本或迁移。

规划响应的 Attempt 完成、费用、计划 Artifact/指针/事件和回到 QUEUED 在 Task 锁内一起提交。非法提案先回滚再结算失败费用；取消后的迟到响应只补费用不收计划；环境丢失、超时、中断和超预算均不能将部分回答作为有效计划。并发规划只发一轮；事件落库失败整体回滚。现有 `TurnResult`/`TurnDriver` 抽到 `turn.py` 共用，第二段落地时 Advisor 入口尚未调用规划服务，第三段已接线；隔离数据库使用 Driver 替身测试，不冒充真实沙箱验收。

派发必须携带父计划版本：初次为 0，明确的后续调整为当前已接受版本。过期派发只读返回，不把“重试初次规划”自动变成又一轮重规划和收费。

`judge_numbers` 的动态 `covers` 验收现经 `active_method_inputs` 复核活动实例及输入链，再读 Attempt 登记的确切 ID/版本/摘要；同名但未验收的新版本不会替换本轮输入。固定专家保持原读法。模型的提案、Task 有效计划、开步输入和验收依据可以分别追溯。

**本段后续进度**：第三段接 Advisor 规划/方法派发、原子收尾与完整最终成果核验，第四段接读取面和页面，第五段接实际 MCP 调用鉴权与原生审批定位；见下文。真实 v3 准入保持关闭；本批不进入 qwen 正在发布的合并候选。工程证据及复跑入口在 knowbench-backend `docs/method-execution.md`，后续仍属单元 3。

### 单元 3 第三段：Advisor 动态循环与事务收尾（开发分支，未发布）

原 Advisor 直接调用规划服务、按有效视图开步并沿原 Runner 沙箱执行。规划和定数据轮次不计作方法已执行，首个方法仍做范围检查。每个边界先检查数据等待，包括最后一步；明确输入版本因返工失效时先拒绝派发，再在作者规划次数内申请新计划收据，只重绑已验收的同一上游新版，不改写旧计划/Attempt 或已完成前缀。

验收原文、文件存在性与最终指纹在 Task 锁外读取。锁内复核活动实例和输入链，输出、费用/turn_id、事件、游标与回队列/返工/交人一次提交；验收异常与绑定不符不收成果，已发生费用仍结算。迟到响应不能结束新轮次的问题或释放其项目占用。最终 handback 列全部 final_outputs，核齐有效成果，产出 Outbox 与成功终态同事务；取消或版本变化阻止交付，事务失败后可从已验收末尾恢复而不重发模型轮次。

隔离数据库及既有 ScriptedAppServer 验证上述循环、重启、故障与固定专家回归；预录响应不是实际模型质量验收。当前尚缺工具调用的可信每轮身份与强制权限、统一页面/底稿/测试报告，真实 v3 入口仍关闭。没有新增数据库迁移、第二套执行器或模型客户端，qwen 合并候选不变。
