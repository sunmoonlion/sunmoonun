## 一、knowfeed 是什么

- **供给的门，不是真源**：管需求的受理、供给（渠道、取、加工、质检）、两边的切合，把结果交 knowbase；不在读的路上。说「平台跑腿、平台加工」时，指的是 knowfeed 这项服务替提需求的用户做事；数据归谁，按用户算（平台人员用的账号也是用户）。
- **不收上传**（在 knowbase web端，0044）；上传的资料由 knowbase 交来加工（第 3.4 节）。
- **三个端**：web端（用户提需求、「我的需求」）；后端（本页全部）；管理端（来源目录、渠道审核与试采、待审网站、缺口清单、队列监控）。
- **需求只用统一词表说「要什么」，不知道渠道；供给用同一套词表说「能取到什么」，不知道是谁要的**；两边共用的只有 knowbase 管的词表。

## 二、需求侧

### 2.1 四种需求

| 种类 | 是什么 |
| --- | --- |
| 精确描述 | 主体、类型、期间说清楚 |
| 给网址 | 用户指着某个页面或文件说「取这个」 |
| 订阅 | 一次说好，以后有新的就自动取 |
| 按主题找 | 用户只给话题，先列出候选，用户勾了再取 |

### 2.2 需求单

**公共部分**：需求单编号；种类；提出主体（2.3）；确认（knowbase 的确认编号与时间，或订阅的范围同意编号）；要的读法（原件、正文文字、抽好的表，可多选，决定怎样算办成）；最晚什么时候要（亲手提的必填；应用代提的按任务时限填；都没给按保守预计加系数）；说明（选填）；需求项（可多项）。一张单对应一次确认；各项各有状态，可单独取消。

| 种类 | 需求项写什么 |
| --- | --- |
| 精确描述 | 主体（证券代码含市场，或词表里的主体编号）、类型（词表）、期间（报告期或日期区间）、版本要求（最新、截至某日已披露、指定某一版）、口径（报表类） |
| 给网址 | 网址（一个或几个）；范围（只这一页，或加上它直接链到的文件，同一网站、只往下一层，最多 20 份，超出的列给用户看「还有几个没取」）；用户声明「公开页面、不用登录」；预填的描述（选填） |
| 订阅 | 订阅什么（按描述订：只有主体与类型，从订阅那天起往后新发的；按网址订：栏目页、RSS 源；按主题订：定期重新找）；多久查一次；起止（必须有截止日，最长一年，可续）；上限（每月最多多少份，按配额）；有新的怎么办（直接取并通知；按主题订的每轮候选要用户勾）；落到哪（默认是提订阅的应用） |
| 按主题找 | 主题（一句话或关键词）；范围（时间、来源类型、可指定网站、语言）；要多少候选 |

- 订阅：建订阅时由本人在 knowbase 留下一条**长期范围同意**（用户、订阅编号与修订、描述或网址范围、起止、用途、自动取得方式；可撤、续订出新修订）；范围内每轮不再逐份确认，knowbase 入库时核依据仍有效、没超范围。按主题订阅每轮候选都要用户勾。
- 按主题找的结果是候选清单，不是数据；用户勾的每条变成一个新的需求项（给网址或精确描述），再确认才去取。
- 需求单里不写渠道、采集器、作业、许可档。

### 2.3 提出主体

| 字段 | 写什么 |
| --- | --- |
| 提出方 | ① 用户本人在 knowfeed web端亲手提；② 应用代用户提（哪个应用、哪件任务或草稿）；③ 专家运行中提（哪位专家哪一版、哪件委托，经 knowbench 提交）；④ 订阅按期自动生成（哪条订阅、第几轮） |
| 归属用户 | 数据给谁、谁确认、配额算谁的；永远是一个用户（平台人员用的账号也是用户） |
| 代办链 | 提出方到归属用户的每一层，如「专家 X 第 3 版 → 委托 123 → 用户甲」 |

确认规矩随提出方：本人亲手提的提交即确认；应用代提的列清单、用户确认一次；专家提的必须经用户确认；订阅生成的凭订阅的范围同意（按主题订阅的候选每轮仍要勾）。

### 2.4 从哪来、带什么、先核什么

- **入口只有两个**：knowfeed web端、各应用调 knowfeed 的接口；另有 knowfeed 内部按订阅生成。knowbase web端不是入口；knowmart 的「需求条目」不是采集需求；平台运营不能替用户提，knowbase 不提，knowfeed 只在执行订阅时生成。
- **带什么**：证明（本人亲手提：本人令牌，knowfeed 凭它请 knowbase 记确认；应用代提：应用服务身份按关系校验 + knowbase 确认编号；订阅：范围同意编号）；提出方与代办链；需求单内容；幂等钥匙；进度通知给谁。
- **先核什么**（只核需求侧），顺序是：
  1. 认证归属、核同一请求摘要：同一幂等钥匙、内容相同的，回原结果（已受理的不因确认过期而被拒）；同一钥匙内容不同的，拒绝；
  2. 格式：字段、词表版本、项数上限；
  3. 凭证：确认编号真、7 天内、条目对得上（问 knowbase），或订阅范围同意有效；应用能不能替这个用户提；
  4. 配额：请求频率、在途单数、订阅条数、**每人每月新取份数**；按预估大小核一次用户空间，不足就「已拒绝」附「先清理空间」。

  只有真正的新受理才扣配额。「再试一次」用新的幂等钥匙。

### 2.5 需求的一生

```text
待确认 ──确认──▶ 已提交 ──核过──▶ 已受理 ──找到供给──▶ 取数中 ──▶ 已就绪
   │               │                 │                    │
   └─不确认作废    └─核不过：已拒绝   └─没有供给：无法满足  ├─▶ 部分就绪
                                     │                    ├─▶ 失败
                                     └─内容与读法已齐────▶ 已就绪（不经取数中）
                                                          └─▶ 超时
   任何没结束的状态 ──用户或应用取消──▶ 已取消
```

- 只往前走：迟到的事件不能把已取消、超时改成已就绪；完成事件只推进仍有效的需求依据。
- 不能改，只能撤了重提；新旧关联、历史都留。
- 「再试一次」：失败、超时、无法满足的生成挂在原项下的新项。
- **部分就绪**写明哪些读法还在加工、哪些已终止可补加工；只要原文的需求，不因表格加工失败而降成部分就绪。
- 需求单状态由各项汇总；超时后数据到了照样进用户的栏、另发通知，不自动重启任务。
- 网站待审时需求项停在「已受理」，附「这个网站还在审核，审过就取」。
- **命中照实**（所有者 10-26 定）：内容与读法都已齐的项从「已受理」直接到「已就绪」，看得出「这份公开披露以前有别的用户要过」，看不出是谁；不做假的「办理中」。
- **订阅**：生效中、暂停、已到期、已取消、被停用（附原因）。两种执行计划：目录、RSS 类走「看新的」；按主题订阅走定时「搜 → 本轮候选 → 用户勾 → 确认」。每轮记查的时间、发现几份、取了几份、因上限没取几份。**每条订阅各有进度**（共用的只是渠道的发现游标）：新加入的只收起始日之后的；当月超额的记「本月超额未取」，下月初在下月配额里优先补取，用户可选跳过；暂停后从自己的进度恢复。提前 14 天通知续订，续订 = 范围同意出新修订；到期不续，它生成的在途需求项标「已取消（订阅到期）」。按主题订阅每轮候选 7 天内不勾作废。
- 按主题找：正在找 → 候选已出（7 天）→ 已结束。
- **需求状态只由 knowfeed 通知**：每次变化经发件箱通知提需求的应用（现在「分发只投 knowbase」的锁要解开，第七节块 4）；用户收站内信，knowfeed web端「我的需求」能看、取消、再试。knowbase 只给 knowfeed 回执。

## 三、供给侧

### 3.1 渠道与来源目录

渠道 = 能取到数据的地方，加上取的方式与规矩；登记在来源目录里，由管理端维护。加渠道是登记一条记录，不改代码。

| 大类 | 是什么 |
| --- | --- |
| 有目录的披露渠道 | 按主体、类型、期间能列出有哪些文件 |
| 订阅源 | 按时间发布新条目（RSS、Atom、栏目页） |
| 通用网页 | 没有目录，只能按网址取；兜底渠道 |
| 搜索服务 | 输入话题返回候选网址 |

**登记写什么**：名称、大类；能提供什么（词表写：类型、主体范围、期间、能给的读法，以及这项能力的先后）；怎么取（适配器加配置）；条款与许可（条款链接、审核结论、取来的数据属于哪一档）；规矩（限速、每日上限、能否用无头浏览器渲染、是否守 robots 等，审核时定；robots 在通用网页型适配器里默认守，审核可逐渠道改）；状态（待审、白名单、停用附原因）；审核记录。

**审核就是第一道关**：每个渠道审一次，不逐条审。通用网页按网站（域名）审：用户给的网址落在没登记的网站上，自动建一条「待审」渠道，需求等审核；审过以后同一网站照这条走。采集这一层只管取，不管合规。待审网站有时限：N 天没人审自动转「无法满足」并通知用户；管理端对待审数量与等待时长告警。

**试采与自动暂停**：渠道点白名单之前，管理端对一条样例描述跑一次「列」和「取」，看得到结果才能放行；渠道连续失败 N 次自动暂停并告警，不让需求堆成失败。

**限速按出站地址全局算**：所有订阅、批量都挤同一个出站地址（生产出站是家庭宽带），渠道登记要有总的每日上限，不只按用户。

已有的写死的采集器里，巨潮在这里只是渠道实例：一条目录型渠道加一个插件。东方财富 F10 **不再采、不迁**（10-27 定：三大表改从年报原件抽，第三方整理的数给不出出处到页，[0047](0047-public-disclosures-facts-search.md) 第四节）。证券专线不再单独存在。

### 3.2 适配器

| 动作 | 输入 | 输出 |
| --- | --- | --- |
| 列 | 一条描述 | 渠道里符合的条目（渠道内编号、标题、发布时间、网址、版本线索） |
| 取 | 一个条目或网址 | 原件（内容、内容类型、取回时间、来源网址） |
| 看新的 | 游标 | 游标之后新出的条目（带版本线索：更正公告算已有原件的新版本）、新游标 |
| 搜 | 话题与范围 | 候选（标题、网址、摘要、日期），按搜索给的原始顺序，不重排、不评级、不截断 |

| 适配器 | 会哪几个动作 | 渠道登记时配什么 |
| --- | --- | --- |
| 目录型 | 列、取、看新的 | 目录接口与参数模板；主体换渠道编号；词表类型对应渠道分类 |
| 订阅源型 | 看新的、取 | RSS、Atom 地址；或栏目页地址加列表位置；网页变化监测 |
| 通用网页型 | 取 | 是否渲染、怎么抽正文、往下一层跟哪些文件链接 |
| 搜索型 | 搜 | 用哪个搜索接口（钥匙在密钥库） |

特殊渠道写**渠道插件**，只管映射与解析；排队、限速、留存、交付由框架做；插件不得自带网络客户端绕过框架。现有通用采集的 RSS、Atom、API、网页变化监测收进订阅源型与目录型。

**执行层的安全边界**（工程边界，不是合规审批）：
- 只许 http、https；取之前解析域名，拒私网、环回、链路本地、云元数据与保留地址；每次重定向重核；连上后核对端地址；不带任何凭据。现有 `crawl_http.py` 的协议、端口、公网地址、重定向、体积与时间限制照用。
- **无头浏览器放 knowfeed 自己的一个单独工作负载**（不是外部爬虫）：不挂密钥，只许出公网，系统调用收紧；页面的子资源与后台请求都经受控出口、同样拒内部地址；每次渲染隔离 Cookie、下载目录，页面与附件总量、时间、内存设上限。现在依赖里刻意没有浏览器内核（「休眠能力」测试断言内置爬虫引擎不存在），这一条决定反过来，测试跟着改。
- 出站网络策略只给采集与渲染的工作负载，且只到公网。

**给应用的公开索引查询**：knowlab 测试集要「这家公司有哪些报告」时用；按主体查，回条目不回内容，记谁为哪个草稿查的。（10-27 删「不开『列公司』」：功能做全，合规用资格、权限、开关管；全市场的公开原件由平台人员用的账号订阅采进 knowbase，网页全文搜见 0047 第五节。）

**平台人员用的账号订阅全市场**（10-27 定）：这个账号像普通用户一样订阅 A 股三个交易所全部上市公司的定期报告、公告、招股书，回填先后与年限、排在调度第 ④ 档、全量前 100 家实测，见 [0047](0047-public-disclosures-facts-search.md) 第三节。

### 3.3 作业与调度

| 作业 | 做什么 | 按什么去重、共享 |
| --- | --- | --- |
| 列 | 查目录 | 渠道 + 描述，短时缓存，所有人共用 |
| 下载 | 取回条目或网址 | 渠道 + 渠道内编号 + 版本；通用网页按规范化网址，只在同一次或明确的新鲜度窗口内共享（网址是身份不是版本，重取后按内容摘要决定是否新版本） |
| 加工 | 正文、按页文字、抽表、描述 | 内容版本 + 加工器版本与配置；跨用户共享 |
| 看新的 | 订阅的一轮查看 | 渠道 + 订阅对象；订同一个的人共用发现游标，各订阅各记进度 |
| 搜 | 按主题搜一次 | 每个需求一次，同样话题短时缓存 |

- **需求、请求、作业三层**：每次「用户 × 应用 × 任务（或订阅轮次）× 确认修订 × 需求项」是一条需求依据，不可变；同一用户同一描述键的未办完请求合流成一条请求、挂多条依据；作业跨用户共享。取消只摘自己那条依据，最后一条摘掉才取消请求；所有请求都撤了作业才取消。
- **尝试**：每次执行记开始、结束、结果、原因。临时出错按逐次拉长的间隔重试，有次数上限；被限流等到能取再取；渠道明说没有不重试、转「无法满足」；内容不对不重试、转「失败」；被打断记「被打断」，调度按规矩重排、计入次数。每次尝试有时限。
- **调度**：每个渠道一条队列（现有的按来源准入锁只做到「不等就拒」，要改成排队等待），按登记的限速与并发；先后四档（① 有任务在等数据的；② knowlab 测试集这类成批的；③ 订阅；④ 后台补加工），同档按用户轮流；预计时间按队列与限速算；渠道停用时作业暂停或取消、需求项转「无法满足」。订阅的周期查看是新加的定时任务（现在定时任务里只有投递泵）。
- **订阅**：查的频率取用户希望的与渠道允许的最快里慢的那个。

### 3.4 原件留存与加工

- **原件**一个字节不改先存下，按摘要去重，记出处（渠道、编号或网址、取回时间、返回状态与响应头摘要）。交 knowbase 拿到回执后再留 30 天，然后删内容、只留出处与摘要。
- **加工归 knowfeed**（变成人和专家能直接读的形态，作为读法交 knowbase）；**检索索引与 RAGFlow 解析归 knowbase**（0043 第五节）：扫描版、复杂版面的按页文字，由 knowbase 建检索索引时从 RAGFlow 取回完整解析结果存成读法，knowfeed 不碰 RAGFlow。

| 加工器 | 做什么 |
| --- | --- |
| 正文抽取 | 网页去导航、广告，转文本或 Markdown，取标题、发布日期 |
| 按页文字 | 可抽文字的 PDF 按页切，带页码（扫描版的见上） |
| 表格整理 | Excel、CSV、网页表格转统一的表结构（按表、物理行列存，见 0043 第五节） |
| 描述识别 | 先用渠道列表给的（主体、类型、期间、披露时间），不够再从内容认 |
| 领域插件 | 某一类内容的专门加工，如财报抽表（认三张表、统一科目名、单位与口径、勾稽、每格带页码，作为语义标注写在表格单元上；季报、半年报、银行保险另配科目表都在插件里） |

- 加工器有版本，升级后重新加工产生新的读法版本，旧的保留；质检标记改变也产生新的读法版本。
- 渠道列表来的描述记「入库质检过」，从内容猜的记「自动识别未确认」。
- 加工没成功原件照样交付，需求项按第 2.5 节写清。
- **上传的资料（推）**：用户上传时按页面说明采用加工，knowbase 记依据，向 knowfeed 提交只指向这份内容版本的加工作业，把内容推过来；knowfeed 不留存，作业完成即删；结果只能挂回这份原件，不改所有者、许可、区；许可「只许本人用」的结果同样只许本人用；加工中撤销或清除，晚到的结果不建可读版本。
- **重新加工（拉）**：knowfeed 经 knowbase 接口取原件（不碰桶），凭限定作业、目的、版本、时限的「加工」授权；knowbase 按「系统加工」留痕，用户在「谁读过」里看得到。

### 3.5 质检与交付

| 层 | 核什么 | 核不过 |
| --- | --- | --- |
| 取回检查 | 内容类型；是不是错误页；完整没有；摘要 | 这次尝试失败 |
| 加工检查 | 正文非空；页数对得上；表格完整；领域插件自己的检查（勾稽、两种读法互核） | 不挡原件交付，照实标出 |
| 对得上需求吗（精确描述） | 主体、类型、期间是不是同一份 | 不算就绪，转「失败」附原因 |

不拿第三方整理的数当「对」的标准（东方财富 F10 已不采）。三大表抽成事实行写回 knowbase（原样层、标准化层），质检用会计恒等式与年报「主要会计数据」互核，见 0047 第四节。

- **交 knowbase**：原件版本与读法、描述（带确认状态）、出处与加工器版本、质检报告、许可档、关联的需求依据。
- knowbase 放法：公开披露的进公开原件层、给每条有效依据记第二区引用；非公开的内容只存一份、每个用户各得一份自己名下的资料，各算各的许可与删除；按「落到哪」展示，依据是确认那一次或订阅范围同意。网站审过不等于页面是法定披露：数据区与许可按实际来源与审核规则定。
- **回执**：每项一张（编号、版本、哪几种读法已就绪）；knowfeed 凭回执标「已就绪」「部分就绪」；交付可安全重试；拒收的转「失败」。

## 四、切合

- **预切合只查来源目录**（第三轮评审 F 2.6）：确认之前，应用问 knowfeed 这几项「这类能取 / 取不到 / 网站待审」、候选渠道的许可档、按队列估的预计时间；毫秒级，不在用户确认之前替他去问渠道，也不看 knowbase 已有什么。「渠道里有没有这一份」放到受理后。
- **确认记供给条件快照**：确认关联这次预切合的结果，以及可接受的来源限制与用途条件（例如要随公开专家用，就要「可以经专家给别人用」）。
- **入口分支**（0043 第 3.3 节）：本人已有、内容与读法都齐的不进 knowfeed；本人没有但都齐的，knowbase 按确认建关系、立即完成；缺原件、缺读法、要刷新来源版本的才进 knowfeed。
- **受理后正式切合**：

| 种类 | 怎么切合 |
| --- | --- |
| 精确描述 | ① 已有原件、缺读法的只建加工作业。② 缺原件或要刷新的，按来源目录里覆盖这条描述、**且满足确认快照**的渠道先后排；对第一个渠道「列」，确认有这一份、版本合要求（缓存新鲜度证明不了就核源站），有就建下载与加工作业，没有换下一个。③ 都没有转「无法满足」，分「渠道里没有这一份」与「这类数据我们还取不到」；只有不满足快照的渠道能取时，回「当前供给条件不满足」，让用户调整用途或确认新条件 |
| 给网址 | 看网址落在哪个网站：属于已登记渠道照那条；否则走通用网页，看网站审核状态（审过照取、待审等审核、审不过转「无法满足」） |
| 订阅 | 建订阅时找能执行的渠道（目录、RSS 类找会「看新的」的；按主题订阅找搜索渠道），找不到订阅建不起来；以后每轮生成的需求项已知渠道，直接建作业 |
| 按主题找 | **第一版只在用户指定的网站与审核过的政府、交易所、监管渠道里搜**（站内搜索或目录型「列」），通用搜索接口等律师意见（所有者 10-26 定）；每条候选先预切合，标由哪个渠道取、许可哪一档、网站审没审过，按原始顺序列给用户勾 |

- **渠道先后**：登记时写；官方在第三方前，许可宽的在窄的前；取不到自动换下一个，只在满足确认快照的渠道之间换。
- **缺口清单**：「这类数据我们还取不到」的需求记进管理端，管理端据此补渠道。

## 五、knowfeed 自己存什么

需求单、需求项、需求依据、请求、作业、尝试、来源目录（渠道、能力、审核与试采记录）、待审网站、缺口清单、订阅与各订阅的进度和每轮记录，以及留 30 天的原件。不再存文档与文档版本（真源在 knowbase）。

## 六、拆旧线

**生产现状**（2026-10-26 只读查）：knowfeed 通用采集的信息源、采集器、采集作业、原文、文档、文档版本、抽取内容、分发记录，证券请求、证券数据集、证券入库，全是 0 行，只有关注清单 10 行（加 10 行日志）；knowbase 的知识文档、知识数据集也是 0 行。所以拆旧线**不用迁数据**，就是关入口、删代码。

1. **第 0 步，独立的提前发布**（`kind-flux-final` 之后、0043 块 1 之前，只加 fail-closed 拒绝、不带新功能）：关注清单自动批准、运营代用户发起请求、证券请求的旧接口、通用采集里「运营建作业直接分发进 knowbase」的那条路（分发记录）。
2. **退两套旧模型**：
   - 证券专线：请求、关注清单（那 10 行留作历史后删）、写死的采集器、证券数据集（SQLite）与入库；巨潮改登记为渠道实例，F10 删掉（10-27）。
   - knowfeed 自己的通用文档模型（文档、文档版本、抽取内容、分发记录）：第四版里一份内容只在 knowbase 存一份，knowfeed 不再有文档与版本；信息源、采集器的配置并进来源目录与渠道登记。
3. **最后清**：旧管理页、相关接口、「休眠能力」测试里不再成立的两条（内置爬虫引擎、分发只投 knowbase）。
