## 一、knowfeed 是什么

- **供给的门，不是真源**：管需求的受理、供给（渠道、取、加工、质检）、两边的切合，把结果交 knowbase；不在读的路上。
- **不收上传**（在 knowbase web端，0044）。
- **三个端**：web端（用户提需求、「我的需求」）；后端（本页全部）；管理端（来源目录、渠道审核、待审网站、缺口清单、队列监控）。
- **需求只用统一词表说「要什么」，不知道渠道；供给用同一套词表说「能取到什么」，不知道是谁要的**；两边共用的只有 knowbase 管的词表。

## 二、需求侧

### 2.1 四种需求

| 种类 | 是什么 |
| --- | --- |
| 精确描述 | 主体、类型、期间说清楚 |
| 给网址 | 用户指着某个页面或文件说「取这个」 |
| 订阅 | 一次说好，以后有新的就自动取 |
| 按主题找 | 用户只给话题，先列出候选，用户勾了再取 |

### 2.2 需求单

**公共部分**：需求单编号；种类；提出主体（2.3）；确认（knowbase 的确认编号与时间）；要的读法（原件、正文文字、抽好的表，可多选，决定怎样算办成）；最晚什么时候要；说明（选填）；需求项（可多项）。一张单对应一次确认；各项各有状态，可单独取消。

| 种类 | 需求项写什么 |
| --- | --- |
| 精确描述 | 主体（证券代码含市场，或词表里的主体编号）、类型（词表）、期间（报告期或日期区间）、版本要求（最新、截至某日已披露、指定某一版）、口径（报表类） |
| 给网址 | 网址（一个或几个）；范围（只这一页，或加上它直接链到的文件，同一网站、只往下一层）；用户声明「公开页面、不用登录」；预填的描述（选填） |
| 订阅 | 订阅什么（按描述订：只有主体与类型，从订阅那天起往后新发的；按网址订：栏目页、RSS 源；按主题订：定期重新找）；多久查一次；起止（必须有截止日，最长一年，可续）；上限（每月最多多少份，按配额）；有新的怎么办（直接取并通知；按主题订的每轮候选要用户勾）；落到哪（默认是提订阅的应用） |
| 按主题找 | 主题（一句话或关键词）；范围（时间、来源类型、可指定网站、语言）；要多少候选 |

- 订阅：建订阅时确认「这个范围内往后新的都要」，范围内不再逐份确认；按主题订阅每轮候选都要用户勾。
- 按主题找的结果是候选清单，不是数据；用户勾的每条变成一个新的需求项（给网址或精确描述），再确认才去取。
- 需求单里不写渠道、采集器、作业、许可档。

### 2.3 提出主体

| 字段 | 写什么 |
| --- | --- |
| 提出方 | ① 用户本人在 knowfeed web端亲手提；② 应用代用户提（哪个应用、哪件任务或草稿）；③ 专家运行中提（哪位专家哪一版、哪件委托，经 knowbench 提交）；④ 订阅按期自动生成（哪条订阅） |
| 归属用户 | 数据给谁、谁确认、配额算谁的；永远是一个用户（平台账号也是用户） |
| 代办链 | 提出方到归属用户的每一层，如「专家 X 第 3 版 → 委托 123 → 用户甲」 |

确认规矩随提出方：本人亲手提的提交即确认；应用代提的列清单、用户确认一次；专家提的必须经用户确认；订阅生成的范围内不再确认（按主题订阅的候选每轮仍要勾）。

### 2.4 从哪来、带什么、先核什么

- **入口只有两个**：knowfeed web端、各应用调 knowfeed 的接口；另有 knowfeed 内部按订阅生成。knowbase web端不是入口（给链接跳 knowfeed web端）；knowmart 的「需求条目」不是采集需求；平台运营不能替用户提，knowbase 不提，knowfeed 只在执行订阅时生成。
- **带什么**：证明（本人亲手提：本人令牌，knowfeed 凭它请 knowbase 记确认；应用代提：应用服务身份按关系校验 + knowbase 确认编号；订阅：订阅编号）；提出方与代办链；需求单内容；幂等钥匙（同一件任务重发不成两张单）；进度通知给谁。
- **先核什么**（只核需求侧）：格式（字段、词表版本、项数上限）；凭证（确认编号真、7 天内、条目对得上，问 knowbase；应用能不能替这个用户提；订阅在有效期）；配额（请求频率、在途单数、订阅条数）；重复（同一幂等钥匙回原单）。

### 2.5 需求的一生

```text
待确认 ──确认──▶ 已提交 ──核过──▶ 已受理 ──找到供给──▶ 取数中 ──▶ 已就绪
   │               │                 │                    │
   └─不确认作废    └─核不过：已拒绝   └─没有供给：无法满足  ├─▶ 部分就绪
                                                          ├─▶ 失败
                                                          └─▶ 超时
   任何没结束的状态 ──用户或应用取消──▶ 已取消
```

- 只往前走：迟到的事件不能把已取消、超时改成已就绪。
- 不能改，只能撤了重提；新旧关联、历史都留。
- 「再试一次」：失败、超时、无法满足的生成挂在原项下的新项；确认在 7 天内不用再确认。
- 需求单状态由各项汇总；超时后数据到了照样进用户的栏、另发通知，不自动重启任务。
- 网站待审时需求项停在「已受理」，附「这个网站还在审核，审过就取」。
- 订阅：生效中、暂停、已到期、已取消、被停用（附原因）；每轮记查的时间、发现几份、取了几份、因上限没取几份；到每月上限本月停取、通知，下月恢复；提前 14 天通知续订，续订 = 重新确认范围；按主题订阅每轮候选 7 天内不勾作废。
- 按主题找：正在找 → 候选已出（7 天）→ 已结束。
- **需求状态只由 knowfeed 通知**：每次变化经发件箱通知提需求的应用（应用据此恢复任务或报失败，也可按编号查）；用户收站内信，knowfeed web端「我的需求」能看、取消、再试。knowbase 只给 knowfeed 回执。

## 三、供给侧

### 3.1 渠道与来源目录

渠道 = 能取到数据的地方，加上取的方式与规矩；登记在来源目录里，由管理端维护。加渠道是登记一条记录，不改代码。

| 大类 | 是什么 |
| --- | --- |
| 有目录的披露渠道 | 按主体、类型、期间能列出有哪些文件 |
| 订阅源 | 按时间发布新条目（RSS、Atom、栏目页） |
| 通用网页 | 没有目录，只能按网址取；兜底渠道 |
| 搜索服务 | 输入话题返回候选网址 |

**登记写什么**：名称、大类；能提供什么（词表写：类型、主体范围、期间、能给的读法，以及这项能力的先后）；怎么取（适配器加配置）；条款与许可（条款链接、审核结论、取来的数据属于哪一档）；规矩（限速、每日上限、能否用无头浏览器渲染等，审核时定）；状态（待审、白名单、停用附原因）；审核记录。

**审核就是第一道关**：每个渠道审一次，不逐条审。通用网页按网站（域名）审：用户给的网址落在没登记的网站上，自动建一条「待审」渠道，需求等审核；审过以后同一网站照这条走。采集这一层只管取，不管合规。

已有的两个写死的采集器，在这里都只是渠道实例：巨潮是一条目录型渠道加一个插件；东方财富 F10 也是一条渠道，和别的一样过审核、由审核定许可。证券专线不再单独存在。

### 3.2 适配器

| 动作 | 输入 | 输出 |
| --- | --- | --- |
| 列 | 一条描述 | 渠道里符合的条目（渠道内编号、标题、发布时间、网址、版本线索） |
| 取 | 一个条目或网址 | 原件（内容、内容类型、取回时间、来源网址） |
| 看新的 | 游标 | 游标之后新出的条目、新游标 |
| 搜 | 话题与范围 | 候选（标题、网址、摘要、日期） |

| 适配器 | 会哪几个动作 | 渠道登记时配什么 |
| --- | --- | --- |
| 目录型 | 列、取、看新的 | 目录接口与参数模板；主体换渠道编号；词表类型对应渠道分类 |
| 订阅源型 | 看新的、取 | RSS、Atom 地址；或栏目页地址加列表位置；网页变化监测 |
| 通用网页型 | 取 | 是否渲染、怎么抽正文、往下一层跟哪些文件链接 |
| 搜索型 | 搜 | 用哪个搜索接口（钥匙在密钥库） |

特殊渠道写**渠道插件**，只管映射与解析；排队、限速、留存、交付由框架做。无头浏览器渲染在 knowfeed 自己的工作进程里跑。现有通用采集的 RSS、Atom、API、网页变化监测收进订阅源型与目录型，Scrapy、Playwright 两个空壳改为通用网页型的渲染能力。

### 3.3 作业与调度

| 作业 | 做什么 | 按什么去重、共享 |
| --- | --- | --- |
| 列 | 查目录 | 渠道 + 描述，短时缓存，所有人共用 |
| 下载 | 取回条目或网址 | 渠道 + 渠道内编号 + 版本；通用网页按规范化网址；跨用户共享 |
| 加工 | 正文、按页文字、抽表、描述 | 原件版本 + 加工器版本与配置；跨用户共享 |
| 看新的 | 订阅的一轮查看 | 渠道 + 订阅对象；订同一个的人共用 |
| 搜 | 按主题搜一次 | 每个需求一次，同样话题短时缓存 |

- **需求、请求、作业三层**：每次「用户 × 应用 × 任务 × 确认清单修订 × 需求项」是一条需求依据，不可变；同一用户同一描述键的未办完请求合流成一条请求、挂多条依据；作业跨用户共享。取消只摘自己那条依据，最后一条摘掉才取消请求；所有请求都撤了作业才取消；完成事件只推进仍有效的依据。
- **尝试**：每次执行记开始、结束、结果、原因。临时出错按逐次拉长的间隔重试，有次数上限；被限流等到能取再取；渠道明说没有不重试、转「无法满足」；内容不对不重试、转「失败」；被打断记「被打断」，调度按规矩重排、计入次数。每次尝试有时限。
- **调度**：每个渠道一条队列，按登记的限速与并发；先后四档（① 有任务在等数据的；② knowlab 测试集这类成批的；③ 订阅；④ 后台补加工），同档按用户轮流；预计时间按队列与限速算；渠道停用时作业暂停或取消、需求项转「无法满足」。
- **订阅**：查的频率取用户希望的与渠道允许的最快里慢的那个；订同一个东西的共用一次查看，按每条订阅的上限分别生成需求单。

### 3.4 原件留存与加工

- **原件**一个字节不改先存下，按摘要去重，记出处（渠道、编号或网址、取回时间、返回状态与响应头摘要）。交 knowbase 拿到回执后再留 30 天，然后删内容、只留出处与摘要；以后重新加工从 knowbase 取原件。
- **加工归 knowfeed**（变成人和专家能直接读的形态，作为派生版本交 knowbase）；**检索索引归 knowbase**（切段、向量，见 0043 存储一节）。

| 加工器 | 做什么 |
| --- | --- |
| 正文抽取 | 网页去导航、广告，转文本或 Markdown，取标题、发布日期 |
| 按页文字 | PDF 按页切，带页码 |
| 文档解析（RAGFlow） | 扫描版文字识别、版面与表格识别，处理扫描版与复杂版面的 PDF |
| 表格整理 | Excel、CSV、网页表格转统一的表结构 |
| 描述识别 | 先用渠道列表给的（主体、类型、期间、披露时间），不够再从内容认 |
| 领域插件 | 某一类内容的专门加工，如财报抽表（认三张表、统一科目名、单位与口径、勾稽、每格带页码；季报、半年报、银行保险另配科目表都在插件里） |

规矩：加工器有版本，升级后重新加工产生新派生版本，旧的保留；渠道列表来的描述记「入库质检过」，从内容猜的记「自动识别未确认」；加工没成功原件照样交付，需求项转「部分就绪」写明原因；用户上传的资料也走同一套加工（knowbase 交来，结果只给上传者，评审 E2）。

### 3.5 质检与交付

| 层 | 核什么 | 核不过 |
| --- | --- | --- |
| 取回检查 | 内容类型；是不是错误页；完整没有；摘要 | 这次尝试失败 |
| 加工检查 | 正文非空；页数对得上；表格完整；领域插件自己的检查 | 不挡原件交付，照实标出 |
| 对得上需求吗（精确描述） | 主体、类型、期间是不是同一份 | 不算就绪，转「失败」附原因 |

- **交 knowbase**：原件版本与派生版本、描述（带确认状态）、出处与加工器版本、质检报告、许可档、关联的需求依据（归属用户、从哪来、落到哪）。
- knowbase 放法：公开披露的进公开原件层、给每条有效依据记第二区引用；非公开的内容只存一份、每个用户各得一份自己名下的资料，各算各的许可与删除；按「落到哪」展示，依据是确认需求单那一次。
- **回执**：每项一张（编号、版本、哪几种读法已就绪）；knowfeed 凭回执标「已就绪」「部分就绪」；交付可安全重试；拒收的转「失败」。

## 四、切合

- **确认之前先预切合**：应用列清单前问 knowfeed 能不能满足、大概多久、许可哪一档；只看供给侧，不看 knowbase 已有什么（不泄露命中）。清单只给总数与保守的预计时间，不分已有和要新取。
- **受理后正式切合**：

| 种类 | 怎么切合 |
| --- | --- |
| 精确描述 | ① 问 knowbase 原件与读法是否都有：都有直接记引用；原件有缺读法只建加工作业。② 没原件，按来源目录里覆盖这条描述的渠道先后排。③ 对第一个渠道「列」，确认有这一份、版本合要求，有就建下载与加工作业，没有换下一个。④ 都没有转「无法满足」，分「渠道里没有这一份」与「这类数据我们还取不到」 |
| 给网址 | 看网址落在哪个网站：属于已登记渠道照那条；否则走通用网页，看网站审核状态（审过照取、待审等审核、审不过转「无法满足」） |
| 订阅 | 建订阅时找会「看新的」的渠道，找不到订阅建不起来；以后每轮生成的需求项已知渠道，直接建作业 |
| 按主题找 | 按范围挑搜索渠道；每条候选先预切合（标由哪个渠道取、许可哪一档、网站审没审过）再列给用户勾 |

- **渠道先后**：登记时写；官方在第三方前，许可宽的在窄的前；取不到自动换下一个。
- **缺口清单**：「这类数据我们还取不到」的需求记进管理端，管理端据此补渠道。

## 五、knowfeed 自己存什么

需求单、需求项、需求依据、请求、作业、尝试、来源目录（渠道、能力、审核记录）、待审网站、缺口清单、订阅与每轮记录，以及留 30 天的原件。

## 六、拆旧线

被打断的批次不会自己恢复，顺序是硬约束；时机在 `kind-flux-final` 之后、0043 块 1 之前（评审 Q 四）：

1. **先关写入口**（fail-closed，拒收并说明）：关注清单自动批准、运营代用户发起请求、F10 进用户的数据、证券请求的旧接口。
2. **再迁**：在跑的跑完或标失败；原件主档交到 knowbase 公开原件层（knowfeed 只留作业记录与 30 天原件）；现有 F10 数据集迁进平台账号第一区；巨潮、F10 改登记为渠道实例。
3. **最后清**：证券专线的代码（请求、关注清单、写死的采集器）、旧管理页与 SQLite 数据集。
