## 一、要解决什么

| # | 问题 | 现在 |
| --- | --- | --- |
| 1 | 左边栏把过程和结果混在一起 | 管理端、web端都是「创意 / 分身 / 专家」三栏，每栏既放过程又放产物；右边栏放的是输入（对照材料） |
| 2 | 有「退回」，结果会被改 | 测试没过、超时可以「退回待测试」；同一个分身重测，上一次的报告被盖掉（只剩 `run_attempts` 一个数） |
| 3 | 没有版本与编号 | 创意改了就是改了，没有版本；测试没有编号；专家版本号由 knowmart 交付时才给 |
| 4 | 上架只有一道门 | 用户点「要这一版」就直接交 knowmart（knowlab 后端 `b7b7edb`，同步到 qwen、没发），我们不审 |
| 5 | 补充方法让方法有两处来源 | 创意原文 + 补充方法（0035），规则出处要指到两种地方 |
| 6 | 交付把数据一起绑给专家 | 准专家清单里的 `data_bindings` 随交付进 knowmart，knowbench 请专家时读作者绑的那几版；10-23 定「专家不绑数据」 |

## 二、总原则

1. **过程和结果分开**：左边栏是过程，右边栏是这个过程的结果（输出）；右边栏只放输出，输入在过程里从上一段的输出里选。
2. **没有退回**：每个过程跑一次出一个结果，结果定了不改；要改就再跑一次、出新的。通过、没通过是测试的结果。
3. **只增**：创意、准专家、专家用**版本号**，测试用**编号**，都只增、不回改。
4. **一个名称一生**：从申请到专家是同一个名称，改也只是版本不同；换一套完全不同的方法另起新名称（新申请）。
5. **进 knowmart 只走 knowlab**：都要孵化、测试、过两道门；用户自编的走 knowlab 的简化流程，没有绕过测试的路。
6. **专家归用户自己，默认自用；公开按资质**（`C-L4`，10-20 已改）。公开本期一起做（第十二节）。
7. **专家只是逻辑、不绑数据**（10-23）：knowlab 测试时用 knowlab 知识库里的数据，测试可复现；请专家的人用自己的数据。怎么落地见第十节。
8. **三个应用相互独立**（10-23）：knowlab 只管孵化与测试，数据不从 knowbench、knowmart 拿；交 knowmart 走跨应用契约。

## 三、叫法

| 叫法 | 是什么 | 编号 | 代码里（不改名） |
| --- | --- | --- | --- |
| **创意** | 用户申请交来的方法（六问或 skill）、验收用例、测试同意 | 版本号 v1、v2…；改一次加一 | `knowbot_request`（加版本表，第九节） |
| **受理单** | 受理的输出：受理 / 不受理与理由 | 不单独编号：「创意 v2 的受理」 | 新表 |
| **准专家** | 照某一版创意孵化出来、还没测或没测过的那一份（清单） | 版本号 1.1、1.2…（「1」是它要冲的专家第几版，所有者 10-23 定保留） | `knowbot_draft` |
| **测试** | 拿一个准专家按用例跑一次 | 编号，同一个名称里只增：「测试 5（准专家 1.3）」 | 新表 |
| **专家** | 测试通过的那一版；**通过即是专家** | 版本号：第 1 版、第 2 版…，测试通过时定 | 新表；交 knowmart 后是 `knowbot` |
| **交回记录** | 交回的输出：何时通知用户、用户要没要（用户同意门） | 跟着那一版专家 | 专家表上的字段 |
| **运营审核** | 上架前我们这道门的结论：通过 / 不通过与理由；通过的定自用，或发布主体有资质的定公开 | 跟着那一版专家 | 专家表上的字段 |

- 没通过的准专家永远是准专家，收在历史里。
- 专家版本号在测试通过时定；这一版用户不要、或审核没过，就不上架，所以 knowmart 里上架的版本号可能有空号（第一个上架的是第 2 版），详情页写明空号那一版的结局。
- 界面不写「我的专家」「我的准专家」；栏目就叫「专家」。
- **「分身」不再用**：2026-10-19 至 10-22 文档与界面里的「分身」就是今天的准专家；活文档改到哪份换哪份，历史记录与原话不改。
- **补充方法（0035）取消**：以后改方法就是改创意、出新版本；规则出处指到「创意第几版的哪一句」。已有的补充（sig-am `e6df96db…`）与引它的准专家 1.3 留作历史，出处照旧可查，接口只读、不再新建。
- 代码、表名、接口路径不改名（`knowbot_request`、`knowbot_draft`）；新加的页面路径用新叫法。

## 四、生命周期：过程、输入、输出

| 过程 | 在哪端、谁做 | 输入（在过程里选） | 输出（右边栏） |
| --- | --- | --- | --- |
| **申请** | web端，用户 | 用户写的 | 创意 vN |
| **受理** | 管理端，我们 | 选创意的某一版 | 受理单 |
| **孵化** | 管理端写清单；web端「审核」里用户审核、回答 | 选受理了的创意版本 | 准专家 x.y |
| **测试** | 管理端发起，平台跑 | 选核过出处的准专家 | 测试 N：通过 / 没通过 / 平台出错、报告、成稿与各步交回物；**通过即出专家第 n 版** |
| **交回** | 管理端发起，用户在 web端看到并作答 | 选一版专家 | 交回记录（含**用户同意门**的结论） |
| **上架** | 管理端 | 选用户同意了的那一版专家 | 运营审核（**运营审核门**）→ 交 knowmart，自用或公开（要资质） |

- **来龙去脉自动有**：专家第 1 版 ← 测试 5 ← 准专家 1.3 ← 创意 v2，每一环都是在过程里选的。
- **选的约束**：孵化只能选受理了的创意版本；测试只能选核过出处的准专家；交回只能选专家；上架只能选用户同意了的；默认选中最新的。
- **选中的输入，内容在过程页中间完整显示**（孵化时读得到创意原文，测试时看得到准专家的规则出处），它是这个过程的一部分，不是右边栏的东西。
- **平台出错就重测同一个准专家**（「测试 6（准专家 1.3）」）；专家自己没做对，才再孵化出新准专家。原来的「超时退回待测试」改成：这次测试记「平台出错（超时）」结束，再发起一次就是新编号。
- 同一个名称同时只能有一个测试在跑（沿用现在的规矩）；用户可以随时改创意出新版本，不影响正在跑的那次。
- 创意出新版本时，测试数据说明的文字没变就沿用上一版的同意，变了才要用户重新同意。
- **受理改人工**，查三样（所有者 10-23 按拟的）：是不是投资建议类（`C-L5` 不做的不受理）；用户声明的测试数据有没有权用（`C-L2`）；归不归这类专家能做的范围（`C-L1`：方法只来自用户）。不受理写明理由，用户改创意出新版本再受理。

## 五、上架前两道门

| 门 | 谁 | 在哪 | 结论 |
| --- | --- | --- | --- |
| 用户同意门 | 用户 | web端「审核」里一条待办，点进去是那版专家：看成稿、测试结果 | 要这一版 / 不要 |
| 运营审核门 | 管理端的人：admin、operator 现在都能审（所有者 10-23，见决定记录） | 管理端「交付」 | 通过（定自用，或有资质的定公开）/ 不通过与理由 |

- 顺序：**先用户、后运营**（用户不要的不白审）。
- 自用也过运营审核，只是审得轻：核成稿没有目标价、评级类内容（`C-L5`），核受理单与测试结果对得上。公开要发布主体有资质（第十二节）。
- 两道都过才上架：交 knowmart、能在工作台请。
- 以后需要时，运营审核独立成单独的审核角色（所有者「以后有需要独立出来」）。
- knowlab 后端 `b7b7edb`（用户点了就交）改成：用户点了只过第一道，运营审过才交。账 144：`accepted_at` 等新字段随两个前端一起上，不单独发后端。

## 六、各种结局

没有退回，每个结局都是一个定了的结果；下一步从哪接着，写在结果旁边。

| 在哪 | 结局 | 下一步 |
| --- | --- | --- |
| 受理 | 不受理（附理由） | 用户改创意出新版本，再受理 |
| 测试 | 没通过（第几步、原因） | 再孵化出新准专家；或用户改创意 |
| 测试 | 平台出错（含超时） | 重测同一个准专家，新编号 |
| 用户同意门 | 用户不要 | 这版专家不上架；用户改创意，或等下一位准专家 |
| 运营审核门 | 不通过（附理由） | 这版专家不上架；按理由改创意或再孵化 |
| 上架后 | 停用（用户或我们） | 看记录；可以上架新版本 |

**左边栏（都是过程）**：受理 · 孵化 · 测试 · 交付（交回和上架）。「CRUD 参考」「富能力参考」「设置」不动。

| 栏 | 中间：大类 + 列表 | 进到过程里做什么 | 右边栏（输出） |
| --- | --- | --- | --- |
| 受理 | 待受理 / 已受理 / 不受理 | 选创意版本，看三样、写受理单 | 受理单 |
| 孵化 | 待孵化 / 孵化中（等用户审核、回答）/ 已孵出 | 选受理了的创意版本；写清单、校验；核出处 | 准专家 |
| 测试 | 待发起 / 排队 / 进行中 / 等用户答 / 已结束（通过、没通过、平台出错） | 选核过出处的准专家；预算、超时、发起；刷新、补取产出 | 测试结果、成稿与各步交回物；通过的专家 |
| 交付 | 待交回 / 等用户同意 / 待运营审核 / 已上架 / 没上架（用户不要、审核不过）/ **全部专家** | 交回：选专家、通知用户；上架：运营审核，交 knowmart，失败可重试；全部专家：停用（第八节） | 交回记录、运营审核结论、上架记录 |

- 左边栏旁的数：每栏数「等我们」的条数。
- **全部专家**（待定第 3 项，所有者 10-23「直接全做了」）：放在「交付」栏的一个大类里，不另占左边栏（左边栏都是过程）。列出每个名称的每一版专家：版本号、出自哪次测试、两道门的结论、上架没有、停用没有；能停用（写理由），停用经 knowmart 新接口（第九节第 6 条）。
- 角色：admin、operator 现在能做的一样（决定记录 10-23）；按钮不按角色藏。

## 八、knowlab web端

**左边栏（按用户的事排）**：申请 · 审核 · 专家。

| 栏 | 是什么 | 中间：大类 + 列表 | 右边栏 |
| --- | --- | --- | --- |
| 申请 | 过程：提交、修改创意（改一次出一个新版本） | 在做 / 已出专家 / 没受理 | 创意（各版本） |
| 审核 | **用户的待办箱**：孵化、测试、交回里所有要用户做的事——审核孵化、回答问题（含测试中冒出的问题）、用户同意门 | 等你回答 / 等你审核 / 等你决定要不要这一版 | 用户答过、定过的记录 |
| 专家 | 成品（唯一不是过程的一栏） | 新交回 / 你已同意，等我们审核 / 能用 / 停用了 / 没上架 | 各版专家 |

- 左边栏旁的数：审核数「要你做的」；专家数「新交回」。
- 让用户知道有新专家：web端首页顶上一条「你的创意『…』测试通过了，去确认」，直达审核里那条；消息、邮件以后再接。
- 用户看的结果用白话：成稿在最前，各步交回物收在下面；平台出错写「这次是平台出了错，不是你方法的问题，我们会重测」。
- 平台的错、规则名、run、case id 这类内部字段不给用户看。
- 「我的数据」（测试用的数据，现在在 web端上传、管理）照旧：它就是 knowlab 知识库里给测试绑的数据（10-23「knowlab 有自己的知识库」）；页面叫法本期不改，等知识库的页面一起定。
- 专家停用：用户在「专家」栏那一版上点停用（knowmart 已有 `POST /web/v1/knowbots/{id}/versions/{v}/stop`，经 knowlab 后端转调或跳 knowmart 页面，实施时按跨应用现有做法选）。

## 附一、成稿与交回物带回测试结果（2026-10-19 那一版第五节，仍有效）

> 原文照录；文中「分身」即今天的准专家，「这个分身交付、或被下一个分身取代后 90 天」照旧按准专家算。

### 1. 谁、什么时候取

| 谁 | 做什么 |
| --- | --- |
| knowbench（测试推进器） | **每条用例跑完、记结果的那一刻**（`KnowbotTestConductor._record`，下一条用例开跑前、整次测试收尾删目录前）取这条用例的产出，存进 `workbench_test_cases.outputs` |
| knowbench 接口 | `GET /internal/v1/knowbot-runtime/test-runs/{run_id}/cases/{case_id}/outputs`（服务身份 `knowbench:testrun`，同现有测试接口） |
| knowlab | 刷新测试结果时，看到某条用例已有结论、本地还没存它的产出，就取一次，存进新表；以后不再取 |

成稿在 `_record` 时取：每条用例的底稿写在自己那一格（`底稿/对话-<编号>/<开始时间>-<专家名>/`，advisor 的 `run_folder`），不会被下一条盖掉；但隔离打开后整次测完目录就删，晚了取不到。

### 2. 取什么

每条用例一份：

```text
{case_id,
 deliverable: {path, text, truncated} | null,   成稿（第 8 步写的 Markdown）
 deliverable_note: 为什么没有成稿 | null,
 steps: [{step_id, title, outcome: accepted | rejected | not_reached,
          artifact: 交回物 JSON | null,          通过的那一版
          returned_raw: 没过那次的交回原文 | null, 只有 rejected 才有
          checks: [{label, pass, detail}] }]}    验收逐条（管理端看；web 只用 pass 与白话原因）
```

- **成稿**：只读这条用例验收时记下了 `workspace_path` 的那份，经会合点请测试电脑上的代理 `fs/readFile` 读；**文件修改时间早于这条用例开始的不认**。没写、没走到那步、读失败都不读，`deliverable_note` 写原因。成稿带 `step_id`；超时收尾时取的，`deliverable_note` 写「超时收尾时取的，可能没写完」。
- **交回物**：从工作台的步骤视图（`ExpertDesk.steps(full=True)`）取每步最后一次尝试：通过的取那一版交回物；没过的取最后一次交回的内容与原文；没走到的记 `not_reached`。
- **上限**：成稿 20 万字（超了截断、`truncated: true`）；每步交回物序列化后 20 万字节，超了不带、注明原来多大；没过的原文 2 万字；一条用例的产出合计不超过 2 MB（留 64 KB 余量）。合计超了一级一级让，每级只走一遍：拿掉最大的几步交回物 → 原文截到 2000 字 → 拿掉原文 → 只留没过的验收 → 成稿截到 2 万字 → 拿掉成稿 → 只留各步结局。测试电脑上读文件的单次上限是 512 KiB，成稿超过就记「成稿太大没取」。
- 取产出出错**不影响**这条用例的结论：结果照记，`outputs` 记 `{error: …}`（白话，不带异常类名）。

### 3. 契约：`knowbot-test-run/v1` 只加不改

- 加一个接口与结果模式 `test-run-case-outputs.schema.json`，真源在 knowlab 的 pydantic（`domain/knowbots/test_run.py`，同 `RunResultV1`），由模型生成，knowbench 的锁 `contracts/knowlab-test-run-lock.json` 跟着更新。
- 现有 `RunResultV1`、`/test-runs/{id}` 一个字段不动；产出每条用例只取一次。
- knowlab 取产出：运行方自己的 404 记「没有产出」；路由不存在的 404 与不可达一样当暂时取不到，这一轮就停；回包不合契约、答错用例是确定的错，记下原因不再取。一次刷新最多取 10 条；测完的在管理端「补取产出」再取。

### 4. 存在哪、留多久

| 哪里 | 存什么 | 留多久 |
| --- | --- | --- |
| knowbench `workbench_test_cases.outputs` | 第 2 节那一份 | 整次测试收尾后 **30 天**清空这一列 |
| knowlab `knowbot_test_output` | `draft_id`、`run_id`、`case_id`（主键）、`fetched_at`、成稿、各步 JSON | 准专家**上架、或被下一个准专家取代后 90 天**清掉正文、留一句原因 |

### 5. 谁看得到

| --- | --- |
| 管理端的人（admin、operator） | 所有准专家的成稿与交回物；每次读记一行日志：谁、哪一版、何时，不记正文 |
| 用户（knowlab web端） | 只有自己创意的 |
| knowbench web 端的测试账号 | 不经页面看 |

## 附二、合规（2026-10-19 那一版第六节，仍有效）

- **同意版本**：创意记下用户同意的是第几版测试数据说明（`consent_version`）。第 1 版是「测试产出不给任何人看，7 天后删除」；第 2 版是「只给本人和做测试的工作人员看，不拿去训练、不给别的用户、不作别的用途，上架或被取代后 90 天清掉」。低于第 2 版的不取、不显示产出，用户点「同意新说明」才升到 2。本期起同意版本记在创意版本上（第十节第 1 条）。
- 0027「结果」那一行改为：「回每条用例的成稿与各步交回物：管理端看来验证这一版，用户看来作验收依据（`C-L3`）」。
- 守住的边界：成稿与交回物只用于验证与验收，不拿去训练、宣传或给别的用户；测试结果里没有收益、胜率、评级类字段（`C-L5`）；成稿不许写目标价、评级（第 8 步的验收守着）。
- `C-L3` 不用改；`C-L4` 已于 10-20 改为默认自用、公开按资质。
