## 二、knowbase 的数据模型

只写要有什么、有什么规矩，表名列名实现时按现有命名定。

### 2.1 资料、版本、内容来源与取得依据

- **资料**：逻辑上的一份；挂描述、许可档、所有者、状态（正常、逻辑删、禁用）。
- **版本**：一份内容（sha256、大小、内容类型、对象键）；只增不改。
- **内容来源**挂在资料与版本上：公开披露、为某用户采集、用户上传、产出转来；加上派生关系（原件 → 正文、按页文字、表格、检索索引）。
- **取得依据**挂在用户与资料的关系上：上传、采集、购买、确认引用、产出。同一份内容，卖家是「我上传的」，买家是「买来的」；总栏按当前用户的取得依据分类（评审 L2-10）。
- 上传同名同描述的新内容：用户选「作为新版本」或「另一份资料」，默认另一份。

### 2.2 使用权

- 所有者天然有；买家凭交易有，**只到交易那一版**；公开原件的使用权就是第二区引用。
- 带：取得依据、适用版本、许可档、有效条件（违规下架收回；买家注销即终止，内容不清除）。
- 交易幂等：同一交易编号只建一条有效使用权；成交以使用权建好为准，失败可重试。
- 空间：资料算所有者的，直到最后一条别人的使用权失效；第二区引用不算空间。

### 2.3 展示即同意

- 同意依据加用途表达展示：`app:knowbench`、`app:knowlab`（在这个应用的栏出现、可解析、可读）；`market`（交给 knowmart 待上架）；`expert:<专家>`（绑给名下这位专家，交付时冻结成 `expert:<专家>@<版本>`，第 4.4 节）；`platform:<应用>:<过程>`（平台孵化、平台测试、交付审核、自助重跑）；`app:knowfeed`（平台账号的资料给 knowfeed 质检用，平台也是用户）。
- 同意依据只能由用户本人留下：在 knowbase web端点，或在应用页面由应用后端凭本人令牌转交。
- 「展示给 knowbench」同时覆盖委托与会话（会话的范围宽得多），页面写明。
- **默认展示**：账号级「新数据默认展示给我的全部应用」开关默认开，只对「我上传的」「为我采集的」生效；买来的、产出转来的由用户点。用户第一次进 knowbase web端时把这个开关亮出来、点一下「知道了 / 改」，这一下就是依据。迁移来的旧资料照原范围，不套默认。
- 现有同意依据表的 `app` 列退役，含义并进用途。

### 2.4 公开原件层与第二区引用

- 公开原件层建在 knowbase 现有知识文档（`knowledge_document`、`knowledge_document_version`）上，原件版本与派生版本只存一份。
- **第二区引用**：用户名下对某个原件的一条引用，记出自哪件任务、哪条声明、哪次确认；状态：已确认等采、可用、采集失败、已取消、已撤回，失败、取消、撤回的也留着。没有可用的引用就读不到。
- 公开原件许可档由系统定为「可以经专家给别人用」，不能当知识出售。

### 2.5 描述与词表

- 描述：主体（证券代码、巨潮机构编号、词表主体编号）、类型（封闭枚举）、报告期间、**披露时间**、格式；三个时间分开：报告期间、源站披露时间、平台获取时间。
- 词表归 knowbase、有版本号；声明契约引用同一份词表。
- 确认状态：入库质检过、用户确认过、自动识别未确认；只有前两种参与解析。迁移来的未确认描述，用户首次进入时引导确认。
- 描述改动留记录，不产生新的内容版本。

### 2.6 产出区

- 内容来源多一种：产出；产出区的资料不参与解析。
- **服务写入路**：应用后端（knowbench runner、knowlab）以服务身份替用户写产出，只能写进产出区：调用方应用、受益用户、任务或测试编号、运行编号，按（任务，运行编号）幂等，算进用户空间。测试证据只增不改。
- 自助测试证据的链路：用户 link →（设备令牌）knowbench 后端 →（knowbench 服务身份）knowbase 产出区；自报的不作数，靠过门时平台重跑核。
- 「转为数据」：用户在 knowbase web端点，新建一份资料（内容来源 = 产出转来，带出处），许可档默认「只许本人用」，上游受限的不得升档。

### 2.7 运行授权

| 改动 | 做法 |
| --- | --- |
| 授权项逐项记依据与所有者 | 一份授权可以有多项，每项记：钉住的输入组合（第 2.9 节）、权利依据（展示同意 / 使用权 / 冻结的绑定同意 / 第二区引用）、内容所有者；外层记过程与执行主体。knowbase 签发时逐项核，取代现在「`item.owner == grant.owner`」。一件委托可以同时读请的人的、买来的（卖家所有）、作者绑定的三种（评审 L2-02） |
| 受益人 | 专家绑定的数据：所有者是作者，受益人是请专家的人，依据是冻结的 `expert:<专家>@<版本>`；留痕两人都记 |
| 平台过程 | 由用户本人留下 `platform:` 同意依据；读的一方分运营（人）与机器（测试电脑），授权与留痕分开记；上限按过程配（拟：孵化 7 天、测试 14 天、交付审核 30 天）；过程结束、撤回、不受理立即撤 |
| 自助重跑 | 用户「提交交付」时同时记两种范围：机器重跑要读的冻结输入（测试集与绑定），审核员能看的清单与结果；重跑建新运行编号、申请新的机器授权，记明复核哪次自助测试；不复活旧授权，审核员不能凭机器授权看原始输入（L2-01） |
| 会话 | 每首读一份签一条小授权（一份一条），会话结束一并撤，不改授权模型（「范围只能更小」照旧）；单段会话累计读到 50 份时在界面提示一次，不挡 |
| 签的时机 | 解析阶段不签；开跑时签，与钉住同时完成 |
| 时限 | 测试、委托 7 天，会话 24 小时，孵化 6 小时照旧 |

`RECEIVING_APPS`、`GRANT_PARTITION` 随分区一起退役，买来的落到哪由展示决定。

### 2.8 删除、撤权、清除

| 动作 | 做法 |
| --- | --- |
| 从栏里拿掉、取消展示 | 撤对应用途的同意依据：停新的解析和授权申请；已签的到期或任务结束为止。取消「绑给专家」只影响下一版，已冻结的不撤 |
| 作者删、卖家下架 | 资料标逻辑删：所有者栏里不显示、不解析；买家使用权、钉住的测试与专家版本照旧可读 |
| 撤回平台过程授权 | 撤同意依据并立即撤这次过程的全部授权 |
| 禁用、许可失效、许可改低、违规下架 | 资料标禁用或改档：停一切新读取，在跑的授权也撤；在售专家转「待处理」并通知作者；知识条目下架；违规下架收回买家使用权；改低时买家已有使用权不动 |
| 注销、依法删除个人信息 | 真删内容（含产出区、描述字段、RAGFlow 里的切段），按保留规则留编号级留痕；卖家注销买家不受影响、卖家名匿名；内容属于必须删的个人信息且已卖出的，通知、补偿买家 |

- 现在的 `delete` 是删对象；改成逻辑删要迁移代码路径。
- 测试证据拆两半：结论、数值、判定理由留；引用的原始内容随依法清除一起清，复现不了判「证据不可复现」。

### 2.9 钉住的输入组合

运行输入引用一个不可变组合：**原件版本、派生（读法）版本、各自摘要**。清单 v2 的绑定、测试集、授权项、格子地址、数值验收都引用同一组合；抽表器修正数字产生新派生版本，旧测试照旧读旧组合，不会悄悄串换（评审 L2-07）。

## 三、按描述查与解析

### 3.1 声明契约：`knowbot-manifest/v2`

| 层 | 谁写 | 内容 |
| --- | --- | --- |
| 声明模板 | 作者在 knowlab | key、名字、说明；类型；期间规则（固定期间，或「最近 N 个完整年度 / 季度」，可加「截至任务日期已披露」）；格式；份数上下限；必填或可选；来源限制；表格类的表与列；口径；多候选时的优先策略 |
| 任务参数 | 请专家的人发起任务时 | 主体（一家或几家）；必要时覆盖期间 |
| 绑定 | 作者 | 资料加输入组合，随专家版本冻结、进版本摘要 |

- 声明结构与词表的定义只放一处（knowbase 管的跨应用契约），三个应用现在逐字段相同的 `DataNeed` 收成一份。
- **v1 专家的兼容分支**（L2-08）：v1 声明认不出主体与期间，解析造不出候选；过渡期给 v1 单独一条路：在请的人有权用的云端范围里，按旧声明由他明确绑定，随后照新的组合与授权检查；不自动补采，不恢复本地来源。只对 v1，到「财务分析与预测」第 2 版上架为止。

### 3.2 按描述查与解析

- **按描述查**：只接受精确的键，只回答这一份在不在、在哪个范围里；不开列表、浏览、模糊搜公开原件层的接口；同一用户短时间大量不同描述的查询限流。
- **解析**：输入声明模板、任务参数、使用者、请的人；输出解析清单（全局唯一编号，存 knowbase）。每样一个结果：

| 结果 | 应用怎么办 |
| --- | --- |
| 已定（某个输入组合） | 照用 |
| 你有没放开（只对本人的数据提示） | 请他到 knowbase 放开 |
| 待确认（不分平台已有还是要新取，评审 F 2.1） | 进确认清单 |
| 采不来（私有资料） | 告诉他去 knowbase 上传（直达链接） |
| 有歧义 | 开跑前请他选 |
| 等数据（knowbase 部分不可用、正在导入） | 不补采，任务等或报错 |
| 不能用（禁用、许可不允许） | 照实告诉他 |

- 解析时公开原件优先于上传；有偏好时偏好优先。「最新」只在声明允许时用，按「截至什么时候能拿到」算。
- 解析清单固定所用描述与词表的修订、时间口径；运行中冒出的新需求形成清单的新修订，不覆盖冻结的部分。

### 3.3 确认一次

1. 应用先对待确认的那几项向 knowfeed 预切合（0045 第四节），拿到能不能满足、保守的预计时间、许可档；满足不了的直接标出。
2. 把清单列给用户：总数、预计多久（按全部要新取算）、每项的许可档；用户可以取消部分条目（可选的取消即降级，必填的取消即变更需求）。
3. 用户点一次，应用后端凭本人令牌交给 knowbase，knowbase 记一条确认（清单修订、任务、声明快照、确认的条目），回确认编号；确认 7 天内有效、只对这张清单修订的条目有效。已有原件的立即记引用；要新取的记引用（状态已确认等采），由应用后端连同确认编号把需求单交 knowfeed；knowfeed 受理前向 knowbase 核这个确认编号。
4. **确认不能被跳过**：账号设置、应用默认、模型调用都不能免确认；偏好只记选哪份，不记免确认（评审 F 3.6）。

### 3.4 等数据与恢复

- 任务进「等数据」，带清单编号；进度由应用后端查 knowfeed 的需求单状态。
- **需求状态只由 knowfeed 通知**（采集讨论记录第 9 条）：knowfeed 交 knowbase 拿到回执后，把需求依据标「已就绪」或「部分就绪」，经发件箱通知提需求的应用；knowbase 只给 knowfeed 回执，把对应引用改成可用。应用重新解析这件任务的清单，齐了就恢复；恢复时另核当前状态与清单修订，重复或乱序的通知不重复开跑。
- 供给完成的判据：原件已由 knowbase 接管、版本能定位、权限能校验、要的读法已就绪。
- 超时转用户看得见的失败，已定的部分留着；超时后到的数据留在用户栏里，不自动重启任务。

### 3.5 开跑前列出、可换、偏好

- 开跑前列出解析清单（每样用哪份、哪一版、为什么），默认直接跑，用户可以换，有歧义的必须选。
- 换过的记成偏好：**用户 × 使用者 × 声明契约版本 × 需求 key × 规范化的任务参数** → 资料与版本策略，存 knowbase；只是排序输入，每次仍核当前权利；词表改版、资料不可用时失效（评审 L2-03、Q 3.3）。
- knowbench「同一项目上次请这位专家用的那几份」改作偏好的来源。

### 3.6 开跑、钉住、校验

- 开跑时凭清单申请运行授权，与钉住同时完成；跨服务沿用幂等与失败交还。
- 钉住层复用 knowbench `workbench_task_data`（槽位、输入组合、摘要、授权编号、格子地址）；接口不再收本地来源，数据库仍容纳历史本地记录。
- 按声明核格式、份数、表头列、同一份不用两次（现在的 `choice_problems`）原样保留，用来核机器挑的结果。
- 必填缺了不算成功；可选缺了照做、记「不完整」；模型不能自己改声明。

## 四、各应用怎么改

### 4.1 knowbench

- **删**：选数据弹框、`data_choice` 与本地来源；「云端知识库」页的上传入口（页面只展示 `app:knowbench` 的，标「在 knowbase 管理」）；会话逐份选的入口。
- **请专家**：填任务参数 → 解析 → 预切合 → 确认清单 → 等数据 → 开跑前列出（可换）→ 开跑；委托单记清单编号、确认编号。
- **会话**：范围 = 展示给 knowbench 的加用户名下可用的公开原件引用；首读一份签一条小授权并钉组合；每轮说明列出读过哪几份；要一份他名下还没有的公开披露，同样预切合、确认。
- **本地 link 0.5.4 只删不加**：删本地知识库目录设置、服务流对它的只读范围、Windows 桌面界面那一栏，老配置读了忽略；项目目录的读写由现有白名单目录管，照旧。`source='local'` 的老委托只读，界面只写「本地来源已退役」，不显示路径。

### 4.2 knowlab

- **知识库页**只展示 `app:knowlab` 的。
- **测试集**：**主体一律由作者给**（评审 E3），解析器只按声明展开类型、期间、口径；公开披露的版本候选来自 knowfeed 的公开索引（只回「这家公司有哪些报告」，不开「列公司」）；作者确认（对公开披露同时是第 3.3 节的确认）后钉在草稿上，钉组合、不跟新版。测试集有自己的版本号；**每次测试记测试集版本**，同一测试集版本的结果才直接比。声明变了，「绑定过期」提示重新生成。
- **自助与平台**（孵化、测试各自选）：

| | 自助 | 平台 |
| --- | --- | --- |

- 选自助时页面照实写明（评审 E4）：「平台的人看不到你的数据；过门时平台的测试电脑会为审核重跑一次，没人看数据，产出只进你的产出区」。平台的同意文本写明运营的清单、受理意见可能引用数据片段。
- 每个准专家版本、每次测试记下模式。0042 的「整栏测试同意」退役，迁移时改成 `app:knowlab`。
- **交付**：交出去的是清单 v2，绑定的数据留在 knowbase；用户交审时由本人留下 `platform:knowlab:<交付过程>`（审核员看清单与证据）；审完即撤。交付以后：请专家的人用自己的数据（经解析），绑定的数据按受益人授权读；绑定数据失效在售版本转「待处理」；改绑定出新一版、重新交付，买家那一版不变。

### 4.3 knowmart

- **改成每个用户一家小店**（0018 第十一节第 7 之二小节）：首页是小店列表、点进去是小店详情页；「我发布的」「知识库」「发布主体与资质」并进「我的小店」；「我买到的」拆掉：知识在 knowbase 总栏「买来的」，请过的专家在 knowbench，订单记录留在小店「交易记录」。
- **我的知识**（原 D 知识库页）没有上传；卖家在 knowbase 把资料展示给 `market`，资料进「待上架」（状态归 knowmart），填介绍、样张、价格、驻场规则后上架。
- **成交**：记订单后请 knowbase 给买家建使用权（交易那一版），不复制；`purchase-copy` 留给历史。
- **两种许可检查**（评审 L2-04）：专家**交付到本人自用**，绑了「只许本人用」的也可以；**公开供别人用**，所绑每份要「可以经专家给别人用」，有「只许本人用」的拒；自用转公开时重查。知识上架要「可以出售」，公开原件与平台抽的表一律拒。knowlab 运营审核门预查，knowmart 收清单时硬查。
- 买来的继承卖家的转卖设置，不得升档；`no_resale` 限的是上架、交给 knowmart、绑给公开专家，不限下载。
- 违规下架收回买家使用权；卖家注销时卖家名匿名。

### 4.4 专家绑定数据

- 作者在 knowbase 总栏对资料点「绑给专家」→ `expert:<专家>`；**绑定关系存 knowbase**。名下专家的名录由 knowlab 在建版本时经发件箱推给 knowbase（编号、名字、版本、作者），knowbase 存只读影子表，绑定时只认推来的（评审 F 3.8、Q 2.1）。
- 交付时冻结成 `expert:<专家>@<版本>`，随清单 v2 进版本摘要；总栏按钮只管下一版还绑不绑（评审 F 2.2）。
- 绑公开原件时绑引用；别人请这位专家时，按他的任务在他名下记引用（确认清单里一并列出），按他自己的第二区读。
- 承诺只到「没有浏览、下载入口，产出里可能引用」，绑定时页面照实写明。
- 解绑、下架的历史留痕。

## 五、存储

按描述分类、按读法分表（采集讨论记录第 11 条）：

| 放哪 | 放什么 |
| --- | --- |
| 对象存储 | 原件，按摘要存 |
| knowbase PostgreSQL：目录与权利 | 资料、版本、描述、词表、使用权、展示、引用、授权、留痕、解析清单、偏好、专家名录影子表 |
| knowbase PostgreSQL：正文 | 每个版本一行：标题、发布日期、正文 |
| knowbase PostgreSQL：按页文字 | 每个版本每页一行 |
| knowbase PostgreSQL：表格单元 | 每格一行：版本、哪张表、行（科目标准名）、列（期间）、值、单位、口径、页码、质检标记 |
| RAGFlow（由 knowbase 管） | 切段、向量、混合检索 |

**RAGFlow 四条规矩**：
1. knowbase 是真源，RAGFlow 只是派生索引：一个 RAGFlow 文档对应一个 knowbase 派生版本，只增不改；丢了从原件重建。
2. 检索一律经 knowbase：先核授权，只把钉住的那几版对应的文档编号交给 RAGFlow；应用不直接碰 RAGFlow。
3. 删除与清除经发件箱同步到 RAGFlow，拿到回执才算删完。
4. 结构化的留在 PostgreSQL：表格单元、描述、权利不进 RAGFlow。

不按类别建表；类别靠描述字段与索引分，新加类型不改表结构。向量模型随 RAGFlow 配置，实施时拿真实数据比过再定。

## 八、怎么验

除每块的单测与契约锁外，两条端到端真跑：

1. **sig-am 自助孵化「财务分析与预测」第 2 版**：作者给主体、生成测试集、预切合、确认一次、等数据、开跑前列出、自助测试证据进产出区、提交交付、平台重跑、留痕可查、产出转为数据。
2. **knowmart**：上架一份知识、另一账号买、使用权可读、卖家下架后仍可读、违规下架后不可读。

反例（评审 L 末节）：不同用户的偏好不串；三个所有者的输入能在一件委托里合法共用，换成卖家另一份、作者另一版未绑定的被拒；取消一条需求不取消别人的；迟到事件不复活任务；原件已有但缺表能补加工；更正版不会被旧命中吞掉；自用专家能交付但不能绕过公开许可；删过的资料迁移后仍不可读；抽表新版不改变旧测试；取消「绑给专家」不坏已售版本。
