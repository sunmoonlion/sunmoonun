## 二、knowbase 的数据模型

只写要有什么、有什么规矩，表名和列名到实现时按现有命名定。迁移原则见第五节。

### 2.1 资料与版本

- **资料**：逻辑上的一份。挂描述、许可档、所有者、逻辑删状态、展示和使用权。
- **版本**：一份内容（sha256、大小、内容类型、对象键）。挂钉住、留痕、派生关系（原件 → 抽表、检索索引）。版本只增不改。
- 上传同名同描述的新内容：用户选「作为新版本」或「另一份资料」；默认另一份。
- 现有 `user_data_item` 一行迁成一份资料加它的第 1 版。

### 2.2 使用权

- 一份资料对谁可用，由使用权决定：所有者天然有；买家凭交易有，**指向交易那一版**；公开原件的使用权就是第二区引用（第 2.4 节）。
- 使用权带：依据（上传、采集、购买、产出）、适用版本（全部版本或某一版）、许可档、有效条件（违规下架收回）。
- 交易幂等：同一个交易编号只建一条有效使用权（照现在 `purchase` 按交易编号幂等的做法）。成交以使用权建好为准，失败可以重试。
- 空间：资料算所有者的空间，直到最后一条别人的使用权失效。

### 2.3 展示即同意

- 用现有的同意依据表达展示，用途写成：
  - `app:knowbench`、`app:knowlab`：在这个应用的知识库栏出现，这个应用可以解析、读；
  - `market`：卖家把它交给 knowmart 待上架；
  - `expert:<专家编号>`：绑给名下这位专家（第 4.4 节）；
  - `platform:<应用>:<过程编号>`：平台模式里给平台这一次过程用（第 4.2 节）。
- 同意依据只能由用户本人留下：在 knowbase web端点（0044），或在应用页面上由应用后端凭令牌交换后的本人令牌转交。光有服务身份不算。
- 「展示给 knowbench」对 knowbench 的委托、会话都算数；「展示给 knowlab」对 knowlab 自助孵化、自助测试算数。
- 账号级「新数据默认展示给我的全部应用」开关默认开：开着时，新资料自动建 `app:knowbench`、`app:knowlab` 两条（所有者本人的设置动作就是依据）。
- 现有同意依据表里的 `app` 列退役，含义并进用途。

### 2.4 公开原件层与第二区引用

- 公开原件层建在 knowbase 现有知识文档（`knowledge_document`、`knowledge_document_version`）上，原件版本与派生版本都在这里，只存一份；去重与读回核摘要按 knowfeed `IngestionStore` 的语义（0045）。
- **第二区引用**：一条记录 = 某个用户名下对某个原件（及其派生版本）的引用。带：
  - 出自哪件任务（应用、任务或草稿编号）、按哪条声明匹配到；
  - 依据哪次确认（第 3.3 节的确认编号）；
  - 状态：已确认等采、可用、采集失败、已撤回。失败和撤回的也留着。
- 读公开原件一律要有一条可用的引用，没有就当不存在。
- 公开原件的许可档由系统定为「可以经专家给别人用」；不能当知识上架出售（数据拓扑第 7.3 节）。

### 2.5 描述与词表

- 每份资料带描述：主体（证券代码、巨潮机构编号）、类型（封闭枚举）、期间（日期区间）、格式；外加从哪来、许可档、需求来源（多值：用户、应用、任务或草稿）。
- **词表归 knowbase**，带版本号。声明契约（第 3.1 节）引用同一份词表；词表改版时，旧声明能查出「用的是旧词」。
- **确认状态**：入库质检过（knowfeed 采来的）、用户确认过（上传时用户填或确认自动识别结果）、自动识别未确认。只有前两种参与解析。
- 描述改动留记录，不产生新的内容版本。

### 2.6 产出区

- 资料的「从哪来」多一种：产出。产出区的资料不参与解析。
- 云端干的活（平台测试电脑上跑的）产出进这里，归用户；knowlab 测试证据也进这里，钉在测试编号上，只增不改。
- 「转为数据」：用户在 knowbase web端点，新建一份资料（从哪来 = 产出转来、带出处：哪位专家哪一版、哪件任务、用了哪几份数据的哪几版），许可档默认「只许本人用」，上游受限的不得升档。

### 2.7 运行授权

在现有四种（测试、委托、会话、孵化）上改：

| 改动 | 做法 |
| --- | --- |
| 授权项指向版本 | 授权里每一项钉到资料的某一版（现在钉的是条目加 sha256，迁移后一一对上） |
| 范围来自展示 | 委托、会话的授权只能落在 `app:knowbench` 的同意依据里；测试落在 `app:knowlab`（自助）或 `platform:knowlab:<过程>`（平台）里；公开原件落在用户名下的可用引用里 |
| 受益人不是所有者 | 授权多记一个受益人：专家绑定的数据，所有者是作者，受益人是请专家的人；依据是 `expert:<专家编号>` 的同意依据。留痕两人都记 |
| 加一种：平台过程 | 用户选平台孵化、平台测试时，由他本人留下 `platform:` 同意依据；knowlab 凭它申请。读的一方分两种主体：运营（人，经 knowlab 管理端）、机器（测试电脑），授权与留痕分开记 |
| 签的时机 | 解析阶段不签；开跑时签，并和钉住同时完成 |
| 时限 | 测试、委托 7 天，会话 24 小时，孵化 6 小时照旧；平台过程按过程，最长 7 天，过程结束、用户撤回、不受理时立即撤 |

`RECEIVING_APPS`、`GRANT_PARTITION`（授权种类对应哪个分区）随分区一起退役。

### 2.8 删除、撤权、清除

| 动作 | 做法 |
| --- | --- |
| 从栏里拿掉、取消展示 | 撤对应用途的同意依据：停新的解析和授权申请；已签的授权到期或任务结束为止 |
| 作者删、卖家下架 | 资料标逻辑删：所有者的栏里不再显示、不再解析；买家的使用权、钉住的测试与专家版本照旧可读 |
| 撤回平台过程授权 | 撤同意依据并立即撤这次过程的全部授权 |
| 禁用、许可失效、违规下架 | 资料标禁用：停一切新读取，在跑的授权也撤；在售专家转「待处理」并通知作者；违规下架收回买家使用权 |
| 注销、依法删除个人信息 | 真删内容（含产出区与描述字段），按适用的保留规则留编号级留痕；内容属于必须删的个人信息且已卖出的，通知、补偿买家（流程由 knowmart 做） |

- 现在的 `delete` 是删对象；改成逻辑删要迁移代码路径，真删只走最后一行。
- 测试证据拆两半：结论、数值、判定理由留；引用的原始内容随依法清除一起清，复现不了的判「证据不可复现」。

## 三、按描述查与解析

### 3.1 声明契约：`knowbot-manifest/v2`

现在的 `data_needs`（名字、说明、格式、份数、表与列）只能告诉人「要 5 份年报」，机器认不出哪家公司、哪几期。改成两层，出清单 v2（按 C-C10：声明的含义和绑定的规矩都变了，不在 v1 里改）：

| 层 | 谁写 | 内容 |
| --- | --- | --- |
| 声明模板（每样数据一条） | 作者在 knowlab | key、名字、说明；类型（词表）；期间规则（固定期间，或「最近 N 个完整年度 / 季度」，可加「截至任务日期已披露」）；格式；份数上下限；必填或可选；来源限制（只要公开原件 / 也接受上传）；表格类的表与列；口径（合并 / 母公司）、多候选时的优先策略 |
| 任务参数 | 请专家的人在发起任务时 | 主体（一家或几家，按声明允许的个数）；必要时覆盖期间 |
| 绑定 | 作者 | 专家自带的数据：资料编号加版本，随专家版本冻结、进版本摘要 |

- 声明结构与词表的定义只放一处（knowbase 管的跨应用契约），knowmart、knowbench、knowlab 现在三份逐字段相同的 `DataNeed` 收成一份，各自按契约版本校验。
- v1 的专家照旧能请（只有名字、格式、份数，没有类型和期间规则的声明，退回「请用户在开跑前确认解析结果」那条路，第 3.5 节）。只有绑定、没有声明的旧格式专家，照旧读作者绑的，到「财务分析与预测」第 2 版上架为止。

### 3.2 knowbase 的「按描述查」与「解析」

- **按描述查**：只接受精确的键（主体、类型、期间、格式），只回答这一份在不在、在哪个范围里；不回答「有什么」，不开列表、浏览、模糊搜公开原件层的接口。同一用户短时间大量不同描述的查询限流。
- **解析**：输入声明模板、任务参数、使用者（应用，或专家加版本）、请的人；输出一份解析清单。每样数据一个结果：

| 结果 | 含义 | 应用怎么办 |
| --- | --- | --- |
| 已定 | 在这个使用者能用的范围里，定了某一版 | 照用 |
| 你有没放开 | 请的人有，但没展示给这个使用者（只对本人的数据提示） | 请他到 knowbase 放开 |
| 待确认：已有原件 | 公开原件层有，他名下没引用 | 进确认清单 |
| 待确认：要新取 | 确定缺失、白名单渠道能采 | 进确认清单 |
| 采不来 | 确定缺失、不能采（私有资料、渠道不支持） | 告诉他去 knowbase 上传（直达链接，0044） |
| 有歧义 | 多个候选、按优先策略仍选不出 | 开跑前请他选（第 3.5 节） |
| 暂时判断不了 | knowbase 部分不可用、资料正在导入 | 不补采，任务停下等或报错 |
| 不能用 | 被禁用、许可不允许这种用法 | 照实告诉他，不补采 |

- 解析时公开原件优先于上传；有偏好（第 3.5 节）时偏好优先。
- 「最新」只在声明允许时用，按「截至什么时候能拿到」算。
- 解析清单存在 knowbase，带清单编号：需求、匹配理由、选中的版本、时间条件。应用把清单编号记进任务；重试读同一份清单；运行中冒出的新需求形成这份清单的新修订，不覆盖冻结的部分。

### 3.3 确认一次

1. 应用把清单里待确认的列给用户：「要为这件任务取得这 N 份公开披露，其中 M 份要新取，预计多久」，免费、收费、要审核的标在旁边。
2. 用户点一次，应用后端凭他的本人令牌交给 knowbase，knowbase 记一条确认（清单编号、任务、声明快照、确认的条目），回确认编号：
   - 已有原件的，立即在他名下记引用（状态可用）；
   - 要新取的，记引用（状态已确认等采），由应用后端把这些条目连同确认编号交 knowfeed（0045）。knowfeed 受理前向 knowbase 核这个确认编号是真的、条目对得上。
3. 已经在他名下有引用的，不再确认。

### 3.4 等数据与恢复

- 任务进「等数据」，带清单编号；页面能查进度（由应用后端查 knowfeed 的请求状态），能和卡死分开。
- knowfeed 采到、质检、交 knowbase 入库后，knowbase 把对应引用改成可用，按需求来源经发件箱通知那个应用；应用重新解析这件任务的清单，齐了就恢复。
- **供给完成的判据**：原件已由 knowbase 接管、版本能定位、权限能校验、任务要的读法已就绪（要读表的等表抽好；读原文不等全文索引）。
- 超时（委托默认 3 天，可配）转成用户看得见的失败，已定的部分留着；以后补的时候不重新采已到的。

### 3.5 开跑前列出、可换、偏好

- 开跑前把解析清单列给用户（每样：用哪份、哪一版、为什么是它）。默认直接跑；用户可以换一份（从这个使用者能用的范围里），有歧义的必须选。
- 换过的记成偏好：使用者 × 声明 key × 任务参数 → 资料与版本策略，存在 knowbase；下次同一使用者解析同一声明时优先。knowbench 现在「同一项目上次请这位专家用的那几份」那条查询改作偏好的来源。
- 这不是恢复选数据：不选是默认，不是每次必选。

### 3.6 开跑、钉住、校验

- 开跑时应用凭清单向 knowbase 申请运行授权，申请与钉住同时完成。
- 钉住层复用：knowbench `workbench_task_data`（槽位、资料与版本、摘要、授权编号、格子地址），去掉 `source='local'` 那条分支。
- 按声明核格式、份数、表头列、同一份不用两次的校验（现在的 `choice_problems`）原样保留，用来核机器挑的结果。
- **必填缺了不算成功**：依赖它的步骤等、失败、或经用户明确变更需求后继续；可选的缺了照做，任务记「不完整：缺了什么」。模型不能自己改声明。

## 四、各应用怎么改

### 4.1 knowbench

- **删**：请专家的选数据弹框、`data_choice` 与本地来源、`GET .../data-needs` 给弹框的那部分；「云端知识库」页的上传入口（页面留着，只展示 `app:knowbench` 的，标「在 knowbase 管理」）；会话里逐份选的入口。
- **请专家**：发起时填任务参数（主体）→ 解析 → 有待确认的弹确认清单 → 等数据 → 开跑前列出（可换）→ 开跑。委托单记清单编号、确认编号。
- **会话**：模型可用范围 = 展示给 knowbench 的加用户名下可用的公开原件引用；`list_library`、`read_library_item` 改读这个范围；第一次读某份时把它加进这段会话的授权并钉版本；每轮说明里列出这段话读过哪几份。会话里要一份他名下还没有的公开披露，同样弹确认。
- **读数工具、`compute`、数值验收**：照旧按钉住的读（0042 已做），数值验收只对钉在 knowbase 的。
- **本地**：本地 link 0.5.4 删本地知识库目录设置、服务流对它的只读范围、Windows 桌面界面那一栏；老配置里的这一项读了忽略。`source='local'` 的老委托只读，界面显示「本地来源已退役」。专家在项目目录里就地读写照旧（白名单目录管的就是这个）。

### 4.2 knowlab

- **知识库页**只展示 `app:knowlab` 的，上传移到 knowbase。
- **测试集**：作者在草稿上点「生成测试集」→ 解析器按声明提议候选（公开披露的候选来自披露渠道的公开索引，由 knowfeed 提供，不来自 knowbase 有什么）→ 作者确认或增删（这一步对公开披露同时是第 3.3 节的确认）→ 钉在草稿上，钉摘要、不跟新版。测试集有自己的版本号，和准专家版本分开。声明变了，现有「绑定过期」提示重新生成。
- **自助与平台**：孵化、测试各有「自己做 / 请平台做」。
  - 自助：用 `app:knowlab` 的同意依据。自助测试在用户自己的 link 上跑：测试授权照旧由 knowlab 申请、knowbench 执行端读；结论、数值、判定理由作为测试证据上传进产出区，原始产出留本地。
  - 平台：用户选的时候由本人留下 `platform:knowlab:<过程>` 同意依据，范围是这次过程（平台孵化：孵化用的那几份；平台测试：这次测试的测试集）。运营在 knowlab 管理端看数据凭平台过程授权（人），平台测试电脑读凭同一过程的机器授权；运营每看一次留痕，用户在 knowlab 网页能看到。同意文本写明运营的清单、受理意见可能引用数据片段。
  - 受理：平台孵化走现在的受理单；只请平台测试的走轻受理（只核测试集与用例齐不齐、数据授权在不在）；自助孵化不受理。
  - 每个准专家版本、每次测试记下模式。
- **过两道门**：自助测的，平台在测试电脑上凭测试授权按钉住的测试集重跑一遍，审核员看结果；要看原始数据另请用户同意（另一条 `platform:` 同意依据）。
- 0042 的「整栏测试同意」退役：迁移时把现有同意依据改成 `app:knowlab`。

### 4.3 knowmart

- **D 知识库页**去掉上传；卖家在 knowbase 把资料展示给 `market`，资料进 knowmart「待上架」（状态归 knowmart），卖家填介绍、样张、价格、驻场规则后上架。
- **成交**：knowmart 记订单后请 knowbase 给买家建使用权（交易那一版），不再复制；`purchase-copy` 的留痕值留给历史。
- **卖时审有权卖**：上架知识时核资料许可档为「可以出售」，公开原件、平台抽的表一律拒；专家上架时核所绑每份为「可以经专家给别人用」，有「只许本人用」的拒（买来的继承卖家转卖设置，`no_resale` 并进许可档）。
- **违规下架**收回买家使用权（第 2.8 节）；卖家注销时条目上的卖家名匿名。

### 4.4 专家绑定数据

- 作者在 knowbase 总栏对资料点「绑给专家」→ `expert:<专家编号>` 同意依据；knowlab 写清单 v2 时，绑定列出资料加版本，随专家版本冻结、进版本摘要；改绑定出新一版。
- 绑公开原件时绑引用；别人请这位专家时，在请的人名下按他的任务记引用（第 3.3 节确认清单里一并列出），按他自己的第二区读。
- 委托开跑时，knowbench 申请的授权里加上绑定的数据：所有者是作者、受益人是请的人。
- 承诺只到「没有浏览、下载入口，产出里可能引用」，作者绑定时页面照实写明（专家跑在请的人电脑上，原文会进他的上下文）。
- 绑的数据被禁用、许可失效：在售专家转「待处理」，通知作者，和 0018 资质过期自动下架用同一套机制。解绑、下架的历史留痕。
