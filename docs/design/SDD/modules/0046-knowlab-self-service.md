## 一、要做成什么

- 孵化、测试各自可选**自助**（用户自己做）或**平台**（运营做），可以组合，按每一次过程选。
- 自助的：只有用户本人和机器看得到他的东西，用他自己的模型 key、电脑、钱；平台的：照 0037。
- 用户始终在 knowlab web端，运营始终在管理端，两边看同一条记录的两个视图，切换不跳转。

## 二、自助孵化

> **10-28 起以 [专家孵化方案](../../../总纲/专家孵化方案.md) 为准**（decisions ⑮）：下表三种写法合成一份工作稿上的几种动作（作者直接改、AI 起草、AI 按指令改、导入）；方法模板不做，方法由 AI 按作者的问题起草、作者改定；作者只填方法层的格子，交回物结构、验收规则、工具与给模型的指令由程序生成；作者在工作稿里打的字凭编辑记录算原话，AI 与运营写的是提议、作者接受才算。下表留作 10-26 的原样。

| 做法 | 怎么做 | 规则的出处 |
| --- | --- | --- |
| 自己写 | web端编辑器一步一步填：步骤、每步的规则、交回物、验收（10-28 起不再写数据声明模板；要提示模型「这一步一般要什么数据」写在步骤说明里，0043 第 3.1 节）；有模板可套 | 用户原话 |
| AI 帮着写 | 0029 第六节的孵化方法，跑在他自己的 knowbench 工作台（固定项目「孵化」）、他的沙箱、他的模型 key：抽结构标出处 → 列缺口附提议 → 工程化出清单 → 自查；缺口直接进他的「待办」，答完再来一轮 | AI 起草的每条规则要他确认才算用户确认 |
| 导入 | 已有的 skill 或专家包直接导入 | 用户原话 |

- 出处把关照旧、由程序做：原话核对（`user_text` 的原话逐字出现在创意或答复里，`user_confirmed` 指向他答过的问题）与 `draft_manifest_problems`；对不上的不能拿去测（C-L1）。
- 不受理：记一种「自助（不受理）」受理记录，草稿直接建在创意版本上；创意改了出新版本照常往下孵。
- 每轮费用上限由用户自己设，记在他名下。
- 平台的人看不到：创意、草稿、问答。

## 三、自助测试

**流程**（10-28 按 decisions ⑭ 改，原写「测试集：作者给主体，解析器展开类型、期间、口径」）：验收用例（测试问题，期望值只能由他填或确认）→ 发起（选模式；自助的选电脑、设费用上限）→ 运行（他的工作台里按用例逐条开委托，用他的模型 key；平台模式也在他的账号与电脑上，decisions ⑯）→ **第一次测、或用例没有测试集的：每条用例先走第 0 步定数据**（见下），作者确认后钉成测试集 → 照逻辑做 → 结果（编号；通过 / 没通过 / 平台出错附报告；结论、数值、判定理由经服务写入路进产出区，原始产出留本地；记测试集版本、准专家版本、模式）。

**测试集怎么来（10-28，decisions ⑭）**：测试集 = 测试问题 + 作者确认的数据，按用例记，有版本号。

1. 运行方在每条用例的委托里先跑第 0 步：模型读草稿的逻辑和这条测试问题，用「查主体」「提出数据」提要哪些数据。测试委托里提出的不经运行方的账号去 knowbase 解析，而是作为一个「待回答的问题」（种类 `data`，带提出的几样）报给 knowlab，委托停下等（照「有人值守」的做法，等人的时间不计入超时）。
2. knowlab 凭作者本人令牌在 `app:knowlab` 的范围里解析（他放开给 knowlab 的、名下的引用、公开原件），在测试页列给作者：能换一份、改主体或年份、去掉、自己加一样；缺的公开披露照常确认一次、交 knowfeed，取齐了接着往下（平台模式也由作者本人确认，运营不能替他确认）。
3. 作者确认后，knowlab 签这条用例的测试运行授权（凭展示依据、引用、公开原件、冻结绑定；一条用例一张，不中途追加），连同钉住的输入组合回答那个问题；运行方钉进委托，接着跑第 1 步。
4. 每条用例钉住的那几份记成测试集的这一版。之后重测带着测试集发起：每条用例开跑前就钉好、签好，不跑第 0 步，同一测试集版本测出的结果才直接比；作者要换数据就出测试集新版本。第 0 步提了什么、作者改了什么记进测试证据，本期不单独打分。
5. 作者挑选的数据（冻结的绑定）每条用例照样钉上。

**怎么选电脑**：
- knowlab 后端凭本人令牌向 knowbench 要他接入过的电脑（「我的电脑」里那几台），列出电脑名、系统、在线与否。
- 默认：上次测试用的那台在线就是它；只有一台在线就是那台；离线的灰着；一台都不在线不能发起（「去 knowbench 接入或打开电脑」）。
- 第一次在某台电脑上测，从这台电脑的白名单目录里选一个放测试项目，以后记住；每次测试建自己的子目录（「测试-名称-编号」）。
- 模型 key 用他在 knowbench 填的，没填不能发起（「去 knowbench 填模型 key」）。
- 途中电脑掉线停在「等电脑」，回来接着跑；等太久记「平台出错（电脑离线）」，可重测。

**规矩**：通过即出专家第 n 版（可以自用，公开要交付时平台重跑）；每次测试的费用上限由他自己设，到了停、记「超预算」；平台出错重测（新编号、同一个准专家），专家没做对就改草稿出新准专家；平台的人看不到测试集、用例、报告、证据。

| | 自助测试 | 平台测试 |
| --- | --- | --- |
| 谁发起 | 用户自己 | 运营（只请平台测试的先过轻受理） |
| 在哪跑 | 用户自己的电脑 | 用户自己的电脑（10-28 decisions ⑯ 改，原为平台的测试电脑）：在作者的账号下跑，和自助测试同一条路 |
| 用谁的模型 key、谁出钱 | 用户自己 | 用户自己（decisions ⑯，原为平台） |
| 谁看结果 | 用户自己 | 运营和用户 |
| 测试中的问题转给谁 | 用户自己 | 运营看过后转给用户 |

## 四、组合与切换

| 组合 | 怎么走 | 谁看得到什么 |
| --- | --- | --- |
| 自助孵化 + 自助测试 | 全程自己做 | 只有他自己；交审时另外授权给审核员 |
| 自助孵化 + 平台测试 | 把草稿交平台测：轻受理，本人授权平台测这一次（范围是这次的测试集），在作者的账号下、作者的电脑上跑（decisions ⑯） | 运营看得到这一版草稿、这次测试集与结果；看不到之前的草稿与问答 |
| 平台孵化 + 自助测试 | 平台受理、孵化（照 0037），草稿交还给他，他拿自己的数据自己测 | 运营看得到孵化过程；看不到他的测试集与结果 |
| 平台孵化 + 平台测试 | 0037 这一版 | 运营和用户 |

| 切换 | 怎么做 |
| --- | --- |
| 孵化：自助转平台 | 在当前草稿上点「请平台孵化」= 提受理申请、附这版草稿；弹确认框写明平台会看到什么、到什么时候，确认即本人授权（`platform:knowlab:<孵化>`）；受理后运营接着孵化 |
| 孵化：平台转自助 | 点「我自己来」：平台对这个创意的授权立即撤销；当前草稿归他继续改，原来的出处不变；他改出的新版本运营看不到 |
| 测试 | 每次发起时选模式，跑起来不能切；要换就取消、用另一种模式重新发起（新编号） |

- 每个准专家版本、每次测试记模式；运营只看得到平台模式的那几步与用户另外授权的。
- 默认：第一次让用户自己选，两边的说明并排给他看（谁看得到他的数据、用谁的 key、谁出钱）；以后默认用他上次的选择。
- **切换不跳转**：转平台后留在原页，模式标签变「平台」，页面换成平台视图（进度、在等你什么、运营问了什么）；这一条同时进管理端队列；运营要用户答问题、确认或有了结果，进「待办」、首页「在等你」、发站内信。转回自助，同一页换回编辑器，顶上提示「平台的授权已撤销」。

## 五、交付

| 测试通过的那一次是 | 用户同意门 | 自用 | 公开 |
| --- | --- | --- | --- |
| 自助测的 | 「提交交付」即过 | 轻审：能自动查的自动查（成稿里有没有目标价、评级这类内容；测试结果与受理单对不对得上），查不过才交人看 | 完整审核 + 平台发起重跑，在作者的账号下用作者的 key 与电脑跑，全程事件记在 knowbench、作者改不了（decisions ⑯，原为平台测试电脑；另签机器授权，审核员看结果、不看原始数据） |
| 平台测的 | 平台孵化的：用户在 web端确认要这一版（先用户、后运营）；自助孵化的：「提交交付」即过 | 轻审 | 完整审核，不用重跑 |

不管哪种组合：交出去的是清单 v2，绑定的数据留在 knowbase；交审时本人授权审核员看这次交付（`platform:knowlab:<交付过程>`），审完撤销；自用转公开时许可重查；改绑定出新一版、重新交付，买家那一版不变（0043 第 4.2、4.3 节）。

## 九、实施进度

块 7（0043）按这个顺序做（10-28 定）：

1. knowbench：用户本人作为测试运行方（本页块 2）——测试契约加运行方（只有用户本人，decisions ⑯；电脑、目录）；列出用户的电脑给 knowlab（本人令牌）。
2. knowbench：测试委托的第 0 步——提出的数据报成种类 `data` 的待回答问题；回答带测试授权与钉住的输入组合，钉进委托接着跑；用例带测试集的直接钉、不跑第 0 步。契约加用例的数据、`data` 问题与回答。
3. knowlab：测试集（按用例、有版本）；`data` 问题的解析、确认（换、改、去掉、加）、补采与等数据、签每条用例的测试授权、回答；重测带测试集。
4. knowlab：自助测试的发起（选电脑、费用上限）、测试记模式、测试集版本与电脑。
5. knowlab web端：测试栏（用例、测试集、确认数据、发起、历次测试）。

## 2026-11-03 增补：明确未复测的人工特批发布

所有者明确批准“增加人工特批发布，修复后按特批上架”，适用于不再调用模型测试的修订发布。此为正式例外流程，不把原测试判成通过、不复用旧版测试通过作为新版的通过记录，也不替代正常交付的作者同意、绑定数据许可、公开类目与资质审核。

作者对一个未测试的新准专家版本发起特批请求，指定同一专家的旧版已通过测试作为参考，绑定新清单SHA-256，记录理由、变更、离线验证与尚未验证的范围，并授权发布人员查看这份包。已启动或已结束测试的目标稿、同名活动测试、已占用版本、摘要不一致均拒绝；旧测试结论和费用只读保留。

管理端依现有`knowlab:admin`及`knowlab:release`角色审批，批准/拒绝与人员、时间、理由不可变。批准生成独立专家版本，`test_id=null`，`manual_release.retested=false`；准专家仍保留未测状态，不能对已发布修订补写通过。后续要测试先出新修订。再次提交相同申请/决定幂等，不同载荷冲突。审批记录与专家快照归knowlab；跨应用仍只用既有交付接口。

作者随后提交正常交付；`test_mode=unrun`、`needs_rerun=false`，不申请模型费用。自动审查给出`manual_unretested`，连自用也不得自动审过。发布人员继续核许可、类目及资质后交knowmart，交付前重核审批绑定的摘要。作者端和管理端显示“人工特批，本修订未复测”，时间线不显示“测试通过”。本次固定财务候选简介也明确该限定，供商城/请入显示。

入口：作者名称详情“人工特批发布”；管理端交付页“特批申请与记录”。所有变更沿用会话与CSRF，审批身份由服务端认证，不接受客户端伪造actor。新增独立迁移0026审计表及专家可空快照列；有特批历史时downgrade拒绝删除证据。已有特批交付后，不单独退回不识别unrun的旧前端。
