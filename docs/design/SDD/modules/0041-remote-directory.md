## 一、三种放法

本地 link 里干活的那部分叫**执行端**（「手」）：`codex exec-server`（起进程、读写文件、列目录）加上把它关住的沙箱。大脑（Codex 的 app-server，调模型）一直在云端沙箱里，不随项目走。项目在另一台机器（下称远程机器）上时，执行端放在哪有三种放法：

| | 挂载（作废） | **甲：做** | 乙：不做（第三节） |
| --- | --- | --- | --- |
| 远程机器上放什么 | 什么都不放 | 本地 link 的一部分：执行端 | 整份本地 link |
| 命令在哪跑 | 用户电脑（隔着网络读写远程文件） | 远程机器 | 远程机器 |
| 什么过网络 | 每一次读写文件 | 指令和结果 | 指令和结果 |
| 谁连会合点 | 用户电脑上的本地 link | 用户电脑上的本地 link；远程机器不连 | 远程机器上的本地 link 自己连 |
| 令牌 | 一份 | 一份，还是用户电脑上那份 | 远程机器另一份，要改「一个账号一份本地 link」 |
| 远程机器要不要上外网 | 不要 | 不要，用户电脑能 SSH 到就行 | 要 |
| 用户电脑关机 | 用不了 | 远程项目也用不了 | 不受影响 |

市面上的做法（OpenAI Codex 应用、Claude Desktop 的 SSH 远程会话、VS Code Remote-SSH、JetBrains Gateway、Zed）都不挂载，都是经 SSH 把引擎放到远程机器上跑。我们照搬的是原则（执行端放到文件旁边），不照搬形态：它们放的是整个引擎，远程机器上要登录或放模型 key；我们的大脑在云端，远程机器上只放执行端，**不放模型 key，也不放令牌**。

## 二、甲

### 1. 新建项目选目录：三种方式

| 方式 | 做什么 |
| --- | --- |
| 本地目录 | 在装有本地 link 的电脑的工作区里新建文件夹，或选已有的文件夹（现在就有） |
| 拉取仓库 | 把 git 仓库拉进工作区（现在就有） |
| **远程目录**（新） | 选远程机器上的目录：本地 link 先经 SSH 连上那台机器、放好执行端，再在那台机器上选项目 |

### 2. 选「远程目录」的流程

1. 新建项目时选「远程目录」。
2. 看本地 link 上已经登记的远程机器：
   - 有：列出来（地址、系统、连没连着），选一台；
   - 没有，或要的那台不在里面：点「添加远程机器」，填地址（IP 或主机名）、端口、用户名。本地 link 当场经 SSH 连上，第一次连要用户核对并确认主机指纹（第 6 小节）；连上后判断远程机器的系统与架构，把对应的执行端放上去（第 5 小节）。
3. 放好后直接选项目：浏览这台远程机器上白名单里的目录，选已有的文件夹当项目，或新建文件夹，或把仓库拉进来（在远程机器上拉）——和本地目录一样。
4. 登记项目，记上「在哪台远程机器上」（第 3 小节），以后当普通项目用。

### 3. 远程机器归电脑管；项目只记「在哪台」

- 远程机器是本地 link 的设置，和白名单目录一样：本地 link 记着登记了哪几台（编号、地址、端口、用户名、固定的主机指纹、系统、远程白名单）。
- 项目记录多一项：**在哪台远程机器上**，只记本地 link 给那台机器的编号，不记地址。地址只在本地 link 的设置里；改了地址项目不受影响。
- 电脑照旧按设备编号认（会合点备忘第三节），不按 IP 认。
- 换了装有本地 link 的电脑时，远程机器不自动搬过去，在新电脑上重新添加一次；旧电脑上登记的远程项目，和本地项目一样提示「在旧电脑上」。

### 4. 链路；本地项目和远程项目的差别只在这几处

```
云端沙箱（大脑）──会合点──▶ 用户电脑上的本地 link ──SSH──▶ 远程机器上的执行端
                           出站桥、过滤、本地确认          exec-server + 沙箱
```

- 会话的项目在远程机器 X 上时，本地 link 把这个会话的执行请求转给 X 的 SSH 通道，不交给本机的 exec-server；其余会话照旧在本机执行。
- exec-server 支持 `--listen stdio`（Codex 0.155.1 已核），本地 link 经 SSH 直接起 `codex exec-server --listen stdio`，走 SSH 的标准输入输出，**不在远程机器上开端口**，也不要求远程机器允许端口转发。
- 过滤（白名单、本地上限）与本地确认**留在用户电脑上**，规则只有一份，远程机器上的东西越少越好；沙箱必须在远程机器上，在那边关住执行端（第 6 小节）。
- 浏览器读文件（右边栏、新建项目，账 165）：浏览器在装有本地 link 的电脑上 → 回环口 → 本地 link → SSH → 远程执行端；在远程登录 link 的电脑上 → 服务流 → 本地 link → SSH → 远程执行端。回环口（`localFiles.ts`、`localProjects.ts`）与服务流（`service.ts`）都要多认一个「在哪台」：本机就照旧读本机，远程就转给那台的执行端。

**原则**（所有者 10-23 问「本地建项目和远程项目不一样了，之后工作也不一样了，要判断了，右边栏随之跟着变，对吗」后定下的写法）：「在哪台」只在新建项目时定一次，作为项目的一个属性往下传；真正分叉的地方集中在本地 link 里，不让判断散到网页和后端各处。

| 地方 | 变不变 | 怎么变 |
| --- | --- | --- |
| 新建项目 | 变 | 多第三种「远程目录」，这就是这个功能本身 |
| 项目记录 | 多一项 | 「在哪台远程机器上」（本地项目为空） |
| 工作（Codex 干活） | 基本不变 | 云端照旧把请求发给本地 link，本地 link 按项目在哪台转给本机 exec-server 或远程执行端；后端给模型的系统说明本来就按项目路径判断 Windows 还是 Linux（knowbench 后端 `projects.py` 的 `is_windows_root`），远程 Linux 项目的路径自然按 Linux 处理 |
| 右边栏（文件树、工作底稿） | 界面基本不变 | 网页照旧向本地 link 要文件，多带一个「哪个项目」，由本地 link 决定读本机还是读远程；网页只多「在远程机器 ×× 上」的标注和「远程机器连不上」的提示；「在资源管理器里打开」这类操作（如有）对远程项目隐藏，文件不在这台电脑上 |
| 账 165（浏览器在远程登录 link 的电脑上） | 不变 | 「浏览器在哪」和「项目在哪」互不相干：前者决定网页走回环口还是服务流，后者只是往下传的参数 |

和挂载比：挂载时本地 link 以上完全不用分叉，但沙箱拦不住越界写（第四节），不能拿安全换简单；甲的代价就是多这一个属性，并守住「只在本地 link 里分叉」。

### 5. 远程机器上放什么、平时怎么管

| 远程机器是 | 放什么 | 沙箱 |
| --- | --- | --- |
| Linux | `codex`（exec-server）、bwrap | 照本地 link 的 Linux 外沙箱（`outerSandbox.ts`）：bwrap 把 exec-server 整个关起来，只把远程白名单目录绑成可写 |
| Windows | `codex.exe`（exec-server）、Codex Windows 沙箱的两个小程序，加上本地 link 在沙箱里读写文件用的 Node 小助手（`windowsBridge.ts`、`native/helper.mjs`）及 `node.exe` | Codex 自带的 Windows 沙箱（普通模式，受限令牌），同本地 link 现在的做法 |

- 放在远程用户的家目录下（如 `~/.sunmoon-link-remote/`），**不要管理员权限**；一台远程机器一份，不是一个项目一份；**只留一个版本**，升级时临时多一份，装好删旧的。
- 执行端版本跟着本地 link 走（Codex 版本要和云端 app-server 对得上）：本地 link 升级后下次连远程机器时一并升级。
- 包从哪来：本地 link 从我们的下载站取对应系统与架构的包、核摘要，再经 SSH 传上去；**远程机器不用上外网**。
- 大小（2026-10-23 量的 Windows 版 0.5.1）：`codex.exe` 293 MB（压缩后 98 MB），`node.exe` 89 MB，Windows 沙箱两个小程序 23 MB；Windows 远程机器估占盘 300～400 MB、第一次传 100～150 MB。Linux 版没量。`codex-code-mode-host.exe`（69 MB）要不要带，实施前核。
- 远程机器上已经装了版本对得上的 Codex 的，可以直接用它的，不再放一份（实施时定要不要做）。

远程执行端的一生：

| 阶段 | 做法 |
| --- | --- |
| 放上去 | 第一次添加远程机器时，本地 link 经 SSH 判断系统与架构，把包传到远程家目录、核摘要再解开；不装服务、不改系统设置 |
| 平时：**不常驻，用时才起** | 有会话要在这台机器上干活时，本地 link 经 SSH 起 `codex exec-server --listen stdio`（Linux 外面套 bwrap）；它只和这一条 SSH 连接的标准输入输出说话，远程机器上不开端口，那台机器上的其他人、其他程序连不到它；SSH 一断它就退出，远程机器上不留常驻进程、不开机自启 |
| 多个会话 | 一台远程机器一条 SSH 连接、一个执行端，多个会话共用（同本机，`--concurrent-requests 8`） |
| 能动什么 | 以 SSH 登录的用户身份运行，权限不超过它；沙箱只放开这台机器的远程白名单目录可写；每个请求先在用户电脑上过一遍过滤再转过去 |
| 升级 | 本地 link 升级后，下次连这台机器发现版本不对，就传新版、换好删旧版，只多占一份的空间 |
| 删掉远程机器 | 用户在设置里删这台远程机器时，本地 link 经 SSH 把 `~/.sunmoon-link-remote/` 整个删掉；连不上就照实提示「远程机器上还留着 ××，请自己删」并给出路径 |

**不常驻的代价**：SSH 一断（网络抖动、用户电脑睡眠），远程机器上正在跑的命令（如跑了一半的长测试）跟着中断。Claude Desktop 让引擎在远程常驻、重连后接着跑，但要在远程留常驻进程并管它的安全。先不常驻，断了照实告诉用户和 Codex；以后真有长任务的需要，再加「断线后接着跑」。

### 6. 安全

| 项 | 做法 |
| --- | --- |
| 模型 key、令牌 | 不上远程机器：大脑在云端，令牌留在用户电脑上的本地 link |
| SSH 钥匙 | 用用户电脑现有的（`~/.ssh` 里的钥匙、ssh-agent、`~/.ssh/config` 里的主机设置），钥匙不离开用户电脑；不开 agent 转发 |
| 主机指纹 | 第一次连由用户核对确认，之后固定；指纹变了照实报、拒绝连接，不自动接受 |
| 远程白名单 | 每台远程机器各有一份（远程机器上的哪些目录允许用）；添加远程机器、放宽它的白名单都要在装有本地 link 的电脑前点允许，同本地白名单 |
| 过滤 | 在用户电脑上按远程白名单查每个请求的路径，再转给远程执行端 |
| 沙箱 | 在远程机器上：Linux 用 bwrap，远程机器不支持（例如没开非特权用户命名空间）时照实报、不启用这台机器；Windows 用 Codex 的 Windows 沙箱，和本地 link 现在一样（它不拦删除的问题见第四节） |
| 远程机器上的权限 | 执行端以 SSH 登录的那个用户身份运行，权限不超过它；建议用户给它一个只有所需目录权限的账户 |

0024 第七节（10-14）写过「『本地代理经 ssh 转发每条命令』不走：本地沙箱与白名单管不到远程」。甲不是那种做法：沙箱随执行端放到远程机器上，在那边关住它；白名单按远程机器各一份，由用户电脑上的本地 link 查。

### 7. 连不上

- 远程机器没开、地址变了、SSH 被拒：本地 link 回一个专门的错误代码（如 `remote_unreachable`，带地址），右边栏、新建项目、Codex 的报错都照实写「远程机器连不上 192.168.1.20」，不笼统写读取失败、不当成空目录。设置里能改地址。
- 用户电脑关机或本地 link 没在运行：远程项目和本地项目一样用不了，项目页照实说明（「电脑关了远程照样跑」只有乙能做到，乙不做，见第三节）。
- SSH 断线：远程执行端随之退出（第 5 小节「不常驻」），断线时正在跑的命令会丢（同本地 link 现在 exec-server 重启时一样），照实告诉 Codex 与网页；本地 link 自动重连，下一个请求来时重新起执行端。

### 8. 网页要做的

- 新建项目对话框加第三种「远程目录」，按第 2 小节的流程。
- 设置「电脑与沙箱」里列出登记的远程机器：地址、系统、连没连着、执行端版本、远程白名单；能添加、删除、改地址。
- 项目页、文件树标明「在远程机器 ×× 上」；连不上时照实写原因。

### 9. 第一次的准备：在装有本地 link 的电脑前做

1. 添加远程机器、确认主机指纹、定远程白名单（放宽要在电脑前点允许）；
2. 远程是 Windows 时，那台机器要开 OpenSSH Server（Windows 10/11 自带、默认没开，由用户在那台机器上开一次）。

用户人不在那台电脑前时，第 2 小节第 2 步的页面照实提示「第一次要在『电脑名』前做一次准备」；做过以后在哪都能直接建远程项目。

### 10. 不做

- 挂载（SMB、sshfs）：作废，理由见第四节。
- NAS 这类跑不了执行端的机器：不管，以后要做再单独议。
- 远程机器上不放模型 key、令牌；不开 SSH agent 转发。
- 不按 IP 认电脑。

### 11. 实施前要先核、先实测的

| 项 | 怎么核 |
| --- | --- |
| 本地 link 用什么 SSH 客户端（Windows 自带的 OpenSSH 客户端，还是随包带一个） | 查 Windows 10/11 自带情况与 `~/.ssh/config` 兼容性后定 |
| exec-server 经 SSH 的标准输入输出跑一轮 Codex | 在所有者的 Windows 上连一台 Linux 远程机器、一台 Windows 远程机器各实测一次；用哪台机器当远程要先问所有者 |
| 执行端最小组成与大小（`codex-code-mode-host.exe`、`node.exe` 要不要；Linux 版多大） | 读 Codex 与本地 link 代码，再量 |
| Linux 远程机器上 bwrap 能不能用（非特权用户命名空间、常见发行版的默认设置） | 查文档并在一台 Linux 上实测 |
| Windows 远程机器经 SSH 登录时，Codex 的 Windows 沙箱能不能起（SSH 会话的登录类型与桌面不同） | 实测 |
| 云端 Codex 面对的执行端从 Windows（用户电脑）换成 Linux（远程机器）时，选 shell、路径规则能不能按执行端那边的系统自动切；后端按路径给的 Windows 说明会不会误加 | 读 Codex app-server 与 exec-server 的环境信息代码，再实测 |

**第一轮实测（2026-10-23）**：所有者说「你直接用43.153,135.74也就是你所在的就行了啊」。用户电脑 = 所有者的 Windows（本地），远程机器 = 云服务器（远程，Ubuntu 24.04，x86_64），经公网；Windows 上用所有者现有的 `~/.ssh/config`（`Host txy-tokyo`）和钥匙。远程上只用一个临时目录、单独的 CODEX_HOME，没碰那台机器上已有的 Codex 与 `~/.codex`；测完临时目录、Windows 与 WSL 上的测试文件都已删。

| 项 | 结果 |
| --- | --- |
| SSH 客户端 | Windows 自带的 OpenSSH 客户端（9.5p2）直接认用户的 `~/.ssh/config` 与钥匙，`BatchMode` 下可用；不随包带客户端也行 |
| exec-server 经 SSH 的 stdio | 通：`initialize` 含 SSH 建连 1.4 秒；之后每个请求往返约 40～50 毫秒（10 次 `fs/getMetadata` 共 0.4 秒）；读文件、列目录、写文件、起进程拿输出都正常。还没接云端跑一轮完整的 Codex |
| 执行端报的环境 | `initialize` 回 `platformOs: "linux"`、shell 是 zsh、家目录：云端拿得到远程机器的系统；app-server 会不会据此换 shell 与路径规则仍要核。Linux（musl）版报的 `executorVersion` 是 `0.0.0`，Windows 版是 `0.155.1`（本地 link 的 Windows 助手按 `0.155.1` 核），核版本要换别的办法 |
| Linux 版大小 | `codex` 257 MB；npm 包整个压缩后 142 MB（含 `codex-code-mode-host` 66 MB、rg、语音组件）；只传 `codex` 的话估压缩后约 90 MB |
| bwrap 外沙箱 | 照 `outerSandbox.ts` 的参数套上后，工作目录里能写，工作目录外 `fs/writeFile` 与 shell 写入都报 `Read-only file system`；进程以 SSH 用户身份运行。**这台机器关掉了 Ubuntu 对非特权用户命名空间的限制**（`kernel.apparmor_restrict_unprivileged_userns = 0`，不是 24.04 的默认），默认设置下的表现还没测；推断默认设置下只有系统自带的 `/usr/bin/bwrap`（有 AppArmor 配置）能用，随包带的 bwrap 会被拦，远程机器有系统 bwrap 时应优先用它 |
| 断线 | 正在跑 `sleep` 时直接杀掉用户电脑上的 ssh：远程上的 exec-server、bwrap、`sleep` 都随之退出，没有留下进程，和第 5 小节「不常驻」一致 |
| 上传 | 从所有者 Windows 传 30 MB 到远程机器用了 3 秒（约 10 MB/s），放一次执行端约十几秒 |
| 读的范围 | 外沙箱是「全盘只读、白名单可写」，远程命令能读到 SSH 用户能读的一切（如那台机器上的 `~/.ssh`、`~/.codex`）；过滤只管经 exec-server 的文件请求，管不到命令自己读什么。同本地 link 的 Linux 做法，所以第 6 小节建议给执行端一个只有所需目录权限的账户 |

## 四、挂载为什么作废（2026-10-23 在所有者 Windows 上实测）

用 rclone（SFTP）+ WinFsp 把 WSL 里一个临时 sshd 的目录挂到 Windows 上测：

| 测了什么 | 结果 |
| --- | --- |
| 写入正确性 | 缓存模式 `writes`、上传延迟 5 秒时，改名、「写临时文件再改名」都对；延迟 0 秒出竞态（改名被撤销、远程留下临时文件）。5 秒只缩小窗口，不能证明没有竞态；文件关闭约 5 秒后才到远程机器 |
| Codex 的 Windows 沙箱读写挂载盘 | 能读写；但按 rclone 默认挂法，沙箱**拦不住写到允许范围外**（挂载盘不按 Windows 权限表把关）。挂载时指定固定权限表（`-o FileSecurity=…`）能让只读会话写不进，但可写会话要把 Codex 内部按目录分配的「可写身份」写进表里，依赖 Codex 的内部做法 |
| 本地 link 的路径检查 | 挂在盘符或文件夹上时 `fs.realpathSync.native` 一律报 `UNKNOWN`，网络盘方式返回 `\\server\…`；三条读写路都会把挂载目录当成白名单外拒掉 |
| 挂到文件夹 | 能挂，挂载点是指向卷的 junction，Node 的 `lstat` 不当链接 |
| rclone 的主机钥匙 | 默认**不校验**；SFTP 默认跟着远程机器上的符号链接走 |

这些问题全是「手和文件隔着网络」带来的，甲把执行端放到文件旁边，一个都不碰。

**顺带发现、与远程无关**：Codex 的 Windows 沙箱（普通模式）**拦写不拦删**——只读档下也删掉了 `%LOCALAPPDATA%` 下的测试文件、删掉了空目录（推断是令牌只限写，Windows 不把删除算写，未读源码确认）。现在的本地 link 0.5.1 就有这个问题，甲在 Windows 远程机器上也会有。

测试用的 rclone、临时 sshd、临时目录 10-23 已全部删掉；WinFsp 是所有者手动装的，留不留由所有者定。
