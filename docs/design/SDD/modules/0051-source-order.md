## 一、现在的样子（2026-11-06 各仓头）

1. **knowbase 先解析已有的**，没有的才交 knowfeed。这一段对，不动。
2. **走不走 Wind 是模型定的。**knowbench 数据步的提示（`advisor.py` 1859 行起）写「Prefer an available supplier query (for example Wind) via source_query」；工具说明（`workbench_mcp.py` 205 行）教模型把 `source_query={channel,service,tool,arguments}` 写进需求。写了，这一项就**点名了供应商**，和 5.1 相反。先后（Wind 先）和所有者 11-06 定的一致，但写在提示词里，模型、提示一换，选源就变。
3. **Wind 和其它渠道是两条不相通的道。**knowfeed `Channel.covers`（`domain/supply/models.py` 436 行）：带 `source_query` 的项只有它点名的 Wind 渠道能供；不带的项 Wind 渠道一律不供。描述键里还拼了 `|query:`，两种项连身份都不同。
4. **按次序换源的机制其实已经有了**：渠道有 `priority`（管理端可调先后），`candidates` 按先后排、按用户确认的供给条件筛；一个渠道取不到，`_next_channel`（`application/supply/jobs.py` 1289 行）跳过 `tried_channels` 换下一个。只是因为第 3 条，Wind 取不到不会落到巨潮，巨潮取不到也不会去问 Wind。
5. **prematch**（`knowfeed-supply-prematch/v1`）确认前已经回每项的候选渠道、许可档、预计时间；确认快照 `supply.conditions.channels` 已能记用户接受哪些渠道。

## 二、做法（2026-11-07 改定）

所有者 11-06 至 11-07 几轮讨论定的四条（原话见第六节）：

1. **需求只说要什么，不说怎么取**：「需求和供给不一致，应该不是一个好的做法」；「需求不能决定取法，到了供给端才分」。
2. **口径不写时默认当期原始披露**（同上，「第一条行」）。
3. **不另建抽数引擎**：年报保底用 [0047](0047-public-disclosures-facts-search.md) 已做好的抽表（三张合并报表 → 原样层 → 按科目表对成标准化层，带恒等式质检与重述标记）。knowfeed 收到的别的请求也要数，所以数由平台抽，不留给专家方法。
4. **取回的先进 knowbase、再通知需求方来取**：现有的 `knowfeed-supply-status/v1`（knowbase 收下回执后同一事务排通知，发件箱重发），需求方凭授权从 knowbase 取。

### 2.1 需求：要哪些数（和资料需求并列）

| 项 | 写什么 | 取值 |
| --- | --- | --- |
| 主体 | 哪家公司 | 同资料需求（0049） |
| 期间 | 哪几期 | 期末日；同资料需求 |
| 指标 | 要哪些数 | knowbase 科目表的编码（`chart_of_accounts`，0047 第 4.1 节），如 `IS.REVENUE` 营业收入；科目表带版本，跟词表一起管 |
| 口径 | 怎么算的数 | 报表范围：合并 / 母公司；覆盖时长：全年 / 半年 / 单季 / 年初至今；披露版本：**当期原始披露**（默认）/ 最新调整后 |

不写渠道、不写取法、不写 Wind 字段。要逐页核原件的方法，另要那份年报（现有资料需求、按页读法），不靠限定取法。

### 2.2 先在 knowbase 找

knowbase 按（主体、期末日、科目编码、口径）在**标准化层**里找本人有授权的那几行；「当期原始披露」取首次出现它的那份报告，「最新调整后」取最后一份。都有就直接给，不派作业。

### 2.3 没有的交 knowfeed：取法是渠道的事

| 渠道 | 怎么取 | 写回 knowbase 的是 |
| --- | --- | --- |
| Wind（`wind-mcp`） | 插件里一张「科目编码 + 口径 → Wind 字段与参数」对照，翻得出才认这一项 | Wind 原样回答作一份资料（照实记取自 Wind），它的表格读法里是对到科目编码的事实行（原样层记 Wind 字段原文，标准化层记科目编码） |
| 巨潮 | 这一项落在哪份定期报告（全年 → 年报，单季 → 季报），下原件，用现有抽表 | 年报原件与它的表格读法（0047 现成的路） |

- **先后 = 渠道 `priority`**，默认 Wind 在前、巨潮保底（11-06 定）；在管理端可调。取不到（没有这一项、额度用完、渠道停用）用现有 `tried_channels` 换下一个。
- Wind 某个科目、某个口径登记进对照之前，先做同组样本对照（双轨 10.1）：几家公司几年的数与年报原文逐个比，差异写原因；对照过了才登记。给不出某个口径的就不登记那个口径。
- 同一个数两个渠道都取过、又不一样：两行都留，标「待核」，不让后来的盖掉前面的。

### 2.4 通知与取用

照现有的：knowfeed 写进 knowbase、拿到回执后把这一项标「已就绪」并排状态通知；knowbench 的「等数据」接着推，knowlab 的测试集接着用；需求方凭运行授权从 knowbase 取标准化层的这几行，每行带它出自哪份资料、怎么取来的。

### 2.5 改哪些地方

| 步 | 改什么 | 仓 |
| --- | --- | --- |
| 1 | 数据需求加「要哪些数」这一种（主体、期间、科目编码、口径）；`data-request` 出新版（加法） | knowbase（契约提供方），knowbench、knowlab 跟锁 |
| 2 | 按（主体、期末日、科目编码、口径）查标准化层，含「首次披露 / 最新」两种取法 | knowbase |
| 3 | knowfeed 需求项认「要哪些数」；巨潮按「落在哪份报告」认这一项 | knowfeed |
| 4 | Wind 插件：科目编码与口径到 Wind 字段的对照（随 W0 核实的字段逐条加）；Wind 回答写成资料 + 事实行 | knowfeed |
| 5 | `covers` 改成按上面认；旧的 `source_query` 项照旧只认点名的渠道（过渡） | knowfeed |
| 6 | prematch 出 v2：每项回按先后排好的候选渠道与各自怎么取（照实给用户看）、许可档 | knowfeed（提供方），knowbench、knowlab 跟锁 |
| 7 | 确认页照 prematch 列出候选，用户可去掉某个渠道（已有的 `conditions.channels`） | knowbench 网页 |
| 8 | 数据步：提示里删掉「Prefer … Wind」，不让模型写 `source_query`；要数就提「要哪些数」 | knowbench |

## 三、不做的

不做跨渠道的「取最快的」「取最便宜的」打分；不让需求写取法或渠道；不让 knowbench 再知道有哪些供应商；不让 Wind 冒充年报原件或页码；不另写抽数引擎（用 0047 现成的）；不动 knowbase 先解析已有的那一段；不改调度的四档与按用户轮流。

## 四、迁移

- 第 1–5 步上线前，现在的 `source_query` 路照旧能跑；上线后新委托默认走描述，旧委托、已确认在队里的 Wind 作业照旧。
- `source_query` 路要不要保留给「作者方法里点名要某个供应商工具」的情况，第六节第 3 条定；不保留就在所有使用方锁升到不带它的版本后删（按 [0052](0052-contract-hygiene.md) 的退役做法）。

## 五、验收（照双轨 8.3、10.1 的做法）

用宁德时代 `300750.SZ` 2023—2025 年营业收入（合并、全年、当期原始披露）：

| # | 情形 | 要看到 |
| --- | --- | --- |
| 1 | knowbase 已有这几个数且本人有授权 | 不派作业，直接给 |
| 2 | 没有 | 先派给 Wind，写回 knowbase 后通知，需求方取到的每行标「取自 Wind」 |
| 3 | Wind 取不到（关掉它、额度为 0 或返回无数据） | 自动换巨潮下年报抽表，需求项留痕两次，取到的每行标出自哪份年报第几页 |
| 4 | 用户在确认页去掉 Wind | 只走巨潮 |
| 5 | 口径写「最新调整后」 | 取后一年年报里的「上年同期」那一栏 |
| 6 | Wind 与年报同一组样本 | 主体、口径、单位、数值逐个比，差异写原因（10.1 同等验收），对照过了才登记 |
| 7 | 两个渠道给的数不一样 | 两行都在，标「待核」 |

远程能跑的是三个后端的真库测试（假渠道）；Wind 真调用、页面要本地卡。
