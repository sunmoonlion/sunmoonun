## 一、现在的样子（2026-11-06 各仓头）

1. **knowbase 先解析已有的**，没有的才交 knowfeed。这一段对，不动。
2. **走不走 Wind 是模型定的。**knowbench 数据步的提示（`advisor.py` 1859 行起）写「Prefer an available supplier query (for example Wind) via source_query」；工具说明（`workbench_mcp.py` 205 行）教模型把 `source_query={channel,service,tool,arguments}` 写进需求。写了，这一项就**点名了供应商**，和 5.1 相反。先后（Wind 先）和所有者 11-06 定的一致，但写在提示词里，模型、提示一换，选源就变。
3. **Wind 和其它渠道是两条不相通的道。**knowfeed `Channel.covers`（`domain/supply/models.py` 436 行）：带 `source_query` 的项只有它点名的 Wind 渠道能供；不带的项 Wind 渠道一律不供。描述键里还拼了 `|query:`，两种项连身份都不同。
4. **按次序换源的机制其实已经有了**：渠道有 `priority`（管理端可调先后），`candidates` 按先后排、按用户确认的供给条件筛；一个渠道取不到，`_next_channel`（`application/supply/jobs.py` 1289 行）跳过 `tried_channels` 换下一个。只是因为第 3 条，Wind 取不到不会落到巨潮，巨潮取不到也不会去问 Wind。
5. **prematch**（`knowfeed-supply-prematch/v1`）确认前已经回每项的候选渠道、许可档、预计时间；确认快照 `supply.conditions.channels` 已能记用户接受哪些渠道。

## 二、做法：让 Wind 成为普通渠道，先后只看渠道优先级

不新建策略引擎。把第 3 条那道墙拆了，第 4、5 条现成的机制就成了「一处策略」。

| 步 | 改什么 | 在哪 |
| --- | --- | --- |
| 1 | 词表加一类**指标数值**：主体、期间、指标名（受控列表，如营业收入、归母净利润）、口径（合并/母公司、报告期/单季）。它只说「要这些数」，不说从哪来 | knowbase 词表（0049 第四节新一版），knowfeed、knowbench 跟锁 |
| 2 | **巨潮**登记能供「指标数值」：取对应定期报告原件，再按表格读法抽出这些指标（官方来源） | knowfeed 巨潮渠道配置；抽取用 knowbase 已有的表格读法 |
| 3 | **Wind 插件**登记能供「指标数值」：插件里有一张**指标名 → Wind 字段码、口径 → 参数**的映射表，描述能翻成一次 Wind 查询的才认。原件、按页、正文读法 Wind 一律不认（保住 PDF 原件链，双轨 10.1 末段） | knowfeed Wind 插件（`plugin = 'wind-mcp'`）配置与适配器；映射表随 W0 核实的字段逐条加 |
| 4 | `covers` 改成：Wind 渠道看「描述能不能翻成查询」；`source_query` 项照旧只认点名的渠道（旧委托、过渡期用） | knowfeed `domain/supply/models.py` |
| 5 | **先后 = 渠道 `priority`**，默认 **Wind 在前、巨潮等公告原件渠道在后**（所有者 11-06 定：官方下载太慢，官方保底），之后在管理端调；**取不到就换下一个**用现有 `tried_channels`；Wind 额度用完、返回无数据都算「这个渠道取不到」 | knowfeed，基本不用新代码 |
| 6 | prematch 出 v2：每项回**按先后排好的候选**，每个候选带**来源性质**（官方披露 / 供应商加工）和许可档 | knowfeed 契约 `supply-prematch/v2`（加法），knowbench、knowlab 跟锁 |
| 7 | knowbench 确认页照 prematch 的先后列出来源与性质，用户可去掉某个（写进已有的 `conditions.channels`），不能加没登记的 | knowbench 网页与 `expert_data.py` |
| 8 | knowbench 数据步：提示里删掉「Prefer … Wind」，`request_data` 默认不让模型写 `source_query`，指标类需求按第 1 步的描述提 | knowbench `advisor.py`、`workbench_mcp.py` |

换源时不越过用户确认过的东西：期间、口径、用途不变；只在用户留下的候选里按次序换。换到了哪个来源，需求项上留痕（`tried_channels` 与最终渠道），页面写明「这份数来自 Wind（供应商加工）」或「来自年报（官方披露）」。

## 三、不做的

不做跨渠道的「取最快的」「取最便宜的」打分；不让 knowbench 再知道有哪些供应商；不让 Wind 冒充年报原件或页码；不动 knowbase 先解析已有的那一段；不改调度的四档与按用户轮流。

## 四、迁移

- 第 1–5 步上线前，现在的 `source_query` 路照旧能跑；上线后新委托默认走描述，旧委托、已确认在队里的 Wind 作业照旧。
- `source_query` 路要不要保留给「作者方法里点名要某个供应商工具」的情况，第六节第 3 条定；不保留就在所有使用方锁升到不带它的版本后删（按 [0052](0052-contract-hygiene.md) 的退役做法）。

## 五、验收（照双轨 8.3、10.1 的做法）

用宁德时代 `300750.SZ` 2023—2025 年营业收入：

| # | 情形 | 要看到 |
| --- | --- | --- |
| 1 | knowbase 已有这几个数且本人有引用 | 不派作业 |
| 2 | 没有 | 先派给 Wind，拿到后进 knowbase |
| 3 | Wind 取不到（关掉它、额度为 0 或返回无数据） | 自动换巨潮下年报抽表，需求项留痕两次 |
| 4 | 用户在确认页去掉 Wind | 只走巨潮 |
| 5 | 同一需求另要年报原件 | Wind 不在原件那一项的候选里 |
| 6 | Wind 与巨潮同一组样本 | 主体、口径、单位、数值逐个比，差异写原因（10.1 同等验收） |

远程能跑的是 knowfeed 真库测试（假渠道）；Wind 真调用、页面要本地卡。
