## 一、要紧的（上线后难回头）

### Q-01 回填 SQL 的测试编号排序可能不稳定
- **在哪**：knowlab-backend 迁移 `20261024_0012`，`_backfill()` 里 INSERT INTO knowbot_test 的 ORDER BY
- **为什么**：用 `coalesce(d.run_started_at, d.updated_at), d.revision` 排序。如果两个准专家的 `run_started_at` 都是 NULL（例如开跑失败、从未真正启动），就退到 `updated_at`；同一事务里写的两条 `updated_at` 可能相同（Opus 顺手改的那条真库测试就是这个问题），这时 `d.revision` 决定顺序。revision 是准专家的修订号，不是测试编号的语义，可能不反映真实先后。
- **建议**：对 `run_started_at IS NULL` 的情况加一个兜底排序键（例如 `d.id`），确保回填结果确定性。部署前在现网数据上跑一遍核对编号是否合理。

### Q-02 令牌交换的 aud/azp 验证需要在认证中间件里确认
- **在哪**：knowbase-backend 的认证中间件（不在 `user_data_service.py` 里，服务层假设 owner 已经过验证）
- **为什么**：0042 的安全模型完全依赖 knowbase 能正确验证交换来的令牌的 `aud`（必须是 knowbase）和 `azp`（代办应用）。设计文档说「10-23 在临时 Casdoor 4.12.0 上实测通过」，但那是令牌交换流程的测试，不是 knowbase 端验证逻辑的测试。如果 knowbase 的认证中间件没有显式检查 `aud` 和 `azp`，那么一个发给别的应用的令牌也能访问 knowbase。
- **建议**：部署前必须确认 knowbase 的 JWT 验证中间件包含 `aud` 和 `azp` 的检查。建议 Opus 写一个集成测试：拿一个 `aud` 不是 knowbase 的令牌去调 knowbase，确认被拒。

### Q-03 证件照片存数据库 LargeBinary，备份与清理需确认
- **在哪**：knowmart-backend 迁移 `20261023_0007`，`publisher_document` 表的 `content` 列（`sa.LargeBinary()`）
- **为什么**：身份证正反面、营业执照、证照照片都是几百 KB 到几 MB 的图片，存在数据库里会让数据库备份膨胀。更关键的是：清理逻辑（`purge_after` 一年后 `purged_at`）是把 content 置 NULL 还是删行？如果只是置 NULL，行还在，`publisher_document` 表会越来越大。如果是删行，外键 `publisher_license.document_id` 设了 `ON DELETE SET NULL`，这是安全的，但需要确认清理逻辑确实做了。
- **建议**：明确清理策略——建议一年后把 `content` 列置 NULL（保留元数据用于审计），并在 sweep 定时任务里加一个「清理超过 N 天的已 purge 行」的步骤（或者不删，留作审计痕迹，但要确认存储量可接受）。

### Q-04 专家停用的跨应用一致性有窗口期
- **在哪**：knowlab-backend `knowbot_experts.py` 的 `stop` 方法；knowmart-backend 的停用接口
- **为什么**：设计是「先停 knowmart，停成了才记 knowlab」。如果 knowlab 记录失败（网络抖动、数据库暂时不可用），knowmart 那一版已经停了，但 knowlab 的专家状态还是「上架中」。重试是安全的（设计文档第 4 条也提到了），但中间这段时间：用户在 knowmart 看是停了的，在 knowlab 看还能动。
- **建议**：可以接受，但建议加一个对账机制——定时任务或管理端提供一个「同步 knowmart 停用状态到 knowlab」的按钮，运营发现不一致时能手动修。

## 二、值得改的（不影响上线，但拖着会有技术债）

### Q-05 栏目接口全量加载，性能隐患明确
- **在哪**：knowlab-backend `knowbot_board.py`（Opus 自己提到了，request 第 121 行）
- **为什么**：每次请求把所有创意的版本、受理单、准专家、测试、专家都取出来在内存里分。试行期量小没问题，但如果一个用户有几十个创意、每个创意有几个版本和多次测试，数据量会快速增长。`answered_by_user` 逐个查也是 N+1 问题。
- **建议**：本期可以不做，但建议在 `knowbot_board.py` 里加一个 TODO 注释标出性能边界（例如「创意数 > 50 或测试数 > 200 时需要下推到 SQL」），并在管理端加一个响应时间的日志，上线后观察。

### Q-06 运行授权的时限与业务场景的匹配
- **在哪**：knowbase-backend `domain/user_data.py`，`grant_expiry` 函数
- **为什么**：四种授权的时限：test 最长 26 小时、delegation 24 小时（设计文档说 7 天兜底，但代码里 `grant_expiry` 的默认值需要核实）、session 12 小时（设计文档说 24 小时）、incubation 6 小时。incubation 只有 6 小时的话，复杂的专家孵化可能不够——孵化过程中如果要反复读格式验证，6 小时可能中途断。
- **建议**：核实代码里的实际值与设计文档是否一致。incubation 建议至少 24 小时，或者改成「孵化任务的生命周期」而不是固定时长。

### Q-07 需求条目的生命周期没写完整
- **在哪**：knowmart-backend 迁移 `20261023_0007`，`demand` 表
- **为什么**：0018 第十一节第 2 小节说「卖家在期限内响应」，但 demand 表里没看到 `deadline`（期限）和 `status`（需求状态：开放、已选中、已关闭、已过期）的列。如果需求没有状态管理，买家发了需求后怎么关？卖家响应后买家不选怎么办？
- **建议**：如果本期确实不做需求的生命周期管理（只记一笔），建议在 design 文档里明确写「需求条目没有状态，买家手动关闭或定时清理」，避免上线后运营困惑。如果有 `status` 列但我没看到，请指出。

### Q-08 本地 link 的 `fs/digest` 向后兼容
- **在哪**：sunmoon-link `855655b`（0.5.2）
- **为什么**：0042 块 5 的请专家选数据，本地文件的 sha256 由 link 的 `fs/digest` 算。设计文档说「老 link 一块块读回来算」，但 knowbench 后端 `41596bd` 里的兼容逻辑需要确认：如果 link 版本太老不支持 `fs/digest`，回退路径是否真的能工作？回退路径的性能（大文件一块块读回来算 sha256）是否可接受？
- **建议**：在 knowbench 后端的兼容代码处加一个日志，记录有多少请求走了回退路径，以便推动用户升级 link。

## 三、小问题（改了更好，不改也行）

### Q-09 同意文字改了但版本号没升
- **在哪**：knowlab-web-frontend 的申请表；knowlab-backend 的同意版本逻辑
- **为什么**：Opus 自己提到了（request 第 119 行）：「分身」改「准专家」、「交付」改「上架」，但同意版本号仍是 2。意思确实没变，但用户对术语变化敏感。如果所有者认为这只是叫法对齐、不影响用户理解，那可以不升；如果担心用户困惑，可以升到 3。
- **建议**：待议。建议 Opus 在发版说明里记一句「同意文字微调但含义不变，版本号未升」。

### Q-10 market-sweep 的幂等性
- **在哪**：knowmart-backend `tasks/market.py` 的 sweep 定时任务
- **为什么**：每小时跑一次，做三件事：资质到期提醒、过期改回自用/下架、照片清理。如果 Celery worker 重启导致同一小时跑了两次，提醒会不会发两遍？照片清理如果是「置 NULL」操作，重复执行是安全的；但提醒邮件/消息发了两遍就不好了。
- **建议**：提醒操作加一个「已提醒」标记（`reminded_at`），重复执行时跳过已提醒的。照片清理操作确认是幂等的。

### Q-11 知识条目的 `items` 列是 JSONB，结构没约束
- **在哪**：knowmart-backend 迁移 `20261023_0007`，`knowledge_listing` 表的 `items` 列
- **为什么**：知识条目说「一份或一组资料」，`items` 是 JSONB 但没有 CHECK 约束限定结构。如果前端传一个空数组或格式不对的 JSON，后端不会拦。
- **建议**：加一个 CHECK 约束确保 `items` 是非空数组，或者在应用层验证。本期量小可以后补。

### Q-12 专家详情「需要的数据」显示的数据需求声明，格式校验在哪一层
- **在哪**：knowmart-backend `cf1cdbe`（清单外层加 `data_needs`）
- **为什么**：`data_needs` 每样有 key、名字、说明、格式、必填、份数范围等，合起来不超过 64 份。这个 64 份的上限是应用层检查还是数据库层？如果卖家在 knowmart 网页上手动改 JSON 绕过前端校验，后端能不能挡住？
- **建议**：确认 `data_needs` 的份数上限在后端有校验（不只是前端）。

### Q-13 168 的 Windows 沙箱补授读范围
- **在哪**：sunmoon-link `windowsSandboxRead.ts`
- **为什么**：给 `CodexSandboxUsers` 授读程序目录（node、app、用户 PATH），排除 `.ssh`、控制目录、codex-home。排除列表是否完整？如果用户把敏感脚本放在 PATH 里的某个目录，沙箱账户能读到。
- **建议**：Astra 更熟悉 Windows 沙箱，请 Astra 重点看这条。我只提一个方向：排除列表是黑名单，理论上不如白名单安全，但白名单可能太严。建议在文档里写明「已知限制：沙箱账户能读 PATH 里所有目录的文件」。

## 四、设计层面的观察（不是问题，是记录）

### O-01 0037 的「只增不缩」迁移策略是合理的
- 准专家上的旧字段（run_id、report、delivery 等）留着不写，等新流程跑稳再出收缩迁移。这降低了上线风险，我同意。建议收缩迁移在 0037 真跑通过后立即出，不要拖太久。

### O-02 0042 的四类知识库隔离是清晰的
- A/B/C/D 四类，真源各不同，互不读。这个设计在概念上很干净。唯一要注意的是「买来的知识复制一份进买家的 B 或 C」——这意味着同一份知识在 knowbase 里可能有两份（卖家的 D 和买家的 B/C），删除时要分别处理。设计文档已经考虑到了（0042 第四节「删了不影响已卖出的」），确认实现也是如此。

### O-03 供需市场的「本期不接支付」是正确的取舍
- 接支付涉及外部条件（商户号、托管、结算），不是纯技术问题。本期只标价、记成交，把支付留到后面，降低了本期复杂度。建议成交记录的 schema 设计时就把支付字段留好（哪怕本期全是 NULL），以后接支付时不用改表。

### O-04 发版顺序的依赖链需要严格执行
- knowbase → knowmart → knowbench → knowlab。这个顺序是因为：knowbase 先上令牌交换和运行授权；knowmart 上清单格式和供需市场；knowbench 上数据钉住和选数据；knowlab 最后上迁移和两端重做。如果顺序错了，例如 knowlab 先上但 knowbase 还没上令牌交换，knowlab 的知识库搬家就会失败。建议在发版卡里写明每一步的验证点（例如「knowbase 上完后，验令牌交换能通」）。

## 五、总结

Opus 这次工作量很大（11 个子仓、42 个提交在父仓），涉及数据结构大改（0037 四张新表、0042 用户资料体系、0018 供需市场）和跨应用契约变化。整体设计思路清晰，「只增不缩」的迁移策略、分区隔离、令牌交换的安全模型都是合理的。

最要紧的四个问题（Q-01 到 Q-04）建议在发版前解决或确认：
1. 回填 SQL 的确定性排序
2. knowbase 认证中间件的 aud/azp 验证
3. 证件照片的存储与清理策略
4. 跨应用停用一致性的对账机制

其余的可以排进后续迭代。
